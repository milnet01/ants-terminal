# Release Standards — v1

**Status:** v1 (2026-08-08).

**Why a rule here reads as it does: [`docs/history/releases.md`](../docs/history/releases.md).**
Pedigree only — what a rule used to say and what changed it. A dated
measurement a rule rests on stays in the rule.

**Purpose: so that a released version is one thing — the same version
number, the same contents and the same description everywhere it
appears.**

Every rule here traces to that sentence. A release is the moment a
project stops being private work and becomes something other people
depend on, and almost every release defect is one of its descriptions
disagreeing with another.

Governs ROADMAP bullets with `Kind: release`. Everyday commits, branches
and tags are [commits.md](commits.md); this file starts where a version
is being cut.

---

## 1. One version number, everywhere

A version appears in more places than anyone remembers: the build
files, the packaging metadata, the README, the roadmap, the changelog,
sometimes an about-box string.

**This section owns where the number is written. It does not own which
number to pick** — that is [versioning.md](versioning.md), which covers
what makes a change breaking, `0.x`, pre-release suffixes and when a
number may move at all.

- **Enumerate the version-bearing files once, and record the list as the
  project's release recipe** — at the path and in the dialect the release
  tool fixes, which owns both, and **name that tool here or the pointer
  resolves to nothing**: on this machine it is `cut-release`, whose format
  contract is `skills/cut-release/references/bump-recipe.md` — rather than
  rediscovering it under release
  pressure, or writing the list somewhere no tool reads.
- **A release changes all of them or none of them.** A half-bumped
  repository builds and ships, and reports the wrong version to whoever
  is debugging it.
- **Verify after bumping, mechanically.** Anything that reads the list
  and reports a mismatch. A human re-reading the list is the check that
  passes right up until it matters.

## 2. The changelog entry is the release description

The changelog section for a version is the single description of what
shipped. Everything else — the release commit body, **the annotated
tag's body**, the published release notes, any announcement — is that
text, not a fresh summary of the same work.

The tag was added to that list 2026-08-18 (ROADMAP CFG-0143).
[commits.md](commits.md) §1.4 exempts both the release commit body and
the tag body from its 72-column wrap on the ground that both are this
text copied verbatim, and cited this section for it — which enumerated
the commit body and not the tag. §4 below requires the tag be annotated
without saying what it carries, so the tag half of that exemption rested
on `commits.md`'s own sentence. It now has a source here.

**Two descriptions of one release will disagree**, and the one users
read is the one nobody checked.

- Each entry cites the ROADMAP IDs it covers, so a reader can get from
  "what changed" to "why it changed".
- Entries are written as the work lands, under an unreleased heading,
  and are moved into a dated section at release time. Written afterwards
  from a commit log, a changelog records what was easy to reconstruct
  rather than what mattered.
- **Say when a release contains a security fix.** Users on the previous
  version cannot decide to upgrade if they are not told.

## 3. The release commit

- Subject carries the version rather than a ROADMAP ID — the release
  aggregates many tracked items into one shipping point, so no single ID
  fits. The bullets inside its body still cite their IDs.
- Body is the changelog section for that version.
- Touches the version-bearing files, the changelog, and the roadmap
  statuses this release makes true.

## 4. Tags

- **Annotated, never lightweight.** A lightweight tag carries no message
  and no tagger, so the release loses the one piece of metadata that
  says what it was.
- **Never force-push a tag.** A tag people have already fetched will not
  update for them, so the same name comes to mean two different commits.
  On a collision, stop and ask.
- **Nothing is published from a tag whose checks have not passed.** A
  tag is cheap to create and expensive to retract once fetched.
  **Where the repository runs no checks on the release tag, this gate is
  satisfied by whatever run does cover the release commit** — a branch
  run counts — **and where nothing covers it at all, the publish step
  proceeds.** So this clause lifts the wait for a *tag-triggered* run
  that will never appear; it does not let a red branch run through, which
  §7 forbids by name and §6 step 8 waits for. It is **wider than**
  `commits.md` §4.1's *"any repository with no CI at all"*: a repository
  whose CI runs on a branch push and never on a tag is inside it, and
  waits for that branch run.
  Without this clause a tool built
  from §6 either waits forever for a run that will never appear or
  publishes on the ground that nothing has failed. Two tools, one
  hanging and one shipping, from one sentence.
- **Push the release tag with the commit it names, not separately and
  not later.** Send the annotated tags reachable from what you are
  already pushing — `git push --follow-tags` — rather than a bulk push
  of every local tag, which publishes ones never meant to leave the
  machine. A tag that exists locally and nowhere else is a release
  nobody can fetch, and §6's publish step will publish from it anyway.
  **One case is exempt: a repository with no remote.** There the local
  tag is the end state and the publish step skips silently.

The push rule above is stated here rather than in
[commits.md](commits.md), which owns everyday tags and defers release
tagging to this section.

## 5. Publishing

- **Notes are the changelog section, verbatim**, for the reason in §2.
- **Preserve the markdown.** Notes passed through shell quoting lose
  their formatting; use a form that hands the text over untouched.
- **Do not upload a second, separately built set of artifacts.** Two sets
  of binaries for one release, with nothing to tell them apart, is worse
  than none. **The ban is on a rival build, not on every asset** — one
  produced by the project's own release scripts is part of the release,
  and withholding it publishes an incomplete one. The stable alias below
  is a second *copy of the same bytes* and is exempt by construction.
- **Publish a stable alias beside the versioned artefact, on a stable
  release only.** GitHub's one direct-download URL is
  `/releases/latest/download/<exact-filename>`, so a name that changes every
  release leaves a project with no permanent link to offer, only a *page*.
  Upload a second copy of the same bytes under a version-less name. **The
  versioned filename stays the artefact of record**: version-less alone
  leaves two downloads indistinguishable, so no
  bug report traces to a build and nobody can pin one. **Not on a
  candidate** — `latest` never resolves to a prerelease, so the alias is
  unreachable there, and an unversioned RC binary invites the mix-up a
  separate candidate channel exists to prevent. **Scope: a project that
  publishes downloadable artefacts**; a library or a docs repository has
  nothing to name.
- **Publishing is irreversible in practice.** Deleting a release does
  not un-fetch it. Confirm before **each** publish of a version,
  candidates included; never after.

## 6. Order

The sequence exists because each step can invalidate the one before it.
**It is the order of a STABLE cut.** A candidate does not date the
changelog heading — an undated one is that flow's own state — and
carries its suffix at the tag, the release title and the artifact
filename only, never in a version-bearing file
([versioning.md](versioning.md) § 5). It also publishes no stable alias —
§5 puts that on a stable cut only. Every other step is unchanged.

1. Move the unreleased changelog entries into a dated section.
2. Update roadmap statuses this release makes true.
3. Bump the version everywhere, and verify mechanically.
4. Build and test **from the bumped tree** — not from what was tested
   before the bump.
5. **If the repository has a CI pipeline, run it locally from that same
   tree** —
   [local-gate.md](local-gate.md), which requires the local run and the
   remote run to share one list of steps — the repository's own gate
   script, which `ci.yml` also calls, or `act` executing
   `.github/workflows/*.yml` where the pipeline cannot be inverted.
   Step 4 does not discharge this: a project's own build and test is not
   that shared list, and `local-gate.md` § 3 calls a script the workflow
   does not call a mirror, worse than no mirror. **A release is never
   docs-only**, so its documentation mode and its narrow skip cannot apply
   whatever the diff looks like. Its other
   relief does: where a job genuinely cannot run on this machine, cover
   what you can and write down which jobs you could not.
6. Commit.
7. Tag, annotated.
8. **Push without asking, on every repository that has a remote, public
   or private**, and wait for checks where the repository runs any. With
   no remote there is nothing to push and §4's exemption applies. A release push is
   neither batched nor gated on a confirmation —
   [commits.md](commits.md) §4.1 owns why.
9. Publish, with the changelog section as the notes — **confirming first,
   per §5.**

Building before bumping tests a tree that will never be shipped.

**The local pipeline run sits before the commit, not before the push.**
The tree is byte-identical either way, and a failure found at step 5
costs an edit — found after step 7 it costs an amended commit and a
moved tag, which §4 forbids doing to a tag anyone has fetched.

**The changelog and the roadmap come before the bump, not after.** A
release tool refuses to bump until a dated changelog section exists with
content and every ROADMAP ID it claims shipped is already ✅ — so a
sequence that bumps first stalls at its own step 1. **Two branches
qualify the changelog half, and neither touches the roadmap half.**
Where the recipe closes `[Unreleased]` itself, that cut is part of the
bump and the pre-flight passes; on a candidate cut the date is not yet
owed.

## 7. Anti-patterns

- ❌ Bumping some version-bearing files and not others.
- ❌ Re-summarising the changelog for the release notes.
- ❌ Writing the changelog from `git log` at release time.
- ❌ A lightweight tag for a release.
- ❌ Force-pushing a tag after a mistake.
- ❌ Publishing before checks have passed.
- ❌ Hand-uploading a second, separately built set of artifacts — §5's
  stable alias excepted, being the same bytes under a fixed name.
- ❌ A silent security fix.

## What checks this

| Rule | What catches a breach |
|---|---|
| One version everywhere (§1) | **`Partial:`** `cut-release` Phase 1c runs the recipe's `post_check`, a version-drift check over the version-bearing list — **and only where the recipe carries one**, which the recipe format makes optional. A recipe without a `post_check` leaves §1 caught by nothing. **It reads the recipe**, so a version-bearing file the recipe never names is invisible to it — and **that half is caught by nothing**. Corrected 2026-08-25 (CFG-0175); this deferred to [versioning.md](versioning.md) § 7's row, which answers a different question — a line that must NEVER move, absent deliberately and missing its reason |
| Changelog entry exists for the version (§2) | `cut-release` Phase 0e, a stop-gate. **Missing or empty always stops**, before the bump. **Undated stops a stable cut only** — `--pre` lifts it. **And where the recipe closes `[Unreleased]` itself the pre-flight passes**, the check moving to Phase 1c's `post_check` after the bump. §6 states the same two branches. Corrected 2026-08-25 (CFG-0175); the unqualified form was fixed in §6's prose and left standing here, which is the failure §6's own fix pass exists to catch. **Not** the changelog file at rest, which [changelog-format.md](changelog-format.md) says nothing validates |
| Tag is annotated (§4) | the repository — `git` reports the tag's type |
| Checks passed before publish (§4) | the host's own status |
| Notes match the changelog (§5) | **nothing mechanical** — compared by hand |
| Publishing is confirmed first (§5, §6 step 9) | `cut-release` Phase 6 asks, and it is the one confirmation that run still makes. **It asked once per version until 2026-08-25** — so a second candidate, and the stable cut after it, published unprompted; corrected there with this row (CFG-0175). Each publish is separately irreversible, which is the whole of §5's reason |
| Checks have passed before the publish (§4, §6 step 8) | `cut-release` Phase 6 waits for whatever run covers the pushed commit, and a red run stops it. **Added there 2026-08-25 (CFG-0175)**: until then the skill went from the push straight to the publish, so the one conformer this table names breached §4 on every release |
| A stable alias is published beside the versioned artefact (§5) | **`Partial:`** `cut-release` Phase 6 reads the release back and counts its assets, so a release that should carry artefacts and carries none is caught. **A release carrying the versioned file and no alias passes that count** — the alias is checked by name only where the recipe names it, and nothing verifies that it is the same bytes |
| Release description is honest (§2) | **nothing mechanical** |
| The release push is unprompted (§6 step 8) | **nothing** — no check reads the tool's phases against this step. `cut-release` Phase 5 did breach it, prompting once before pushing a private repository, and was corrected 2026-08-19 (ROADMAP CFG-0144) to push on every repository and quote the CI cost rather than ask for it. That was found by loops 2 and 3 of the gate below rather than by anything standing, which is what the empty catcher means: the next divergence has nothing to catch it either |
| Pipeline run locally before the commit (§6 step 5) | **`Partial:`** `cut-release` Phase 2b performs it, added 2026-08-19 (ROADMAP CFG-0144); a red run stops the release before anything is committed. **It covers step 5 where the workflow calls a repository-owned script — `local-gate.md` § 3's own inversion — or where `act` is present.** With workflows, no inversion and no `act`, the phase does not run and names what went uncovered. Corrected 2026-08-25 (CFG-0175); this named a gate script as covering when Phase 2b carried no such branch, and that branch was added to the phase in the same change. **No `pre-push` hook covers step 5 whatever it runs** — it fires after the commit and the tag, and step 5 sits before both. **So a project not using this skill is checked by nothing here**, its own gate script included, because nothing runs that script before the commit. Corrected 2026-08-25 (CFG-0175); the row gave a second, incompatible reason — what `~/.claude/githooks/pre-push` happens to run — whose closing clause implied a gate script alone covered step 5 |

The rows reading **nothing** are this standard's honest error budget.
**The table names the rules that have a check to discuss, not every rule
in the document** — §3, §4's force-push and tag-push bullets and §6's
ordering appear in no row, and their absence is not a claim that anything
catches them.

**The changelog row is where the pointer rule has an edge, and it is worth
stating.** [documentation.md](documentation.md) § 2.1 requires a row about
machinery *another document owns* to cite that document rather than restate
its coverage — so on 2026-08-14 this row became a bare pointer to
`changelog-format.md`, replacing a copy that claimed a changelog is parsed.
But that document owns the changelog **file's shape**, not the **release
gate**: it correctly answers *nothing validates a `CHANGELOG.md` at rest*,
and this rule is caught anyway, by the release tool refusing to bump. A bare
pointer therefore told a reader nothing catches this when something does.
Corrected the same day (ROADMAP CFG-0107); the rule that settles it —
*point at the document that owns the machinery, not the subject* — is
[documentation.md](documentation.md) § 2.1's, stated there.
