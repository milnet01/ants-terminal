# Versioning Standard — v1

**Status:** v1 (2026-08-20).

**Purpose: so that a version number tells a reader what upgrading will
do to them.**

Every rule here traces to that sentence. A version is the only thing
about a release that everyone sees and nobody reads twice, so it has to
carry its meaning without a paragraph beside it.

Governs **which number to pick, and when it moves**. Where the number is
written, and the order a release is cut in, is
[releases.md](releases.md); other people's version numbers are
[dependencies.md](dependencies.md). This file has no `Kind:` of its own —
the decision it governs is made during `implement`, `fix` or `refactor`
work and is only *recorded* by `Kind: release`.

---

## 1. Principles

1. **A version is a promise to whoever upgrades.** Everything below is a
   way of keeping it.
2. **The level is decided from the change, never computed from the
   history.** A number derived from the tag list or the commit count
   makes *"is this breaking?"* unanswerable by construction, and that
   question is the whole point of the number.
3. **A number moves when something is released, and at no other time.**
   A version that moves with every commit is a build counter wearing a
   release marker.
4. **The surface a version protects is whatever a user can rely on**,
   which for most projects here is not an imported API. Read §3 before
   assuming SemVer's own wording covers you.

## 2. Which number to bump

**Every project follows [Semantic Versioning
2.0.0](https://semver.org/spec/v2.0.0.html).** This is not a preference
being stated for the first time — every conforming `CHANGELOG.md`
already publishes it in its header fence
([changelog-format.md](changelog-format.md) §4.1). This section is what
that promise means, so that a reader can tell whether it is kept.

**Every level below is the `1.0`-and-after ladder. Inside `0.x`, §4 shifts
whatever this section returns down one**, so read them together or a `0.x`
project cuts `1.0.0` for its first breaking change.

- **A change is breaking if a user, or an integrator, who upgrades has
  something that used to work stop working.** Nothing about imports,
  nothing about type signatures. It is the only definition that reads
  the same for a library, an app, a CLI and a site.
- **MAJOR** for a breaking change. **MINOR** for something a user can
  now do that they could not before, and for marking something
  deprecated. **PATCH** for everything else.
- **Bump one component and reset the ones to its right.** `1.4.7` with a
  breaking change is `2.0.0`, never `2.4.7`.
- **When MINOR and PATCH both look right, ask: did I add something a
  user can now do that they could not before, or mark something
  deprecated?** Yes is MINOR. No is PATCH. The doubt is nearly always
  this one, and it has a mechanical answer.
- **A security fix that only fixes is a PATCH. A security change that
  adds a feature is a MINOR.** Hardening usually arrives as both — a
  hole closed and a control added — and the feature half is what a user
  sees. This case is got wrong repeatedly because the *severity* of the
  work argues for a larger bump than the *change* does. Severity is not
  a version level.
- **The changelog already contains the answer. Read it as three ordered
  tests over the whole `[Unreleased]` section, not as a table of
  categories.** First: does any entry, in any category, stop something
  working? MAJOR. Then: does any entry add something a user can now do,
  or mark something deprecated? MINOR — SemVer 2.0.0 clause 7 requires
  the deprecation half. Otherwise PATCH. The level is therefore derivable
  from work already recorded, rather than argued about under release
  pressure. **Ordered tests rather than a lookup, because a lookup keyed
  on the six category names is wrong the moment an entry's category does
  not match its effect** — a `Security` line that removes a permissive
  default is breaking, and a `Fixed` line can be too.

## 3. Breaking, when nothing imports you

SemVer is written for something other code imports. Most projects here
are not that, and *"the public API"* has no referent for an app, a CLI
tool, a game or a site — which is how a breaking change comes to be
shipped as a patch in good faith.

- **Each project names its own breaking surfaces, once, in
  `docs/standards/versioning-overrides.md`** — the case-2 file
  [README.md](README.md) § The three cases already defines, and the only
  path a merge or an audit can be told to open. **It is the one override a
  project otherwise following the global set still writes**, because it is
  not a delta arguing with a rule — it is the answer this standard
  deliberately refuses to supply, and the list is therefore what differs.
  **§ 4 puts a `0.x` project's `1.0` exit condition in the same file on the
  same ground**, and it is an answer rather than a delta for the same reason.
  The usual candidates: a
  command's flags and its output shape, a config file's keys, a save-file
  or database schema, a URL someone has bookmarked, a plugin or theme
  interface, a keyboard shortcut people have in their fingers.
- **Do not copy another project's list.** The shape generalises and the
  contents do not, so this standard supplies the question and each
  project answers it. A borrowed list is a list nobody has checked
  against the thing it describes.
- **A surface nobody wrote down is still a surface.** If a user relies
  on it and it stops working, the release was breaking whether or not
  the list mentioned it. The list exists to make the common cases cheap,
  not to bound the promise.

## 4. Zero-dot-x

`0.x` is where SemVer suspends its own guarantees, so every reader
assumes something different unless the project says otherwise.

- **A `0.x` project states in one line what would make it `1.0`, in
  `docs/standards/versioning-overrides.md` beside its breaking
  surfaces.** An exit condition, checkable by someone else — *"MAJOR
  stays 0 until X is feature-complete against the roadmap's Phase 2
  goals"*. Not a feeling about maturity.
- **A `0.x` project with no such line is not deliberately `0.x`.** It is
  a project whose leading zero has gone inert, and its version has
  stopped saying anything at all. The visible symptom is a long release
  history under a `0.` prefix that nobody has revisited.
- **Inside `0.x` the levels shift down one, and both cases are stated
  because either alone is ambiguous.** A breaking change bumps the MINOR
  and resets the PATCH. **Everything else — a new capability included —
  bumps the PATCH.** Suspended guarantees are not an excuse for an
  arbitrary number.
- **No check may push a `0.x` project onto the `1.0` ladder.** A level floor
  written for the ladder above reads an `### Added` entry as MINOR, which is
  correct there and wrong here. `cut-release` skips its floor while MAJOR is
  `0` (CFG-0238). **If some other check stops a correct PATCH, the PATCH
  stands** — bumping the MINOR to get through it publishes a number this
  section calls wrong and spends the `1.0` runway to satisfy a check.

## 5. Pre-release suffixes

- **One spelling: `-rc.N`, where `N` is a decimal integer starting at 1 with
  no leading zeros.** Dot-separated identifiers are SemVer's own
  form, and they compare numerically where `-rc10` sorts before `-rc2`.
  Pick a different one and two projects' tags stop sorting the same way.
- **The suffix lives at the tag, the release title and the artifact
  filename. It never enters a version-bearing source file.** The recipe
  format defines the extracted value as the version triple, so a suffix in
  a source file is not rejected — it is silently half-read the next time the
  version is extracted. **What the lockstep check makes of it is the
  project's own `post_check`, which this standard does not own**: it may
  report the mismatch or miss it, and neither follows from this rule.
- **A pre-release is therefore tagged, not bumped.** The version-bearing
  files carry the plain triple the cycle is working toward; the suffix is
  added where the tag, the title and the artifact name are written, and
  nowhere else. **The sanctioned route is `cut-release --pre rc.N`**, which
  keeps the target argument a bare triple and appends the candidate to the
  tag and the release title, and to no version-bearing file. `cut-release` does not
  name artifacts; the project's own release scripts do, and this bullet is
  the rule they follow.
  Amended 2026-08-20 (CFG-0179): until that landed there was
  no route that *advanced* a candidate, and this bullet routed the whole flow
  outside the tool — by hand or by a project's own RC script, which is still
  what a project not using the skill does. A recipe's `tag` template is a free
  string, so `"tag": "v{NEW}-rc.1"` also puts a suffix on the tag alone, but
  it pins the candidate number in the recipe and has to be hand-edited before
  every cut; the recipe format now says not to.
- **A release tag whose triple carries a `-` suffix publishes as a
  pre-release; a plain triple publishes as latest.** The tag is the string
  this is decidable from; the version-bearing value never carries a suffix,
  so keying the decision off it would publish every candidate as latest.
  **A tag that is no version triple at all is not a release, and this rule
  does not reach it** — § 6's `phase-1` and `checkpoint-2026-08-25` carry a
  `-`. Corrected 2026-08-25 (CFG-0240); *"any tag carrying a `-` suffix"*
  was unanchored in exactly the way § 6 warns a triple scan against.
- **Everything that is not the tag, the release title or the artifact
  filename carries the plain triple — the changelog heading included.**
  Whether it enters the recipe at all is
  `skills/cut-release/references/bump-recipe.md`'s and `cut-release` Phase
  0e's: a body still to be written is a todo case and stays out of
  `files`; a section only to be closed may be a `files` entry, and being
  one is what lets the pre-flight pass. `cut-release` matches its pre-flight
  against a `## [<NEW>]` heading carrying the plain triple.
  **A final release needs it dated. Under `--pre` that stop is lifted, so
  dated or undated both pass** — an undated heading is the candidate flow's
  own state, not a requirement of it. A heading carrying `-rc.2` stops
  **either** cut. Corrected 2026-08-25 (CFG-0240), twice: this read
  *"`CHANGELOG.md` is not a recipe-bumped file"*, which sent a recipe author
  into a Phase 0e stop on every cut; the first repair then called the
  changelog *"not bumped in lockstep"* four lines above the sentence letting
  it into `files`, which is the lockstep set.
- **A README badge the recipe lists carries the plain triple, like every
  other listed file. A prose "latest release" line names the last stable
  version, and moves only on a stable release.** The two are different
  fields and a pre-release separates them: the badge is lockstep state, the
  prose line is what a reader should install. **The recipe does not move it
  at all** — a `files` entry and a todo both fire on a candidate cut, and
  this line names the last *stable* version. So it moves by hand, on the
  stable cut. Corrected 2026-08-25 (CFG-0240) three times: this prescribed a
  `todos` entry the recipe format forbids, then deferred the mechanism to a
  file that supplies no route, then gave an unconditional rule a reason that
  held only where a badge put the file in `files`.

## 6. When a number moves, and who moves it

- **A version bump belongs to a release and to nothing else, and a
  candidate cycle counts as one.** The bump that precedes an `-rc.N` tag
  belongs to the release that cycle is working toward. Not to a merge,
  not to a commit, not to a nightly build. **A bump staged and left
  uncommitted has not moved anything** — `cut-release --bump-only` stops
  exactly there, so running it breaches nothing; committing that tree
  without cutting the release is the breach this bullet names. A number that
  increments per code change tells a reader nothing about upgrading,
  which is the one thing §1 asks of it.
- **A project versions from its first release, and not before.** Until
  something is published there is nobody to make a promise to, and an
  invented number in a repo that has never shipped is a claim about a
  history that does not exist. **Seeding the number is part of cutting
  that first release**, not versioning before it — the release tool reads
  the old version out of a file and stops if it cannot, so the file has to
  carry one by the time the first release runs. **The first release names its
  version literally rather than stepping from the seed**, so the seeded value
  never reaches a published number and two projects seeding differently still
  publish the same first version.
- **"No consumers" is not an exemption once you have released.** The
  changelog and the future maintainer are the consumers; both read the
  number, and both are misled by a wrong one.
- **A person picks the level. A tool may compute the string.** Once a
  person has named `patch`, `minor` or `major`, deriving the next triple
  from the current one is arithmetic and should be automated. Deriving
  the *level* from the tag list, the commit count or the diff size is
  the failure §1's second principle names.
- **A non-release tag must not be spellable as a release version.**
  Where a repository tags phases, milestones or checkpoints alongside
  releases, **those tags carry a prefix AND no version triple at all** —
  `phase-1`, `milestone-3`, `checkpoint-2026-08-25`. A prefix alone is not
  enough: an unanchored `[0-9]+\.[0-9]+\.[0-9]+` scan matches inside
  `phase-1.2.3`, and this standard cannot know which scans a project's
  tools run. Otherwise the tag namespace stops answering *"what has been
  released?"*, and every tool that reads it inherits the ambiguity.

## 7. Version lines that are not the project's version

Some numbers in a repository look like the project's version and are
not. They must never move with it.

- **A config, state or database schema version** moves when its own
  format changes, which is on a different clock from the release.
- **A bundled or vendored component's version** is that component's,
  and the project does not get to bump it.
- **An upstream constant kept for compatibility** — a `VERSION` a file
  format or a protocol requires — is the upstream number, whatever it
  resembles.
- **Each of these is deliberately absent from the release recipe, and the
  recipe says why.** An unexplained absence reads as an omission, and the
  next person auditing lockstep adds it. One line of why, in the file the
  auditor already has open. **The form is
  `skills/cut-release/references/bump-recipe.md` § Notes'**, this file's
  header having handed recipe questions to [releases.md](releases.md).
  Corrected 2026-08-25 (CFG-0240); the form was stated here and nowhere the
  recipe author reads.

## 8. Anti-patterns

- **Shipping a breaking change as a patch because the diff was small.**
  §2's definition is about what stops working, not about how much was
  written.
- **Bumping MAJOR for a big release.** Marketing weight is not a version
  level. A release can be enormous and MINOR.
- **Bumping PATCH for a security fix that also added a control.** §2's
  carve-out exists because severity argues one way and the change argues
  the other.
- **Sitting on `0.x` with no stated exit.** §4 — the number has gone
  inert and nobody has noticed.
- **Bumping on every code change.** §6 — that is a build counter.
- **Spelling the pre-release suffix any other way.** §5 — the tags stop
  sorting.
- **Putting the suffix in a source file.** §5 — it is half-read at the
  next extraction.
- **Computing the level from history.** §1 — it answers the question by
  refusing to ask it.
- **Arguing the level out at release time from a record nobody kept.**
  §2's last bullet — reading it off the `[Unreleased]` entries at release
  time is the prescribed route, not the anti-pattern.

## 9. A project that already has its own versioning document

**Fold it into this one rather than keeping two.** A rule stated in two places
is two rules that will disagree ([documentation.md](documentation.md) § 2.1),
and the project's copy is the one that goes stale.

**One test decides every rule in it: would this be true of any project on this
machine?** Yes — it is this file's, and the project's statement of it becomes a
pointer here. **Where this file does not already state it, adding it here is an
edit to a machine-global standard** — gated, and taken only on the bar below,
before the project's copy is reduced to a pointer.

No — it names something only that project has, and it stays the project's.
**It does not stay in the old file, and nothing named `versioning.md` survives
the fold**: a file left beside this one is the second document this section
exists to remove. **Where this standard names a home, the content moves there**
— the breaking surfaces and a `0.x` exit condition to
`docs/standards/versioning-overrides.md`, which § 3 calls the only path a merge
or an audit can be told to open and which `README.md`'s carve-out covers by
name; the version-bearing file list to the release recipe
([releases.md](releases.md) § 1). **Where it names none — a release cadence —
§ 9 does not route it**, and it goes wherever that project keeps its own
practices.

**What the test has already sorted**, from the fleet survey this standard was
built from (CFG-0173):

- **This file's:** minor versus patch, the user-facing definition of breaking,
  the security carve-out, the changelog-category inference, the reset mechanic,
  independent version lines, the pre-release suffix spelling, and both
  *requirements* below.
- **Two items split, and the shape is the same both times: the requirement is
  this file's, the answer is the project's.** § 4's `1.0` exit condition, and
  § 3's list of breaking surfaces. Both answers live in the override file.
  Corrected 2026-08-25 (CFG-0240); this said *one*, and § 3's requirement was
  in neither list.
- **The project's:** its own list of breaking surfaces — § 3 asks for exactly
  that — its `1.0` exit condition, its release cadence, and its
  version-bearing file list,
  which is [releases.md](releases.md) § 1's rather than this standard's.

**A project that MECHANISES the decision keeps the half § 6 sanctions.** A
tool that computes the version *string* once a person has named the level is
arithmetic, and § 2's breaking test is written for a person to apply — no
category name answers *what stopped working*. **Its MINOR test has a
mechanical floor, and `cut-release` Phase 0e runs it.** That mechanism stays,
and this file is what it must *agree with* rather than what replaces it — a
disagreement there is a finding about the mechanism. Corrected 2026-08-25
(CFG-0240); calling all three tests unrunnable by a script told a merger to
delete the only mechanical coverage § 2 has, which this file's own
What-checks row counts.

**A mechanism that derives the LEVEL from the tag list, the commit count or
the diff size is the failure § 1's second principle names, and folding is the
moment to remove it.**

**This section does not reach a project standard that shares no headings with
this one.** `README.md` § The three cases calls that a case-3 document — read
instead of the global file of that name, and **correct**. § 9's subject is a
document that argues with this one, never one that merely shares its topic.

**The bar is `README.md`'s: a rule this file does not state is added here only
when a second project would use it unchanged** — never on generality alone.
A one-project rule goes to the home this section names above, and where it
names none, wherever that project keeps its own practices. One project's
rules living in one project is the right outcome rather than debt. Corrected
2026-08-25 (CFG-0240); this sent every such rule to the override file, which
`README.md` § The three cases limits to what differs plus the two answers
§ 3 and § 4 ask for.

**Nothing dispatches the merge.** `adopt-project` names the project's
versioning document beside its verdict and stops there, because deciding the
split means reading the document and that is the audit it does not do. Whoever
performs the merge performs it by this section.

**And no skill owns it yet, deliberately.** Two projects need it today, and
[coding.md](coding.md) § 1.3's Rule of Three says to wait for a third. Decided
by the user 2026-08-20 (CFG-0174).

## What checks this

| Rule | What catches a breach |
|------|----------------------|
| §2 — the level matches the change | **nothing.** `cut-release` takes `<X.Y.Z\|patch\|minor\|major>` as an argument and validates the string's shape, never whether the level matches the change. Calling a breaking change a patch release is caught by a person or not at all. This is the honest state of every project surveyed on 2026-08-20, and it is why §2 is written as a decision procedure rather than as a preference |
| §2 — the changelog implies the level | **Partial:** `cut-release` Phase 0e stops a PATCH whose LOCATED `## [<NEW>]` section — dated for a final cut, dated or undated under `--pre` — carries an `### Added` or `### Deprecated` heading (CFG-0180, decided by the user 2026-08-20). **A floor, not a verdict:** it cannot catch a level that is too HIGH, and it cannot catch a breaking change filed under `Fixed` — the failure that matters most. The breaking test is not mechanical: it asks what stopped working, which no category name answers. **And it is scoped to the `1.0`-and-after ladder**, skipping itself while MAJOR is `0` (CFG-0238) because §4 makes an `### Added` entry a correct PATCH there — so below `1.0` this row's rule is caught by nothing at all |
| §3 — a project names its own breaking surfaces | **nothing**, and nothing tracks it either. `CFG-0174` runs the other way — it merges a project's *existing* versioning standard up into the global one, and records that the surfaces list stays project-local. No item asks a project that has never written one to write it |
| §4 — a `0.x` project states its `1.0` condition | **nothing.** A leading zero is not a signal any tool reads |
| §5 — the suffix stays out of version-bearing files | **Partial:** `cut-release`'s target validation, an argument-shape check — `^[0-9]+\.[0-9]+\.[0-9]+$` rejects a suffixed target, so the tool cannot introduce one *through its argument*; `--pre rc.N` (CFG-0179) carries the candidate as a separate value that reaches the tag and the release title and no version-bearing file, so the sanctioned route cannot introduce one either. Corrected 2026-08-25 (CFG-0240); this said *"the tag text only"*, which § 5's own second bullet contradicts. **Not covered:** a suffix written into a source file by hand, or baked as a literal into a recipe's `files[].replace` template, which the tool then writes for you. Worse than absent there — a recipe's `version_pattern` captures the triple, so the value comes back truncated at the next extraction. **What the lockstep verify makes of it is the project's own `post_check`, which this standard does not own** and which may report the mismatch or miss it |
| §6 — the number moves only on a release | **nothing.** `cut-release` is the sanctioned route, but taking it does not make a bump a release: `--bump-only` runs the bump and stops, leaving a bumped tree uncommitted and untagged — which §6 permits, and which nothing then stops anyone committing. A hand edit to a version-bearing file is uncaught as well, and is the form this breach usually takes |
| §6 — a non-release tag is not spellable as a version | **nothing** — no pass reads the tag namespace |
| §7 — an independent version line is absent from the recipe, with a reason | **nothing** — the recipe *can* hold the reason, in a `$`-prefixed comment key, and nothing reads those keys back. A missing one is caught by a person auditing lockstep or not at all |
| §9 — a project's own versioning document is folded in | **nothing.** `adopt-project` names the document when it sees one and stops; whether the merge then happens, and whether it split the rules by §9's test correctly, is read by a person or not at all |
| Where the version is written, and that all copies move together | **Pointer** — [releases.md](releases.md) §1 owns lockstep and names `cut-release`'s recipe as its mechanism. Not restated here; one number with two homes is what that section exists to prevent |
