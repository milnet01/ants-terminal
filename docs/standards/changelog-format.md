## 4. CHANGELOG.md format spec

A conforming project keeps a Keep-a-Changelog-style
`CHANGELOG.md` at the repo root. The format is defined at
<https://keepachangelog.com/> and pinned here as a sub-spec.

### 4.1 Structure

```markdown
# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- New feature.

### Fixed
- Bug fix.

## [X.Y.Z] - YYYY-MM-DD

**Theme:** one-line summary of the release.

### Added
…

### Changed
…

### Deprecated
…

### Removed
…

### Fixed
…

### Security
…

## [X.Y.Z-1] - YYYY-MM-DD
…
```

**A dated release heading takes an ASCII hyphen, not an em dash** —
`## [X.Y.Z] - YYYY-MM-DD`. This repo's prose uses em dashes everywhere else, so
the hyphen looks like a slip. It is not. `changelog_log op:"release"` writes it,
and Keep a Changelog uses it. **Do not "correct" it back.**

**Published em-dash sections conform. Do not rewrite them.** This standard
prescribed the em dash until 2026-08-20 (CFG-0152). The rule binds headings
written from that date.

**Only the writer is bound. A consumer matches either dash and lets the date
decide** — as `cut-release` Phase 0e does.

**It does not reach the feature-grouped `### <date> <Category> — <headline>`
subsection.** That em dash is what its writer emits.

**The flat category structure in the fence above is the only `[Unreleased]`
shape this standard permits.** The writer verb also
supports a *feature-grouped* `[Unreleased]` — `###` subsections that are dated
topics rather than categories, written by `changelog_log op:"add_subsection"`
— and **a project under this foundation does not use it.** Ruled out
2026-08-12 (CFG-0073) rather than specified: one shape is what lets a reader,
a parser and § What checks this all bind to the same structure.

**So: do not call `op:"add_subsection"`.** It writes the shape this standard
does not permit.

**A `[Unreleased]` that is already feature-grouped is converted by moving its
topics out and then writing flat.** Not by cutting a release: executed
2026-08-20, `op:"release"` carries the dated-topic headings into the dated
section verbatim, so the shape is relocated rather than removed — and § 4.2
binds every dated section too. Do not hand-write a flat block beside a dated
topic either: the verb's own refusal says a mixed section locks the file, and
executed 2026-08-20, `op:"add"` against one succeeds — so nothing stops the mix
and nothing reports it.

**This is a scope decision, not a judgement about the layout.** Executed
2026-08-20: `op:"add_subsection"` refuses `flat_section` against a flat
`[Unreleased]`, and `op:"add"` refuses `feature_grouped_section` against a
dated-topic one, naming the shape that section uses. **Both refusals need
existing `###` headings to fire, so an EMPTY `[Unreleased]` is unguarded** —
and § 4.3 step 2 leaves one empty after every release. One call there still
converts the project silently, so the exclusion rests on the author rather
than on the verb (CFG-0172).

**Re-decided 2026-08-20 by the user, and kept.** The verb's guard becoming
symmetric was this rule's own trigger to revisit it, and it was revisited. Two
reasons to keep it, and neither is the one it was written under: the one-shape
argument above does not depend on the tooling at all, and the empty-section
hole is a live author-side reason. Lifting it would first have to answer what a
release does to a dated-topic `[Unreleased]` (CFG-0073), which nobody has
defined. **The trigger is spent** — do not reopen this on the strength of the
guard alone.

### 4.2 Conventions

- `[Unreleased]` block at the top, **always** — even if empty.
  The ROADMAP viewer reads it for current-work signaling per
  `roadmap-format.md` § 3.6.2.
- Dated sections in **reverse chronological order**.
- `**Theme:**` line is one sentence; sets the release's
  character.
- Bullets categorical: Added / Changed / Deprecated / Removed / Fixed /
  Security. Don't invent new categories. **That is also the heading order, in
  `[Unreleased]` and in every dated section.**
- Bullets terse — **one line, plus at most one indented continuation.**
  Anything longer goes in the commit. **This one is entirely on the
  author**: `changelog_log`'s `body` takes up to 4000 characters and
  writes as many continuation lines as it is given, and
  `add_from_roadmap` reuses the roadmap bullet's `Layman:` line by
  default. Neither enforces a limit, so "I wrote it through the verb" is
  not evidence of conformance.
- **Cite ROADMAP IDs** in bullets when applicable: `- live search
  filter (ANTS-1042).` under `### Added`. The category is the heading,
  never repeated in the bullet. The bidirectional link helps readers
  move between the changelog and the roadmap.

### 4.3 Release flow with ROADMAP integration

When a release ships:

1. `[Unreleased]` block contents move to a new dated section
   `## [X.Y.Z] - YYYY-MM-DD`, **and its `**Theme:**` line is written.** The
   theme is not carried over — § 4.1's fence puts it in every dated section and
   in no `[Unreleased]` block, so there is nothing to move, and
   `changelog_log op:"release"` does not author one either. Somebody writes it
   at this step or the section ships without it.
2. Empty `[Unreleased]` section is left at the top (with an
   empty-state hint or just the heading).
3. ROADMAP bullets that were 🚧 flip to ✅.
4. Released ROADMAP block changes from `(target: YYYY-MM)` to
   `shipped (YYYY-MM-DD)`.

**All four steps are the author's on a file-backed project** — see the
store-backed carve-out below for steps 3 and 4. **Except where the bump recipe
calls `changelog_log op:"release"`: that verb closes `[Unreleased]` into the
dated section and opens a fresh empty one above it, so it performs steps 1 and
2.** It authors no `**Theme:**` line, so step 1's second half stays the
author's on every route. `cut-release` carves out the same split at Phase 0e —
*"Unless the recipe performs the cut itself — then 0e passes."*

**Absent that recipe step, `cut-release` performs none of them, and checks
two.** Its Phase 0e stops unless a **dated** section for the new version
already exists with content, and its Phase 0f stops on any ROADMAP ID the
section claims shipped that is not ✅. Neither check is an edit, and on no
route does the skill draft a section or flip a bullet: where `[Unreleased]`
moves inside a run, the recipe's verb moves it.

**Until 2026-08-13 the predecessor did neither.** `/release` never read or wrote
a roadmap at all — a `grep -c 'roadmap'` over its `SKILL.md` returned 0, checked
2026-08-12, the file since deleted — and its step 2 would dispatch `changelog-writer` to draft a missing
section from the commit range, which § 7 of `releases.md` names an anti-pattern.
`cut-release` dropped that dispatch and claimed step 3 as a check; charter 17
required one or the other. The first run found the case immediately: a 0.7.105
changelog bullet claiming ANTS-4065 shipped, against a roadmap still holding it
🚧 (`~/.claude/docs/cut-release-first-run-2026-08-13.md`).

**On a store-backed project** (`roadmap-format.md` § 3.12), steps 1–2 are unchanged —
`CHANGELOG.md` is not generated. **Step 3** is a roadmap edit and goes
through the store's write verb, which mutates the store and re-renders;
editing the rendered file by hand loses the change at the next render.
**Step 4 is not yet performable** — `roadmap-format.md` § 3.12 owns that and says why.

## What checks this

**Almost nothing, and that is the honest summary.** `roadmap-format.md`'s
half of the original document is checked hard because a parser binds to it.
This half is checked mostly at write time, inside `changelog_log`, or not at
all.

**Read the rows; this section does not summarise them.** Every gloss written
here went stale when the next row landed. `documentation.md` § 2.8 item 3.

| Rule | What catches a breach |
|------|----------------------|
| § 4.1 the dated heading's ASCII hyphen | **Almost nothing.** `cut-release` Phase 0e matches either dash on purpose. A bump recipe's `post_check` may grep `^## \[$V\] - `, but `post_check` is optional, so a project without one catches nothing |
| § 4.1 structure | Partial: `changelog_log`'s `add` / `add_from_roadmap` / `add_batch` write the flat shape. **Nothing** validates a hand-edited changelog at rest — `format_mismatch` fires on a *YAML* changelog and `no_changelog` on a missing one, neither on a malformed Markdown one |
| § 4.1 nobody calls `op:"add_subsection"` | **Partial, and the gap is the state this standard leaves after every release.** The op refuses `flat_section` against a flat `[Unreleased]`, and `op:"add"` refuses `feature_grouped_section` against a dated-topic one. Both need existing `###` headings, so against an **empty** `[Unreleased]` the op writes and **nothing** catches it. A hand-written dated topic is caught by nothing either. Exercised 2026-08-20 |
| § 4.2 bullets terse — one line plus at most one continuation | **nothing.** `body` accepts 4000 characters and writes as many continuation lines as it is given; `add_from_roadmap` adds one by default. No op counts lines |
| § 4.2 the six categories, and no invented ones | `changelog_log`'s own enum, for every op that takes a category. A hand-added `### Notes` heading is accepted by every reader |
| § 4.2 the heading order | `op:"normalize"`, and **only inside `[Unreleased]`** — nothing orders a dated release section, so one written out of order stays that way. **And nothing calls that op**: no skill, hook or recipe here invokes it, so it runs only when someone does by hand |
| § 4.2 bullets cite ROADMAP IDs where applicable | **nothing** — an uncited bullet is well-formed, and the bidirectional link this rule exists for simply is not there |
| § 4.3 step 1 — a dated section exists with content | `cut-release` Phase 0e, which stops the release — **unless the recipe performs the cut itself, when 0e passes and the check moves to the recipe's `post_check`, which is optional**. It reads for readiness, not format: any dash, and it does not check the section's internal shape |
| § 4.3 step 3 — bullets flipped to ✅ | `cut-release` Phase 0f, which stops on any ROADMAP ID the section claims shipped that is not ✅ |
| § 4.3 step 2 — `[Unreleased]` was actually emptied | **nothing** — a changelog whose `[Unreleased]` was never emptied looks exactly like one with nothing unreleased |
| § 4.3 step 4 on a store-backed project | **`roadmap-format.md` § 3.12**, which owns why it is not yet performable |
