# ANTS-3636 — `doc_citations`: resolve a doc's `path:line` citations and return the cited text

**Status:** spec draft, cold-eyes loops 1–6 folded, then consolidated per
`documentation.md` § 1.5–1.6 (2026-07-26). Loop 7 pending.
**Kind:** implement.
**Source:** ROADMAP.md ANTS-3636 (OneUp_Ants_MCP_Feedback.md, 2026-07-26 addendum).
**Blocked by:** ANTS-3649 (hoists `MarkdownScan::codeSpans` out of
`DocIntegrity::maskInlineCode` and adds the `fenceMask` unclosed-opener
overload — the two primitives § 2.3 and § 2.5 consume; INV-44 moved there).
**Composes with:** ANTS-3601 (`doc_integrity` — shares the fence primitives),
ANTS-1637 (`codebase_index` — the basename→path map).
**Pairs with:** ANTS-3596, which hardened `docs/specs/ANTS-2161.md` by hand —
converting its § 2.2–§ 2.4 approximate anchors to symbol references, while
deliberately leaving the loop log's historical line citations in place
(`ROADMAP.md:19474`). This verb generalises the motivation, not the fix.
**Blocker for:** ANTS-3642 (request-side `expect` map), ANTS-3643 (corpus-wide
digest mode).

**Layman:** Design docs are full of "see `file.cpp`, line 200" pointers that rot
silently as code moves; this adds one call that looks every pointer up and shows
what is on those lines today.

---

## 1. Problem

Global rule 13 requires every doc claim naming a file, line, function, or
constant to be checked against live source rather than recalled. `/cold-eyes`
runs that check on every loop, for every reviewer, on every doc. There is no
verb for it, so it is done by hand or skipped — and when it is skipped, the
loop ratifies a stale line number and the next reader is sent to the wrong
place.

The reporting session (OneUp) hit this directly: verifying one spec meant
resolving 33 `updater.py:NNN` citations, and they wrote a throwaway Python
script because no verb existed. `read_regions` is the closest fit but takes a
hand-extracted list of `{path, start_line, end_line}` — and extracting that
list *is* the tedious part.

**The corpus is large enough that hand-verification does not scale.** Measured
2026-07-26 over `docs/`, excluding this spec, by the commands below — recorded
inline because three cold-eyes loops caught unverified counts in this very
table, and a number without its command is the kind of claim this verb exists
to catch. Two scans with different regexes run here, so each row names its own
denominator. One caveat applies throughout: **the greps do not skip fenced
blocks and the verb does** (§ 2.3), so the table over-states the real harvest by
about 2% — 42 of scan P's 1,935 tokens sit inside a fence.

| Shape | Count | Of what |
|---|---:|---|
| `path.ext:N` citations (scan **P**) | 1,935 in 167 docs | — |
| …carrying a directory component (`src/foo.cpp:12`) | 551 | 28% of scan P |
| …**bare basename** (`foo.cpp:12`) | 1,384 | **72% of scan P** |
| Line **ranges** (`:208-228` or en-dash `:208–228`) | 673 | 35% of scan P |
| Multi-locus / open-ended (`:262/265/286`, `:5669+`) | 38 | 2% of scan P |
| Approximate (`:~752`) | 10 | <1% of scan P |
| Citations opening a code span (`` `foo.cpp:12` ``) — scan **S** | 1,791 | — |
| …preceded by an identifier code span (§ 2.5) | 388 | 22% of scan S |
| Bare continuations (`` `:548-549` ``, path inherited) | 727 in 78 files | own scan — **not** in scan P (no dotted path to match) |
| …themselves preceded by an identifier code span | 138 | 19% of continuations |
| **Anchorable total** — 388 + 138 | **526** | **20% of everything the verb harvests** |

```bash
E='--include=*.md --exclude=ANTS-3636.md'
P='[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:[0-9]+'
grep -rhoE "$P" docs/ $E | wc -l                      # scan P total    1935
grep -rhoE "$P" docs/ $E | grep -c '/'                # with directory   551
grep -rhoE "$P(-|–)~?[0-9]+" docs/ $E | wc -l         # ranges           673
grep -rhoE "$P(/[0-9]+|\+)" docs/ $E | wc -l          # multi-locus       38
grep -rhoE '[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:~[0-9]+' docs/ $E | wc -l   # approximate 10
grep -rhoE "\`$P" docs/ $E | wc -l                    # scan S          1791
C='`:~?[0-9]+(-|–)?~?[0-9]*`'
A="\`[A-Za-z_][A-Za-z0-9_:]*\`[^\`]{0,40}"
grep -rhoE "$A\`$P" docs/ $E | wc -l                  # anchored         388
grep -rhoE "$C" docs/ $E | wc -l                      # continuations    727
grep -rhoE "$A$C" docs/ $E | wc -l                    # anchored conts   138

# tokens the greps see but the verb will not (§ 2.3) — 42
find docs -name '*.md' ! -name 'ANTS-3636.md' -print0 | xargs -0 awk '
  FNR==1 { infence=0 }
  /^[ ]{0,3}(```|~~~)/ { infence = !infence; next }
  infence { n += gsub(/[A-Za-z0-9_.@+\/-]+\.[A-Za-z]{1,5}:[0-9]+/, "&") }
  END { print n }'
```

**Anchorable total, worked.** The verb harvests scan P plus the continuations,
less what fences hide: `1,935 + 727 − 42 ≈ 2,620`. Of those, 388 + 138 = 526
carry a checkable anchor — **20%**.

Both are bounds in the same direction: the awk counts only *path-bearing* fenced
tokens, so fenced **continuations** stay in the 727 and are never subtracted.
**2,620 is a ceiling and 20% a floor.** Left uncorrected because an exact
fence-aware count is only obtainable from the implementation this spec
describes, and a verification tool should err toward under-claiming its own
coverage.

Densest single doc: `docs/specs/ANTS-1750.md`, 56 citations over 7 distinct
targets. Largest: `ROADMAP.md` at **27,046 lines on 2026-07-26 and growing
monotonically**, 673 of them carrying a citation-shaped token. That 673 counts
*lines*, not occurrences — the only figure here that does, since the
`docs/`-scoped scans never touch `ROADMAP.md`; its equality with the range row
is coincidence. § 5's guard sizing must read the line count as a floor.

Three consequences follow, and they shape the design:

1. **Existence checking is not enough.** A citation that has drifted onto an
   unrelated statement still points at a line that exists; only the cited *text*
   exposes that, which is why the text is the load-bearing output rather than an
   option. A live instance found while writing this spec:
   `docs/specs/ANTS-2090.md` claims `isFieldProjectionTool` gates
   `compactEnvelope` at `mcpprojection.cpp:28`, but that line is today blank —
   it falls between the close of `terseDefault()` and the ANTS-3550 hint-latch
   comment block, with `claimHint()` the next function. Every existence-based
   check passes; the claim is false. Tracked for repair as ANTS-3641.
2. **Bare basenames are the common case, not an edge case.** A resolver that
   only handled repo-relative paths would silently skip ~72% of the corpus —
   worse than no verb, because the empty result reads as "all clear".
3. **No mechanical signal covers most citations.** Only ~20% carry a nearby
   identifier the verb can check the text against (§ 2.5), and the remainder
   splits two ways: *resolved and shown but not judged*, and not shown at all —
   per consequence 2 and § 2.4, a bare basename outside the indexed roots
   resolves nowhere and lands in `unparsed[]`. Neither group may be mistaken for
   a verified one, and they need different fields to say so: `unchecked` and
   `counts.unparsed` (§ 2.1).

## 2. Surface

### 2.1 Verb shape

New verb `doc_citations`, **not** a mode on `doc_integrity`: that verb's
contract is a *defect list* (`findings[]` + `counts{}` narrowed together by
`kinds` — ANTS-3601 INV-18, `RemoteControl::docIntegrityBuildResponse`), while
this one *enumerates every citation with its text*, most of them healthy.
Folding an enumeration into a findings verb would either break `kinds`/`counts`
or bury the payload. They share only `MarkdownScan`'s fence and code-span
primitives (§ 2.3).

The nearer neighbour is `FeatureCoverage::runContractDocDriftCheck` — the
`contract_doc_drift` audit lane — and the two are complementary.
`contract_doc_drift` asks *does this identifier exist anywhere in the repo*;
this verb asks *does the line this doc points at still say what the doc
claims*. Neither subsumes the other: § 1's `mcpprojection.cpp:28` case passes
`contract_doc_drift` cleanly, because `isFieldProjectionTool` does still exist
— just not there. A divergence recorded, not a duplication to resolve.

Request:

```jsonc
{
  "caller_cwd":       "<required>",       // CallerCwdContract::Required
  "path":             "docs/specs/ANTS-2090.md",  // required, a FILE
  "only":             "all" | "stale",    // default "all"
  "offset":           0,                  // 0-based index into the post-filter list
  "max_range_lines":  3,                  // per-citation; every numeric argument
  "max_bytes":        131072,             // clamps to the range its § 2.7
  "max_doc_lines":    20000,              // `Options` field documents
  "etag_match":       "<opt>"
}
```

**That is the whole request surface.** Every other bound in this spec is an
engine-side `Options` default with no request argument, because each guards the
engine rather than shaping the caller's view. **§ 2.7's `Options` block is the
single source of every limit's value and clamp; no prose in this spec restates
one.** A bound named anywhere here but absent from that block is a
specification defect — a literal an implementer must invent and a test cannot
vary.

Clamping lives in the handler (`docCitationsClampOptions`, § 2.7), never in the
engine, so a unit test's direct engine call is not silently re-clamped; `offset`
alone has no upper clamp, since that bound is `count`, which the handler has not
computed (INV-21, INV-38).

**Out-of-domain values coerce; they do not refuse.** An unrecognised `only`
becomes `"all"`; a wrong-typed numeric falls back to its default rather than to
a clamp endpoint. This keeps INV-18's refusal set at exactly five by giving
every other malformed input a defined destination, and it errs toward the
unfiltered view — the safe direction for a verb whose failure mode is
under-reporting drift.

`path` must name a single **file**:

| `path` | Outcome |
|---|---|
| absent or empty | refuse `missing_field` |
| escapes the project root | refuse `bad_path` |
| a directory | refuse `bad_args` |
| in-root, does not exist | `ok:true`, empty `citations[]` |
| exists, but unreadable / over `maxDocBytes` / not UTF-8 | refuse `read_failed` |

Two rows diverge from `doc_integrity` deliberately, and are called out because
the verbs run in the same review loop where a silent difference is a caller
trap. It **accepts** a directory and walks it (ANTS-3601 INV-16); this verb
refuses, because its payload is per-citation *text* and `docs/` holds 1,935
citations (§ 1) — the refusal names the file-only requirement and points at
ANTS-3643's sweep mode. `bad_args` is the closest generic fit, not an exact one
— minting a code for one verb is not worth amending `mcp-error-codes.md` for.
The empty-result row matches `doc_integrity` (ANTS-3601 INV-15) rather than
refusing — companion verbs should answer a typo'd path the same way.

An undecodable **doc** ends the call, where an undecodable **target** is a
per-row `read_error`: a target that fails to decode costs one row, a doc that
fails to decode leaves nothing to enumerate.

`dry_run` does not apply — the verb writes nothing (INV-16). `path` need not be
`.md`; any UTF-8 text file is scanned, and § 6's "non-markdown inputs" non-goal
is about the *workflow*, not an input guard.

Response. **A synthetic fixture, not a live capture** — every field is derivable
from the rules below by inspection, so it cannot rot the way a captured example
in *this* spec would. Six citation-shaped tokens (anchored-and-matching, a dead
file, an ambiguous bare basename, an anchor that no longer matches, an
unanchored one, and a prose false positive), called with `only:"stale"`:

`only` and `offset` echo their post-clamp values, so a page saved to a file or
handed to another session can say which slice of which view it is (the
`workspace_search` precedent).

**`basename_index_size` is the number of distinct basenames** —
`Options::basenameIndex.size()`, not the file count, since 14 files named
`bad.cpp` occupy one key. Measured 2026-07-26 **from the index's own cache**,
not from a hand-rolled directory walk (the walk's file set is the index's, so
guessing at it produces a number that does not reproduce):

```bash
python3 -c 'import json,glob,os
for p in glob.glob(os.path.expanduser("~/.cache/ants-terminal/codebase-index/*.json")):
    d=json.load(open(p))
    if "Ants_Terminal" not in (d.get("root_canonical") or ""): continue
    f=[x["path"] for x in d["files"]]
    print(len(f), len({os.path.basename(x) for x in f}))'   # → 762 730
```

So **762 indexed files collapse to 730 keys** — the field is the map's size
because that is what governs whether ladder step 2 can answer. That 730 and the
14-way `bad.cpp` collision above are the block's **only live measurements**; the
same command confirms the collision is the repo's largest today, so an
implementer sees the candidate cap fire on a condition this repo actually
contains. Every other field is derivable from the rules by inspection.

The JSON is the tool's payload; the dispatcher applies the standard ANTS-1294
`<ants_mcp_data>` wrap (`mcp-tools.md` step 5) with no special handling.

**Field emission.** `ok`, `truncated` and per-citation `anchor_found` are
**always emitted, including when false** — `anchor_found:false` is the drift
signal this verb exists to produce and what `only:"stale"` selects on, so a
blanket omit-when-false rule would delete it. (`anchor_symbol` and
`anchor_found` are still absent *together* when there is no anchor at all,
§ 2.5: "absent" and "false" are different answers.) `candidates_total` is
emitted whenever `candidates[]` is.

Every other **flag** is omitted when false: per citation `range_truncated`,
`end_clamped`, `inherited_path`, `approximate`, `partial`, `text_clipped`,
`text_escaped`, `truncated_candidates`; per `unparsed[]` entry `raw_clipped`;
top-level `basename_index_truncated`, `read_budget_exhausted`, and
`unterminated_fence` (absent, never `0`). At 400 citations the eight per-entry
flags would otherwise cost 3,200 always-false keys on a verb whose premise is
frugality.

**Every truncation sets a flag** (INV-28) — silently shortened output is the one
thing a verification tool must never emit.

**Tallies**, checked against the fixture above. The six `status` keys partition
`count` (`3+1+0+0+1+0 = 5`). `anchor_missing` and `unchecked` are **overlays on
the `ok` subset**, not statuses — an anchor whose needle was not found, and no
anchor at all (shown, never judged) — so `counts.ok` = anchored-and-found +
`anchor_missing` + `unchecked` (`3 = 1+1+1`). `counts.unparsed` mirrors
`unparsed_total` and sits **outside** `count`. `count` and `counts` are whole-doc
(pre-`only`, pre-`offset`) over the scanned prefix; `returned` is the emitted
length (INV-26).

`counts.unchecked` is the honesty field, and its **denominator is `counts.ok`,
not the document** — "how much of what I showed you did I judge", 1 of 3 in the
fixture. § 1's ~20%-anchored figure is a different ratio over a strictly larger
population — "how much of what exists could ever be judged" — and the two must
not be read as one. `counts.unparsed` covers the other shortfall, which
`basename_index_size` explains: a cold codebase index (§ 2.7) pushes bare
basenames, ~72% of the corpus, into `unparsed[]`, and a reader who cannot see
that the index was empty would read the shortfall as a clean doc.

`only:"stale"` keeps every non-`ok` citation plus every `ok` one with
`anchor_found:false` (INV-14). `counts` stays unfiltered, so a caller reading
only the filtered list is misreading rather than mis-served.

This is the ROADMAP bullet's `stale[]`, reshaped as a filter over one array plus
unfiltered counts so the healthy majority stays addressable in the same call,
and broader than the bullet's "missing or out of range" — it keeps anchor drift
too. The bullet's sketch keys are renamed: `cited_path` → `path`, `cited_line` →
`start_line`, and the boolean `exists` → the six-valued `status` (a boolean
cannot separate a dead file from an ambiguous basename from a line past EOF).

**Order is document order** — ascending `doc_line`, then ascending column of the
citation's first character; `unparsed[]` likewise (INV-33). `offset` paging is
only meaningful over a defined order, and INV-29 mandates two separate entries
for two citations on one line.

**The emission caps bound what is emitted, not what is examined** (INV-42): the
bound on *work* is `max_doc_lines` plus the line cache, the bound on *response
size* is `max_bytes`. Two consequences, both chosen. Because INV-16 forbids
cross-call state, paging re-resolves and re-reads the whole doc on every page —
cheap at the corpus's densest doc, 56 citations over 7 targets. And **paging is
not atomic**: each page is an independent resolution of the doc
*as it is at that moment*, so if the doc or a cited target is edited between
calls, an entry can be seen twice or missed entirely and `count` can move.
Callers needing a consistent view raise `max_bytes` and take one page; callers
that page compare `count` across pages and restart if it moved. The alternative
— a server-side snapshot with an expiry contract — is far more machinery than a
56-citation worst case justifies.

**`unparsed[]` is never filtered by `only`, never trimmed by `max_bytes`, and
has no pagination.** Its bounds are `maxUnparsed` and per-entry `maxRawChars`
(§ 2.7), which together keep it small enough that `max_bytes` never needs to
touch it. When `maxUnparsed` binds, `unparsed_total` still reports the true
count, so the loss is *countable* even though no `offset` retrieves those
entries. If that array ever needs paging, that is ANTS-3643's digest shape.

`offset` pages the post-filter list and **is applied before the emission caps**:
filter by `only`, drop the first `offset` entries, then fill the page until a cap
binds. That is what makes `next_offset == offset + returned` correct and every
entry reachable — under the reverse order nothing past `maxCitations` could ever
be fetched. `next_offset` is emitted **exactly when a resumable cap dropped
trailing entries** (the `roadmap_query` / `workspace_search` precedent), so
`truncated:true` has three flavours that it alone does not separate:

| Cause | `next_offset` | How to tell | Resumable by paging |
|---|---|---|---|
| `maxCitations` / `max_bytes` | emitted | `next_offset` present | yes |
| `max_doc_lines` | absent | `scanned_lines < doc_lines` | no — raise `max_doc_lines` |
| `maxUnparsed` | absent | `unparsed_total > unparsed.length` | no — that array has no paging |

Both `next_offset`-absent cases carry their own evidence field, which is why
those two fields are always emitted. A caller treating `truncated:true` as one
condition mis-handles two of the three.

**`fields=` and `raw:true` are not adopted.** Both are optional in
`mcp-tools.md`, and `doc_integrity` is likewise absent from
`mcp::isFieldProjectionTool`; `only` + `offset` cover this verb's narrowing at a
fraction of the surface, and raw mode's verbatim-bytes frame
(`mcp::isRawEligible`) is the wrong shape for a structured envelope in which
file text is one field among many.

The dispatcher-injected `etag` (`mcp-tools.md` step 7) hashes the **response**,
so an unchanged etag means every field the response *reports* is unchanged —
verdicts included, since `anchor_found` is computed over the full resolved range
(§ 2.5) rather than the clipped `text`, so a tail edit that flips a verdict does
change it. It does **not** mean the cited files are unchanged: an edit inside the
unshown tail that changes no reported field leaves the etag equal. Read it as
"my answer is the same", never "the target is the same".

### 2.2 Citation grammar

Matching is two-stage: a permissive **recognise** pass finds token boundaries,
then a **validate** pass decides whether the token is a citation or a
`bad_locus`. This is not decoration — a single strict production cannot report
what it fails to match (see the locus bullet below).

```
--- stage 1: recognise (what the scanner matches) -------------------
token        := path ":" rawlocus trailing?
continuation := codespan( ":" rawlocus trailing? ) // path inherited (sticky rule below)
path         := "/"? seg ( "/" seg )*              // last seg must contain a "."
seg          := [A-Za-z0-9_.@+-]+
rawlocus     := "~"? D [ ("-" | "–") "~"? D ]      // hyphen or EN DASH
trailing     := ( "/" "~"? D )+ | "+"              // extra loci, dropped (partial)
D            := [0-9]+                             // greedy: the WHOLE digit run

--- stage 2: validate (citation, or unparsed[]/bad_locus) -----------
A recognised token is a citation iff every D it kept satisfies
    1 <= value(D) <= 9999999   and   len(D) <= 7
and, for a range, start <= end. Otherwise → unparsed[], reason "bad_locus".
```

Five constraints that are part of the grammar, not commentary on it:

- **A continuation must fill a whole inline code span.** `` `:45` `` is a
  continuation; the `:45` inside `09:45`, `3:1`, or `INV-3:` is not. Without
  this rule the § 2.3 raw-line scan would harvest every clock time and ratio in
  the corpus, inherit an unrelated path, and emit *the real text of that file's
  line 45* under `status:"ok"`. The delimiters are what make a continuation
  authored rather than coincidental, and all 727 corpus continuations are
  written that way; a citation *with* a path needs no such guard, since prose
  punctuation cannot produce a path. `codespan(…)` is `MarkdownScan::codeSpans`,
  and "fills" is tested against the span's content **after CommonMark's
  one-space strip**, so `` ` :45 ` `` counts — matching what a renderer shows
  the author. A span containing a newline never does.
- **`raw` is the matched token without its delimiters.** `` `:45` `` yields
  `raw:":45"`, and `` `src/a.cpp:2` `` yields `raw:"src/a.cpp:2"`. The
  backticks are grammar, not content.
- **`doc_line` is the line the citation's own first character sits on**, which
  matters only for the rare span that crosses a newline (§ 2.7): such a span has
  a start line and an end line, and the citation inside it takes whichever line
  its own text begins on, not the span's. Same rule for `unparsed[]` entries.
  Stated because the § 2.1 sort order and every fixture assertion key on
  `doc_line`, so an ambiguous case would make two implementations order
  differently.
- **The dot must be in the final segment.** `src.old/README:12` does not parse
  (no dot in `README`); `docs/specs/ANTS-2161.md:5` does. The dot stands in for
  "names a file", and a directory component's dot says nothing about the leaf.
- **A locus is 1–7 digits, so up to 9,999,999** — 370× this repo's largest file.
  **The two-stage split exists for this rule specifically.** The obvious
  single-stage spelling `[0-9]{1,7}(?![0-9])` is safe but silent: against
  `src/a.cpp:99999999999999` it matches *nothing*, so the token is neither a
  citation nor an `unparsed[]` entry and no field reports it — it vanishes
  exactly as the `~:N` gap below does. Stage 1's greedy `D` takes the whole run
  and stage 2 rejects it as `bad_locus`: identical safety (no truncated line
  number becomes a citation, no over-large value reaches an `int`) with the
  reporting recovered. The same two stages let `:0` and `:10-5` be reported —
  both recognise cleanly and fail only validation.
- **`trailing` is exhaustive.** Only further `/`-separated loci and a single
  `+` are absorbed and reported as `partial:true`. Every other character ends
  the token, so the `.` closing a sentence in ``see `src/a.cpp:12`.`` is
  ordinary punctuation and sets no flag. A `~` on a *dropped* trailing locus
  (`:262/~265`) is dropped with it — `approximate` reflects the first locus
  only.

Further rules:

- **En dash is not optional.** The corpus writes both `:208-228` and
  `:208–228`; a hyphen-only regex loses a large minority of the 673 ranges.
- **Trailing loci are dropped, not guessed.** `:262/265/286/300` and `:5669+`
  parse as their first locus with `partial:true` (38 occurrences, ~2%).
- **`~N` sets `approximate:true` and changes nothing else.** It is an echo so a
  reader can see the author hedged. Status is computed identically for tilde
  and non-tilde loci — there is no fuzzy-match tolerance, because there is
  nothing to be tolerant *against* (10 corpus occurrences, <1%).
- **Malformed loci are not citations.** A locus of 0, an end below its start, or
  a digit run longer than 7 → `unparsed[]` with `reason:"bad_locus"` (stage 2).
  None of the three occurs in the corpus today (all measured at 0); the rule
  exists so the read path never receives arguments it would refuse, and so that
  when one does appear it is *visible* rather than dropped.
- **Known unsupported spelling: `~:N`** (tilde *before* the colon, as in
  ``remotecontrol.cpp `~:11985` ``). **10** such tokens across 4 files
  (`grep -rhoE '~:[0-9]+' docs/`, counted as tokens not lines), and `ROADMAP.md`
  ANTS-3596 names the class by that spelling. They match neither `citation` nor
  `continuation`, so they are invisible — absent from `count` *and* from
  `unparsed[]`. Admitting them would mean a second approximate form throughout
  the grammar for 10 tokens; the gap is measured, stated, and tracked as
  **ANTS-3646**.
- **Two citations on one doc line are two entries**, as are two occurrences of
  the same citation. `count` is occurrences, not distinct targets; the line
  cache (§ 5) makes the repeat free.
- **Sticky path.** A bare continuation inherits from the most recent
  **antecedent** earlier in the same document: the most recent entry that
  reached `citations[]` with a status other than `unresolved`. An `unparsed[]`
  entry is never an antecedent; a continuation is itself eligible to become the
  next one.

  **`inherited_path:true` means "this entry's target came from an antecedent
  rather than its own text", and is set whenever an antecedent was found** —
  including the ambiguous case, where what is inherited is the candidate set
  rather than a path. It is **not** set on an `unresolved` continuation, which
  found nothing to inherit and is identified by its status alone. So the flag
  never appears on an entry whose target is unknown.

  **Only the antecedent's resolved `path` is inherited** — the continuation runs
  the read step itself and takes its own status. A `missing_file` antecedent
  followed by `` `:2` `` yields a second `missing_file`; an `ok` antecedent whose
  continuation cites past EOF yields `out_of_range`. Only § 2.4's *resolution*
  steps 1–3 are skipped, so the two entries can never disagree about which file
  is meant. The exception is an `ambiguous` antecedent, which has no path to
  give: the continuation inherits its `status` and a copy of its `candidates[]`
  (with `candidates_total` and `truncated_candidates`), reads nothing, and emits
  no `path`. An ambiguity chain is possible and intended.

  With no antecedent → `status:"unresolved"`. Attribution can be wrong when the
  author's antecedent was a prose mention rather than a citation; the flag is the
  mitigation, and the alternative — dropping 727 real citations — is worse. A
  fenced block **resets the tracker**: a continuation after a fence does not
  inherit from a citation before it. A fence is a context break, not merely
  skipped text — a `` `:45` `` after a code sample far more likely discusses
  that sample, and a visible `unresolved` beats a silent mis-attribution. This is
  the one place where "skipped" (§ 2.3, a block's *contents*) and "resets" (the
  block *boundary* clears state) deliberately differ.

### 2.3 Scrape rule (masking is inverted vs. `doc_integrity`)

- **Fenced blocks are skipped**, via `MarkdownScan::fenceMask`
  (`src/markdownscan.h:58`) — a `path:line` inside a ```` ```cpp ```` sample is
  illustrative text, not a claim about the repo. Shared with `doc_integrity`,
  including its ANTS-3638 list-container awareness.
- **An unterminated fence is reported, not absorbed.** `fenceMask` masks an
  unclosed fence true to end-of-input (its documented CommonMark leniency,
  `src/markdownscan.h:45-48`). Inherited silently, a single stray ```` ``` ````
  would blank every citation after it and return `truncated:false` — a
  clean-looking all-clear over a document the verb barely read. So the response
  carries **`unterminated_fence`**, the 1-based line of the unclosed opener,
  omitted when there is none. The mask is not second-guessed (this verb does
  not get to disagree with the project's one fence parser); the reader is told.
  The risk is live: ANTS-3638 and ANTS-3640 were both open-fence defects, and
  this spec is a doc full of fences *about* fences.

  **The fact is not recoverable from the mask, which is why § 2.7 adds an
  overload rather than post-processing.** `fenceMask` returns `QVector<bool>`
  and masks the closer line true as well as the opener (`markdownscan.h:45-48`:
  "The opener and closer lines are themselves masked true"). A document whose
  last line is a fence *closer* and one whose last line is inside an *unclosed*
  fence therefore produce byte-identical masks — both end in a run of `true`.
  Any rule inferred from the mask alone ("trailing `true` means unterminated")
  false-alarms on every doc that ends in a properly closed code block, which in
  this repo is most specs. The opener line must come from the scanner that
  already knows it.
- **Inline code spans are scanned, not masked — the POLICY inverts, the SCANNER
  is shared.** `doc_integrity` masks spans *out* before harvesting links,
  because a link inside a code span is a code sample; for citations the rule
  inverts, since the span is exactly where the data is. That is a difference in
  what the two verbs *do with* a span, not in how a span is *found*, and only
  the policy is allowed to diverge.
- **`MarkdownScan::codeSpans` is consumed, not written here** — ANTS-3649
  hoists it out of `DocIntegrity::maskInlineCode`, which already contains the
  whole algorithm, and re-bases that function on it so there is one
  implementation rather than two. What matters to this spec is that the
  primitive runs over the **whole document, not line by line**: a CommonMark
  span may cross a newline, the defect ANTS-3635(a) fixed, and a per-line pass
  leaves such a span's tail exposed. Spans are located rather than masked
  because two rules here turn on their boundaries — a continuation must fill one
  (§ 2.2) and an anchor must be one (§ 2.5), neither answerable from blanked-out
  text.
- The scan otherwise runs on the **raw** line, so a citation with a path is
  harvested wherever it appears — bare prose (`ROADMAP.md:19418 was …`), inside
  emphasis (``**`a.cpp:1`**``), or inside link text (``[`a.cpp:1`](x)``).

### 2.4 Path resolution ladder

Applied in order; first hit wins. Every terminal step names where the entry
lands, so the ladder is total.

| # | Condition | Filesystem | Outcome |
|---|---|---|---|
| 0 | **Lexical reject** — leading `/`, or lexically escaping root (`../..`) | none | `unparsed[]`, `reason:"out_of_root"` |
| 1 | Contains `/` → project-relative from the repo root | stat | regular file → gate G; else → `missing_file` |
| 2 | Bare basename, exactly one match in `basenameIndex` | stat | regular file → gate G; else → `missing_file` |
| 2b | Bare basename, ≥2 matches | none | `ambiguous` + `candidates[]` |
| 3 | Bare basename, not indexed, `<root>/<basename>` exists | stat | regular file → gate G; else → step 4 |
| 4 | A path part was present and none of the above resolved | none | `unparsed[]`, `reason:"unresolvable"` |
| 5 | No path part at all (bare continuation, no antecedent) | none | `citations[]`, `status:"unresolved"` |

**The stat is a regular-file test, not an existence test.** The grammar's only
requirement is a dot in the final segment, which a directory can satisfy
(`src/build.d:12`, `docs/assets.old:3`). Testing existence alone would send a
directory to the read path, where its status would be decided by whatever the
platform returns from opening one.

**Path-bearing and bare citations resolve asymmetrically, and it biases a
count.** A citation carrying a path part is decided at step 1, whose else is
explicit: `missing_file` — the doc named a specific path and there is no file at
it. A bare one can only reach step 3, whose else falls through to step 4 →
`unparsed[]`/`unresolvable`. So `src/build.d:12` (a directory) and
`src/gone.cpp:1` (a dead file) are `missing_file`, while `build.d:12` and
`gone.cpp:1` are not. Both populations are drift, but only the first is a
*definite* file claim: a bare token resolving to no file is indistinguishable
from prose (`6.2:1`), and guessing would put false `missing_file` findings in
front of a reviewer. `counts.missing_file` therefore under-reports the bare
majority by construction, and `counts.unparsed` / `unparsed[]` are where that
population is visible. The directory examples above are written path-bearing so
they exercise the branch they illustrate.

**Gate G — the anchor re-check, applied to every existing candidate before it
is read.** `PathValidation::isInsideProject(rootCanonical, candidate)`
(`src/pathvalidation.h:60`, ANTS-1832) canonicalises *both* sides and returns a
bare boolean, building no error envelope. False → `unparsed[]`,
`reason:"out_of_root"`, and the file is never opened.

Gate G is where the symlink case is closed, and it is a **separate step from
the lexical step 0** for a reason worth stating: a `QFileInfo::isSymLink` check
would inspect only the *final* component, so `src/link/foo.cpp:1` where
`src/link` is a symlink to `/etc` would pass it. Canonicalisation resolves
every component. It costs one stat on an in-root candidate that is about to be
read anyway — the "never probe" rule (ANTS-3601 INV-6's posture) binds
*lexically out-of-root* shapes, which step 0 rejects with zero filesystem
calls. `isInsideProject` returns false for a non-existent candidate, so gate G
runs only after existence is established; a missing file is `missing_file`,
never mis-reported as an escape.

`PathValidation::validatePath` is deliberately **not** used per-citation: its
product is a whole-response `bad_path` envelope, the wrong granularity for one
citation among 33. It still applies, unchanged, to the request's own `path`
argument at the handler. A citation target is not a "path-typed arg" in
`mcp-tools.md` step 4's sense — it is scraped file content — so the contract is
discharged at the handler and gate G is the defence in depth.

**What step 2 can and cannot see.** The `basenameIndex` is built from the
codebase index, whose walk is `source_roots` + `test_roots` — `src/` and
`tests/` by default, widened when a project declares them in
`.ants/project.json` (ANTS-2160). Step 3 adds repo-root files, which is what
catches `CMakeLists.txt:148` and `README.md:…`. A bare basename living anywhere
else — `mcp-tools.md:12` under `docs/standards/`, `safe-build.sh:20` under
`tools/` — resolves at neither step and lands in `unparsed[]` as
`"unresolvable"`. So § 1 consequence 2's gap is *narrowed*, not closed, and
`count` under-reports those. Stated rather than papered over, because a reader
comparing `count` against a hand tally will otherwise find the difference and
mistrust the rest.

Step 4 is the **only** producer of `reason:"unresolvable"`, and step 5 the
**only** producer of `status:"unresolved"`. Step 4 is *not* the only producer of
`unparsed[]` entries — step 0 and gate G both emit `reason:"out_of_root"` there,
and the grammar emits `reason:"bad_locus"` before the ladder runs at all. Three
reasons, four producers. A prose false positive like
`` `6.2:1` `` (path part `6.2` — it contains a dot, so the grammar admits it)
lands at step 4, not in `citations[]`.

**Ambiguity is reported, never resolved by guessing.** `src/` is flat (no
subdirectories) so in-lane collisions are impossible today, but the indexed
tree holds 14 `good.cpp` and 14 `bad.cpp` under `tests/audit_fixtures/`
(measured 2026-07-26). `candidates[]` is sorted on the project-relative path by
**UTF-16 code point (`QString::operator<`), not locale collation** — the same
choice ANTS-2120 forced elsewhere, because CI runs under `C.UTF-8` while a
developer's desktop does not, and a locale-sensitive sort would make the cap
select a *different* 8 of 14 candidates on the two machines. It is capped at
`maxCandidates`, with `candidates_total` giving the true match count and
`truncated_candidates:true` beyond the cap. `TestAuditEngine` merges such
collisions by picking the longest path (`src/testauditengine.cpp:1568-1591`);
that heuristic is fine for a
ranking aid and wrong for a verification tool, where a confidently-wrong line
of text is worse than a flagged unknown.

Step 0's out-of-root stance is modelled on the file-local `resolveRelative`
(`src/docintegrity.cpp:228`), but only its posture is borrowed — the helper is
an anonymous-namespace static inside `namespace DocIntegrity`, so it is not
callable from here, and its base differs: it resolves relative to the **citing
doc's directory** (correct for a markdown link) where a path-bearing citation
resolves from the **repo root** (correct for `src/foo.cpp:12` written in a doc
three levels down).

### 2.5 Anchor-symbol check — a derived drift signal, not a replacement for `expect`

The ROADMAP bullet asks for an `expect` mode ("does the cited line still
contain this substring?"). The corpus supplies a weaker version for free: its
most common citation idiom names the symbol immediately before the location.

```
`RemoteControl::filterControlChars` (`remotecontrol.h:95-113`) strips C0
`uniqueSlug` (`roadmapindex.cpp:72-86`) DOES auto-append `-2`, `-3`
```

Both lines are verbatim from the corpus, and — checked 2026-07-26 — **the first
one has already drifted.** `filterControlChars` is declared at
`src/remotecontrol.h:127`, outside the cited `95-113`, so the verb would resolve
that citation `ok`, show three lines of unrelated comment text, and report
`anchor_found:false`. The second is healthy: `uniqueSlug` is defined at
`src/roadmapindex.cpp:73`, inside the cited range, so its needle is found. The
pair is kept exactly as written because a live true-positive standing beside a
live true-negative is a better specification of this check than anything
invented — and because a spec about citation rot that carried only pristine
examples would be making the wrong point.

Pinned precisely, so two implementers build the same thing:

- **Anchor** = the nearest preceding inline code span on the **same line**
  (located by `MarkdownScan::codeSpans`) whose content matches
  `^[A-Za-z_][A-Za-z0-9_:]*$`, and whose closing backtick is within **40
  characters** of the opening backtick of the span containing the citation
  (measured on the raw line). A citation **not inside a code span** has no
  anchor, regardless of what precedes it.
- **Needle** = the anchor's final `::` component (`A::b` → `b`). An anchor
  ending in `::` yields an empty component and is discarded — no anchor.
- **Match** = case-sensitive, whole-identifier (the needle's occurrence must
  not be flanked by `[A-Za-z0-9_]`, so `id` does not match `invalid`), searched
  over the **full resolved range** — not the `max_range_lines`-clipped `text`,
  so display width never changes a verdict. When the range was clamped at EOF
  (§ 2.6) the search covers the existing portion. Trailing `\r` is stripped
  first (§ 5).
- `anchor_symbol` / `anchor_found` are **absent** when no anchor is found, and
  absent for every status that emits no text (`missing_file`, `out_of_range`,
  `read_error`, `ambiguous`, `unresolved`).

`anchor_found:false` is **advisory, not a `status`**: `status` answers "did the
citation resolve", this answers "does it still say what the doc claims".

**Measured coverage: 526 of the ≈2,620 tokens the verb harvests — 20%, and that
is a floor** (§ 1: 388 anchored path citations plus 138 anchored continuations,
over a denominator that is itself a ceiling). Two further caveats keep the
number honest rather than flattering. The anchor is only ever *evaluated* on an
`ok` citation — one that resolved and was read — so the share of the corpus this
check actually judges is 20% intersected with the resolvable population, which
§ 2.4 notes is itself less than the whole. And an anchored citation that fails
to resolve reports its status, not an anchor verdict.

The check is still worth its cost — it catches precisely the drift the ROADMAP
bullet describes, at zero authoring cost, on a fifth of the corpus — but it is a
*default*, not the `expect` mode. The residual (the un-anchored remainder, and
the scripted-re-verification case where a caller genuinely does hold an
expectation) is deferred to **ANTS-3642**, not quietly dropped.

**`anchor_found:false` is a prompt to look, not a verdict — and it is what
`only:"stale"` selects on, so its false-positive rate is a design parameter.**
Two shapes produce a false positive by construction. A citation naming a symbol
that sits a line or two *outside* the cited range reports stale although the
range may be fine. And a citation pointing at a *call site* rather than a
definition will not contain the symbol at all. Neither is tunable away:
widening the search past the cited range would silently convert real drift into
"found", which is the failure direction this verb must never take. The residual
is stated so a reviewer reads a stale flag as "check this one" rather than
"this is broken", and so nobody later widens the window to make the number look
better.

### 2.6 Status taxonomy, ranges, and decoding

| `status` | Meaning | `text` emitted |
|---|---|---|
| `ok` | Resolved, start in range, read | yes |
| `missing_file` | Path resolved, no regular file there | no |
| `out_of_range` | File read, `start_line > file_lines` | no |
| `read_error` | File present but unreadable, over `maxTargetBytes`, not decodable, or past `maxTargetReads` | no |
| `ambiguous` | Basename matches ≥2 indexed paths | no (`candidates[]` instead) |
| `unresolved` | Bare continuation with no antecedent (ladder step 5) | no |

`read_error` (a per-citation *status*) is distinct from the `read_failed`
*refusal code* the verb returns for an unreadable `path` argument: one is a row
in a successful response, the other ends the call.

**`maxTargetReads` is the absolute bound on work.** Past it, a citation needing
a fresh read is `read_error` and the response sets
**`read_budget_exhausted:true`**. Reaching it signals pathological input, not an
expected mode. § 5 derives why the bound is a counter rather than a product of
`max_doc_lines` and `maxTargetBytes`.

**`file_lines` is emitted for `ok` and `out_of_range`** (INV-41) — on the latter
it is *how* a caller sees that a citation to line 9,999 points past a 442-line
file, so omitting it would remove the finding's only evidence. Absent elsewhere,
including `read_error`, which may well have opened the file — an undecodable or
NUL-bearing target is only discovered by reading it — but has no trustworthy
line count to report.

**`unparsed[]` entries carry `doc_line`, `raw` (capped at `maxRawChars`, with
`raw_clipped:true` when the cap bites), and `reason`**, in document order. Two
identical malformed tokens on one line are two entries, distinguishable by
position in the array and nothing else — a column number would be the only field
on this verb whose value nothing consumes.

**Emitted `text` lines are capped at `maxTextBytes` each**, with
`text_clipped:true` on the citation when any line was cut. The unit is **UTF-8
bytes, not characters**, because every budget it interacts with is measured in
bytes; a character cap would let a CJK or emoji-bearing line cost 3–4× its
budgeted size. Clipping cuts at a UTF-8 boundary, never mid-sequence. Without
the cap `max_bytes` is not a bound at all — one minified `.json` or generated
`.h` line can exceed its floor unaided.

**So `max_bytes` is a *soft* ceiling**, and this spec says so rather than
pretending otherwise: INV-35 requires at least one `citations[]` entry even when
that entry alone overruns the remaining budget, and `unparsed[]` is never
trimmed. A response may therefore exceed `max_bytes` by at most one entry, whose
size the per-line cap bounds (§ 5 does the arithmetic); beyond that single
overshoot the cap is hard. Emitting a partial entry, or none, is worse — a
paging caller that receives zero entries with `next_offset == offset` loops
forever, the exact failure INV-35 prevents. A bounded, disclosed overshoot is
the honest resolution, and `truncated` plus `next_offset` make it visible.

**Ranges past EOF.** Only `start_line` decides `out_of_range`. A range whose
**end** exceeds `file_lines` — `:400-500` in a 442-line file — is `ok`:
`end_line` echoes what the doc wrote (500), `text` stops at EOF, and
`end_clamped:true` marks it. This is the common path (35% of the corpus is
ranges) and it is real drift information, so it must be visible without being a
hard failure.

An **empty** target needs no special case and gets none: `file_lines` is 0, so
the smallest legal `start_line` of 1 is already greater than it and the citation
is `out_of_range` with `file_lines:0`. That is the correct reading — a citation
to line 1 of an empty file points at nothing.

**The three range flags are independent and may all fire on one citation**
(INV-27) — `:1-9999` in a 10-line file at `max_range_lines:3`, with a long line
among the three, sets all of them. Each answers a different question:
`range_truncated` — "you are not seeing the whole cited range" (clipped to
`max_range_lines`, and nothing else); `end_clamped` — "the cited range runs past
EOF"; `text_clipped` — "you are not seeing the whole of a line". A reader needs
all three answers, so none suppresses another, and none is the top-level
`truncated`.

**Decoding.** Targets are decoded as UTF-8. A decode error, or an embedded NUL
byte, → `read_error` rather than mojibake `text`.

**The envelope rewrites some text, and the citation says so.** `wrapMcpData`
(`src/claudeintegration.cpp:11169`) sanitises every payload before it ships:
the literal `<ants_mcp_data>` close tag and its case/whitespace variants, the
open tag (ANTS-1670 M2), and the `<!--` / `-->` comment markers (ANTS-1996) are
each replaced with a visibly-modified inert form. That is correct and must not
be bypassed — it is what stops a hostile file line from closing the wrap — but
it means a cited line containing one of those tokens **arrives altered**, and
the files most likely to contain them are this project's own MCP sources and
standards docs, i.e. exactly what a reviewer cites. `read_region` answers this
with `raw:true`; § 2.1 declines that mode, so the answer here is disclosure: the
engine sets **`text_escaped:true`** on a citation whose text contains one. The
rewriting still happens downstream, unchanged — the reader is simply told the
text is not byte-exact, because a verification tool that silently shows altered
text is worse than one that shows none.

`unresolved` is the one
unresolvable shape that lives in `citations[]` rather than `unparsed[]`,
because a bare continuation has a valid locus and is a citation the author
actually made — merely un-attributable — where an `unparsed[]` entry may be
prose that was never a citation at all.

**Blocked by ANTS-3649**, which hoists `DocIntegrity::maskInlineCode` into

Two primitives are consumed from it:

```cpp
// ANTS-3649, src/markdownscan.h
struct CodeSpan { int startLine, startCol, endLine, endCol; };  // span CONTENT, delimiters excluded

`codeSpans` returns boundaries rather than a mask because two rules here turn on
them — a continuation must *fill* a span (§ 2.2) and an anchor must *be* one
(§ 2.5), neither answerable from blanked-out text. The `fenceMask` overload
exists because the mask alone cannot carry an unterminated fence: an unclosed
opener and a fence closing on the final line produce identical masks (§ 2.3).

```cpp
namespace DocCitations {

enum class Only { All, Stale };

// Test-only counters. INV-6 asserts "zero filesystem calls" and INV-20 "one
// open for five citations"; neither is observable from the returned JSON, so
// without this they could only be asserted by inspection — which is how a
// spec ends up with an invariant nothing actually checks. Nullptr in
// production; the engine's only cost is a null test per operation.
struct Probe {
    int stats = 0;   // QFileInfo / isInsideProject probes of a candidate
    int opens = 0;   // target files actually read (cache misses)
};

struct Options {
    // Basename → project-relative paths, built by the CALLER (§ 2.4 step 2).
    // Passing it in keeps the engine Qt6::Core-pure and unit-testable without
    // a CodebaseIndex on disk; empty → steps 0/1/3/4/5 only.
    QHash<QString, QStringList> basenameIndex;
    // True when the index hit kMaxIndexFiles. The engine cannot learn this
    // from the map itself (a capped index still looks large), so it must be
    // passed in — it drives `basename_index_truncated` (INV-37).
    bool   basenameIndexTruncated = false;

    Only   only           = Only::All;   // request arg
    int    offset         = 0;           // request arg
    int    maxRangeLines  = 3;           // request arg, handler-clamped [1, 20]
    int    maxDocLines    = 20000;       // request arg, handler-clamped [1000, 50000]
    int    maxBytes       = 128 * 1024;  // request arg, handler-clamped [64 KiB, 4 MiB]

    int    maxCitations   = 400;         // engine-side, no request arg
    int    maxUnparsed    = 200;         // engine-side
    int    maxCandidates  = 8;           // engine-side
    int    maxRawChars    = 120;         // engine-side, bounds unparsed[] size
    int    maxTextBytes   = 2000;        // engine-side, UTF-8 BYTES per emitted line
    int    maxTargetReads = 1000;        // engine-side, absolute read budget

    qint64 maxTargetBytes = 8 * 1024 * 1024;    // engine-side, on-disk bytes

    Probe *probe = nullptr;              // test-only, see above
};

**Reused:** `MarkdownScan::fenceMask` (the ANTS-3649 overload);
`PathValidation::isInsideProject` (gate G) and `::validatePath` (handler);
`ants::resolveCallerCwdRoot`; and the basename map, built by the handler in
**five** steps:

1. `CodebaseIndex::cachePathFor(rootCanonical)` — open it; absent → empty map.
2. `QJsonDocument::fromJson` its bytes; unparseable → empty map.
3. `CodebaseIndex::fromJson(obj)` — it takes a parsed object, not a path, which
   is why steps 1–2 are the caller's job.
4. **Validate: reject unless `idx.version == CodebaseIndex::kIndexVersion` and
   `idx.rootCanonical == rootCanonical`; either mismatch → empty map.**
5. One pass over `Index::files`, keyed on `path.section('/', -1)`.

**Step 4 is not optional and is easy to omit.** `CodebaseIndex::fromJson`
*copies* `version` and `root_canonical` into the struct and then parses `files`
unconditionally — it validates neither. The reject-on-mismatch a reader might
assume lives one level up, in `CodebaseIndex::serve`, which this recipe
deliberately bypasses because `serve` may *build* the index and a read verb must
not. Skipping step 4 silently mines a stale-schema or wrong-project cache for
basenames and reports every health field green.

No new index, cache or disk artifact, so ANTS-1439's cache-keying contract is
inherited rather than re-implemented. Any step failing yields an empty map,
visible as `basename_index_size:0`; the verb never cold-builds the index itself,
because a multi-second build is the wrong thing to do inside a read verb.
`session_orient` refreshes it at session start (ANTS-2140).

Degradation is **visible, not silent**, and the two modes carry different
signals. A *cold* cache yields an empty map — bare basenames fall to
`unparsed[]`, and `basename_index_size:0` says why. A *truncated* index
(`Index::filesTruncated`, set when the walk hits the `kMaxIndexFiles` ceiling or
the index's own byte cap) yields a large, healthy-looking map while basenames
beyond the cap fall through to `unparsed[]`, indistinguishable from a genuine
prose false positive; **`basename_index_truncated`** (INV-37) is the only thing
that separates them, which is why the `Options` field above is passed in rather
than inferred.

**Explicitly NOT reused — `ReadRegion::extract`.** The obvious candidate, and it
does not fit for three independent reasons: it opens and reads the file on every
call (defeating the line cache), it never reports the target's total line count
(so `file_lines` and the `out_of_range` predicate have no source), and its
`truncated` is byte-based where `range_truncated` is line-based. The engine
therefore reads each target once into the cache and slices from it — which
yields `file_lines` for free, since the read already walked the file.

**That read streams line by line** (a `QTextStream` over the open `QFile`,
appending to the cache entry). A requirement, not an optimisation note:
`readAll()` + `split('\n')` transiently holds the `QByteArray`, the decoded
`QString` *and* the `QStringList` at once, roughly tripling the peak for one
maximal target, and § 5's peak figure is false without streaming.

**All six registration hooks are mandatory, and they span two files** — an
implementer who registers the verb and stops ships a red suite. The split is
easy to get wrong: `registerToolProvider` is called from `src/mainwindow.cpp`,
while everything the `tools/list` response carries is authored in
`src/claudeintegration.cpp` (`mcp-tools.md` step 1 and its "File note for
steps 7–8").

1. **`src/mainwindow.cpp`** — `registerToolProvider("doc_citations",
   ClaudeIntegration::CallerCwdContract::Required, rcDelegate(...))`, the
   three-argument form with the contract as the **second positional** argument;
   `doc_integrity`'s call is the model.

The remaining five are in `src/claudeintegration.cpp`:

2. `inputSchema` — `type:"object"`, `additionalProperties:false`, explicit
   `required:["caller_cwd","path"]`, `makeEtagMatchProp()`, one-line description
   per property. Two `mcp-tools.md` step-11 prohibitions apply and are **not
   equally enforced** (checked 2026-07-26), which is what INV-22 turns on: a
   descriptor comment must not contain the literal `props["`, which makes the
   `mcp_dispatch_forward_completeness` scraper miscount properties — already
   tested; and the `description` must not begin with `[`, because `processTools`
   prepends a `[<kind>] ` tag at runtime and a hand-written one would double it
   — **no existing test asserts this**, since `mcp_tool_prefix_tags` checks
   `kindForName` *coverage*, not the description's first character. Overflow
   past the ~800 B guideline goes in a sibling `detail`.
3. `selection_hint` beside the descriptor — the one-line "when to use" that
   `tool_info {catalog:true}` surfaces. **Enforced by two feature tests under a
   format contract `mcp-tools.md` documents nowhere**, so a reasonable-looking
   hint ships a red suite:

   | Rule | Enforced by |
   |---|---|
   | present beside every descriptor | `mcp_selection_hint` HINT-1; `mcp_orientation_install` INV-6 also fails on name/hint count drift |
   | begins with `Use ` (case-insensitive) | `mcp_orientation_install` INV-7 (ANTS-1897) |
   | ≤ 240 characters | `mcp_selection_hint` HINT-3 (ANTS-1453), tightening INV-7's 280 — 240 binds |

   So the hint reads like `Use to resolve a doc's path:line citations and see
   the cited text …`. **ANTS-3645** tracks the *standard's silence* on all three
   rules; each is enforced, none is written down.
4. `kindForName` — `mcp_tool_prefix_tags` walks every registered name and fails
   the suite on an unbucketed verb.
5. The token-cost table, where `doc_integrity` sits. Also unlisted in
   `mcp-tools.md` — same gap, same ANTS-3645.
6. `callerCwdContractFor` → `Required`, and `isEtagSupportedTool`. Drift between
   the contract table and the registration call is **refused in every build
   configuration** (ANTS-1834); a debug build *additionally* aborts via
   `Q_ASSERT_X`.

**Not** a hook: the ANTS-2158 eager-load set (`kEagerVerbs`). That is a
deliberately small curated list replacing always-loaded built-ins like grep and
Read; a review-time verb called once per doc does not belong in it, and each
entry costs every session context.

## 5. RAM / build cost

- **Per-target read cap.** A target over `maxTargetBytes` (8 MiB) is **not
  read**: it is `read_error`, with no `file_lines`. Without this the cache's
  bound would govern only *retention*, and a single in-root citation to a
  generated `.json` or a log would pull an unbounded `QStringList` into memory.
- **Target-file line cache**, keyed by resolved path, so a doc citing one file
  30 times reads it once. Bounded at **16 files or `maxCacheBytes`, whichever
  binds first**; past the bound, further targets are read without being cached
  — no eviction, no LRU churn, no unbounded growth.

  **`maxCacheBytes` is measured in memory, not on disk, and the distinction is
  a factor of three.** The cache holds `QStringList`s: Qt strings are UTF-16,
  so an ASCII source doubles on the way in, and every line carries a `QString`
  header plus its own allocation. An 8 MiB source of ~40-byte lines is ~200k
  lines ≈ 16 MiB of characters plus ~8 MiB of per-string overhead. Budgeting by
  file size would promise 8 MiB and deliver ~24 MiB. The accounting is
  `sum over cached files of (2 × on-disk bytes + 40 × line count)`, charged
  before insertion, with the cap at **24 MiB** so the number here is the number
  in RSS.

  **Worst-case peak, by that same formula applied to every buffer alive at
  once** — the earlier figure of 48 MiB charged the in-flight read at its
  on-disk size, which is the very mistake this bullet exists to correct:

  | Buffer | Bound | In memory |
  |---|---|---|
  | Line cache | `maxCacheBytes` | 24 MiB |
  | One in-flight target read | `maxTargetBytes` 8 MiB on disk | ~24 MiB |
  | The doc's own `QStringList` | `maxDocBytes` 8 MiB on disk, and `max_doc_lines` 50,000 × 96.6 B ≈ 4.6 MiB — whichever binds first | ~12 MiB |
  | Response `QJsonObject` | `max_bytes` ceiling, ~2× as a live object | ~8 MiB |
  | Its serialization | `max_bytes` ceiling | 4 MiB |
  | `basenameIndex` | `kMaxIndexFiles` 5,000 paths | ~1 MiB |
  | **Peak** | | **~73 MiB** |

  Every row is charged by the same `2 × bytes + 40 × count` formula, including
  the ones an earlier draft omitted — the response object alongside its own
  serialization, and the basename map. The in-flight read is charged once, not
  three times, **because the read streams** (§ 2.7): a `readAll()` +
  `split('\n')` implementation would hold the `QByteArray`, the decoded
  `QString` and the `QStringList` simultaneously and put this row nearer 48 MiB
  on its own.

  A realistic call — one spec, a handful of small targets — is well under 5 MiB.
  ~73 MiB is the worst case that has to be defensible on a 32 GiB host running
  earlyoom, and it is, but only because two ceilings are set where they are:
  `max_doc_lines` at 50,000 rather than 100,000, and `maxDocBytes` bounding the
  doc by size as well as by line count.
- **Time is bounded by a counter, not by an argument.** Within the cache bound
  each distinct target is read once. Past it, INV-20 is explicit that a target
  is re-read *per citation*, so the worst case is
  `(citations past the cache bound) × (one target read)`. Deriving a bound on
  that product from `max_doc_lines` and `maxTargetBytes` is arithmetically true
  and practically useless — it permits 20,000 lines' worth of citations each
  pulling an 8 MiB read. So the product is bounded directly:
  **`maxTargetReads`**, after which a citation needing a fresh read is
  `read_error` and `read_budget_exhausted` is set (§ 2.6, INV-46). The densest
  doc in the corpus needs 7. No wall-clock timeout is set: there is no network
  and no subprocess, and a mid-response timeout would produce exactly the
  half-truthful output this design rejects — a count is deterministic where a
  deadline is not, and determinism is what INV-16's byte-identity assertion
  needs.
- **Input guard**: a doc over `max_doc_lines` is scanned to that line only;
  `scanned_lines` reports the prefix, `doc_lines` the true length, and
  `truncated:true` is set — but **no `next_offset`**, because the tail was
  never examined and no page reaches it (INV-31). The default of 20,000 is
  sized for specs (the densest is 56 citations); the project's largest doc,
  `ROADMAP.md` at 27,046 lines and growing, therefore **is** truncated at the
  default and needs `max_doc_lines:30000` to scan whole. That is why the guard
  is a request argument rather than a fixed constant — a caller who needs the
  tail can ask for it, and nothing is permanently unreachable. The upper clamp
  of 50,000 keeps the doc's own `QStringList` bounded at ~12 MiB by the
  accounting above, roughly 1.8× the project's current largest doc.

  **A line cap is not a size cap**, so `maxDocBytes` (8 MiB, engine-side) bounds
  the doc independently: 96.6 bytes/line is a corpus average, and one long-line
  file satisfies any `max_doc_lines` at arbitrary size. Over it the call refuses
  `read_failed` rather than truncating, because a doc that cannot be held has no
  partial answer worth giving — unlike a citation *target*, where the same
  condition costs one row.
- **Response budget**: `max_bytes` (128 KiB default — lower than the
  read-family 512 KiB because the value here is a compact review artifact)
  bounds the **serialized response**. When it or `maxCitations` (400) binds,
  whole trailing `citations[]` entries are dropped — never a half-populated
  entry — `truncated:true` is set, and `next_offset` names where to resume.
  Neither touches `unparsed[]`, which is bounded instead by `maxUnparsed` (200)
  with each `raw` capped at `maxRawChars` (120), so that array cannot exceed
  ~40 KiB and always fits inside the 64 KiB `max_bytes` floor. **`max_bytes` is
  a soft ceiling with one bounded overshoot** (§ 2.6): INV-35 emits at least one
  citation even when it does not fit, and `maxTextBytes` caps that entry at
  `max_range_lines × maxTextBytes` ≈ 40 KB at the clamp ceiling. So the response
  can exceed `max_bytes` by up to ~40 KB and no more.
  Without the per-line cap that overshoot would be unbounded, which is the only
  reason the cap exists. `returned` is always the emitted length.
- **Text normalisation**: a trailing `\r` is stripped from every emitted line
  and before the § 2.5 comparison, so a CRLF target does not produce phantom
  mismatches.
- **Build**, with the dominant cost estimated rather than only the small parts:

  | Change | Estimate | Comparable |
  |---|---:|---|
  | `src/doccitations.{h,cpp}` — new | **~350–400 lines** | `src/docintegrity.cpp` is 378 lines for a comparable engine |
  | Handler + two pure statics | ~120 lines | `doc_integrity`'s equivalents |

  So ~470–520 new lines here; the `MarkdownScan` hoist is ANTS-3649's cost, and
  is a net reduction there rather than an addition. `specs.md` § 5.3's brevity
  gate applies to the first row, which an earlier draft left unestimated while
  sizing the small helpers — the wrong way round. No new external
  dependency, no new target, and no new test bundle — both new feature
  directories join bundles that already exist.
