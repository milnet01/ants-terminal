# ANTS-3636 — `doc_citations`: resolve a doc's `path:line` citations and return the cited text

**Status:** spec draft, cold-eyes loops 1–5 folded (2026-07-26).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-3636 (OneUp_Ants_MCP_Feedback.md, 2026-07-26 addendum).
**Composes with:** ANTS-3601 (`doc_integrity` — shares the fence primitives),
ANTS-1637 (`codebase_index` — the basename→path map).
**Pairs with:** ANTS-3596, which hardened `docs/specs/ANTS-2161.md` by hand —
converting its § 2.2–§ 2.4 approximate anchors to symbol references, while
deliberately leaving the loop log's historical line citations in place
(`ROADMAP.md:19474`). This verb generalises the motivation, not the fix.
**Blocker for:** ANTS-3642 (request-side `expect` map), ANTS-3643 (corpus-wide
digest mode).

**Layman:** Design docs are full of "see `file.cpp`, line 200" pointers that rot
silently as code moves; this adds one call that looks every pointer up and shows
what is on those lines today.

---

## 1. Problem

Global rule 13 requires every doc claim naming a file, line, function, or
constant to be checked against live source rather than recalled. `/cold-eyes`
runs that check on every loop, for every reviewer, on every doc. There is no
verb for it, so it is done by hand or skipped — and when it is skipped, the
loop ratifies a stale line number and the next reader is sent to the wrong
place.

The reporting session (OneUp) hit this directly: verifying one spec meant
resolving 33 `updater.py:NNN` citations, and they wrote a throwaway Python
script because no verb existed. `read_regions` is the closest fit but takes a
hand-extracted list of `{path, start_line, end_line}` — and extracting that
list *is* the tedious part.

**The corpus is large enough that hand-verification does not scale.** Measured
2026-07-26 over `docs/`, excluding this spec. Two scans with different regexes
run here, so each row names its own denominator rather than implying one shared
total. Every figure is reproducible with the commands below — recorded inline
because three cold-eyes loops caught unverified counts in this very table, and
a number without its command is exactly the kind of claim this verb exists to
catch.

One caveat applies to every row: **the greps do not skip fenced blocks and the
verb does** (§ 2.3). 42 of scan P's 1,935 tokens sit inside a fence, so the
table over-states what the verb would actually harvest by about 2%. The
direction is stated rather than corrected for, because the fence-aware count is
only obtainable from the implementation this spec describes.

| Shape | Count | Of what |
|---|---:|---|

| …carrying a directory component (`src/foo.cpp:12`) | 551 | 28% of scan P |
| …**bare basename** (`foo.cpp:12`) | 1,384 | **72% of scan P** |
| Line **ranges** (`:208-228` or en-dash `:208–228`) | 673 | 35% of scan P |
| Multi-locus / open-ended (`:262/265/286`, `:5669+`) | 38 | 2% of scan P |
| Approximate (`:~752`) | 10 | <1% of scan P |
| Citations opening a code span (`` `foo.cpp:12` ``) — scan **S** | 1,791 | — |
| …preceded by an identifier code span (§ 2.5) | 388 | 22% of scan S |
| Bare continuations (`` `:548-549` ``, path inherited) | 727 in 78 files | own scan — **not** in scan P (no dotted path to match) |

| **Anchorable total** — 388 + 138 | **526** | **20% of everything the verb harvests** |

```bash
E='--include=*.md --exclude=ANTS-3636.md'
P='[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:[0-9]+'
grep -rhoE "$P" docs/ $E | wc -l                      # scan P total    1935
grep -rhoE "$P" docs/ $E | grep -c '/'                # with directory   551
grep -rhoE "$P(-|–)~?[0-9]+" docs/ $E | wc -l         # ranges           673
grep -rhoE "$P(/[0-9]+|\+)" docs/ $E | wc -l          # multi-locus       38
grep -rhoE '[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:~[0-9]+' docs/ $E | wc -l   # approximate 10
grep -rhoE "\`$P" docs/ $E | wc -l                    # scan S          1791
C='`:~?[0-9]+(-|–)?~?[0-9]*`'
A="\`[A-Za-z_][A-Za-z0-9_:]*\`[^\`]{0,40}"
grep -rhoE "$A\`$P" docs/ $E | wc -l                  # anchored         388
grep -rhoE "$C" docs/ $E | wc -l                      # continuations    727
grep -rhoE "$A$C" docs/ $E | wc -l                    # anchored conts   138

# tokens the greps see but the verb will not (§ 2.3) — 42
find docs -name '*.md' ! -name 'ANTS-3636.md' -print0 | xargs -0 awk '
  FNR==1 { infence=0 }
  /^[ ]{0,3}(```|~~~)/ { infence = !infence; next }
  infence { n += gsub(/[A-Za-z0-9_.@+\/-]+\.[A-Za-z]{1,5}:[0-9]+/, "&") }
  END { print n }'
```

**Anchorable total, worked.** The verb harvests scan P plus the continuations,
less what fences hide: `1,935 + 727 − 42 ≈ 2,620`. Of those, 388 + 138 = 526
carry a checkable anchor — **20%**. The two 22%-of-scan-S figures earlier in
this spec's history described the anchored *path* citations against their own
denominator only; 20% is the figure that applies to the whole harvest, and it
is the one § 2.5 and § 6 use.

Densest single doc: `docs/specs/ANTS-1750.md` at 56 citations over 7 distinct
targets. Largest doc: `ROADMAP.md` — **27,046 lines at the 2026-07-26
measurement and monotonically growing**, 673 of which carry a citation-shaped
token (`workspace_search`, `glob:ROADMAP.md`, `count_only:true`). That last
figure counts *lines*, not occurrences — the only row here that does, because
the `docs/`-scoped scans never touch `ROADMAP.md`. Its equality with the range
row above is a coincidence, not a copy-paste. Every use of the line count in
this spec (§ 5's guard sizing) must therefore be read as a floor.

Three consequences follow, and they shape the design:

1. **Existence checking is not enough.** A citation that has drifted onto an
   unrelated statement still points at a line that exists. Only the cited
   *text* exposes that, which is why the text is the load-bearing output and
   not an option. A live instance, found while writing this spec:
   `docs/specs/ANTS-2090.md:69` reads ``` `compactEnvelope` (gated on
   `isFieldProjectionTool`, `mcpprojection.cpp:28`) ```, but
   `src/mcpprojection.cpp:28` is today a blank line — `:27` closes
   `terseDefault()` and `:29` opens the ANTS-3550 hint-latch comment block, with
   the next function (`claimHint`) at `:41`. The line exists, so every
   existence-based check passes; the claim is nonetheless false. Tracked for
   repair as ANTS-3641.
2. **Bare basenames are the common case, not an edge case.** A resolver that
   only handled repo-relative paths would silently skip ~72% of the corpus —
   worse than no verb, because the empty result reads as "all clear".
3. **No mechanical signal covers most citations.** Only 20% carry a nearby
   identifier the verb can check the cited text against (§ 2.5). The other 80%
   can be *resolved and shown* but not *judged* — so the design must never let
   a filtered or degraded view imply they were verified.

## 2. Surface

### 2.1 Verb shape

New verb `doc_citations`, **not** a mode on `doc_integrity`. The ROADMAP bullet
left this open ("decide at spec time"); the deciding facts are that
`doc_integrity`'s contract is a *defect list* (`findings[]` + `counts{}`
narrowed together by `kinds` — ANTS-3601 INV-18,
`RemoteControl::docIntegrityBuildResponse`) while this verb's primary output is
an *enumeration of every citation with its text*, most of which are healthy.
Folding an enumeration into a findings verb would either break `kinds`/`counts`
or bury the payload. The two engines share only fence and code-span primitives
from `MarkdownScan` (§ 2.3), which already lives in a third module.

Request:

```jsonc
{
  "caller_cwd":       "<required>",       // CallerCwdContract::Required
  "path":             "docs/specs/ANTS-2090.md",  // required, a FILE
  "only":             "all" | "stale",    // default "all"
  "offset":           0,                  // 0-based index into the post-filter list
  "max_range_lines":  3,                  // per-citation, clamped to [1, 20]
  "max_bytes":        131072,             // clamped to [64 KiB, 4 MiB]
  "max_doc_lines":    20000,              // clamped to [1000, 50000]
  "etag_match":       "<opt>"
}
```

Those seven, plus `caller_cwd`, are the **whole** request surface. Every other
bound named in this spec — `maxCitations`, `maxUnparsed`, `maxCandidates`,
`maxRawChars`, `maxTextChars`, `maxTargetBytes`, `maxTargetReads`,
`maxCacheBytes` — is an engine-side default in `Options` (§ 2.7) with no
request argument, because each guards the engine rather than shaping the
caller's view.

**Numeric arguments clamp rather than refuse, and the clamping lives in the
handler** — `docCitationsClampOptions` (§ 2.7) maps request arguments onto
`Options`, and the engine trusts the `Options` it is given, so a direct engine
call in a unit test is never silently re-clamped. Four clamps:

- `max_range_lines` → `[1, 20]`.
- `max_bytes` → `[64 KiB, 4 MiB]` (`ReadRegion::kMaxBytesCeiling` is the upper
  bound). The floor is set so the largest possible `unparsed[]` (~40 KiB, see
  below) plus at least one citation always fits.
- `max_doc_lines` → `[1000, 50000]`. The ceiling is set by the § 5 RAM
  accounting, not chosen for roundness: 50,000 lines of the corpus's measured
  96.6 bytes/line is ~4.8 MiB on disk and ~12 MiB held as a `QStringList`.
  100,000 would double that for no reachable benefit — nothing in this project
  is that long, and `ROADMAP.md` at 27,046 fits with room to grow.
- `offset` → **`max(0, offset)` only.** The handler cannot clamp the upper end,
  because that bound is `count`, which the engine has not computed yet;
  past-the-end is therefore engine behaviour, defined in INV-38.

`dry_run` does not apply: the verb writes nothing (INV-16), so there is no
mutation to preview.

`path` must name a single **file**. Two deliberate divergences from
`doc_integrity`, both stated here because the two verbs are used together in
the same review loop and a silent difference is a caller trap:

- **A directory refuses `bad_args`**, where `doc_integrity` accepts one and
  walks it (ANTS-3601 INV-16). The reason is response size: `docs/` holds 1,935
  citations (§ 1), and this verb's payload is per-citation *text*, not a defect
  count. `bad_args` is the closest generic fit rather than an exact one — the
  taxonomy's full row reads "A required argument is missing or has the wrong
  shape… reach for `bad_args` when the value is present but ill-formed (wrong
  type, bad enum, failed regex), or when one guard covers both absent-and-
  malformed at once" (`mcp-error-codes.md:35`), and a directory is none of
  those three. The exact analogue would be a *minted* code, as
  `not_feedback_file` was for "this path is fine, just the wrong kind of file"
  (`:48`); minting one for a single verb is not worth amending the taxonomy
  for. The refusal message names the file-only requirement and points at
  ANTS-3643 for the sweep mode.
- **A well-formed but non-existent in-root `path` returns `ok:true` with an
  empty `citations[]`**, matching `doc_integrity` (ANTS-3601 INV-15,
  `src/remotecontrol.cpp:12334`) rather than refusing. Companion verbs should
  answer a typo'd path the same way. An existing but **unreadable** `path`
  refuses `read_failed`; an absent or empty `path` refuses `missing_field`.

`path` is not required to be `.md` — any UTF-8 text file is scanned. § 6's
"non-markdown inputs" non-goal is about the *workflow*, not an input guard.

Response. **This block is a synthetic fixture, not a live capture** — it is the
worked example an implementer checks their output against, so every field is
derivable from the rules below by inspection rather than from any file's current
contents. (A live capture would rot the moment the cited files moved, and a
rotted example in *this* spec would be self-refuting.) The fixture doc holds six
citation-shaped tokens: an anchored-and-matching one, a dead file, an ambiguous
bare basename, an anchor that no longer matches, an unanchored one, and a prose
false positive. The call is `only:"stale"`.

**`only` and `offset` are echoed** for the same reason `workspace_search` echoes
its effective arguments: a page saved to a file, or handed to another session,
otherwise cannot say which slice of which view it is. They are the request's
post-clamp values.

**`basename_index_size` is the number of distinct basenames** —
`Options::basenameIndex.size()`, not the file count, since 14 files named
`bad.cpp` occupy one key. Measured over this repo on 2026-07-26: 769 indexed
files collapse to **737** keys. The two numbers are close here and would not be
in a project with a deep tree; the field is the map's size because that is what
governs whether ladder step 2 can answer.

The 14-way `bad.cpp` collision above is **real, not invented for the fixture** —
`find src tests -name bad.cpp | wc -l` returns 14 today. It is the only part of
this synthetic block taken from live measurement, because an implementer needs
to see that the cap and `candidates_total` fire on a condition this repo
actually contains.

The JSON above is the tool's **payload**; the dispatcher wraps it in the
ANTS-1294 `<ants_mcp_data tool="doc_citations">…</ants_mcp_data>` envelope
(`mcp-tools.md` step 5). This is an ordinary, non-control-plane verb, so it
takes the standard wrap with no special handling — noted only because the
response block is shown unwrapped.

**Field-emission rule.** Every boolean in this response is **omitted when
false**, at three levels:

- **Per citation** — `range_truncated`, `end_clamped`, `inherited_path`,
  `approximate`, `partial`, `text_clipped`, `text_escaped`,
  `truncated_candidates`. At 400 citations, always-emitting these eight costs
  3,200 always-false keys on a verb whose premise is token frugality.
- **Per `unparsed[]` entry** — `raw_clipped`.
- **Top level** — `basename_index_truncated`, `read_budget_exhausted`;
  `unterminated_fence` is an integer and is absent rather than `0` when there is
  no unclosed fence.

`candidates_total` is emitted whenever `candidates[]` is. **Every truncation
this verb performs sets a flag** — that is the rule the list above exists to
keep, and INV-28 asserts it: `text_clipped` for the per-line character cap,
`raw_clipped` for a clipped `unparsed[]` `raw`, `range_truncated` for the line
cap, `end_clamped` for EOF, `truncated` for the response caps, and
`truncated_candidates` for the candidate cap. Silently shortened output is the
one thing a verification tool must never emit.

**How the tallies partition**, checked against the fixture above because that is
what an implementer will do:

- The six `status` keys partition `count`: `3 + 1 + 0 + 0 + 1 + 0 = 5`.
- `anchor_missing` and `unchecked` are **overlays on the `ok` subset**, not
  statuses, and they are not the same thing. `anchor_missing` counts `ok`
  citations that *had* an anchor whose needle was **not found** in the range;
  `unchecked` counts `ok` citations with **no anchor at all**, which were shown
  but never judged. So `counts.ok` = anchored-and-found + `anchor_missing` +
  `unchecked` — in the fixture, `3 = 1 + 1 + 1`.
- `counts.unparsed` mirrors `unparsed_total` and is **outside** `count` — an
  unparsed token is not a citation.
- `count` and `counts` are whole-doc (pre-`only`, pre-`offset`) over the scanned
  prefix; `returned` is the emitted length.

`counts.unchecked` is the load-bearing honesty field: per § 1 consequence 3 it
is ~80% of a typical doc. `basename_index_size` is its companion: a cold
codebase index (§ 2.7) pushes bare basenames — ~72% of the corpus — into
`unparsed[]`, and a reader who cannot see the index was empty would read the
shortfall as a clean doc.

`only:"stale"` keeps every non-`ok` citation plus every `ok` citation with
`anchor_found:false`. It **drops** `ok` citations that are anchored-and-found
(nothing to report) and `ok` citations with no anchor (no drift signal for
them) — which is exactly why `counts` stays unfiltered. A caller reading only
the filtered list and ignoring `counts.unchecked` will believe more was
verified than was; the field exists so that is a misreading rather than a
design flaw.

The ROADMAP bullet asks for a `stale[]` array; this is that, reshaped into a
filter over one array plus unfiltered counts, so the healthy majority stays
addressable in the same call. It is also broader than the bullet's "missing or
out of range" — it keeps anchor drift too. The bullet's per-entry sketch keys
are renamed here: `cited_path` → `path`, `cited_line` → `start_line`, and the
boolean `exists` → the six-valued `status` (a boolean cannot distinguish a dead
file from an ambiguous basename from a line past EOF).

**Sort order is document order** — ascending `doc_line`, and within one line
ascending column of the citation's first character. Stated because `offset`
paging is only meaningful over a defined order, and because INV-29 mandates two
separate entries for two citations on one line, which would otherwise have no
defined relative position. `unparsed[]` is ordered the same way.

**`count` and `counts` are whole-doc, which means resolution does not stop when
the emission caps bind.** `maxCitations` / `max_bytes` bound what is *emitted*,
not what is *examined*: every citation in the scanned prefix is resolved, and
every `ok` one is read, so the tallies and the two overlays are true of the
whole doc rather than of the first page. The bound on *work* is `max_doc_lines`
(§ 5) together with the line cache; the bound on *response size* is
`max_bytes`. Consequence, stated so it is a choice rather than a surprise:
because INV-16 forbids cross-call state, paging with `offset` re-resolves and
re-reads the whole doc on every page, and re-emits `counts` and `unparsed[]`
each time. At the corpus's densest doc (56 citations over 7 targets) that is
cheap.

**Paging is therefore not atomic**, and a caller assembling pages must know it.
Each page is an independent resolution of the doc *as it is at that moment*: if
the doc or any cited target is edited between calls, page 2 is computed over
different bytes than page 1, so an entry can be seen twice or missed entirely
and `count` can differ across pages. This is the cost of holding no cross-call
state, and it is the right trade for a review-time verb — the alternative is a
server-side snapshot with an expiry contract, which is far more machinery than a
56-citation worst case justifies. Callers that need a consistent view should
raise `max_bytes` and take one page; callers that page should compare `count`
between pages and restart if it moved.

**`unparsed[]` is never filtered by `only`, is never trimmed by `max_bytes`,
and has no pagination.** Its sole bound is `maxUnparsed` (200 entries), and
each entry's `raw` is capped at `maxRawChars` (120), so the array cannot exceed
~40 KiB — which is why `max_bytes` never needs to touch it and why the
`max_bytes` floor is set above it. When `maxUnparsed` binds, `unparsed_total`
reports the true count, so the loss is *countable* even though those entries
are gone; there is no `offset` that retrieves them. If the array ever needs
paging, that is ANTS-3643's digest shape, not a second offset on this verb.

`offset` pages the post-filter `citations[]` list. **`next_offset` is emitted
exactly when a resumable cap dropped trailing `citations[]` entries** — that
is, when `maxCitations` or `max_bytes` bound — and is `offset + returned`, the
`roadmap_query` / `workspace_search` precedent. It is **absent** otherwise,
including on the `max_doc_lines` guard, whose truncation is not resumable by
paging (INV-31): the unscanned tail was never examined, so no `offset` reaches
it — the caller raises `max_doc_lines` instead. `truncated:true` therefore has
two flavours, and `next_offset`'s presence is what distinguishes "there is more
of this list" from "there is more of this document".

**`fields=` is deliberately not adopted.** `mcp-tools.md` step 8 marks it
optional, and `mcp::isFieldProjectionTool` is a curated allowlist that
`doc_integrity` is likewise absent from. `only` + `offset` cover this verb's
real narrowing needs at a fraction of the surface. **`raw:true` is not adopted
either** (`mcp::isRawEligible` — `read_region`, `read_regions`,
`workspace_search`): raw mode returns verbatim bytes in a collision-proof
frame, and this verb's product is a structured envelope in which the file text
is one field among many.

The dispatcher-injected `etag` (`mcp-tools.md` step 7) hashes the **response**,
so an unchanged etag means every field the response *reports* is unchanged. That
does include the verdicts: `anchor_found` is computed over the full resolved
range (§ 2.5), not over the clipped `text`, so a tail edit that flips a verdict
does change the etag. What an unchanged etag does **not** mean is that the cited
files are unchanged — `text` is clipped to `max_range_lines`, and an edit inside
the unshown tail that changes no reported field leaves the etag equal. Read it
as "my answer is the same", never as "the target is the same".

### 2.2 Citation grammar

```
citation     := path ":" locus trailing?
continuation := codespan( ":" locus trailing? )   // path inherited (sticky rule below)
path         := "/"? seg ( "/" seg )*             // last seg must contain a "."
seg          := [A-Za-z0-9_.@+-]+
locus        := "~"? N [ ("-" | "–") "~"? N ]     // hyphen or EN DASH
trailing     := ( "/" "~"? N )+ | "+"             // extra loci, dropped (partial)
N            := [0-9]{1,7} (?![0-9])              // 1-7 digits, NOT followed by a digit
```

Five constraints that are part of the grammar, not commentary on it:

- **A continuation must fill a whole inline code span.** `` `:45` `` is a
  continuation; the `:45` inside `09:45`, `3:1`, or `INV-3:` is not. Without
  this rule the § 2.3 raw-line scan would harvest every clock time and ratio in
  every doc, inherit an unrelated path, and emit *the real text of that file's
  line 45* under `status:"ok"` — a confidently-wrong answer, which § 2.4 fixes
  the ambiguity rule specifically to avoid. Requiring the delimiters is what
  makes a continuation an authored citation rather than a coincidence, and it
  matches how all 727 corpus continuations are written. A citation *with* a
  path needs no such guard: its path part cannot be produced by prose
  punctuation. `codespan(…)` is `MarkdownScan::codeSpans` (§ 2.7), and "fills"
  is tested against the span's **content after CommonMark's one-space strip** —
  a span whose content both begins and ends with a space, without being all
  spaces, loses one from each end. So `` ` :45 ` `` is a continuation, matching
  what a markdown renderer shows the author. A span containing a newline (spans
  may cross lines — § 2.7) can never be a continuation.
- **`raw` is the matched token without its delimiters.** `` `:45` `` yields
  `raw:":45"`, and `` `src/a.cpp:2` `` yields `raw:"src/a.cpp:2"`. The
  backticks are grammar, not content.
- **The dot must be in the final segment.** `src.old/README:12` does not parse
  (no dot in `README`); `docs/specs/ANTS-2161.md:5` does. The dot stands in for
  "names a file", and a directory component's dot says nothing about the leaf.
- **`N` is 1–7 digits and must not be followed by another digit** (so up to
  9,999,999 — 370× the 27,046 lines of this repo's largest file, and over two
  orders of magnitude of headroom).
  The negative lookahead is load-bearing: without it a greedy regex would match
  the first 7 digits of a longer run and silently emit a *citation* at some
  truncated line number. With it the token fails to parse and lands in
  `unparsed[]` as `bad_locus`, which is also what keeps any locus from reaching
  an `int` that cannot hold it.
- **`trailing` is exhaustive.** Only further `/`-separated loci and a single
  `+` are absorbed and reported as `partial:true`. Every other character ends
  the token, so the `.` closing a sentence in ``see `src/a.cpp:12`.`` is
  ordinary punctuation and sets no flag. A `~` on a *dropped* trailing locus
  (`:262/~265`) is dropped with it — `approximate` reflects the first locus
  only.

Further rules:

- **En dash is not optional.** The corpus writes both `:208-228` and
  `:208–228`; a hyphen-only regex loses a large minority of the 673 ranges.
- **Trailing loci are dropped, not guessed.** `:262/265/286/300` and `:5669+`
  parse as their first locus with `partial:true` (38 occurrences, ~2%).
- **`~N` sets `approximate:true` and changes nothing else.** It is an echo so a
  reader can see the author hedged. Status is computed identically for tilde
  and non-tilde loci — there is no fuzzy-match tolerance, because there is
  nothing to be tolerant *against* (10 corpus occurrences, <1%).
- **Malformed loci are not citations.** `N < 1`, an end below its start, or a
  digit run longer than 7 → `unparsed[]` with `reason:"bad_locus"`. None of the
  three occurs in the corpus today (all measured at 0); the rule exists so the
  read path never receives arguments it would refuse.
- **Known unsupported spelling: `~:N`** (tilde *before* the colon, as in
  ``remotecontrol.cpp `~:11985` ``). The corpus holds **10** such tokens across
  4 files — `docs/specs/ANTS-2161.md` ×4,
  `docs/superpowers/plans/2026-06-10-ants-2049-e2e-harness.md` ×3,
  `docs/specs/ANTS-3579.md` ×2, `docs/plans/ANTS-1160.md` ×1 (counted as
  *tokens*, not lines; `grep -rhoE '~:[0-9]+' docs/`) — and `ROADMAP.md`
  ANTS-3596 names the class by that spelling. They match neither `citation` nor
  `continuation`, so they are invisible — absent from `count` *and* from
  `unparsed[]`. Admitting them would mean a second approximate form throughout
  the grammar for 10 tokens; instead the gap is measured, stated, and tracked
  as **ANTS-3646**.
- **Two citations on one doc line are two entries**, as are two occurrences of
  the same citation. `count` is occurrences, not distinct targets; the line
  cache (§ 5) makes the repeat free.
- **Sticky path.** A bare continuation inherits from the most recent
  **antecedent** earlier in the same document: the most recent entry that
  reached `citations[]` with a status other than `unresolved`. An `unparsed[]`
  entry is never an antecedent. The continuation is itself eligible to be the
  next antecedent.

  **`inherited_path:true` marks "this entry's target came from an antecedent
  rather than from its own text", and it is set whenever an antecedent was
  found** — including the ambiguous case, where what is inherited is the
  candidate set rather than a path. It is **not** set on an `unresolved`
  continuation, which found no antecedent and inherited nothing; that entry is
  identified by its status alone. So the flag never appears on an entry whose
  target is unknown, and its absence on a continuation always means the same
  thing: nothing upstream to attach to.

  **Only the antecedent's resolved `path` is inherited — the continuation then
  runs the read step itself and takes its own status.** So a `missing_file`
  antecedent followed by `` `:2` `` yields a second `missing_file` (the file is
  still absent), and an `ok` antecedent whose continuation cites a line past EOF
  yields `out_of_range`. What is skipped is only the § 2.4 ladder's *resolution*
  steps 1–3, so the two entries can never disagree about which file is meant.
  The one antecedent with no path to inherit is an `ambiguous` one: the
  continuation inherits `status:"ambiguous"` plus a copy of its `candidates[]`
  (with `candidates_total` and `truncated_candidates`), reads nothing, and emits
  no `path`. An ambiguity chain is therefore possible and intended.

  With no antecedent → `status:"unresolved"`. Attribution can be wrong when the
  author's antecedent was a prose mention rather than a citation; the flag is
  the mitigation, and the alternative (dropping 727 real citations) is worse. A
  fenced block **resets the antecedent tracker**: a continuation after a fence
  does not inherit from a citation before it, and with nothing between the
  fence and itself is `unresolved`. A fence is a context break, not merely
  skipped text — a `` `:45` `` after a code sample is far more likely to be
  discussing that sample than the citation that preceded it, and an
  `unresolved` entry the reader can see beats a silent mis-attribution. This is
  the one place where "skipped" (§ 2.3, a block's *contents* are not scanned)
  and "resets" (the block *boundary* clears state) deliberately differ.

### 2.3 Scrape rule (masking is inverted vs. `doc_integrity`)

- **Fenced blocks are skipped**, via `MarkdownScan::fenceMask`
  (`src/markdownscan.h:58`) — a `path:line` inside a ```` ```cpp ```` sample is
  illustrative text, not a claim about the repo. Shared with `doc_integrity`,
  including its ANTS-3638 list-container awareness.
- **An unterminated fence is reported, not absorbed.** `fenceMask` masks an
  unclosed fence true to end-of-input (its documented CommonMark leniency,
  `src/markdownscan.h:45-48`). Inherited silently, a single stray ```` ``` ````
  would blank every citation after it and return `truncated:false` — a
  clean-looking all-clear over a document the verb barely read. So the response
  carries **`unterminated_fence`**, the 1-based line of the unclosed opener,
  omitted when there is none. The mask is not second-guessed (this verb does
  not get to disagree with the project's one fence parser); the reader is told.
  The risk is live: ANTS-3638 and ANTS-3640 were both open-fence defects, and
  this spec is a doc full of fences *about* fences.

  **The fact is not recoverable from the mask, which is why § 2.7 adds an
  overload rather than post-processing.** `fenceMask` returns `QVector<bool>`
  and masks the closer line true as well as the opener (`markdownscan.h:45-48`:
  "The opener and closer lines are themselves masked true"). A document whose
  last line is a fence *closer* and one whose last line is inside an *unclosed*
  fence therefore produce byte-identical masks — both end in a run of `true`.
  Any rule inferred from the mask alone ("trailing `true` means unterminated")
  false-alarms on every doc that ends in a properly closed code block, which in
  this repo is most specs. The opener line must come from the scanner that
  already knows it.
- **Inline code spans are scanned, not masked** — the inverse of
  `maskInlineCode` (`src/docintegrity.cpp:115`), which `doccitations` therefore
  never calls. `doc_integrity` masks spans *out* before harvesting links,
  because a link inside a code span is a code sample; for citations the rule
  inverts, since the span is exactly where the data is. This is the deepest
  reason the two checks cannot share a scrape pass.
- Spans are still *located*, by `MarkdownScan::codeSpans` (§ 2.7), because two
  rules turn on their boundaries: a continuation must fill one (§ 2.2) and an
  anchor must be one (§ 2.5). **It runs over the whole document, not line by
  line**, because a CommonMark span may cross a newline — this is not a
  hypothetical, it is the defect ANTS-3635(a) fixed in the sibling scanner
  (`src/docintegrity.cpp:104-108`: a span opening on `ANTS-1150.md:197` and
  closing on `:198` left its tail exposed to a per-line pass). Specifying the
  new helper line-scoped would re-introduce a bug this project has already paid
  to find once.
- The scan otherwise runs on the **raw** line, so a citation with a path is
  harvested wherever it appears — bare prose (`ROADMAP.md:19418 was …`), inside
  emphasis (``**`a.cpp:1`**``), or inside link text (``[`a.cpp:1`](x)``).

### 2.4 Path resolution ladder

Applied in order; first hit wins. Every terminal step names where the entry
lands, so the ladder is total.

| # | Condition | Filesystem | Outcome |
|---|---|---|---|
| 0 | **Lexical reject** — leading `/`, or lexically escaping root (`../..`) | none | `unparsed[]`, `reason:"out_of_root"` |
| 1 | Contains `/` → project-relative from the repo root | stat | regular file → gate G; else → `missing_file` |
| 2 | Bare basename, exactly one match in `basenameIndex` | stat | regular file → gate G; else → `missing_file` |
| 2b | Bare basename, ≥2 matches | none | `ambiguous` + `candidates[]` |
| 3 | Bare basename, not indexed, but `<root>/<basename>` is a regular file | stat | gate G |
| 4 | A path part was present and none of the above resolved | none | `unparsed[]`, `reason:"unresolvable"` |
| 5 | No path part at all (bare continuation, no antecedent) | none | `citations[]`, `status:"unresolved"` |

**The stat is a regular-file test, not an existence test.** The grammar's only
requirement is a dot in the final segment, which a directory can satisfy
(`build.d:12`, `assets.old:3`). Testing existence alone would send a directory
to the read path, where its status would be decided by whatever the platform
returns from opening one. A directory is `missing_file`: the doc claimed a file
at that path and there is no file at that path.

**Gate G — the anchor re-check, applied to every existing candidate before it
is read.** `PathValidation::isInsideProject(rootCanonical, candidate)`
(`src/pathvalidation.h:60`, ANTS-1832) canonicalises *both* sides and returns a
bare boolean, building no error envelope. False → `unparsed[]`,
`reason:"out_of_root"`, and the file is never opened.

Gate G is where the symlink case is closed, and it is a **separate step from
the lexical step 0** for a reason worth stating: a `QFileInfo::isSymLink` check
would inspect only the *final* component, so `src/link/foo.cpp:1` where
`src/link` is a symlink to `/etc` would pass it. Canonicalisation resolves
every component. It costs one stat on an in-root candidate that is about to be
read anyway — the "never probe" rule (ANTS-3601 INV-6's posture) binds
*lexically out-of-root* shapes, which step 0 rejects with zero filesystem
calls. `isInsideProject` returns false for a non-existent candidate, so gate G
runs only after existence is established; a missing file is `missing_file`,
never mis-reported as an escape.

`PathValidation::validatePath` is deliberately **not** used per-citation: its
product is a whole-response `bad_path` envelope, the wrong granularity for one
citation among 33. It still applies, unchanged, to the request's own `path`
argument at the handler. A citation target is not a "path-typed arg" in
`mcp-tools.md` step 4's sense — it is scraped file content — so the contract is
discharged at the handler and gate G is the defence in depth.

**What step 2 can and cannot see.** The `basenameIndex` is built from the
codebase index, whose walk is `source_roots` + `test_roots` — `src/` and
`tests/` by default, widened when a project declares them in
`.ants/project.json` (ANTS-2160). Step 3 adds repo-root files, which is what
catches `CMakeLists.txt:148` and `README.md:…`. A bare basename living anywhere
else — `mcp-tools.md:12` under `docs/standards/`, `safe-build.sh:20` under
`tools/` — resolves at neither step and lands in `unparsed[]` as
`"unresolvable"`. So § 1 consequence 2's gap is *narrowed*, not closed, and
`count` under-reports those. Stated rather than papered over, because a reader
comparing `count` against a hand tally will otherwise find the difference and
mistrust the rest.

Step 4 is the **only** producer of `reason:"unresolvable"`, and step 5 the
**only** producer of `status:"unresolved"`. Step 4 is *not* the only producer of
`unparsed[]` entries — step 0 and gate G both emit `reason:"out_of_root"` there,
and the grammar emits `reason:"bad_locus"` before the ladder runs at all. Three
reasons, four producers. A prose false positive like
`` `6.2:1` `` (path part `6.2` — it contains a dot, so the grammar admits it)
lands at step 4, not in `citations[]`.

**A deliberate asymmetry, stated because it biases a count.** A
directory-bearing dead citation (`src/gone.cpp:1`) is `missing_file`; a bare
dead basename (`gone.cpp:1`) falls to step 4 and is `unparsed[]`. Both are
drift, but only the first is a *definite* file claim — a bare token that
resolves nowhere is indistinguishable from prose (`6.2:1`), and guessing would
put false `missing_file` findings in front of a reviewer. So
`counts.missing_file` under-reports the bare-basename majority by construction;
`counts.unparsed` and `unparsed[]` are where that population is visible.

**Ambiguity is reported, never resolved by guessing.** `src/` is flat (no
subdirectories) so in-lane collisions are impossible today, but the indexed
tree holds 14 `good.cpp` and 14 `bad.cpp` under `tests/audit_fixtures/`
(measured 2026-07-26). `candidates[]` is sorted on the project-relative path by
**UTF-16 code point (`QString::operator<`), not locale collation** — the same
choice ANTS-2120 forced elsewhere, because CI runs under `C.UTF-8` while a
developer's desktop does not, and a locale-sensitive sort would make the cap
select a *different* 8 of 14 candidates on the two machines. It is capped at
`maxCandidates` (8), with
`candidates_total` giving the true match count and `truncated_candidates:true`
beyond the cap. `TestAuditEngine` merges such collisions by picking the longest
path (`src/testauditengine.cpp:1568-1591`); that heuristic is fine for a
ranking aid and wrong for a verification tool, where a confidently-wrong line
of text is worse than a flagged unknown.

Note the deliberate asymmetry with the file-local `resolveRelative`
(`src/docintegrity.cpp:228` — an anonymous-namespace helper inside
`namespace DocIntegrity`, so it is internal linkage and **not** callable from
here; only its posture is being compared), whose out-of-root stance step 0
models: it resolves relative to the **citing doc's directory** (correct for a
markdown link), while a citation's directory-bearing path resolves from the
**repo root** (correct for `src/foo.cpp:12` written in a doc three levels
down). Only the posture is borrowed, not the base.

### 2.5 Anchor-symbol check — a derived drift signal, not a replacement for `expect`

The ROADMAP bullet asks for an `expect` mode ("does the cited line still
contain this substring?"). The corpus supplies a weaker version for free: its
most common citation idiom names the symbol immediately before the location.

```
`RemoteControl::filterControlChars` (`remotecontrol.h:95-113`) strips C0
`uniqueSlug` (`roadmapindex.cpp:72-86`) DOES auto-append `-2`, `-3`
```

Both lines are verbatim from the corpus, and — checked 2026-07-26 — **the first
one has already drifted.** `filterControlChars` is declared at
`src/remotecontrol.h:127`, outside the cited `95-113`, so the verb would resolve
that citation `ok`, show three lines of unrelated comment text, and report
`anchor_found:false`. The second is healthy: `uniqueSlug` is defined at
`src/roadmapindex.cpp:73`, inside the cited range, so its needle is found. The
pair is kept exactly as written because a live true-positive standing beside a
live true-negative is a better specification of this check than anything
invented — and because a spec about citation rot that carried only pristine
examples would be making the wrong point.

Pinned precisely, so two implementers build the same thing:

- **Anchor** = the nearest preceding inline code span on the **same line**
  (located by `MarkdownScan::codeSpans`) whose content matches
  `^[A-Za-z_][A-Za-z0-9_:]*$`, and whose closing backtick is within **40
  characters** of the opening backtick of the span containing the citation
  (measured on the raw line). A citation **not inside a code span** has no
  anchor, regardless of what precedes it.
- **Needle** = the anchor's final `::` component (`A::b` → `b`). An anchor
  ending in `::` yields an empty component and is discarded — no anchor.
- **Match** = case-sensitive, whole-identifier (the needle's occurrence must
  not be flanked by `[A-Za-z0-9_]`, so `id` does not match `invalid`), searched
  over the **full resolved range** — not the `max_range_lines`-clipped `text`,
  so display width never changes a verdict. When the range was clamped at EOF
  (§ 2.6) the search covers the existing portion. Trailing `\r` is stripped
  first (§ 5).
- `anchor_symbol` / `anchor_found` are **absent** when no anchor is found, and
  absent for every status that emits no text (`missing_file`, `out_of_range`,
  `read_error`, `ambiguous`, `unresolved`).

`anchor_found:false` is **advisory, not a `status`**: `status` answers "did the
citation resolve", this answers "does it still say what the doc claims".

**Measured coverage: 526 of the ~2,620 tokens the verb harvests — 20%** (§ 1:
388 anchored path citations plus 138 anchored continuations). This is the honest
limit. The check is worth its cost — it catches precisely the drift the bullet
describes, at zero authoring cost, on a fifth of the corpus — but it is a
*default*, not the `expect` mode. The residual gap (the other 80%, and the
scripted-re-verification case where a caller genuinely does hold an
expectation) is deferred to **ANTS-3642**, not quietly dropped.

**`anchor_found:false` is a prompt to look, not a verdict — and it is what
`only:"stale"` selects on, so its false-positive rate is a design parameter.**
Two shapes produce a false positive by construction. A citation naming a symbol
that sits a line or two *outside* the cited range reports stale although the
range may be fine. And a citation pointing at a *call site* rather than a
definition will not contain the symbol at all. Neither is tunable away:
widening the search past the cited range would silently convert real drift into
"found", which is the failure direction this verb must never take. The residual
is stated so a reviewer reads a stale flag as "check this one" rather than
"this is broken", and so nobody later widens the window to make the number look
better.

### 2.6 Status taxonomy, ranges, and decoding

| `status` | Meaning | `text` emitted |
|---|---|---|
| `ok` | Resolved, start in range, read | yes |
| `missing_file` | Path resolved, no regular file there | no |
| `out_of_range` | File read, `start_line > file_lines` | no |
| `read_error` | File present but unreadable, over `maxTargetBytes`, not decodable, or past `maxTargetReads` | no |
| `ambiguous` | Basename matches ≥2 indexed paths | no (`candidates[]` instead) |
| `unresolved` | Bare continuation with no antecedent (ladder step 5) | no |

`read_error` (a per-citation *status*) is distinct from the `read_failed`
*refusal code* the verb returns for an unreadable `path` argument: one is a row
in a successful response, the other ends the call.

**`maxTargetReads` (1,000) is the absolute bound on work**, and it is what makes
the cost of a call finite rather than merely "bounded by other bounds". Past it,
a citation that would need a fresh read is `read_error` and the response sets
**`read_budget_exhausted:true`**. This exists because the obvious claim — that
work is bounded because `max_doc_lines` bounds the citation count and
`maxTargetBytes` bounds each read — multiplies out to 20,000 lines' worth of
citations each triggering an 8 MiB read once the line cache is full (§ 5), which
is not a bound anyone would accept if it were written as a number. One counter
replaces the argument. Reaching it is a pathological-input signal, not an
expected mode: the corpus's densest doc needs 7 reads.

**`file_lines` is emitted whenever the target was read**, which is `ok` and
`out_of_range` — the latter is *how* a caller sees that a citation to line
9,999 points past a 442-line file, so omitting it there would remove the
finding's only evidence. It is absent for `missing_file`, `ambiguous`,
`unresolved` — which never open a file — and for `read_error`, which **may**
have opened one: an oversized target is rejected on its stat, but an undecodable
or NUL-bearing one is only discovered by reading it. The field is absent there
because a failed decode yields no trustworthy line count, not because nothing
was opened.

**`unparsed[]` entries carry `doc_line`, `raw` (capped at `maxRawChars`, with
`raw_clipped:true` when the cap bites), and `reason`**, in document order. Two
identical malformed tokens on one line are two entries, distinguishable by
position in the array and nothing else — a column number would be the only field
on this verb whose value nothing consumes.

**Emitted `text` lines are capped at `maxTextChars` (2,000) each**, with
`text_clipped:true` on the citation when any of its lines was cut. Without this
`max_bytes` is not a bound at all: one minified `.json` or generated `.h` line
can exceed the entire 64 KiB floor by itself, and INV-35 requires the response
to emit at least one entry no matter what — so the two rules together would
oblige the verb to return a response larger than its own maximum. The cap is per
*line*, not per citation, so a 3-line range of long lines is capped at ~6 KB;
that is the worst case a single entry can contribute, and it is what makes the
`max_bytes` floor satisfiable by construction. 2,000 characters is far past any
hand-written source line and far short of a minified one.

**Ranges past EOF.** Only `start_line` decides `out_of_range`. A range whose
**end** exceeds `file_lines` — `:400-500` in a 442-line file — is `ok`:
`end_line` echoes what the doc wrote (500), `text` stops at EOF, and
`end_clamped:true` marks it. This is the common path (35% of the corpus is
ranges) and it is real drift information, so it must be visible without being a
hard failure.

An **empty** target needs no special case and gets none: `file_lines` is 0, so
the smallest legal `start_line` of 1 is already greater than it and the citation
is `out_of_range` with `file_lines:0`. That is the correct reading — a citation
to line 1 of an empty file points at nothing.

`range_truncated` means "clipped to `max_range_lines`" and nothing else. It
never signals EOF clamping (`end_clamped`) nor byte-budget truncation
(`truncated`).

**Decoding.** Targets are decoded as UTF-8. A decode error, or an embedded NUL
byte, → `read_error` rather than mojibake `text`.

**The envelope rewrites some text, and the citation says so.** `wrapMcpData`
(`src/claudeintegration.cpp:11169`) sanitises every payload before it ships:
the literal `<ants_mcp_data>` close tag and its case/whitespace variants, the
open tag (ANTS-1670 M2), and the `<!--` / `-->` comment markers (ANTS-1996) are
each replaced with a visibly-modified inert form. That is correct and must not
be bypassed — it is what stops a hostile file line from closing the wrap — but
it means a cited line containing one of those tokens **arrives altered**, and
the files most likely to contain them are this project's own MCP sources and
standards docs, i.e. exactly what a reviewer cites. `read_region` answers this
with `raw:true`; § 2.1 declines that mode, so the answer here is disclosure: the
engine detects the tokens in a line it is about to emit and sets
**`text_escaped:true`** on that citation. The rewriting still happens
downstream, unchanged; the reader is simply told that what they are looking at
is not byte-exact. A verification tool that silently shows altered text is worse
than one that shows none.

`unresolved` is the one
unresolvable shape that lives in `citations[]` rather than `unparsed[]`,
because a bare continuation has a valid locus and is a citation the author
actually made — merely un-attributable — where an `unparsed[]` entry may be
prose that was never a citation at all.

// src/markdownscan.h — additions beside the existing fenceMask()
namespace MarkdownScan {

// One inline code span. Line indices are 0-based into the input list; column
// offsets are UTF-16 code units into their line, half-open [startCol, endCol),
// and name the span's CONTENT — the backtick delimiters are excluded.
// startLine == endLine for the overwhelming majority; a span may cross lines.
struct CodeSpan {
    int startLine, startCol, endLine, endCol;
};

// Every inline code span in the document, in document order.
//
// Whole-document, not per-line, because a CommonMark span may cross a newline
// (CommonMark spec § 6.1, not this doc) — the same reason ANTS-3635(a)
// rewrote docintegrity's maskInlineCode,
// which this shares its scanning rules with:
//   * a span cannot cross a blank line or a fenced-block line, so the forward
//     search for the closing run stops at either (hence the `fence` argument,
//     which the caller already has);
//   * the closing run must be the same length as the opening run
//     (``a`b`` closes on ``, not on the inner `);
//   * an opening run with no matching close is literal text and yields NO
//     span, so one stray backtick cannot swallow the rest of the document.
//
// doccitations needs the boundaries rather than a mask because two of its rules
// turn on them: a continuation must FILL a span (ANTS-3636 § 2.2) and an anchor
// must BE one (§ 2.5) — neither is answerable from blanked-out text.
QVector<CodeSpan> codeSpans(const QStringList &lines,
                            const QVector<bool> &fence);

// As fenceMask(lines), and additionally reports an unterminated fence:
// *unterminatedOpenerLine is set to the 1-based line of an unclosed opener, or
// 0 when every fence closed. Nullptr is accepted.
//
// An overload rather than a separate scanner (ANTS-3636 § 2.3): the mask alone
// cannot carry the fact, because the closer line is masked true too, so an
// unclosed fence and a fence closing on the final line produce identical
// masks. Deriving it a second time from fenceOpenerChar() would duplicate this
// function's list-container tracking (ANTS-3638) and could disagree with it.
QVector<bool> fenceMask(const QStringList &lines, int *unterminatedOpenerLine);

}

// without this they could only be asserted by inspection — which is how a
// spec ends up with an invariant nothing actually checks. Nullptr in
// production; the engine's only cost is a null test per operation.
struct Probe {
    int stats = 0;   // QFileInfo / isInsideProject probes of a candidate
    int opens = 0;   // target files actually read (cache misses)
};

struct Options {
    // Basename → project-relative paths, built by the CALLER (§ 2.4 step 2).
    // Passing it in keeps the engine Qt6::Core-pure and unit-testable without
    // a CodebaseIndex on disk; empty → steps 0/1/3/4/5 only.
    QHash<QString, QStringList> basenameIndex;
    // True when the index hit kMaxIndexFiles. The engine cannot learn this
    // from the map itself (a capped index still looks large), so it must be
    // passed in — it drives `basename_index_truncated` (INV-37).
    bool   basenameIndexTruncated = false;

    Only   only           = Only::All;   // request arg
    int    offset         = 0;           // request arg
    int    maxRangeLines  = 3;           // request arg, handler-clamped [1, 20]
    int    maxDocLines    = 20000;       // request arg, handler-clamped [1000, 50000]
    int    maxBytes       = 128 * 1024;  // request arg, handler-clamped [64 KiB, 4 MiB]

    int    maxCitations   = 400;         // engine-side, no request arg
    int    maxUnparsed    = 200;         // engine-side
    int    maxCandidates  = 8;           // engine-side
    int    maxRawChars    = 120;         // engine-side, bounds unparsed[] size
    int    maxTextChars   = 2000;        // engine-side, per EMITTED LINE (§ 2.6)
    int    maxTargetReads = 1000;        // engine-side, absolute read budget
    qint64 maxTargetBytes = 8 * 1024 * 1024;    // engine-side, on-disk bytes
    qint64 maxCacheBytes  = 24 * 1024 * 1024;   // engine-side, IN-MEMORY bytes

    Probe *probe = nullptr;              // test-only, see above
};

// Reads `docAbsPath`, resolves every citation under `rootCanonical`, returns
// the § 2.1 envelope including `ok` and `path` (so INV-16 can compare whole
// returns). Writes nothing; holds no cross-call state.
QJsonObject check(const QString &rootCanonical, const QString &docAbsPath,
                  const Options &opts = {});

}  // namespace DocCitations

**Reused:** `MarkdownScan::fenceMask` (via the new overload above);
`PathValidation::isInsideProject` (gate G) and `::validatePath` (handler);
`ants::resolveCallerCwdRoot` (`src/resolvedroot.h:63`); the basename map, built
by the handler in four steps, because `CodebaseIndex::fromJson` takes a parsed
object rather than a path (`src/codebaseindex.h:118`) — open
`CodebaseIndex::cachePathFor(rootCanonical)` (`:121`), `QJsonDocument::fromJson`
its bytes, hand the resulting object to `CodebaseIndex::fromJson`, then one pass
over `Index::files` keyed on `path.section('/', -1)`. No new
index, no new cache, no new disk artifact, so the ANTS-1439 cache-keying
contract is inherited rather than re-implemented. A cache that is absent,
unparseable, or version-mismatched yields an empty map; the verb never
cold-builds the index itself, because a multi-second build is the wrong thing
to do inside a read verb. `session_orient` refreshes it at session start
(ANTS-2140).

Degradation is **visible, not silent**, and the two degraded modes need
different signals. A *cold* cache yields an empty map: bare basenames fall to
`unparsed[]`, and `basename_index_size:0` says why. A *truncated* index (`Index::filesTruncated`, `src/codebaseindex.h:53`, set when
the walk hits either the `kMaxIndexFiles` ceiling of 5,000 (`:24`) or the
index's own byte cap) yields a large, healthy-looking map while any basename
beyond the cap silently falls through step 2 to step 4 — indistinguishable from
a genuine prose false positive. Size
alone cannot carry that, so the handler passes `basenameIndexTruncated` into
`Options` and the response carries **`basename_index_truncated`**. Without it a
project over 5,000 files would report real dead citations as unparseable prose
with every health field green.

**Explicitly NOT reused — `ReadRegion::extract`.** It was the obvious candidate
and does not fit, for three independent reasons: it opens and reads the file on
every call (defeating the line cache, § 5), it never reports the target's total
line count (so `file_lines` and the `out_of_range` predicate have no source),
and its `truncated` is byte-based where `range_truncated` is line-based. The
engine therefore reads each target once into the cache and slices from it —
which yields `file_lines` for free, since the read already walked the file.

**All six registration hooks are mandatory**, and they span **two** files — an
implementer who registers the verb and stops ships a red suite. The split is
easy to get wrong: `registerToolProvider` is called from `src/mainwindow.cpp`
(81 call-sites there, none in `claudeintegration.cpp`), while everything the
`tools/list` response carries is authored in `src/claudeintegration.cpp`.
`mcp-tools.md` step 1 and its "File note for steps 7–8" say so explicitly.

1. **`src/mainwindow.cpp`** — `registerToolProvider("doc_citations",
   ClaudeIntegration::CallerCwdContract::Required, rcDelegate(...))`, the
   three-argument form with the contract as the **second positional** argument
   (`doc_integrity`'s call sits at `src/mainwindow.cpp:5140`).

The remaining five are in `src/claudeintegration.cpp`:

2. `inputSchema` (`type:"object"`, `additionalProperties:false`, an explicit
   `required:["caller_cwd","path"]`, `makeEtagMatchProp()`, and a one-line
   description per property). Two prohibitions from `mcp-tools.md` step 11,
   which are **not** equally enforced — checked 2026-07-26, and the difference
   decides what INV-22 has to do:
   - A descriptor comment must not contain the literal `props["`, which makes
     the `mcp_dispatch_forward_completeness` scraper miscount schema
     properties. This one has a test already.
   - The `description` must not begin with `[`, because `processTools`
     prepends a `[<kind>] ` tag at runtime and a hand-written one would double
     it. **No existing test asserts this** —
     `tests/features/mcp_tool_prefix_tags` checks `kindForName` *coverage*
     (that no verb lands in the `other` bucket), not the description's first
     character. INV-22 therefore asserts it for this verb rather than assuming
     the suite would catch it.

   Overflow past the ~800 B guideline goes in a sibling `detail`.
3. `selection_hint` beside the descriptor — the one-line "when to use" that
   `tool_info {catalog:true}` surfaces per verb (the catalog builder reads it
   at `src/claudeintegration.cpp:10799-10813`; `doc_integrity`'s is at
   `:4111`). It is hand-authored per tool with no default, so a verb without
   one lists in the catalog with an empty hint — silently degrading the exact
   discovery surface `CLAUDE.md` points every session at. Tracked as a gap in
   the standard itself: ANTS-3645.
4. `kindForName` (`:10019`) — `tests/features/mcp_tool_prefix_tags` walks every
   registered name and fails the suite on an unbucketed verb.
5. The token-cost table (`:9927`, where `doc_integrity` sits). Also unlisted in
   `mcp-tools.md` — same gap, same ANTS-3645.
6. `callerCwdContractFor` (`:11478`) → `Required`, and `isEtagSupportedTool`
   (`:11662`). Drift between the contract table and the registration call is
   **refused in every build configuration** (ANTS-1834,
   `src/claudeintegration.cpp:1298-1300`); a debug build *additionally* aborts
   via `Q_ASSERT_X` (`:1319`).

**Not** a hook: the ANTS-2158 eager-load set (`kEagerVerbs`,
`tests/features/mcp_eager_load/`). That is a deliberately small curated list of
verbs replacing always-loaded built-ins like grep and Read; a review-time verb
called once per doc does not belong in it, and each entry costs every session
context.

  `missing_file` → `returned:2`, `count:10`, `counts.missing_file:3`.
- **INV-43** — Each emitted `text` line is capped at `maxTextChars` characters,
  and any citation with a clipped line carries `text_clipped:true`. *Test:*
  target whose line 1 is 5,000 characters and line 2 is 10, cited `:1-2` at the

  untouched, `text_clipped:true`; a target of only short lines → key absent.
- **INV-44** — `MarkdownScan::codeSpans` finds spans that cross a newline, and

  below it → zero spans, and (through the engine) the citations on the

- **INV-45** — A citation whose emitted text contains a token `wrapMcpData`

- **INV-46** — Past `maxTargetReads`, a citation needing a fresh read is

  third `read_error`, flag set; the same fixture at the default → three `ok`,

- **INV-47** — A well-formed but non-existent in-root `path` returns `ok:true`
  with an empty `citations[]` (matching ANTS-3601 INV-15), and a well-formed
  existing `path` returns the documented fields — `citations[]`, `counts`,

## 5. RAM / build cost

- **Per-target read cap.** A target over `maxTargetBytes` (8 MiB) is **not
  read**: it is `read_error`, with no `file_lines`. Without this the cache's
  bound would govern only *retention*, and a single in-root citation to a
  generated `.json` or a log would pull an unbounded `QStringList` into memory.
- **Target-file line cache**, keyed by resolved path, so a doc citing one file
  30 times reads it once. Bounded at **16 files or `maxCacheBytes`, whichever
  binds first**; past the bound, further targets are read without being cached
  — no eviction, no LRU churn, no unbounded growth.

  **`maxCacheBytes` is measured in memory, not on disk, and the distinction is
  a factor of three.** The cache holds `QStringList`s: Qt strings are UTF-16,
  so an ASCII source doubles on the way in, and every line carries a `QString`
  header plus its own allocation. An 8 MiB source of ~40-byte lines is ~200k
  lines ≈ 16 MiB of characters plus ~8 MiB of per-string overhead. Budgeting by
  file size would promise 8 MiB and deliver ~24 MiB. The accounting is
  `sum over cached files of (2 × on-disk bytes + 40 × line count)`, charged
  before insertion, with the cap at **24 MiB** so the number here is the number
  in RSS.

  **Worst-case peak, by that same formula applied to every buffer alive at
  once** — the earlier figure of 48 MiB charged the in-flight read at its
  on-disk size, which is the very mistake this bullet exists to correct:

  | Buffer | Bound | In memory |
  |---|---|---|
  | Line cache | `maxCacheBytes` | 24 MiB |
  | One in-flight target read | `maxTargetBytes` 8 MiB on disk | ~24 MiB |
  | The doc's own `QStringList` | `max_doc_lines` 50,000 × 96.6 B ≈ 4.8 MiB on disk | ~12 MiB |
  | Serialized response | `max_bytes` ceiling | 4 MiB |
  | **Peak** | | **~64 MiB** |

  A realistic call — one spec, a handful of small targets — is well under
  5 MiB. 64 MiB is the number that has to be defensible on a 32 GiB host that
  runs earlyoom, and it is, but only because `max_doc_lines` is capped at
  50,000 rather than 100,000: the 100,000 ceiling would have added ~12 MiB for
  a length no file in this project approaches.
- **Time is bounded by a counter, not by an argument.** Within the cache bound
  each distinct target is read once. Past it, INV-20 is explicit that a target
  is re-read *per citation*, so the worst case is
  `(citations past the cache bound) × (one target read)`. Deriving a bound on
  that product from `max_doc_lines` and `maxTargetBytes` is arithmetically true
  and practically useless — it permits 20,000 lines' worth of citations each
  pulling an 8 MiB read. So the product is bounded directly:
  **`maxTargetReads` (1,000)**, after which a citation needing a fresh read is
  `read_error` and `read_budget_exhausted` is set (§ 2.6, INV-46). The densest
  doc in the corpus needs 7. No wall-clock timeout is set: there is no network and no
  subprocess, and a mid-response timeout would produce exactly the half-truthful
  output this design rejects — a count is deterministic where a deadline is not,
  and determinism is what INV-16's byte-identity assertion needs.
- **Input guard**: a doc over `max_doc_lines` is scanned to that line only;
  `scanned_lines` reports the prefix, `doc_lines` the true length, and
  `truncated:true` is set — but **no `next_offset`**, because the tail was
  never examined and no page reaches it (INV-31). The default of 20,000 is
  sized for specs (the densest is 56 citations); the project's largest doc,
  `ROADMAP.md` at 27,046 lines and growing, therefore **is** truncated at the
  default and needs `max_doc_lines:30000` to scan whole. That is why the guard
  is a request argument rather than a fixed constant — a caller who needs the
  tail can ask for it, and nothing is permanently unreachable. The upper clamp
  of 50,000 keeps the doc's own `QStringList` bounded at ~12 MiB by the
  accounting above, and leaves `ROADMAP.md` most of a decade of headroom at its
  historical growth rate.
- **Response budget**: `max_bytes` (128 KiB default — lower than the
  read-family 512 KiB because the value here is a compact review artifact)
  bounds the **serialized response**. When it or `maxCitations` (400) binds,
  whole trailing `citations[]` entries are dropped — never a half-populated
  entry — `truncated:true` is set, and `next_offset` names where to resume.
  Neither touches `unparsed[]`, which is bounded instead by `maxUnparsed` (200)
  with each `raw` capped at `maxRawChars` (120), so that array cannot exceed
  ~40 KiB and always fits inside the 64 KiB `max_bytes` floor alongside at
  least one citation. That last clause is only true because `maxTextChars`
  (2,000) bounds a single citation's contribution to ~6 KB (§ 2.6): without it
  one entry could exceed the floor by itself and INV-35 would be unsatisfiable.
  `returned` is always the emitted length.
- **Text normalisation**: a trailing `\r` is stripped from every emitted line
  and before the § 2.5 comparison, so a CRLF target does not produce phantom
  mismatches.
- **Build**: one new `.cpp` in an existing static lib, plus two additions to
  the existing `markdownscan` header/source pair — `codeSpans` (~60 lines; it
  shares `maskInlineCode`'s multi-line scanning rules but returns boundaries
  instead of a mask) and a `fenceMask` overload (~5 lines, since it threads one
  out-parameter through the existing scanner rather than duplicating it). No
  new external dependency, no new target, and no new test bundle — both feature
  directories join bundles that already exist.

## 6. Out of scope

- **Request-side `expect` map** → **ANTS-3642**. § 2.5's derived anchor covers
  20% of what the verb harvests; the scripted-re-verification case the ROADMAP
  bullet names is genuinely unserved until this ships.
- **Directory / whole-corpus sweeps** → **ANTS-3643**. Needs a digest response
  shape (counts + stale subset, no text), which is a different contract.
- **The `~:N` spelling** → **ANTS-3646**. 10 corpus tokens across 4 files,
  currently invisible to both `count` and `unparsed[]` (§ 2.2).
- **Rewriting drifted citations.** A verb that edits line numbers in a doc is a
  different risk class; the drift may mean the *claim* moved, not the line.
  Not tracked — a deliberate non-goal.
- **Non-markdown *workflows*.** Scraping citations out of source comments
  (`// see foo.cpp:12`) as a review surface is out; the verb itself will read
  any UTF-8 text file handed to `path` (§ 2.1). Not tracked — a non-goal.
- **A reverse "which docs cite this file?" index.** That is a cache with an
  invalidation contract, and nothing has asked for it. Not tracked.

## Cold-eyes loop log

**Loop 1 (2026-07-26)** — 3 lanes (design / accuracy / conformance), two-tier;
accuracy lane accepted clean over 32 verification calls. **CRITICAL 4 · HIGH 7
· MEDIUM 12 · LOW 12 · INFO 3** — 35 verified, 1 dismissed. `CodebaseIndex::
serve` returns a `QJsonObject`, not an `Index`, so the named reuse could not
have worked; the `unparsed[]`/`unresolved`/`missing_file` three-way
contradiction was resolved by making the ladder total; `ReadRegion::extract`
was dropped as a reuse. The load-bearing correction: § 2.5's anchor idiom had
been asserted "dominant" and measures **22%** — `only:"stale"` as first drafted
would have dropped the unanchored 78% of healthy citations, making a filtered
view read "all clear" over citations that were never judged.

**Loop 2 (2026-07-26)** — same 3 lanes, re-briefed cold. **CRITICAL 6 · HIGH 6
· MEDIUM 14 · LOW 16 · INFO 3**. Loop 1's symlink guard was a **false security
claim**: `QFileInfo::isSymLink` inspects only the final component, so
`src/link/foo.cpp:1` would have been read. Replaced with gate G
(`PathValidation::isInsideProject`, which canonicalises every component). Also:
`counts` had no bucket for `unparsed[]`, so a cold index — which pushes ~72% of
the corpus into that array — was invisible, reproducing loop 1's own failure
one layer down.

**Loop 3 (2026-07-26)** — same 3 lanes, all dispatched straight to depth (loop
2's cheap breadth pass had cleared lanes the depth pass then found 6 CRITICALs
in). **CRITICAL 3 · HIGH 8 · MEDIUM 11 · LOW 22 · INFO 3** — 47 verified, 0
dismissed. All three lanes independently found the same registration-file
error. Two genuine design holes: the continuation grammar had no left-context
rule, so `09:45` in prose would have inherited an unrelated path and emitted
that file's real line 45 as `ok`; and INV-17 promised a resumable `next_offset`
for a cap that truncates the *scan*, not the list. Also the RAM budget counted
on-disk bytes for a cache of UTF-16 `QStringList`s (~3× understated), a
truncated index reported itself healthy, and an unterminated fence would have
blanked every later citation with `truncated:false`.

**Loop 4 (2026-07-26)** — same 3 lanes, re-briefed cold. **CRITICAL 4 · HIGH 5
· MEDIUM 12 · LOW 20 · INFO 5** — 46 verified, 0 dismissed.

Genuinely new findings, none cosmetic. `ROADMAP.md` is **27,024 lines**, not
the ~19.5k this spec had claimed, so the 20,000-line guard silently truncated
the very file used to justify it — and INV-31 had just made that truncation
unresumable, leaving the project's largest doc permanently half-checked. Fixed
by making `max_doc_lines` a request argument. The grammar had no leading-`/`
production, so ladder step 0's absolute-path branch was unreachable and INV-6
unsatisfiable. `Options` had no channel for the index-truncation fact INV-37
mandates a field for. `offset` was clamped against `count` in the handler,
which cannot know `count`. And three invariants were specified as "verb-level
calls" against a handler that needs a live MainWindow and therefore cannot be
called at all — ANTS-3601 had already solved this with extracted pure statics,
which § 2.7 now names.

**The finding that changed how this spec is maintained.** Six of loop 4's
defects were introduced by *loop 3's own fixes*, and every one had the same
shape: a passage was edited and the passages referencing it were not. The
worked example was replaced but the arithmetic beneath it still summed the old
one; a digit cap was written into the grammar and the prose in two forms that
disagree; a response field was mandated with no way to supply it. Across four
loops, roughly half of all findings have been this class — bookkeeping, not
design. The design core has been endorsed on review each time.

So loop 4's response was structural rather than another round of corrections.
The document was **consolidated**: argument addressed to previous reviewers was
removed (this log already owns that history), each rule is now stated exactly
once, and every fix was written against an explicit ledger of "what else must
agree with this", followed by a reconciliation pass over the cross-reference
pairs that had bitten before. Loops 1–3's habit of adding prose to defend each
fix was itself the mechanism generating the next loop's findings.

**Loop 5 (2026-07-26)** — same 3 lanes, re-briefed cold. **CRITICAL 4 · HIGH 6
· MEDIUM 10 · LOW 22 · INFO 0** — 42 verified, 0 dismissed.

*The ledger worked, partially.* The accuracy lane found **every `file:line`
citation exact**, and the design lane confirmed **all seven tracked
cross-reference pairs reconcile** — the first loop in five with no
edited-a-passage-and-left-its-neighbour defect. That class, which had produced
roughly half of every prior loop's findings, produced one.

*The one it produced defined the new rule.* Loop 4's fix had split the tests
across two bundles, citing ANTS-3601 as precedent — without opening ANTS-3601.
That verb uses **two** feature directories; the fix specified one, which cannot
build, because a directory owns one Suite name and its source is listed in one
bundle. The pair list could not catch this: both halves of the assertion were
internally consistent, and only the world disagreed. Hence the ledger's new
standing entry — *when a fix cites a precedent as its justification, open the
precedent*.

*Three findings were nobody's regression and are the loop's real value.*
Nothing capped the length of an emitted `text` line, so one minified line
defeated `max_bytes` entirely while INV-35 simultaneously required at least one
entry — the two rules were jointly unsatisfiable (now `maxTextChars` +
INV-43). `unterminated_fence` was specified as derivable from `fenceMask`,
which returns bare bools and masks the *closer* line true as well, making "open
at line 4" and "closed on the last line" byte-identical — as written it would
have false-alarmed on nearly every spec in this repo (now a `fenceMask`
overload + INV-36's third case). And the new `codeSpans` primitive was
specified line-scoped, which would have re-introduced ANTS-3635(a), a
multi-line-span defect this project has already paid to find once (now
whole-document + INV-44).

*Two smaller ones worth recording.* The MCP envelope sanitises `<ants_mcp_data>`
and `<!--`/`-->` out of every payload, so cited text from this project's own MCP
sources arrives **altered** — in a verb whose entire product is "here is what
that line says" (now `text_escaped` + INV-45). And the anchor coverage figure
was 22% *of one scan's denominator*, quietly reused as though it applied to
everything the verb harvests; measured against the real harvest it is **20%**,
and the continuations that make up the difference had never been counted at all.

*Finally, a small piece of self-demonstration, kept deliberately.* § 2.5's
"healthy anchor idiom" example is itself drifted — `filterControlChars` has
moved to `remotecontrol.h:127`, outside the range the example cites. It is
retained and relabelled as a live `anchor_found:false`, because a spec arguing
that citations rot silently should not illustrate the point with citations that
happen not to have.
