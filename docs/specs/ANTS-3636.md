# ANTS-3636 — `doc_citations`: resolve a doc's `path:line` citations and return the cited text

**Status:** spec draft (2026-07-27).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-3636 (OneUp_Ants_MCP_Feedback.md, 2026-07-26 addendum).
**Blocked by:** ANTS-3649 — the `MarkdownScan` hoist this verb consumes (§ 2.7);
ANTS-3653 — the citation scan whose token list this spec's resolution ladder
takes as input (§ 2.2).
**Extended by:** ANTS-3654 — the anchor-symbol drift check and `only:"stale"`
filter (§ 2.5). Optional; this verb is complete without it.
**Composes with:** ANTS-3601 (`doc_integrity` — shares the fence primitives),
ANTS-1637 (`codebase_index` — the basename→path map).
**Pairs with:** ANTS-3596, which hardened `docs/specs/ANTS-2161.md` by hand —
converting its approximate anchors to symbol references while deliberately
leaving the loop log's historical line citations in place. This verb
generalises the motivation, not the fix.
**Blocker for:** ANTS-3642 (request-side `expect` map), ANTS-3643 (corpus-wide
digest mode).

**Layman:** Design docs are full of "see `file.cpp`, line 200" pointers that rot
silently as code moves; this adds one call that looks every pointer up and shows
what is on those lines today.

---

## 1. Problem

Global rule 13 requires every doc claim naming a file, line, function, or
constant to be checked against live source rather than recalled. `/cold-eyes`
runs that check on every loop, for every reviewer, on every doc. There is no
verb for it, so it is done by hand or skipped — and when it is skipped, the
loop ratifies a stale line number and the next reader is sent to the wrong
place.

The reporting session (OneUp) hit this directly: verifying one spec meant
resolving 33 `updater.py:NNN` citations, and they wrote a throwaway Python
script because no verb existed. `read_regions` is the closest fit but takes a
hand-extracted list of `{path, start_line, end_line}` — and extracting that
list *is* the tedious part.

**The corpus is large enough that hand-verification does not scale.** Measured
2026-07-26 over `docs/`, excluding this spec, by the commands below — recorded
inline because a number without its command is the kind of claim this verb
exists to catch. Three scans with different regexes run here, so each row names
its own denominator.

| Shape | Count | Of what |
|---|---:|---|
| `path.ext:N` citations (scan **P**) | 1,934 in 167 docs | — |
| …carrying a directory component (`src/foo.cpp:12`) | 551 | 28% of scan P |
| …**bare basename** (`foo.cpp:12`) | 1,383 | **72% of scan P** |
| Line **ranges** (`:208-228` or en-dash `:208–228`) | 673 | 35% of scan P |
| Multi-locus / open-ended (`:262/265/286`, `:5669+`) | 38 | 2% of scan P |
| Approximate (`:~752`) | 10 | <1% of scan P |
| Citations opening a code span (`` `foo.cpp:12` ``) — scan **S** | 1,791 | — |
| …preceded by an identifier code span (ANTS-3654 § 2) | 388 | 22% of scan S |
| Bare continuations (`` `:548-549` ``, path inherited) — scan **C** | 727 in 78 files | not in scan P (no dotted path to match) |
| …themselves preceded by an identifier code span | 138 | 19% of scan C |

```bash
E='--include=*.md --exclude=ANTS-3636.md'
P='[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:[0-9]+'
grep -rhoE "$P" docs/ $E | wc -l                      # scan P total    1934
grep -rhoE "$P" docs/ $E | grep -c '/'                # with directory   551
grep -rhoE "$P(-|–)~?[0-9]+" docs/ $E | wc -l         # ranges           673
grep -rhoE "$P(/[0-9]+|\+)" docs/ $E | wc -l          # multi-locus       38
grep -rhoE '[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:~[0-9]+' docs/ $E | wc -l   # approximate 10
grep -rhoE "\`$P" docs/ $E | wc -l                    # scan S          1791
C='`:~?[0-9]+(-|–)?~?[0-9]*`'
A="\`[A-Za-z_][A-Za-z0-9_:]*\`[^\`]{0,40}"
grep -rhoE "$A\`$P" docs/ $E | wc -l                  # anchored         388
grep -rhoE "$C" docs/ $E | wc -l                      # scan C           727
grep -rhoE "$A$C" docs/ $E | wc -l                    # anchored conts   138

# tokens the greps see but the verb will not (ANTS-3653 § 3) — 42
find docs -name '*.md' ! -name 'ANTS-3636.md' -print0 | xargs -0 awk '
  FNR==1 { infence=0 }
  /^[ ]{0,3}(```|~~~)/ { infence = !infence; next }
  infence { n += gsub(/[A-Za-z0-9_.@+\/-]+\.[A-Za-z]{1,5}:[0-9]+/, "&") }
  END { print n }'
```

**Anchorable total, worked — and this section owns the arithmetic; nothing
below restates it.** The verb harvests scan P plus scan C, less what fences
hide: `1,934 + 727 − 42 ≈ 2,619`. Of those, `388 + 138 = 526` carry a checkable
anchor — **20%**.

Three caveats, all in the same direction, so **2,619 is a ceiling and 20% a
floor**. The greps do not skip fenced blocks and the verb does, which is what
the 42 corrects — but the awk counts only *path-bearing* fenced tokens, so
fenced continuations stay in the 727 and are never subtracted. And `$P` is
narrower than ANTS-3653 § 2's grammar (it demands a 1–5-letter extension where the
grammar demands only a dot in the final segment); re-measuring without that
restriction adds 2 tokens to scan P and 3 to scan C. Left uncorrected because
an exact fence-aware count is only obtainable from the implementation this spec
describes, and a verification tool should err toward under-claiming its own
coverage.

Densest single doc: `docs/specs/ANTS-1750.md` — **56 citation occurrences, 10
distinct written spellings, 7 distinct basenames**, three of the spellings bare
basenames of `src/`-qualified siblings. Largest: `ROADMAP.md` at **27,167 lines
and growing monotonically**, 680 of them carrying a citation-shaped token. Both
`ROADMAP.md` figures are floors that rise every session, which is the point:
§ 5's guard sizing must read them that way rather than as fixed facts.

```bash
D=docs/specs/ANTS-1750.md      # all 2026-07-26; $P is the block above's
grep -ohE "$P" $D | wc -l                                          # 56
grep -ohE "$P" $D | sed 's/:[0-9]*$//' | sort -u | wc -l           # 10
grep -ohE "$P" $D | sed 's/:[0-9]*$//;s#.*/##' | sort -u | wc -l   #  7
wc -l ROADMAP.md                                                   # 27167
grep -cE '[A-Za-z0-9_.@+-]+\.[A-Za-z0-9]+:[0-9]+' ROADMAP.md       # 680 LINES
```

Three consequences follow, and they shape the design:

1. **Existence checking is not enough.** A citation that has drifted onto an
   unrelated statement still points at a line that exists; only the cited *text*
   exposes that, which is why the text is the load-bearing output rather than an
   option. A live instance found while writing this spec:
   `docs/specs/ANTS-2090.md` claims `isFieldProjectionTool` gates
   `compactEnvelope` at `mcpprojection.cpp:28`, but that line is today blank —
   it falls between the close of `terseDefault()` and the ANTS-3550 hint-latch
   comment block, with `claimHint()` the next function. Every existence-based
   check passes; the claim is false. Tracked for repair as ANTS-3641.
2. **Bare basenames are the common case, not an edge case.** A resolver that
   only handled repo-relative paths would silently skip 72% of scan P — worse
   than no verb, because the empty result reads as "all clear".
3. **No mechanical signal covers most citations.** Only the 20% above carry a
   nearby identifier the verb can check the text against (ANTS-3654 § 2), and the
   remainder splits two ways: *resolved and shown but not judged*, and not shown
   at all — a bare basename the index does not cover resolves nowhere **unless
   it sits at the repo root**, which ladder step 3 catches (§ 2.4), and
   otherwise lands in `unparsed[]`. Neither group may be mistaken for a verified
   one, and they need different fields to say so: `unchecked` and
   `counts.unparsed`, whose denominators § 2.1 pins.

## 2. Surface

### 2.1 Verb shape

New verb `doc_citations`, **not** a mode on `doc_integrity`: that verb's
contract is a *defect list* (`findings[]` + `counts{}` narrowed together by
`kinds` — ANTS-3601 INV-18, `RemoteControl::docIntegrityBuildResponse`), while
this one *enumerates every citation with its text*, most of them healthy.
Folding an enumeration into a findings verb would either break `kinds`/`counts`
or bury the payload. They share only `MarkdownScan`'s fence and code-span
primitives (ANTS-3653 § 3).

The nearer neighbour is `FeatureCoverage::runContractDocDriftCheck` — the
`contract_doc_drift` audit lane — and the two are complementary.
`contract_doc_drift` asks *does this identifier exist anywhere in the repo*;
this verb asks *does the line this doc points at still say what the doc
claims*. Neither subsumes the other: § 1's `mcpprojection.cpp:28` case passes
`contract_doc_drift` cleanly, because `isFieldProjectionTool` does still exist
— just not there. A divergence recorded, not a duplication to resolve.

Request:

```jsonc
{
  "caller_cwd":       "<required>",         // CallerCwdContract::Required
  "path":             "docs/specs/x.md",    // required, a FILE
  "only":             "all" | "stale",      // filter over citations[]
  "offset":           <int>,                // 0-based into the post-filter list
  "max_range_lines":  <int>,                // every default and clamp lives in
  "max_bytes":        <int>,                //   ONE place — § 2.7's `Options`
  "max_doc_lines":    <int>,                //   block, never in prose here
  "encoding":         "json" | "tabular",   // ANTS-2090, dispatcher-side
  "etag_match":       "<opt>"
}
```

Each `snake_case` request argument maps onto the `camelCase` `Options` field of
the same name (`max_bytes` → `Options::maxBytes`); the split is the layer
boundary, and `docCitationsClampOptions` (§ 2.7) is where it is crossed.

**That is the whole request surface.** Every other bound *this verb sets* is an
engine-side `Options` default with no request argument, because each guards the
engine rather than shaping the caller's view. **§ 2.7's `Options` block is the
single source of every such limit's value and clamp.** No prose in this spec
restates one; § 5's budget arithmetic is the sole exception, and there every
operand names the field it came from. A bound of this verb's named anywhere in
this document but absent from that block is a specification defect — a literal
an implementer must invent and a test cannot vary. (Limits owned by *other*
subsystems, such as `codebase_index`'s `kMaxIndexFiles`, are cited as external
facts and are not this rule's business.)

Clamping lives in the handler (`docCitationsClampOptions`, § 2.7), never in the
engine, so a unit test's direct engine call is not silently re-clamped; `offset`
alone has no upper clamp, since that bound is `count`, which the handler has not
computed (INV-21, INV-38).

**Out-of-domain values coerce; they do not refuse.** An unrecognised `only`
becomes `"all"`; a wrong-typed numeric falls back to its default rather than to
a clamp endpoint. This keeps INV-18's refusal set at exactly five by giving
every other malformed input a defined destination, and it errs toward the
unfiltered view — the safe direction for a verb whose failure mode is
under-reporting drift.

`path` must name a single **file**:

| Condition | Outcome |
|---|---|
| no focused project — `rootCanonical` arrives empty | refuse `bad_path` |
| `path` absent or empty | refuse `missing_field` |
| `path` escapes the project root | refuse `bad_path` |
| `path` is a directory | refuse `bad_args` |
| in-root, does not exist | `ok:true`; every field below present, `citations[]` / `unparsed[]` empty, all `counts` and `count` / `returned` / `doc_lines` / `scanned_lines` / `unparsed_total` **0**, `path` echoed as given, `only` / `offset` echoed as coerced, `basename_index_size` the real index size, `truncated:false` (INV-47) |
| exists, but unreadable or over `maxDocBytes` | refuse `read_failed` (from `QFileInfo` in the handler) |
| exists, but not decodable as UTF-8 | refuse `read_failed` (from the engine, which is reading it anyway — § 2.7) |

Six refusing rows, five refusal *branches* in the handler: the first five are
`docCitationsValidate`'s whole set (INV-18), and the undecodable-doc row raises
the same `read_failed` from the engine, which is reading the file anyway.
`caller_cwd` is in neither: `CallerCwdContract::Required` (§ 2.7 hook 1) makes
the dispatcher refuse `caller_cwd_required` before the handler runs (INV-48).

Three notes on how this table sits beside `doc_integrity`, called out because
the verbs run in the same review loop where a silent difference is a caller
trap. **One row diverges deliberately:** `doc_integrity` *accepts* a directory
and walks it (ANTS-3601 INV-16); this verb refuses, because its payload is
per-citation *text* and `docs/` holds the whole corpus § 1 counts — the refusal
names the file-only requirement and points at ANTS-3643's sweep mode.
`bad_args` is the closest generic fit, not an exact one; minting a code for one
verb is not worth amending `mcp-error-codes.md` for. **A second differs in
default:** an absent `path` refuses `missing_field` here, where
`RemoteControl::cmdDocIntegrity` treats it as "walk the project's `docs_dir`".
**The empty-result row converges:** it matches ANTS-3601 INV-15 rather than
refusing, because companion verbs should answer a typo'd path the same way.

An undecodable **doc** ends the call; an undecodable **target** is a per-row
`read_error` (§ 2.6). A target that fails to decode costs one row; a doc that
fails to decode leaves nothing to enumerate.

`dry_run` does not apply — the verb writes nothing (INV-16). `path` need not be
`.md`; any UTF-8 text file is scanned, and § 6's "non-markdown workflows"
non-goal is about the *workflow*, not an input guard.

Response. **A synthetic fixture, not a live capture** — every field but
`basename_index_size` and the `candidates[]` set is derivable from the rules
below by inspection, so it cannot rot the way a captured example in *this* spec
would. Those two are live, and are re-measured with the command below. Six
citation-shaped tokens (anchored-and-matching, a dead file, an ambiguous bare
basename, an anchor that no longer matches, an unanchored one, and a prose false
positive), called with `only:"stale"`:

```jsonc
{

  "path": "fixture.md",
  "doc_lines": 13,                         // the doc's true length
  "scanned_lines": 13,                     // < doc_lines when max_doc_lines binds
  "citations": [
    {
      "doc_line": 5,

    }

  "count": 5,                              // citations found in the scanned prefix
  "counts": { "ok": 3, "missing_file": 1, "out_of_range": 0, "read_error": 0,
              "ambiguous": 1, "unresolved": 0,
              "anchor_missing": 1, "unchecked": 1, "unparsed": 1 },
  "unparsed": [ { "doc_line": 13, "raw": "6.2:1", "reason": "unresolvable" } ],

```

`only` and `offset` echo the values the engine actually received — `only` after
coercion, `offset` after its clamp — so a page saved to a file or handed to
another session can say which slice of which view it is (the `workspace_search`
precedent).

**`basename_index_size` is the number of distinct basenames** —
`Options::basenameIndex.size()`, not the file count, since 14 files named
`bad.cpp` occupy one key. Measured 2026-07-26 **from the index's own cache**,
not from a hand-rolled directory walk (the walk's file set is the index's, so
guessing at it produces a number that does not reproduce):

```bash
python3 -c 'import json,glob,os,collections
for p in glob.glob(os.path.expanduser("~/.cache/ants-terminal/codebase-index/*.json")):
    d=json.load(open(p))
    if "Ants_Terminal" not in (d.get("root_canonical") or ""): continue
    f=[x["path"] for x in d["files"]]
    c=collections.Counter(os.path.basename(x) for x in f)
    print(len(f), len(c), c.most_common(3))'   # → 762 730 [(bad.cpp,14),(good.cpp,14),(bad.c,4)]
```

So **762 indexed files collapse to 730 keys** — the field is the map's size
because that is what governs whether ladder step 2 can answer. That 730 and the
14-way `bad.cpp` collision are the block's only live measurements, and the
`most_common` tail confirms the collision is the repo's largest today, so an
implementer sees the candidate cap fire on a condition this repo contains.

The JSON is the tool's payload; the dispatcher applies the standard ANTS-1294
`<ants_mcp_data>` wrap (`mcp-tools.md` step 5). That wrap **rewrites some cited
text**, which § 2.6's `text_escaped` discloses.

**Field emission.** `ok` and `truncated` are **always emitted, including when
false**. So is per-citation `anchor_found` — but only on a citation that was
anchor-*checked*: `anchor_found:false` is the drift signal this verb exists to
produce and what `only:"stale"` selects on, so a blanket omit-when-false rule
would delete it, while `anchor_symbol` and `anchor_found` are absent *together*
whenever there was nothing to check — no anchor in range, or a status that emits
no text (ANTS-3654 § 2, ANTS-3654 INV-13). "Absent" and "false" are different answers, and only
the second one means *checked*. `candidates_total` is emitted whenever
`candidates[]` is.

Every other **flag** is omitted when false — eight per citation, one per
`unparsed[]` entry, three top-level: per citation `range_truncated`,
`end_clamped`, `inherited_path`, `approximate`, `partial`, `text_clipped`,
`text_escaped`, `truncated_candidates`; per `unparsed[]` entry `raw_clipped`;
top-level `basename_index_truncated`, `read_budget_exhausted`, and
`unterminated_fence` (absent, never `0`). At the `maxCitations` ceiling the
eight per-entry flags would otherwise cost thousands of always-false keys on a
verb whose premise is frugality.

**Every truncation sets a flag** — silently shortened output is the one thing a
verification tool must never emit. `maxCitations` and `max_bytes` set top-level
`truncated`; `max_doc_lines` and `maxUnparsed` also set it (see the table
below); `max_range_lines` sets `range_truncated`, `maxTextBytes` sets
`text_clipped`, `maxCandidates` sets `truncated_candidates`, and `maxRawChars`
sets `raw_clipped`. Only the first four are response-level: `truncated` never
reflects a per-entry cap.

**Tallies**, checked against the fixture above. The six `status` keys partition
`count` (`3+1+0+0+1+0 = 5`). `anchor_missing` and `unchecked` are **overlays on
the `ok` subset**, not statuses — an anchor whose needle was not found, and no
anchor at all (shown, never judged) — so `counts.ok` = anchored-and-found +
`anchor_missing` + `unchecked` (`3 = 1+1+1`). `counts.unparsed` mirrors
`unparsed_total` and sits **outside** `count`. `count` and `counts` are whole-doc
(pre-`only`, pre-`offset`) over the scanned prefix; `returned` is the emitted
length (INV-42, ANTS-3654 INV-14).

`counts.unchecked` is the honesty field, and its **denominator is `counts.ok`,
not the document** — "how much of what I showed you did I judge", 1 of 3 in the
fixture. § 1's 20% is a different ratio over a strictly larger population —
"how much of what exists could ever be judged" — and the two must not be read as
one. `counts.unparsed` covers the other shortfall, which `basename_index_size`
explains: a cold codebase index (§ 2.7) pushes bare basenames, 72% of scan P,
into `unparsed[]`, and a reader who cannot see that the index was empty would
read the shortfall as a clean doc.

`only:"stale"` keeps every non-`ok` citation plus every `ok` one with
`anchor_found:false` (ANTS-3654 INV-14). `counts` stays unfiltered, so a caller reading
only the filtered list is misreading rather than mis-served.

This is the ROADMAP bullet's `stale[]`, reshaped as a filter over one array plus
unfiltered counts so the healthy majority stays addressable in the same call,
and broader than the bullet's "missing or out of range" — it keeps anchor drift
too. The bullet's sketch keys are renamed: `cited_path` → `path`, `cited_line` →
`start_line`, and the boolean `exists` → the six-valued `status` (a boolean
cannot separate a dead file from an ambiguous basename from a line past EOF).

**Order is document order** — ascending `doc_line`, then ascending column of the
citation's first character; `unparsed[]` likewise (ANTS-3653 INV-33). `offset` paging is
only meaningful over a defined order, and ANTS-3653 INV-29 mandates two separate entries
for two citations on one line.

**The emission caps bound what is emitted, not what is examined** (INV-42): the
bound on *work* is `max_doc_lines` plus the line cache, the bound on *response
size* is `max_bytes`. Two consequences, both chosen. Because INV-16 forbids
cross-call state, paging re-resolves and re-reads the whole doc on every page —
cheap even at the corpus's densest doc (§ 1). And **paging is not atomic**: each
page is an independent resolution of the doc *as it is at that moment*, so if
the doc or a cited target is edited between calls, an entry can be seen twice or
missed entirely and `count` can move. Callers needing a consistent view raise
`max_bytes` and take one page; callers that page compare `count` across pages
and restart if it moved. The alternative — a server-side snapshot with an expiry
contract — is far more machinery than a 56-citation worst case justifies.

**`unparsed[]` is never filtered by `only`, never trimmed by `max_bytes`, and
has no pagination.** Its bounds are `maxUnparsed` and per-entry `maxRawChars`
(§ 2.7), which together keep it small enough that `max_bytes` never needs to
touch it (§ 5 does the arithmetic). When `maxUnparsed` binds, `unparsed_total`
still reports the true count, so the loss is *countable* even though no `offset`
retrieves those entries. If that array ever needs paging, that is ANTS-3643's
digest shape.

`offset` pages the post-filter list and **is applied before the emission caps**:
filter by `only`, drop the first `offset` entries, then fill the page until a cap
binds. That is what makes `next_offset == offset + returned` correct and every
entry reachable — under the reverse order nothing past `maxCitations` could ever
be fetched. `next_offset` is emitted **exactly when a resumable cap dropped
trailing entries** (the `roadmap_query` / `workspace_search` precedent), so
`truncated:true` has three causes that it alone does not separate:

| Cause | `next_offset` when this is the only cause | How to tell | Resumable by paging |
|---|---|---|---|
| `maxCitations` / `max_bytes` | emitted | `next_offset` present | yes |
| `max_doc_lines` | absent | `scanned_lines < doc_lines` | no — raise `max_doc_lines` |
| `maxUnparsed` | absent | `unparsed_total > unparsed.length` | no — that array has no paging |

**The three causes are not mutually exclusive, and `next_offset` turns on the
resumable one alone.** A doc can hit `max_doc_lines` *and* overflow
`max_bytes` inside the prefix that was scanned; `next_offset` is emitted then,
because the entries it resumes are the ones that were found and dropped. It
says "there is more of *this page's* list", never "the whole doc was scanned" —
`scanned_lines < doc_lines` is the only field that answers that, and it stays
set. Suppressing `next_offset` because a scan-level cap also bound would strand
the citations that *were* found, which is the silent shortening this section
forbids. The two `next_offset`-absent rows each carry their own evidence field,
which is why those fields are always emitted. A caller treating `truncated:true`
as one condition mis-handles two of the three.

**`fields=` and `raw:true` are not adopted; `encoding:"tabular"` is.** Staying
out of `mcp::isFieldProjectionTool` — which `doc_integrity` also stays out of —
is *required* here, not merely economical: that helper is what gates the
dispatcher's `compact` pass, which `mcp::terseDefault()` turns on by default and
which drops every `false` value outside its protected set
(`ok`/`code`/`error`/`etag`/`found`/`unchanged`). Enrolling this verb would
therefore delete `anchor_found:false` and `truncated:false`, the two fields the
emission rules above require present when false. `only` + `offset` cover the
narrowing instead. Raw mode's verbatim-bytes frame (`mcp::isRawEligible`) is the
wrong shape for a structured envelope in which file text is one field among
many. **`encoding:"tabular"` (ANTS-2090) is adopted** — declared with the shared
`makeEncodingProp()`, so `additionalProperties:false` admits it (INV-22).
`mcp::tabularize` runs dispatcher-side on the finished response, so the engine
and `docCitationsClampOptions` never see it and `max_bytes` bounds the
pre-repack body; it is self-guarding per array, repacking `citations[]` and
`unparsed[]` only at ≥2 object elements and only when the columnar form is
smaller; and a `false` cell survives as `false` while an absent key becomes a
`null` that decodes back to absent — so neither always-emitted signal is at
risk.

The dispatcher-injected `etag` (`mcp-tools.md` step 7) hashes the **response**,
so an unchanged etag means every field the response *reports* is unchanged —
verdicts included, since `anchor_found` is computed over the full resolved range
(ANTS-3654 § 2) rather than the clipped `text`, so a tail edit that flips a verdict does
change it. It does **not** mean the cited files are unchanged: an edit inside the
unshown tail that changes no reported field leaves the etag equal. Read it as
"my answer is the same", never "the target is the same".

### 2.2 Citation grammar · 2.3 Scrape rule — *moved to ANTS-3653*

The two-stage recognise/validate grammar, the maximal-munch left edge, the
five grammar constraints, en dash, trailing loci, `~`, the `~:N` gap, fence
masking, unterminated-fence reporting and the inline-span policy inversion
are specified in **ANTS-3653 § 2 and § 3**. That layer is a pure function —
document text in, citation tokens out — and it carries INV-1, 2, 3, 9, 10,
24, 29, 32, 33, 36, 39 and 40.

This spec consumes its output: an ordered token list, each entry with its
`raw`, `doc_line`, path text or continuation marker, loci, and the
`approximate` / `partial` / `raw_clipped` flags, plus the `unparsed[]`
entries for tokens that recognise but fail validation. Everything from the
resolution ladder onward is this document.
### 2.4 Path resolution ladder

Applied in order; first hit wins. Every terminal step names where the entry
lands, so the ladder is total.

| # | Condition | Filesystem | Outcome |
|---|---|---|---|
| 0 | **Lexical reject** — leading `/`, or lexically escaping root (`../..`) | none | `unparsed[]`, `reason:"out_of_root"` |
| 1 | Contains `/` → project-relative from the repo root | stat | regular file → gate G; else → `missing_file` |
| 2 | Bare basename, exactly one match in `basenameIndex` | stat | regular file → gate G; else → `missing_file` |
| 2b | Bare basename, ≥2 matches | none | `ambiguous` + `candidates[]` |
| 3 | Bare basename, not indexed, `<root>/<basename>` exists | stat | regular file → gate G; else → step 4 |
| 4 | A **bare basename** that steps 2–3 did not match | none | `unparsed[]`, `reason:"unresolvable"` |
| 5 | **No filename at all** — a continuation, and ANTS-3653 § 2 found no antecedent | none | `citations[]`, `status:"unresolved"` |
| G | **Gate G** — the candidate's canonical path is in-root | canonicalise | true → the read step (§ 2.6); false → `unparsed[]`, `reason:"out_of_root"` |

**Three shapes, and the word "bare" alone does not separate them.** A citation
is **directory-bearing** (`src/a.cpp:1` — contains a `/`), a **bare basename**
(`a.cpp:1` — a filename, no `/`), or a **continuation** (`:1` — no filename at
all). The first two both carry a filename and differ only in which step decides
them; the third carries none, which is why it is the only shape that can reach
step 5. **Step 1 is terminal in both its branches**, and so is gate G's, so a
directory-bearing citation never reaches step 4 — only a bare basename can fall
that far. Where this document says "bare" **of a citation** it always names
which of the last two it means.

**A continuation with an antecedent never enters this ladder.** § 2.4's sticky
rule hands it an already-*resolved* path, so steps 0–4 have nothing left to
decide — it goes straight to the read step and computes its own status from
there (INV-7). Only an antecedent-less continuation reaches step 5.

**The stat is a regular-file test, not an existence test.** The grammar's only
requirement is a dot in the final segment, which a directory can satisfy
(`src/build.d:12`, `docs/assets.old:3`). Testing existence alone would send a
directory to the read path, where its status would be decided by whatever the
platform returns from opening one.

**Directory-bearing and bare-basename citations resolve asymmetrically, and it
biases a count.** Only step *3*'s else falls through to step 4 →
`unparsed[]`/`unresolvable`. Step **2**'s else is `missing_file` like step 1's,
and for the same reason: the index asserted a specific path, so its absence is a
definite claim about a specific file. That case is real but uncommon — it needs
an index entry stale since the last refresh.

So in the common case `src/build.d:12` (a directory) and `src/gone.cpp:1` (a
dead file) are `missing_file` while `build.d:12` and `gone.cpp:1` are not. Both
populations are drift, but only the first is a *definite* file claim: an
unindexed bare token resolving to no file is indistinguishable from prose
(`6.2:1`), and guessing would put false `missing_file` findings in front of a
reviewer. `counts.missing_file` therefore under-reports the bare majority in the
common case, and `counts.unparsed` / `unparsed[]` are where that population is
visible. The directory examples above are written directory-bearing so they
exercise the branch they illustrate.

**Gate G — the anchor re-check, applied to every existing candidate before it
is read.** `PathValidation::isInsideProject(rootCanonical, candidate)`
(`src/pathvalidation.h`, ANTS-1832) canonicalises *both* sides and returns a
bare boolean, building no error envelope.

Gate G is where the symlink case is closed, and it is a **separate step from
the lexical step 0** for a reason worth stating: a `QFileInfo::isSymLink` check
would inspect only the *final* component, so `src/link/foo.cpp:1` where
`src/link` is a symlink to `/etc` would pass it. Canonicalisation resolves
every component. It costs one canonicalisation of a candidate that is about to
be read anyway (the root's own is the second half of the same call, on a path
already canonical) — the "never probe" rule (ANTS-3601 INV-6's posture) binds
*lexically out-of-root* shapes, which step 0 rejects with zero filesystem
calls. `isInsideProject` returns false for a non-existent candidate, so gate G
runs only after existence is established; a missing file is `missing_file`,
never mis-reported as an escape.

`PathValidation::validatePath` is deliberately **not** used per-citation: its
product is a whole-response `bad_path` envelope, the wrong granularity for one
citation among § 1's 33. It still applies, unchanged, to the request's own `path`
argument at the handler. A citation target is not a "path-typed arg" in
`mcp-tools.md` step 4's sense — it is scraped file content — so the contract is
discharged at the handler and gate G is the defence in depth.

**What step 2 can and cannot see.** The `basenameIndex` is built from the
codebase index, whose walk is `source_roots` + `test_roots` — `src/` and
`tests/` by default, widened when a project declares them in
`.ants/project.json` (ANTS-2160). Step 3 adds repo-root files, which is what
catches `CMakeLists.txt:148` and `README.md:…`. **The walk filters four ways,
and two of them matter here**: it visits only those roots, *and* within them
only files whose extension `CodebaseIndex::isIndexableSuffix` admits. (The
other two — `QDir::NoSymLinks`, and `ProjectSettings::isNoiseDir` pruning of
`node_modules` / `vendor` / `venv` / `build*` per path component, ANTS-3393 —
are no-ops on this repo's `src/` + `tests/`, but bite on a project that widens
`source_roots`.) So a bare
basename misses step 2 for either reason: `mcp-tools.md:12` under
`docs/standards/` and `safe-build.sh:20` under `tools/` are outside the roots,
but a `spec.md:12` or `run.sh:3` **under `src/` or `tests/` is equally
invisible**, because that predicate does not admit `.md` or `.sh`. Measured over
the same scan: of 1,383 bare basenames, **180 (13%) carry a non-indexable
extension** — 67 `.md`, 58 `.txt`, 45 `.sh`, 7 `.yml`, 2 `.com`, 1 `.xml`:

```bash
grep -rhoE "$P" docs/ $E | grep -v '/' \
  | grep -oE '\.[A-Za-z0-9]+:' | sort | uniq -c | sort -rn   # 2026-07-26
```

Each falls to step 3, and to step 4 unless it sits at the repo root. So § 1
consequence 2's gap is *narrowed*, not closed, and `count` under-reports those.
Stated rather than papered over, because a reader comparing `count` against a
hand tally will otherwise find the difference and mistrust the rest.

Step 4 is the **only** producer of `reason:"unresolvable"`, and step 5 the
**only** producer of `status:"unresolved"`. Step 4 is *not* the only producer of
`unparsed[]` entries — step 0 and gate G both emit `reason:"out_of_root"` there,
and the grammar emits `reason:"bad_locus"` before the ladder runs at all. Three
reasons, four producers. A prose false positive like `` `6.2:1` `` (path part
`6.2` — it contains a dot, so the grammar admits it) lands at step 4, not in
`citations[]`.

**Ambiguity is reported, never resolved by guessing.** `src/` is flat (no
subdirectories) so in-lane collisions are impossible today, but the indexed
tree holds 14 `good.cpp` and 14 `bad.cpp` under `tests/audit_fixtures/`
(§ 2.1's command). `candidates[]` is sorted on the project-relative path by
**UTF-16 code unit (`QString::operator<`), not locale collation** — the same
choice ANTS-2120 forced elsewhere, because CI runs under `C.UTF-8` while a
developer's desktop does not, and a locale-sensitive sort would make the cap
select a *different* set of candidates on the two machines. It is capped at
`maxCandidates`, with `candidates_total` giving the true match count and
`truncated_candidates:true` beyond the cap. `TestAuditEngine` merges such
collisions by picking the longest path (its basename merge,
`src/testauditengine.cpp`); that heuristic is fine for a ranking aid and wrong
for a verification tool, where a confidently-wrong line of text is worse than a
flagged unknown.

Step 0's out-of-root stance is modelled on the file-local `resolveRelative` (in
`src/docintegrity.cpp`), but only its posture is borrowed — the helper is an
anonymous-namespace static inside `namespace DocIntegrity`, so it is not
callable from here, and its base differs: it resolves relative to the **citing
doc's directory** (correct for a markdown link) where a path-bearing citation
resolves from the **repo root** (correct for `src/foo.cpp:12` written in a doc
three levels down).
- **Sticky path.** A bare continuation inherits from the most recent
  **antecedent** earlier in the same document: the most recent entry that
  reached `citations[]` with a status other than `unresolved`. An `unparsed[]`
  entry is never an antecedent; a continuation is itself eligible to become the
  next one.

  **`inherited_path:true` means "this entry's target came from an antecedent
  rather than its own text", and is set whenever an antecedent was found** —
  including the ambiguous case, where what is inherited is the candidate set
  rather than a path. It is **not** set on an `unresolved` continuation, which
  found nothing to inherit and is identified by its status alone. So the flag
  never appears on an entry whose target is unknown.

  **Only the antecedent's resolved `path` is inherited** — the continuation runs
  the read step itself and takes its own status. A `missing_file` antecedent
  followed by `` `:2` `` yields a second `missing_file`; an `ok` antecedent whose
  continuation cites past EOF yields `out_of_range`. Only § 2.4's *resolution*
  steps 0–4 are skipped — all of them, since the antecedent's path is already
  resolved — so the two entries can never disagree about which file is meant.
  The regular-file stat and gate G belong to the read step, not to resolution,
  so both still run on the continuation's own read; a `missing_file` antecedent
  never reached gate G, and its continuation re-derives `missing_file` from its
  own stat. The exception is an `ambiguous` antecedent, which has no path to
  give: the continuation inherits its `status` and a copy of its `candidates[]`
  (with `candidates_total` and `truncated_candidates`), reads nothing, and emits
  no `path`. An ambiguity chain is possible and intended.

  With no antecedent → `status:"unresolved"`. Attribution can be wrong when the
  author's antecedent was a prose mention rather than a citation; the flag is the
  mitigation, and the alternative — dropping the 727 real continuations — is
  worse. A fenced block **resets the tracker**: a continuation after a fence does
  not inherit from a citation before it. A fence is a context break, not merely
  skipped text — a `` `:45` `` after a code sample far more likely discusses that
  sample, and a visible `unresolved` beats a silent mis-attribution. This is the
  one place where "skipped" (ANTS-3653 § 3, a block's *contents*) and "resets" (the block
  *boundary* clears state) deliberately differ.

### 2.5 Anchor-symbol check — *moved to ANTS-3654*

The anchor rule (immediately-preceding identifier span within `maxAnchorGap`),
the needle, the match semantics and the `only:"stale"` filter are specified in
**ANTS-3654 § 2**, which carries INV-13 and INV-14. `anchor_symbol`,
`anchor_found` and `only` keep their rows in § 2.1's schema — this spec owns
the response shape — but their semantics live there. The check is advisory and
never a `status`; the verb is complete without it.
### 2.6 Status taxonomy, ranges, and decoding

| `status` | Meaning | `text` emitted |
|---|---|---|
| `ok` | Resolved, start in range, read | yes |
| `missing_file` | Path resolved, no regular file there | no |
| `out_of_range` | File read, `start_line > file_lines` | no |
| `read_error` | File present but unreadable, over `maxTargetBytes`, past `maxTargetReads` (§ 5), or not decodable as UTF-8 — a decode error or an embedded NUL byte, never mojibake `text` | no |
| `ambiguous` | Basename matches ≥2 indexed paths, **or** inherited from an `ambiguous` antecedent (§ 2.4) | no (`candidates[]` instead) |
| `unresolved` | Bare continuation with no antecedent (ladder step 5) | no |

**`path` is emitted for exactly the statuses that resolved one** — `ok`,
`missing_file`, `out_of_range`, `read_error` — and is absent for `ambiguous`
(which carries `candidates[]` instead) and for `unresolved`, which resolved
nothing to name. That is the same partition as § 2.4's ladder: only steps 1–3
and gate G hand a path forward.

`unresolved` is the one unresolvable shape that lives in `citations[]` rather
than `unparsed[]`, because a bare continuation has a valid locus and is a
citation the author actually made — merely un-attributable — where an
`unparsed[]` entry may be prose that was never a citation at all.

`read_error` (a per-citation *status*) and `read_failed` (the refusal code for
an unreadable `path` argument) are different things with similar names; § 2.1
gives the scope rule that separates them.

**`file_lines` is emitted for `ok` and `out_of_range`** (INV-41) — on the latter
it is *how* a caller sees that a citation to line 9,999 points past a 442-line
file, so omitting it would remove the finding's only evidence. Absent elsewhere,
including `read_error`, which may well have opened the file — an undecodable or
NUL-bearing target is only discovered by reading it — but has no trustworthy
line count to report.

**`unparsed[]` entries carry `doc_line`, `raw` (capped at `maxRawChars`, with
`raw_clipped:true` when the cap bites), and `reason`**, in document order. Two
identical malformed tokens on one line are two entries, distinguishable by
position in the array and nothing else — a column number would be the only field
on this verb whose value nothing consumes.

**Emitted `text` lines are capped at `maxTextBytes` each**, with
`text_clipped:true` on the citation when any line was cut. The unit is **UTF-8
bytes, not characters**, because every budget it interacts with is measured in
bytes; a character cap would let a CJK or emoji-bearing line cost 3–4× its
budgeted size. Clipping cuts at a UTF-8 boundary, never mid-sequence. Without
the cap `max_bytes` is not a bound at all — one minified `.json` or generated
`.h` line can exceed its floor unaided. **`max_bytes` is therefore a *soft*
ceiling with one bounded overshoot**, whose arithmetic § 5 does: INV-35 requires
at least one `citations[]` entry even when that entry alone overruns the
remaining budget, because a paging caller that receives zero entries with
`next_offset == offset` loops forever.

**Ranges past EOF.** Only `start_line` decides `out_of_range`. A range whose
**end** exceeds `file_lines` — `:400-500` in a 442-line file — is `ok`:
`end_line` echoes what the doc wrote (500), `text` stops at EOF, and
`end_clamped:true` marks it. This is the common path (ranges are 35% of scan P,
§ 1) and it is real drift information, so it must be visible without being a
hard failure.

An **empty** target needs no special case and gets none: `file_lines` is 0, so
the smallest legal `start_line` of 1 is already greater than it and the citation
is `out_of_range` with `file_lines:0`. That is the correct reading — a citation
to line 1 of an empty file points at nothing.

**The three range flags are independent and may all fire on one citation**
(INV-27's second variant, which asserts exactly this) — `:1-9999` in a 10-line
file at `max_range_lines:3`, with a
long line among the three, sets all of them. Each answers a different question:
`range_truncated` — "you are not seeing the whole cited range **because
`max_range_lines` bound it**", and nothing else; `end_clamped` — "the cited
range runs past EOF"; `text_clipped` — "you are not seeing the whole of a line".
A reader needs all three answers, so none suppresses another, and none is the
top-level `truncated`.

**The envelope rewrites some text, and the citation says so.** `wrapMcpData`
(`src/claudeintegration.cpp`) sanitises every payload before it ships: the
literal `</ants_mcp_data>` close tag and its case/whitespace variants, the open
tag (ANTS-1670 M2), and the `<!--` / `-->` comment markers (ANTS-1996) are each
replaced with a visibly-modified inert form. That is correct and must not be
bypassed — it is what stops a hostile file line from closing the wrap — but it
means a cited line containing one of those tokens **arrives altered**, and the
files most likely to contain them are this project's own MCP sources and
standards docs, i.e. exactly what a reviewer cites. `read_region` answers this
with `raw:true`; § 2.1 declines that mode, so the answer here is disclosure: the
engine sets **`text_escaped:true`** on a citation whose text contains one. The
rewriting still happens downstream, unchanged — the reader is simply told the
text is not byte-exact, because a verification tool that silently shows altered
text is worse than one that shows none.

// ANTS-3649, src/markdownscan.h
// A span's closing run is searched FORWARD across lines but never past a blank
// line or a fence line — an inline span cannot cross either. That is the
// `maskInlineCode` behaviour being hoisted, and it is load-bearing here: it
// decides where a span ends, which ANTS-3653 § 2's "fills a whole span" and ANTS-3654 § 2's
// "an anchor must be one" both branch on. A genuinely whole-document scan that
// omitted the rule would change `count`. The scan runs over the WHOLE document,
// not line by line: a CommonMark span may cross a newline (the defect
// ANTS-3635(a) fixed) and a per-line pass leaves such a span's tail exposed.
// startCol/endCol bound the span's CONTENT (delimiters excluded); delimLen is
// the backtick-run length, so the opening delimiter starts at
// startCol - delimLen and the closing run ends at endCol + delimLen. ANTS-3654 § 2's
// anchor window measures between THOSE columns, which a content-only struct
// cannot express for a multi-backtick span (`` ` ``).
struct CodeSpan { int startLine, startCol, endLine, endCol, delimLen; };
// Content is returned verbatim; CommonMark's one-space strip is the CONSUMER's
// job, so ANTS-3653 § 2's "fills a span" test applies it and ANTS-3654 § 2's anchor match does
// not (an anchor is an identifier, which the strip cannot alter).
QVector<CodeSpan> codeSpans(const QStringList &lines, const QVector<bool> &fence);
QVector<bool>     fenceMask(const QStringList &lines, int *unterminatedOpenerLine);
```

this does not break the engine's Qt6::Core purity) and `::validatePath` (the
handler); `ants::resolveCallerCwdRoot` (the handler); and the basename map,
built by the handler in **five** steps:

1. `CodebaseIndex::cachePathFor(rootCanonical)` — open it; absent → empty map.
2. `QJsonDocument::fromJson` its bytes; unparseable → empty map.
3. `CodebaseIndex::fromJson(obj)` — it takes a parsed object, not a path, which
   is why steps 1–2 are the caller's job.
4. **Validate: reject unless `idx.version == CodebaseIndex::kIndexVersion` and
   `idx.rootCanonical == rootCanonical`; either mismatch → empty map.**
5. One pass over `Index::files`, keyed on `path.section('/', -1)`.

**Step 4 is not optional and is easy to omit.** `CodebaseIndex::fromJson`
*copies* `version` and `root_canonical` into the struct and then parses `files`
unconditionally — it validates neither. The reject-on-mismatch a reader might
assume lives one level up, in `CodebaseIndex::serve`, which this recipe
deliberately bypasses because `serve` may *build* the index and a read verb must
not. Skipping step 4 silently mines a stale-schema or wrong-project cache for
basenames and reports every health field green.

The verb creates no index, cache or disk artifact of its own, so ANTS-1439's
cache-keying contract never engages. Any step failing yields an empty map,
visible as `basename_index_size:0`; the verb never cold-builds the index itself,
because a multi-second build is the wrong thing to do inside a read verb.
`session_orient` refreshes it at session start (ANTS-2140).

Degradation is **visible, not silent**, and the two modes carry different
signals. A *cold* cache yields an empty map — bare basenames fall to
`unparsed[]`, and `basename_index_size:0` says why. A *truncated* index
(`Index::filesTruncated`) yields a large, healthy-looking map while basenames
beyond the cap fall through to `unparsed[]`, indistinguishable from a genuine
prose false positive; **`basename_index_truncated`** (INV-37) is the only thing
that separates them, which is why the `Options` field above is passed in rather
than inferred.

**Explicitly NOT reused — `ReadRegion::extract`.** The obvious candidate, and it
does not fit for three independent reasons: it opens and reads the file on every
call (defeating the line cache), it never reports the target's total line count
(so `file_lines` and the `out_of_range` predicate have no source), and its
`truncated` is byte-based where `range_truncated` is line-based. The engine
therefore reads each target once into the cache and slices from it — which
yields `file_lines` for free, since the read already walked the file.

**That read streams line by line** (a `QTextStream` over the open `QFile`), and
the stream decides what to keep as it goes. A requirement, not an optimisation
note, on two counts.

First, `readAll()` + `split('\n')` transiently holds the `QByteArray`, the
decoded `QString` *and* the `QStringList` at once, roughly tripling the peak for
one maximal target.

Second — and this is what bounds the in-flight buffer at all — a target is only
ever materialised whole when it is going to be cached. The cache charges
`2 × bytes + 40 × lines` (§ 5) as the lines accumulate, and the moment the
running charge would exceed the cache's remaining budget that candidate entry is
**abandoned**: from there the stream retains only what the response will emit —
the first `maxRangeLines` lines of the cited range, each already clipped to
`maxTextBytes` — plus its counters, and discards the rest. **Lines the response
will emit that were already accumulated before the abandonment are kept** — only
the non-emitted accumulation is dropped, so the citation's text is never lost to
the abandonment. `file_lines` comes from the count either way. ANTS-3654 § 2's anchor
search covers the **full** resolved range, but as a predicate evaluated on each
line as the stream passes it, so it retains nothing: that is why a
`:1-9999999` citation costs the same in memory as a `:1-3` one, and why the
abandoned path's retention is bounded at `maxRangeLines × maxTextBytes` (≈ 40
KiB at the clamp ceiling) rather than by the range the doc wrote. Without this
rule `maxTargetBytes` would bound a target's
*bytes* but not its line count, which § 5 works through. The uncached path is
the one INV-20 already specifies (re-read per citation, no eviction); this says
what it holds while doing so.

**Decoding is checked, not silently substituted.** A `QTextStream`'s default
replaces undecodable bytes with U+FFFD, which would produce exactly the
mojibake `text` § 2.6 forbids. The read therefore decodes through a
`QStringDecoder` and tests `hasError()`, and scans the raw bytes for a NUL —
either condition is `read_error` (or, for the doc itself, the `read_failed`
refusal).

## 5. RAM / build cost

- **Per-target read cap.** A target over `maxTargetBytes` is **not read**: it is
  `read_error`, with no `file_lines`. Without this the cache's bound would
  govern only *retention*, and a single in-root citation to a generated `.json`
  or a log would pull an unbounded `QStringList` into memory.
- **Target-file line cache**, keyed by resolved path, so a doc citing one file
  30 times reads it once. Bounded at **`maxCacheFiles` files or `maxCacheBytes`,
  whichever binds first**; past the bound, further targets are read without
  being cached — no eviction, no LRU churn, no unbounded growth.

  **`maxCacheBytes` is measured in memory, not on disk, and the distinction is
  a factor of three.** The cache holds `QStringList`s: Qt strings are UTF-16,
  so an ASCII source doubles on the way in, and every line carries a `QString`
  header plus its own allocation. An 8 MiB source of ~40-byte lines is ~200k
  lines ≈ 16 MiB of characters plus ~8 MiB of per-string overhead. Budgeting by
  file size would promise a `maxTargetBytes`-sized 8 MiB and deliver ~24 MiB.
  The accounting is `sum over cached files of (2 × on-disk bytes + 40 × line
  count)`, charged as the lines accumulate (§ 2.7), so `maxCacheBytes` is the
  number in RSS rather than a number on disk.

  **Worst-case peak — every buffer alive at once:**

  | Buffer | Bound | In memory |
  |---|---|---|
  | Line cache | `maxCacheBytes` | 24 MiB |
  | One in-flight target read | either a cache entry (already charged above) or, uncached, only the lines the response will emit — `maxRangeLines × maxTextBytes` | ~40 KiB |
  | The doc's raw bytes | `maxDocBytes` | 8 MiB |
  | The doc's `QStringList` | `maxDocBytes` on disk **and** `maxDocLines` at its clamp ceiling — both bind at once | ~18 MiB |
  | Response `QJsonObject` | `maxBytes` ceiling, ~2× as a live object | ~8 MiB |
  | Its serialization | `maxBytes` ceiling, a `QByteArray` at 1× | 4 MiB |
  | `basenameIndex` | `kMaxIndexFiles` paths, `5000 × ~200 B` | ~1 MiB |
  | **Peak** | | **~63 MiB** |

  Every row holding **decoded strings** is charged by the `2 × bytes +
  40 × count` formula; the serialization is raw bytes at 1×, and
  `basenameIndex` is bounded by path count rather than line count. The
  in-flight read costs ~40 KiB, which rounds out of the peak: § 2.7's streaming
  rule is what keeps it there. A target that will be cached is accumulated
  inside the cache's own budget; one that will not is streamed retaining only
  the lines that will be emitted, with the anchor predicate evaluated as each
  line passes, so the cited *range* never has to be held whatever the doc wrote.
  Note what would happen without that second half: at a full cache the headroom
  is nil, yet a `:1-9999999` citation's range is the whole file, so an
  implementation retaining "the cited range" literally would hold an entire
  `maxTargetBytes` target off-budget. That is the only reason `maxTargetBytes`
  bounds this table at
  all — it caps a target's *bytes*, never its line count, so a
  materialise-then-cache implementation would put one 8 MiB file of one-byte
  lines at ~160 MiB on its own.

  A realistic call — one spec, a handful of small targets — is well under 5 MiB.
  ~63 MiB is the worst case that has to be defensible on a 32 GiB host running
  earlyoom, and it is, but only because `maxDocLines` and `maxDocBytes` bound
  the doc by line count *and* by size: either alone leaves the other unbounded,
  which is why the doc rows charge both at once rather than taking whichever
  looks smaller.
- **Time is bounded by a counter, not by an argument.** Within the cache bound
  each distinct target is read once. Past it, INV-20 is explicit that a target
  is re-read *per citation*, so the worst case is
  `(citations past the cache bound) × (one target read)`. Deriving a bound on
  that product from `max_doc_lines` and `maxTargetBytes` is arithmetically true
  and practically useless — it permits a whole document's worth of citations
  each pulling a `maxTargetBytes` read. So the product is bounded directly:
  **`maxTargetReads`**, after which a citation needing a fresh read is
  `read_error` and `read_budget_exhausted` is set (INV-46). Reaching it signals
  pathological input, not an expected mode; the densest doc in the corpus needs
  7. No wall-clock timeout is set: there is no network and no subprocess, and a
  mid-response timeout would produce exactly the half-truthful output this
  design rejects — a count is deterministic where a deadline is not, and
  determinism is what INV-16's byte-identity assertion needs.
- **Input guard**: a doc over `max_doc_lines` is scanned to that line only;
  `scanned_lines` reports the prefix, `doc_lines` the true length, and
  `truncated:true` is set — but **no `next_offset`**, because the tail was
  never examined and no page reaches it (INV-31). `maxDocLines`' default is
  sized so that the ordinary specs and standards docs scan whole; the
  exceptions are few and named. `ROADMAP.md`, at § 1's line count and growing,
  **is** truncated at the default and needs a raised `max_doc_lines` to scan
  whole; `CHANGELOG.md` is next at 19,303 lines (2026-07-26) and gains a
  section every release, so expect this claim to rot visibly rather than
  silently. That is why the guard is a request argument rather than a fixed
  constant — a caller who needs the tail can ask for it, and nothing inside the
  clamp ceiling is unreachable. Past that ceiling it would be: `maxDocLines`
  tops out at 50,000, so a doc growing beyond it has a permanently unscannable
  tail. `ROADMAP.md` is the file that will reach it first, which is the
  re-sizing trigger. Its clamp ceiling is set where it is to keep the doc
  rows of the table above defensible.

  **A line cap is not a size cap**, so `maxDocBytes` bounds the doc
  independently: one long-line file satisfies any `maxDocLines` at arbitrary
  size. The corpus's worst case is `docs/standards/mcp-error-codes.md` at
  **179 bytes/line** (`ROADMAP.md` runs 96, and the `docs/` mean is 53 — all
  measured 2026-07-26 by dividing bytes by lines). Over `maxDocBytes` the call
  refuses `read_failed` rather than truncating, because a doc that cannot be
  held has no partial answer worth giving — unlike a citation *target*, where
  the same condition costs one row.
- **Response budget**: `maxBytes` bounds the **serialized response**. Its clamp
  ceiling matches the read family's 4 MiB; its *default* is a quarter of theirs
  (128 KiB against `read_region`'s 512 KiB), because the value here is a compact
  review artifact rather than source. When it or `maxCitations` binds, whole trailing
  `citations[]` entries are dropped — never a half-populated entry — and § 2.1's
  truncation rules apply. Neither touches `unparsed[]`, bounded instead by
  `maxUnparsed` entries each capped at `maxRawChars`: `200 × 120 chars` plus per
  entry keys ≈ 32 KiB, which fits inside `maxBytes`' clamp floor of 64 KiB with
  room to spare.

  **`maxBytes` is a soft ceiling with one bounded overshoot** (§ 2.6): INV-35
  emits at least one citation even when it does not fit. That entry's *text* is
  bounded at `maxRangeLines × maxTextBytes` = `20 × 2000` ≈ 40 KiB at the clamp
  ceiling, and the serialized entry is that plus JSON escaping (up to 6 bytes
  per control character) and the entry's other keys — `raw`, `path`,
  `candidates[]` — so the overshoot is **on the order of 40–100 KiB, not an
  exact 40**. The number that matters is that it is bounded at all: without the
  per-line cap it would be unbounded, which is the only reason that cap exists.
- **Build**, with the dominant cost estimated rather than only the small parts:

  | Change | Estimate | Comparable |
  |---|---:|---|
  | `src/doccitations.{h,cpp}` — new | **~350–400 lines** | `src/docintegrity.cpp` is 378 lines for a comparable engine |
  | Handler + two pure statics | ~120 lines | `doc_integrity`'s equivalents |

  So ~470–520 new lines here; the `MarkdownScan` hoist is ANTS-3649's cost, and
  is a net reduction there rather than an addition. No new external dependency,
  no new target, and no new test bundle — both new feature directories join
  bundles that already exist.

  is § 2.1's. Not tracked — a non-goal.
- **A reverse "which docs cite this file?" index.** That is a cache with an
  invalidation contract, and nothing has asked for it. Not tracked.

## Cold-eyes loop log

Loops 1–10 ran three lanes each (design / accuracy / conformance), re-briefed
cold every loop, all on 2026-07-26. Entries below are compressed to the counts
and the findings that changed the design; loop 11 rewrote the document, so its
entry is kept in full.

**Loop 1** — **C4 · H7 · M12 · L12 · I3**, 35 verified / 1 dismissed.
`CodebaseIndex::serve` returns a `QJsonObject`, not an `Index`, so the named
reuse could not have worked; the `unparsed[]`/`unresolved`/`missing_file`
three-way contradiction was resolved by making the ladder total;
`ReadRegion::extract` was dropped as a reuse. Load-bearing: § 2.5's anchor idiom
had been asserted "dominant" and measures 22% — `only:"stale"` as first drafted
would have dropped the unanchored majority of healthy citations.

**Loop 2** — **C6 · H6 · M14 · L16 · I3**. Loop 1's symlink guard was a false
security claim: `QFileInfo::isSymLink` inspects only the final component, so
`src/link/foo.cpp:1` would have been read. Replaced with gate G. Also: `counts`
had no bucket for `unparsed[]`, so a cold index was invisible.

**Loop 3** — **C3 · H8 · M11 · L22 · I3**, 47 verified. All three lanes found
the same registration-file error. Two design holes: the continuation grammar had
no left-context rule, so `09:45` in prose would have inherited an unrelated path
and emitted that file's real line 45 as `ok`; and INV-17 promised a resumable
`next_offset` for a cap that truncates the *scan*. Also the RAM budget counted
on-disk bytes for a cache of UTF-16 `QStringList`s (~3× understated).

**Loop 4** — **C4 · H5 · M12 · L20 · I5**, 46 verified. `ROADMAP.md` was 27,024
lines, not the ~19.5k claimed, so the 20,000-line guard silently truncated the
very file used to justify it — and INV-31 had just made that truncation
unresumable. Fixed by making `max_doc_lines` a request argument. The grammar had
no leading-`/` production, so step 0 was unreachable and INV-6 unsatisfiable.
Three invariants were specified as verb-level calls against a handler needing a
live MainWindow; ANTS-3601 had already solved this with extracted pure statics.

**The finding that changed how this spec is maintained.** Six of loop 4's
defects were introduced by *loop 3's own fixes*, every one the same shape: a
passage was edited and the passages referencing it were not. So loop 4's
response was structural: the document was consolidated, each rule stated once,
and every fix written against an explicit ledger of "what else must agree with
this". Loops 1–3's habit of adding prose to defend each fix was itself the
mechanism generating the next loop's findings.

**Loop 5** — **C4 · H6 · M10 · L22**, 42 verified. The ledger worked, partially:
the edited-a-passage-and-left-its-neighbour class produced one finding instead
of half. That one defined a new rule — loop 4's fix had split the tests across
two bundles citing ANTS-3601 as precedent *without opening ANTS-3601*, which
uses **two** feature directories where the fix specified one. Hence: *when a fix
cites a precedent, open the precedent*. Three findings were nobody's regression:
nothing capped an emitted `text` line, so one minified line defeated `max_bytes`
while INV-35 required at least one entry (now INV-43); `unterminated_fence` was
specified as derivable from `fenceMask`, which returns bare bools and masks the
closer line true as well (now a `fenceMask` overload + INV-36); and `codeSpans`
was specified line-scoped, which would have re-introduced ANTS-3635(a) (now
whole-document + INV-44). Also: the MCP envelope sanitises `<ants_mcp_data>` and
`<!--`/`-->` out of every payload, so cited text arrives altered (now
`text_escaped` + INV-45); and the anchor coverage figure was 22% *of one scan's
denominator*, which against the real harvest is 20%.
