# ANTS-3636 — `doc_citations`: resolve a doc's `path:line` citations and return the cited text

**Status:** spec draft, cold-eyes loops 1–3 folded (2026-07-26).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-3636 (OneUp_Ants_MCP_Feedback.md, 2026-07-26 addendum).
**Composes with:** ANTS-3601 (`doc_integrity` — shares the fence primitives),
ANTS-1637 (`codebase_index` — the basename→path map).
**Pairs with:** ANTS-3596, which hardened `docs/specs/ANTS-2161.md` by hand —
by *converting* its drift-prone `:~N` citations to symbol references, so that
file carries none today. This verb generalises the motivation, not the fix.
**Blocker for:** ANTS-3642 (request-side `expect` map), ANTS-3643 (corpus-wide
digest mode).

**Layman:** Design docs are full of "see `file.cpp`, line 200" pointers. Code
moves; the pointers rot silently. This adds one call that looks up every such
pointer in a document and shows what is actually on those lines today.

---

## 1. Problem

Global rule 13 requires every doc claim naming a file, line, function, or
constant to be checked against live source rather than recalled. `/cold-eyes`
runs that check on every loop, for every reviewer, on every doc. There is no
verb for it, so it is done by hand or skipped — and when it is skipped, the
loop ratifies a stale line number and the next reader is sent to the wrong
place.

The reporting session (OneUp) hit this directly: verifying one spec meant
resolving 33 `updater.py:NNN` citations, and they wrote a throwaway Python
script because no verb existed. `read_regions` is the closest fit but takes a
hand-extracted list of `{path, start_line, end_line}` — and extracting that
list *is* the tedious part.

**The corpus is large enough that hand-verification does not scale.** Measured
2026-07-26 over `docs/`, excluding this spec. Two scans with different regexes
run here, so each row names its own denominator rather than implying one shared
total. Every figure is reproducible with the commands below — recorded inline
because three cold-eyes loops caught unverified counts in this very table, and
a number without its command is exactly the kind of claim this verb exists to
catch.

| Shape | Count | Of what |
|---|---:|---|
| `path.ext:N` citations (scan **P**) | 1,935 in 167 docs | — |
| …carrying a directory component (`src/foo.cpp:12`) | 551 | 28% of scan P |
| …**bare basename** (`foo.cpp:12`) | 1,384 | **72% of scan P** |
| Line **ranges** (`:208-228` or en-dash `:208–228`) | 673 | 35% of scan P |
| Multi-locus / open-ended (`:262/265/286`, `:5669+`) | 38 | 2% of scan P |
| Approximate (`:~752`, `:~1413`) | 10 | <1% of scan P |
| Citations opening a code span (`` `foo.cpp:12` ``) — scan **S** | 1,791 | — |
| …preceded by an identifier code span (§ 2.5) | 388 | **22% of scan S** |
| Bare continuations (`` `:548-549` ``, path inherited) | 727 in 78 files | own scan — **not** in scan P (no dotted path to match) |

P='[A-Za-z0-9_.@+/-]+\.[A-Za-z]{1,5}:[0-9]+'
grep -rhoE "$P" docs/ $E | wc -l                      # scan P total    1935
grep -rhoE "$P" docs/ $E | grep -c '/'                # with directory   551

grep -rhoE "\`$P" docs/ $E | wc -l                    # scan S          1791
grep -rhoE "\`[A-Za-z_][A-Za-z0-9_:]*\`[^\`]{0,40}\`$P" docs/ $E | wc -l  # anchored   388
grep -rhoE '`:~?[0-9]+(-|–)?~?[0-9]*`' docs/ $E | wc -l                   # continuations 727
```

Densest single doc: `docs/specs/ANTS-1750.md` at 56 citations.

Four consequences follow, and they shape the design:

1. **Existence checking is not enough.** A citation that has drifted onto an
   unrelated statement still points at a line that exists. Only the cited
   *text* exposes that, which is why the text is the load-bearing output and
   not an option. A live instance, found while writing this spec:
   `docs/specs/ANTS-2090.md:69` reads ``` `compactEnvelope` (gated on
   `isFieldProjectionTool`, `mcpprojection.cpp:28`) ```, but
   `src/mcpprojection.cpp:28` is today a blank line — `:27` closes
   `terseDefault()` and `:29` opens the ANTS-3550 hint-latch comment block, with
   the next function (`claimHint`) at `:41`. The line exists, so every
   existence-based check passes; the claim is nonetheless false. Tracked for
   repair as ANTS-3641.
2. **Bare basenames are the common case, not an edge case.** A resolver that
   only handled repo-relative paths would silently skip ~72% of the corpus —
   worse than no verb, because the empty result reads as "all clear".
3. **Citations live inside inline code spans.** Nearly every one is written
   `` `remotecontrol.cpp:335` ``. `doc_integrity` deliberately *masks inline
   code out* before harvesting links (`maskInlineCode`,
   `src/docintegrity.cpp:115`) because a link inside a code span is a code
   sample. For citations the rule inverts: the code span is exactly where the
   data is. This is the single most important reason the two checks cannot
   share a scrape pass.
4. **No mechanical signal covers most citations.** Only 22% carry a nearby
   identifier the verb can check the cited text against (§ 2.5). The other 78%
   can be *resolved and shown* but not *judged* — so the design must never let
   a filtered or degraded view imply they were verified (§ 2.1, § 2.6).

## 2. Surface

### 2.1 Verb shape

New verb `doc_citations`, **not** a mode on `doc_integrity`. The ROADMAP bullet
left this open ("decide at spec time"); the deciding facts are that
`doc_integrity`'s contract is a *defect list* (`findings[]` + `counts{}`
narrowed together by `kinds` — ANTS-3601 INV-18,
`RemoteControl::docIntegrityBuildResponse`) while this verb's primary output is
an *enumeration of every citation with its text*, most of which are healthy.
Folding an enumeration into a findings verb would either break `kinds`/`counts`
or bury the payload. The only shared code is `MarkdownScan::fenceMask` (§ 2.3),
which already lives in a third module; the two engines are otherwise
independent.

Request:

```jsonc
{
  "caller_cwd":       "<required>",       // CallerCwdContract::Required
  "path":             "docs/specs/ANTS-2090.md",  // required, a FILE
  "only":             "all" | "stale",    // default "all"
  "offset":           0,                  // 0-based index into the post-filter list
  "max_range_lines":  3,                  // per-citation, clamped to [1, 20]
  "max_bytes":        131072,             // clamped to [8 KiB, 4 MiB]
  "etag_match":       "<opt>"
}
```

**Every numeric argument clamps rather than refuses, and the handler
(`cmdDocCitations`) is what clamps** — it maps request args onto `Options`
(§ 2.7) and the engine trusts the `Options` it is given, so a direct engine
caller in a unit test is not silently re-clamped. Three clamps:

- `max_range_lines` → `[1, 20]`.
- `max_bytes` → `[8 KiB, 4 MiB]`. The **floor matters**: below one entry's
  serialized size the response would be `returned:0` with `truncated:true` and
  `next_offset == offset`, and a caller paging on `next_offset` would loop
  forever. At least one entry is always emitted, even if it alone exceeds
  `max_bytes`.
- `offset` → `[0, count]`; a negative value clamps to 0. An `offset` at or past
  the end of the post-filter list returns an empty `citations[]` with `ok:true`
  and no `next_offset` — the `roadmap_query` past-end precedent, adopted rather
  than merely cited.

`maxDocLines` is deliberately **not** a request argument. It is an input guard
(§ 3), not a pagination knob, and unlike the other caps its truncation is
**not resumable** — see INV-31.

`path` must name a single **file**. Two deliberate divergences from
`doc_integrity`, both stated here because the two verbs are used together in
the same review loop and a silent difference is a caller trap:

- **A directory refuses `bad_args`**, where `doc_integrity` accepts one and
  walks it (ANTS-3601 INV-16). The reason is response size: `docs/` holds
  ~1,870 citations, and this verb's payload is per-citation *text*, not a
  defect count. The taxonomy's `bad_args` row opens "A required argument is
  missing or **has the wrong shape**" (`mcp-error-codes.md` § 1), which is the
  case here — a directory is the wrong shape of value for an arg contracted to
  one doc. (`not_feedback_file` is the precedent for instead *minting* a code
  for a well-formed-but-wrong-kind path; that would mean amending the taxonomy,
  which is not worth it for one verb.) The refusal message names the file-only
  requirement and points at ANTS-3643 for the sweep mode.
- **A well-formed but non-existent in-root `path` returns `ok:true` with an
  empty `citations[]`**, matching `doc_integrity` (ANTS-3601 INV-15,
  `src/remotecontrol.cpp:12334`) rather than refusing. Companion verbs should
  answer a typo'd path the same way. An existing but **unreadable** `path`
  refuses `read_failed`; an absent or empty `path` refuses `missing_field`.

`path` is not required to be `.md` — any UTF-8 text file is scanned. § 6's
"non-markdown inputs" non-goal is about the *workflow*, not an input guard.

Response. **This block is a synthetic fixture, not a live capture** — it is the
worked example an implementer checks their output against, so every field here
is derivable from the rules below by inspection rather than from any particular
file's current contents. (A live capture would rot the moment the cited files
moved, and a rotted example in *this* spec would be self-refuting.) The fixture
doc holds six citation-shaped tokens: an anchored-and-matching one, a dead
file, an ambiguous bare basename, an anchor that no longer matches, an
unanchored one, and a prose false positive.

```jsonc
{
  "ok": true,
  "path": "fixture.md",
  "doc_lines": 13,                         // the doc's true length
  "scanned_lines": 13,                     // < doc_lines when maxDocLines binds

      "raw": "src/gone.cpp:1",

      "path": "src/gone.cpp",

                     "tests/audit_fixtures/insecure_http/bad.cpp",

      "path": "src/a.cpp",                 // resolved, project-relative
      "start_line": 2,
      "end_line": 2,

      "text": ["    return 0;"],
      "anchor_symbol": "parseHeader",      // absent when none precedes
      "anchor_found": false                // ← the drift this verb exists to catch
    }
  ],
  "returned": 3,                           // length of citations[] after `only` + `offset`
  "count": 5,                              // citations found in the scanned prefix
  "counts": { "ok": 3, "missing_file": 1, "out_of_range": 0, "read_error": 0,
              "ambiguous": 1, "unresolved": 0,
              "anchor_missing": 1, "unchecked": 1, "unparsed": 1 },
  "unparsed": [ { "doc_line": 13, "raw": "6.2:1", "reason": "unresolvable" } ],
  "unparsed_total": 1,

Check the block against the rules, because an implementer will: the three
`status` values in `citations[]` plus the two dropped `ok` entries sum to
`count:5`; `counts.ok` (3) = anchored-and-found (1, dropped) + `anchor_missing`
(1, shown) + `unchecked` (1, dropped); `candidates[]` is lexicographic, capped
at `maxCandidates` (8) with `truncated_candidates` set because 14 fixture paths
carry that basename; and `unparsed[]` is outside `count` entirely.

**Field-emission rule.** The five per-citation booleans — `range_truncated`,
`end_clamped`, `inherited_path`, `approximate`, `partial` — are **omitted when
false**. At 400 citations, always-emitting them costs 2,000 always-false keys
on a verb whose premise is token frugality. `truncated_candidates` follows the
same rule.

**How the tallies partition.** The six `status` keys of `counts` partition
`count` (7+1+0+0+1+0 = 9). `anchor_missing` and `unchecked` are **overlays on
the `ok` subset**, not statuses: `counts.ok` = anchored-and-found +
`anchor_missing` + `unchecked` (7 = 1+1+5). `counts.unparsed` mirrors
`unparsed_total` and is **outside** `count` — an unparsed token is not a
citation. `count` and `counts` are always whole-doc (pre-`only`, pre-`offset`)
over the scanned prefix; `returned` is the emitted length.

`counts.unchecked` is the load-bearing honesty field: `status:"ok"` citations
with **no** anchor symbol — resolved and shown, but never judged. Per § 1
consequence 4 that is ~78% of a typical doc. `basename_index_size` is its
companion: a cold or truncated codebase index (§ 2.7) pushes bare basenames —
~72% of the corpus — into `unparsed[]`, and a reader who cannot see the index
was empty would read the shortfall as a clean doc.

`only:"stale"` keeps every non-`ok` citation plus every `ok` citation with
`anchor_found:false`. It **drops** `ok` citations that are anchored-and-found
(nothing to report) and `ok` citations with no anchor (no drift signal for
them) — which is exactly why `counts` stays unfiltered. `unparsed[]` is never
filtered — but it *is* capped; see below. Ordering is: filter by `only` → apply
`offset` → fill until a cap binds. A caller reading only the filtered list and
ignoring `counts.unchecked` will believe more was verified than was; the field
exists so that is a misreading rather than a design flaw.

**Sort order is document order** — ascending `doc_line`, and within one line
ascending column of the citation's first character. Stated because `offset`
paging is only meaningful over a defined order, and because INV-29 mandates two
separate entries for two citations on one line, which would otherwise have no
defined relative position.

**`count` and `counts` are whole-doc, which means resolution does not stop when
the emission caps bind.** `maxCitations` / `maxBytes` bound what is *emitted*,
not what is *examined*: every citation in the scanned prefix is resolved, and
every `ok` one is read, so that the tallies and the `anchor_missing` /
`unchecked` overlays are true of the whole doc rather than of the first page.
The bound on *work* is `maxDocLines` (§ 3) together with the line cache; the
bound on *response size* is `maxBytes`. They are different mechanisms and an
implementer must not collapse them. Consequence, stated so it is a choice
rather than a surprise: because INV-16 forbids cross-call state, paging with
`offset` re-resolves and re-reads the whole doc on every page. At the corpus's
densest doc (56 citations) that is cheap; it is the reason `maxDocLines` exists
rather than a larger page count.

**`unparsed[]` has no pagination and its tail is not recoverable.** It is
capped at `maxUnparsed` (200) and `offset` pages `citations[]` only. When the
cap binds, `unparsed_total` reports the true count so the loss is *countable*
even though the entries are gone; `max_bytes` drops trailing `citations[]`
entries before it drops `unparsed[]`, so a byte-squeezed response never hides
the parse failures. If the array ever needs paging, that is ANTS-3643's digest
shape, not a second offset on this verb.

The ROADMAP bullet asks for a `stale[]` array; this is that, reshaped into a
filter over one array plus unfiltered counts, so the healthy majority stays
addressable in the same call. It is also broader than the bullet's "missing or
out of range" — it keeps anchor drift too. The bullet's per-entry sketch keys
are renamed here: `cited_path` → `path`, `cited_line` → `start_line`, and the
boolean `exists` → the six-valued `status` (a boolean cannot distinguish a
dead file from an ambiguous basename from a line past EOF). Recorded so the
rename reads as deliberate against `ROADMAP.md` ANTS-3636.

`offset` pages the post-filter list. **`next_offset` is emitted exactly when a
resumable cap dropped trailing `citations[]` entries** — that is, when
`maxCitations` or `maxBytes` bound — and is `offset + returned`, the
`roadmap_query` / `workspace_search` precedent. It is **absent** otherwise,
including on the `maxDocLines` guard, whose truncation is not resumable
(INV-31): the unscanned tail was never examined, so no `offset` reaches it.
`truncated:true` therefore has two flavours, and `next_offset`'s presence is
what distinguishes "there is more of this list" from "there is more of this
document, and this call will not show it to you".

The JSON above is the tool's **payload**; the dispatcher wraps it in the
ANTS-1294 `<ants_mcp_data tool="doc_citations">…</ants_mcp_data>` envelope
(`mcp-tools.md` step 5). This is an ordinary, non-control-plane verb, so it
takes the standard wrap with no special handling — noted only because the
response block is shown unwrapped.

**`fields=` is deliberately not adopted.** `mcp-tools.md` step 8 marks it
optional, and `mcp::isFieldProjectionTool` is a curated allowlist that
`doc_integrity` is likewise absent from. `only` + `offset` cover this verb's
real narrowing needs at a fraction of the surface. **`raw:true` is not adopted
either** (`mcp::isRawEligible` — `read_region`, `read_regions`,
`workspace_search`): raw mode returns verbatim bytes in a collision-proof
frame, and this verb's product is a structured envelope in which the file text
is one field among many. A caller who wants unframed bytes wants
`read_region`.

The dispatcher-injected `etag` (`mcp-tools.md` step 7) hashes the **response**,
so an unchanged etag means nothing the response *reports* has changed —
including the cited text it shows. It is not a whole-target guarantee: text is
clipped to `max_range_lines`, so an edit inside the unshown tail of a range
leaves the etag equal.

### 2.2 Citation grammar

```
citation     := path ":" locus trailing?
continuation := "`" ":" locus trailing? "`"      // path inherited (sticky rule below)
path         := seg ( "/" seg )*                 // last seg must contain a "."
seg          := [A-Za-z0-9_.@+-]+
locus        := "~"? N [ ("-" | "–") "~"? N ]    // hyphen or EN DASH
trailing     := ( "/" "~"? N )+ | "+"            // extra loci, dropped (partial)
N            := [0-9]{1,7}                       // ≤ 7 digits; see below
```

Four constraints that are part of the grammar, not commentary on it:

- **A continuation must be a whole inline code span.** `` `:45` `` is a
  continuation; the `:45` inside `09:45`, `3:1`, or `INV-3:` is not. Without
  this rule the § 2.3 raw-line scan would harvest every clock time and ratio in
  every doc, inherit an unrelated path, and emit *the real text of that file's
  line 45* under `status:"ok"` — a confidently-wrong answer, which § 2.4 fixes
  the ambiguity rule specifically to avoid. Requiring the delimiters is what
  makes a continuation an authored citation rather than a coincidence, and it
  matches how all 727 corpus continuations are written. A citation *with* a path
  needs no such guard: its path part already cannot be produced by prose
  punctuation.
- **The dot must be in the final segment.** `src.old/README:12` does not parse
  (no dot in `README`); `docs/specs/ANTS-2161.md:5` does. The dot is standing in
  for "names a file", and a directory component's dot says nothing about the
  leaf.
- **`N` is capped at 7 digits** (up to 9,999,999 — three orders of magnitude
  past the largest file in this repo). A longer run of digits is not a locus:
  the token lands in `unparsed[]` with `reason:"bad_locus"`. Without the cap an
  implementer parsing into `int` gets undefined overflow on adversarial input,
  and the status would be whatever the overflow happened to produce.
- **`trailing` is exhaustive.** Only further `/`-separated loci and a single
  `+` are absorbed and reported as `partial:true`. Every other character ends
  the token, so the `.` closing a sentence in ``see `src/a.cpp:12`.`` is
  ordinary punctuation and sets no flag. Without this the flag would fire on
  most prose citations and mean nothing.

- **En dash is not optional.** The corpus writes both `:208-228` and
  `:208–228`; a hyphen-only regex loses a large minority of the 673 ranges.
- **Trailing loci are dropped, not guessed.** `:262/265/286/300` and `:5669+`
  parse as their first locus with `partial:true` (38 occurrences, ~2%).
- **`~N` sets `approximate:true` and changes nothing else.** It is an echo so a
  reader can see the author hedged. Status is computed identically for tilde
  and non-tilde loci — there is no fuzzy-match tolerance, because there is
  nothing to be tolerant *against* (10 corpus occurrences, <1%).
- **Malformed loci are not citations.** `N < 1`, an end below its start, or a
  digit run longer than 7 → `unparsed[]` with `reason:"bad_locus"`. None of the
  three occurs in the corpus today (all measured at 0); the rule exists so the
  read path never receives arguments it would refuse, and so no locus reaches
  an `int` that cannot hold it.
- **Two citations on one doc line are two entries**, as are two occurrences of
  the same citation. `count` is occurrences, not distinct targets; the line
  cache (§ 3) makes the repeat free, so there is nothing to gain by de-duping
  and a doc that cites the same line twice in two different claims deserves two
  verdicts.
- **Sticky path.** A bare `:NNN` continuation inherits from the most recent
  **antecedent** earlier in the same document: the most recent entry that
  reached `citations[]` with a status other than `unresolved`. An `unparsed[]`
  entry is never an antecedent. The continuation always carries
  `inherited_path:true`, and is itself eligible to be the next antecedent. Two
  cases:
  - *Resolved antecedent* — its already-resolved `path` is substituted and the
    § 2.4 ladder is **skipped** (no re-resolution, so the two entries can never
    disagree).
  - *`ambiguous` antecedent* — it has no `path` to substitute, so the
    continuation inherits `status:"ambiguous"` and a copy of its `candidates[]`
    (and `truncated_candidates`), reads nothing, and emits no `path`. An
    ambiguity chain is therefore possible and intended.

  With no antecedent → `status:"unresolved"`. Attribution can be wrong when the
  author's antecedent was a prose mention rather than a citation; the flag is
  the mitigation, and the alternative (dropping 727 real citations) is worse. A
  fenced block **resets the antecedent tracker**: a continuation after a fence
  does not inherit from a citation before it, and with nothing between the
  fence and itself is `unresolved`. The reason is that a fence is a context
  break, not merely skipped text — a `` `:45` `` after a code sample is far more
  likely to be discussing that sample than the citation that preceded it, and an
  `unresolved` entry the reader can see beats a silent mis-attribution to a file
  from another section. This is the one place where "skipped" (§ 2.3, the
  block's *contents* are not scanned) and "resets" (the block *boundary* clears
  state) deliberately differ.

### 2.3 Scrape rule (masking is inverted vs. `doc_integrity`)

- **Fenced blocks are skipped**, via `MarkdownScan::fenceMask`
  (`src/markdownscan.h:58`) — a `path:line` inside a ```` ```cpp ```` sample is
  illustrative text, not a claim about the repo. This is the one primitive
  shared with `doc_integrity`, including its ANTS-3638 list-container awareness.
- **An unterminated fence is reported, not absorbed.** `fenceMask` masks an
  unclosed fence true to end-of-input (its documented CommonMark leniency,
  `src/markdownscan.h:45-47`). Inherited as-is, a single stray ```` ``` ```` in
  a long doc would silently blank every citation after it and return
  `truncated:false` — a clean-looking all-clear over a document the verb barely
  read, which is the failure mode § 1 consequence 2 rules out. So the response
  carries **`unterminated_fence`** — the 1-based line of the unclosed opener,
  omitted when there is none. The mask is not second-guessed (this verb does not
  get to disagree with the project's one fence parser); the reader is simply
  told. The risk is live, not theoretical: ANTS-3638 and ANTS-3640 were both
  open-fence defects, and this spec is itself a doc full of fences *about*
  fences.
- **Inline code spans are scanned, not masked** — the inverse of
  `maskInlineCode`, which `doccitations` therefore does not call.
- The scan runs on the **raw** line, so a citation is harvested wherever it
  appears — bare prose (`ROADMAP.md:19418 was …`), inside emphasis
  (``**`a.cpp:1`**``), or inside link text (``[`a.cpp:1`](x)``). No markdown
  construct other than a fence suppresses a citation.

### 2.4 Path resolution ladder

Applied in order; first hit wins. Every terminal step names where the entry
lands, so the ladder is total.

| # | Condition | Filesystem | Outcome |
|---|---|---|---|
| 0 | **Lexical reject** — absolute (`/…`) or lexically escaping root (`../..`) | none | `unparsed[]`, `reason:"out_of_root"` |
| 1 | Contains `/` → project-relative from the repo root | stat | regular file → gate G; else → `missing_file` |
| 2 | Bare basename, exactly one match in `basenameIndex` | stat | regular file → gate G; else → `missing_file` |
| 2b | Bare basename, ≥2 matches | none | `ambiguous` + `candidates[]` |
| 3 | Bare basename, not indexed, but `<root>/<basename>` is a regular file | stat | gate G |
| 4 | A path part was present and none of the above resolved | none | `unparsed[]`, `reason:"unresolvable"` |
| 5 | No path part at all (bare `:NNN`, no antecedent) | none | `citations[]`, `status:"unresolved"` |

**The stat is a regular-file test, not an existence test.** The grammar's only
requirement is a dot in the final segment, which a directory can satisfy
(`build.d:12`, `assets.old:3`). Testing existence alone would send a directory
to the read path, where its status would be decided by whatever the platform
returns from opening one — `read_error` on Linux, but by accident rather than
by contract. A directory is `missing_file`: the doc claimed a file at that
path and there is no file at that path, which is precisely what that status
means.

**Gate G — the anchor re-check, applied to every existing candidate before it
is read.** `PathValidation::isInsideProject(rootCanonical, candidate)`
(`src/pathvalidation.h:60`, ANTS-1832) canonicalises *both* sides and returns a
bare boolean, building no error envelope. False → `unparsed[]`,
`reason:"out_of_root"`, and the file is never opened.

Gate G is where the symlink case is actually closed, and it is a **separate
step from the lexical step 0** for a reason worth stating: a `QFileInfo::isSymLink`
check would inspect only the *final* component, so `src/link/foo.cpp:1` where
`src/link` is a symlink to `/etc` would pass it. Canonicalisation resolves every
component, which is the only correct check. It costs one stat on an in-root
candidate that is about to be read anyway — the "never probe" rule (ANTS-3601
INV-6's posture) binds *lexically out-of-root* shapes, which step 0 rejects
with zero filesystem calls. `isInsideProject` returns false for a non-existent
candidate, so gate G runs only after existence is established; a missing file is
`missing_file`, never mis-reported as an escape.

`PathValidation::validatePath` is deliberately **not** used per-citation: its
product is a whole-response `bad_path` envelope, the wrong granularity for one
citation among 33. It still applies, unchanged, to the request's own `path`
argument at the handler. A citation target is not a "path-typed arg" in
`mcp-tools.md` step 4's sense — it is scraped file content — so the contract is
discharged at the handler and gate G is the defence in depth.

Step 3 is what catches `CMakeLists.txt:148`, `ROADMAP.md:19418` and
`README.md:…` — root files outside the index's `src/`+`tests/` walk. (If a
project sets `source_roots` in `.ants/project.json` (ANTS-2160), the index walk
widens accordingly and step 3 simply fires less often; the ladder is unchanged.)

Step 4 is the **only** producer of `unparsed[]` entries from a shape match, and
step 5 the **only** producer of `unresolved`. A prose false positive like
`` `6.2:1` `` (path part `6.2` — it contains a dot, so the grammar admits it)
lands at step 4, not in `citations[]`. Nothing is silently dropped.

**A deliberate asymmetry, stated because it biases a count.** A
directory-bearing dead citation (`src/gone.cpp:1`) is `missing_file`; a bare
dead basename (`gone.cpp:1`) falls to step 4 and is `unparsed[]`. Both are
drift, but only the first is a *definite* file claim — a bare token that
resolves nowhere is indistinguishable from prose (`6.2:1`), and guessing would
put false `missing_file` findings in front of a reviewer. So `counts.missing_file`
under-reports the bare-basename majority by construction; `counts.unparsed` and
`unparsed[]` are where that population is visible, which is why both are
emitted unfiltered.

**Ambiguity is reported, never resolved by guessing.** `src/` is flat (no
subdirectories) so in-lane collisions are impossible today, but the indexed
tree holds 14 `good.cpp` and 14 `bad.cpp` under `tests/audit_fixtures/`
(measured 2026-07-26). `candidates[]` is sorted lexicographically on the
project-relative path and capped at `maxCandidates` (8), with
`truncated_candidates:true` beyond. `TestAuditEngine` merges such collisions by
picking the longest path (`src/testauditengine.cpp:1568-1591`); that heuristic
is fine for a ranking aid and wrong for a verification tool, where a
confidently-wrong line of text is worse than a flagged unknown.

Note the deliberate asymmetry with the file-local `resolveRelative`
(`src/docintegrity.cpp:228` — an anonymous-namespace helper inside
`namespace DocIntegrity`, so it is internal linkage and **not** callable from
here; only its posture is being compared), whose out-of-root stance step 0
models: it
resolves relative to the **citing doc's directory** (correct for a markdown
link), while a citation's directory-bearing path resolves from the **repo
root** (correct for `src/foo.cpp:12` written in a doc three levels down). Only
the posture is borrowed, not the base.

### 2.5 Anchor-symbol check — a derived drift signal, not a replacement for `expect`

The ROADMAP bullet asks for an `expect` mode ("does the cited line still
contain this substring?"). The corpus supplies a weaker version for free: its
most common citation idiom names the symbol immediately before the location.

```
`RemoteControl::filterControlChars` (`remotecontrol.h:95-113`) strips C0
`uniqueSlug` (`roadmapindex.cpp:72-86`) DOES auto-append `-2`, `-3`
```

Pinned precisely, so two implementers build the same thing:

- **Anchor** = the nearest preceding inline code span on the **same line**
  whose content matches `^[A-Za-z_][A-Za-z0-9_:]*$`, and whose closing
  backtick is within **40 characters** of the opening backtick of the span
  containing the citation (measured on the raw line). A citation **not inside a
  code span** has no anchor, regardless of what precedes it.
- **Needle** = the anchor's final `::` component (`A::b` → `b`). An anchor
  ending in `::` yields an empty component and is discarded — no anchor.
- **Match** = case-sensitive, whole-identifier (the needle's occurrence must
  not be flanked by `[A-Za-z0-9_]`, so `id` does not match `invalid`), searched
  over the **full resolved range** — not the `max_range_lines`-clipped `text`,
  so display width never changes a verdict. When the range was clamped at EOF
  (§ 2.6) the search covers the existing portion. Trailing `\r` is stripped
  first (§ 3).
- `anchor_symbol` / `anchor_found` are **absent** when no anchor is found, and
  absent for every status that emits no text (`missing_file`, `out_of_range`,
  `read_error`, `ambiguous`, `unresolved`).

`anchor_found:false` is **advisory, not a `status`**: `status` answers "did the
citation resolve", this answers "does it still say what the doc claims".

**Measured coverage: 388 of 1,791 citations (22%).** This is the honest limit.
The check is worth its ~30 lines — it catches precisely the drift the bullet
describes, at zero authoring cost, on a fifth of the corpus — but it is a
*default*, not the `expect` mode. The residual gap (the other 78%, and the
scripted-re-verification case where a caller genuinely does hold an
expectation) is deferred to **ANTS-3642**, not quietly dropped.

**`anchor_found:false` is a prompt to look, not a verdict — and it is the
signal `only:"stale"` selects on, so its false-positive rate is a design
parameter rather than an implementation detail.** Two shapes produce a false
positive by construction. A single-line citation whose symbol sits a line or
two away — the most common *near-miss* drift, and the shape of this spec's own
motivating example — reports stale although the doc is arguably still correct.
And a citation that names a *call site* rather than a definition will not
contain the symbol at all. Neither is a bug to be tuned away: widening the
search window past the cited range would silently convert real drift into
"found", which is the failure direction this verb must never take. The residual
is accepted and stated here so a reviewer reads a stale flag as "check this
one" rather than "this is broken", and so nobody later tunes the window to make
the number look better.

### 2.6 Status taxonomy, ranges, and decoding

| `status` | Meaning | `text` emitted |
|---|---|---|
| `ok` | Resolved, start in range, read | yes |
| `missing_file` | Path resolved, file absent | no |
| `out_of_range` | File read, `start_line > file_lines` | no |
| `read_error` | File present but unreadable, over `maxTargetBytes`, or not decodable | no |
| `ambiguous` | Basename matches ≥2 indexed paths | no (`candidates[]` instead) |
| `unresolved` | Bare continuation with no antecedent (ladder step 5) | no |

`read_error` (a per-citation *status*) is distinct from the `read_failed`
*refusal code* the verb returns for an unreadable `path` argument: one is a
row in a successful response, the other ends the call.

**`file_lines` is emitted whenever the target was read**, which is `ok` and
`out_of_range` — the latter is *how* the caller sees that a citation to line
9,999 is pointing past a 442-line file, so omitting it there would remove the
finding's only evidence. It is absent for `missing_file`, `read_error`,
`ambiguous`, and `unresolved`, none of which opened a file.

**`unparsed[]` entries carry `doc_line`, `raw`, and `reason`, and are emitted
in document order** (left to right within a line). Two identical malformed
tokens on one line are two entries, distinguishable by position in the array
and nothing else — deliberate, since a column number would be the only field on
this verb whose value nothing else consumes.

**Ranges past EOF.** Only `start_line` decides `out_of_range`. A range whose
**end** exceeds `file_lines` — `:400-500` in a 442-line file — is `ok`:
`end_line` echoes what the doc wrote (500), `text` stops at EOF, and
`end_clamped:true` marks it. This is the common path (36% of the corpus is
ranges) and it is real drift information — the doc claims a span the file no
longer has — so it must be visible without being a hard failure.

`range_truncated` means "clipped to `max_range_lines`" and nothing else. It
never signals EOF clamping (`end_clamped`) nor byte-budget truncation
(`truncated`).

**Decoding.** Targets are decoded as UTF-8. A decode error, or an embedded NUL
byte, → `read_error` rather than mojibake `text`. `unresolved` is the one
unresolvable shape that lives in `citations[]` rather than `unparsed[]`,
because a bare `:NNN` has a valid locus and is a citation the author actually
made — merely un-attributable — where an `unparsed[]` entry may be prose that
was never a citation at all.

  rather than re-implemented. A cache that is absent, unparseable, or version-
  mismatched yields an empty map; the verb never cold-builds the index itself,
  because a multi-second build is the wrong thing to do inside a read verb.

  `unparsed_total`, and `basename_index_size` reports the map's size (0 for a

  it. When `Index::filesTruncated` is set at the `kMaxIndexFiles` cap (5,000),

  bare basename beyond the cap falls through step 2 to step 4 and lands in
  `unparsed[]` as `"unresolvable"`, indistinguishable from a genuine prose
  false positive like `` `6.2:1` ``. So the response also carries
  **`basename_index_truncated`** (omitted when false). Without it a project
  over 5,000 files would report real dead citations as unparseable prose and
  show every health field green — the same "degraded state that reads as clean"
  this design has had to close twice already, one layer further down.

**Explicitly NOT reused — `ReadRegion::extract`.** It was the obvious
candidate and does not fit, for three independent reasons: it opens and reads
the file on every call (defeating the line cache below), it never reports the
target's total line count (so `file_lines` and the `out_of_range` predicate
have no source), and its `truncated` is byte-based where `range_truncated` is
line-based. The engine therefore reads each target once into the cache and
slices from it — which yields `file_lines` for free, since the read already
walked the whole file.

## 3. RAM / build cost

- **Per-target read cap.** A target over `maxTargetBytes` (8 MiB) is **not
  read**: it is `read_error`, with no `file_lines`. Without this the cache's
  bound would govern only *retention*, and a single in-root citation to a
  generated `.json` or a log would pull an unbounded `QStringList` into memory.
- **Target-file line cache**, keyed by resolved path, so a doc citing one file
  30 times reads it once. Bounded at **16 files or `maxCacheBytes`, whichever
  binds first**; past the cap, further targets are read without being cached —
  no eviction, no LRU churn, no unbounded growth.

  **`maxCacheBytes` is measured in memory, not on disk, and the distinction is
  a factor of three.** The cache holds `QStringList`s: Qt strings are UTF-16, so
  an ASCII source doubles on the way in, and every line carries a `QString`
  header plus its own allocation. An 8 MiB source of ~40-byte lines is ~200k
  lines ≈ 16 MiB of characters plus ~8 MiB of per-string overhead. Budgeting the
  cache by file size would therefore promise 8 MiB and deliver ~24 MiB. The
  accounting is `sum over cached files of (2 × on-disk bytes + 40 × line count)`,
  charged before insertion, and the cap is set at **24 MiB** so the number in
  this spec is the number in RSS. Peak is `maxCacheBytes` + one in-flight
  `maxTargetBytes` read ≈ 24 + 24 MiB ≈ **48 MiB worst case**, against a
  realistic doc (a handful of small targets) of well under 5 MiB.
- **Input guard**: a doc over `maxDocLines` (20 000) is scanned to that line
  only; `scanned_lines` reports the prefix, `doc_lines` the true length, and
  `truncated:true` is set — but **no `next_offset`**, because the tail was never
  examined and no page reaches it (INV-31). Without the guard,
  `path:"ROADMAP.md"` (~19.5k lines, 673 citations measured 2026-07-26) is a
  legal call.
- **Time**: no wall-clock budget is set, because the work is bounded by
  construction — at most `maxDocLines` lines scanned, at most 16 cached targets
  plus the uncached tail read once each, and no network or subprocess. The
  densest real doc (56 citations over 5 distinct targets) is a handful of file
  reads. If a pathological doc ever makes this untrue, the fix is a lower
  `maxDocLines`, not a timeout mid-response.
- **Response budget**: `maxBytes` (128 KiB default — lower than the read-family
  512 KiB because the value here is a compact review artifact) bounds the
  **serialized response**. When it, `maxCitations` (400), or `maxUnparsed`
  (200) binds, whole trailing entries are dropped — never a half-populated
  entry — and `truncated:true` is set. `maxCitations` and `maxBytes` also emit
  `next_offset`; `maxUnparsed` does not, since `unparsed[]` has no paging.
  `returned` is always the emitted length.
- **Text normalisation**: a trailing `\r` is stripped from every emitted line
  and before the § 2.5 comparison, so a CRLF target does not produce phantom
  mismatches.
- **Build**: one new `.cpp` in an existing static lib; no new external
  dependency, no new target.

- **INV-24** — A malformed locus (`N < 1`, or end below start) is not a

  citing `src/a.cpp:0` and `src/a.cpp:10-5` → two `unparsed` entries, zero

- **INV-25** — Gate G: an in-root candidate whose **canonical** path leaves the

  `text`); plus an in-root symlink citation → `status:"ok"`.
- **INV-26** — The `counts` partition holds: the six status keys sum to
  `count`; `counts.ok` equals anchored-found + `anchor_missing` + `unchecked`;
  `counts.unparsed` equals `unparsed_total` and is excluded from `count`.

- **INV-27** — A range whose end exceeds `file_lines` is `ok` with `end_line`

- **INV-29** — Two citations on the same doc line, and two occurrences of the

  one line → `count:2`, one open (INV-20's counter).
- **INV-30** — `doc_lines` is the doc's true line count and `scanned_lines` the
  prefix actually scanned; they differ exactly when `maxDocLines` binds.
  *Test:* a 30-line fixture at `maxDocLines:10` → `doc_lines:30`,
  `scanned_lines:10`, `truncated:true`.
- **INV-31** — The `maxDocLines` guard is **not resumable**: it sets
  `truncated:true` and emits **no** `next_offset`, and no `offset` reaches a
  citation past `scanned_lines`. *Test:* the INV-30 fixture with citations on
  lines 5 and 25 → `count:1`, no `next_offset`; a follow-up call at
  `offset:1` returns an empty `citations[]`, never the line-25 entry.
- **INV-32** — A bare `:N` is a continuation only when it is a whole inline

- **INV-34** — A citation whose resolved path is a directory is `missing_file`,

  `src.d:1` with `<root>/src.d` an existing directory → `missing_file`, no

- **INV-35** — At the `max_bytes` floor the response still emits at least one

- **INV-36** — An unterminated fence sets `unterminated_fence` to the 1-based

## 6. Out of scope

- **Request-side `expect` map** → **ANTS-3642**. § 2.5's derived anchor covers
  22% of citations; the scripted-re-verification case the ROADMAP bullet names
  is genuinely unserved until this ships.
- **Directory / whole-corpus sweeps** → **ANTS-3643**. Needs a digest response
  shape (counts + stale subset, no text), which is a different contract.
- **Rewriting drifted citations.** A verb that edits line numbers in a doc is a
  different risk class; the drift may mean the *claim* moved, not the line.
  Not tracked — a deliberate non-goal.
- **Non-markdown *workflows*.** Scraping citations out of source comments
  (`// see foo.cpp:12`) as a review surface is out; the verb itself will read
  any UTF-8 text file handed to `path` (§ 2.1). Not tracked — a non-goal.
- **A reverse "which docs cite this file?" index.** That is a cache with an
  invalidation contract, and nothing has asked for it. Not tracked.

## Cold-eyes loop log

**Loop 1 (2026-07-26)** — 3 lanes (design / accuracy / conformance), two-tier:
all 3 breadth on Haiku, 2 escalated to depth. Accuracy lane accepted clean
(32 verification calls, 0 findings). Tally: **CRITICAL 4 · HIGH 7 · MEDIUM 12 ·
LOW 12 · INFO 3** — 35 verified, 1 dismissed.

Substantive fixes: `CodebaseIndex::serve` returns a `QJsonObject`, not an
`Index` — the named reuse could not have worked, replaced with
`fromJson`/`cachePathFor`; the `unparsed[]`/`unresolved`/`missing_file`
three-way contradiction resolved by making the § 2.4 ladder total;
`ReadRegion::extract` dropped as a reuse (it re-reads per call, cannot yield
`file_lines`, and its `truncated` is byte-based) in favour of slicing from the
cache; `PathValidation` demoted to a handler-only check; two unacknowledged
divergences from ANTS-3601 (non-existent path, directory path) either aligned
or stated; the five mandatory `claudeintegration.cpp` registration hooks
enumerated; `read_error`, `bad_locus`, `maxDocLines`, `maxUnparsed` and CRLF
handling added.

The load-bearing correction: § 2.5's anchor idiom was asserted "dominant" and
measures **22%** (404/1,830 as counted then; re-measured in loop 3 as 388/1,791, same ratio). `only:"stale"` as first drafted would have
dropped the unanchored 78% of healthy citations, making a filtered view read
"all clear" over citations that were never judged. Fixed by keeping `counts`
whole-doc, adding `counts.unchecked`, and deferring the real `expect` mode to
ANTS-3642.

**Loop 2 (2026-07-26)** — same 3 lanes, re-briefed cold. All 3 breadth clean of
CRITICAL/HIGH; 2 escalated to depth on MEDIUM suspicion and the depth pass
found substantially more. Tally: **CRITICAL 6 · HIGH 6 · MEDIUM 14 · LOW 16 ·
INFO 3**.

The finding that mattered: loop 1's symlink guard was a **false security
claim**. `QFileInfo::isSymLink` inspects only the final path component, so
`src/link/foo.cpp:1` — where `src/link` is a symlink to an out-of-root
directory — passed it and would have been read. It also contradicted the same
paragraph's "must not stat" rule and made INV-6 unsatisfiable as written.
Replaced with **gate G**: `PathValidation::isInsideProject`
(`src/pathvalidation.h:60`, ANTS-1832) canonicalises both sides, resolving
*every* component, and returns a bare boolean with no envelope — the
per-citation granularity loop 1 wrongly concluded `PathValidation` could not
offer. Step 0 is now purely lexical with zero filesystem calls (INV-6) and gate
G is a separate post-resolution step (INV-25).

Also substantive: `counts` had no bucket for `unparsed[]`, so a cold or
truncated codebase index — which pushes ~72% of the corpus into that array —
was invisible, reproducing loop 1's own "reads as all clear" failure one layer
down (fixed with `counts.unparsed`, `unparsed_total`, `basename_index_size`);
ranges whose **end** passes EOF were undefined on 36% of the corpus (fixed with
`end_clamped`); `maxBytes` did not say whether it bounded text or response, nor
what exhaustion did (pinned to serialized bytes, whole-entry drops,
`next_offset`); the line cache bounded *retention* but not *reads*, so one
citation to a large generated file was unbounded (fixed with `maxTargetBytes`);
`maxCitations` had no pagination escape (added `offset`/`next_offset`); the
`ambiguous`-antecedent branch of the sticky rule was undefined precisely where
§ 2.2 called it out; and the ETag claim ("neither the doc nor any line it cites
has moved") was overbroad, since the response holds only clipped text.

**Loop 3 (2026-07-26)** — same 3 lanes, re-briefed cold, all three dispatched
straight to depth: loop 2's cheap breadth pass had come back clean of
CRITICAL/HIGH on lanes the depth pass then found 6 CRITICALs in, so breadth was
not routing usefully on this spec and was skipped rather than trusted. Tally:
**CRITICAL 3 · HIGH 8 · MEDIUM 11 · LOW 22 · INFO 3** — 47 verified, 0
dismissed. All three lanes independently found the same registration-file
error, from three different directions.

Two findings were genuine design holes. **The continuation grammar had no
left-context rule**: `continuation := ":" locus` plus § 2.3's "the scan runs on
the raw line" meant `09:45` in prose parsed as a citation, inherited an
unrelated path, and would have emitted *the real text of that file's line 45*
under `status:"ok"` — a confidently-wrong answer, which is the one output this
design exists to prevent. Fixed by requiring a continuation to be a whole
inline code span (INV-32). And **INV-17 promised a resumable `next_offset` for
all four caps**, but `maxDocLines` truncates the *scan*, not the list: no
`offset` reaches an unscanned line, so the largest docs would have paged
forever over the same prefix. Split into INV-17 (resumable) and INV-31 (not).

Also substantive: the § 3 memory budget counted **on-disk** bytes for a cache
of UTF-16 `QStringList`s, understating peak RSS by ~3× (re-derived, and
`maxCacheBytes` is now stated in in-memory bytes); a **truncated** codebase
index reported `basename_index_size` large and healthy while silently
misfiling real dead citations as unparseable prose (`basename_index_truncated`
added — the third time this loop sequence has had to close a
degraded-state-reads-as-clean path, after loop 1's filtered view and loop 2's
missing `unparsed` bucket); an unterminated fence would have blanked every
citation after it with `truncated:false` (`unterminated_fence` added); the
grammar had no production for the trailing `/`/`+` that INV-9 tested, and no
digit cap, so an adversarial locus overflowed an `int`; `max_bytes` had no
floor, so a small value produced `next_offset == offset` and an infinite paging
loop; the ladder tested existence rather than file-ness; sort order was never
defined although `offset` paging depends on it; and `registerToolProvider` was
attributed to `claudeintegration.cpp` when it lives in `mainwindow.cpp`,
contradicting this spec's own § 2.7 table. A sixth registration hook
(`selection_hint`) was missing entirely — without it the verb ships with an
empty "when to use" on the `tool_info {catalog:true}` surface `CLAUDE.md`
points every session at.

**The pattern worth naming, since it is now three-for-three.** Roughly half of
every loop's findings have been the same defect class, and it is not in the
design: invented illustrative detail. Loop 1 fabricated example data, loop 2
produced an arithmetically impossible example, loop 3 found the example
fabricated *again* — its `bad.cpp` entry cited a doc line that holds no
citation, and demonstrated the exact inverse of the sorting/cap/flag rule
sitting 90 lines above it — alongside a wrong file length (412 vs 372), a
corpus count off by 2.7× (~1,800 vs 673), and a `:~197` exemplar that exists
nowhere but this spec. The design core, by contrast, has been endorsed on
review. So the structural fix this loop is not another round of corrections:
**the worked example is now explicitly synthetic and derivable from the rules
by inspection**, so it cannot rot and cannot be mistaken for a capture, and
**every corpus figure now carries the command that produced it** (§ 1). Both
changes remove the failure mode rather than its current instance.
