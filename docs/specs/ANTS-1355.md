# ANTS-1355 — `token_usage` v2: wrap-overhead + latency breakdown

**Status:** spec draft, pre cold-eyes (2026-05-15). Loop log at end (§ 10).
**Source:** indie-review-2026-05-14 lane-3 follow-up — "`token_usage` v2:
break out wrap overhead + latency." ROADMAP.md ANTS-1355.
**Blocked by:** none (additive fields on existing in-process counter).
**Pairs with:** ANTS-1284 (v1 — `token_usage` engine + tool, shipped
2026-05-14), ANTS-1294 (wrap framing — shipped 2026-05-14), ANTS-1360
(`mcp_trace` ring with per-call `duration_us`, shipped 2026-05-15).

## 1. Problem

`token_usage` v1 reports per-tool `bytes_in`, `bytes_out`, and an
`est_tokens_saved` displacement delta. Two cost dimensions are
**hidden inside `bytes_out`** that v1 cannot surface:

1. **Wrap overhead (ANTS-1294).** Every non-control-plane response
   is enclosed in `<ants_mcp_data tool="…">…</ants_mcp_data>` framing
   at dispatch. The current `bytes_out` accounts the *wrapped*
   payload — there is no way to ask "how many bytes are framing vs
   payload" from the report. After 100 calls to a tool returning a
   500-byte payload, framing adds ~3500 B (35 B/call × 100); v1
   silently rolls that into `bytes_out` and the saved-delta math.
   If a future tool registration adds a long tool-name (raising the
   per-call wrap to ~50 B), or the framing format changes (ANTS-1296
   namespacing prefix), the regression hides inside `bytes_out`.

2. **Latency (ANTS-1360 `duration_us`).** The `mcp_trace` ring stores
   per-call latency on every dispatch, but the ring is a debug tap
   capped at 200 records. A long session sees the oldest records
   evicted, so questions like "what's the typical `roadmap_query`
   latency this session?" cannot be answered after ~200 calls. v1
   tracks no aggregates.

The fix is two additive accumulators on `TokenUsageEngine::ToolCounter`:
a cumulative `wrapBytes` and a `(min, max, sum, count)` latency
quadruple. The MCP response surfaces them as new top-level + per-tool
fields. The engine API gains two parameters on `recordCall` (wrap
bytes + duration µs). The dispatch site is the single mutation point
and already has both values in hand (the wrap delta computed from
`wrapped.size() - responseText.size()`; the duration from the same
`QElapsedTimer` ANTS-1360 starts).

### 1.1 Why aggregate inside `TokenUsageEngine`, not derive from `mcp_trace`?

Three reasons:

- **Ring capacity.** `mcp_trace` caps at 200 records (ANTS-1360
  spec § 2.5). A session with > 200 MCP calls loses the oldest
  records; aggregates derived from it are biased toward recent
  calls. Aggregates inside `token_usage` track every call since
  `since`.
- **Single source of truth for per-tool totals.** v1 already
  aggregates `bytes_in` / `bytes_out` / `n_calls` per tool;
  adding `wrap_bytes` + latency next to them keeps related
  numbers in one struct rather than spread across two engines.
- **Read cost.** `buildReport` already iterates `m_counters`
  (O(distinct tools)). Adding 4 more sums to the loop is free.
  Reconstructing the same view from the ring is O(ring size) = up
  to 200 records per call; pays nothing for tools with > 200 calls.

`mcp_trace` keeps its per-call event role (raw records for
debugging; the same data the assistant uses to spot a stuck tool);
`token_usage` v2 keeps the session-aggregate role.

## 2. Surface

### 2.1 Tool signature

Unchanged from v1:

```
mcp__ants__token_usage
  (no required args)

  optional: include_zero: bool   // default false
```

No new args. Backwards-compatible by construction.

### 2.2 Response shape (v2)

```json
{
  "ok": true,
  "since": "2026-05-15T11:02:00Z",
  "since_unix_ms": 1810378920000,
  "calls": [
    {
      "tool": "roadmap_query",
      "n_calls": 8,
      "bytes_in": 124,
      "bytes_out": 48312,
      "wrap_bytes": 312,
      "duration_us_min": 412,
      "duration_us_max": 11_204,
      "duration_us_mean": 2_847,
      "est_tokens_saved": 110888
    }
  ],
  "total_saved": 110888,
  "total_wrap_bytes": 312,
  "tools_called": 1,
  "reset_performed": false
}
```

**New fields, per-tool (`calls[i]`):**

| Field | Type | Meaning |
|---|---|---|
| `wrap_bytes` | int (bytes) | Cumulative ANTS-1294 framing overhead across `n_calls`. Computed at dispatch as `wrapped.toUtf8().size() - responseText.toUtf8().size()`. Always `0` for control-plane tools (`get_session_info`, `token_usage`) whose responses bypass the wrap (verified `claudeintegration.cpp:2700–2705`). |
| `duration_us_min` | int (µs) | Smallest single-call latency observed since `since`. `0` if `n_calls == 0` (the entry only exists when `n_calls ≥ 1`, so `0` here means a genuine sub-µs sample, not "uninitialised"). |
| `duration_us_max` | int (µs) | Largest single-call latency observed. |
| `duration_us_mean` | int (µs) | Integer arithmetic mean: `floor(duration_us_sum / n_calls)`. Sum is not surfaced (chosen over `_p95` because v2 has no reservoir; see § 9 out-of-scope). |

**New field, envelope-level:**

| Field | Type | Meaning |
|---|---|---|
| `total_wrap_bytes` | int (bytes) | Sum of `wrap_bytes` across **all** tracked tools (including those filtered out of `calls[]` by `include_zero:false`). Lets the caller answer "how much of my session bytes_out was framing?" with one number. |

`est_tokens_saved` semantics unchanged from v1 (INV-4 v1). v2
deliberately does NOT change the math to subtract `wrap_bytes` — the
v1 formula already counts the wrap inside `bytes_out`, so the
displacement delta is correct as-is. `wrap_bytes` is informational.

### 2.3 Backwards compatibility (INV-12)

- **Field additivity.** v1 callers parsing the response see four
  extra per-tool fields + one extra envelope field. A strict-mode
  JSON-schema validator would reject these (no schema in v1 §
  2.2 — INV-6 v1 declared `additionalProperties:false` on the
  *input*, not the output). v2 adds **no** strictness to the
  response.
- **Field ordering.** New per-tool fields are inserted between
  `bytes_out` and `est_tokens_saved` in the documented shape, but
  JSON object key order is not contract — only field names are.
- **Engine ABI break.** `recordCall(toolName, bytesIn, bytesOut)`
  becomes `recordCall(toolName, bytesIn, bytesOut, wrapBytes,
  durationUs)`. This is a source-level break, but the engine has a
  single in-tree caller (the dispatch site at
  `claudeintegration.cpp:2713`) and a single test-only seam
  (`ClaudeIntegration::recordTokenUsageForTest` at
  `claudeintegration.h:231`). Both are updated atomically in the
  ship commit. No external callers; no compatibility shim needed.
- **Test seam compat.** `recordTokenUsageForTest` v2 takes the new
  parameters as defaulted (`wrapBytes = 0, durationUs = 0`) so
  existing tests recompile without touching every callsite. New
  tests opt in.

### 2.4 Engine API (v2)

```cpp
namespace TokenUsageEngine {

struct ToolCounter {
    int     nCalls         = 0;
    qint64  bytesIn        = 0;
    qint64  bytesOut       = 0;
    qint64  wrapBytes      = 0;       // NEW
    qint64  durationUsMin  = 0;       // NEW; sentinel "unset" handled via nCalls==0
    qint64  durationUsMax  = 0;       // NEW
    qint64  durationUsSum  = 0;       // NEW
};

struct ToolReport {
    QString tool;
    int     nCalls         = 0;
    qint64  bytesIn        = 0;
    qint64  bytesOut       = 0;
    qint64  wrapBytes      = 0;       // NEW
    qint64  durationUsMin  = 0;       // NEW
    qint64  durationUsMax  = 0;       // NEW
    qint64  durationUsMean = 0;       // NEW; computed in buildReport
    qint64  estTokensSaved = 0;
};

struct Snapshot {
    qint64           sinceUnixMs    = 0;
    QList<ToolReport> calls;
    qint64           totalSaved     = 0;
    qint64           totalWrapBytes = 0;  // NEW
    int              toolsCalled    = 0;
};

class Tracker {
public:
    Tracker();
    // Signature break. See § 2.3.
    void recordCall(const QString &toolName,
                    qint64 bytesIn,
                    qint64 bytesOut,
                    qint64 wrapBytes,
                    qint64 durationUs);
    void reset();
    Snapshot buildReport(bool includeZero) const;
    static qint64 baselineFor(const QString &toolName);
    qint64 sinceUnixMs() const;
};

}
```

### 2.5 Instrumentation point (delta vs v1)

`src/claudeintegration.cpp:2700–2719`. The dispatch site already
holds every value v2 needs; the change is the single `recordCall`
line:

```cpp
// v1:
const qint64 outBytes = wrapped.toUtf8().size();
m_tokenUsage.recordCall(toolName, argBytes, outBytes);

// v2:
const qint64 outBytes  = wrapped.toUtf8().size();
const qint64 rawBytes  = responseText.toUtf8().size();
const qint64 wrapBytes = outBytes - rawBytes;          // ≥ 0 (INV-3)
const qint64 durUs     = mcpTraceTimer.nsecsElapsed() / 1000;
m_tokenUsage.recordCall(toolName, argBytes, outBytes, wrapBytes, durUs);
```

Reuses the same `mcpTraceTimer` ANTS-1360 already starts before the
cache lookup (line 2643). One QElapsedTimer, two consumers.

**Failure-path symmetry.** The `tool_not_found` branch at
`claudeintegration.cpp:2721–2733` does *not* call `recordCall`
in v1 (token_usage v1 only counts successful dispatches —
verified by reading the `if (toolHandled)` guard). v2 keeps this:
unknown tools never appear in `token_usage` (they appear in
`mcp_trace` with `result:"tool_not_found"` per ANTS-1360 INV-7).
Rationale: token_usage measures displacement of *real* tools;
counting non-existent ones distorts the per-tool totals (`n_calls`
for `foo_misspelled` is not actionable).

### 2.6 Response builder (delta in `remotecontrol.cpp`)

`cmdTokenUsage` at `remotecontrol.cpp:3157–3199`. Three additions to
the existing builder:

```cpp
// Envelope:
env["total_wrap_bytes"] = static_cast<qint64>(snap.totalWrapBytes);

// Per-call object (inserted between bytes_out and est_tokens_saved):
c["wrap_bytes"]        = static_cast<qint64>(r.wrapBytes);
c["duration_us_min"]   = static_cast<qint64>(r.durationUsMin);
c["duration_us_max"]   = static_cast<qint64>(r.durationUsMax);
c["duration_us_mean"]  = static_cast<qint64>(r.durationUsMean);
```

`buildReport` v2 derives `durationUsMean` per entry:

```cpp
r.durationUsMean = (it.value().nCalls > 0)
    ? (it.value().durationUsSum / it.value().nCalls)
    : 0;
```

`durationUsSum` itself is not exposed to the wire (INV-9).
Rationale: surface the *meaningful* metric (mean) and the
*decision-grade* bounds (min, max); the underlying sum is
implementation detail and would invite "why don't I get this from
the wire" requests when the answer is "compute mean × n_calls
locally if you really need it." Keeping sum private narrows the
contract.

## 3. Invariants

- **INV-1 (carried from v1).** Counter exactness. `recordCall`
  increments `n_calls` by exactly 1 per call AND adds the supplied
  byte counts.

- **INV-2 (carried from v1).** Byte units are UTF-8 wire bytes for
  `bytes_in`, `bytes_out`, AND `wrap_bytes` (computed as the
  difference of two `.toUtf8().size()` calls — same units, so the
  subtraction is well-defined).

- **INV-3 (new — wrap_bytes non-negative).** `wrapBytes` is always
  `≥ 0`. The dispatch site computes `wrapBytes = wrapped.size() -
  responseText.size()` where `wrapped` is one of:
  - `responseText` itself for control-plane tools → `wrapBytes = 0`.
  - `wrapMcpData(toolName, responseText)` otherwise. The wrap is a
    pure-suffix-and-prefix transform (`<ants_mcp_data tool="…">` +
    body + `</ants_mcp_data>`, plus escape substitutions verified at
    `claudeintegration.cpp:2763–2795`); every escape substitution
    is **non-shrinking** (a `</ants_mcp_data>` becomes
    `<ants_mcp_data_escaped/>` — 16 chars → 24 chars; the regex
    variant `</\s*ants_mcp_data\s*>` ≤ same source → ≥ same target;
    HTML entity encoding of `&`/`<`/`>`/`"` in `safeTool` is also
    strictly non-shrinking — verified `claudeintegration.cpp:
    2790–2794`).
    Therefore `wrapped.size() ≥ responseText.size()` strictly.

- **INV-4 (new — duration min/max correctness).** On the first
  call for a tool (`nCalls == 0 → 1`), `durationUsMin` and
  `durationUsMax` are set to the supplied `durationUs`
  unconditionally. On subsequent calls, `durationUsMin =
  min(prev, durationUs)` and `durationUsMax = max(prev, durationUs)`.
  Sentinel pattern: a zero-initialised `durationUsMin` is overwritten
  on first record (not treated as a real "0 µs sample" that would
  pin min forever).

- **INV-5 (new — duration_us_mean = floor(sum / n)).** Integer
  division; rounds toward zero. Documented so consumers don't
  expect floating-point precision. Worst-case truncation error is
  `< 1 µs` per tool — negligible at the cost-decision granularity
  these numbers inform.

- **INV-6 (carried from v1).** Reset atomicity. `Tracker::reset()`
  clears every accumulator (including the new ones) AND updates
  `m_sinceUnixMs` to "now" in the same method body.

- **INV-7 (carried from v1).** `est_tokens_saved` floor. Unchanged.
  v2 does NOT subtract `wrap_bytes` from the saved math — the v1
  formula already counted wrap inside `bytes_out`, so the delta is
  correct.

- **INV-8 (carried from v1).** Baseline lookup O(1). Unchanged.

- **INV-9 (new — `duration_us_sum` not surfaced).** The wire
  response includes `duration_us_mean` but **never** the sum that
  produced it. Tightens the public contract; private state of the
  engine.

- **INV-10 (carried from v1).** Pure-read `buildReport`. v2's added
  per-entry mean computation is pure (reads from `ToolCounter`,
  writes to a new `ToolReport`); no mutation of `m_counters`.

- **INV-11 (carried from v1).** Single-threaded mutation.

- **INV-12 (new — backwards-compat surface).** The v2 response is a
  proper superset of the v1 response: every v1 field is present
  with v1-identical semantics. Callers that parse v1 should
  continue to parse v2 (modulo strict-additional-property
  validators, which v1 did not specify on the response).

- **INV-13 (new — RAM bound).** Per-entry growth: v1 was ~96 B
  (24 B `ToolCounter` + ~72 B `QHash` overhead per slot + key). v2
  adds 4 × `qint64` = 32 B to the counter struct → ~128 B/entry.
  Worst-case after a session calls all currently-registered tools
  (`grep -c registerToolProvider src/mainwindow.cpp = 32` verified
  2026-05-15 + 1 inline `get_session_info` = 33 tools):
  33 × 128 B = ~4.2 KiB. (v1 INV-8's 6 KiB estimate already
  rounded up; v2 stays well inside.)

- **INV-14 (new — failure path is not counted).** Unknown-tool
  dispatches (the `tool_not_found` branch at line 2721) do NOT
  invoke `recordCall`. Their record exists only in `mcp_trace`
  with `result:"tool_not_found"`. Verified by re-reading
  `claudeintegration.cpp:2694–2733`: `recordCall` is inside the
  `if (toolHandled)` arm.

## 4. Failure modes

- **`durationUs` negative on the wire (shouldn't happen).** The
  dispatch site computes `mcpTraceTimer.nsecsElapsed() / 1000`;
  `QElapsedTimer` is monotonic on all supported platforms (Qt6
  docs: backed by `clock_gettime(CLOCK_MONOTONIC_RAW)` on Linux).
  If `nsecsElapsed()` ever returned negative (timer not started),
  the division rounds toward zero. Defensive only — not asserted
  in v2; INV-4 documents the assumption.

- **Tool re-registers with same name mid-session.** Counter state
  persists across re-registration (`m_counters` is keyed by name).
  Same as v1 — no behaviour change.

- **`include_zero:false` filters out a tool whose `est_tokens_saved
  == 0` but `wrap_bytes > 0`.** The tool drops from `calls[]` (v1
  filter unchanged). However, its `wrap_bytes` contribution to
  `total_wrap_bytes` is preserved — that envelope-level field
  sums across **all** tracked tools, not just the filtered subset.
  Documented; tests assert this.

- **Counter overflow.** `qint64::max ≈ 9.2 EB` or `~290 millennia
  of microseconds`. Not achievable in practice. No special handling.

## 6. Performance / RAM budget

- **Engine RAM**: ≤ 3.5 KiB worst case (INV-13).
- **Per-call instrumentation overhead**: adds 4 × integer compare/
  add operations (~10 ns) on top of v1's ~6 µs. Negligible.
- **`buildReport` cost**: adds one division per entry for
  `durationUsMean`. O(distinct tools) — same complexity as v1.
- **Response payload size**: 4 new per-tool int fields (≈ 80 B
  per tool with key text + integer) + 1 envelope int. Worst case
  27 tools × 80 B = ~2 KiB added to the response. Typical
  ~3–5 tools touched per session → ~300 B added.
- **No new threads, no new file watchers, no new caches.**

## 7. Migration

- Same in-process counter — no on-disk state, no schema migration.
- v1 tests touching `recordCall` recompile thanks to the defaulted
  test seam (§ 2.3); they continue to pass without changes
  (`wrapBytes = 0, durationUs = 0` defaults match v1 behaviour
  exactly when those fields didn't exist).
- One commit ships engine + dispatch site + response builder + new
  tests; no flag, no opt-in.

## 8. Workflow integration

Same as v1 (end-of-session summary; mid-session prioritisation).
Two new questions v2 lets the assistant answer:

1. **"Is the wrap costing us?"** — If `total_wrap_bytes` is > 10%
   of cumulative `bytes_out` summed across `calls[]`, surface as a
   flag for the v3 framing-compression idea (out of scope here).

2. **"Which tool is slow?"** — `duration_us_max` per tool identifies
   the worst latency outlier. `duration_us_mean` identifies the
   typical cost. Cross-reference with `n_calls` to know whether
   a slow outlier is a one-off (high max, low mean) or systemic
   (high mean).

## 9. Out of scope

- **p50/p95 percentile latency.** Would need a reservoir sampler
  (or T-Digest). v2 ships min/max/mean only. A future v3 could
  add percentiles if the cost decisions need them; v2's
  min/max/mean is enough to flag pathological cases.

- **Per-cwd / per-project latency breakdown.** Same v1 caveat —
  counters are global to the ants-terminal process.

- **Failure-path latency.** Unknown-tool dispatches are recorded in
  `mcp_trace` (with full duration_us) but not in `token_usage`
  (INV-14). v2 does not change this; if a future need arises, it
  needs a separate `failed_calls` counter, not a re-aggregation of
  the existing one.

- **Updating est_tokens_saved math to subtract wrap_bytes.** The v1
  formula already counts wrap inside `bytes_out` — the displacement
  delta is correct. Changing the formula would silently shift every
  prior reading.

- **Exporting `duration_us_sum` on the wire.** Private engine
  state (INV-9). Consumers compute `mean × n_calls` if they need
  the total.

- **A `mutex`-protected `Tracker` for thread-safe access.** Same as
  v1 INV-7 (single-threaded model unchanged).
