# ANTS-2093 — Sandboxed server-side query verb (`project_query`)

**Status:** **implemented on main** (2026-06-25). Cold-eyes loops 1–5 folded
(clean pass loop 5). Implemented per this spec with one layering correction
(see *Implementation note* below — the handler is `LuaEngine::projectQueryVerb`
in `ants_lua_lib`, not `cmdProjectQuery` in core-lib `remotecontrol.cpp`).
11 feature tests in `tests/features/project_query/` (test_claude bundle) green;
test_lua + full test_claude (1216) still pass. Flips to shipped X.Y.Z at next
release.
**Kind:** feature.
**Source:** ROADMAP.md ANTS-2093 (in-session-2026-06-11 — the code-execution /
"code-mode" pattern, Anthropic-documented ~98.7% token reduction; promoted
considered→planned 2026-06-25 as phase-2 of the token-savings bundle, after the
ANTS-2090 tabular-encoding spec).
**Composes with:** ANTS-2094 (result offload, `docs/specs/ANTS-2094.md`) — a
query result large enough to spill still rides the offload path; ANTS-1901
(master MCP gate — `claude.mcp_enabled`); ADR-0004 (same-UID trust model,
`docs/decisions/0004-same-uid-trust-model-for-mcp-audit-suite.md`). Reuses the
hardened Lua sandbox in `src/luaengine.{cpp,h}` (ANTS-1172 / ANTS-1268 /
ANTS-1332 / ANTS-2001).

**Layman:** Today, when Claude needs a number that lives across many project
files ("how many TODOs are there?", "which files import X?"), it reads every
file into the chat and counts by hand — thousands of tokens of raw text just to
get one answer. This adds a verb that lets Claude send Ants a tiny read-only
script, Ants runs it safely over the files on its side, and hands back **only
the answer** — the number, not the files. The script can only *read* inside the
current project, can't write anything, can't touch the network, and is killed
if it runs too long or uses too much memory.

## 1. Problem

The biggest avoidable token cost in an Ants MCP session is **reading raw file
content into the conversation only to compute a small aggregate over it**:
count, filter, group-by, sum, "which files match a predicate". A grep+Read loop
pulls every matched line (or whole files) into context, the model reduces them
to one figure, and the raw text is never referenced again. Anthropic's
code-execution / "code-mode" write-up measured ~98.7% token reduction by
flipping this: the agent ships *code* that computes server-side and gets back
*only the result*.

Ants is unusually well-placed to offer this because it **already ships a
hardened Lua sandbox** — verified surface (`src/luaengine.cpp`):

1. Only 5 standard libraries are opened — `string`, `table`, `math`, `utf8`,
   and the base library (the Lua standard globals, loaded via `luaopen_base` and
   exposed as the `_G` table) — via `luaL_requiref` (`luaengine.cpp:110–114`). `os`, `io`, `package`/`require`,
   `coroutine`, `debug` are **never loaded**.
2. `sandboxEnvironment()` (`luaengine.cpp:294`) is an **allowlist** (close by
   default, ANTS-1268): it enumerates `_G` and nils every name not on
   `kAllowed` (`luaengine.cpp:304–341`), additionally nils `string.dump`
   (`:355`), and redirects `print`/`warn` away from host stdio (`:371`, `:378`).
3. A custom allocator `luaAlloc` (`luaengine.cpp:35`) enforces a hard
   `MAX_LUA_MEMORY = 10 * 1024 * 1024` (10 MiB) per VM (`luaengine.h:59`).
4. An instruction-count + per-line hook installed via `lua_sethook(...,
   LUA_MASKCOUNT | LUA_MASKLINE, 100000)` (`luaengine.cpp:141`) plus a
   wall-clock deadline (`startPcallBudget()`, `luaengine.cpp:196`, default
   `m_pcallBudgetMs = 1500`, `luaengine.h:180`) with a sticky-kill latch
   (`m_killed`, `luaengine.cpp:175`) so inner `pcall`s can't swallow a timeout.
   **Caveat (load-bearing for §2.4 / INV-4):** the hook is dormant during a
   single uninterruptible C call (one giant `string.gsub`/`table.sort`), so the
   wall-clock budget cannot preempt it — "the budget is enforced at the next
   bytecode boundary" (`luaengine.cpp:134–136`); the existing engine handles
   that case off the GUI thread plus a detach path, not via the hook
   (`luaengine.cpp:159–160`).
5. Bytecode is rejected and load is text-only (`luaL_loadfilex(..., "t")`,
   `luaengine.cpp:386–401`).

So the sandbox — the hard part of safely running agent-supplied code — exists
and is field-proven. **What it does not have**, confirmed this session, is the
surface a query verb needs (none of these are reusable today):

- **No file-read primitive exposed to Lua.** No `io`/`os`, no `loadfile`, and
  no `ants.*` function reads disk. The only host-side `QFile`/`QDir` use is in
  `PluginManager` and is never Lua-callable.
- **No string entry point + result marshaller.** `loadScript`
  (`luaengine.cpp:379`) loads a *file* and **discards return values**;
  `fireEvent` (`:442`) marshals only a single boolean veto. No
  "run this code string, return its value" path exists.
- **No output-size cap.** The 10 MiB cap bounds *VM memory*; nothing bounds the
  bytes of a value handed back to C++.

This spec covers exactly that delta — a read-only file primitive scoped to
`caller_cwd`, a string-entry + result marshaller, and an output cap — bolted
onto the existing sandbox.

### 1.1 Threat model (what the sandbox is defending against)

The caller is the **local Claude Code agent**, same-UID — ADR-0004 is the
canonical statement of that trust model; this section adds only the
Lua-snippet-specific risk. The realistic threat is a **buggy LLM-generated
snippet**, not a crafted exploit: an accidental infinite loop, an unbounded
allocation, a path typo that walks out of the project, a snippet that returns a
50 MB dump. The sandbox bounds every one of those (read-only · FS-confined to
`caller_cwd` · 10 MiB · wall-clock-capped on a worker thread, §2.4 · output-
capped · no network/exec/write) — the bar to judge the controls against is
**damage-limitation of accidents**. A same-UID *local attacker* is explicitly
**out of scope**: they can already run arbitrary code directly (per ADR-0004), so
this does **not** widen that trust boundary — `project_query` adds a
*more*-restricted path for the agent, never a less-restricted one.

## 2. Surface

### 2.1 New verb `project_query`

A new read MCP verb (`cmdProjectQuery` in `src/remotecontrol.cpp`, registered in
the dispatch registry like the existing `project_*` verbs — `project_layout` /
`project_settings` / `project_conventions`). `CallerCwdContract::Required`:
`caller_cwd` both routes the project **and** is the filesystem allowlist root.

Per-call arguments — deliberately just two (tuning lives in config, §2.5,
mirroring the ANTS-2094 offload knobs):

| Arg | Type | Required | Meaning |
|---|---|---|---|
| `caller_cwd` | string | yes | Project root; canonicalised, becomes the FS allowlist anchor. |
| `code` | string | yes | The read-only Lua snippet. Must `return` a value (the answer). |

Success envelope:

```json
{ "ok": true, "result": <marshalled value>, "elapsed_ms": 12 }
```

`result` is the marshalled top-of-stack return value of the snippet (§2.4).
There is no `head`/`offloaded` field here — if the *wrapped* envelope is large
enough, the standard offload transform (ANTS-2094) masks it downstream like any
other read reply (§3 INV-9).

A refusal uses the standard MCP envelope shape (`docs/standards/mcp-error-codes.md`
§ 1) — `{ "ok": false, "error": "<message>", "code": "<refusal_code>" }` — with
the `code` drawn from the §2.5 / §3-INV-8 set: the **existing** `missing_field`
and `mcp_disabled`, plus **five new codes added by this work** (`query_error`,
`query_timeout`, `query_oom`, `result_too_large`, `query_disabled` — §7). A
refusal (`ok:false`) is small and is **never** offloaded (ANTS-2094 masks only
large `ok:true` read bodies); offload composition (INV-9) concerns the success
result only.

### 2.2 The read-only Lua API (`project.*`)

A query VM is configured exactly like the plugin VM (5-lib allowlist +
`sandboxEnvironment()` + allocator + hook) **except** `registerApi()` is
replaced by a `registerQueryApi()` that installs **only** a read-only `project`
table — and **none** of the plugin write/side-effect callbacks (`ants.send`,
`ants.notify`, `ants.set_status`, `ants.settings.set`, `ants.clipboard.write`,
`ants.palette.register`, `ants.on`). The `ants` table is absent entirely in
query mode; `project` is the whole host surface:

| Function | Returns | Behaviour |
|---|---|---|
| `project.read(relpath)` | string | UTF-8 contents of a file **inside** the root. Raises a Lua error (caught → `query_error`, §3 INV-8) on a path that escapes the root, a missing file, or a read failure. |
| `project.list(subdir?)` | array of relpaths | Project-relative paths of regular files under the root (or under `subdir`, itself root-confined). Skips `.git/` (internal metadata, not project content; also perf on large repos). Order is sorted **by byte/UTF-8-codepoint, locale-independent** (determinism, INV-7). |
| `project.root()` | string | The absolute canonical root (for building messages); read-only. |

This is the **minimal sufficient** surface: `list` to enumerate, `read` to pull
a file, and the `string`/`table`/`math`/`utf8` libs to filter/aggregate. The
snippet greps and counts *itself*; Ants returns only what the snippet
`return`s. Richer primitives (a host-side `project.search(pattern)` that drives
ripgrep, glob filters, line iterators) are **out of scope v1** (§5) — `list` +
`read` + the string lib cover count/filter/aggregate, which is the documented
win.

**Not a `workspace_search` replacement.** Whole-repo *content* scanning is what
ripgrep (`workspace_search`) is for; pulling every file through `project.read`
to scan it would burn the VM's 10 MiB / 1.5 s budget on a large tree. The
intended shape is "scope to a known file set (or a `workspace_search` result),
then aggregate" — noted in the verb's `description` so the agent picks the right
tool.

### 2.3 Filesystem confinement (the load-bearing control)

Every `project.read` / `project.list` path is resolved and **confined to the
canonical `caller_cwd`** before any disk access, reusing the project's
established path-anchoring rather than re-deriving it:

The single confinement mechanism is **`PathValidation::validatePath`**
(ANTS-1295) — the same helper the `bad_path` code is documented against
(`docs/standards/mcp-error-codes.md` § 1). Its signature already accepts an
arbitrary root: `validatePath(rawPath, rootCanonical, toolName, paramName,
allowOutsideRoot=false)` (`pathvalidation.h:46–50`), performing NFC +
control-char/backslash rejection + canonicalisation + root anchoring. Call it
with `rootCanonical` = the canonicalised `caller_cwd` and `allowOutsideRoot`
left **false** — no wrapper, no forked logic. Internally that logic is the
canonical-prefix containment also proven at `pluginmanager.cpp:309–352`
(`canonicalRoot = QFileInfo(root).canonicalFilePath()`, then accept a path iff
its own `canonicalFilePath()` equals `canonicalRoot` or `startsWith(canonicalRoot
+ "/")`) — the **mandatory** property is **canonicalisation, not string
prefixing**, so a symlink whose target lies outside the root is rejected,
exactly as the plugin scanner rejects a symlinked `init.lua`
(`pluginmanager.cpp:364–374`).

A path that fails confinement makes the `project.*` call **raise a Lua error**
(it does not silently return nil) — so an unguarded snippet fails loudly as
`query_error`, and a snippet that `pcall`s the read sees the failure. The host
never opens a file whose canonical path is outside the root, and never opens it
for writing. The **invariant** is canonical confinement to `caller_cwd` (INV-2);
`validatePath` already carries it (signature confirmed against current source,
`pathvalidation.h:46`).

### 2.4 Result marshalling + output cap

A new entry point on `LuaEngine` — `runQuery(code, root, caps) → QueryResult` —
loads `code` as a text-only buffer (`luaL_loadbufferx(..., "t")`, mirroring the
bytecode rejection in `loadScript`, `luaengine.cpp:386–401`), runs it under the
existing budget, and marshals the **single** top-of-stack return value.

**Execution thread (load-bearing — resolves the pure-C-spin freeze).** The MCP
`tools/call` dispatcher is **single-threaded on the Qt GUI thread**
(`claudeintegration.h:613–614`, "Single-threaded by INV-10 … Qt main thread").
Running the VM *directly* on that thread means a single uninterruptible C call
(catastrophic `string.gsub`) — which the wall-clock hook cannot preempt
(§1 caveat) — would **freeze the GUI**. So the query VM runs on a **fresh,
ephemeral worker thread created per call** — a *new* query-specific worker
(one `QThread` + one `LuaEngine` per `runQuery`, destroyed on return/timeout),
**modelled on** the ANTS-1750 parentless-engine `moveToThread` + detach pattern
(`pluginmanager.cpp:481–499`), **not** the plugin manager's long-lived
per-plugin threads or any shared pool: the dispatcher hands the snippet to the
worker and **waits on a bounded join** (`QThread::wait`, like
`pluginmanager.cpp:125`) of `timeout_ms` + a fixed **250 ms `grace`**. **Be
honest about what this costs:** the join runs *on* the GUI/dispatch thread, so a
well-behaved snippet returns in well under 100 ms but a pathological one **blocks
the GUI for up to `timeout_ms` + 250 ms** before the join gives up. The win over
running directly on the GUI thread is **bounded vs. unbounded**: a snippet stuck
in an uninterruptible C call (which the hook can't preempt) would freeze the GUI
*forever* if run inline; on the worker it is **detached** at the join deadline —
the verb returns `query_timeout` and the GUI resumes. The detached worker is
**not freed**: per the ANTS-1750 design it is held in a zombie list until process
exit (`pluginmanager.cpp:138–150`, `:492`), because its `lua_State` is owned by
the stuck C frame and can't be safely closed (RAM consequence in §4). The
single-threaded INV-10 dispatch serialises calls, so at most one query VM is live
at a time (§4).

The new `LuaEngine` surface (Qt6::Core only, behind `#ifdef ANTS_LUA_PLUGINS`):

```cpp
// Read-only API for query mode: installs ONLY the `project` table
// (read/list/root, §2.2) — none of registerApi()'s write callbacks.
// `root` is the canonicalised caller_cwd used for FS confinement (§2.3).
void registerQueryApi(const QString &root);

struct QueryResult {            // marshalled outcome of one snippet run
    bool        ok = false;
    QJsonValue  result;         // §2.4 marshal of the snippet's return value
    QString     code;           // refusal code — set iff !ok (INV-8)
    QString     error;          // operator-facing message — set iff !ok
    qint64      elapsedMs = 0;  // wall-clock around the lua_pcall
    // Invariant: code/error are non-empty iff ok==false; a success
    // carries neither, a refusal carries both.
};

// Run `code` text-only under the budget on a fresh VM configured for `root`,
// marshalling the single top-of-stack return value under `resultCapBytes`.
// Pure outcome — no signals emitted in query mode.
QueryResult runQuery(const QString &code, const QString &root,
                     qint64 timeoutMs, int resultCapBytes);
```

`runQuery` builds a fresh `lua_State` (5-lib allowlist + `sandboxEnvironment()`
+ `luaAlloc` + the hook, exactly as `initialize()` does), calls
`registerQueryApi(root)` **instead of** `registerApi()`, sets the per-call
deadline via `setPcallBudgetMs(timeoutMs)` + `startPcallBudget()` (the existing
budget path, `luaengine.cpp:196`), loads `code` text-only, runs it under
`lua_pcall`, and marshals the result. Failure paths are distinct: a snippet that
**raises** (syntax / load error / runtime error / explicit `error(...)`) fails
the `pcall` → `code = "query_error"` with the Lua message (**never** `null` —
`null` is only a clean *no-return*); a **marshal** failure (invalid UTF-8,
depth > 32, non-string key) likewise → `query_error`. It never returns a partial
value.

Marshalling rules for the return value:

| Lua return | JSON `result` |
|---|---|
| `nil` / no return | `null` |
| boolean | `true` / `false` |
| number | JSON number (integer subtype preserved where Lua 5.4 reports it) |
| string | JSON string (UTF-8; invalid UTF-8 → `query_error`) |
| table, array-like (1..n contiguous) | JSON array (recursive, ≤ 32 levels) |
| table, otherwise | JSON object (string keys; non-string keys → `query_error`; recursive, ≤ 32 levels) |
| function / userdata / thread | refuse — `query_error` ("unsupported return type") |

Tables marshal recursively with a **fixed depth bound of 32 levels** (a table
nested deeper → `query_error`). The depth bound is also what stops a
**circular** table (`t={}; t.self=t`) from looping the encoder — it is caught by
the depth limit, not by separate cycle detection. The marshalled JSON
is serialised to UTF-8 and size-checked: **if its UTF-8 byte count exceeds
`result_cap_bytes` (default 64 KiB, §2.5) the verb refuses with
`result_too_large`** carrying the byte count and a hint to aggregate further
(return a count, not the rows) — never a truncated/partial result, which would
read as a complete answer.

### 2.5 Config keys + gating

Gating mirrors the ANTS-2094 offload pattern: one Settings toggle + config-only
tuning, all under the ANTS-1901 master `claude.mcp_enabled` gate.

- **`claude.mcp_project_query_enabled`** (bool, **default true**) — feature
  gate, surfaced in Settings → General ("Let Ants run read-only project
  queries for Claude"). Default ON per the standing "token-savers default ON"
  rule: the verb is fully sandboxed (read-only, FS-confined, mem/time/output
  capped, no network/exec/write), so the safe default is the one that actually
  saves tokens. When false, the verb refuses with **`query_disabled`** *before*
  a VM is constructed. The feature gate is the **first** statement inside
  `cmdProjectQuery`, *before* the `caller_cwd` / `code` argument validation, so a
  feature-off call yields `query_disabled` regardless of other arg state (an
  empty `caller_cwd` with the feature off still returns `query_disabled`, not
  `caller_cwd_required`). **Gate precedence:** the master gate is checked earlier
  still — the **first** check in the `tools/call` dispatcher, *before any verb
  handler runs* (`claudeintegration.cpp:8688–8706`, the master-gate block, ANTS-1901) — so a caller with both
  gates off sees `mcp_disabled` (never `query_disabled`); `query_disabled` is
  reachable only when the master gate is on but this feature gate is off.
- **`claude.mcp_project_query_timeout_ms`** (int, default 1500, clamp
  `[100, 5000]`) — wall-clock budget, applied via the existing
  `setPcallBudgetMs()` path. Because the join blocks the GUI for up to this long
  (§2.4), the ceiling (5000) bounds the worst-case UI stall; the floor (100)
  keeps a usable budget for metadata-heavy trees. 1500 ms is the inherited
  plugin default — conservative; most queries finish in well under 100 ms.
  Config-file-only.
- **`claude.mcp_project_query_result_cap_bytes`** (int, default 65536, clamp
  `[1024, 1048576]`) — the §2.4 output cap. 64 KiB suits an aggregate answer
  (a count, a small list); a result that large is already a signal to aggregate
  harder in the snippet. The ceiling (1 MiB) is the point past which the reply
  should spill via offload (ANTS-2094) rather than inline; the floor (1 KiB)
  still admits a non-trivial answer. Config-file-only.

The 10 MiB VM memory cap and the 100k-instruction hook are **inherited
unchanged** from `LuaEngine` and are not re-exposed as keys (they bound the VM
itself, not this feature).

**Optional-Lua build.** The Lua plugin subsystem is optional, gated on the
`ANTS_LUA_PLUGINS` compile definition (`CMakeLists.txt:378`, `:499`, `:1676`;
built with `-DANTS_LUA_PLUGINS=OFF`). When Ants is built without it,
`cmdProjectQuery` is compiled out under the same `#ifdef ANTS_LUA_PLUGINS`
guard and the verb is **not registered** — it simply does not appear in the
catalogue (cleanest: no dead refusal path, mirrors how other optional surfaces
drop out). The `tool_info` catalogue therefore lists it only in
`ANTS_LUA_PLUGINS`-enabled builds (tested per §6).

## 3. Invariants

- **INV-1** — No write / no side-effect surface. A query VM exposes only
  `project.read`/`project.list`/`project.root` plus the read-only stdlib
  allowlist. None of `ants.send`/`notify`/`set_status`/`settings.set`/
  `clipboard.write`/`palette.register`/`on` is registered; `os`/`io`/`load`/
  `loadfile`/`require`/`package`/`debug` remain unloaded; there is no network
  surface. *Test:* source-scrape that `registerQueryApi` installs none of the
  write callbacks; runtime cases where a snippet referencing `ants`,
  `os.execute`, `io.open`, or `require` errors (indexing nil) rather than
  acting.
- **INV-2** — Filesystem confinement. `project.read`/`project.list` resolve
  only paths whose **canonical** form is the canonical `caller_cwd` or under
  `caller_cwd + "/"`; a `..`-traversal, an absolute path outside the root, or a
  symlink whose target escapes the root is rejected before any open. *Test:*
  snippets reading `"../../etc/passwd"`, an absolute out-of-root path, and an
  in-root symlink pointing outside each raise; an in-root read succeeds.
- **INV-3** — Read-only to disk. No `project.*` primitive opens a file for
  write, creates, renames, or deletes; `project.read` opens read-only. *Test:*
  the API table has no write entry (scrape) and a snippet has no callable that
  mutates disk (covered with INV-1).
- **INV-4** — Budget enforcement & bounded GUI stall. Every call runs under the
  inherited 100k-instruction + per-line hook, the wall-clock `timeout_ms`
  deadline (default 1500) with the sticky-kill latch, and the 10 MiB allocator
  cap, **on a worker thread** (§2.4). A looping snippet returns `query_timeout`;
  an allocation that trips the cap returns `query_oom` (the allocator returns
  null → Lua raises "not enough memory", surfaced as the failed-pcall path — not
  a silent nil). The bound is **bounded, not zero**: the dispatcher waits on the
  worker via a join that runs on the GUI thread, so the **GUI is blocked for up
  to `timeout_ms` + 250 ms grace** in the pathological case — but never longer,
  which is the whole point versus running inline (a single uninterruptible C
  call would freeze the GUI *forever* inline; on the worker it is detached at the
  join deadline and the GUI resumes, the worker held as a zombie until process
  exit, §4). *Test:* `runQuery` unit cases assert the exits — `while true do end`
  → `query_timeout` within ~`timeout_ms`; a growing-table alloc → `query_oom`
  (the refusal, not a partial/nil result). The **bounded-stall** property itself
  (worker detached, GUI resumes within `timeout_ms` + grace on a pure-C spin) is
  an integration/manual check — a `string.rep`-driven C spin on the worker while
  asserting the dispatch returns by the deadline — not a direct-call unit test
  (the unit path drives `runQuery` synchronously, off the dispatch thread).
- **INV-5** — No cross-call state bleed. Each `project_query` runs in a **fresh
  `lua_State`**, constructed for the call and torn down on return; a global,
  table, or file handle from one call is invisible to the next. *Test:* call A
  sets `_G.x`; call B observes `x == nil`.
- **INV-6** — Result fidelity & type floor. A scalar return marshals to the
  matching JSON scalar; an array-like table → JSON array, a string-keyed table
  → JSON object (recursively, within the depth bound); `nil`/no-return →
  `null`; a function/userdata/thread/non-string-key/over-depth/invalid-UTF-8
  return → `query_error`. *Test:* one case per row of the §2.4 table.
- **INV-7** — Output cap, no partial. The marshalled result is returned only
  when ≤ `result_cap_bytes`; over-cap refuses with `result_too_large` + the
  byte size and emits **no** `result` field (never a truncated value). `list`
  output is sorted **by byte/codepoint, locale-independent** (not via a
  locale-sensitive collator — guards against the `C.UTF-8`-vs-locale divergence
  the project already hit in CI, ANTS-2120) so identical project snapshots yield
  identical bytes. *Test:* a snippet returning a string > cap →
  `result_too_large` with no `result`; a `list` determinism case (two calls →
  byte-identical arrays).
- **INV-8** — Refusal codes from the taxonomy. Absent `code` → `missing_field`;
  load/syntax/runtime error, path-escape, unsupported return type →
  `query_error` (message carried in `error`); wall-clock/instruction budget →
  `query_timeout`; memory cap → `query_oom`; over output cap →
  `result_too_large`; feature gate off → `query_disabled`; master gate off →
  `mcp_disabled` (which the dispatcher returns *before* the handler runs, so it
  takes precedence over `query_disabled` — §2.5). Each new code is added to
  `docs/standards/mcp-error-codes.md` in the implementing commit (§7). *Test:*
  one assertion per code path.
- **INV-9** — Composition with offload. The success envelope is a normal read
  reply: when it exceeds the offload threshold it spills via the ANTS-2094
  `offloadBody` transform and `read_spill` returns it verbatim. `project_query`
  is added to `isOffloadEligible` so a large `result` masks like any other read.
  *Test:* source-scrape that `project_query` is in the offload-eligible set;
  a large-result spill round-trips.

## 4. RAM / build cost

- **Memory:** per call, one ephemeral VM hard-capped at 10 MiB (inherited
  `MAX_LUA_MEMORY`) plus the marshalled result buffer ≤ `result_cap_bytes`
  (default 64 KiB). On a **clean return** the VM is torn down — **no retained
  state, no cache, no steady-state growth**. Queries run on a **worker thread**
  (§2.4) and the single-threaded INV-10 dispatch serialises calls, so at most one
  *active* query VM is live at any instant (transient peak ≤ 10 MiB + 64 KiB).
  **One non-zero-growth case, by design:** a worker stuck in an uninterruptible C
  call past the join deadline is **detached and held in a zombie list until
  process exit** (its `lua_State` is owned by the stuck C frame and can't be
  safely closed — the ANTS-1750 contract, `pluginmanager.cpp:138–150`, `:492`).
  Each such zombie leaks ≤ 10 MiB + one thread until the app closes. The cost is
  bounded **per query** (one zombie each) but **additive across a session**: the
  single-threaded dispatch serialises *execution* (one VM active at a time), it
  does **not** serialise *teardown*, so N pathological queries in one session
  leak N zombies (≤ N × 10 MiB until exit). It is not steady-state and each
  occurrence is rare (needs an uninterruptible C spin that outlives the join),
  but the session total is not capped — this is the accepted price of keeping the
  GUI responsive (§2.4), matching the existing plugin behaviour.
- **Build:** no new translation unit and no new external dependency — a
  `registerQueryApi()` + `runQuery()` added to the existing `luaengine` TU
  (already compiled when `ANTS_LUA=ON`) and a `cmdProjectQuery` in
  `remotecontrol.cpp`. Compiled out entirely under `-DANTS_LUA=OFF` (verb
  unregistered, §2.5). Tests join an existing feature bundle (no
  `add_executable`).

## 5. Out of scope (v1)

- **A host-side `project.search(pattern)`** that drives ripgrep from inside the
  snippet (Lua aggregates ripgrep's hits) — the most powerful shape, but it adds
  a re-entrant host callback **and re-opens the uninterruptible-C-call
  preemption surface (§2.4) on a larger, pattern-driven footprint** (catastrophic
  user-supplied regex), so it needs its own threading/timeout analysis; deferred.
  v1's `list`+`read`+string-lib covers the documented aggregate cases; pair
  `workspace_search` → `project_query` when a content scan is needed first.
- **Glob/line-iterator convenience primitives** (`project.glob`,
  `project.lines`) — the snippet filters `list()` and splits `read()` itself in
  v1.
- **Caching query results** — each call is a fresh computation; no result cache
  (the inputs are files that change).
- **Write or mutation primitives of any kind** — permanently out of scope; this
  verb is read-only by definition (a write path would be a different verb with
  a different trust analysis).
- **A `.gitignore`-aware `list`** — v1 skips only `.git/`; respecting ignore
  files is a follow-up if listing noise proves costly.

## Implementation note (2026-06-25) — verb placement correction

The spec (§2.1, §4) located the handler as `cmdProjectQuery` in
`src/remotecontrol.cpp`. Implementation found that **infeasible**:
`remotecontrol.cpp` compiles into `ants_core_lib`, the **lowest** library
layer; `LuaEngine` lives in `ants_lua_lib`, which depends on
`ants_core_lib` (`CMakeLists.txt:496`), so core cannot link `LuaEngine`
without a dependency cycle. The behaviour is unchanged; only the file
placement moved to respect the layering:

- The verb body is a static **`LuaEngine::projectQueryVerb(req, enabled,
  timeoutMs, capBytes)`** in `src/luaengine.cpp` (lua_lib — where both
  `LuaEngine` and `PathValidation`, itself in core_lib, are visible). It
  performs the §2.5 gate-first → caller_cwd → code validation → envelope.
- The worker-thread orchestration (§2.4) is a static
  **`LuaEngine::runQueryThreaded`**; the in-VM run + marshal is the
  instance method **`runQuery`**; `registerQueryApi` installs `project.*`.
- The thin **provider lambda** is registered in `src/mainwindow.cpp`
  (chrome_lib, which links lua_lib) under `#ifdef ANTS_LUA_PLUGINS`; it
  reads the three `claude.mcp_project_query_*` keys from `Config` and
  delegates to `projectQueryVerb`.
- The shared VM construction (5-lib allowlist + allocator + hook) was
  extracted from `initialize()` into a private `buildVm(queryMode, root)`
  so the plugin and query paths cannot drift on a future sandbox fix; the
  sandbox allowlist gained `"project"` (a no-op in plugin mode).
- A non-finite number (NaN/Inf) marshals to `query_error` rather than the
  JSON `null` it would otherwise serialise to — preserving INV-6 fidelity
  (a small addition to the §2.4 number row).
- One refusal code beyond the spec's enumerated set is reused for the
  non-directory `caller_cwd` edge the dispatcher's non-empty Required gate
  lets through: **`cwd_bad`** (the same code `project_layout` uses), not a
  new code.

Also noted during implementation (logged for follow-up, not blocking):
ANTS-2131's `rcDelegateWorker` already runs blocking core-lib verbs on a
joined worker, but its join is **unbounded** (`worker->wait()`), so it
cannot host the pure-C-spin **detach** this verb needs — hence the
dedicated bounded-join orchestrator here. If a future need arises for a
*bounded* `rcDelegateWorker`, the two could converge.

## Implementation note (2026-06-26) — ANTS-2193 (bounded GUI stall re-confirmed)

Indie-review #8 re-flagged `runQueryThreaded`'s `worker->wait(timeout_ms +
250 ms)` on the dispatch thread as a GUI-freeze contradicting the ANTS-1750
"GUI never blocks on a worker" intent. This is **the accepted, already-
documented design** (INV-4, §2.4, cold-eyes Loop 1 C), not a regression — but
two clarifications close the finding:

- **Common case is not a stall.** `QThread::wait(timeout)` returns the instant
  the worker finishes, *not* after the full budget. A well-behaved snippet
  (the overwhelming common case) blocks the GUI only for its actual runtime —
  sub-100 ms. The worst-case `timeout_ms + 250 ms` (~5.25 s at the 5 s ceiling)
  is reached **only** by a snippet that runs to its wall-clock budget or wedges
  in an uninterruptible C call; the bounded detach is precisely what caps that
  case (vs. an inline run that would freeze the GUI forever, Loop 1 C).
- **Why not fully async.** Making the GUI never block *at all* would require an
  asynchronous MCP dispatcher: the `tools/call` handler returns its response
  string **synchronously** to the socket-read lambda
  (`claudeintegration.cpp` `handler(argsObj)`), and the ANTS-2131
  `rcDelegateWorker` wrapper still **joins on the dispatch thread** (it buys
  re-entrancy safety against the ANTS-2102 nested-event-loop UAF, not GUI
  responsiveness — see the 2026-06-25 note above). So wrapping `project_query`
  in a worker would not shorten the stall; it would only add a thread. A truly
  non-blocking dispatcher is a cross-cutting change across **every** synchronous
  verb (`audit_run`, `verify_changes`, … all block the dispatch thread for
  their duration today) and is out of scope for this verb. The `timeout_ms`
  ceiling (clamp [100, 5000]) is the lever that bounds the worst case, and
  `project_query` is in fact *better*-bounded than the unbounded build/audit
  verbs. No code change; INV-4 stands.
