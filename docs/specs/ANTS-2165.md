# ANTS-2165 — Out-of-cadence hotfix path (`cut-rc.sh hotfix`)

**Status:** accepted (2026-06-24) — cold-eyes loops 1–5 folded, converged.
**Kind:** implement.
**Source:** ROADMAP.md ANTS-2165 (user-request-2026-06-24 — an urgent bug in the

## 1. Problem

The cadence handles a bug found *during* the RC freeze (cherry-pick onto the RC
tag → `respin`, ANTS-1318 §2.3) and a bug found on ship-day (defer one week,
§4.2). It has **no path for an urgent bug in the already-published release**
(security / data-loss / crash / shipped-broken) that must ship before the next
Wednesday. Today the only options are "wait for Wednesday" or hand-roll an
ad-hoc tag — exactly the unguarded ad-hoc releases the cadence was built to end
(ANTS-1318 §1).

The complication is **version numbering under a frozen RC**: the public is
`vN` (e.g. `0.7.97`) and an RC for the next patch `v(N+1)-rc1` (e.g.
`0.7.98-rc1`) is mid-freeze. A hotfix wants the next public patch — which is
`N+1`, the number the in-flight RC already holds. Cutting the hotfix as `N+2`
would make the hotfix sort *above* the RC (version regression when the RC
later promotes); reusing `N+1` collides with the RC tag.

**Layman:** if a bad bug reaches everyone, we need an emergency lane to ship a
small fix-only release straight away — without dragging out the half-finished
new features, and without the version numbers going backwards.

## 2. Surface

User-chosen model (2026-06-24): **dedicated hotfix, RC rolls up.** The hotfix
is the next patch off the *public* line (`vN` + the fix only); the in-flight RC
renumbers up one so numbering stays monotonic:

```
public  0.7.97  ──hotfix──▶  0.7.98   (= v0.7.97 tree + cherry-picked fix only)
RC      0.7.98-rc1  ──roll up──▶  0.7.99-rc1   (same content, new number)
```

All changes are to `packaging/cut-rc.sh` (one new `hotfix` subcommand) plus its
feature test. Per `ANTS-1318 INV-9`, `cut-rc.sh` never edits version files; the
two version bumps in this procedure (the hotfix branch's version, and the RC
roll-up on `main`) are assistant-orchestrated `/bump` steps — the same division
of labour as `ANTS-2164 §2.5` (the script guards, the assistant supplies the
version edits + release-note bodies).

### 2.1 The procedure

Let `N` = the latest public version (`0.7.97`), `H = N` with patch+1 (`0.7.98`,
the hotfix), `R` = the in-flight RC's base (`0.7.98` today). When an RC is in
flight `R == H`, so the RC must move out of the way first.

1. **Fix lands on `main`** (normal dev; trunk-canonical, `ANTS-1318 INV-7`).
2. **Roll the in-flight RC up** (assistant-orchestrated, before the hotfix;
   skip if no RC in flight): assistant `/bump`s `main` `R` → `R+1` (`0.7.99`),
   renaming the `## [R]` CHANGELOG section and the metainfo
   `<release version="R">` / debian `ants-terminal (R-<rev>)` blocks to `R+1`;
   delete the superseded `v(R)-rc*` tag(s) + GitHub pre-release(s); then
   `cut-rc.sh new-rc` re-cuts `v(R+1)-rc1` from `main` (ANTS-2164's guards
   apply). Exactly one RC stays in flight — INV-8. (If no RC is in flight —
   e.g. ANTS-2164 §5's reconciliation already deleted the empty `v(R)-rc1` —
   this whole step is a no-op and the hotfix simply takes the next patch; the
   two reconciliations compose.) (Order-safe: this `new-rc`
   targets base `R+1`, which is never the just-/about-to-be-published `vH`
   (`= vR`), so `ANTS-2164 INV-9`'s already-public-base refusal holds whether
   this step runs before or after step 3.)
3. **Cut the hotfix — two phases around the `/bump`** (a shell script cannot
   invoke `/bump`, so the command stops for it; same script-guards/assistant-
   content split as `ANTS-2164 §2.5`):

   **Phase 1 — `cut-rc.sh hotfix <fix-sha>...`:**
   - Guards (hard, exit≠0): `require_clean_main`; `require_no_version_drift`
     (against `main` — confirms `main`'s own packaging is internally consistent
     before we start, catching a pre-existing drift; it does NOT validate `H`);
     each `<fix-sha>` is an ancestor of `main` (`git merge-base --is-ancestor`;
     else `fix_not_on_main`); the latest public tag `vN` exists. If an RC is in
     flight, its base must equal `H` (the next patch after public — the normal
     cadence state); else refuse (`rc_base_mismatch`), since the roll-up's
     `R`→`R+1` arithmetic assumes `R == H`. **`N` is read from the public tag
     list** (`git tag -l 'v[0-9]*.[0-9]*.[0-9]*' | grep -vE -- '-rc' | sort -V
     | tail -1`, as `cmd_status`, `cut-rc.sh:159`) — NOT from `CMakeLists.txt`,
     which always tracks the RC / next-patch line (`R` or `R+1`), never the last
     public release. `H` = `N` with patch+1.
   - Branch `_hotfix` off `vN` (`git checkout -b _hotfix vN`); cherry-pick the
     `<fix-sha>`(s) — abort + prune `_hotfix` on conflict (mirrors `respin`,
     `cut-rc.sh:234-240`) — INV-6. If a stale `_hotfix` from an interrupted run
     already exists, refuse (`hotfix_branch_exists`) pointing at
     `git branch -D _hotfix` or `cut-rc.sh hotfix --continue` — never silently
     reset. (This idempotency guard is new — `respin` has no pre-existing-branch
     check, so it is written fresh, not copied.)
   - Stop, printing the next step: "`/bump` `_hotfix` to `H`, write its `[H]`
     notes, then `cut-rc.sh hotfix --continue`."

   **Assistant step:** `/bump` `_hotfix` to `H` and write the `## [H]`
   CHANGELOG / metainfo / debian bodies = *the fix only* (not `main`'s
   unreleased work). When several `<fix-sha>` are given, they fold into one
   combined `## [H]` entry (one logical emergency fix, possibly several commits).

   **Phase 2 — `cut-rc.sh hotfix --continue [--push] [--skip-build]`:**
   - `H` is recomputed from `_hotfix`'s `CMakeLists.txt` (the `/bump` just set
     it to `H`); `vH` = `v` + that version.
   - Guards: on the `_hotfix` branch with **no in-progress cherry-pick**
     (`CHERRY_PICK_HEAD` absent — phase 1 completed cleanly, so a half-applied
     branch never tags `vH`); `require_no_version_drift` against the
     **`_hotfix` working tree** (where `CMakeLists.txt` == `H`, so it passes —
     NOT `main`, now `R+1`); `vH` is not already a public tag; and `vN` (the
     branch point) is still the latest public tag (guards a concurrent promote
     landing between phases).
   - `build_and_test` on `_hotfix`; tag `vH` (annotated) at `_hotfix` HEAD,
     **public** (`prerelease=false`, no `--prerelease`); publish; `--push`-gated
     like every other path. The annotated `vH` tag pins its commit and survives
     the branch prune.
   - Record the `## [H]` entry on `main` too (below the rolled `## [R+1]`
     section — `R+1` == `H+1` since `R` == `H`), so `main`'s CHANGELOG shows
     `[H+1] > [H] > [N]` with no version gap — INV-4.
   - Return to `main`, prune `_hotfix` (local-only, like `respin`).

No Wednesday guard on either phase — `hotfix` is out-of-cadence by definition
(INV-7).

### 2.2 New helper / subcommand in `cut-rc.sh`

```bash
# Out-of-cadence emergency release: vN (latest public) + cherry-picked fix(es),
# tagged as the next patch vH, prerelease=false. cut-rc.sh never bumps the
# version (ANTS-1318 INV-9) — the assistant /bump's the _hotfix branch to H
# between the two phases:
#   cut-rc.sh hotfix <fix-sha>...          # phase 1: guard + branch off vN +
#                                          #   cherry-pick, then STOP for /bump
#   cut-rc.sh hotfix --continue [--push]   # phase 2: build + tag vH public +
#     [--skip-build]                       #   publish + record [H] on main + prune
cmd_hotfix

# True if <sha> is already an ancestor of main (the fix landed on trunk first).
# Called once per <fix-sha> (phase 1 loops over them). Refusal code when any is
# false: fix_not_on_main (the predicate name is positive; the refusal code is
# negative — distinct on purpose).
fix_is_on_main <sha>      # git merge-base --is-ancestor <sha> main
```

The new `hotfix` subcommand and its `--continue` flag need explicit arm entries
in the arg-parser `case` (`cut-rc.sh:52-61`) and the usage string (`:63`):
without them, `hotfix`'s `<fix-sha>` positionals fall through into the existing
`RESPIN_SHAS` array.

## 3. Invariants

- **INV-1** — Monotonic numbering: the hotfix takes the next patch off the
  *public* line (`H` = `N`+1 in the patch field); if an RC for `H` is in flight
  it is rolled up to `H`+1 **before** the hotfix tag is cut, so no two live tags
  share a version and a later RC promote never regresses below the hotfix.
  *Test:* fixture — with `vN` public + `v(N+1)-rc1` in flight, the procedure
  yields public `v(N+1)` and in-flight `v(N+2)-rc1`; `git tag` sort is strictly
  increasing.
- **INV-2** — Minimal tree: the `vH` tag's tree is the `vN` commit + ONLY the
  cherry-picked `<fix-sha>`(s) — never `main` HEAD. The in-flight RC's preview
  features are absent from the hotfix. *Test:* fixture — a feature commit on
  `main` is NOT in `vH`'s ancestry (the load-bearing check); and `git diff vN
  vH` touches only the fix's files.
- **INV-3** — Trunk-canonical: `cut-rc.sh hotfix` refuses (exit≠0,
  `fix_not_on_main`) any `<fix-sha>` not already an ancestor of `main` (the fix
  lands on trunk first — `ANTS-1318 INV-7`). *Test:* source-scrape
  (`git merge-base --is-ancestor` + the refusal) + a fixture with an
  off-main sha.
- **INV-4** — No CHANGELOG gap: the hotfix's `## [H]` entry (CHANGELOG +
  metainfo `<release>` + debian block, the fix only) is also recorded on `main`
  below the rolled `## [H+1]` section (the roll-up's `R+1`, with `R == H` per
  §2.1), so `main`'s CHANGELOG reads `[H+1] > [H] > [N]` with no gap.
  When no RC was in flight (step 2 skipped, no roll-up), it reads `[H] > [N]`.
  *Test:* both cases — RC-in-flight asserts `[H+1] > [H] > [N]` descending;
  no-RC asserts `[H] > [N]`.
- **INV-5** — Public, gated: the `vH` tag's GitHub release has
  `prerelease=false`; `check-version-drift.sh` hard-gates the publish — run
  against the `_hotfix` working tree (where `CMakeLists.txt` == `H`), never
  `main` (now `R+1`), so it does not false-trip; every remote action is
  `--push`-gated (rehearsal prints, mutates nothing). *Test:* source-scrape
  **scoped to the `cmd_hotfix` body** (a `from_marker`-style function slice,
  like the existing per-subcommand scrapes — not a repo-global match a
  non-conforming `cmd_hotfix` could pass): asserts it omits `--prerelease`,
  calls `require_no_version_drift`, and gates publish on `DO_PUSH`.
- **INV-6** — Conflict-safe: a cherry-pick conflict aborts cleanly with
  recovery instructions and prunes `_hotfix`, leaving no partial branch/tag
  (mirrors `respin`, `ANTS-1318 §4.5`). *Test:* fixture — a conflicting
  cherry-pick exits non-zero and leaves `git status` clean on `main`.
- **INV-7** — Out-of-cadence exception: `cut-rc.sh hotfix` does NOT run
  `wednesday_guard` — it is the explicit exception to `ANTS-1318 INV-1`. The
  path is reserved for security / data-loss / crash / shipped-broken severity
  (a documented bar, maintainer judgment — not machine-enforced). *Test:*
  source-scrape asserts `cmd_hotfix` contains no `wednesday_guard` call.
- **INV-8** — One RC in flight preserved (applies only when an RC was in
  flight; if none was, there is no roll-up and the hotfix leaves no RC):
  rolling the in-flight RC up (`/bump` `R`→`R+1`, rename the `[R]` sections,
  delete `v(R)-rc*`, re-cut `v(R+1)-rc1`) leaves exactly one RC in flight at
  base `R+1`. Both release-track guards still hold: `ANTS-1318 §4.4` (refuses a
  second concurrent in-flight RC) and `ANTS-2164 INV-9` (`new-rc` refuses a
  base already public — `R+1` is not). *Test:* fixture asserts no public
  `v(R+1)` exists and `v(R+1)-rc1` is the sole in-flight RC after the procedure.

## 4. RAM / build cost

None. Bash/awk in an existing script (no `sed -i`); no state held, no build
target, no external library. The hotfix's one extra `build_and_test` on the
`_hotfix` branch reuses the CMake cache (~5–10 min incremental, as `respin`).

## 5. Out of scope

- A 4th version component (`0.7.97.1`) — rejected: the chosen model keeps
  3-part SemVer by consuming the next patch + rolling the RC up. Revisit only if
  two hotfixes are needed against the same public before a Wednesday.
- Auto-detecting hotfix-worthy severity — the bar is documented (INV-7),
  maintainer judgment, never machine-gated.
- Distro-package hotfix channels — distros consume stable tags; a hotfix `vH`
  is a normal public tag they pick up by convention.
