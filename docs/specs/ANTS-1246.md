# ANTS-1246 — Tasks chip: progress semantics (`done / total`, visible whole run)

- **Status:** 📋 Draft (pre-implementation). Spec produced per
  the project's draft → /cold-eyes → user sign-off → implement
  workflow. `--quick` cold-eyes pass given the 2-line surface.
- **Source:** user feedback 2026-05-12 on two live screenshots —
  (1) chip vanished mid-run while in-progress tasks remained
  (visibility hole left by ANTS-1221's pending-only predicate);
  (2) after re-instating visibility, chip showed 13/15 for a batch
  the user knew was 4 tasks — Mode B (TaskCreate) accumulator never
  reset between fully-completed batches, so 11 stale completed
  tasks from a prior batch piled up with the current 4.
- **Lanes:** `claudestatuswidgets` (chip text + hide gate) +
  `claudetasklist` (parser: batch-reset on `TaskCreate` after a
  fully-completed prior batch). No public-API change on the
  tracker — count methods still return the same `int` shape.
- **Kind:** fix (two coordinated UX corrections; both prompted by
  the same user-visible symptom).

## 1. Problem

The Tasks chip in the bottom status bar today reads
`☰ X/Y` where:

```cpp
m_tasksBtn->setText(QStringLiteral("☰ %1/%2")
    .arg(total - unfinished).arg(total));
```

at `claudestatuswidgets.cpp:743`. Post-ANTS-1221,
`unfinishedCount() = pendingCount()`, so the numerator is
`total - pending = done + in_progress`. The hide gate at
`:724` is:

```cpp
if (total <= 0 || unfinished <= 0) { m_tasksBtn->hide(); return; }
```

So the chip is hidden whenever **no pending tasks** remain, even
if **in_progress** tasks are still running. User reproduced this
on 2026-05-12 with a screenshot: ~11 tasks all completed or
in_progress, 0 pending → chip vanished while Claude was clearly
still working through the list.

The original intent of ANTS-1221's "pending only" was to make
the chip mean "outstanding *for the user to action*" — because
`in_progress` is Claude's responsibility, not the user's. That
distinction has become moot in practice: a separate `Claude:
thinking` status widget already surfaces "Claude is doing
something". The Tasks chip is therefore free to take on a
different role: **progress indicator** for the active task list,
visible end-to-end.

A second symptom surfaced after the visibility fix landed: the
chip read **13/15** while the user knew the current logical
batch was 4 tasks (the spec / cold-eyes loops for the bug fix
they were reading). Cause: `ClaudeTaskListTracker::parseTranscript`
runs in two modes:

- **Mode A (`TodoWrite`)** snapshots-and-replaces the entire list
  on every event (line 234: `out.clear()`). Each TodoWrite
  represents the whole current state, so this is correct by
  design.
- **Mode B (`TaskCreate` + paired `TaskUpdate`)** is incremental
  — every TaskCreate appends to `out`; there's no event that
  signals "new logical batch starts here." A long Claude
  Code session that completes a batch (say 11 TaskCreates),
  then starts a new batch (4 fresh TaskCreates) ends up with
  15 entries in the tracker, of which 11 are stale completed
  noise.

The mode the user has been hitting today is Mode B (Claude Code
2.1.x with the modern `TaskCreate` API). Mode A users were never
exposed to the pile-up.

## 2. Mechanism

Two textual changes at `claudestatuswidgets.cpp:683-753` (the
`refreshTasksButton` slot):

### 2.a Numerator: `total - unfinished` → `done`

```cpp
// BEFORE (line 743)
m_tasksBtn->setText(QStringLiteral("☰ %1/%2").arg(total - unfinished).arg(total));

// AFTER
m_tasksBtn->setText(QStringLiteral("☰ %1/%2").arg(done).arg(total));
```

`done` is already in scope at `:696` (`const int done =
m_tasks->completedCount()`).

### 2.b Hide condition: `unfinished <= 0` → `done >= total`

```cpp
// BEFORE (line 724)
if (total <= 0 || unfinished <= 0) {
    m_tasksBtn->hide();
    return;
}

// AFTER
if (total <= 0 || done >= total) {
    m_tasksBtn->hide();
    return;
}
```

Effect:

| State | Before chip | After chip |
|---|---|---|
| 0 tasks (no list) | hidden | hidden (unchanged — `total <= 0` branch) |
| 7 created, 0 done, 0 running, 7 pending | `0/7` visible | `0/7` visible (unchanged) |
| 7 created, 0 done, 1 running, 6 pending | `1/7` visible | `0/7` visible (in_progress no longer counted) |
| 7 created, 4 done, 1 running, 2 pending | `5/7` visible | `4/7` visible |
| 7 created, 6 done, 1 running, 0 pending | **hidden** ← bug | **`6/7` visible** (fix) |
| 7 created, 7 done | hidden | hidden (post-completion) |

### 2.c Comment refresh

The comment block at `:735-742` documents the old semantics
("counts UP (completed-or-running of total)"). It needs to be
rewritten to reflect `done / total` plus an explanation of why
the chip stays visible until 100 %.

### 2.d Tooltip stays as-is

Tooltip text at `:744-751` already reads:

> Claude Code task list — N task[s] (X done, Y running, Z outstanding). Click to view.

This is informative under both the old and new semantics — no
change needed.

### 2.e Parser batch-reset (Mode B only)

In `ClaudeTaskListTracker::parseTranscript` at the
`TaskCreate` branch (`src/claudetasklist.cpp:245`), insert a
batch-reset check before appending the new task:

```cpp
if (name == QLatin1String("TaskCreate")) {
    if (sawTodoWrite) continue;          // Mode A wins
    if (!out.isEmpty()) {                // ← batch-reset
        bool allCompleted = true;
        for (const auto &existing : out) {
            if (existing.status != QLatin1String("completed")) {
                allCompleted = false;
                break;
            }
        }
        if (allCompleted) {
            out.clear();
            idxByToolUseId.clear();
        }
    }
    // …append the new task as before…
}
```

Semantics: a `TaskCreate` event that arrives when **every** task
already in `out` has status `completed` is treated as the start
of a new logical batch. The prior batch is dropped (both the
task list and the tool-use-id → index map). If even one prior
task is `pending` or `in_progress`, the new task appends
normally — partial batches are preserved.

This brings Mode B (TaskCreate) into parity with Mode A
(TodoWrite, which already snapshot-replaces).

**Why not always clear on TaskCreate?** Because legitimate
multi-task batches (Claude calls TaskCreate 7 times in a row
to set up a 7-step plan) are still cumulative. The reset only
fires when the accumulator is *exhausted* (all done), which
is the natural "new batch" signal.

**Why not clear inside `refreshTasksButton` when hidden?** The
parser is the source of truth; clearing at the view layer would
desync the tracker and the dialog (which reads the same `m_tasks`
field). Doing it in the parser keeps both surfaces consistent.

## 6. Cross-references

- **ANTS-1216** (shipped 2026-05-08) — original "hide chip at
  100 %" fix. This spec preserves that contract via the
  `done >= total` branch.
- **ANTS-1221** (shipped 2026-05-10) — "chip stays visible when
  only an `in_progress` task remains" — original user ask. That
  resolution counted pending-only; this spec closes the residual
  visibility hole by switching to a progress-counter semantics.
  ANTS-1221's ROADMAP entry should be updated to point at this
  follow-on as the better fix.
- **`docs/standards/status-bar.md`** — project-local status-bar
  widget convention. The Tasks chip continues to follow the
  "visible only when carrying information; hide on empty" rule;
  the *definition* of "carrying information" widens from
  "outstanding to user" to "in-flight progress".

## 7. Memory budget

Zero new allocations. The change is two arithmetic substitutions
on already-computed local ints (`done`, `total`,
`unfinished`). No new members, no new caches, no new signals.

## 8. Re-open conditions

- **Chip visibly flickers** at the transition `done == total -1
  → done == total` (chip going from "6/7" to hidden). If the user
  reports this as jarring, add a 500 ms grace window before the
  hide fires. Out of scope for v1.
- **A future task-management surface** (multi-list, per-tab
  list, hierarchical tasks) reshapes what "done / total" means.
  Re-derive the invariants at that time.
- **Telemetry from ANTS-1245** (token-usage tracker, also
  proposed 2026-05-12) shows users find the all-the-way-to-100 %
  visibility distracting. Re-evaluate the hide condition.

## 9. Out of scope

- Adding an animated progress fill to the chip background. Pure
  text-only change.
- Hierarchical / nested task display in the chip. Today's chip is
  a single count.
- Changing the Tasks dialog's content. Dialog already shows
  per-status breakdown; that's unchanged.
- Changing the `pendingCount` / `inProgressCount` /
  `completedCount` API on `ClaudeTaskListTracker`. Those are
  still useful for tooltip and dialog rendering.
