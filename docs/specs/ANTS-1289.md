# ANTS-1289 — `verify_changes` MCP tool

**Status:** spec draft, pre cold-eyes (2026-05-14). Loop log at end (§ 11).
**Source:** ROADMAP.md ANTS-1289 (line in `🔌 MCP — skill displacement` block).
**Blocked by:** none — engine is shell-out to the project's own build/test
plumbing; the MCP scaffolding has been proven by ANTS-1112 / ANTS-1113.
**Pairs with:** ANTS-1283 (session memory KV — optional cache backing for
the result), ANTS-1284 (token-usage telemetry — counts this tool's savings),
ANTS-1290 (`plan_template` — same skill-displacement pattern). None are

## 1. Problem

The `superpowers:verification-before-completion` skill is invoked on every
code-changing task — its rule is "no completion claims without fresh
verification evidence." Each invocation pulls **140 lines / ~4.1 KiB** of
skill markdown into Claude's context AND drives Claude through a
three-step mechanical loop (build → tests → lint), each step costing
additional Bash-output round-trips through parent context.

Per-step breakdown of a typical verify cycle on Ants Terminal (numbers
indicative — output magnitudes vary widely by code state and build cleanliness):

| Step | Command | Output magnitude | Through parent context |
|---|---|---:|---:|
| Skill load | (skill markdown) | 140 lines | ~4.1 KiB |
| Build | `cmake --build build --quiet` | ~5–500 lines | ~1–25 KiB |
| Tests | `ctest --test-dir build --output-on-failure` | ~20–500 lines | ~1–25 KiB |
| Clazy (opt) | per-file invocation | ~1–10 KiB | ~1–10 KiB |
| **Subtotal** | | | **~7–64 KiB per check** |

(`| tail -20` documented in `CLAUDE.md` is a user-side ergonomic — the
MCP tool replaces tail-piping with engine-side log capping per INV-3,
so the table strips it.)

A typical "is this ready?" check is **~1.5–2 K tokens** today — the
4.1 KiB skill markdown (~1 K tokens at 4 chars/token) plus per-Bash-call
frame overhead × 2–3 calls (~0.5–1 K tokens).

Per-session math (assume ~12 verify checks in a typical code-edit session):

| Component | Per check | Per session (×12) |
|---|---:|---:|
| Skill markdown (conditional on § 7(a)) | ~1 K tokens | ~12 K tokens |
| Bash-frame overhead (unconditional) | ~0.5–1 K tokens | ~6–12 K tokens |
| **Floor (unconditional only)** | **~0.5–1 K** | **~6–12 K** |
| **Ceiling (with skill update)** | **~1.5–2 K** | **~18–24 K** |

Headline: **~6–12 K tokens saved per session unconditionally,
~18–24 K with the optional skill update** (§ 7(a)). Earlier rough
estimates of "~30–60 K" overstated by ~2× — see § 11 cold-eyes
loop 2 finding HIGH-4.

The mechanical loop has no reasoning content — it's "run X, parse exit
code, return pass/fail." The reasoning the skill protects against —
"do not lie about completion" — is enforced by *whether the assistant
calls the tool at all*, not by the in-conversation walkthrough.
Replacing the walkthrough with a single MCP call preserves the gate while
removing the per-invocation Bash round-trip cost.

## 2. Surface

### 2.1 Tool signature

```
mcp__ants__verify_changes
  (no required args)
  optional: gates: array<string>   // subset of ["build","tests","lint"]
  optional: max_log_lines: integer // server-clamped [10, 500]; default 50
  optional: timeout_sec: integer   // server-clamped [10, 1800]; default 1200 (see INV-2)
```

`gates` lets a caller run a subset — e.g. `["build"]` for a quick syntax
check, `["tests"]` to skip a known-clean build. Default is all configured
gates.

### 2.2 Response shape

```json
{
  "ok": true,
  "all_passed": false,
  "gates": {
    "build": {
      "ran": true,
      "passed": true,
      "exit_code": 0,
      "duration_sec": 47.3,
      "log_tail": "[build excerpt …]",
      "log_truncated": true,
      "log_total_lines": 1287
    },
    "tests": {
      "ran": true,
      "passed": false,
      "exit_code": 8,
      "passed_count": 432,
      "total_count": 434,
      "failing_tests": ["test_claude_task_list", "test_qpointer_destroyed_safe"],
      "duration_sec": 12.1,
      "log_tail": "[ctest excerpt …]",
      "log_truncated": false,
      "log_total_lines": 18
    },
    "lint": {
      "ran": false,
      "skipped_reason": "no lint command configured"
    }
  },
  "project_root": "/mnt/Games/Scripts/Linux/Ants_Terminal",
  "config_source": ".ants/verify.json"
}
```

`ok` reflects whether the tool itself executed cleanly (config loaded,
commands resolvable, no internal error). `all_passed` is the AND of every
ran gate's `passed`. The distinction matters: a test failure is `ok:true,
all_passed:false` (the tool did its job, the project failed); a missing
build directory is `ok:false` (the tool couldn't proceed).

### 2.3 Per-gate fields

| Field | Type | Meaning | Present when |
|---|---|---|---|
| `ran` | bool | did the gate execute (process started) | always |
| `passed` | bool | exit code 0 (or, for `tests`, all tests passed) | always |
| `skipped_reason` | string | why the gate didn't run cleanly | `ran:false` OR ran-but-killed (timeout / SIGKILL) |
| `exit_code` | int | the underlying process's exit | `ran:true` only |
| `duration_sec` | number | wall-clock, 1-decimal precision | `ran:true` only |
| `log_tail` | string | tail of stdout+stderr, see § 2.5 | `ran:true` only |
| `log_truncated` | bool | true iff `log_total_lines > max_log_lines` | `ran:true` only |
| `log_total_lines` | int | total combined-stream line count | `ran:true` only |
| `passed_count` / `total_count` | int | parsed from ctest's `Passed` summary | `tests` gate AND format `ctest` AND parser matched |
| `failing_tests` | array<string> | list of failing test names | `tests` gate AND format `ctest` |

Fields omitted under their "present when" rules are simply absent from
the JSON object (not `null`). The MCP schema declares them with
`additionalProperties: false` but does NOT mark them as `required`,
so omission validates cleanly. `skipped_reason` covers two cases —
gate-not-started and gate-killed-mid-run — because both carry a
caller-actionable explanation (config gap vs timeout vs external
signal).

### 2.4 Project config — `.ants/verify.json`

Optional, project-relative path. Schema:

```json
{
  "build":  {"command": "cmake --build build --quiet"},
  "tests":  {"command": "ctest --test-dir build --output-on-failure", "format": "ctest"},
  "lint":   {"command": "clazy-standalone -p build src/*.cpp", "format": "lint"}
}
```

Each gate is optional — omitted gates are skipped. `format` hints to the
parser:
- `"ctest"` → parse "Passed: N / N" line + Failed listing
- `"lint"` → exit 0 = pass, non-zero = fail (no count parsing)
- `"plain"` (default) → exit 0 = pass

`command` is shell-quoted whole-string; runs via `/bin/sh -c <command>`
with the project root as `cwd`. **No shell metacharacter sanitization** —
the file is a trusted artifact under the project root (same trust model
as `.audit_suppress`, `.semgrep.yml`).

### 2.5 Auto-detection fallback

If no `.ants/verify.json` exists, auto-detect by file probe. **Priority
order**: first-match wins, top-to-bottom.

| Probe | If found, register |
|---|---|
| `CMakeLists.txt` + `build/` directory exists | build: `cmake --build build --quiet`, tests: `ctest --test-dir build --output-on-failure`, format: `"ctest"` |
| `CMakePresets.json` exists (no `build/` yet) | build: `sh -c 'cmake --preset=default && cmake --build --preset=default'`, tests: `ctest --preset=default --output-on-failure`, format: `"ctest"` |
| `package.json` exists, has `scripts.build` | build: `npm run build` |
| `package.json` exists, has `scripts.test` | tests: `npm test`, format: `"plain"` |
| `Cargo.toml` exists | build: `cargo build --quiet`, tests: `cargo test`, format: `"plain"` |
| `pyproject.toml` with `[tool.pytest]` | tests: `pytest -q`, format: `"plain"` |

Rationale for the cmake ordering: an existing `build/` directory means
the user has already configured (likely via a preset, likely the
default). Re-driving them via `--preset=default` would force a config
re-run; `--build build` reuses the existing configure. This row also
matches `CLAUDE.md`'s documented build invocation byte-for-byte. The
preset row is only the fallback for a fresh checkout that hasn't been
configured yet — and the command **must run the configure step first**
because `cmake --build --preset=X` alone fails with `<path>/build is
not a directory` if the configure has never run.

`format` for `tests` stays `"plain"` for non-ctest test runners in v1 —
parsing pytest / Jest / cargo output to a count is a v2 extension.

**Auto-detection runs once per `verify_changes` call** — no caching in
v1. Cheap (~5 file stats); the perf cost lives in the build/test commands
themselves.

`config_source` in the response is either the project-relative path to
`.ants/verify.json` if used, the string `"auto-detected"` if the
fallback fired, or `"none"` if no gate could be configured (response then
has `ok:true, all_passed:true, gates:{}` with each gate `ran:false`).

### 2.6 Engine API

```cpp
namespace VerifyEngine {

enum class GateName { Build, Tests, Lint };

struct GateConfig {
    GateName name;
    QString  command;      // shell string
    QString  format;       // "ctest" | "lint" | "plain"
};

struct GateResult {
    GateName    name;
    bool        ran        = false;
    bool        passed     = false;
    int         exitCode   = 0;
    double      durationSec = 0.0;
    QString     skippedReason;
    QString     logTail;
    bool        logTruncated = false;
    int         logTotalLines = 0;
    int         passedCount = -1;   // -1 = unparsed (non-ctest format)
    int         totalCount  = -1;
    QStringList failingTests;
};

struct VerifyOptions {
    QList<GateName> only;          // empty = all configured
    int             maxLogLines = 50;
    int             timeoutSec  = 1200;   // per INV-2
};

// MCP-layer key string for a gate name. Lowercase: "build" / "tests" / "lint".
// The response object in § 2.2 is keyed by gateKey(result.name), not by integer.
QString gateKey(GateName g);

struct VerifyReport {
    QList<GateResult> gates;
    bool              allPassed = false;
    QString           configSource;   // ".ants/verify.json" | "auto-detected" | "none"
};

// Loads .ants/verify.json (or auto-detects), validates per § 5.
QList<GateConfig> loadGateConfig(const QString &projectPath,
                                 QString *configSource);

// Top-level entry. Drives gates sequentially; per-gate timeout is the
// VerifyOptions cap divided by configured-gate count (so the total
// upper-bound is the user's `timeout_sec`).
VerifyReport runVerify(const QString &projectPath,
                       const VerifyOptions &opts);

}  // namespace VerifyEngine
```

The engine is Qt6::Core only — matches the layering of `auditengine`
(ANTS-1119), `indiereviewengine` (ANTS-1112), `debtsweepengine`
(ANTS-1113). Concretely: `src/verifyengine.{h,cpp}` is added to the
main `ants_chrome_lib` source list in `CMakeLists.txt` alongside the
other engines, and reused by test bundles via the standard
`SRC_VERIFY_ENGINE_*` define pattern (no new static-library target —
the existing engines are sources, not separate libs).

### 2.7 MCP tool description

```
verify_changes: Run the project's build / test / lint gates and return
pass/fail with log tails. Replaces the verification-before-completion
skill's mechanical loop. Reads .ants/verify.json (or auto-detects from
CMakePresets/package.json/Cargo.toml/pyproject.toml). Pure shell-out.
No optional args required.
```

## 3. Invariants

- **INV-1** — Hand-rolled config takes precedence. If `.ants/verify.json`
  exists and parses, auto-detection is skipped entirely (even if the
  hand-rolled file omits a gate that auto-detection would have found).
  Reason: explicit config is the user's choice, including the choice to
  skip gates.

- **INV-2** — Per-gate timeout enforcement. Each gate runs under a
  timeout of `max(10, opts.timeoutSec / max(1, configured_gate_count))`.
  Process killed via `QProcess::kill()` on timeout; gate result reports
  `passed:false, exit_code:-1, skipped_reason:"timeout after Nsec"`.
  **Default `timeoutSec` is 1200 s** (20 min total ÷ 3 gates = 400 s
  per gate) — measured generous of Ants Terminal's worst-case clean-
  build cost on a 32 GiB workstation host under the in-tree
  `compile_pool=max(2, nproc/4)` JOB_POOLS cap (typical clean release
  build: 4–10 min single-pool; under sanitizer-on debug preset it can
  reach 12 min). Callers running on warm-cache incremental builds will
  see < 30 s per gate; the 400 s default only matters for first-build
  scenarios.

- **INV-3** — Log capping. `logTail` is the last `maxLogLines` lines of
  combined stdout+stderr, with a hard byte cap of 16 KiB. **The byte
  cap is the floor**: if `maxLogLines × avg_line_size > 16 KiB`, lines
  are trimmed from the head (oldest first) until the byte cap holds.
  Single lines longer than 16 KiB are mid-truncated with a `… [N
  bytes elided] …` marker. `logTotalLines` reports the unfiltered count
  so the caller knows how much was elided.

- **INV-4** — Path-traversal guard. `.ants/verify.json` must resolve
  (after `QFileInfo::canonicalFilePath()`) such that the canonical path
  starts with `rootCanonical + '/'` — strictly **below** the project
  root, matching `IndieReviewEngine::assembleBriefManifest`'s guard at
  `indiereviewengine.cpp:208–228`. (Note:
  `corroboratedFindingsFromDir` at lines 419–437 allows
  `canon == rootCanon`; this spec follows the stricter
  `assembleBriefManifest` form because `.ants/verify.json` is always
  one level below the root.) If `.ants/verify.json` is a symlink to
  anything outside the project root, the config is rejected and
  auto-detection runs.

- **INV-5** — ctest-format parsing. When `format == "ctest"`, the parser
  matches the regex `(\d+)% tests passed, (\d+) tests failed out of (\d+)`
  applied **per-line** to combined stdout+stderr (i.e. split on `\n`
  first; do NOT apply `^...$` against the whole multi-line buffer
  without `QRegularExpression::MultilineOption`, since Qt's default
  treats `$` as end-of-string). The expected summary line is e.g.
  `100% tests passed, 0 tests failed out of 434`. On match, sets
  `passedCount = total - failed`, `totalCount = total`. The
  failing-test list is extracted from ctest's `The following tests
  FAILED:` block (regex `^\s*\d+ - (\S+) ` applied per-line within
  that block). On no match, fields remain `-1` / `[]`; gate still
  reports `passed:true` iff exit code 0.

- **INV-6** — Sequential execution. Gates run one at a time, never
  concurrently. Reason: a build + tests in parallel would compete for
  the same `build/` artefacts and the same JOB_POOLS slots; serial is
  the only safe ordering and matches what the skill prescribes.
  Order: build → tests → lint. **Test gate auto-skips iff `prior_build
  .ran == true && prior_build.passed == false`** — i.e. only when the
  build actually ran and reported failure. A timed-out build counts as
  `ran:true, passed:false` and therefore DOES cause tests to skip
  (skipped_reason: `"prior gate failed"`), because we don't have build
  artefacts to test against. A `ran:false` build (no build gate
  configured) does NOT skip tests. Lint always runs regardless of
  prior gates. § 4's failure-mode prose is amended to match this rule.

- **INV-7** — Schema: response object sets `additionalProperties: false`
  on the top-level envelope and on each `gates.<name>` object. New
  fields require an explicit schema update + invariant.

- **INV-8** — RAM bound. Combined stdout+stderr is streamed; only the
  rolling last-N lines are retained. Peak engine RAM per gate ≤
  `maxLogLines × 1 KiB + 32 KiB process bookkeeping` ≈ **80 KiB worst
  case**. Long-running builds emitting hundreds of MiB of log output
  do not cause unbounded memory growth.

- **INV-9** — No PATH inheritance hazards. `QProcess` inherits the
  ants-terminal process's environment. The MCP server doesn't sanitize
  `$PATH` — same trust model as the rest of the MCP surface (caller
  is the user's local Claude session, which already has full shell
  access via Bash). Documented; not a v1 hardening item.

## 4. Failure modes

- **No project root resolved** (`m_main` missing focused project).
  `{ok:false, error:"no_project", message:"verify_changes: no focused project"}`.

- **`.ants/verify.json` malformed JSON.** `{ok:false,
  error:"bad_config", message:"verify.json: <parser error>"}`. Auto-
  detection does NOT run as a fallback — a malformed config is a
  user-actionable error, not a "try harder" trigger.

- **`.ants/verify.json` valid but every gate command is empty / refers
  to non-existent binary.** Each gate reports `ran:false,
  skipped_reason:"command not resolvable"`. Tool returns
  `ok:true, all_passed:true` and `gates` contains all three gate
  entries each with `ran:false` — no gates run, no failures, but the
  shape stays consistent so the caller can branch on per-gate state
  rather than on object emptiness.

- **Gate process killed externally.** Treated as exit-code-non-zero;
  `passed:false`, exit code is the signal-killed value (e.g. 137 for
  SIGKILL), log_tail captures whatever was written before the kill.

- **Gate times out.** Per INV-2 — `ran:true, passed:false,
  exit_code:-1, skipped_reason:"timeout after Nsec"`. The `skipped_reason`
  field doubles as a kill-reason when `ran:true` (per § 2.3 "Present
  when" column). Per INV-6, a timed-out *build* causes the *tests* gate
  to skip (no usable artefacts); a timed-out *tests* gate doesn't
  affect *lint* (lint always runs).

- **Cwd inaccessible.** `{ok:false, error:"cwd_unreachable"}` — should
  not happen in practice because the focused-project resolution already
  validated the path, but defensive.

## 6. Performance / RAM budget

- **Engine RAM per gate**: ≤ 80 KiB worst case (INV-8).
- **Engine RAM end-to-end**: at most one gate active at a time (INV-6);
  peak ≤ 80 KiB.
- **MCP response payload**: ≤ 3 gates × ~17 KiB log + ~200 B fields ≈
  **52 KiB worst case** (every gate hits the byte cap with the
  `--output-on-failure` ctest case being the realistic worst); ~2 KiB
  typical (all-pass case with short ctest summary). Empirical anchor:
  a `cmake --build build --quiet` on a hot tree emits ~5–15 lines
  (~0.5 KiB), and a passing `ctest --output-on-failure` emits ~18
  lines on Ants Terminal today (verified by inspection of recent
  ctest runs). Failure cases dominate response size; the byte cap
  per INV-3 holds them bounded.
- **Caller token cost** (see § 1 table for the consolidated per-check /
  per-session math):
  - (a) **conditional** ~4.1 KiB / ~1 K tokens skill-markdown
    displacement — only when the skill itself is updated to short-
    circuit on Ants projects (§ 7(a)).
  - (b) **unconditional** ~1 KiB-per-Bash-frame overhead × 2–3 frames
    collapsed into one MCP call frame ≈ ~0.5–1 K tokens per check.
  Floor is (b) only (~6–12 K tokens/session); ceiling is (a) + (b)
  (~18–24 K tokens/session).
- **No new caches, no new file watchers, no new background threads.**

## 7. Workflow integration

The `verification-before-completion` skill **discipline** stays in
place — its rule ("evidence before assertions, always") is non-
negotiable and is preserved regardless of which mechanism produces
the evidence. The MCP tool is the *mechanism*; the skill's guidance
is the *gate*.

Two follow-on changes — tracked as separate work items, **NOT gated
on this spec landing.** This spec is sign-off-able with only the
unconditional (b)-class savings in § 6:

(a) **Skill text update** (~4 KiB consistent saving per session
unlocked). The skill markdown at
`~/.claude/plugins/cache/claude-plugins-official/superpowers/5.1.0/skills/verification-before-completion/SKILL.md`
gets edited so the gate-function pseudocode at lines 26–38 mentions
`mcp__ants__verify_changes` as the preferred mechanism on Ants-
equipped projects. Done in a separate vendor-skill-update commit —
the file is outside this repo's tree (vendor-cached), so this is a
machine-local edit gated on the user's explicit go-ahead. Spec does
NOT require it.

(b) **Skill activation suppression** (~4 KiB saving × every verify
in every project). A future harness-side change could short-circuit
the skill's auto-load when an MCP `verify_changes` tool is
discoverable. Out of scope here — depends on Claude Code's plugin
architecture, not this project's code.

Without (a) and (b), this spec still delivers the unconditional
~2–3 KiB-per-check Bash-round-trip saving (§ 6) plus the structured
response format (no parsing of `tail -20` output to count failing
tests; the caller sees `failing_tests:[]` directly).

## 8. Migration

- New tool — no existing API to deprecate.
- No `.ants/` directory convention exists yet in this project; the
  spec introduces `.ants/verify.json` as the first inhabitant. If
  ANTS-1283 (session memory KV) later wants `~/.cache/ants-terminal/`,
  that stays separate — `.ants/` is for *project-committed* config,
  `~/.cache/` is for *machine-local* state.
- Auto-detection covers projects without a hand-rolled config, so the
  user doesn't have to author `.ants/verify.json` for the tool to work
  on Ants Terminal itself (CMakePresets.json + build/ exist → fallback
  catches them).

## 9. Out of scope

- **Pytest / Jest / cargo output parsing for `passed_count`** — v1
  reports those as `format:"plain"`, leaving the integer counts at -1.
  Follow-up if/when a real consumer needs the structured count.
- **Watching for file changes between calls** — every `verify_changes`
  invocation re-runs from scratch. The natural "did anything change?"
  caching pairs with ANTS-1283 (session memory KV) and is out of scope
  here.
- **Telemetry of how many tokens this saved** — handled by ANTS-1284
  (`token_usage` tool).
- **Concurrent multi-project verify** — the focused-project model is
  one project at a time; a multi-tab user must invoke per-tab. v2
  could accept an explicit `project_path` arg.
- **Verbose mode that returns full logs not just tail** — caller can
  re-run with `max_log_lines: 500` (server-clamped); a `full:true`
  toggle that bypasses the cap is rejected as a footgun (an MCP
  response with multi-MiB logs would tank Claude's context budget).
- **A `verify_changes` sub-tool for re-running just the failing tests**
  — `gates: ["tests"]` covers the "just run tests" case; selective
  test re-run is `ctest -R <pattern>` and lives outside this tool.
- **Server-side caching of "last verify result"** — pairs with
  ANTS-1283.
