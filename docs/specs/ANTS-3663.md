# ANTS-3663 — `doc_lint`: every deterministic doc check in one call

**Status:** spec draft, cold-eyes loops 1–5 folded; ANTS-3669 merged back
(2026-07-28).
**Kind:** enhancement.
**Covers:** **ANTS-3663** — the walk, the five-checker composition, the adapters,
the envelope and the ordering — and **ANTS-3669**, the fix path. One verb, one
registration entry, one translation unit, specified once; they remain two
ROADMAP items because they ship as two implementation phases (§ 2.3). (The
umbrella-header form is `specs.md` § 2's: one spec whose header lists the ids it
covers.)
**Source:** ROADMAP.md ANTS-3663 (user-request-2026-07-27) and ROADMAP.md
ANTS-3669 (cold-eyes-2026-07-28, split from ANTS-3663 and merged back).
**Blocked by:** ANTS-3664 (the finding shape and the family wire conventions),
and ANTS-3660 / ANTS-3661 / ANTS-3662 existing to be composed.
**Composes with:** ANTS-3601 (`doc_integrity`) and ANTS-3636 (`doc_citations`),
the two producers that already ship and are adapted rather than rewritten.
**Supersedes:** `docs/specs/ANTS-3669.md`, which is a redirect to § 2.3.

**Layman:** One button that runs all the document checks together, and — only if
you ask it to — repairs the one kind of problem that has a single correct fix.

---

## 1. Problem

Running this family's checks over one tree takes **five separate verb calls**.
Each re-walks the same directory, re-reads the same files, re-computes the same
fence masks, and returns a differently-shaped envelope the caller then
reconciles by hand. **That reconciliation is the actual cost**, and it is paid
on every loop of every review. (`/cold-eyes` § 1e names two of the five today —
`doc_integrity` and `doc_citations`; the other three shipped after it was
written, and § 7 covers what naming them there requires.)

Two consequences, and the second is the one that bites:

1. **Four walks and a caller-side loop, where one walk would do.**
   `doc_integrity` and the three new verbs each enumerate `*.md` under the same
   root by calling the same helper — `RemoteControl::docIntegrityEnumerate`,
   which `cmdDocSymbols`, `cmdSpecLint` and `cmdDocDedup` reuse rather than
   clone (ANTS-3661 § 2.4) — but they call it **once each**, so it is four
   walks over one directory, and each re-reads every document it enumerated.
   The duplication is in the calls, not in the code. `doc_citations` does not
   walk at all — it is *file*-scoped, so the caller loops it, which is the same
   cost wearing a different hat.
2. **Five vocabularies.** Without ANTS-3664 the five checkers would report a
   problem five different ways, and the caller — a skill, not a program — would
   flatten them into prose to compare. `ColdEyesEngine::BriefManifest`
   (`src/coldeyesengine.h`) shows the shape that produces: it renders
   `doc_integrity`'s findings to `"<file>:<line>: [<kind>] <message>"` strings
   and carries its own separate regex-derived `staleCitations` list — two
   producers, two representations, structure discarded on the way in. ANTS-3664
   gives the three new verbs one shape; this spec adapts the two that ship
   into it.

## 2. Surface

### 2.1 One walk, five checkers

`doc_lint` enumerates once. It reads each document once and passes the **text**
to the three new checkers — which is a design constraint on them, not a
description of them: ANTS-3660/3661/3662 each take document text plus a
project-relative path, never a path alone. **ANTS-3664 § 2.3 rule 1 owns that
convention**; it is named here because it is the reason the shared read is
possible, not because this spec fixes it.

**The two adapted checkers re-read, and pretending otherwise would be the
spec's most load-bearing lie.** § 2.2 freezes `doc_integrity` and
`doc_citations` as adapter-only, and neither engine accepts text:
`DocIntegrity::check` consumes a resolved relative-path list, and
`DocCitations::check` is handed one document path. Taking text would mean
changing a shipped, tested signature — the thing § 2.2 exists to forbid. So the
honest budget over a three-document tree with all five checks on is **nine
opens**: three shared by the new checkers, three by `doc_integrity`, three by
`doc_citations`. Against fifteen for five separate verb calls, the saving is
real; against three, the claim is false. **INV-1 asserts the three-open native
call and deliberately attaches no assertion to the nine** — its own note
records why six of the nine are unobservable without editing a frozen engine.

**ANTS-3664 § 2.3 rule 1 governs engine signatures, not this verb's total.**
That rule — the engine never opens the document, the caller hands it text — is
what makes the three-open shared read possible, and it binds the three *native*
engines. It does not say `doc_lint` opens each document once; the two frozen
adapters make that unachievable, which is why the budget here is nine. Where
that section reads as stating a one-open-per-document guarantee for this verb,
this paragraph is the one that holds.

```jsonc
// request
{ "caller_cwd": "…",          // required
  "path": "docs/",            // file or dir; absent → the docs_dir default,
                              //   matching doc_integrity, NOT doc_citations'
                              //   missing_field (that verb is file-scoped)
  "checks": ["doc_integrity"],// default: all five; unknown name → bad_args
  "fix": false,               // opt-in; § 2.3
  "dry_run": false,           // preview; § 2.3. bad_args unless fix:true
  "max_findings": 500 }       // default 500, clamped to [1, 5000]
```

The cap is applied **after** INV-7's total sort, never before: the retained page
is therefore a deterministic prefix, and raising the cap only ever appends. A
cap applied during collection would return a different 500 findings per run from
the same tree, which is the failure the total order exists to prevent.

**`max_findings` pages `findings[]` and nothing else.** `counts`, `check_stats`,
`fixed[]` and `files_written` all describe the whole run, so a caller may lower
the cap to keep a response small without changing either the totals it reads or
the files on disk. The alternative — a cap that also bounds the repairs — would
make `fix:true` write different bytes at `max_findings:5` than at `500` from the
same tree, turning a display preference into a silent change of what gets
repaired. INV-11 asserts the paging half and INV-15 the repair half.

**Each checker declares which documents it is eligible for, and the shared walk
applies that predicate before dispatch.** The walk is `docs_dir`-wide, but the
checkers are not all corpus-wide: `spec_lint` is defined over specs only
(ANTS-3662 § 5 — "a README has no invariants to check"), and without a filter it
would emit `missing_section`, `invariant_id_gap` and `loop_row_no_outcome`
against every standard, journal and README under `docs/`. That is not a rare
edge: it is what `/cold-eyes` — the caller this verb is built for — gets on its
first run over a default path.

| Checker | Eligible documents |
|---|---|
| `doc_integrity` | every enumerated `*.md` |
| `doc_citations` | every enumerated `*.md` |
| `doc_dedup` | every enumerated `*.md` |
| `doc_symbols` | every enumerated `*.md` |
| `spec_lint` | those under `specs_dir` (ANTS-2160's key, else `docs/specs/`) |

A document filtered out of a checker is **not** a `skipped[]` entry — nothing
failed. The checker still appears in `checks_run[]` provided it was eligible for
at least one document; a run whose path selects no eligible document for a
checker leaves that checker out of `checks_run[]`, which is exactly the "did not
run" signal that array exists to carry.

```jsonc
// response
{ "ok": true,
  "findings": [ /* the ANTS-3664 § 2.2 wire form; INV-7 order */ ],
  "counts":   { "doc_integrity": { "toc_gap": 2 } },  // whole run, before the cap
  "truncated": false,          // omitted when false. Set when max_findings
                               //   elided findings, OR a cap elided a
                               //   document (§ 2.4)
  "checked_docs": ["a.md"],
  "checks_run":   ["doc_integrity"],   // ran clean ≠ did not run
  "check_stats":  { "doc_citations": { "unparsed_total": 1,
                                       "examples_suppressed": 57 } },
  "skipped":      [ { "file": "b.md", "reason": "read_failed" } ],
  "check_errors": [ { "verb": "doc_symbols", "file": "c.md",
                      "reason": "…" } ],
  "pairs":        [ /* doc_dedup only; element shape ANTS-3660 § 2.5 */ ],
  "clusters":     [ /* doc_dedup only; element shape ANTS-3660 § 2.5 */ ],
  "fixed":        [ { "verb": "doc_integrity", "kind": "toc_gap",
                      "file": "a.md", "line": 12 } ],   // fix:true only
  "files_written": 1,                                    // fix:true only
  "fix_errors":   [ { "file": "d.md", "reason": "write_failed" } ],
  "dry_run":      true }       // echoed on a dry run; § 2.3
```

Two of these carry contracts stated elsewhere in this document rather than
inline: `check_stats` in § 2.2 (the whole-document tallies that are not
findings), and `skipped` / `check_errors` / `fix_errors` in § 2.4 (partial
failure). The three fix-only keys are § 2.3's.

**Presence rule.** `ok`, `findings`, `counts`, `checked_docs` and `checks_run`
are **always present**, empty rather than absent when there is nothing to say —
a caller distinguishing "clean" from "malformed" needs them unconditionally.
`truncated` and `dry_run` are omit-when-false under the family wire conventions
ANTS-3664 § 2.4 owns. `check_stats`, `skipped`, `check_errors`, `pairs` and
`clusters` are omit-when-empty. `fixed`, `files_written` and `fix_errors` are absent entirely
under `fix:false` — absent, not zero, because `files_written:0` on a report-only
run reads as "tried and wrote nothing" when the truth is "never entered the fix
path".

**Under `fix:true` the first two are present even when nothing was repaired** —
`fixed:[]` and `files_written:0` — and `fix_errors` is omit-when-empty. That is
what makes the absence meaningful in the other direction: absent says the fix
path was never entered, present-and-empty says it ran and found nothing to do.
A verb that omitted them in both cases would collapse the distinction the
paragraph above exists to draw.

**`check_stats` is where a checker's envelope-level signals land.** The
per-check envelopes are gone (below), so any value a checker would have
returned at *its* top level needs a route or it is lost. The shape is
`check_stats[<verb>][<key>]`, and the walk is **per document** while this map is
**per checker** — so every key needs a stated way to combine across documents:

| Value class | Combined across documents by | Keys |
|---|---|---|
| counter | **sum** | `unparsed_total`, `examples_suppressed`, `counts.*`, `passages_total`, `passages_compared` |
| flag | **logical OR** (true if true for any document) | `truncated`, `sections_checked` |
| per-document map | **merged**, keyed by project-relative path | `line_count` |

| Checker | `check_stats` entries |
|---|---|
| `doc_citations` | `unparsed_total`, `examples_suppressed` |
| `doc_symbols` | `counts.total`, `counts.resolved`, `counts.unresolved`, `counts.not_checked`, `truncated` |
| `spec_lint` | `sections_checked`, `line_count` |
| `doc_integrity` | — (its envelope carries no scalar beyond `counts`) |
| `doc_dedup` | `passages_total`, `passages_compared`, `truncated` (`pairs[]` and `clusters[]` are hoisted to the top level) |

`sections_checked` is the one flag whose OR needs saying out loud: it is
`false` by default in `spec_lint` and true only where the format standard's
required-section block was found, so it describes the *run's* configuration
rather than a per-document outcome and is identical for every document anyway.

**`truncated` names four different incompletenesses in this envelope**, and a
caller that reads any one of them as the others gets a wrong answer about what
the run covered:

| Where | Means |
|---|---|
| top level | this **response** is partial — `max_findings` capped `findings[]`, or a cap elided a document (§ 2.4) |
| `check_stats["doc_symbols"]` | some symbol occurrences were never looked up; pairs with `counts.not_checked` |
| `check_stats["doc_dedup"]` | some passages were never compared |
| `doc_citations`' own | **not in `check_stats` at all** — it means that document's citation set is partial, so it routes to `check_errors[]` as `citations_truncated` (§ 2.2) |

The first is about the response, the middle two about a checker's coverage, and
the last about one document's input. Only the first is a paging signal; the
other three survive raising `max_findings` to its ceiling.

`doc_citations`' `read_budget_exhausted` is **not** here — § 2.2 routes it to
`check_errors[]`, because a resolution budget that ran out degrades the citation
statuses rather than describing them, and a caller must be able to tell a clean
run from a curtailed one. It was listed in both places until loop 4; `check_errors[]`
is the single route.

`doc_symbols`' names are ANTS-3661 § 2.2's own (`counts: { total, resolved,
unresolved, not_checked }`). An earlier draft called the first
`candidates_total` — which is ANTS-3636's name for a different quantity, the
match count behind an *ambiguous citation*, not anything `doc_symbols` returns —
and quoted the shape without `not_checked`, the one key that must not be
dropped. ANTS-3661 makes it a
**third state, not a flavour of unresolved**: an occurrence elided by
`maxSymbolsPerRun` or by that spec's resolve deadline was never looked up, so it
produces no finding, and reporting it as unresolved would assert that a symbol
does not exist on the strength of never having asked. Drop the key and a
`doc_lint` caller sees `truncated:true` with no count of what went unchecked —
re-importing at the composite level the exact false claim that verb exists to
avoid, and violating this section's own rule that every envelope-level signal
needs a route.

`spec_lint`'s `sections_checked` is the sharp one: ANTS-3662 ships that
`missing_section` **rule** disabled, so without this route a `doc_lint` caller
cannot tell a spec with no missing sections from a spec whose section rule never
ran — the precise distinction `checks_run[]` exists to preserve one level up.
(Rule, not check: ANTS-3664 § 2.4 reserves "check" for one of the five checkers,
which is what `checks_run[]` counts.)

The five legal `checks[]` values are exactly the `verb` strings ANTS-3664's
findings carry — one vocabulary, not two:

| `checks[]` value = `verb` | Engine |
|---|---|
| `doc_integrity` | `DocIntegrity::check` (adapter) |
| `doc_citations` | `DocCitations::check` (adapter) |
| `doc_dedup` | ANTS-3660 |
| `doc_symbols` | ANTS-3661 |
| `spec_lint` | ANTS-3662 |

`counts` comes from `DocFinding::countsByVerbAndKind` over the whole run.
`checks_run[]` is not decoration: it distinguishes "check ran and found nothing"
from "check did not run", which `counts` alone cannot express.

**Not** the full per-check envelopes. The first draft promised them and it was
wrong twice: `doc_citations`' envelope carries `text[]` for every healthy
citation, thousands corpus-wide on a verb whose premise is frugality; and that
verb is *file*-scoped, so "the envelope it would have returned alone" is N
envelopes with N copies of every top-level field. A caller wanting the full
shape calls the verb directly — they remain independently callable (§ 5). The
structured payloads that survive are `doc_dedup`'s **`pairs[]` and
`clusters[]`**, both hoisted to the top level, because `DocFinding::Finding` has
neither a second-location field nor a grouping field (ANTS-3660 § 2.5).
Hoisting only `pairs[]` hands the composer the ungrouped output clustering was
added to prevent — ANTS-3660 records that as a defect it already fixed once,
naming this document as where it came from.

### 2.2 The two adapters

`doc_integrity` and `doc_citations` ship with tested envelopes and live callers,
so **neither is rewritten**. Each gains a pure adapter in the verb layer:

| Source | → `DocFinding::Finding` |
|---|---|
| `DocIntegrity::Finding` | `kind` from its `Kind` enum (`dead_anchor` / `broken_link` / `toc_gap`); `file`, `line`, `message` map straight across |
| a non-`ok` `doc_citations` citation | `kind` from `status` (`missing_file`, `out_of_range`, `ambiguous`, `read_error`, `unresolved`); `line` from `doc_line`; `message` composed from `raw` and the status |

Four rules the adapters obey, all load-bearing:

- **`file` is the document the finding was found *in*, never the target it
  points at.** A citation is the one finding shape in this set with two
  locations — the spec that wrote a line reference into `src/foo.cpp`, and the
  `src/foo.cpp` that cannot satisfy it — and `DocFinding::Finding` has one
  `file` field. It holds
  the scanned document, and `line` holds `doc_line`, so every finding in the run
  groups and sorts by the document a reader would open to fix it. The target is
  named in `message`, which is the only place it appears. Without this rule the
  adapter is a coin-flip: half the corpus's citation findings would sort under
  files that are not documents at all and that `checked_docs[]` never listed.
- **An `ok` citation is never a finding**, including one whose
  `anchor_found:false` (ANTS-3654). That flag is *advisory* — it says a needle
  moved, not that the citation is wrong — and promoting it to a finding would
  contradict the parent spec, where it is explicitly not a status.
- **`unparsed[]` entries are not findings.** ANTS-3653's design contains them:
  a prose token that happens to parse (`6.2:1`, `counts.missing_file:3`)
  resolves nowhere and lands there precisely so it never reaches `ok`. They are
  contained noise, and ANTS-3659 § 5 scopes them out by name. Surfacing them
  here would re-import the exact drowning problem that spec was written to fix.
- **The adapter assigns `emissionIndex`.** `DocFinding::Finding` documents that
  field as set by the producer, and neither frozen engine has one —
  `DocIntegrity::Finding` carries no such member and `doc_citations` returns
  JSON. So for these two the *adapter* is the producer: it numbers findings from
  0, in the order the source engine returned them, per verb per run. That order
  is well-defined on both sides — `DocIntegrity::check` documents its findings
  as returned in `(file, line)` order, and `doc_citations`' citations are in
  document order (ANTS-3653 INV-33). Without this rule INV-7's tiebreak has no
  value to break ties with on exactly the two producers whose findings the
  corpus has most of.

**This deliberately diverges from `only:"stale"`, and the divergence is the
point.** ANTS-3654 INV-14 has that filter *keep* an `ok` citation whose
`anchor_found` is false — it is a **view** over citations, built for a reader
scanning drift. `findings[]` is a list of **defects**, and an advisory flag
saying a needle moved is not one; ANTS-3654 § 2 is explicit that `anchor_found`
is never a status. Two different questions, two different answers, and a caller
wanting the drift view calls `doc_citations` with `only:"stale"` directly.

**Reading convention.** Adapters and consumers read an absent `auto_fixable` as
false and a present `line:0` as document scope — the two conventions ANTS-3664
INV-1 fixes. The `doc_integrity` adapter sets `autoFixable` from a small
per-adapter kind list (today: `toc_gap` alone), because that struct predates the
flag; ANTS-3664 § 2.1 records why that is accepted rather than pushed upstream.

**Whole-document alarms are not dropped on the floor.** `doc_citations` returns
**seven** per-document scalars that are not citations and so have no row in the
adapter table above — an adapter that only walks `citations[]` loses all seven
silently. They split three ways, on whether the scalar describes a defect, a
statistic, or an *incomplete run*:

| Scalar | Becomes | `check_errors[]` `reason` |
|---|---|---|
| `unterminated_fence` | a finding, `kind:"unterminated_fence"`, `line` = the opener | — |
| `unterminated_examples` | a finding, `kind:"unterminated_examples"`, `line` = the opener | — |
| `examples_suppressed` | `check_stats`, not a finding | — |
| `unparsed_total` | `check_stats`, not a finding — INV-4's second half asserts it | — |
| `read_budget_exhausted` | `check_errors[]` — the citation statuses are a floor | `read_budget_exhausted` |
| `basename_index_truncated` | `check_errors[]` — same, resolution was degraded | `basename_index_truncated` |
| `truncated` | `check_errors[]` — same, the citation set itself is partial | `citations_truncated` |

**The seventh row is the one an implementer building from a shipped envelope
would miss.** `doc_citations`' top-level `truncated` is not one flag but three
disjuncts (`src/doccitations.cpp:925`): a resumable page cap, a document longer
than `maxDocLines`, or `unparsed[]` past `maxUnparsed`. Every one of them means
this document's citation set is a **floor** — the same claim
`read_budget_exhausted` makes about resolution — so it routes the same way. It
is easy to lose precisely because the other two alarms read as errors and this
one reads as pagination.

The first two are defects by construction: an unterminated fence swallows the
rest of the document, and an unterminated `doc-examples` region suppresses every
citation after it. Both are invisible to a reader — the eye reconstructs what
the renderer ate — which is exactly why `/cold-eyes` § 1e adopted the fence
check, and § 1e reads it **from this field**. Dropping it here would break the
one caller this verb exists to serve. `examples_suppressed` and `unparsed_total`
are counts of things working as intended, so they are statistics.

The last three rows are neither, and putting them in `check_stats` would be the
quiet mistake. `read_budget_exhausted` says the engine stopped opening targets
before it ran out of citations, `basename_index_truncated` says it resolved
against a partial index, and `truncated` says it did not return every citation
it found — in all three cases the `ok`/`missing_file` split for that document is
a **floor**, not an answer, and a caller that reads `findings[]` as complete is
reading it wrong. `check_errors[]` is where this verb already says
"this checker's output for this document is not the whole story" (§ 2.4), so the
signal reuses it rather than inventing a third channel. Neither is a *failure*:
`ok` stays true and the findings that were produced are all valid.

### 2.3 The fix path (ANTS-3669)

**This is the only part of the doc-lint family that writes to a file.**
Everything else reads, computes and returns. A defect in the read path returns a
wrong string and the caller notices; a defect here silently rewrites a document
the user has not opened. Three contracts follow from that one fact, and nothing
else in this document needs any of them: a `dry_run` preview, exclusion from
`isEtagSupportedTool`, and a gate on `autoFixable` rather than on `kind`.

**It ships second.** The walk and the envelope (§§ 2.1–2.2) serve `/cold-eyes`
§ 1e without any of this, and that is the order the caller wants — the pre-pass
reads far more often than it repairs. The two phases keep separate ROADMAP ids
for that reason. They are specified together because one verb, one registration
entry and one translation unit cannot have two contracts: the response envelope
spans both phases, and when they were two documents every write-side field had
two owners and diverged. The loop log's `4-merge` row records what that cost.

#### What may be repaired

Auto-fixable is **exactly one kind**:

- **`toc_gap`** — a hand-maintained table of contents disagrees with the
  document's own headings. There is one correct answer and the document already
  contains it.

**What the repair writes.** "Regenerable from the headings" is not a contract; a
naive reading of it destroys content, so the output form is fixed here.
`DocIntegrity` emits `toc_gap` for exactly two causes and checks coverage for
**H2 only** (`src/docintegrity.cpp` — `duplicate TOC entry` and `section '%1'
missing from TOC`, both guarded by `if (h.level != 2) continue`). The repair is
therefore **a patch, never a regeneration**:

| Cause | Repair |
|---|---|
| `section '<t>' missing from TOC` | insert one entry for that H2, at the position its heading holds in document order relative to the entries already present |
| `duplicate TOC entry '<slug>'` | delete the later occurrence; keep the first |

Everything else inside the TOC region is **left byte-identical**: H3 and deeper
entries, free-text rows, blank lines, and any entry whose slug matches no
heading. That last one looks like a defect and is deliberately not repaired —
`doc_integrity` does not report it (coverage runs heading→entry, never
entry→heading), so removing it would be the fixer acting on a judgement no
checker made. An implementation that rebuilds the region from the H2 set passes
a fixture whose TOC is H2-only and silently deletes a hand-written sub-entry on
the first real document it meets; **INV-18 is the row that catches it**.

The inserted entry copies the form of the entries already in the region — the
list marker, the indent, and the link form (`[<heading text>](#<gfmSlug>)`) of
the nearest existing H2 entry, whose slug is computed by
`DocIntegrity::gfmSlug`, the same function that found the gap. A region with no
existing H2 entry to copy is **not repaired** (`fix_errors[]`, reason
`no_template`): the file's convention is unknown, and guessing it is how a fixer
starts writing markdown the author did not choose.

The ROADMAP bullet behind ANTS-3663 also named a version string disagreeing with
`project(... VERSION X.Y.Z)` in `CMakeLists.txt`. **It is dropped, because no
checker in the composed set produces such a finding**: `DocIntegrity::Kind` is
`{DeadAnchor, BrokenLink, TocGap}`, `doc_citations` emits citation statuses, and
none of ANTS-3660/3661/3662 checks versions. A fix path for a finding nobody
emits is untestable by construction. If version drift is ever wanted it needs a
producer first, filed as its own item at that point — nothing is filed today.

**Everything else is report-only by design, not by omission**, and each refusal
has a reason rather than a shrug:

- deleting one of two duplicated facts needs a decision about which is
  canonical, and the wrong choice destroys the authoritative copy (ANTS-3660
  § 2.5);
- an unresolved symbol may be a forward reference to something the doc is about
  to create, which the verb must not adjudicate (ANTS-3661 § 2.3);
- renumbering an `INV-N` breaks every citation of it, which `specs.md` § 5.5
  forbids outright and `/cold-eyes` Phase 4 permits only where every citation is
  re-pointed in the same pass — neither of which a verb can do;
- a missing section needs prose only an author can write.

The gate is the **flag on the finding, never the kind.** An implementation that
tests `kind == "toc_gap"` instead of reading `autoFixable` passes every fixture
here and breaks the moment a native producer marks something else fixable —
which is the whole reason ANTS-3664 carries the flag. While `toc_gap` is the
only fixable kind the two gates are behaviourally identical, so no fixture can
separate them: **INV-5 carries a source-scrape arm** for this, and § 6 a
mutation row. A rule whose only enforcement is a sentence is a rule that ships
broken.

#### `fixed[]`, `files_written`, and what correlates them

**`fixed[]` is per finding; `files_written` is per file, and they are not the
same number.** Each element is `{verb, kind, file, line}` — a report of what was
repaired, not a description of the edit and not a join key. `emission_index` is
deliberately absent; ANTS-3664 § 2.1 owns why. A caller correlating the two
arrays matches on the four fields and, where two findings agree on all four, in
order — both arrays are totally ordered by INV-7.

One document with three TOC gaps produces three `DocIntegrity::Finding`s —
`toc_gap` is emitted **per occurrence** by the producer, which appends one
finding per uncovered H2 and one per duplicate entry (`src/docintegrity.cpp`,
check 3) — and one patched table of contents, therefore `fixed[]` of length
three with `files_written:1`. (The verb-layer tally in
`docIntegrityBuildResponse` counts those findings, so it is consistent with
per-occurrence emission but does not by itself prove it; the producer is the
evidence.) Both numbers are
reported because a caller asking "did it touch anything it shouldn't" wants the
file count, and a caller reconciling against `findings[]` wants the finding list.

Neither array is paged by `max_findings`; § 2.1 owns that rule and INV-15
asserts it.

#### `dry_run`

`dry_run:true` computes the would-be result and writes nothing, and it must
share the code path that performs the write — a preview assembled separately is
a preview that drifts. The response echoes `dry_run:true` so a caller reading a
stored envelope can tell a preview from a run that really wrote.

**`dry_run:true` with `fix:false` refuses `bad_args`.** There is nothing a
report-only run would have written, so the request has no coherent answer, and
the alternative is worse than a refusal: the fix keys are absent under
`fix:false` (§ 2.1), so a silently-accepted preview returns exactly the envelope
of a plain read. A caller who mistyped the flag pair would read "nothing to
repair" where the truth is "never asked to repair" — the same absent-not-zero
confusion the presence rule exists to prevent, arriving through the request side.

#### Writes

**The repair re-reads the file at write time and re-derives the gaps from those
bytes.** It does not patch the text the walk read. The walk happens first, the
whole walk finishes, and only then does the fix path open anything — so between
the finding and the write the user may have saved the file, and the findings
carry line numbers into a document that no longer has those lines. This is the
one precondition that cannot be inferred from "atomic write": `apply_edits`
re-reads each file immediately before applying (`src/remotecontrol.cpp`,
`cmdApplyEdits` — `QFile in(resolved); working = in.readAll()` inside the
per-file loop), and matching that verb means matching this, not only its
`QSaveFile` call.

If the re-derivation yields no `toc_gap` for that document, **nothing is
written**: the file gets a `fix_errors[]` entry with reason `stale`, and the
run continues. A repair computed against bytes that are gone is not a repair.

The write itself is the project's full atomic-write idiom, not `QSaveFile`
alone: open, write, **check the write was not short**, `commit()`, then
`fsyncParentDir()` — the sequence `cmdApplyEdits` uses and
`tests/features/mcp_apply_edits/` locks by source-scrape (W1). A failure at any
step appends `fix_errors[]` with reason `write_failed` and leaves the original
file untouched, which `QSaveFile` guarantees by construction.

A document is rewritten **once per run, not once per finding** — three TOC gaps
in one file are one patch and one write.

### 2.4 Partial failure

One walk, five checkers, and they do not agree today on what an unreadable
document means: `DocIntegrity::check` silently excludes it, while
`DocCitations::check` refuses `read_failed`. Under one walk that collision needs
a decision, so:

- **A document that cannot be read or decoded is excluded from
  `checked_docs[]`, listed in `skipped[]` with a reason, and the run
  continues** with `ok:true`. One bad file in a tree must not fail a whole
  review pass.
- **A document elided by a cap is skipped the same way, and says so.**
  `DocIntegrity::Options` caps both the document count (`maxDocsPerRun`, whose
  comment is explicit that docs beyond it are "skipped, not read") and the bytes
  of any one document (`maxDocBytes`). Neither is a read failure, a checker
  failure or a write failure, so without a route they land in no channel at all
  and a run over a large corpus silently drops documents while reporting
  `ok:true` with a complete-looking `findings[]`. They go in `skipped[]` with
  reasons `doc_cap` and `too_large`, **and they set `truncated:true`** —
  extending that flag from "`max_findings` elided findings" to its honest
  meaning, *this response does not describe the whole tree*. § 4's inherited
  discipline is that every truncation sets a flag; this is the case where the
  flag had no wiring.
- **A fix that fails to write** (read-only file, permissions) appends to
  `fix_errors[]` and leaves `ok:true` — asserted by **INV-14**, and named here
  because it is the partial-failure case and belongs beside the other two. A
  partial write is still a successful call: the incompleteness is in the
  envelope, not the status.
- **A checker that fails on one document** — it refuses, throws, or hits its own
  internal cap — appends `{verb, file, reason}` to `check_errors[]`, and the
  walk continues with the remaining checkers on that document and with that
  checker on the remaining documents. The failure is *per document per checker*,
  never per run: one malformed spec must not silence `spec_lint` across a tree.
  The verb stays in `checks_run[]`, because it did run — but **a caller must
  read `checks_run[]` together with `check_errors[]`**, since a check with
  entries in the latter ran incompletely and its `counts` are a floor rather
  than a total. This is the one place in the envelope where a count is not
  authoritative, and it is stated rather than left to be discovered.

**The three channels, their element shapes and their whole `reason`
vocabulary.** `check_errors[]` carries a `verb` because the same document can
fail one checker and satisfy the others; `skipped[]` and `fix_errors[]` do not,
because a document either got read or did not, and a file either got written or
did not — the asymmetry is deliberate, not an oversight.

| Channel | Element | `reason` values |
|---|---|---|
| `skipped[]` | `{file, reason}` | `read_failed`, `doc_cap`, `too_large` |
| `check_errors[]` | `{verb, file, reason}` | `check_failed`, `read_budget_exhausted`, `basename_index_truncated`, `citations_truncated` |
| `fix_errors[]` | `{file, reason}` | `write_failed`, `stale`, `no_template` |

**`check_errors[]` carries two kinds of entry and the `reason` is what tells
them apart.** `check_failed` means the checker refused, threw, or hit its own
internal cap — it produced nothing for that document. The other three mean it
succeeded but *incompletely*, and `ok` stays true with valid findings returned
(§ 2.2). A caller that treats every `check_errors[]` entry as a failure
under-reports; one that treats them all as advisory misses a checker that never
ran. `write_failed` is this verb's single name for what `apply_edits` splits
into open- and commit-time failures: it reports per file, not per edit, so the
finer split has nothing to attach to.

### 2.5 Files and hooks

Engine `src/doclint.{h,cpp}` in `ants_core_lib`, calling the five engines under
the convention ANTS-3664 § 2.3 fixes: each takes the document's text and its
project-relative path, and the composer opens each file exactly once.

**`DocLint::Options` carries the injected inputs through.** Two of the five
engines need something `ants_core_lib` cannot see, so per ANTS-3664 § 2.3 rule 3
the verb layer supplies it and this composer forwards it unchanged:

| Forwarded to | Member | Filled by `cmdDocLint` from |
|---|---|---|
| `doc_symbols` | `excludedNames` | the MCP verb names and schema argument names |
| `doc_symbols` | `rootCanonical` | the resolved project root |
| `spec_lint` | `requiredSections` | the format standard's `<!-- required-sections -->` block, read once per run |
| `doc_dedup` | `excludedPathGlobs` | ANTS-3660 § 2.4 |

A composer that drops these does not fail — it produces exactly the
verb-name false-positive flood ANTS-3661's own loops removed, and a
`sections_checked:false` that looks like a missing standard rather than a
missing pass-through. That silence is why the forwarding is a stated contract
here rather than left to the implementer.
Verb layer mirrors `doc_integrity`: `cmdDocLint` plus one pure static
`docLintBuildResponse`, and the registration set ANTS-3661 § 2.4 enumerates —
one `registerToolProvider` with `CallerCwdContract::Required` in
`src/mainwindow.cpp`, plus five `src/claudeintegration.cpp` hooks (the
`tools/list` entry, the token-cost row, the `kindForName` bucket,
`callerCwdContractFor`, `isEtagSupportedTool`).

**The walk is reused, not cloned — there is no `docLintEnumerate`.**
`cmdDocLint` calls `RemoteControl::docIntegrityEnumerate` directly, as all three
shipped siblings do (`cmdDocSymbols`, `cmdSpecLint` — passing `specsDir` — and
`cmdDocDedup`; the comment beside the last reads "reusing `docIntegrityEnumerate`
for the walk"). ANTS-3661 § 2.4 settled this in as many words — "two enumerations
that must agree forever are two that will eventually disagree" — and ANTS-3660
§ 2.4 adds that a further `*Enumerate` differing only in its verb name is the
duplication this family reports. The per-checker eligibility predicate (§ 2.1) is
a **filter over that one enumeration's result**, not a second walk.

`doc_integrity` and `doc_symbols` both already ship a `selection_hint` in their
`tools/list` descriptor, and `doc_lint` follows suit — a five-checks-in-one verb
is the strongest candidate in this lane for one. It adds **no** hook:
`selection_hint` is a key on the `tools/list` entry, which is hook one of the
five above.

**The net is four hooks**: the inherited five, minus `isEtagSupportedTool` —
which the next paragraph removes.

**Two departures from that set, both forced by the fix path (§ 2.3).**
`doc_lint` is the only verb in this family that can write, so:

- it declares `dry_run` through the shared `makeDryRunProp()` factory, as
  `mcp-tools.md` requires of every mutating verb; and
- it is deliberately **absent** from `isEtagSupportedTool`. ETag-304 is specified
  for read verbs: a matching `etag_match` short-circuits to
  `{ok, unchanged, etag}`, which on a `fix:true` call is a **success envelope for
  a repair that never happened**.

**The exclusion is unconditional from the first ship, not a later removal.**
There is one verb and one registration entry, so "the read phase has ETag
support and the fix phase gives it up" is not something the registration can
express — and phase 1 ships before any write path exists, so there is no moment
at which adding the entry would be safe. A reader assembling the hooks from the
inherited list alone would add it by symmetry with the siblings, which is
precisely the mistake that lets an `etag_match` swallow a repair. INV-13 locks
it from both the schema side and the behaviour side.

Both phases land in the same files: no new engine and no new verb arrives with
the fix path, only `fix` / `dry_run` handling on `cmdDocLint` and the
regeneration itself in `src/doclint.cpp`.

## 3. Invariants

- **INV-1** — One walk; **one shared read per enumerated document serving all
  three native checkers**, plus one read per adapted engine per document.
  *Test:* a `DocLint::Probe` open-counter over a three-document tree called with
  `checks:["doc_dedup","doc_symbols","spec_lint"]` → **three** opens — one per
  document, serving three checkers. An implementation that reads once per
  checker returns nine here, so this call discriminates and is the whole
  assertion.

  **The nine-open all-checks figure is a budget, not a test.** `doc_lint` can
  instrument only what it owns, and § 2.2 freezes the two adapted engines.
  `DocIntegrity` exposes no probe at all — its surface is `Finding`, `Options`,
  `check` and `gfmSlug` — and `DocCitations::Probe` counts `opens` as *target*
  files read, a different quantity from opening the document. Six of the nine
  are therefore unobservable without editing a frozen engine, so § 2.1 states
  nine as the honest budget and attaches no assertion to it. Target reads keep
  their own budget (ANTS-3636's `maxTargetReads`) and are out of scope here
  either way.
- **INV-2** — `checks[]` narrows findings *and* counts together; an unknown name
  refuses `bad_args`. *Test:* a fixture producing findings from two checkers →
  `checks:["doc_integrity"]` returns only those, with `counts` matching; plus
  `checks:["nope"]` → `bad_args`. **Guarded by an unfiltered run first**,
  asserting both checkers do produce findings on this fixture — without it the
  narrowing half passes against an engine that produces nothing at all, which is
  the state it first runs in.
- **INV-3** — An `ok` citation is never a finding, including one with
  `anchor_found:false`. *Test:* a doc with a healthy citation, an
  anchor-missing-but-`ok` one, and a `missing_file` one → exactly one finding.
  The middle row is the one that fails against an adapter treating the advisory
  flag as a status.
- **INV-4** — `unparsed[]` entries never become findings, and are not lost
  either. *Test:* a doc whose only citation-shaped token is `6.2:1` → zero
  findings, **and** `check_stats["doc_citations"]["unparsed_total"] == 1`. Both
  halves are needed: without the first the verb re-imports ANTS-3659's problem,
  and without the second an adapter that discards `unparsed[]` entirely passes.
- **INV-5** — `fix:true` changes only `autoFixable` findings; `fixed[]` names
  each finding repaired and `files_written` counts files. *Test:* a tree of
  three documents — one with a TOC missing **two** H2s, one with a
  near-duplicate pair, one with an unresolved symbol → `fixed[]` of length
  **two**, `files_written:1`, and **the other two files byte-identical
  afterwards**. The two-gap TOC is deliberate: it separates the per-finding list
  from the per-file count, and a one-gap fixture makes both numbers 1 and tests
  neither. The byte-identical half is the assertion about restraint — a
  `fixed[]` of the right length proves nothing about what was left alone.

  **Plus a source-scrape arm: the fix path reads `autoFixable`, and the string
  `"toc_gap"` does not appear in its gate.** While `toc_gap` is the only fixable
  kind the two gates behave identically, so the behavioural fixture above cannot
  tell them apart — and the kind gate breaks silently the moment a native
  producer marks anything else fixable. Same technique as INV-6's arm.
- **INV-6** — Default is report-only: without `fix`, no file is written, and the
  envelope says the fix path was never entered. *Test:* the INV-5 tree run
  without the flag → every file byte-identical; `fixed`, `files_written` and
  `fix_errors` **absent from the response object** (not empty — § 2.1's presence
  rule, which INV-16's justification depends on); and a source-scrape confirming
  the write path is reachable only under the flag. Then the same tree with
  `fix:true` over a document with nothing repairable → `fixed:[]` and
  `files_written:0` **present**. The pair is the assertion: either arm alone is
  satisfied by a verb that always omits the keys.

  **These two ids were tombstoned to ANTS-3669 on 2026-07-28 and restored the
  same day** when the split was unwound; each carries the claim it was written
  for, so no id changed meaning and `specs.md` § 5.5 is satisfied by restoration
  rather than by renumbering. Verified before restoring: no document outside
  this one cited `ANTS-3663 INV-5/INV-6` or `ANTS-3669 INV-1/INV-2`, so nothing
  was redirected. The corpus's remaining `*moved to <ID>*` tombstones are
  unaffected: fifteen, all in ANTS-3636 — `workspace_search` for
  `^- \*\*INV-\d+\*\* — \*(moved to|withdrawn)` over `docs/specs`, 2026-07-28,
  which returned seventeen before this edit and fifteen after.
- **INV-7** — Findings are in a **total** order: `file`, then `line`, then
  `verb`, then `kind`, then `message`, and finally
  **`DocFinding::Finding::emissionIndex`** — the producer's own 0-based counter
  within one run (ANTS-3664 § 2.1, where the field lives). *Test:* a tree producing findings from three
  checkers on one file, including two findings from the same verb on the same
  line (two dead links in one line, or two citations sharing a `doc_line`)
  **and two whose `message` strings are byte-identical** — two `broken_link`s on
  one line pointing at the same missing target — → the stated order,
  byte-identical across two runs.

  The identical-message row is why the sixth key exists. The first five are all
  properties of a finding, so two findings can agree on every one of them, and
  a five-key comparator leaves those two in whatever order the underlying
  container happened to yield — the definition of *not* total. The emission
  index is the tiebreak of last resort and is well-defined because each producer
  emits in its own document order, which its own spec fixes (ANTS-3661 INV-5,
  ANTS-3653 INV-33) and which § 2.2's fourth adapter rule fixes for the other
  three. An unstable tail makes every caller's diff noise, which is the whole
  reason this invariant is here.

  **The tied pair is asserted at the engine, not on the wire.** Two findings
  agreeing on all five serialised fields are indistinguishable in the response —
  `emission_index` is never emitted — so swapping them changes no byte, and the
  envelope arm above proves only that two runs agree. The discriminating
  assertion runs against the returned `QList<DocFinding::Finding>`: the tied pair
  appears in ascending `emissionIndex`. A five-key comparator passes the envelope
  arm and fails this one, which is the point.
- **INV-8** — The verb-contract minimum `mcp-tools.md` § Tests requires of every
  `Required` tool, in the arms ANTS-3601 **INV-10** (the two refusals) and
  **INV-15** (the third arm, which is not one) establish. *Test:* three verb
  calls — absent `caller_cwd` → `caller_cwd_required`; a root-escaping `path` →
  `bad_path`; and a well-formed **non-existent** in-root `path` → **`ok:true`
  with an empty `checked_docs`**, not a refusal.

  **The third arm is the one to state rather than point at.** ANTS-3601 INV-15
  is explicit that a typo'd `docs/typo.md` yields `ok:true`, and an implementer
  who reads "the refusal minimums" and builds three refusals breaks a contract
  the whole family shares — so the expected result is written out here even
  though the rationale stays a pointer. The rest is deliberately not restated:
  a fourth copy of the arms is a fourth place for them to drift.
- **INV-9** — `doc_citations`' whole-document alarms survive the adapter:
  `unterminated_fence` and `unterminated_examples` become findings carrying the
  opener's line, `examples_suppressed` becomes a `check_stats` entry. *Test:* a
  document with an unterminated fence, one with an unterminated `doc-examples`
  region, and one with a closed region suppressing two citations → two findings
  with the two kinds and the two opener lines, and
  `check_stats["doc_citations"]["examples_suppressed"] == 2` with **no** finding
  of that kind. This is the row that fails against the obvious implementation —
  an adapter that walks `citations[]` and nothing else — and `/cold-eyes` § 1e
  reads the fence alarm from this field, so losing it breaks the caller this
  verb was built for.

  **And the three incompleteness alarms, which route to `check_errors[]` rather
  than to either of the above:** a document run with `maxTargetReads` lowered
  below its citation count → one `check_errors[]` entry with
  `reason:"read_budget_exhausted"`; a document longer than `maxDocLines` → one
  with `reason:"citations_truncated"`; in both cases `ok:true` and the citation
  findings that *were* produced still present. All seven of § 2.2's scalars are
  covered between the two halves of this row — the second half is the one whose
  route was already got wrong once, and the seventh scalar is the one an adapter
  written from a shipped envelope never sees.
- **INV-10** — A checker failing on one document does not stop the walk, and its
  incompleteness is visible. *Test:* a three-document tree where one document
  makes one checker fail → `check_errors[]` of length one naming that
  `{verb, file}`, that verb still in `checks_run[]`, findings still present from
  it on the other two documents, findings still present from the *other*
  checkers on the failing document, and `ok:true`. Five assertions because
  failure containment is two-dimensional: per document and per checker, and an
  implementation that gets one axis right routinely gets the other wrong.
- **INV-11** — `max_findings` truncates after the sort, and `counts` is computed
  before it. *Test:* a tree producing twelve findings run with
  `max_findings:5` → `findings[]` of length five that is **the first five of the
  same run at `max_findings:500`**, `truncated:true`, and `counts` totalling
  twelve. The prefix identity is the assertion: a cap applied during collection
  also returns five findings and also sets the flag, and only the comparison
  against the uncapped run tells the two apart. Plus the bounds: an omitted
  `max_findings` behaves as 500, and `0` and `9999` clamp to `1` and `5000`
  rather than refusing.
- **INV-12** — `dry_run:true` returns the envelope a real run would return and
  writes nothing. *Test:* the INV-5 tree run with `fix:true, dry_run:true` →
  `fixed[]` and `files_written` **identical to the `dry_run:false` run**, the
  envelope carrying `dry_run:true`, and every file byte-identical. The identity
  half is load-bearing: "wrote nothing" alone passes against a `dry_run` that
  returns an empty envelope, and passes *vacuously* against a verb with no write
  path at all — which is the state this row first runs in.
- **INV-13** — No `doc_lint` call can short-circuit to `{ok, unchanged}`.
  *Test:* two arms. (a) The registered schema for `doc_lint` carries **no
  `etag_match` property**, and a source-scrape of `isEtagSupportedTool` in
  `src/claudeintegration.cpp` finds no `doc_lint` entry. (b) A `fix:true` call
  passing an arbitrary `etag_match` does **not** return `{ok, unchanged}` — it
  either performs the repair and returns the full envelope, or refuses the
  undeclared property; which of those two depends on the schema layer's handling
  of unknown properties and is not this invariant's business. Arm (b) cannot be
  written as "take the returned `etag` and pass it back": a verb outside the
  ETag set returns no `etag`, so the obvious round-trip test is unwritable and
  its absence here is deliberate. This is the row that fails against the obvious
  registration, which is to add the verb to `isEtagSupportedTool` alongside its
  siblings.
- **INV-14** — A write failure on one document neither stops the run nor is
  silent. *Test:* a three-document tree with two repairable gaps where one
  target is read-only → `fix_errors[]` of length one naming that file with
  `reason:"write_failed"`, the other document repaired, `files_written:1`, and
  `ok:true`.
- **INV-15** — `max_findings` pages `findings[]` and does not bound the repairs.
  *Test:* the INV-5 tree run with `fix:true, max_findings:1` → `findings[]` of
  length one and `truncated:true`, but `fixed[]` of length **two**,
  `files_written:1`, and the repaired document **byte-identical to the same run
  at `max_findings:500`**. The byte comparison is the assertion: a fixer that
  consumes the capped list still reports a plausible envelope, and only the
  file's contents reveal that the cap changed what was written.
- **INV-16** — `dry_run` is meaningful only with `fix:true`. *Test:* two calls —
  `{fix:false, dry_run:true}` → `bad_args`; `{fix:true, dry_run:true}` →
  `ok:true`. Both arms are needed: the first alone is satisfied by a verb that
  refuses `dry_run` outright, which would break INV-12.
- **INV-17** — Each checker runs only on the documents it is eligible for, and
  an ineligible document is not a failure. *Test:* a tree with one spec under
  `specs_dir` and two documents outside it → `spec_lint` findings from the spec
  only, **neither** non-spec in `skipped[]` or `check_errors[]`, and both
  non-specs still in `checked_docs[]` with the other four checkers' findings
  intact; plus a run whose `path` selects no spec at all → `spec_lint` absent
  from `checks_run[]` while the other four are present. The second call is the
  discriminating one: an implementation that filters by silently emitting
  nothing leaves `spec_lint` in `checks_run[]` and reports a clean spec set that
  was never checked.

  **The same fixture carries the `check_stats` aggregation assertion**, because
  it is the only one that runs a directory-scoped checker over a known document
  set: `check_stats["spec_lint"]["sections_checked"]` is present (`false`, the
  shipping default), and `line_count` holds **one entry per checked spec, keyed
  by project-relative path** — the map-merge rule of § 2.1's value-class table,
  and the only one of the three whose combination is not obvious. A composer
  that treats `line_count` as a scalar overwrites it once per document and
  returns the last one, which looks entirely plausible in an envelope. Without this row the failure § 2.1 describes — a
  `missing_section` flood over every README and standard — reaches the primary
  caller on its first default-path run.
- **INV-18** — The `toc_gap` repair patches; it never regenerates the region.
  *Test:* a document whose TOC region holds two H2 entries, **one H3 sub-entry,
  one free-text row and one entry whose slug matches no heading**, with one H2
  missing and one duplicated → after `fix:true`, the missing H2 is inserted in
  document order, the later duplicate is gone, and **every other line of the
  region is byte-identical**, the unmatched entry included. The three untouched
  rows are the whole assertion: a fixer that rebuilds the region from the H2 set
  produces a correct-looking TOC, passes any fixture whose TOC is H2-only, and
  deletes hand-written content on the first real document it meets.
- **INV-19** — Every document the run does not check is named, and the response
  says it is incomplete. *Test:* a four-document tree run with `maxDocsPerRun:2`
  and one of the remaining two unreadable → the unreadable file in `skipped[]`
  with `read_failed`, the cap-elided file in `skipped[]` with `doc_cap`, neither
  in `checked_docs[]`, **`truncated:true`**, findings still present from the
  checked document, and `ok:true`. The `truncated` half is the one an
  implementation gets wrong: it is easy to list a skipped file and still report
  a response that reads as a complete account of the tree.
- **INV-20** — A citation finding is filed against the document that contains
  it, never the target it names. *Test:* `a.md` line 12 cites
  line 400 of a `src/gone.cpp` that does not exist → exactly one finding with
  `file:"a.md"` and `line:12`, `src/gone.cpp` appearing **only** inside
  `message`, `a.md` present in `checked_docs[]`, and `src/gone.cpp` absent from
  it. (The fixture's target is written with its line number *detached* on
  purpose: a literal `path:line` token in this sentence is one `doc_citations`
  harvests from this very spec, and the spec would then fail the check it
  specifies.) The last two assertions are what fail against the coin-flip adapter: filing
  under the target yields a findings list whose `file` values are not documents
  and were never enumerated.

## 4. RAM / build cost

Per document, peak is **up to three copies of one document's text** — § 2.1's
nine-open model is where those three reads come from and why the adapter-only
rule makes them unavoidable — together with the union of the five checkers'
per-document state, all held while that document is processed and dropped
before the next.

**The three copies are capped by two different constants, and `maxDocBytes` is
the name of both.** `DocIntegrity::Options::maxDocBytes` is 2 MiB;
`DocCitations::Options::maxDocBytes` is 8 MiB. `doc_lint`'s own shared read
takes the walk's cap, `DocIntegrity`'s, since it feeds the same enumeration. So
the per-document worst case is **2 + 2 + 8 = 12 MiB**, not three times one
bound — and it is a worst case per document, not a figure any real document in
this corpus reaches.

**Three things live for the whole run, not one.** The peak is their sum plus one
document's 12 MiB:

| Run-scoped state | Bound | Owner |
|---|---|---|
| `doc_dedup`'s passage index | `maxPassages`, `maxPostings` | ANTS-3660 § 4 owns the figure |
| `doc_symbols`' resolution cache | `maxSymbolsPerRun` distinct needles | ANTS-3661 § 4 |
| the accumulated `findings[]` | the five checkers' own caps — **not** `max_findings`, which pages the response and must not bound what the fixer sees (INV-15) | this spec |

`doc_dedup` is the expensive one and the only one a caller can switch off:
disabling it via `checks[]` drops the largest row. The other two shrink with the
tree but do not go away. The figures are named where they are owned rather than
restated here — a second copy is what this composite's own `doc_dedup` check
would report.

Caps are inherited, not re-invented: `maxDocsPerRun` and `maxDocBytes` from
`DocIntegrity::Options`, `maxPassages` and `maxPostings` from ANTS-3660,
`maxSymbolsPerRun` from ANTS-3661. `doc_lint` adds exactly one of its own —
`max_findings`, with `truncated:true` past it — because `findings[]` is the one
thing it produces that none of the five bounds, and ANTS-3636's discipline is
that every truncation sets a flag. `counts` is computed before the cap, so a
truncated response still reports the true totals.

The fix path adds one transient per repaired document — the regenerated table of
contents, built and written inside the same iteration and dropped before the
next document opens. Nothing accumulates across documents, so it does not move
the peak. `fixed[]` is bounded by the `autoFixable` findings, which the caps
above already bound; `max_findings` deliberately does not bound it (INV-15).

Build cost is the family default (ANTS-3664 § 4), with one deviation: the fix
path adds **no** translation unit of its own, landing in the `src/doclint.cpp`
this document's phase 1 already creates. **Three** new feature-test sources —
two in phase 1 and one in phase 2 (§ 6) — all into the existing `test_core`
bundle, so no new build target arrives either.

## 5. Out of scope

- **Any fix beyond `toc_gap`.** The narrowness is the design; § 2.3 gives the
  reason per refused kind. A permanent exclusion, not a deferral — a new fixable
  kind arrives with its producer, not ahead of it, so there is no id to name.
- **A version-string fix.** Needs a producer first (§ 2.3). No follow-up id is
  filed because nothing is deferred: the work does not exist until a checker
  emits the finding.
- **Repairing a document that no checker reported on.** A permanent exclusion:
  the fix path consumes `findings[]` and never scans independently, which is
  what keeps "what may be repaired" answerable by reading § 2.3 alone.
- **Interactive or partial application** (fix this finding, not that one). A
  permanent exclusion, not deferred work. A caller needing that granularity
  filters with `checks[]` and re-runs; a per-finding selector is a bigger
  surface than one fixable kind justifies, and it would grow every time a
  fixable kind was added.
- **Replacing the five verbs.** Each stays independently callable; this is a
  convenience and a shared walk, not a deprecation.
- **`AuditEngine` / `DebtSweep` findings.** Different lane, different consumer,
  and ANTS-3664 § 5 draws that boundary.
- **Running an LLM over anything.** Every check here is deterministic; the
  judgement calls are what the reviewer lanes are for.
