# ANTS-1111 — Fold `/audit` triage into the Project Audit tool

**Status:** v1 shipped 2026-05-13 in 0.7.88 (engine + foundation +
alias + framework detect). UI affordances (Fold-into-ROADMAP button,
per-finding Allow button, Since-baseline filter pill) deferred to
v2 — tracked under a new ROADMAP item; see § 12. Spec converged
after 3 cold-eyes loops; loop-by-loop fixes at § 11.
**Source:** ROADMAP.md ANTS-1111; ADR-0002 dec 8 relaxed by
[ADR-0003](../decisions/0003-cc-fold-relax-gate-and-draw-boundary.md)
dec 1 + 2.
**Blocked by:** none (foundation lives inside this ship).
**Unblocks:** ANTS-1112 (reuses `RoadmapFoldIn`), ANTS-1113 (reuses
`RoadmapFoldIn` + the widened allowlist machinery).
**Boundary:** see ADR-0003 dec 2 (per-surface table).

## 1. Problem

The `/audit` workflow today is **two halves stitched together**:

1. **Detection (already mechanical, in-process).** AuditDialog runs
   every detector (cppcheck, clazy, semgrep, ruff, bandit, gitleaks,
   custom grep rules). Output is parsed into `Finding` structs.
   Already in the dialog, no LLM round-trip.
2. **Triage (LLM-shaped today).** The `/audit` skill invokes the
   `audit-triage` Claude subagent to turn N raw findings into K
   actionable ones. Per-call cost: ~3-15 K tokens.

The triage half is **mostly mechanical** in disguise. Cross-tool
corroboration, framework auto-detect, allowlist matching, baseline
diff, suppression token recognition — none need a model. What's left
for a model is the genuinely-ambiguous tail: "is this stale comment
actually wrong, or merely terse?", "does this generic rule match the
codebase's intent here?".

ANTS-1111 lifts the mechanical bulk into AuditDialog, leaves the
ambiguous tail behind one optional "Triage with AI" button (already
shipped — `requestAiTriageBatch`), and adds a one-click
"Fold actionable into ROADMAP" button so the user-confirmed
actionable set lands in `ROADMAP.md` without a second LLM round
trip.

### 1.1 Scope (residual after ADR-0003 dec 4 inventory)

The ROADMAP body listed six mechanical pieces. Five of them are
already partially or fully shipped — see ADR-0003 dec 4. Residual
work this spec specifies:

| ROADMAP piece | Already shipped | Residual (this spec) |
|---|---|---|
| (1) Pre-triage drop catalog | Per-project `.audit_allowlist.json` for grep rules (`auditdialog.h:107-115`). | **Widen** to cover *every* detector's findings, not just custom grep rules. Add per-finding "Allow" button that appends to the file with a `reason` field. |
| (2) Cross-tool corroboration scoring | `computeConfidence` adds +20 for cross-tool agreement. | **Severity-tier shift** on top of the score: ≥ 2 distinct tools at the same `file:line` → severity += 1 (clamp to BLOCKER); single-tool from a known-noisy rule → severity -= 1 (clamp to INFO). |
| (3) Framework auto-detect | In `/audit` skill orchestration. | **Lift to `audithygiene`** — `detectProjectFrameworks(projectPath)` returns `["flask","react","qt6",…]`; consumers map to semgrep rule packs. |
| (4) Inline suppression coverage | `inlineSuppressed` already recognises NOLINT, noqa, nosec, nosemgrep, gitleaks:allow, eslint-disable-*, pylint: disable, ants-audit: disable[=rule]. | **Add `// audit: drop[=rule]` short alias** for the same semantic. The unification goal is already met under the longer token; this alias gives users an ergonomic shorthand. |
| (5) Since-baseline diff | `m_baselineFingerprints` + `m_showNewOnly` + `m_recentLinesOnly` + `m_recentFiles` exist. | **Combine into one "Since baseline" toggle** — when on, requires both (showNewOnly AND recentLinesOnly), so only findings on changed lines that aren't in baseline are visible. |
| (6) AI-triage fallback | `requestAiTriageBatch`, `m_batchTriageBtn`, `onBatchTriageClicked`. | None. Already off-by-default per existing config. |
| Fold-into-roadmap button | None. | **New `RoadmapFoldIn` helper** + AuditDialog button. Templates the dated block, allocates IDs via `.roadmap-counter` flock, atomic-rewrites `ROADMAP.md`. |

Total residual ≈ 6 small pieces + 1 new shared helper. Estimated
diff: ~600-900 LoC across `auditengine`, `audithygiene`,
`auditdialog`, new `roadmapfoldin.{h,cpp}`, plus tests.

## 2. Surface

### 2.1 New AuditDialog buttons (right of `m_batchTriageBtn`)

```
[ 📥 Allow this finding ] [ 🌳 Fold actionable into ROADMAP ]
```

- **"Allow this finding"** — appears in each finding's expanded
  panel (next to the existing suppress link). Pops a one-line
  prompt for the `reason` text, appends an entry to
  `<projectPath>/.audit_allowlist.json` with the finding's
  `(rule, file_glob, line_regex)`, redraws.
- **"Fold actionable into ROADMAP"** — appears in the dialog
  footer, next to `m_batchTriageBtn`. Enabled iff at least one
  visible finding has `aiVerdict == TRUE_POSITIVE` OR
  `confidence >= 70`. Clicking pops a confirmation modal listing
  the actionable findings and the IDs that will be allocated
  (`[ANTS-NNNN]` … `[ANTS-NNNN+K-1]`); on confirm, atomic-writes
  the templated block into `ROADMAP.md` and bumps
  `.roadmap-counter`.

### 2.2 New AuditDialog filter pill

Inserted into `m_filterBar` between the severity pills and the text
filter:

```
[ Since baseline ]    (default off)
```

When on, sets both `m_showNewOnly = true` AND `m_recentLinesOnly =
true` and recomputes `m_recentFiles` / `m_recentLines` from `git
diff --name-only HEAD vs the baseline-snapshot's commit`. When off,
both flags revert to their previously-saved per-toggle state. The
two underlying buttons (`m_baselineBtn`, `m_newOnlyBtn`) remain
available for power users who want the modes independently.

### 2.3 New `audithygiene` API

```cpp
namespace AuditHygiene {

// Probe for project markers and return the list of recognised
// frameworks. Lookups (in order, additive — a project may use more
// than one):
//   "flask"      — requirements.txt or pyproject.toml mentions flask
//   "django"     — manage.py at project root, or "django" in deps
//   "react"      — package.json dependencies.react or .react-dom
//   "vue"        — package.json dependencies.vue
//   "qt6"        — CMakeLists.txt mentions Qt6:: or find_package(Qt6
//   "rust"       — Cargo.toml at project root
//   "go"         — go.mod at project root
// Empty list if none match. Filesystem-bounded (does not chase
// symlinks outside projectPath).
QStringList detectProjectFrameworks(const QString &projectPath);

// Map detected frameworks to the semgrep rule-pack arguments to
// splice into the semgrep invocation. Each framework maps to **two
// consecutive list entries** (`{"--config", "p/flask"}`) so callers
// can splice them directly into a `QProcess::start(args)` argv-style
// list without re-tokenising. Unknown framework names contribute
// nothing.
//
// Example: `semgrepRulePacks({"flask", "react"})` returns
//   {"--config", "p/flask", "--config", "p/react"}.
QStringList semgrepRulePacks(const QStringList &frameworks);

} // namespace AuditHygiene
```

### 2.4 New `auditengine` API

```cpp
namespace AuditEngine {

// Apply severity-tier shifts based on cross-tool corroboration count
// per (file, line). In-place mutation of `findings[].severity`.
//
//   coverageCount(f) = number of distinct CheckIds whose findings
//                      cite the same (f.file, f.line) pair.
//
//   shift = +1 if coverageCount >= 2
//   shift = -1 if coverageCount == 1 AND f.checkId in noisyRules
//   shift =  0 otherwise
//
// Severity is clamped to [Info, Blocker]. The score-side +20 in
// computeConfidence is unchanged — this shift complements it, not
// replaces it.
//
// `noisyRules` is the set of checkIds with ≥50 % suppression rate
// over the last 30 days, supplied by the caller. AuditDialog computes
// it via a new accessor on RuleQualityTracker:
//
//   QStringList RuleQualityTracker::noisyRuleIds(int fpThreshold = 50,
//                                                int minSamples = 5) const;
//
// (~15 LoC, walks the existing report() output, filters where
// fpRate30d >= fpThreshold && fires30d >= minSamples. Min-samples
// guard prevents a rule that fired twice and was suppressed once
// from being labelled noisy at 50 %.)
void applyCorroborationShift(QList<Finding> &findings,
                             const QSet<QString> &noisyRules);

// Render a single ROADMAP fold-in block. Pure string templating;
// caller does the file IO + ID allocation. Subsection shape per
// roadmap-format.md § 3.8 (Findings fold-in subsections); per-bullet
// fields (Kind / Source / Lanes / status emoji) per § 3.5 (Bullet
// structure) so the block parses cleanly on next
// ROADMAP::renderHtml() call.
//
// Output shape:
//   ### 🔍 Audit fold-in (YYYY-MM-DD)
//   - 📋 [ANTS-N] **<one-line theme from finding>**
//     <body bullet from finding.message + file:line + rule>
//     Kind: audit-fix.
//     Source: audit-YYYY-MM-DD.
//     Lanes: <lane derived from finding.file path>.
//
// Each finding maps to one bullet. Caller pre-allocates IDs.
QString templateRoadmapFoldInBlock(
    const QList<Finding> &actionable,
    const QList<int> &allocatedIds,
    const QString &dateIso /* YYYY-MM-DD */);

} // namespace AuditEngine
```

### 2.5 New `RoadmapFoldIn` helper (`roadmapfoldin.{h,cpp}`)

```cpp
namespace RoadmapFoldIn {

// Allocate N consecutive IDs from <projectPath>/.roadmap-counter
// under flock. Returns the list of allocated integers (e.g.
// [1255, 1256, 1257]) on success; empty list on flock acquisition
// failure or counter-file IO error.
//
// Crash-safe: the counter is bumped *atomically* via
// QSaveFile::commit() before the return — so even if the caller
// crashes before writing the bullet block, the IDs are still
// reserved (a re-run won't double-allocate). The cost is the
// reserved-but-never-used slot in the ID space; mitigation is the
// caller's responsibility (typically: never crashes between this
// call and the ROADMAP write because both are seconds apart).
QList<int> allocateIds(const QString &projectPath, int n);

// Atomic insert of `block` (a fully-formed `### …` fold-in subsection,
// per roadmap-format.md § 3.8) into <projectPath>/ROADMAP.md, placed
// IMMEDIATELY AFTER the named release-block heading line.
//
// `releaseBlockHeading` MUST be the exact first-line text of an
// existing `## ` heading in ROADMAP.md (e.g.
// `"## 0.7.88 — audit fold (target: 2026-05)"`). The helper searches
// for a line equal to `releaseBlockHeading` (after `rstrip("\n")` of
// any trailing newline the caller may have included) and inserts
// `block` on the line directly following.
//
// Caller picks the heading. The dialog's "Fold actionable" modal
// pre-fills `releaseBlockHeading` via `findActiveReleaseHeading()`
// (returns the first heading body matching `(target: …)` for the
// in-flight case, or the most-recent shipped heading otherwise) and
// the user can edit before confirm. If the named heading does NOT
// exist in the file, `insertBlock` returns false WITHOUT writing —
// the user is shown a "no such heading; please create it in
// ROADMAP.md first" dialog. The helper does NOT auto-create release
// headings; that is policy (which version, which target date),
// not mechanics.
//
// Each call appends a new `### …` subsection under the named
// heading — non-idempotent by design (each call allocates fresh
// IDs and writes a fresh dated block).
//
// Algorithm:
//   1. Read ROADMAP.md into memory.
//   2. Locate `releaseBlockHeading` via exact-line match. Return
//      false if not found.
//   3. Insertion offset = end of that heading line + 1 (i.e. start
//      of the next line).
//   4. QSaveFile to a sibling tmp file with the block inserted,
//      preserving the source file's existing permissions
//      (typically 0644 for ROADMAP.md — see § 9).
//   5. commit() — atomic rename.
// Returns true on success, false on any IO error or heading-not-found.
bool insertBlock(const QString &projectPath,
                 const QString &releaseBlockHeading,
                 const QString &block);

// Locate the "active" release block in <projectPath>/ROADMAP.md.
// "Active" = first `^## ` heading whose body matches
// `\(target:\s*\d{4}-\d+\)` (in-flight). If none match, returns the
// first `^## ` heading whose body matches `^\d+\.\d+\.\d+\s*—`
// (most-recent shipped). If neither matches, returns empty string —
// the caller surfaces "no recognisable release block found."
//
// Returns the FULL heading line (e.g.
// `"## 0.7.88 — audit fold (target: 2026-05)"`) so the caller can pass it
// straight to insertBlock.
QString findActiveReleaseHeading(const QString &projectPath);

} // namespace RoadmapFoldIn
```

### 2.6 New inline-suppress alias

`commentSuppresses` regex (auditdialog.cpp:2055) gains the
`audit:\s*drop(?:-next-line|-file)?` alternative. The semantic is
identical to the existing `ants-audit:\s*disable…` token — the same
parser code runs. Coexistence: both forms continue to work
indefinitely; CHANGELOG entry mentions the new short form. No
deprecation of the long form.

**Collision-prevention.** The bare prefix `audit:` is generic
enough to occur in unrelated comments (e.g. `// audit: 0/55
actionable…` at auditdialog.cpp:4242 — prose, not a directive).
Two layers of defence already exist for the existing
`ants-audit: disable` token, which the new `audit: drop` alias
inherits:

1. The **verb constraint** `\s*drop` after `audit:` (just as
   `\s*disable` confines matches for `ants-audit:`). Comments
   like `// audit: see ANTS-1111` or `// audit: 0/55 actionable`
   never match.
2. The **rule-list parser** at `auditdialog.cpp:2083-2107`
   (existing code). After the regex matches, the suffix is
   parsed for a rule-id list. If the suffix is empty (or
   starts with `--`), bare suppress fires (line 2071). If the
   suffix contains tokens, they are split and matched against
   the finding's rule. A comment like `// audit: drop the
   redundant arg here` produces tokens `["the","redundant","arg",
   "here"]` — none match a real rule (e.g. `clazy-X`),
   so `commentSuppresses` returns false (line 2107). The
   only over-match window is a literally-bare `// audit: drop`
   in non-directive prose, which is contrived enough to accept.

INV-12 locks the negative cases that are mechanically possible
but should still not match.

### 2.7 Widened `.audit_allowlist.json` scope

Today, `AuditDialog::allowlisted(Finding &)` is called only on
custom grep-rule findings (the post-filter loop in `runAudit()`).
This spec moves the call into `handleCheckOutput` so it runs on
every finding regardless of detector. Schema unchanged
(`{rule, path_glob, line_regex, reason}`); semantics widened to
"matches any finding's checkId, file path, and source line." Existing
files keep working — the file format does not change.

## 3. Algorithm

### 3.1 New triage pipeline order

The current `handleCheckOutput` order (CLAUDE.md module map) is:

```
OutputFilter → parseFindings → mark .audit_suppress → drop
generated-file → drop/shift path_rules → drop allowlist →
drop inline-suppress → drop non-recent → dedup →
comment/string filter → mypy-stub fold → cap →
enrichment (snippet ±3, git blame, confidence 0-100) →
trend → render + SARIF v2.1.0 / HTML
```

After this spec ships, the order becomes:

```
OutputFilter → parseFindings → mark .audit_suppress → drop
generated-file → drop/shift path_rules → drop allowlist (widened
to all detectors) → drop inline-suppress (now also recognises
"audit: drop") → drop non-recent → dedup → comment/string filter
→ mypy-stub fold → cap → enrichment → applyCorroborationShift
(NEW, after enrichment so coverageCount is settled) → trend →
render + SARIF v2.1.0 / HTML
```

Two changes: the allowlist drop moves earlier (was per-rule loop,
now in the main pipeline), and `applyCorroborationShift` lands
between enrichment and trend.

### 3.2 Fold-into-roadmap workflow

1. User clicks **"Fold actionable into ROADMAP"** button.
2. Dialog computes the actionable set:
   `[f for f in m_findingsByKey.values() if f.aiVerdict == TRUE_POSITIVE or f.confidence >= 70]`,
   filtered by current visibility.
3. Modal opens with N rows (one per finding), each with a
   checkbox (default checked), the rule, file:line, and message.
4. User confirms (or unchecks specific rows and confirms).
5. Dialog calls `RoadmapFoldIn::allocateIds(projectPath, K)`
   where K is the confirmed count.
6. Dialog calls `AuditEngine::templateRoadmapFoldInBlock(confirmed,
   allocatedIds, todayIso)` — pure templating, no IO.
7. Dialog calls `RoadmapFoldIn::insertBlock(projectPath, block)`.
8. On success, a status-bar message: *"Folded K findings into ROADMAP
   (allocated [ANTS-N] … [ANTS-N+K-1])."* The actionable findings
   are NOT auto-suppressed — the user can still see + triage them.

### 3.3 Allow-this-finding workflow

1. User clicks per-finding **"Allow this finding"** in the
   expanded panel.
2. One-line dialog prompts for `reason`.
3. Dialog appends one entry to `<projectPath>/.audit_allowlist.json`
   atomic-rewrite via QSaveFile:

   ```json
   {
     "rule": "<f.checkId>",
     "path_glob": "<dirname(f.file)>/<basename(f.file)>",
     "line_regex": "<escaped exact match of source line at f.line>",
     "reason": "<user input>"
   }
   ```

4. Dialog reloads `m_allowlist` and calls `renderResults()` —
   the just-allowed finding disappears from the list.

The schema is the existing `AllowlistEntry`; only the *write* path
is new (today the file is hand-edited).

## 4. Invariants (locked by feature tests)

- **INV-1.** `applyCorroborationShift` lifts severity by exactly
  one tier when `coverageCount(f) >= 2`. Two distinct checkIds
  citing `(file, line)` qualifies; same checkId firing twice does
  not. Clamps to BLOCKER.
- **INV-2.** `applyCorroborationShift` drops severity by one tier
  when the finding's checkId is in `noisyRules` AND
  `coverageCount(f) == 1`. Clamps to INFO.
- **INV-3.** `applyCorroborationShift` is a no-op for findings
  whose checkId is not in `noisyRules` AND `coverageCount(f) == 1`.
- **INV-4.** `detectProjectFrameworks` returns `["flask"]` for a
  project containing `requirements.txt` with `flask` on a line.
  Returns `["react"]` for `package.json` with `"react"` in
  `dependencies`. Returns multi-element list when multiple match.
  Returns `[]` for an empty project.
- **INV-5.** `templateRoadmapFoldInBlock` emits a block whose first
  line is `### 🔍 Audit fold-in (<dateIso>)` and whose first bullet
  starts with `- 📋 [ANTS-<id>]`, where `<id>` is the first element
  of `allocatedIds`. Subsequent bullets use `allocatedIds[1..K-1]`
  in order.
- **INV-6.** `RoadmapFoldIn::allocateIds` is atomic under flock —
  two concurrent callers get disjoint ID ranges. (Locked via
  fork+race test.)
- **INV-7.** `RoadmapFoldIn::insertBlock` is atomic — a kill-9
  during the write either leaves ROADMAP.md untouched or with the
  block fully inserted. (Locked via tmp-file presence assertion +
  size invariant on a forced abort.)
- **INV-8.** `RoadmapFoldIn::insertBlock(projectPath, heading,
  block)`:
  - **Heading found:** `block` is inserted on the line
    immediately following the line whose text exactly equals
    `heading`. Fixture ROADMAP carries a `## 0.7.88 — TBD
    (target: 2026-05)` heading; the post-write file has
    `block` on the next line.
  - **Heading not found:** the helper returns false without
    modifying the file. Locked by a fixture call with a
    deliberately-wrong heading; assert false return + byte-equal
    file unchanged.
- **INV-8b.** `RoadmapFoldIn::findActiveReleaseHeading(projectPath)`
  prefers the first `^## ` heading whose body matches
  `\(target:\s*\d{4}-\d+\)` (in-flight). On a fixture with both
  in-flight and shipped headings, returns the in-flight one. On a
  fixture with only shipped headings, returns the first one (the
  most-recently-listed shipped block). On an empty fixture,
  returns empty string.
- **INV-9.** `commentSuppresses("audit: drop=foo-bar", "foo-bar")`
  returns true; `commentSuppresses("audit: drop=foo-bar", "baz")`
  returns false; `commentSuppresses("audit: drop", "anything")`
  returns true. Same semantics as the existing `ants-audit:`
  alternative.
- **INV-10.** Widened allowlist: `allowlisted(f)` returns true for
  a finding whose checkId is *not* a custom grep rule (e.g.
  `clazy-X`) when the JSON contains a matching entry. Locked by a
  fixture that adds an entry for a clazy rule and asserts the
  filter applies.
- **INV-11.** "Since baseline" filter pill: when on, only findings
  whose `(file, line)` appears in `m_recentLines` AND whose
  fingerprint is NOT in `m_baselineFingerprints` are kept.
- **INV-12.** `audit:`-prefix collision negatives:
  `commentSuppresses("audit: see ANTS-1111", "x")` and
  `commentSuppresses("audit: 0/55 actionable", "x")` both
  return false (regex requires the verb `drop`).
  `commentSuppresses("audit: drop the redundant arg here", "x")`
  also returns false — the rule-list parser at
  `auditdialog.cpp:2083` consumes the suffix tokens and finds no
  match for `"x"`. The tails that fire bare-suppress are
  (a) literally empty (`// audit: drop` with no further text)
  and (b) `--`-prefixed (`// audit: drop -- TODO revisit`),
  per the `tail.isEmpty() || tail.startsWith("--")` branch at
  `auditdialog.cpp:2071`. Both are directive shapes by design,
  matching the existing `ants-audit: disable` semantic.
- **INV-13.** "Allow this finding" file-write contract: clicking
  Allow on finding F appends exactly one entry to
  `<projectPath>/.audit_allowlist.json` whose
  `(rule, path_glob, line_regex)` triple matches F; on next
  `runAudit()` F is silently dropped from the visible set. The
  write is atomic (QSaveFile). Locked by a feature test that
  drives the headless append + reload cycle.
- **INV-14.** Fold-into-roadmap orchestration: clicking
  "Fold actionable into ROADMAP" with K confirmed findings
  results in (i) `RoadmapFoldIn::allocateIds(projectPath, K)`
  invoked exactly once, (ii) `templateRoadmapFoldInBlock` invoked
  exactly once with the K findings + K allocated IDs, (iii)
  `RoadmapFoldIn::insertBlock` invoked exactly once with the
  templated string. The post-condition is that `.roadmap-counter`
  has advanced by K and `ROADMAP.md` contains the new
  `### 🔍 Audit fold-in (DATE)` subsection. Locked headlessly by
  exercising the orchestration helper directly (the QPushButton
  slot is a thin wrapper).

## 5. Memory + perf budget

| Item | Cost | Notes |
|---|---|---|
| `applyCorroborationShift` | O(N) where N = total findings; one extra pass over the list, plus a hashmap of `(file:line)` → `Set<checkId>`. | Negligible — N per check is capped at `kMaxFindingsPerCheck` (100, per `auditdialog.h:308`); total N depends on how many checks the dialog has registered (variable; `populateChecks()` registers ~20-40 hardcoded checks plus any from `audit_rules.json`). Even at 50 checks × 100 findings = 5000, the corroboration pass is microseconds. |
| `detectProjectFrameworks` | One-shot probe at audit-run start; reads up to 6 small files (requirements.txt, pyproject.toml, package.json, CMakeLists.txt, Cargo.toml, go.mod). | Cached in `audithygiene` for the lifetime of the AuditDialog — second `runAudit()` doesn't re-probe. Cache invalidated on dialog destruction. |
| `RoadmapFoldIn::insertBlock` | One full read of ROADMAP.md (~10-200 KiB) + one full write. | Sub-millisecond; user-driven, not in any hot path. |
| Widened allowlist | One extra hash-table lookup per finding (already O(N) over `m_allowlist` size; widened scope doesn't change algorithmic cost). | Negligible. |
| Per-finding "Allow" button | One QSaveFile rewrite of `.audit_allowlist.json` per click. | User-driven, not hot. File is small (typically < 50 entries × ~200 B = 10 KiB). |

Total RAM cost: < 100 KiB additional state in AuditDialog (the
framework cache + the corroboration map, both transient). No
unbounded growth — both reset per audit run.

## 9. Security / lifecycle

- `RoadmapFoldIn::insertBlock` writes via QSaveFile, **preserving
  the source ROADMAP.md's existing permissions** (typically 0644 —
  ROADMAP.md is checked into git and world-readable). Helper reads
  permissions via `QFile::permissions()` before write, applies them
  to the QSaveFile target after `commit()`. The 0600 convention
  used by `.audit_allowlist.json` and `config.json` does NOT apply
  here — those files hold per-user state, ROADMAP.md is shared
  source.
- The "Allow this finding" prompt's `reason` text is JSON-escaped
  before being written (QJsonValue handles this). Free-form text
  is not eval'd anywhere. `.audit_allowlist.json` keeps its existing
  0600 perms (per-project user state).
- `detectProjectFrameworks` reads files inside `projectPath` only;
  resolves symlinks via `QFileInfo::canonicalFilePath` and rejects
  any result that escapes `projectPath` — same defense as
  `resolveProjectPath` in auditdialog.
- "Triage with AI" remains off-by-default behind `Config::aiEnabled`
  (`config.cpp:734`). This spec does NOT enable it; it only adds
  the fold-into-roadmap and allow-this-finding affordances next to
  the existing AI-triage button.
- Fold-into-roadmap allocates IDs *before* writing the block.
  If the write fails (disk full, permissions), the IDs are still
  consumed — the next run picks up from the new counter value.
  Wasted IDs are an accepted cost (cheaper than a two-phase commit
  for a sub-second user-driven operation).
- `RoadmapFoldIn::allocateIds` uses `::flock(fd, LOCK_EX | LOCK_NB)`
  on the `.roadmap-counter` file, adopting the same advisory-lock
  pattern as `ConfigWriteLock` (`configbackup.h:82-117`). Two
  concurrent callers serialise; the loser polls (50 ms × 100, 5 s
  budget) before failing.

### Why split?

- v1 covers the **mechanical bulk** — the engine work that any
  consumer (dialog, IPC, MCP) can reuse. Per ADR-0003 dec 2 this
  is the highest-leverage payload.
- v2 is **dialog-side polish** — non-trivial QtWidgets work
  (~300-400 LoC) that benefits one consumer (AuditDialog).
  Splitting keeps 0.7.88 small and tight; v2 can land once the
  user has shipped 0.7.88 and confirmed the engine layer behaves
  as expected.
- The v1 + v2 totals match the original ~1450 LoC spec budget;
  the split is timing, not scope-cut.
