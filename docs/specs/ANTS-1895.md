# ANTS-1895 — Dry-run / phantom mode for the auto-model switcher

**Status:** accepted (2026-05-28). Cold-eyes loops 1+2+3+4+5+6+7
folded; user gated stop at loop 7 with remaining clarifications
deferred to implementation time.
**Kind:** implement.
**Source:** ROADMAP.md ANTS-1895 (in-session-2026-05-26 — ANTS-1891
brainstorm; trust-building gap surfaced once §8 OQ-3's "default-ON
flip" gate showed the chicken-and-egg problem: the switcher needs
measured outcomes to earn trust, but the user has to flip it ON
*first* to start measuring — at which point the switcher is
already mutating their live sessions).

**Layman:** A "preview mode" for the auto-switcher. With it on, Ants
watches your sessions exactly as the real switcher would, decides
what it *would* switch to, but never actually changes the model.
After a few days you can look at the scorecard and see what the
switcher *would have* done — if you trust the picks, flip the real
switcher on. Like watching the cruise control's recommendations on a
road trip before letting it take the wheel.

**Pairs with:** ANTS-1894 (near-miss telemetry — dry-run uses the
same emit-on-signature-change throttle pattern + the `mode:` arm
convention on `model_switch_stats`). **Composes with:** ANTS-1735
§2.3 firing path (the firing branch is skipped under dry-run; the
ledger append is replayed with `trigger:"dry_run"`).
**Hard-depends on ANTS-1893 landing first:** dry-run reuses
`emitSwitchSurfacing` and `m_undoSwitchBtn` (added by ANTS-1893)
and so cannot ship until ANTS-1893 is merged. Recommended merge
order in the same release cycle: 1893 → 1895 → 1896.

## 1. Problem

The auto-model switcher's two states are binary:

- **OFF** (default): no decide, no ledger record, no
  `model_switch_stats` data. `headline` reads `"auto-switch OFF"`
  forever; the §8 OQ-3 "default-ON flip" gate never trips because
  no measurements accumulate. The user has zero observability into
  *what the switcher would do* without flipping it on.
- **ON**: live `/model` injection on the user's running session.
  The switcher mutates the very thing the user doesn't trust it
  with yet. If a switch is wrong, the user has to undo it
  (ANTS-1893 makes that one click — but the disruption already
  happened).

The trust loop is broken at exactly the place where the user wants
to *audit* the switcher's judgement before granting it real
authority. The user's framing of the gap, captured in
`feedback_model_switch_stats_each_session.md`: "I want to see how
often it would have fired" — observable today only by reading the
near-miss ledger (ANTS-1894), which records when it *didn't* fire
but blocked — not when it *would have* fired (no blockers).

The recommender's silent-agreement case (`target == g.current`)
remains a near-miss via the `target_equals_current` blocker
token (ANTS-1894 INV-9) — `decide()` sets `act=false` via that
blocker (the post-1894 evaluate-all gate records the blocker
and continues; `act` ends up false when ANY blocker token is
appended), so neither live nor dry-run produces a "fired"
record in that case. The
silent-agreement count thus lives in ANTS-1894's near-miss
ledger (where it belongs — the recommender did NOT recommend a
change), NOT in this spec's `would_have_fired` series. The
`would_have_fired` ledger is strictly "what *changes* would
have happened" — every dry-run record has `to_tier !=
from_tier`. The agreement signal is read from
`model_switch_stats` mode:near_misses, not from
mode:firings.dry_run.would_have_fired.

## 2. Surface

Six concerns. Pure-infra additive — no new MCP tools (one
extension of `model_switch_stats`'s default envelope + one new
trigger value on the existing ledger schema). The firing-side
path bit-for-bit unchanged in the `off` and `on` modes; the new
`dry_run` mode is the only new behaviour.

### 2.3 Ledger — `trigger:"dry_run"` records

The firing ledger (`ModelSwitchLedger::Record` —
`src/modelswitchledger.h:39`) has a `trigger` field that today
takes the value `"auto"`. Add `"dry_run"` as a second valid
value. No schema change to the JSON; the existing
`toJson`/`fromJson` already round-trip the field as an opaque
string.

A dry-run record's other fields:

- `ts` — same `nowIso8601()` as live.
- `sessionId` — same `lastHookSessionId()`.
- `project` — same `shellCwd()`.
- `fromTier` — `tierName(dec.currentTier)`.
- `toTier` — `tierName(dec.recommendedTier)`. The
  silent-agreement case (`target == g.current`) never reaches
  this branch because the gate emits a `target_equals_current`
  near-miss instead — so every dry-run firing record has
  `toTier != fromTier` by construction. Consistent with §1's
  framing.
- `scoreReason` — `rec.reason`.
- `trigger` — `"dry_run"`.
- `outcome.pending` — TRUE on the first write.

**Outcome backfill.** A dry-run record's outcome is
*meaningful* in the limited sense that the *live* session is
still on `fromTier`; the assistant turns after the dry-run
"would-have-switched" ts are observed on the un-switched tier.
The fill-in helper (`computeOutcome` —
`src/modelswitchledger.h:128`) compares `fromTier`/`toTier`
against the transcript's observed tiers; for a dry-run record
the `toTier` tier was never actually selected, so
`turnsOnToTier` measures turns whose `modelId` aliases to
`toTier` — typically ZERO (the user is still on `fromTier`).

This is the SHADOW measurement: a dry-run record's
`turnsOnToTier == 0` is *expected* and tells us the switcher
would have moved to `toTier`. The new headline (§ 2.6) reads
those zero-`turnsOnToTier` dry-run records as "would have
downgraded N turns to Haiku" by counting the *fromTier* turns
that elapsed before the dwell ended — exactly the count of
turns the LIVE switcher would have run on `toTier` had it
fired.

Implementation: `computeOutcome` is **unchanged**. The dry-run
record's pending → settled transition follows the same rules
(at least one subsequent auto-switch on the same project OR
≥ 5 post-switch assistant turns OR quiet-window settlement per
ANTS-1891). The aggregator in § 2.6 segregates dry-run records
by `trigger` and computes the dry-run-specific counters there;
the per-record `computeOutcome` stays generic.

**Throttling.** The dry-run firing path uses the same dwell
floor + ticks_stable gating as live (the gate ran for both
modes — same blockers, same evaluation order). So a dry-run
"would have fired" event fires at the same cadence as live —
typically once per 90 s minimum dwell window. No new throttle.

### 2.4 `emitDryRunPhantomSwitch` — controller helper

New private method on `ClaudeStatusBarController`:

```cpp
void ClaudeStatusBarController::emitDryRunPhantomSwitch(
        const ModelAutoSwitch::Decision &dec,
        const ModelAutoSwitch::Gate     &gate,
        const QString                   &scoreReason,
        const QString                   &projectRoot,
        qint64                           nowMs)
{
    ModelSwitchLedger::Record r;
    r.ts          = ModelSwitchLedger::nowIso8601();
    r.sessionId   = m_integration ? m_integration->lastHookSessionId()
                                  : QString();
    r.project     = projectRoot;
    r.fromTier    = ModelRecommender::tierName(dec.currentTier);
    r.toTier      = ModelRecommender::tierName(dec.recommendedTier);
    r.scoreReason = scoreReason;
    r.trigger     = QStringLiteral("dry_run");
    r.outcome.pending = true;
    ModelSwitchLedger::appendRecord(
        ModelSwitchLedger::defaultLedgerPath(), r);

    // §2.5 surfacing — ANTS-1893's emitSwitchSurfacing helper, with
    // a dry-run banner; reuses toast + chip-pulse (no Undo, since
    // there's nothing to undo).
    emitDryRunSurfacing(dec, gate, scoreReason, projectRoot, nowMs);

    // Update only the LIVE state we use to drive the next tick.
    // The dwell tracker (m_autoSwitchLastMs) AND the stability
    // counter (m_autoSwitchTicksStable) are updated so dry-run
    // events respect the configured min-dwell + hysteresis between
    // phantom firings, just like live. m_autoSwitchLastTier is
    // INTENTIONALLY NOT updated — that field encodes "the tier we
    // last injected to the PTY" and the dry-run path never injected.
    // A subsequent dry_run → on mode flip would otherwise read a
    // stale "last tier" that never actually fired, confusing the
    // ANTS-1893 Undo bookkeeping. INV-3's behavioural assertion
    // hinges on this gap.
    m_autoSwitchLastMs      = nowMs;
    m_autoSwitchTicksStable = 0;
    // m_autoSwitchLastTier  — DELIBERATELY UNCHANGED under dry-run.
}
```

**Test seam accessor.** Public on `ClaudeStatusBarController`,
sibling to the existing `lastOverrideMsForProject` at
`claudestatuswidgets.h:144`. Read-only, O(1), const. Returns
the current value of `m_autoSwitchLastTier` (empty when the
controller has never fired a live switch this process):

```cpp
// claudestatuswidgets.h — new public accessor

```

```cpp
// claudestatuswidgets.cpp — definition near lastOverrideMsForProject

{
    return m_autoSwitchLastTier;
}
```

The `lastOverrideMsForProject` cool-down is NOT seeded by
dry-run records — there's no override to record (the user never
saw a switch fire, so they never overrode one). The cool-down
slot stays at -1 unless a real live override happens. The
fill-in path (`fillPendingLedgerOutcomes`) IS still consulted on
dry-run records to populate their `pending → settled` outcome;
the `userOverrideWithin5` field on a dry-run record reflects
whether the user manually `/model`'d during the window, but
those overrides are not auto-switch overrides (no auto switch
happened), so they don't bump the cool-down per ANTS-1890 INV-7
(the cool-down seed gate is `fill.outcome.userOverrideWithin5
&& !fill.outcome.pending` — both must be true, AND the record's
`trigger` must be `"auto"`; add this third check).

Concretely, `fillPendingLedgerOutcomes` at
`claudestatuswidgets.cpp:1687` becomes:

```cpp
if (fill.outcome.userOverrideWithin5 &&
        !fill.outcome.pending &&
        r.trigger == QStringLiteral("auto")) {    // ANTS-1895 — dry-run excluded
    const qint64 tsMs = ModelSwitchLedger::parseIso8601Ms(r.ts);
    qint64 &slot = m_lastOverrideMsByProject[r.project];
    if (tsMs > slot) slot = tsMs;
}
```

**Bootstrap path same patch.** `seedOverrideCacheFromLedger` at
`claudestatuswidgets.cpp:1705` walks the same condition
(`!r.outcome.userOverrideWithin5 || r.outcome.pending` → skip)
but does NOT filter by `trigger`. Without the same filter, a
restart would re-seed `m_lastOverrideMsByProject` from settled
dry-run records on disk and silently violate INV-6. Apply the
mirroring patch to the seed loop:

```cpp
for (const ModelSwitchLedger::Record &r : recs) {
    if (!r.outcome.userOverrideWithin5 || r.outcome.pending) continue;
    if (r.trigger != QStringLiteral("auto")) continue;    // ANTS-1895
    const qint64 tsMs = ModelSwitchLedger::parseIso8601Ms(r.ts);
    qint64 &slot = m_lastOverrideMsByProject[r.project];
    if (tsMs > slot) slot = tsMs;
}
```

Both production callers (the live fill-in at L1687 and the
bootstrap seed at L1705) carry the same trigger filter; the
test `test_dry_run_no_cooldown_seed.cpp` (INV-6) drives BOTH
paths to lock the symmetry.

### 2.5 `emitDryRunSurfacing` — preview banner toast + pulse

A dry-run "would have fired" event is silent by default — the
whole point is non-intrusive. BUT a user actively running the
dry-run preview *wants* to see what the switcher would do, in
real time, alongside their work. A separate sub-toggle:

- `claude.auto_model_dry_run_preview_enabled` (bool, default
  **true**) — shows the dry-run toast + pulse. When false,
  records still accumulate to the ledger; only the live UI
  surfaces are suppressed.

When enabled, `emitDryRunSurfacing` reuses ANTS-1893's
surfacing primitives:

- **Toast** — body `tr("Ants would switch: %1 → %2 (%3) —
  preview")` with the same 6 s timeout. Distinct wording so the
  user can't confuse a dry-run preview with a real switch.
- **Chip-pulse** — same `m_modelStateBtn` pulse (600 ms accent
  border). The pulse is identical to live, because the chip's
  *visual cue* is "the switcher fired" — distinguishing real
  vs preview is the toast's job.
- **Undo button** — NOT shown for dry-run. There's nothing to
  undo (no `/model` injection happened); the existing
  `m_undoSwitchBtn` from ANTS-1893 stays hidden.

When `claude.auto_model_toast_enabled` is FALSE the dry-run
toast is also suppressed (the master per-surface mute applies
across both modes); same for `chip_pulse_enabled`.

### 2.6 `model_switch_stats` — dry-run aggregation + headline

The MCP envelope (per ANTS-1891 + ANTS-1894) carries
`switches`, `downgrades`, `upgrades`, `opus_turns_avoided`,
`regret_count`, `regret_rate`, etc — all aggregated from
records with `trigger:"auto"`. Add a sibling `dry_run` block
that aggregates `trigger:"dry_run"` records using the same
counters:

```json
{
  "switches": 2,
  "downgrades": 2,
  "regret_rate": 0,
  // … existing live fields …
  "dry_run": {
    "would_have_fired": 14,
    "would_have_downgraded": 12,
    "would_have_upgraded": 2,
    "would_have_avoided_opus_turns": 8,
    "would_have_clean_end_count": 3,
    "would_have_weighted_avoided": 9.5,
    "would_have_regretted_count": 1,
    "would_have_regret_rate": 8.33,
    "measured_would_have_downgrades": 12,
    "dry_run_headline_floor": 10
  }
}
```

The `would_have_clean_end_count` field is the dry-run analogue
of the live `clean_end_count` per ANTS-1891 INV-5; it feeds
the `would_have_weighted_avoided` algebra
(`would_have_weighted_avoided = would_have_avoided_opus_turns
+ 0.5 * would_have_clean_end_count` — same shape as live, just
prefixed). The example values above satisfy that formula:
`8 + 0.5 × 3 = 9.5`.

**Field-name discipline.** Every counter inside the `dry_run`
sub-object carries the `would_have_` prefix (or, for the floor
constant, the `dry_run_` prefix on the inner key) so a caller
flattening the envelope into a flat keymap never collides with
a same-name live key. The renames vs the earlier draft:
`weighted_avoided` → `would_have_weighted_avoided`;
`headline_floor` → `dry_run_headline_floor`. Document this
naming rule in the descriptor so future fields auto-comply.

The dry-run block carries the SAME shape as the live block —
just renamed with the `would_have_` prefix to reflect the
counterfactual. Wide consumers (the end-of-session summary in
`feedback_model_switch_stats_each_session.md`) can read both
side-by-side: live "auto-switch ON: avoided 3 Opus turns,
0 regret" *vs* dry-run "would have avoided 8 Opus turns, 1
regret".

**Headline composition.** `statsEnvelope` (in
`ModelSwitchLedger::statsEnvelope` — `src/modelswitchledger.h:158`)
constructs the human headline. **`StatsConfig` gains a `QString
mode` field** (`"off"|"on"|"dry_run"`, default `"off"`) so the
envelope builder can branch on it without knowing about the
config layer:

```cpp
// src/modelswitchledger.h — StatsConfig extended (additive)
struct StatsConfig {
    bool    switchEnabled = false;
    QString floorTier     = QStringLiteral("haiku");
    int     minDwellSec   = 90;
    QString scope         = QStringLiteral("project");
    QString mode          = QStringLiteral("off");   // NEW — ANTS-1895
};
```

`statsForScope` (`src/modelswitchledger.h:162`) at the MCP
dispatch site is updated to populate `cfg.mode` from
`Config::claudeAutoModelMode()` before calling `statsEnvelope`.
The envelope builder picks the headline shape from `cfg.mode`:

- `mode=="off"` → unchanged `"auto-switch OFF"`.
- `mode=="on"` → unchanged ANTS-1891 logic (insufficient data /
  full breakdown).
- `mode=="dry_run"` → new headline:
  - 0 dry-run records: `"auto-switch DRY RUN (floor=haiku): no
    phantom switches yet"`.
  - < `dry_run_headline_floor` measured (envelope field —
    same constant value as the live `kHeadlineFloorMeasured`
    at `src/modelswitchledger.h:28`, namespaced under the
    dry_run block to keep the flat-keymap discipline per
    § 2.6's prefix rule): `"auto-switch DRY RUN: would have
    switched N times — insufficient data (M/F measured)"`.
  - ≥ floor: `"auto-switch DRY RUN: would have avoided N Opus
    turns, K regret (R%)"`.

The headline is informative without claiming an action took
place. The "DRY RUN" label is in caps so a quick visual scan
distinguishes it from live.

## 3. Invariants

- **INV-2** — `mode == "on"` is bit-for-bit identical to pre-1895
  behaviour. The firing branch sends `/model` to the PTY AND
  writes a ledger record with `trigger:"auto"`. Surfaces fire per
  ANTS-1893. *Test:* `tests/features/auto_switch_dry_run/test_mode_on_unchanged.cpp`.
- **INV-3** — `mode == "dry_run"` runs the same `decide()` as live,
  but on `act=true` skips the `sendToPty` AND writes a ledger
  record with `trigger:"dry_run"` instead. The PTY receives ZERO
  bytes from the dry-run branch. *Test:*
  `tests/features/auto_switch_dry_run/test_dry_run_no_pty_write.cpp`
  asserts the behaviour via TWO behavioural signals (no new
  PTY-mock infrastructure — that's out of scope for this spec):
  (a) `lastAutoSwitchTierForTest()` (new public accessor on
  `ClaudeStatusBarController`, declared in § 2.4 alongside the
  existing `lastOverrideMsForProject` test-seam accessor) is
  updated under mode="on" but NOT under mode="dry_run" (per §
  2.4 the dry-run branch intentionally leaves the underlying
  `m_autoSwitchLastTier` field unchanged — see the comment in
  `emitDryRunPhantomSwitch`); the test reads this accessor;
  (b) the ledger gains exactly one `trigger:"dry_run"` record
  per phantom firing — test asserts via the existing
  `ModelSwitchLedger::readRecords` API.
- **INV-4** — A dry-run record's `trigger` field is exactly
  `"dry_run"` (lower-case snake). Live records keep
  `"auto"`. The two values are the v1 enum; never rename or
  renumber. *Test:* `tests/features/auto_switch_dry_run/test_trigger_taxonomy.cpp`.
- **INV-5** — `fillPendingLedgerOutcomes` runs `computeOutcome`
  on dry-run records using the same rules as live; the resulting
  outcome reflects the *un-switched* session (the user stayed on
  `fromTier`). Settlement transition (`pending → !pending`)
  follows the same triple-OR rule as live (subsequent auto-switch
  OR ≥ `kOutcomeWindowTurns` post-switch assistant turns OR quiet
  end). *Test:*
  `tests/features/auto_switch_dry_run/test_fill_in_settles_dry_run.cpp`.
- **INV-6** — A dry-run record's `userOverrideWithin5` MAY be
  true (the user manually `/model`'d during the 5-turn window),
  but does NOT seed `m_lastOverrideMsByProject` — the cool-down
  is a live-switch concept (the user only overrides switches
  they *saw*; a dry-run record's switch never reached them).
  BOTH cool-down-seed call-sites carry the same
  `r.trigger == "auto"` filter: (a) the live fill-in path at
  `claudestatuswidgets.cpp:1687` (the
  `fillPendingLedgerOutcomes` post-compute seed); (b) the
  bootstrap seed at `claudestatuswidgets.cpp:1705`
  (`seedOverrideCacheFromLedger`, run once at controller
  construction). Without the same filter at the bootstrap site,
  a restart would resurrect settled-dry-run-record overrides as
  cool-down history and silently violate the invariant. *Test:*
  `tests/features/auto_switch_dry_run/test_dry_run_no_cooldown_seed.cpp`
  drives both paths — appends a settled dry-run record, calls
  `seedOverrideCacheFromLedger` (bootstrap), asserts
  `lastOverrideMsForProject == -1`; then calls
  `fillPendingLedgerOutcomes` (live path), asserts the same.
- **INV-7** — `Config::claudeAutoModelMode()` returns the
  validated value of `claude.auto_model_switch_mode`. An absent
  key with `claude.auto_model_switch=true` reads as `"on"`; an
  absent key with `claude.auto_model_switch=false` reads as
  `"off"`. An unknown value (typo / hand-edit / downgrade) reads
  as `"off"`. The `claudeAutoModel()` envelope carries the
  derived `switch_enabled == (mode == "on")` field for back-compat
  callers. *Test:*
  `tests/features/auto_switch_dry_run/test_config_mode_back_compat.cpp`
  (covers both the accessor and the envelope's `switch_enabled`
  derivation in one).
- **INV-8** — `Config::setClaudeAutoModelSwitch(true)` writes
  `claude.auto_model_switch_mode = "on"` AND
  `claude.auto_model_switch = true`. The two on-disk fields are
  kept in lockstep on every write through the bool setter. A
  string setter `setClaudeAutoModelMode("dry_run")` writes
  `claude.auto_model_switch = false` (the bool is FALSE for any
  non-"on" mode). *Test:*
  `tests/features/auto_switch_dry_run/test_config_setters_lockstep.cpp`.
- **INV-9** — `emitDryRunSurfacing` emits its toast iff
  `claude.auto_model_toast_enabled && claude.auto_model_dry_run_preview_enabled`
  are BOTH true. The Undo button is never shown for a dry-run
  event. *Test:*
  `tests/features/auto_switch_dry_run/test_dry_run_surfacing_mutes.cpp`.
- **INV-10** — `model_switch_stats` envelope carries the
  `dry_run` sub-object (§ 2.6) when ANY `trigger:"dry_run"`
  records exist in scope. When zero dry-run records exist, the
  sub-object is still present with all counters at zero. The
  presence guarantee mirrors ANTS-1894 INV-12 for `near_misses`.
  *Test:* `tests/features/auto_switch_dry_run/test_stats_dry_run_block_present.cpp`.
- **INV-11** — `model_switch_stats`'s headline reflects the
  active mode. `mode=="dry_run"` produces a "DRY RUN"-prefixed
  headline (§ 2.6). `mode=="off"` → unchanged `"auto-switch
  OFF"`. `mode=="on"` → unchanged ANTS-1891 headline. *Test:*
  `tests/features/auto_switch_dry_run/test_headline_per_mode.cpp`.
- **INV-12** — A user flipping mode `off → dry_run` mid-session
  starts accumulating dry-run records on the next 2 s status
  tick; switching `dry_run → on` mid-session leaves the
  accumulated dry-run records in place + starts writing
  `trigger:"auto"` records alongside. No data loss on a mode
  flip; in particular, the in-flight dwell counter
  (`m_autoSwitchLastMs`) and stability counter
  (`m_autoSwitchTicksStable`) carry across the *flip itself* —
  they reflect controller-state, not mode-state. Subsequent
  firings (live OR dry-run) reset both counters per the
  pre-existing live rules — this is correct, not a reset-on-flip.
  Ledger records are never re-tagged or evicted on a mode flip.
  *Test:*
  `tests/features/auto_switch_dry_run/test_mode_transition_no_loss.cpp`.
- **INV-13** — `statsEnvelope`'s dry-run
  `would_have_avoided_opus_turns` and
  `would_have_weighted_avoided` use the SAME computation as
  the live `opus_turns_avoided` and `weighted_avoided` per
  ANTS-1891 INV-5 (`weighted_avoided = opus_turns_avoided +
  0.5 * clean_end_count`).
  **Dry-run "measured" rule (different from live):** the
  live `measured_downgrades` denominator excludes records
  with `turnsOnToTier == 0 && !any-signal` (per ANTS-1891).
  Applying that rule verbatim to dry-run records would zero
  the denominator — dry-run records ALWAYS have
  `turnsOnToTier == 0` because the live tier stayed on
  `fromTier`. The dry-run rule replaces "turns-on-to-tier"
  with "any meaningful outcome signal": a dry-run record
  counts toward `measured_would_have_downgrades` iff
  `outcome.pending == false` AND
  (`userOverrideWithin5 || correctionSignalWithin5 ||
  underRouteSignalWithin5 || sessionCleanlyEndedOnNewTier`).
  Pending records and settled-but-no-signal records are
  `inconclusive_would_have_count`. *Test:*
  `tests/features/auto_switch_dry_run/test_dry_run_weighted_avoided.cpp`
  drives one of each kind and verifies the denominator counts
  the right subset.

## 4. RAM / build cost

- **Disk:** dry-run records share the firing ledger
  (`~/.cache/ants-terminal/model-switch-ledger.jsonl`, 256 KiB
  cap, drop-oldest). A dry-run record is ~250-300 bytes (same
  shape as a live record). With a typical 90 s min-dwell + 8 h
  active session, ≤ 320 dry-run records per day; cap pressure
  arrives in ~3 days of continuous dry-run use. The drop-oldest
  policy means the ledger always reflects the most-recent
  ~3 days of dry-run data — acceptable for a trust-building
  audit window.
- **RAM (per process):** no new per-tab or per-project state.
  The `mode` local is read once per tick (one Config read,
  ~1 ms). The `emitDryRunPhantomSwitch` helper is a stack-only
  function with no member state beyond what `refreshAutoModelSwitch`
  already maintains (`m_autoSwitchLastMs`, etc).
- **CPU per tick:** identical to live's gate evaluation (the
  decide() path is shared between dry-run and live). The
  per-firing cost is the SAME ledger-append round trip (sub-ms
  on a 256 KiB cap with the existing drop-oldest implementation
  + QSaveFile atomic write). The live path's extra cost
  (`sendToPty` byte-write) is SKIPPED in dry-run.
- **CPU on `model_switch_stats`:** the existing
  `statsEnvelope` iterates the record list once; adding the
  dry-run sub-object adds one more pass over the SAME list,
  filtered by `trigger == "dry_run"`. The two passes can be
  unified with a single filter-on-trigger pass that writes to
  two accumulators — implementation detail, both are linear in
  records.
- **Build cost:** ~80 lines added to
  `claudestatuswidgets.cpp` (`emitDryRunPhantomSwitch` +
  `emitDryRunSurfacing` + the mode branch in
  `refreshAutoModelSwitch`), ~30 lines on `config.{h,cpp}` (the
  mode accessor/setter + the `claudeAutoModel()` derivation),
  ~80 lines on `modelswitchledger.cpp` (dry-run aggregation
  block + headline-per-mode). 4 new accessors / setters on
  `Config`. Test bundle: ~13 new `.cpp` files in
  `tests/features/auto_switch_dry_run/`, ~600 lines, all on
  `test_claude` (controller-touching) and `test_core` (pure
  ledger + stats). No new `add_executable`.

## 6. Migration / compatibility

- **No on-disk migration of the ledger.** The `trigger` field
  already exists (`"auto"`); `"dry_run"` is just a new valid
  value. Old records keep `"auto"`. The aggregator handles both.
- **Config schema additive.** The new
  `claude.auto_model_switch_mode` key is read with
  back-compat fall-through (§ 2.1) — a pre-1895 config with
  `claude.auto_model_switch=true` reads as
  `mode="on"`. No data loss.
- **`claudeAutoModel()` envelope.** Gains a new `mode` key while
  KEEPING the `switch_enabled` boolean. Existing readers of
  `switch_enabled` are unaffected (still bool, still TRUE iff
  mode=="on").
- **`model_switch_stats` envelope.** Gains a `dry_run`
  sub-object. Existing readers (the end-of-session
  `model_switch_stats` summary; consumers in
  `claudeintegration.cpp` MCP dispatch) ignore unknown keys per
  the standard JSON-tolerance pattern. ETag bumps when dry-run
  records change.
- **Settings dialog.** The single bool checkbox at
  `src/settingsdialog.cpp` becomes a tri-state radio. A user
  opening Settings on first run after upgrade sees the radio
  with "Off" or "On" pre-selected (per back-compat fall-through);
  no surprise migration.
- **Downgrade asymmetry.** A user who selects `dry_run` mode
  via the new tri-state setter, then later downgrades to a
  pre-1895 binary, lands on OFF (not ON) — the pre-1895
  reader only sees `claude.auto_model_switch=false` (which
  the new setter writes for any non-"on" mode). This is
  intentional: a pre-1895 binary cannot honour dry-run
  semantics, so falling back to OFF (no live `/model`
  injection) is safer than ON (which would surprise the
  user with live behaviour they didn't opt into).

## 9. Design decisions (resolved, not OQ)

- **D-1: Dry-run records share the firing ledger** (not a
  separate file). The 256 KiB cap holds ~3 days of dry-run; the
  aggregator filters by `trigger`, so lost dry-run records on
  eviction reduce the dry-run counters proportionally — not a
  correctness issue. Users wanting longer audit windows can
  revisit in a follow-up ID.

- **D-2: A `dry_run → on` mode flip does NOT retro-tag past
  dry-run records as `"auto"`.** Retro-tagging would obscure the
  audit window — the records stay `trigger:"dry_run"` forever.
  The `statsEnvelope` aggregator filters by trigger; live and
  dry-run history sit on their respective sides.

- **D-3: Per-process dwell tracker is shared between modes.**
  Flipping `dry_run → on` mid-session does NOT reset
  `m_autoSwitchLastMs` (the dwell counter). Dwell is a property
  of the user's attention pattern, not the mode. Locked by
  INV-12.

- **D-4: First-run nudge does NOT fire under dry-run mode.**
  The gate at `claudestatuswidgets.cpp:1342` reads `!enabled`,
  which under this spec is `mode == "off"`. Dry-run users have
  already opted in by selecting dry-run; re-prompting would
  duplicate the choice.

- **D-5: `mode` is overloaded across two namespaces — config
  envelope key vs MCP-tool arm.** `claudeAutoModel()` carries
  `mode: "off"|"on"|"dry_run"` (this spec); `model_switch_stats`
  carries `mode: "firings"|"near_misses"` (ANTS-1894). Different
  namespaces (config envelope vs tool-call argument); no risk
  of mutual confusion at the dispatch sites (`config.cpp` vs
  `claudeintegration.cpp`). Renaming the config key to
  `claude.auto_model_state` was considered (frees `mode` for
  the MCP-tool-arg sense exclusively) — rejected because the
  ON-DISK key name `claude.auto_model_switch_mode` is already
  bound by this spec's back-compat fall-through (a v1 user's
  config carries that name); renaming it would require a
  separate migration. Disambiguate in prose by always referring
  to "config `mode`" / "envelope `mode`" or "tool-arg `mode`"
  when both might be in scope.

- **D-6: `claude.auto_model_dry_run_preview_enabled` is exposed
  BOTH via the §2.7 Settings checkbox AND as a directly-editable
  config-file key.** Mirrors ANTS-1735's `claude.auto_model_switch`
  which is BOTH a Settings toggle AND a config-file-only key —
  consistency wins, minor redundancy is acceptable.
