# ANTS-1236 — RoadmapDialog v2: keyboard-shortcut cheatsheet

- **Status:** 📋 Spec draft 2026-05-11. Cold-eyes-clean after 7
  loops + ~27 findings fixed (audit trail in `ROADMAP.md`
  § "📝 Cold-eyes 2026-05-12"). Pending user sign-off; on
  sign-off, advance the ROADMAP bullet from 📋 → 🚧 (already
  advanced 💭 → 📋 by this spec sweep).
- **Source:** roadmap-v2 research synthesis 2026-05-11 (Linear,
  GitHub, Notion all expose shortcut overlays via `?`); user
  keyboard-first / partially-sighted workflow.
- **Lanes:** roadmapdialog (key event handler), roadmapshortcutsdialog
  (new module).
- **Kind:** implement (additive — one new modal, one new key
  handler, no changes to existing behaviour).

## 1. Problem

The Roadmap dialog has accumulated four keyboard shortcuts over
its lifetime — `F5` (Refresh), `Esc` (Close), `Ctrl+C` (Copy
selection), `Ctrl+A` (Select All) — plus Qt's built-in
`QTextBrowser` scroll keys (`↑`/`↓`/`PgUp`/`PgDn`/`Home`/`End`)
and `Tab`/`Shift+Tab` focus traversal. The cheatsheet renders
these as nine table rows: the four named shortcuts get one row
each, the scroll keys collapse into three (`↑ ↓`, `PgUp PgDn`,
`Home End`), `Tab`/`Shift+Tab` collapse into one, plus a row for
`?` itself = 9 at first ship; ANTS-1234 added `/` on 2026-05-11
bringing the total to 10 (per § 4 INV-1). None of them are
discoverable; the dialog has no menu bar, no tooltip surfaces them,
and the `Refresh` button is the only one whose UI hints at a
keyboard binding (`setShortcut(Qt::Key_F5)` makes Qt render the
shortcut in the button's tooltip / native shortcut hint).

A keyboard-first user has to read the source to find them. A
partially-sighted user who relies on keyboard navigation (rather
than mouse) gets nothing — the existing shortcuts are usable but
invisible.

Linear, GitHub, Notion, and most modern keyboard-first tools have
converged on `?` (Shift+/) opening a static cheatsheet overlay
that lists every shortcut. Cheap to add, immediately discoverable
once a user tries `?` out of habit.

## 2. Mechanism — what was investigated, what was chosen

### 2.a Rejected — tooltip-only discovery

Adding `setToolTip("F5 — refresh")` to each button surfaces some
shortcuts but:
- Tooltips only appear on hover; keyboard-only users never see them.
- Most shortcuts (`Ctrl+C`, `Esc`, scroll keys) don't have a button
  to attach to.
- Tooltip text is announced inconsistently across screen readers.

### 2.b Rejected — `?` opens README section in a browser

Linking out to documentation has two problems: (a) requires
network/browser, breaks the offline-by-default character of the
dialog; (b) the canonical list lives in the README, which would
drift from the code.

### 2.c Chosen — sub-dialog with a static table, populated from a
file-scope data table that doubles as the authoritative source

Key decisions:

1. **`?` opens a `RoadmapShortcutsDialog`** — a small `QDialog`
   parented to `RoadmapDialog`, modal to the parent (not
   application-modal). Contains a `QTableWidget` with two columns
   (`Shortcut`, `Action`) and a `Close` button.

2. **Data table is the single source of truth.** A file-scope
   `kRoadmapShortcuts[]` array of `{const char *keys; const char *
   action;}` rows lives in `roadmapdialog.cpp`. The sub-dialog
   reads it directly. Tests grep the same symbol to lock the
   contents against drift. New shortcuts (future ANTS items) MUST
   add a row to this table or fail the regression test.

3. **`?` opens the dialog; pressing `?` again or `Esc` closes it.**
   We override `RoadmapDialog::keyPressEvent` and match on
   `event->text() == QLatin1String("?")` rather than
   `event->key() == Qt::Key_Question` — the `text()` route is
   layout-robust because it carries the resolved character
   regardless of whether `?` was reached via Shift+/ on US/UK/DE,
   AltGr+something on Polish, or a dead-key sequence elsewhere.
   Both routes coincide on the common layouts (US, UK, DE) per
   Qt's documented `QKeyEvent` behaviour; the `text()` match
   additionally catches layouts where Qt does not emit
   `Key_Question`. Verification on a non-Latin layout is § 8's
   re-open condition. For the cheatsheet dialog itself, `Esc` is
   already wired by `QDialog::reject`; we additionally override
   its `keyPressEvent` so the same `?` test closes it (toggle).

4. **The dialog is created lazily and reused.** First `?` press
   constructs the dialog (held in a `QPointer<RoadmapShortcutsDialog>
   m_shortcutsDialog` member); subsequent presses call `show()` /
   `raise()` / `activateWindow()`. Closing it leaves the instance
   alive — re-open is instant. Destroyed with the parent.

5. **Accessibility (per ANTS-1235 lessons):** the dialog uses
   `QTableWidget` (native Qt widget, exposes
   `QAccessibleItemViewInterface`) — no HTML metadata fragility.
   Column headers and cell text reach screen readers directly via
   `QAccessibleTableInterface`. The dialog itself gets
   `setWindowTitle(tr("Roadmap Keyboard Shortcuts"))` and
   `setAccessibleName(tr("Roadmap keyboard shortcuts overlay"))`.

6. **Visual styling** inherits from the parent dialog's stylesheet
   (Qt cascade applies app-level QSS to child widgets
   automatically), but the `RoadmapShortcutsDialog` also applies
   the same `bgPrimary` / `accent` / `fg` palette colours its
   parent uses. The theme name is passed in the constructor (the
   parent supplies its own `m_themeName` member) so the overlay
   matches the four navy/dracula/light/dark themes the rest of the
   dialog honours.

### 2.d Out of scope

The roadmap proposal suggested adding `j`/`k`/`Enter` navigation
and number-key tab jumps. **Those are separate work** — adding new
shortcuts changes the surface this cheatsheet documents, but it
doesn't follow that ANTS-1236 has to ship them. Future roadmap
entries (suggested IDs ANTS-1244, 1245) can add navigation; each
will add one row to `kRoadmapShortcuts` and the cheatsheet picks
it up automatically.

## 3. Fix

### 3.a New header: `src/roadmapshortcutsdialog.h`

```cpp
#pragma once
#include <QDialog>
#include <QString>
class QKeyEvent;

class RoadmapShortcutsDialog : public QDialog {
    Q_OBJECT
public:
    RoadmapShortcutsDialog(const QString &themeName,
                           QWidget *parent = nullptr);

protected:
    void keyPressEvent(QKeyEvent *event) override;
};
```

### 3.b New source: `src/roadmapshortcutsdialog.cpp`

Constructor builds a `QTableWidget` with two columns, populates it
from `roadmapShortcutRows()` (an `extern` accessor exposed by
`roadmapdialog.cpp` — see §3.c), applies the theme palette, and
wires a `Close` button. Override `keyPressEvent` so an event whose
`event->text() == QLatin1String("?")` calls `accept()` (toggle
off) — the same layout-robust route §3.d uses on the parent.

### 3.c Data table in `src/roadmapdialog.cpp`

Add a file-scope table near the existing `kStatusLabels`
(ANTS-1235), plus an accessor `roadmapShortcutRows()` that the
sub-dialog calls:

```cpp
struct ShortcutRow {
    const char *keys;    // pass-through: key glyphs / modifier abbreviations
    const char *action;  // tr()-translatable: English prose
};

constexpr ShortcutRow kRoadmapShortcuts[] = {
    {"?",         QT_TR_NOOP("Show this cheatsheet")},
    {"Esc",       QT_TR_NOOP("Close dialog")},
    {"F5",        QT_TR_NOOP("Refresh from disk")},
    {"Ctrl+C",    QT_TR_NOOP("Copy selection")},
    {"Ctrl+A",    QT_TR_NOOP("Select all")},
    {"↑ ↓",       QT_TR_NOOP("Scroll one line")},
    {"PgUp PgDn", QT_TR_NOOP("Scroll one page")},
    {"Home End",  QT_TR_NOOP("Jump to top / bottom")},
    {"Tab Shift+Tab", QT_TR_NOOP("Move focus to next / previous control")},
};
```

Only the `action` column goes through `tr()`. Keys stay
untranslated to match `QKeySequence::toString(PortableText)` —
Qt's default `NativeText` would translate modifier names, which
is the wrong shape for a cheatsheet. Same translation pipeline as
the ANTS-1235 labels for the action column only.

The accessor returns a `QVector<QPair<QString, QString>>` (the
two-column rendering shape):

```cpp
QVector<QPair<QString, QString>> roadmapShortcutRows() {
    QVector<QPair<QString, QString>> out;
    out.reserve(std::size(kRoadmapShortcuts));
    for (const auto &row : kRoadmapShortcuts)
        out.append({QString::fromUtf8(row.keys),
                    RoadmapDialog::tr(row.action)});
    return out;
}
```

### 3.d Key handler in `RoadmapDialog`

Override `keyPressEvent`:

```cpp
void RoadmapDialog::keyPressEvent(QKeyEvent *event) {
    if (event->text() == QLatin1String("?")
        && !(event->modifiers() & Qt::ControlModifier)
        && !(m_searchBox && m_searchBox->hasFocus())) {
        if (!m_shortcutsDialog)
            m_shortcutsDialog = new RoadmapShortcutsDialog(
                m_themeName, this);
        m_shortcutsDialog->show();
        m_shortcutsDialog->raise();
        m_shortcutsDialog->activateWindow();
        event->accept();
        return;
    }
    QDialog::keyPressEvent(event);
}
```

The `!m_searchBox->hasFocus()` guard is critical: when the search
box has keyboard focus, `?` is a legitimate text character to type
into the substring filter. The QLineEdit's own `keyPressEvent`
runs first (it has focus), so this guard is belt-and-braces — if
focus ever escapes to the dialog while the search box still
"logically" has it, we still don't intercept `?`. The search box
is the only text-input surface in `RoadmapDialog` today; if a
future change adds another (e.g. a second QLineEdit or
QTextEdit), the guard must be widened — either by adding a
sibling `hasFocus()` check or by switching to
`qobject_cast<QLineEdit *>(QApplication::focusWidget())`-style
detection. The spec re-opens (§ 8) on that addition.

### 3.e Build wiring

Add `src/roadmapshortcutsdialog.cpp` to the `ants_dialogs_lib`
STATIC sources list in `CMakeLists.txt` (the block that already
lists `src/roadmapdialog.cpp` alongside the other dialog cpps).
Header file does not need a CMakeLists entry — Qt's automoc + the
lib's `target_include_directories` already cover it.

Add `tests/features/roadmap_shortcuts_cheatsheet/test_roadmap_shortcuts_cheatsheet.cpp`
to the `SOURCES` list inside the existing
`ants_add_gui_bundle(test_dialogs …)` block (alongside the other
`tests/features/roadmap_*/…cpp` entries already in that list).
The `test_dialogs` bundle links `ants_dialogs_lib`, so the new
sub-dialog symbol resolves automatically — no library additions
needed.

## 4. Invariants

- **INV-1.** The data table `kRoadmapShortcuts` lives in
  `src/roadmapdialog.cpp` and has exactly 10 rows at ship (bumped
  from 9 by ANTS-1234 on 2026-05-11 when `/` was added) — one for
  each currently-shipped shortcut. A future shortcut addition
  MUST bump the row count and the test count in lock-step (see
  INV-8); the test asserts an exact count, so a mismatched
  addition is a build failure.
- **INV-2.** `roadmapShortcutRows()` returns one entry per
  `kRoadmapShortcuts` row, in declaration order, with the keys
  column rendered as `QString::fromUtf8(row.keys)` (bypassing
  `tr()`, since key glyphs are universal) and the action column
  rendered as `RoadmapDialog::tr(row.action)`.
- **INV-3.** Pressing `?` on the dialog (without the search box
  focused) opens `RoadmapShortcutsDialog`. Pressing `?` again or
  `Esc` closes it.
- **INV-4.** With the search box focused, `?` is appended to the
  search predicate verbatim (and rebuild runs). The cheatsheet
  does NOT open.
- **INV-5.** The cheatsheet `QTableWidget` has two columns
  (`Shortcut`, `Action`) and exactly `std::size(kRoadmapShortcuts)`
  rows (the literal count is owned by INV-1; the test assertion
  by INV-8). Cell text matches
  `QString::fromUtf8(kRoadmapShortcuts[i].keys)` (bypassing
  `tr()`, since key glyphs are universal) and
  `RoadmapDialog::tr(kRoadmapShortcuts[i].action)` — the
  qualified call is mandatory because the strings were extracted
  with `QT_TR_NOOP` in `roadmapdialog.cpp` and live in
  `RoadmapDialog`'s translation context, not
  `RoadmapShortcutsDialog`'s.
- **INV-6.** Re-opening the cheatsheet reuses the same instance
  (`QPointer<RoadmapShortcutsDialog>` is non-null after first
  open). The dialog is destroyed with the parent
  `RoadmapDialog` — no orphan windows after parent close.
- **INV-7.** `setWindowTitle(tr("Roadmap Keyboard Shortcuts"))`
  is set so screen readers announce the dialog by name on open.
- **INV-8.** The feature test asserts `roadmapShortcutRows()
  .size() == 10` (exact match, not minimum; was 9 pre-ANTS-1234).
  A future shortcut
  addition that doesn't bump both the data table AND this test
  count fails the suite — the test forces the cheatsheet, the
  data table, and the new shortcut to land in one commit. This is
  the source-of-truth contract from §2.c.2: drift is a build
  failure, not a silent gap.

## 5. Test plan

New feature test directory:
`tests/features/roadmap_shortcuts_cheatsheet/`.

`spec.md` — short pointer file referencing this spec.
`test_roadmap_shortcuts_cheatsheet.cpp` — C++ test joining the
existing `test_dialogs` bundle. Data-table assertions need only
QtCore; the keyPressEvent assertions use `QTest::keyClick`
against a real `RoadmapDialog` instance constructed with a
tmpdir roadmap fixture, and the `test_dialogs` bundle already
provides the `QApplication` needed for that GUI half.

Assertions:

1. **Data table:** `roadmapShortcutRows().size() == 10` (exact) and
   the 10 entries match the canonical keys in order: `?`, `/`,
   `Esc`, `F5`, `Ctrl+C`, `Ctrl+A`, `↑ ↓`, `PgUp PgDn`, `Home End`,
   `Tab Shift+Tab`.
2. **Source-grep guards** (match as literal byte sequences, not
   regex — the strings contain spaces and Unicode arrows): the
   source contains `constexpr ShortcutRow kRoadmapShortcuts[]`
   and exactly the ten literal key prefixes `{"?"`, `{"/"`,
   `{"Esc"`, `{"F5"`, `{"Ctrl+C"`, `{"Ctrl+A"`, `{"↑ ↓"`,
   `{"PgUp PgDn"`, `{"Home End"`, `{"Tab Shift+Tab"`, plus a
   `keyPressEvent` override on `RoadmapDialog` (declared in
   `src/roadmapdialog.h`, defined in `src/roadmapdialog.cpp`). The
   action column is asserted indirectly via the table-cell text
   checks below; the grep does not need to assert `QT_TR_NOOP(` on
   every row individually (`std::size(kRoadmapShortcuts)` == 10
   from assertion 1 already locks the row count).
3. **Open via `?`:** construct a `RoadmapDialog` against a
   fixture, `QTest::keyClick(&dialog, Qt::Key_Question)`, assert
   `dialog.findChild<RoadmapShortcutsDialog *>() != nullptr` and
   the child is visible.
4. **Close via `?`:** with the cheatsheet open and focused, send
   `Key_Question` to the cheatsheet, assert it's hidden.
5. **Search-box focus guard:** with the search box focused, send
   `Key_Question`, assert (a) the cheatsheet was NOT opened, and
   (b) the search box text gained a `?` character.
6. **Re-open reuses instance:** first open + close + second open
   yields the same pointer (assert via `QPointer` identity).
7. **Cheatsheet table shape:** assert `QTableWidget *table =
   shortcutsDialog->findChild<QTableWidget *>()` has
   `columnCount() == 2`, `rowCount() == roadmapShortcutRows()
   .size()`, and row 0 contains `?` + the localised "Show this
   cheatsheet" string.
8. **Window-title surfacing:** assert
   `shortcutsDialog->windowTitle() == tr("Roadmap Keyboard
   Shortcuts")`.

## 6. Memory budget

- `kRoadmapShortcuts` data table: 10 rows × ~80 bytes (two pointers
  + null terminators) ≈ 800 bytes, static const, in `.rodata`
  (bumped from 9 rows / ~720 bytes by ANTS-1234).
- `RoadmapShortcutsDialog` instance: QDialog + QTableWidget +
  QPushButton + layout objects. Rough order-of-magnitude estimate
  is tens of KiB (a 9×2 `QTableWidget` with ~120 bytes per
  `QTableWidgetItem` is well under 10 KiB; the surrounding QDialog
  / layout chrome dominates). Verify with `valgrind --tool=massif`
  post-implementation if precision matters; the property under
  test is "bounded, allocated once, freed with parent," not the
  exact byte count. Lazy — only allocated on first `?`. Lives
  until parent destruction. No periodic timers, no file-watcher,
  no caches. One instance per `RoadmapDialog` (which is itself one
  per project root the user opens).
- No persistent state. No Config keys. No disk writes.

## 8. Re-open conditions

- A new shortcut lands without updating `kRoadmapShortcuts` —
  surface a `ROADMAP` follow-up bullet.
- A Qt 7 / Qt 6.10+ release changes the
  `QTableWidget::QAccessibleItemViewInterface` contract — surface
  a screen-reader regression check.
- The user reports that `?` doesn't work on their keyboard layout
  — investigate whether `event->text()` carries `"?"` for the
  reported layout, or whether a dead-key / IME path is swallowing
  the event. If a fallback (e.g.
  `QShortcut(QKeySequence::HelpContents)` / F1) needs to be added,
  add a corresponding row to `kRoadmapShortcuts`, bump the
  size-9 invariants (INV-1, INV-5, INV-8) to the new count, and
  update the §5.1 / §5.2 enumerations — the source-of-truth
  contract from §2.c.2 forbids an undocumented binding.

## 9. Out of scope

- New navigation shortcuts (`j`/`k`/`Enter`/number-key tab jumps).
  Those are separate roadmap entries; each will add a row to
  `kRoadmapShortcuts` when implemented.
- Cheatsheet for the main terminal window. The terminal's
  shortcut surface is documented in `README.md` § Shortcuts; a
  parallel cheatsheet dialog there is a separate roadmap proposal
  if the user wants it.
- A "print cheatsheet" action. The user can copy table text via
  `QTableWidget` selection + Ctrl+C (Qt default behaviour).
