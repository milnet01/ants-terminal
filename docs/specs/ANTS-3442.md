# ANTS-3442 — `feedback_log op:"prune_tracking"`: drop superseded duplicate maintainer tracking rows

**Status:** Accepted (cold-eyes converged, 2026-07-04) — ready to implement
**Kind:** enhancement
**Source:** user-request-2026-07-04 (compact + dedup the `*_Ants_MCP_Feedback.md` files)

## 1. Problem

The cross-session `*_Ants_MCP_Feedback.md` files accumulate a **maintainer
tracking table** every triage. As an item progresses 📋 → 🚧 → ✅ across
sessions, the **same `ANTS-NNNN` id gets a fresh row in table after table** —
so a single id can carry 3–6 duplicate rows scattered down the file, each an
older snapshot of a status the last row already supersedes.

`compact_shipped` (ANTS-3421) shortens one contributor *write-up* block to a
stub, but it does **not** touch these repeated tracking rows. After a session's
finding is compacted, its id still appears in every prior tracking table — the
"references for completed items later in the file" the user asked to remove.
This is the deduplication half of the bulk-cleanup gap tracked by the parent
ANTS-3442 roadmap bullet; this spec scopes the tracking-row-dedup op. (The
multi-finding-block collapse half is a sibling, deferred — §5.) The spec id
`ANTS-3442` intentionally matches the bullet id even though it covers one half;
§7 keeps the parent bullet open (or split under a follow-up id) until both
halves ship, so spec↔roadmap stays reconciled.

### 1.1 Why keep the LAST row per id (not the first)

ANTS-3371 already declares the authoritative rule: *"later rows supersede
earlier ones for the same id."* `feedback_query include_tracking` and
`compact_shipped`'s gate-5 both resolve an id's status from the **last**
document-order row. So the last row is the one source of truth; the earlier
rows are stale snapshots. Pruning therefore keeps the last row per id and drops
the earlier duplicates — the final ✅ status is preserved, and every downstream
reader already ignores the dropped rows.

## 2. Surface

`feedback_log op:"prune_tracking"` (maintainer). Pure helper
`FeedbackFile::pruneTracking(content, opts)` does the parse + row selection +
rewrite; the `cmdFeedbackLog` wrapper (remotecontrol.cpp) handles path
resolution, the `*_Ants_MCP_Feedback.md` suffix guard, PathValidation, the
`caller_cwd` contract, and the atomic `QSaveFile` write — identical plumbing to
`compact_shipped`.

### 2.1 Request shape

| field | req? | meaning |
|---|---|---|
| `caller_cwd` | yes | resolves the feedback file (same as other ops) |
| `op` | yes | `"prune_tracking"` |
| `path` | no | feedback-file path; omit to derive `<leaf>_Ants_MCP_Feedback.md` (ANTS-3376) |
| `scope_ids` | no | restrict pruning to these `ANTS-NNNN` ids; **omit** ⟹ every fully-superseded row. An explicitly **empty** array is `bad_args` (INV-12) — "restrict to nothing" is a no-op the caller almost never means; omit the field instead. (Named `scope_ids`, not `ids`, to avoid collision with a row's own id list.) |
| `dry_run` | no | preview the byte report without writing (default false) |

### 2.2 Row locations (implementation prerequisite)

`FeedbackFile::parse(content)` yields every maintainer tracking-table data row
in document order (`ParseResult::trackingRows`, ANTS-3371), but the current
`TrackingRow` (`feedbackfile.h:28`) carries only `{item, ids, status, notes}` —
**no source line**, and `parse()` (`feedbackfile.cpp:189-202`) does not record
one. Row removal needs the line. **This op therefore extends `TrackingRow` with
a 1-based `int line` populated by `parse()`** (the loop var `li` at
`feedbackfile.cpp:165` is 0-based, so the field is `tr.line = li + 1`); it is
additive and back-compatible with `feedback_query include_tracking`. §7 lists this code-side change. (An
alternative — a private re-scan inside `pruneTracking` — is rejected as a second
parser to keep in sync.)

`parse()` extracts `trackingRows` **only from maintainer-block bodies** — the
extraction loop sits inside the `maintainerIdx` scan (`feedbackfile.cpp:154-204`)
— so a contributor's own `| ID | Status |` table appended at file end is never
pulled into `trackingRows` and is therefore never a prune target. `prune_tracking`
touches maintainer tables exclusively.

### 2.3 What a "removable" row is

Removability is a **two-stage pass** over the original parse (each stage's set
is precomputed once — no iteration), so it is order-independent and non-circular.

**Stage 1 — mark `id-superseded` rows.** A data row `R` is *marked* iff **all**
of:

1. `R.ids` is non-empty — a row with `ids == n/a` carries prose only, no id to
   supersede, so it is never marked (INV-4). This preserves narrator rows.
2. For **every** id in `R.ids`, some **later** (strictly greater document
   order) data row's `ids` also contains that id — i.e. `R` is **fully
   superseded**. A multi-id row is unmarked if it is the last occurrence of
   **any** one of its ids (INV-3), so no id ever loses its authoritative last
   row. This test reads only the parsed id column, so it is order-independent.
3. When `scope_ids` is given: **every** id in `R`'s **ID column** (`R.ids`) is
   in the set (INV-6). Notes-cell ids do not affect scoping — Stage 2
   independently guarantees no id (column or notes) is ever lost, so scoping
   only needs to bound which rows are *candidates*.

**Stage 2 — remove marked rows that lose no `mappedId`.** `parse()`'s id scan
runs over the **whole line** of every maintainer-block line (`feedbackfile.cpp:167`),
so an id can live in the `notes` cell — or even in prose / a heading — not just
the id column. Define the **surviving line set** = every maintainer-block line
that is **not** a Stage-1-marked data row (fixed before any removal — this is
what breaks the loop-2 circularity). A marked row `R` is **removed** iff every
`ANTS-NNNN` token anywhere in `R`'s source line also appears in at least one
surviving line. Thus `parse(after).mappedIds == parse(before).mappedIds`
(INV-2b): a notes-cell (or prose) id whose only occurrences are all
Stage-1-marked rows pins every one of those rows (§2.6, INV-2b). The surviving
set is computed once over the original parse, so removing rows bottom-up is
correct (INV-7). This is deliberately **conservative**: because pinned (kept)
rows are excluded from the surviving set, a marked row whose only other
id-occurrences are all in *other* pinned rows is itself kept, even though
removing it would still preserve `mappedIds`. That leaves a few bytes on the
table but is what guarantees idempotency (§2.6) — do not "optimise" it by
re-adding survivors mid-pass.

### 2.4 The rewrite

- Remove exactly the source lines of the removable rows, **bottom-up** (highest
  line first) so earlier removals don't shift not-yet-removed line numbers.
  Header + `|---|` separator rows and all non-table lines (heading, note prose,
  sentinel breadcrumb) are untouched.
- **A tracking table whose data rows are all removed keeps its header +
  separator** (an empty table), and **no maintainer heading, header row, or
  `|---|` separator is ever removed** — so the set of maintainer headings and
  the un-triaged **delta text** are byte-identical before and after (INV-5).
  Note that the numeric `lastMaintainerLine` *legitimately decreases* when rows
  above the final heading are removed; the invariant is delta-text preservation,
  not line-number equality.
- A table that loses its only 4-column (notes-bearing) rows keeps a 4-column
  header over now-3-column data. GFM renders this fine (extra header cells are
  ignored), and equalising the header width is a non-goal for v1 — the rows are
  the byte win, and a header rewrite risks the heading/separator invariants.
- Contributor blocks, fenced code, and the H1 title are never entered (INV-8).

### 2.5 Response envelope

```
{ ok, op:"prune_tracking", path, dry_run,
  rows_removed,                 // count
  bytes_saved,                  // Σ bytes of removed row lines (+ newline)
  removed:[ {ids, status, line} … ],   // each pruned row's id list, original 1-based line
  scope_ids:[…]|null,           // echo of the request scope_ids, or null
  path_derived }                // true when `path` was omitted + derived (ANTS-3376), parity with compact_shipped
```

On no removable row (present file): `ok:true, rows_removed:0, bytes_saved:0,
removed:[]` — a clean no-op, not a refusal (parity with `compact_shipped`'s
empty apply). This applies equally when `scope_ids` names an id absent from the
file: no row matches, so `rows_removed:0`. An **absent file** is different — it
refuses `not_found`, exactly as `compact_shipped` does (`remotecontrol.cpp:10769-10773`);
the empty-apply no-op is only for a present file with nothing to prune (INV-13).

### 2.6 Idempotency

A second `prune_tracking` on the output removes nothing (`rows_removed:0`). Every
surviving row is surviving for a reason that still holds on re-run: it is either
**not Stage-1-marked** (last occurrence of one of its ids, or an `n/a` row) or
**Stage-2-pinned** (a marked row whose notes/prose id has no other occurrence —
still true after the pass, since only non-pinning rows were removed). So no
survivor becomes removable on the next pass (INV-9). Same safety property the
user asked about for `compact_shipped`.

### 2.7 Worked example (before → after)

```
## 📋 … tracking update (2026-06-01, maintainer)
| Item | IDs | Status |
| --- | --- | --- |
| First look        | ANTS-0001          | 📋 |
| Batch A + B        | ANTS-0002, ANTS-0003 | 📋 |

## 📋 … tracking update (2026-06-15, maintainer)
| Item | IDs | Status |
| --- | --- | --- |
| Started           | ANTS-0001          | 🚧 |
| B done            | ANTS-0003          | ✅ |
| Prose note        | n/a                | ✅ |

## 📋 … tracking update (2026-07-01, maintainer)
| Item | IDs | Status |
| --- | --- | --- |
| Shipped           | ANTS-0001          | ✅ |
```

Prune removes `First look` (ANTS-0001 has later rows) and `Started`
(ditto). It KEEPS `Batch A + B` (last occurrence of ANTS-0002), `B done` (last
of ANTS-0003), the `n/a` prose row, and the final `Shipped` row. Every heading
+ header + separator stays; `ANTS-0001/0002/0003` all keep their authoritative
last row.

## 3. Invariants

- **INV-1** — `op:"prune_tracking"` is dispatched inside `cmdFeedbackLog`'s op
  switch (parity with `compact_shipped`, `remotecontrol.cpp:10768`) and is
  added to the valid-op guard (`remotecontrol.cpp:10757`); the work is
  m_main-independent (source-grep).
- **INV-2** — a row **all of whose** ids have later duplicate rows is removed
  (and passes Stage 2); the later (authoritative) row(s) survive.
- **INV-2b** — `parse(after).mappedIds == parse(before).mappedIds`: no
  `ANTS-NNNN` is dropped from the file's mapped-id set (a notes-cell id with no
  other occurrence pins its row — §2.3 Stage 2).
- **INV-3** — a multi-id row is kept when it is the last occurrence of **any**
  of its ids (no id loses its authoritative row).
- **INV-4** — an `ids == n/a` (empty-ids) row is never removed.
- **INV-5** — no maintainer heading, header row, or `|---|` separator is
  removed, and the un-triaged **delta text is byte-identical** before and
  after. (The numeric `lastMaintainerLine` may *decrease* when rows above the
  final heading are removed — that is expected, not a violation.)
- **INV-6** — with request `scope_ids:[…]`, a row is *marked* only if every id
  in its **ID column** is in the set. (Notes-cell ids don't affect scoping;
  Stage 2 / INV-2b independently preserves every id.)
- **INV-7** — the Stage-1 marks and the Stage-2 surviving-line set are computed
  once over the original parse; removing marked rows bottom-up never changes
  either, so the selection is order-independent and correct (no circularity —
  the surviving set excludes all marked rows before any removal).
- **INV-8** — contributor blocks, fenced code, and the H1 title are never
  modified.
- **INV-9** — idempotent: a second run removes nothing. Every survivor is
  either not Stage-1-marked or Stage-2-pinned, and stays so on re-run (§2.6).
- **INV-10** — `dry_run:true` returns the identical envelope (minus the write)
  and leaves the file byte-for-byte unchanged.
- **INV-11** — atomic write via `QSaveFile` … `.commit()` (source-grep).
- **INV-12** — bad request → `bad_args` before any parse-driven work: a
  `scope_ids` element not matching `^ANTS-[0-9]+$`, **or** an explicitly empty
  `scope_ids` array (omit the field for "prune everything").
- **INV-13** — an absent feedback file refuses `not_found` (parity with
  `compact_shipped`); the empty-apply no-op is only for a present file.

## 4. RAM / build cost

One extra pure function in `ants_core_lib` (parse is already O(lines); the
selection is O(rows) with a hash of last-index-per-id over the parsed rows,
whose `line` field §2.2 adds). No new allocation class; the whole file is
already resident for the write. No new build target.

### 4.1 Relation to ANTS-3421 §5 ("never compact maintainer tracking blocks")

ANTS-3421 §5 forbids collapsing a maintainer tracking **block** — "their bytes
are the watermark ledger." `prune_tracking` does **not** collapse a block: it
removes *superseded duplicate rows* while keeping every heading, header,
separator, and the last-per-id row, so the watermark ledger (the set of
maintainer headings + each id's authoritative status) is intact. Row-level
dedup is the sanctioned complement to that block-level prohibition, not a
violation of it. It does narrow the "ledger" to *headings + each id's
authoritative (last) status*: the intermediate 📋→🚧 status-transition rows are
intentionally dropped (that history lives in git and under the id's ROADMAP
bullet). The mcp-feedback-files.md:326 amendment (§7) must state this
reinterpretation crisply so the two docs don't drift.

Like every `feedback_log` op, the write is atomic-*replace* (`QSaveFile`) but
not *isolated*: a `prune_tracking` racing a contributor's `append_finding` on
the same file is last-writer-wins (pre-existing to all `feedback_log` ops,
ANTS-3421 §5). `dry_run` never writes, so it never races.

## 5. Out of scope

- **Multi-finding-block collapse** (collapse a `##` session block when every
  `###` finding is ✅) — the sibling half of the parent ANTS-3442 roadmap
  bullet; deferred to its own follow-up id (§7).
- **Rewriting an emptied tracking table away entirely** (heading + note kept as
  above) — a later polish; removing the heading needs watermark-safe handling.
- **Pruning later prose confirmation mentions** ("X verified fixed" sentences in
  contributor blocks) — contributor content is never auto-edited; only
  `compact_shipped` touches contributor blocks, and only as a whole-block stub.

asserting the Stage-2 pass keeps *both* (neither is a surviving line for the
other), so `X` is not dropped.
