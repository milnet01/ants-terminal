# ANTS-3578 — Delta-envelope foundation: content-hash "changed-since" MCP responses (ANTS-3534 / 3544 / 3546)

**Status:** spec draft (2026-07-19); redesigned after cold-eyes loop 1 (§ 10) to a
uniform **content-hash snapshot diff**. Cold-eyes loop log at § 10.
**Kind:** implement.
**Source:** ROADMAP.md ANTS-3578 (`🔌 MCP integration deepening — token + perf`);
in-session-2026-07-19, designed jointly with the user as the shared foundation
for the three "don't re-send unchanged bytes" token-savers ANTS-3534 / 3544 /
3546 (the "caching trio").
**Builds on:** the all-or-nothing **ETag-304** path — `etagFor`
(`src/claudeintegration.cpp:11309`, `hex16(sha256(payload))`), `applyEtagPattern`
(`:11316`), `isEtagSupportedTool` (`:11254`, already lists the four target
verbs), dispatch seam in `onMcpConnection` (`:10576`); the **offload/spill**
content-store — `offloadBody` (`src/mcpspill.cpp:138`, `handle=sha256(body).hex()`),
`shouldOffload` (`:129`, `bytes ≥ 16 KB`), `readSpill` (`:263`), spill caps
(`src/mcpspill.h`, 64 files / 64 MiB); the **process-scoped LRU** pattern —
`m_idempotentReadCache` (`src/claudeintegration.h:593`, cap 32 / TTL 100 ms); one
`QLocalServer` per process (`:1254`); and `CodebaseIndex::StaleSet`
(`src/codebaseindex.h:75`) used **internally** to rebuild the index cheaply.
**Distinct from:** ANTS-3543 (downshift a would-be-truncated list to lean rows —
a within-response saving). This is a cross-response saving.

## 1. Problem

Every read verb's re-poll is all-or-nothing. `etagFor` hashes the **entire**
response envelope, so `applyEtagPattern` answers only "byte-identical → 304" or
"different → whole body again." Three patterns re-pay a full body for a
near-unchanged one:

- **codebase_index** (ANTS-3544) — session bootstrap eagerly refreshes it
  (ANTS-2140) and any one-file edit changes the map; the caller re-pays the whole
  symbol/lane map though almost every file is unchanged.
- **append-only corpora** (ANTS-3534) — `roadmap_query` / `changelog_query` /
  `feedback_query` change by a few entries between polls; the etag flips, so the
  whole list is re-sent.
- **repeated identical reads** (ANTS-3546) — a subagent review loop reads the
  *same* region N times; nothing changed, but with no client cursor every read
  re-pays the bytes (`token_usage` can't see it; ties ANTS-3536).

All three want what the binary 304 can't give: **"send only what changed since the
response I already have."**

**Layman:** When you ask for the same big thing again and only a little changed,
the app re-sends all of it. This adds a shared "here's just what changed" mode for
three features that each waste tokens re-sending data you already have.

**Design note (why content-hash, not cursors).** Cold-eyes loop 1 (§ 10) killed
the first draft's per-corpus cursors: roadmap reorders and flips status *above* any
tail cursor; feedback `compactResolved`/`migrateV2` and changelog `normalize`
rewrite content in place; codebase_index's `StaleSet` is anchored to a shared cache
that any caller overwrites; and a client cannot re-hash the server's canonical body
to verify a delta. The **only** safe, uniform mechanism is: the server keeps a small
**content-hash snapshot** of what it emitted under each etag, and diffs the new
state against that specific snapshot — position-independent, verify-free for the
client, and identical across all four verbs.

## 2. Surface

One shared mechanism (§ 2.1); three adapters that differ only in *how an element is
keyed* (§ 2.2–2.4). Fallback to a full body on any doubt is mandatory, so a delta is
always a pure optimisation.

### 2.1 Shared foundation — content-hash snapshot diff

**(a) A delta-capable verb declares an extractor.** Its response body carries a
dominant array of keyed elements (roadmap `bullets[]`, changelog `entries[]`,
feedback `findings[]`, codebase_index `files[]`). The verb declares
`(arrayField, keyOf(element))` — enough for the foundation to compute an ordered
list of `{key, contentHash = hex16(sha256(canonical(element)))}`. The foundation
owns everything else; the handler owns only its body + this declaration.

**(b) The per-etag base store — first-class, bounded.** Beside
`m_idempotentReadCache`, a `m_deltaBaseStore`: an LRU of
`fullEtag → { verb, snapshot: map<key,contentHash> }`. **Content-hashes only —
never bodies.** Caps: `kDeltaBaseCap` recent etags (low tens) × the per-verb
element count; evicted by LRU + `kDeltaBaseTtlMs`. RAM in § 4.

**(c) Dispatch flow (at the existing `applyEtagPattern` seam, `:10576`).** The
handler returns the **full** body; the foundation then, in order:

1. `fullEtag = etagFor(fullBody)` — always the whole-body hash (unchanged meaning).
2. If `etag_match == fullEtag` → `{ok, unchanged:true, etag:fullEtag}` (today's
   exact-match 304, byte-for-byte unchanged).
3. Else if `etag_match` is **non-empty and present in `m_deltaBaseStore`** for this
   verb → compute `newSnapshot` from the body via the extractor; diff vs the stored
   base snapshot → `added` / `changed` / `removed` by key; emit
   `{ok, delta:{added:[elems], changed:[elems], removed:[keys], unchanged:<count>},
   base_etag:etag_match, etag:fullEtag}`. Store `newSnapshot` under `fullEtag`.
4. Else (empty / unknown / evicted `etag_match`) → emit the **full body** with
   `etag:fullEtag`; store `newSnapshot` under `fullEtag`.

The exact-match 304 (step 2) is checked **before** any delta, so it never collides
with the delta path. The delta is computed **entirely server-side** from two
snapshots the server holds — the client applies `added`/`changed`/`removed` to the
body it already has and never re-hashes anything.

**(d) Fallback is mandatory (INV-4).** Step 4 — unknown/evicted base, a verb with no
extractor, a keyless element (§ 2.4), any uncertainty — returns the full body. A
wrong or lossy delta is never emitted; worst case is today's cost.

**(e) Position independence (INV-6).** Because the diff is over
`{key → contentHash}`, an element that merely *moved* (roadmap reorder), was
*collapsed in place* (feedback compaction), or sits under a *reordered heading*
(changelog normalize) has the **same key and hash** → it is not reported. Only a
genuine content change (status flip, edited text, added/removed element) appears in
the delta. This is what makes every corpus safe without a cursor.

**No new input arg.** The existing `etag_match` string is the cursor (INV-2); a
stale/unknown value falls through to step 4, never `bad_args`.

### 2.2 Adapter A — `codebase_index` (ANTS-3544)

Extractor: `(files[], keyOf = file.path)`; `contentHash` = `hex16` of the file's
serialized symbol block. The caller-facing delta is the **retained-base diff**
(§ 2.1c), **not** `serve()`'s `StaleSet` — `StaleSet` is anchored to the single-slot
on-disk cache that any caller/`session_orient` re-orient overwrites, so it would
silently omit intervening changes. `serve()` still uses `StaleSet` *internally* to
rebuild the index cheaply (re-outline only changed files); the delta then diffs the
freshly-built `files[]` snapshot against the base the caller's `etag_match` names.
Delta payload: `changed`/`added` files carry symbols, `removed` are paths,
`unchanged` is a count. session_orient's eager re-orient replaying its prior index
etag pays only changed-file symbols — the highest-value case.

### 2.3 Adapter B — server-side auto-304 on repetition (ANTS-3546)

The **no-client-cursor** case: dedup identical re-emissions the client didn't ask a
delta for. A bounded `m_emittedEtagLru` (`fullEtag → {stampMs, handle}`, cap
`kEmittedEtagCap` + TTL). Before emitting, if `fullEtag` is in the LRU, return
`{ok, unchanged:true, etag:fullEtag, handle}` instead of the bytes; the caller
re-fetches via `read_spill`. **Re-fetchability (INV-11):** a large body is already
spilled (`shouldOffload`); a **small** body — the § 1 motivating case — is
**spilled on its repeat** (a repetition-triggered spill, independent of the
16 KB size gate) so `read_spill` always works. **Staleness is automatic:** the LRU
key *is* the content hash, so a changed body has a different `fullEtag` and simply
misses the LRU → full body. No per-file mtime tracking (which is undefined for
multi-file bodies) is needed.

### 2.4 Adapter C — append-verb deltas (ANTS-3534)

Same § 2.1 mechanism, one extractor each — all three corpora become uniform and
position-independent (no watermarks):

- **`roadmap_query`** — `(bullets[], keyOf = [ANTS-NNNN] id)`; `contentHash` covers
  status + headline + body. Reorders and status flips diff correctly (INV-6). A
  bullet with **no id** is keyless → keyed by whole-content hash (so it reads as
  removed+added on any change) or, if that is ambiguous, triggers full fallback
  (INV-14).
- **`changelog_query`** — `(entries[], keyOf = (version, category, id-or-text-hash))`.
  `[Unreleased]` `normalize`/`add` reorder or insert in place → the content diff
  handles it; no reliance on a dated boundary.
- **`feedback_query`** — `(findings[], keyOf = finding id / proposed-id)`.
  `compactResolved`/`migrateV2` rewriting a finding above the old watermark shows up
  as a `changed` element (INV-6/13), which a tail watermark would have missed.

Interacts with the ANTS-1117 100 ms roadmap parser cache (the snapshot is extracted
from the same cached parse). Per the ANTS-3534 body, the roadmap delta may not pay
below the offload threshold — see § 5.

## 3. Invariants

### Foundation

- **INV-1** — a delta-capable verb returns exactly one of: full body + `etag`;
  `{unchanged:true, etag}` (exact-match 304); `{delta:{added,changed,removed,
  unchanged}, base_etag, etag}`; or (Adapter B) `{unchanged:true, etag, handle}`.
  `delta` is **truthy-only** (absent otherwise). *Test:* pure test on the dispatch
  helper across the four outcomes; scrape that no verb emits an empty `delta`.
- **INV-2** — the cursor is the existing `etag_match`; **no new input arg**. A
  stale/unknown `etag_match` falls through to a full body, never `bad_args`. *Test:*
  schema scrape (no new prop) + behavioural (unknown etag → full/delta, never error).
- **INV-3** — a delta is computed **server-side** by diffing the new
  `{key→contentHash}` snapshot against the retained base snapshot named by
  `base_etag`; correctness never depends on the client reconstructing or re-hashing
  anything. *Test:* pure — retain a base, mutate one element, diff → exactly that
  element in `changed`, `base_etag` echoed, `etag` = new full hash.
- **INV-4** — when the base is not retained (unknown/evicted), the verb has no
  extractor, or a keyless element makes the diff ambiguous, the verb returns the
  **full body** + fresh `etag` — never a wrong or partial delta. *Test:* behavioural
  — evict the base, re-poll → correct full body, no `delta`.
- **INV-5** — `m_deltaBaseStore` and `m_emittedEtagLru` are each bounded (named
  caps `kDeltaBaseCap` / `kEmittedEtagCap` + TTL) and hold **content-hash sets /
  handles only, never bodies**. *Test:* source-scrape the named caps; a stress test
  that N distinct emissions never grow either store past its cap.
- **INV-6** — the content-hash diff is **position-independent**: an element that
  only moved / was collapsed in place / sits under a reordered heading (same key,
  same hash) is **not** reported; only a real content change is. *Test:* pure —
  reorder + in-place-collapse a snapshot with no content change → empty delta;
  change one element's content → exactly one `changed`.

### Adapter A — codebase_index (ANTS-3544)

- **INV-7** — codebase_index's extractor is `(files[], path)` with a per-file
  content-hash of its symbol block, stable across rebuilds when the file is
  unchanged (relies on deterministic FileOutline symbol order — § 8). *Test:* pure —
  two builds differing in one file share every other file's content-hash.
- **INV-8** — the caller-facing delta diffs the new `files[]` snapshot against the
  **retained base** for `etag_match`, **not** `serve()`'s cache-anchored `StaleSet`
  (which an intervening `serve()` would have advanced); `StaleSet` is used only to
  rebuild the index cheaply. *Test:* behavioural — a `serve()` by another caller
  between two polls does not make the second poll's delta omit a change.
- **INV-9** — a re-orient replaying a retained index etag pays only changed-file
  symbols, not the whole map. *Test:* full-map bytes ≫ delta bytes for a one-file
  change.

### Adapter B — auto-304 (ANTS-3546)

- **INV-10** — the server keeps a bounded `m_emittedEtagLru`; an about-to-emit body
  whose `fullEtag` is in it returns `{unchanged:true, etag, handle}` without the
  bytes. The LRU key is the content hash, so a changed body (different `fullEtag`)
  never yields a stale 304. *Test:* pure on the LRU-hit helper + behavioural (emit,
  re-emit identical → 304; change content → full body).
- **INV-11** — a repeated body is always re-fetchable: large bodies are already
  spilled; a **small** repeated body is spilled on the repeat (repetition-triggered,
  independent of the 16 KB gate) so `read_spill` works — so the small-region-reread
  case (§ 1) IS served. *Test:* behavioural — repeat an identical small read → 2nd
  is a 304 whose `handle` resolves via `read_spill`.

### Adapter C — append-verb deltas (ANTS-3534)

- **INV-12** — roadmap_query / changelog_query / feedback_query each declare a
  `(arrayField, keyOf)` extractor; a delta returns only elements whose content
  changed vs the retained base, by key. *Test:* per verb — add one entry, re-poll
  with the prior etag → delta of exactly that entry.
- **INV-13** — position/rewrite independence: roadmap reorder + status flip,
  feedback `compactResolved`/`migrateV2`, changelog `normalize([Unreleased])` each
  produce a **correct** content diff (real changes in `changed`, moved-unchanged
  elements absent) — no tail watermark, no silent omission. *Test:* behavioural —
  flip status on an early roadmap bullet → it is in `changed` (a tail watermark
  would miss it); compact a feedback finding above the old watermark → `changed`.
- **INV-14** — a keyless element (roadmap bullet with no id) is diffed by
  whole-content hash or triggers full fallback — never silently mis-keyed against a
  different element. *Test:* pure — two id-less bullets swapping content are not
  reported as unchanged.

## 4. RAM / build cost

- **`m_deltaBaseStore`** — LRU of `fullEtag → map<key, hex16-hash>`. Per entry ≈
  (#elements × ~24 B). Bounded by `kDeltaBaseCap` (low tens of etags) × the corpus
  size: codebase_index ~hundreds of files → low KB/entry; roadmap ~1–2 K bullets →
  ~tens of KB/entry. `kDeltaBaseCap = 16` ⇒ worst case **low hundreds of KB total**,
  named and capped, evicted by LRU + `kDeltaBaseTtlMs`. **Content-hashes only, never
  bodies.**
- **`m_emittedEtagLru`** — `fullEtag → {stampMs, handle}`, `kEmittedEtagCap`
  (~32) + TTL. **< a few KB.** (`handle == fullEtag`'s spill name where spilled; the
  value need only carry `stampMs` + a spilled-flag — see § 8.)
- **Spill-on-repeat** (Adapter B small bodies) reuses the existing spill dir (already
  capped 64 files / 64 MiB, swept at 24 h) — no new store.
- **Build:** no new target, no new library. Reuses `QCryptographicHash` (already
  behind `etagFor`) and the spill/LRU machinery.

## 5. Phasing

All three ship on the § 2.1 foundation (user chose the full corrected build).
Cheapest-and-safest first; each lands independently:

1. **Foundation + Adapter A (codebase_index)** — the extractor + `m_deltaBaseStore` +
   the dispatch flow, proven on the highest-value verb (session-bootstrap map).
2. **Adapter B (auto-304)** — `m_emittedEtagLru` + spill-on-repeat, reusing the
   offload path.
3. **Adapter C (append verbs)** — three extractors on the now-proven foundation;
   land **changelog + feedback** first (simplest keys), **roadmap last** (id-plus
   keyless-fallback is the fiddliest, and its saving below the offload threshold is
   the least certain — defer to its own follow-up if it doesn't pay).

Out of scope: a client-side delta-apply library (the client, Claude Code, applies
`added`/`changed`/`removed` itself); any change to the exact-match 304; ANTS-3543's
within-response downshift.

## 6. Tests

Foundation test dir `tests/features/delta_envelope/` (`features;fast`) + per-adapter
coverage folded into each verb's existing suite:

- **Foundation (INV-1..6):** pure tests on the snapshot-diff + dispatch helper —
  the diff correctness (INV-3), fallback (INV-4), bounded stores (INV-5), and
  position-independence (INV-6) are load-bearing; build a base snapshot, apply
  reorder/collapse/change mutations, assert the exact delta.
- **Adapter A (INV-7..9):** pure on the `(files[], path)` extractor + the
  retained-base-vs-StaleSet distinction (INV-8's intervening-`serve()` case is the
  critical one).
- **Adapter B (INV-10..11):** pure on the emitted-etag LRU + spill-on-repeat;
  behavioural small-repeat → 304 whose handle re-fetches.
- **Adapter C (INV-12..14):** behavioural per corpus — the roadmap
  status-flip-above-any-watermark and feedback compaction cases (INV-13) are the
  ones that must be RED against a naive tail-watermark implementation before the
  content-diff is restored.

Each new test must fail against pre-fix source first (project convention).

## 8. Open questions

- **Keyless changelog/roadmap entries.** Some changelog entries and roadmap bullets
  carry no stable id. The `(version,category,text-hash)` / whole-content-hash
  fallback (§ 2.4) keys them, but a pure text edit then reads as remove+add rather
  than `changed` — acceptable (still correct, INV-4/14), or worth a fuzzier key?
  Settle at Adapter-C time.
- **`m_emittedEtagLru` value shape.** Does it need `handle` at all, or just
  `{stampMs, spilled:bool}` (recompute the spill path from `fullEtag`)? Trim at
  implementation.
- **roadmap delta payoff.** Per the ANTS-3534 body: below the offload threshold, is
  the per-bullet hashing worth it, or defer roadmap (INV-4 fallback keeps it correct
  meanwhile)?

## 9. Security boundaries

No new trust boundary. Deltas cross the same authenticated UDS/MCP socket as full
responses (SO_PEERCRED UID + 0700). Spill re-fetch (Adapter B) reuses the existing
0600 content-addressed spill files under `~/.cache`. `etag_match` is an opaque
server-minted token validated by lookup — an unknown value falls through to a full
body (§ 2.1d), never an error path or a file read. Content-hash snapshots hold no
payload, only `hex16(sha256(...))` digests.

## 10. Cold-eyes loop log

**Loop 1** (2026-07-19) — 3 lanes (foundation / codebase_index+auto-304 /
append-verb+scope), strong-model cold read, all findings verified against source.
`CRITICAL 1 · HIGH 4 · MEDIUM 4 · LOW/INFO 5`. **Not converged** — the draft's
"easy cursors / nearly-free" framing did not hold; findings drove the redesign
above (surfaced to the user, who chose the full corrected build).

- **CRITICAL — client cannot verify a delta.** `etagFor` hashes the canonical Qt
  body before injection; the client (a different serializer) can't reproduce it. →
  Redesigned to a server-side content-hash diff; client applies the delta, never
  re-hashes (INV-3). Client-verifiability claim dropped.
- **HIGH — codebase_index `StaleSet` is cache-anchored, not base-anchored**
  (serve() overwrites the single-slot cache every call). → Delta now diffs vs the
  retained per-etag base; `StaleSet` is internal-only (INV-8).
- **HIGH — auto-304 couldn't serve its small-repeat motivation** (spill is
  large-body only). → Repetition-triggered spill-on-repeat for small bodies (INV-11).
- **HIGH — feedback tail cursor unsafe** (`compactResolved`/`migrateV2` rewrite
  above the watermark). → Content-hash diff, position-independent (INV-6/13).
- **HIGH — dispatch seam / full-body-etag threading broken.** → § 2.1c pins the
  order: full-body etag first, exact-match 304 second, delta third.
- **MEDIUM ×4** — INV-1 now includes Adapter B's shape; § 4 base is hash-sets not
  body-snapshots, hard-capped + named; the etag→base map is first-class in § 2.1b
  (not an open question); changelog `[Unreleased]` handled by content diff, no dated
  boundary needed.
- **LOW/INFO** — staleness is now automatic (content-addressed etag, INV-10, so no
  per-file mtime); caps named (`kDeltaBaseCap`/`kEmittedEtagCap`/`kDeltaBaseTtlMs`);
  FileOutline emission-order determinism flagged (§ 8 / INV-7); `m_emittedEtagLru`
  value trimmed (§ 8); § 7 adds the mcp-tools.md quick-ref.
