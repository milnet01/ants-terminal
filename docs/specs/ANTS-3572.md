# ANTS-3572 — MCP tokens-saved status-bar chip + persisted month / YTD / all-time aggregate

**Status:** spec draft, pre cold-eyes (2026-07-18). Loop log at end (§ 10).
**Source:** ROADMAP.md ANTS-3572 (`📊 Claude Code token-usage tracking + reports`
block); user request 2026-07-18 ("a status-bar tokens-saved counter … keep track
of year-to-date totals and monthly totals as well").
**Builds on:** ANTS-1284 (`TokenUsageEngine::Tracker` + `token_usage` MCP verb —
shipped 2026-05-14; the session counter this work surfaces + persists), ANTS-1355
(wrap/latency v2), ANTS-1432 (failed-call metric), ANTS-3361 (read/search
baselines).
**Distinct from:** ANTS-1245 (design-only Tools → Token Usage dialog with
SQLite + QtCharts) which tracks Claude's *consumed* tokens + $ cost. This work
tracks tokens *saved* by the MCP surface (`baseline − actual` displacement) and
stores its period buckets in `config.json`, NOT the ANTS-1245 SQLite DB. The two
period stores are independent; § 8 records the boundary so they don't collide.

## 1. Problem

`TokenUsageEngine::Tracker` (ANTS-1284) already observes every MCP dispatch and
computes a per-session `total_saved` (the `(baseline − actual-bytes)/4-chars-per-
token` displacement, in **tokens**, floored at 0 — the `/4` is the engine's
`kCharsPerToken`, `src/tokenusageengine.cpp:48`). But it has no face and no memory:

- **No face** — the only way to read the number is for the assistant to call the
  `token_usage` MCP verb. The user never sees "the MCP has saved me tokens" while
  they work. The saving the tooling was built for is invisible.
- **No memory** — the counter resets on every MCP `initialize` handshake
  (`claudeintegration.cpp:1575`, ANTS-1284) and dies with the process. There is no
  "this month" / "this year" / "all-time" figure, so the cumulative payoff — the
  most motivating number — cannot exist.

The fix is two thin layers on the existing engine, no new counter:

1. A **live status-bar chip** ("↓ 1.2M saved") showing the session total, updated
   on each dispatch, matching the existing context-% bar's State-widget pattern.
2. A **persisted aggregate** — a bounded monthly bucket map + an exact all-time
   counter in `config.json` — from which *this-month*, *year-to-date*, and
   *all-time* are derived. Written only at session-reset and app-quit, never per
   call.

## 2. Surface

**Layer map (verified against current source, § 10 Loop 1).** The one canonical
`Config` is `MainWindow`'s by-value member `Config m_config`
(`src/mainwindow.h:246`); it is **not** a singleton (there is no `Config::instance()`)
and `ClaudeIntegration` holds **no** `Config` handle
(`src/claudeintegration.h:78` ctor takes only a `QObject*` parent). So:

| Concern | Home | Why |
|---|---|---|
| Session counter + emit signals | `ClaudeIntegration` | owns `m_tokenUsage`; has the dispatch hook; no Config needed |
| Fold session→aggregate + `config.json` write | `MainWindow` | the **only** layer holding both `m_config` (writable) AND `m_claudeIntegration` — no clobber, no new dependency |
| Chip widget + tooltip | `ClaudeStatusBarController` | owns the status bar; reads config via its existing read-only `cachedConfig()` |
| Verb aggregate fields | `RemoteControl::cmdTokenUsage` | reads `m_main->tokenSavingsSummary()` |
| Pure fold/sum math | `TokenUsageEngine` | Qt6::Core only; unit-testable |

Rejected alternative: injecting a `Config*` into `ClaudeIntegration` or adding a
`Config::instance()` singleton — a larger change than reusing `MainWindow`'s
already-canonical `m_config`, and it would let a second `Config` instance clobber
settings (`Config::save()` at `src/config.cpp:137` rewrites the whole JSON
object — last-writer-wins).

### 2.1 The chip (`ClaudeStatusBarController`, `src/claudestatuswidgets.{h,cpp}`)

A new **State** widget (per `docs/standards/status-bar.md`): read-only fact, not
an Action. A `QLabel` pill `m_tokensSavedChip`, constructed in the controller ctor
next to the context-% bar (`m_contextBar`, built at
`src/claudestatuswidgets.cpp:118`, added at `:128`) and added via
`m_statusBar->addPermanentWidget(...)` immediately after `m_contextBar` so the two
"session telemetry" readouts sit together, before the model chips. Starts
`hide()`-den like `m_contextBar` (`:127`).

- **Face text:** `↓ <humanized session-saved> saved`, e.g. `↓ 1.2M saved`.
  Humanization (§ 2.7): `< 1000 → "820"`, `< 1e6 → "12.4K"`, `< 1e9 → "1.2M"`,
  else `"…B"` (one decimal, trailing `.0` trimmed).
- **Visibility:** shown iff `cachedConfig().claudeTokensSavedChipEnabled()`
  (default true) AND the live session-saved total `> 0`; hidden otherwise (clean
  bar at launch; the pill appears on the first MCP call that saves anything —
  typically `session_orient`). Mirrors the context bar's `hide()`-when-`<=0`.
- **Theme:** styled inside the update slot from `Themes::byName(m_currentThemeName)`
  (border `th.border`, background `th.bgSecondary`, text `th.textPrimary`),
  exactly as the context-bar update slot does — no static stylesheet, so a live
  theme switch repaints it.
- **Tooltip** (the fuller story, always present once the pill shows):
  `This session: 1.2M · This month: 12.4M · This year: 47.8M · All-time: 91.2M
  saved (since 18 Jul 2026)`, with a trailing `· net of <N> wasted on failed
  calls` clause **only when** the session's failed-byte waste
  (`totalFailedBytes/4`, where 4 is the engine's `kCharsPerToken`; § 2.2) is
  non-zero. The "since" date is the **first-fold** date (§ 2.3), not any ship
  date. `setAccessibleName` /
  `setAccessibleDescription` kept in sync (documentation.md § 7).
- **Update path is event-driven, not the `shellCwd()` refresh trio**: the chip is
  integration-scoped (like the context bar), so it is driven by the
  `tokensSavedUpdated` signal (§ 2.2), not `m_statusTimer` + `singleShot` +
  `onTabChanged`.

The update slot reads the persisted aggregates for the tooltip via the file-local
`cachedConfig()` helper (`src/claudestatuswidgets.cpp:65-81`, ANTS-2116 —
mtime-guarded reload; a translation-unit-local free function reachable from the
controller's slots, not a controller member) and derives *this-month* / *this-year*
with the
`TokenUsageEngine` pure helpers (§ 2.7); the live session total arrives as the
signal argument. Because a fold writes `config.json`, `cachedConfig()`'s mtime
guard reloads it on the next slot call, so stored values stay current (INV-1).

### 2.2 `ClaudeIntegration` signals (`src/claudeintegration.{h,cpp}`)

Two new signals, declared next to `contextUpdated(int)` (`src/claudeintegration.h:467`).
`ClaudeIntegration` gains **no** Config access — it only signals; `MainWindow`
owns persistence (§ 2.4).

```cpp
signals:
    void tokensSavedUpdated(qint64 sessionSaved);  // ANTS-3572 — drive the chip
    void tokenSessionEnding();                     // ANTS-3572 — fold-before-reset
```

- `tokensSavedUpdated(sessionSaved)` — emitted at the **tail of `recordDispatch()`**
  (`src/claudeintegration.cpp:1439`, the single unification-tested dispatch hook,
  ANTS-1402), carrying `m_tokenUsage.buildReport(false).totalSaved`. Also emitted
  as `tokensSavedUpdated(0)` immediately **after** each reset (below), so the chip
  clears to hidden at a session boundary — mirroring the context bar's
  `contextUpdated(0)`-on-reset.
- `tokenSessionEnding()` — emitted immediately **before** each
  `m_tokenUsage.reset()` (at the `initialize` handshake `:1575`, and inside
  `resetTokenUsage()` `:337` which the verb calls at `remotecontrol.cpp:18981`).
  Because emitter and receiver are both on the main (Qt event-loop) thread, the
  `MainWindow` slot connected to it runs **synchronously within `emit`** (Qt
  `AutoConnection` → `DirectConnection` same-thread), so `MainWindow` snapshots the
  session total from the still-intact counter *before* `reset()` clears it (INV-3).

Reset sequence at each site becomes:

```cpp
emit tokenSessionEnding();      // MainWindow folds the intact total NOW (sync)
m_tokenUsage.reset();           // clears live counter + re-stamps sinceUnixMs
emit tokensSavedUpdated(0);     // chip → hidden until next dispatch
```

The session total + failed-byte waste are read by consumers through the existing
`ClaudeIntegration::tokenUsageReport(bool includeZero)` accessor
(`src/claudeintegration.h:334`), whose `Snapshot` already carries `totalSaved` and
`totalFailedBytes` (ANTS-1284/1432) — no new getter required.

### 2.3 Persistence schema (`config.json`, via `src/config.{h,cpp}`)

Four keys under the existing `claude.*` namespace (world-readable config; no
secrets — the file's 0600 mode is unchanged):

| Key | Type | Meaning |
|---|---|---|
| `claude.tokens_saved_monthly` | object `{"YYYY-MM": number}` | per-month gross saved buckets; pruned to the most-recent 24 keys |
| `claude.tokens_saved_lifetime` | number | exact all-time gross saved; never pruned |
| `claude.tokens_saved_since` | string (ISO date) | date of the first fold; sets the tooltip's "since …" and is written once |
| `claude.tokens_saved_chip_enabled` | bool (default `true`) | show/hide the chip; does NOT gate the ledger (INV-11) |

Config accessor pairs matching the `config.cpp` `.toBool(true)`/`m_data.value(...)`
idiom (`src/config.cpp:508-541`), all `const` getters so the controller's
`cachedConfig()` (`const Config&`) can read them:
`claudeTokensSavedMonthly()`/`setClaudeTokensSavedMonthly(QJsonObject)`,
`claudeTokensSavedLifetime()`/`set…(qint64)`,
`claudeTokensSavedSince()`/`set…(QString)`,
`claudeTokensSavedChipEnabled()`/`set…(bool)`. The three **data** setters
(`monthly`/`lifetime`/`since`) are **store-only** — they write into `m_data` (via
`storeIfChanged`) and do NOT call `save()` internally, deliberately departing from
the existing `set…` idiom (`src/config.cpp:511-513`) which saves on every call. That
lets the fold batch all three mutations behind its single trailing `m_config.save()`
(INV-7). The `chip_enabled` setter keeps the normal save-on-set idiom (it's an
interactive Settings toggle, written once per user action). Values are stored as
JSON numbers (exact integers to 2^53 — INV-9).

### 2.4 Fold logic (`MainWindow::foldTokenSavingsIntoConfig()`, `src/mainwindow.{h,cpp}`)

`MainWindow` owns the persistence because it holds both `m_config`
(`src/mainwindow.h:246`) and `m_claudeIntegration`
(constructed `src/mainwindow.cpp:3902`):

```cpp
void MainWindow::foldTokenSavingsIntoConfig() {                 // ANTS-3572
    const qint64 s = m_claudeIntegration
                       ->tokenUsageReport(/*includeZero=*/false).totalSaved;
    if (s <= 0) return;                                         // nothing to fold
    const QString month = QDate::currentDate().toString("yyyy-MM"); // local
    m_config.setClaudeTokensSavedMonthly(TokenUsageEngine::foldMonthlyBucket(
        m_config.claudeTokensSavedMonthly(), month, s, /*keepMonths=*/24));
    m_config.setClaudeTokensSavedLifetime(
        m_config.claudeTokensSavedLifetime() + s);
    if (m_config.claudeTokensSavedSince().isEmpty())
        m_config.setClaudeTokensSavedSince(
            QDate::currentDate().toString(Qt::ISODate));
    m_config.save();                                            // one write (INV-7)
}
```

Triggers (each fold reads a total that has accumulated since the last reset, and
is immediately followed by the engine `reset()` that clears it — so a live amount
is folded exactly once, INV-2):

1. **MCP `initialize` handler** — `ClaudeIntegration` emits `tokenSessionEnding()`
   before its `:1575` reset; `MainWindow`'s slot folds the *previous* MCP session
   (same process, Claude Code restart) synchronously (INV-3).
2. **`token_usage` verb `reset:true`** — routes through `resetTokenUsage()`
   (`:337`), which emits `tokenSessionEnding()` before `m_tokenUsage.reset()`; the
   verb's own pre-reset report snapshot (ANTS-1284 INV-9) is unchanged.
3. **App quit** — `MainWindow` calls `foldTokenSavingsIntoConfig()` once from its
   `closeEvent` / `QCoreApplication::aboutToQuit` path, capturing the final live
   session (the case initialize can't cover — a new process starts empty).

`MainWindow` connects `m_claudeIntegration`'s `tokenSessionEnding` to
`foldTokenSavingsIntoConfig` where it already wires the other `ClaudeIntegration`
signals in `setupStatusBarChrome()`.

### 2.5 `token_usage` MCP verb additions (`RemoteControl::cmdTokenUsage`)

`RemoteControl` holds `MainWindow *m_main` (`src/remotecontrol.h:904`, non-owning /
non-null); the verb (`src/remotecontrol.cpp:18963`) gains four top-level fields on
its **response** — three from a new **public** `MainWindow::tokenSavingsSummary()`
(reads `m_config` + the engine, so the values equal `stored + session`, matching
the chip), plus `monthly[]` read directly from `m_config.claudeTokensSavedMonthly()`:

```json
{
  "…": "existing ANTS-1284/1355/1432 fields unchanged",
  "month_saved":    12400000,
  "ytd_saved":      47800000,
  "lifetime_saved": 91200000,
  "monthly": [ { "month": "2026-07", "saved": 12400000 },
               { "month": "2026-06", "saved":  9100000 } ]
}
```

All four fields are appended to the **free-form response envelope** `env` built in
`cmdTokenUsage` (`src/remotecontrol.cpp:18984+`). The `token_usage` verb has only an
`inputSchema` (args `reset`/`include_zero`, `additionalProperties:false` at
`src/claudeintegration.cpp:7553`) and **no response schema**, so no schema edit is
needed and the four output fields must NOT be added to the inputSchema (INV-10).
`monthly[]` is recent-first, capped at the retained 24. On `reset:true` the
aggregate fields are computed BEFORE the fold (so they already include the session
about to be folded); the fold then makes the stored numbers match, so a follow-up
call returns the same lifetime.

`MainWindow::tokenSavingsSummary() const` — **public**, so `RemoteControl` can call
it through `m_main` — returns a small POD
`{ session, month, ytd, lifetime, sessionFailedTokens, sinceDisplay }`. There is no
`monthly` member; the `monthly[]` verb field is read from the config map directly.
Each period is `stored + session` (§ 2.7 helpers); `sessionFailedTokens` is
`totalFailedBytes/4` (4 = `kCharsPerToken`). The verb and the tooltip present the
same numbers.

### 2.6 Config flag surfacing

`claude.tokens_saved_chip_enabled` defaults true (the project's "token-saving
knobs ship ON, keep an off switch" rule). Exposed in Settings → General next to
the other `claude.*` toggles (which bind via `m_config->` in

### 2.7 Pure helpers (`TokenUsageEngine`, `src/tokenusageengine.{h,cpp}`)

The fold/prune/sum math lives as pure static functions in the engine (Qt6::Core
only, already unit-tested) so it is testable without a `MainWindow` — the widget /
Config / verb wiring is source-grep tested, the math is functionally tested:

```cpp
namespace TokenUsageEngine {
// Add `add` to monthly[monthKey], then retain only the `keepMonths`
// lexicographically-greatest keys ("YYYY-MM" sorts chronologically).
QJsonObject foldMonthlyBucket(QJsonObject monthly, const QString &monthKey,
                              qint64 add, int keepMonths);
// Sum of buckets whose key starts with `yearPrefix` (e.g. "2026").
qint64      sumYear(const QJsonObject &monthly, const QString &yearPrefix);
// "820" / "12.4K" / "1.2M" / "…B" — one decimal, trailing ".0" trimmed.
QString     humanizeCount(qint64 n);
}
```

The humanizer is UI-agnostic number formatting, so it lives in `TokenUsageEngine`
(not the widget TU) — that keeps it directly unit-testable (HUMAN-1); the chip just
calls `TokenUsageEngine::humanizeCount(...)`.

## 3. Invariants

- **INV-1 — No jump across a fold.** Every displayed period is
  `stored + liveSession` (§ 2.1 tooltip, § 2.5 verb). A fold (§ 2.4) adds exactly
  `liveSession` to `stored` and the reset then clears the live counter, so
  immediately after the fold the display is `(stored+liveSession) + 0` —
  byte-identical to the pre-fold `stored + liveSession`. The month/YTD/all-time
  numbers never jump or flicker at a session boundary. *Test: fold-parity unit
  test (FOLD-1).*

- **INV-2 — Fold-once, no double-count.** Every `m_tokenUsage.reset()` is
  preceded by a `tokenSessionEnding()` emit (its only fold trigger) and the reset
  clears the counter in the same sequence. The three trigger paths (initialize,
  verb `reset:true`, quit) each fold a live amount that accumulated since the last
  clear; none folds twice without an intervening accumulation. A live amount
  contributes to `stored` exactly once. *Test: source-grep asserts every reset
  site emits `tokenSessionEnding` first; unit test folds a 0 session and asserts
  a no-op (FOLD-2).*

- **INV-3 — Synchronous fold-before-reset.** `tokenSessionEnding` is connected
  `MainWindow`↔`ClaudeIntegration`, both on the main thread, so the fold slot runs
  synchronously inside `emit` (Qt `AutoConnection` resolves to `DirectConnection`
  same-thread) — the fold reads the session total *before* `reset()` clears it. If
  the MCP dispatch ever moves off the main thread (ANTS-1284 INV-7 flags this as a
  v2 change), the connection must be made explicitly `DirectConnection` or the
  fold re-ordered. *Documented; enforced by the emit-before-reset ordering test.*

- **INV-4 — Bounded map, exact all-time.** `foldMonthlyBucket` retains only the 24
  lexicographically-greatest keys after each fold; older buckets are dropped.
  `claude.tokens_saved_lifetime` is a separate counter that is never pruned, so
  all-time stays exact even after buckets age out. YTD sums only current-year keys,
  which (≤ 12 months) always fall inside the retained 24-month window, so pruning
  never truncates YTD. *Test: fold 30 distinct months → map size 24, lifetime =
  sum of all 30; YTD across a year boundary (FOLD-3/4).*

- **INV-5 — Chip visibility.** The pill is shown iff
  `cachedConfig().claudeTokensSavedChipEnabled()` (default true) AND
  `liveSession > 0`; hidden otherwise. Theme-styled from the active theme in the
  update slot. *Test: source-grep the enabled-guard + `>0` guard + `hide()` path
  in the slot (TSC-3).*

- **INV-6 — Single emission hook for the live signal.** `tokensSavedUpdated` with
  a non-zero payload is emitted ONLY from `recordDispatch()`, preserving the
  ANTS-1402 single-observation-site contract; the `tokensSavedUpdated(0)` refresh
  fires only alongside a reset. *Test: source-grep asserts the non-zero emit sits
  in `recordDispatch` (TSC-1).*

- **INV-7 — Write cadence.** `m_config.save()` for these keys happens only inside
  `foldTokenSavingsIntoConfig()` (initialize / verb-reset / quit) — never per MCP
  call, never in `recordDispatch`. A busy session with thousands of dispatches
  performs at most a handful of config writes. *Test: source-grep asserts no
  `setClaudeTokensSaved`/`m_config.save` inside `recordDispatch` (TSC-4).*

- **INV-8 — RAM / footprint bound.** The monthly map is ≤ 24 entries
  (`"YYYY-MM"` key ~7 chars + a number) held inside the already-resident `m_config`
  object; plus one `qint64` lifetime + one date string. The `TokenUsageEngine`
  itself is unchanged (~7 KiB per ANTS-1284 INV-8). No new cache, thread, file
  watcher, or timer. *Documented; no RSS test (flaky in CI).*

- **INV-9 — Storage precision.** Buckets and lifetime are stored as JSON numbers,
  exact-integer to 2^53 (~9.0e15 tokens). At 1 M saved/day that ceiling is ~24
  billion years away, so double storage never loses precision for any real total.
  *Documented.*

- **INV-10 — Verb fields live in the response envelope, not the input schema.**
  `month_saved`, `ytd_saved`, `lifetime_saved`, and `monthly[]` are appended to the
  free-form response `env` built in `cmdTokenUsage`; the `token_usage` `inputSchema`
  (`additionalProperties:false` over `reset`/`include_zero`) is unchanged — the
  response fields must NOT be declared as input args. (The verb has no response
  schema, so there is nothing to close.) *Test: source-grep asserts the four keys
  appear in `cmdTokenUsage` and are absent from the inputSchema block (TSC-5).*

- **INV-11 — Flag gates the chip, not the ledger.** Turning
  `tokens_saved_chip_enabled` off hides the widget but folds still run and the
  aggregate keeps accruing, so re-enabling later shows the true accumulated total
  (no silent gap). *Test: source-grep asserts the enabled-check is in the widget
  update slot, not around `foldTokenSavingsIntoConfig` (TSC-3).*

- **INV-12 — Aggregate is gross saved; failed-waste is session-only.** The
  monthly/YTD/all-time buckets accumulate `tokenUsageReport(false).totalSaved`
  (gross, floored at 0). The failed-call waste (`totalFailedBytes/4`) is surfaced
  only in the live tooltip's "net of …" clause, never persisted — so the stored
  periods are a single consistent gross-saved series. *Documented.*

## 4. Failure modes

- **Corrupt/missing `claude.tokens_saved_monthly`** (hand-edited to a non-object,
  or absent on first run) → `claudeTokensSavedMonthly()` returns an empty
  `QJsonObject`; fold starts a fresh map. No crash, no refusal.
- **A bucket value that is not a number** (hand-edited) → treated as 0 in `sumYear`
  / fold (`QJsonValue::toDouble(0)`), and overwritten on the next fold for that
  month. Self-heals.
- **`tokens_saved_lifetime` < sum of retained buckets** (e.g. buckets hand-edited
  up) → lifetime is authoritative for all-time; the tooltip shows lifetime, not
  the bucket sum, so no contradiction is displayed.
- **Clock moved backwards / timezone change** → a fold may land in an earlier
  `YYYY-MM` key than a prior fold; it simply adds into that bucket. Monotonic
  lifetime is unaffected. Acceptable for a motivational estimate.
- **Crash / OOM-kill before a fold** (earlyoom on this host) → the in-flight
  session's savings are lost from the aggregate (never folded). Accepted: this is
  an estimate, not accounting; § 7 records the rejected per-minute-flush
  alternative.
- **`m_claudeIntegration` null when a fold fires** (teardown ordering) →
  `foldTokenSavingsIntoConfig` guards on the pointer before dereferencing; a null
  integration folds nothing.

## 5. Test plan

`tests/features/token_usage_engine/` (existing bundle `test_audit`) gains
pure-function cases for the new helpers:

before wiring), per test-first.

## 6. Performance / RAM budget

- **Per MCP call:** one extra `buildReport(false)` (O(distinct tools) ~≤ 80
  entries + a sort) to produce the signal payload, plus one signal emission and
  one label repaint. `buildReport` is already the verb's cost; here it runs per
  dispatch — still ~10 µs, imperceptible. No disk I/O on this path (INV-7).
- **Per fold (rare):** one 24-key prune + one `m_config.save()` (the whole config
  is already rewritten atomically on any settings change; these keys add < 1 KiB).
- **RAM:** ≤ 24 map entries + 2 scalars inside the resident `m_config` (INV-8).
- **No new caches, threads, watchers, or timers.**

## 7. Out of scope

- **Per-minute / periodic flush** to bound crash loss. Rejected for v1: adds a
  timer + write-amplification for a motivational estimate; the fold-on-quit +
  fold-on-initialize pair captures every clean session. Revisit only if crash-loss
  proves annoying in practice.
- **Per-project / per-cwd breakdown.** The aggregate is global to the process, as
  the ANTS-1284 session counter already is. A project-keyed view is a later item.
- **Cost ($) estimate / graphs / CSV export.** That is ANTS-1245's surface
  (consumed tokens); this chip is saved-tokens only. No QtCharts dependency.
- **Weekly / daily buckets.** The user asked for monthly + YTD + all-time; day/
  week granularity would need per-call timestamping (out of scope) — the engine
  only knows session totals at fold time.
- **Migrating the aggregate into ANTS-1245's SQLite store** if that ships. Noted
  as the integration seam (§ 8); not built here.
- **Net-of-failure persistence.** Only gross saved is stored (INV-12).

## 8. Migration / integration boundary

- New config keys only; no existing key changes; no schema migration (absent keys
  default cleanly — § 4). First fold seeds `tokens_saved_since`.
- `ClaudeIntegration` gains two signals (no Config dependency); `MainWindow` gains
  `foldTokenSavingsIntoConfig()` + `tokenSavingsSummary()` and one signal
  connection; `TokenUsageEngine` gains two pure helpers; `Config` gains four
  accessor pairs; `RemoteControl::cmdTokenUsage` reads the summary. The only
  behavioural change to existing paths is the `tokenSessionEnding` emit inserted
  before the two `reset()` sites — reset semantics themselves (clear + re-stamp
  `since`) are unchanged.
- **ANTS-1245 boundary:** if the consumed-tokens dialog later ships with SQLite,
  it owns *consumed* tokens; this feature owns *saved* tokens in `config.json`.
  They must not share a store. A future unification (one dialog with both series)
  is a design item, not a silent merge.
