## 1. Problem

`scope:"since-last-run"` (ANTS-1504) re-scans only the files changed since
the prior cached run. But its envelope stops at `changed_files_count` +
the changed-set tool counts — it cannot say **which warnings appeared,
disappeared, or carried over**, and the SARIF it records covers only the
changed files, not the whole tree.

The blocker ANTS-1504 § 5 named was the v1 SARIF: "a per-tool raw-output
blob, not per-finding result entries" (`auditrunner.cpp:18-28`). That
framing over-stated the gap. `parseToolOutput`
(`src/auditrunner.cpp:532`) **already** extracts each finding into a
structured `{file, line, message, rule, severity}` record — it just stops
appending them once `samples.size()` reaches `sampleCap`
(`:603` clamps the count to `kSarifFindingsMax`, `:89` = `10'000`). And a
line-insensitive identity key already exists:
`ants::auditfp::computeFingerprint(file, checkId, message)` (ANTS-1820,
called at `auditrunner.cpp:529`). So the real work is: (1) collect the
**full** per-finding set, not a capped preview; (2) persist it so the next
run can diff against it; (3) compute the delta and fold prior findings on
untouched files into the new SARIF.

**Layman:** make the fast re-audit also tell you exactly which warnings
are new, which you fixed, and which are still there — and keep the saved
report showing the whole project, not just the files you just touched.

## 2. Surface

### 2.1 Full per-finding extraction (the "v2 parser")

`ParsedOutput` (`src/auditrunner.cpp:511`) gains a `QJsonArray findings`
member alongside the existing capped `samples`. Inside `parseToolOutput`
both the JSON-results branch (`:541`-`:607`) and the line-based fallback
(`:608`-`:641`) build a per-finding `QJsonObject s`
(`{file, line, message, rule, severity}`), but **today that construction
is gated by `sampleCap`** — the JSON loop terminates on
`out.samples.size() < sampleCap` (`:561`) and the line branch does
`if (out.samples.size() >= sampleCap) continue;` (`:630`) *before*
building `s`, so findings past the cap are never materialised. The real
work here is to **hoist `s`'s construction out of that guard**: build `s`
for every non-suppressed finding and append it to `findings`
unconditionally (subject only to the `kSarifFindingsMax` ceiling), keeping
the `< sampleCap` condition on the `samples` append alone. `samples` thus
retains its preview behaviour while `findings` collects the full set. Each `findings[]` entry also carries `fp` — the ANTS-1820
fingerprint (§ 2.2). Learned-FP-suppressed entries (the `continue` at
`:586` / `:628`) are
excluded from `findings` exactly as they are from `samples` (a suppressed
finding is not part of the project's finding set). `findings` is bounded
at `kSarifFindingsMax` (10'000) entries; on overflow the array stops
growing and `ParsedOutput` sets `findingsTruncated = true` (surfaced so
the delta can flag itself best-effort, § 2.7).

### 2.2 Finding identity

Two findings are "the same finding across runs" iff their fingerprints are
equal, where `fp = ants::auditfp::computeFingerprint(file, checkId,
message)` (`auditfpledger.h`, the key ANTS-1820 already computes at
`auditrunner.cpp:529`). The key is **line-insensitive by design**: an edit
that merely shifts a warning down three lines must read as
*carried-forward*, not as one removed + one added. `checkId` is the tool
name for the line-based tools (cppcheck/clazy/mypy/shellcheck — matching
the GUI's `Finding::checkId`) and the tool's own `check_id` for the JSON
tools, identical to the namespace ANTS-1820 already persists, so a
fingerprint is stable for a given finding across runs of the same tool.

**Known coarseness (documented, not solved here):** because the key omits
the line, two findings in one file sharing a tool + message but at
different lines collapse to one fingerprint. This matches ANTS-1820's
existing model and is the correct trade for drift-robustness; line-precise
identity is out of scope (§ 5).

### 2.3 Findings sidecar persistence

The full finding set is **not** inlined into the manifest — `index.json`
is read on every run and a 10'000-entry array would bloat it. Instead each
recorded run writes a sibling sidecar
`.audit_cache/findings-<isoFilename>-<sha>.json` (the same
`<isoFilename>-<sha>` stem `AuditCache::sarifPathFor` uses, `auditcache.h:25`;
the basename's iso is `IsoNow.forFilename` — colons→hyphens — while the
JSON body's `iso_timestamp` is the canonical `IsoNow.forManifest`,
`auditcache.h:36`-`40`):

```json
{
  "version": 1,
  "iso_timestamp": "2026-06-17T18:30:00Z",
  "commit": "<short-sha>",
  "scope": "auto",
  "truncated": false,
  "findings": [
    {"file":"src/x.cpp","line":42,"rule":"cppcheck","severity":"UNKNOWN","message":"…","fp":"<16-hex>"}
  ]
}
```

`AuditCache::Manifest.lastRun` (`auditcache.h:59`) gains a `findings_file`
field carrying that basename (resolved relative to `.audit_cache/`, same
self-contained-dir convention as `sarif`/`html`). `recordRun` (declared
`auditcache.h:93`, **implemented in `auditcache.cpp`**, called from
`auditrunner.cpp:1671`) gains a trailing `const QJsonArray &mergedFindings
= {}` parameter placed **after** the existing `QJsonObject *priorRunOut`
out-pointer — the target signature is `recordRun(canonProject,
lastRunJson, priorRunOut, mergedFindings = {})`, so the default sits last
(a defaulted parameter cannot precede the non-defaulted out-pointer).
Default empty → no sidecar, preserving the no-findings behaviour; when
non-empty it writes the sidecar inside its existing
atomic flow — the basename is derivable from the iso+sha it already
computes (step 1) — and sets `last_run.findings_file` to that basename in
the same write. Every scope that finds anything supplies its findings here
— a full / `auto` run passes its whole-tree current set, a
`since-last-run` passes `DeltaResult.merged` (§ 2.6) — so the baseline
sidecar is **always** seeded (the empty default is only the back-compat
path for a caller that records no findings). In particular the first
`since-last-run` after an `auto` sweep reads that sweep's sidecar rather
than falling to `no_prior_findings` forever. The history reaper (`recordRun` step 4, in
`auditcache.cpp`, trims `history[]` to 10) extends to delete the dropped
runs' `findings-*.json` sidecars alongside their SARIF/HTML — same
naming-convention guard (never touches AuditDialog GUI files). A reader,
`AuditCache::loadFindingsSidecar(canonProject, basename) → QJsonArray`
(basename resolved to an absolute path under `.audit_cache/`, the same
self-contained-dir convention `sarifPathFor` uses), returns the persisted
`findings[]`; a missing / unparseable / `version` ≠ 1
sidecar loads as an empty array (mirrors the manifest's own forward-compat
rule, `auditcache.h:54`-`56`).

### 2.4 Delta computation (since-last-run)

Pure helper module (new pure functions in `src/auditdelta.{h,cpp}`,
namespace `AuditDelta`, no `QProcess`, no filesystem — INV-9 parity with
`AuditScope`). It operates directly on the § 2.1 `QJsonArray findings`
shape — the *same* representation the runner builds and the sidecar
(§ 2.3) persists — so there is **no struct⇄JSON conversion** and **no new
`Finding` type**. (The project already has an unrelated
`AuditEngine::Finding`, `auditengine.h:82`; reusing that name here would
collide, so the delta deliberately defines no struct of that name.)

```
struct DeltaResult {
    QJsonArray added;            // current findings whose fp ∉ priorOnChanged
    QJsonArray removed;          // priorOnChanged findings whose fp ∉ current
    QJsonArray carriedForward;   // (current ∩ priorOnChanged) ∪ priorOnUntouched
    QJsonArray merged;           // current ∪ priorOnUntouched — whole-tree, for SARIF + sidecar
    int addedCount = 0, removedCount = 0, carriedForwardCount = 0;
};
DeltaResult computeDelta(const QJsonArray &current,        // this run, changed-set
                         const QJsonArray &prior,          // prior run, whole-tree
                         const QSet<QString> &changedFiles);
```

Each array element is a § 2.1 finding object (`{file, line, rule,
severity, message, fp}`); identity is the `fp` field (§ 2.2). Logic:

1. Partition `prior` by `changedFiles.contains(file)` →
   `priorOnChanged`, `priorOnUntouched`.
2. `added` = `current` whose `fp` ∉ `priorOnChanged` fps.
3. `removed` = `priorOnChanged` whose `fp` ∉ `current` fps.
4. `carriedForward` = (`current` ∩ `priorOnChanged` by fp) ∪
   `priorOnUntouched` (every untouched-file finding — those files were not
   re-scanned, so their prior findings are assumed still present).
5. `merged` = `current` ∪ `priorOnUntouched` — the whole-tree set the
   carry-forward SARIF (§ 2.5) and the recorded sidecar (§ 2.6) both write.
   (`merged` deliberately has no `*Count` field: unlike `carried_forward`
   it is not an envelope surface, only the SARIF/sidecar payload, § 2.8.)

Only `current` and `priorOnChanged` can produce added/removed — an
untouched file contributes only to `carriedForward` / `merged`. The helper
is **total over degenerate inputs**: empty `current` (every
`priorOnChanged` → `removed`); empty `prior` (every `current` → `added`);
both empty (all arrays empty); an all-files-changed run (`priorOnUntouched`
empty, so `merged == current`). Pure and unit-testable with canned
`QJsonArray` lists (no git, no cache).

### 2.5 Carry-forward SARIF merge

`writeSarif` (`auditrunner.cpp:646`) keeps its per-tool driver +
raw-output notification blocks, but its `results[]` array is rebuilt from
the **full** `findings` set (§ 2.1) rather than the capped `samples`,
resolving the `auditrunner.cpp:18-28` / `:26`-`28` "v2 will parse the
SARIF result entries" follow-up. Under `since-last-run` the set written to
SARIF is `DeltaResult.merged` (§ 2.4 step 5 — `current` ∪ `priorOnUntouched`),
so the recorded SARIF represents the **whole tree**, not just the changed
files — closing ANTS-1504 § 2.9's "partial SARIF" caveat for the findings
view. Each carried-forward result carries `properties.carried_forward:
true` so a SARIF consumer can tell a re-scanned finding from an assumed-
still-present one. The `results[]` array is bounded at `kSarifFindingsMax`
(already the finding ceiling). Because `merged` = `current` ∪
`priorOnUntouched` can in principle approach 2×`kSarifFindingsMax`, the
bound keeps **`current` entries first** (the freshly-verified findings,
never dropped) and sheds `priorOnUntouched` overflow; if the union exceeds
the ceiling the recorded sidecar (§ 2.6) sets `truncated:true`, so the next
run reads a truncated baseline and falls to `findings_truncated` (§ 2.7)
rather than silently mis-diffing a dropped finding as removed-then-added.

### 2.6 Recording semantics

When a non-empty `since-last-run` records its run (ANTS-1504 § 2.9,
`recordRun` at `auditrunner.cpp:1671`), the **findings sidecar it writes is
the merged whole-tree set** (`current` ∪ `priorOnUntouched`), not just the
changed-set findings — the caller passes `DeltaResult.merged` (§ 2.4
step 5) as `recordRun`'s `mergedFindings` argument. This keeps `last_run.findings_file` a complete
baseline, so a *chain* of `since-last-run` calls (the fix-verify loop)
does not progressively shed untouched-file findings — each iteration
diffs against, and re-persists, the whole picture. The per-tool counts
(`total_raw` / `total_actionable` / `by_tool`, `auditrunner.cpp:1656`-`1668`)
still reflect what actually ran this iteration (the changed set), since
those measure work done; only the findings sidecar + SARIF are
whole-tree. This divergence is intentional and documented in the sidecar
(`scope` field records the run's actual scope).

When the current run truncated (§ 2.7), `computeDelta` still runs to
produce `merged` for the SARIF + sidecar — only the *envelope* delta
surface is suppressed — and the sidecar records that capped set with
`truncated:true`. A later non-truncating run records `truncated:false`, so
a truncated baseline **self-heals** rather than pinning `findings_truncated`
indefinitely (the fallback fires only while the current or prior set is
actually truncated, § 2.7).

### 2.7 Honest fallback

The delta needs a prior findings sidecar. When it is unavailable the run
still completes; the envelope omits `delta` and carries
`delta_unavailable_reason`. The three reasons are checked in **data-
dependency order**, and the first that holds is the one reported (so they
never coexist): `no_prior_findings` first (no baseline exists to diff, so
neither readability nor truncation is even evaluable), then
`prior_findings_unreadable` (a baseline is referenced but won't load),
then `findings_truncated` (a readable baseline exists, but a truncated
current-or-prior set would mis-report the diff). A first-ever run that
*also* truncates therefore reports `no_prior_findings`, not
`findings_truncated`.

- `no_prior_findings` — `last_run.findings_file` absent (a manifest
  recorded before this feature, or a first sweep). The run records a
  sidecar so the *next* since-last-run has a baseline.
- `prior_findings_unreadable` — the referenced sidecar is missing /
  unparseable / `version` ≠ 1.
- `findings_truncated` — either run hit the `kSarifFindingsMax` ceiling
  (§ 2.1); a delta over a truncated set would mis-report, so it is
  suppressed and the count surface (ANTS-1504's `changed_files_count` +
  tool counts) stands alone. The merged SARIF (§ 2.5) is still written
  (best-effort, capped). The *current* run's truncation is the OR of each
  tool's `ParsedOutput.findingsTruncated`, surfaced on
  `RunResult.findingsTruncated` (§ 2.8); the *prior* run's is read from
  the sidecar's `"truncated"` field (§ 2.3). The fallback fires if either
  is set.

A demoted-to-full run (ANTS-1504 § 2.7) computes **no** delta (there is no
"changed set" to diff) but records a whole-tree findings sidecar that
re-seeds the baseline. `delta` is emitted only for an actually-narrowed,
non-empty `since-last-run` with a readable, untruncated prior baseline.

### 2.8 Envelope additions

Added to the `audit_run` reply built at `src/mainwindow.cpp:4595`+ (beside
`prior_run` `:4605` / `changed_files_count` `:4612`):

```json
{
  "delta": {
    "added":            [ {"file":"…","line":42,"rule":"…","severity":"…","message":"…"} ],
    "removed":          [ {"file":"…","line":17,"rule":"…","severity":"…","message":"…"} ],
    "added_count":            3,
    "removed_count":          1,
    "carried_forward_count":  274
  },
  "delta_unavailable_reason": "no_prior_findings"
}
```

`delta` and `delta_unavailable_reason` are mutually exclusive — exactly
one appears under `since-last-run`, neither under non-narrowing scopes.
The `added` / `removed` arrays are capped at `kSamplesPerToolDefault`
(10, `auditrunner.cpp:86` — the per-tool sample-preview cap) for envelope
size. This is deliberately **not** the caller's `top_findings_count`
(`auditrunner.h:40`), which defaults to 0 and would otherwise empty the
arrays; the `*_count` fields are always exact regardless of the array cap.
The `carriedForward` / `merged` arrays (§ 2.4) are **not** echoed in the
envelope — they exist only to feed the SARIF (§ 2.5) and sidecar (§ 2.6);
the envelope surfaces `carried_forward_count` for them, no array. New `RunResult` fields (after the ANTS-1504
`noChanges` member, `auditrunner.h`): `delta` (`QJsonObject`),
`deltaUnavailableReason` (`QString`), `findingsTruncated` (`bool`, the
OR over the run's per-tool `ParsedOutput.findingsTruncated`).

## 4. RAM / build cost

The per-finding `findings` array and the loaded prior sidecar are each
bounded at `kSarifFindingsMax` (10'000) records. Worst-case record ~400 B
(path + 256 B-capped message + fp + ints) → ~4 MB per array, transient and
freed when the run returns; at most one prior sidecar is loaded at a time
(during a single since-last-run delta). `index.json` itself does **not**
grow — the findings live in the sidecar, referenced by basename, so the
frequently-read manifest stays small. On disk, ≤10 sidecars persist
(history depth), reaped in lockstep with their runs. One new small
translation unit (`auditdelta.cpp`, est. ~120-160 lines) joins
`ants_audit_lib`; no new external dependency.

## 5. Out of scope

- **Cross-tool finding correlation** (cppcheck + clazy reporting the same
  underlying defect as one). Each tool's findings are diffed within its
  own `checkId` namespace, as ANTS-1820 already models.
- **Line-precise identity.** Identity is line-insensitive (§ 2.2) by
  design; a same-file same-message multi-line cluster collapses to one
  fingerprint. Refining the key (e.g. an Nth-occurrence ordinal) is a
  separate follow-up if it ever proves needed.
- **AuditDialog GUI delta display.** This pass surfaces the delta in the
  `audit_run` MCP envelope + the recorded SARIF only; rendering an
  added/removed view in the GUI is a future item.
- **`last_audit_summary` delta echo.** The summary verb continues to
  report counts; teaching it to read the new sidecar/delta is out of scope.
