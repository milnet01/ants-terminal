# ANTS-1410 — `/audit` skill enumerates project-specific CI gates

**Status:** in flight (Bundle D pull 1, 2026-05-16).
**Kind:** implement (cross-session report).
**Lanes:** global skill `~/.claude/skills/audit/SKILL.md` (out-of-tree);
this repo carries the spec + the close-out roadmap entry.
**Source:** cross-session-report-2026-05-15 (MAME Curator —
DS02 R2 hot-fix root cause).
**Pairs with:** ANTS-1351 (server-side `audit_run` orchestrator — once
that lands, the workflow-enumeration logic belongs server-side and
every Ants project inherits it). This is the **stopgap** markdown-side
fix that closes the gap until 1351 ships.

## Problem

The `/audit` skill's tool list (cppcheck, clazy, ruff, bandit, semgrep,
gitleaks, trivy, shellcheck, optionally pyright/mypy, optionally
project-side `audit.py`) is **generic and project-agnostic**. Many real
projects grow per-project CI gates over time — typically Python or
shell scripts under `tools/check_*.py` / `scripts/check_*.{py,sh}` /
`tools/audit/*` — that are invoked from `.github/workflows/*.yml` and
gate the merge but **are invisible to `/audit`**.

Cross-session report 2026-05-15 (MAME Curator project):
- `.github/workflows/ci.yml` runs `python tools/check_api_types_sync.py`
  (Python ↔ TypeScript type-drift detector) as a `run:` step.
- `/audit` never executed this step. `/close-phase` reported "CLEAN"
  while the project-specific gate was actually broken.
- Discovered post-tag when CI failed → required a hot-fix.

The skill's step 1 detection table does include "Custom" → "Makefile
audit: target, audit.py, .audit_rules.json" — but it only probes the
fixed set of conventional script names. Anything bespoke under
`tools/check_*` is missed unless the project also ships an
`audit-config.json` listing it explicitly.

Two failure modes this enables, ranked by how often they actually bite:
1. **Silent miss** — the script exists, CI runs it, `/audit` doesn't.
   Close-phase looks clean; merge breaks CI.
2. **Discovery cost** — a new contributor running `/audit` for the
   first time has no idea the project has bespoke gates beyond the
   generic linters. Project-onboarding friction.

## Goal

`/audit` walks `.github/workflows/*.yml` on every run, extracts the
list of `run:` steps invoking project-local scripts (under `tools/`,
`scripts/`, `bin/`, or any path the workflow author resolved via
`$GITHUB_WORKSPACE`), and **either**:

- **(a) Executes each** as an additional audit pass, threading its
  stdout/stderr into the triage pipeline alongside the canonical
  linters. Findings keyed by `tool: workflow:<path>` so triage can
  surface them in the per-tool summary.
- **(b) At minimum, surfaces them** in the per-tool summary as
  `workflow:<path>: skipped (project-local gate not executed by the
  skill — review manually)` so the caller knows the audit was
  incomplete.

This spec commits to **(a) by default with (b) as a fallback** when
the script is non-executable, requires arguments the skill can't infer,
or fails its `--help` probe. Rationale: (b) alone doesn't fix the
silent-miss class — it just renames it from "silent" to "deferred." (a)
fixes it, with (b) as the graceful degradation path.

## Design

### New step in SKILL.md

Insert **between step 1 (Detect what's runnable) and step 2 (Apply
argument filtering)** as **step 1.5: "Enumerate project-local
CI gates."**

```markdown
1.5. **Enumerate project-local CI gates.** Walk `.github/workflows/*.yml`
     (and `.gitlab-ci.yml` if present). For each `run:` step:

     - Tokenise the command line. Identify the **invoked script path**
       — the first non-flag token that resolves to an existing file
       under the repo root.
     - **Include** scripts under: `tools/`, `scripts/`, `bin/`,
       `tests/`, `ci/`, or any explicit path under
       `$GITHUB_WORKSPACE`.
     - **Exclude** scripts that are already covered by step 1's
       detection table (ruff, bandit, cppcheck, semgrep, gitleaks,
       trivy, shellcheck, pytest, mypy, pyright, clazy, npm scripts,
       `cargo`, etc.) — match on the binary name, not the full path.
     - **Exclude** scripts whose first argument is `--check`-style
       formatting verification AND whose binary is a known formatter
       (`black`, `ruff format`, `prettier`, `clang-format`, `gofmt`)
       — these are formatting gates, not bug-finding gates.
     - **Exclude** workflow steps gated on non-default conditions
       (`if: github.event_name == 'release'`, manual triggers, etc.).
       Only collect steps that fire on the project's default `on:`
       triggers (`push`, `pull_request`).
     - **De-duplicate** by absolute resolved path — the same script
       referenced from multiple workflows runs once.

     For each surviving script:
     - Probe with `<script> --help` (or `--help-short`); 5 s timeout
       (covers Python interpreter startup + cold-cache import on a
       loaded system). Capture exit code AND stderr+stdout — many CI
       scripts print usage to stderr on `--help`.
     - If exit code is 0 (or matches a known "help-shown" signal —
       some scripts exit 2 on `--help`; treat any output containing
       `usage:` / `Usage:` / `--help` as "help shown") AND no
       required positional args are visible in the help text:
       mark **runnable** — invoke with no args during step 5.
     - Otherwise mark **deferred** — surface in step 10's summary as
       `workflow:<repo-relative-path>: deferred (requires args /
       no --help — review manually)`.

     Record the full list in `$WORKFLOW_GATES` for step 5 to invoke
     and step 10 to summarise.
```

### Companion change to step 5

Add a new bullet under § 5 ("Project-appropriate invocations"):

```markdown
- **Workflow gates (from step 1.5):** for each `<script>` marked
  runnable, invoke as `<script>` (no args; the help probe confirmed
  it accepts argless invocation). Capture stdout+stderr to
  `/tmp/audit-workflow-<sessionid>-<basename>.txt`. Treat **non-zero
  exit OR any stdout/stderr output** as a finding; exit 0 with empty
  output is "clean" per step 8.
```

### Companion change to step 10

Add to the report template:

```markdown
**Project-local CI gates** (from `.github/workflows/`):
- workflow:tools/check_api_types_sync.py: <findings | clean | deferred>
- workflow:scripts/check_format.sh: <findings | clean | deferred>
```

### Companion change to step 11 (Fold-in)

Workflow-gate findings fold into the same roadmap subsection as the
rest. The triage subagent already groups by `tool:` — `workflow:<path>`
just becomes one more group key.

## Scope decisions (loop-0 design notes)

These are calls I made at draft time; mark for cold-eyes scrutiny.

- **YAML parsing complexity.** The skill can shell out to `yq` if
  available (`command -v yq`), or fall back to a regex-grep for `run:
  ` lines + a follow-up grep for the invoked script. `yq` produces a
  cleaner result but isn't universally installed; the grep fallback
  is good enough for >95% of single-line `run:` directives that
  invoke a project-local script.
- **GitLab CI scope.** Mentioned in the design (`.gitlab-ci.yml`) but
  the YAML shape is different. **Stretch goal** — implement GitHub
  Actions support first, file a follow-up roadmap item for GitLab if
  any consumer asks.
- **Buildkite / CircleCI / Drone.** Out of scope. Almost all Ants
  Terminal consumers are on GitHub Actions.
- **Recursive script discovery.** A script that itself calls other
  scripts (e.g. `scripts/run-all-checks.sh`) gets enumerated once
  (the entry-point). Its internal recursion is its own contract.
- **Argument inference.** Not attempted. If the help text suggests
  required positional args, the script is deferred to manual
  invocation. Worth revisiting if a common pattern emerges.

## Invariants

- **INV-1 / Workflow walk discovers all `.yml` files.** Step 1.5 globs
  `.github/workflows/*.yml` + `.github/workflows/*.yaml`. Files missing
  from the glob are not silently skipped — empty glob is a "no
  workflows detected, skipping workflow enumeration" log line.
- **INV-2 / Step exclusion respects branch triggers.** A `run:` step
  whose containing job is `if`-gated to non-default triggers (release,
  manual, schedule-only) is NOT enumerated. Confirmed by inspecting
  the parent `jobs.<job>.if` and `on:` declarations.
- **INV-3 / Tool-name dedup beats path dedup for canonical tools.**
  A workflow step `run: pip install ruff && ruff check .` is not
  enumerated as a workflow gate — it's covered by step 1's `ruff`
  detection. For a `&&`/`;` chain, enumerate every non-builtin
  invocation in the chain, drop any whose binary name matches the
  step-1 detection table (ruff, bandit, cppcheck, semgrep, gitleaks,
  trivy, shellcheck, pytest, mypy, pyright, clazy, npm, npx, cargo,
  go, pip, python -m pytest, etc.), drop any that step 1's "Custom"
  row already probes (`tools/audit/audit.py`, `scripts/audit.sh`,
  `audit.py`, `scripts/audit_*.py`, anything routed via a
  `Makefile audit:` target). The remaining tokens — bespoke
  per-project scripts — are the workflow-gate set.
- **INV-4 / Deferred ≠ silent.** Every deferred script gets a line in
  step 10's report. The user sees the gap explicitly.
- **INV-5 / Help-probe failure is deferral, not error.** A script
  whose `--help` hangs (caught by the 2 s timeout) or exits non-zero
  without "usage:" text marks the script deferred, not the audit
  failed. The audit continues.
- **INV-6 / Path safety.** Script paths are resolved relative to the
  repo root, never executed via shell expansion of the workflow
  string. `eval`-style execution of arbitrary YAML content is
  forbidden — the skill extracts the script path, validates it's
  under the repo root (no `../` traversal), and invokes it directly.
- **INV-7 / Skill stays argument-compatible.** Existing `/audit`
  invocations (`/audit cppcheck`, `/audit --quick`, `/audit
  --no-roadmap`) behave identically before and after. The new step
  fires unconditionally on every invocation; `/audit --quick` still
  enumerates workflows but treats each as a quick-mode tool (60 s
  timeout per script).

## Tests

The skill markdown lives at `~/.claude/skills/audit/SKILL.md` —
**outside this repo**. A `tests/features/` source-scrape would have
to read from `$HOME`, which is non-portable (CI runners, fresh
checkouts, multi-user dev boxes) and tightly couples the Ants
Terminal repo to one developer's personal skill installation. That's
a bad trade.

Coverage strategy:

- **(a) Spec-anchor scrape in this repo** — a
  `tests/features/audit_skill_anchors/` test that scrapes this very
  spec file (`docs/specs/ANTS-1410.md`) for the anchor strings the
  skill must contain ("Enumerate project-local CI gates", "step 1.5",
  the INV identifiers, the exclusion list). Doesn't prove the global
  skill is current — only that the spec hasn't lost its load-bearing
  anchors during refactor. A drift-detection lower-bound.
- **(b) Manual recipe (below)** — the runbook for verifying the
  shipped skill behaves correctly on a real project tree. Re-run on
  any future skill change.

Drift between spec and shipped skill is detected by (b) on next
audit-pass invocation, not by in-CI assertion. Documented limitation
— accepted because the alternative (CI dependency on a HOME-side
file) is worse.

### Test recipe (manual)

1. From a project root with `.github/workflows/ci.yml` that runs
   `python tools/check_<thing>.py`:
2. Invoke `/audit` (no args).
3. Observe step 10's report includes a `workflow:tools/check_<thing>.py`
   line.
4. Observe the script was actually executed (check `ps` during the
   run, or `ls /tmp/audit-workflow-*-check_<thing>.txt` after).
5. Force a deferral case: rename the script to require positional
   args; re-run `/audit`; confirm the report shows `deferred`.

## RAM / build cost

Zero. The skill is markdown; nothing compiled or linked. No new files
under `src/`, `tests/`, or `ants_core_lib`.

Spec adds ~6 KB to `docs/specs/`. CHANGELOG line + ROADMAP flip + spec
file = ~7 KB total to this repo.

Test (a) adds ~2 KB of C++ source-scrape test + a CMakeLists entry.

None for end users. The skill change is transparent — `/audit`
invocations behave identically except the report grows new lines for
any project-local CI gates discovered.

## Open questions

- **`yq` vs grep fallback.** Documented as a runtime choice — the
  skill auto-detects. Worth measuring real-world parse-failure rate
  on multi-line `run:` directives (GitHub Actions supports `|` block
  scalars for multi-line scripts). If the grep fallback misses more
  than ~5% of relevant `run:` lines, mandate `yq` as a hard
  dependency for step 1.5 and degrade to no-op when missing. Defer
  measurement to first real-world use.
- **Eviction of stale `/tmp/audit-workflow-*` files.** Re-uses the
  step-7 session-ID pattern; stale-file cleanup is delegated to the
  existing per-session tmpfile sweep (out of this spec's scope).
