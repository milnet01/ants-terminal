# ANTS-3653 — citation scan: the `path:line` grammar and scrape rule

**Status:** shipped (2026-07-27) — `src/doccitations.{h,cpp}`,
`tests/features/doc_citations_scan/`. All twelve invariants have a passing
fixture; both § 5 trap rows plus INV-32's were sabotage-verified (each named
wrong implementation was built and each failed only its own fixture).
**Kind:** implement.
**Source:** split out of ANTS-3636 (user-request-2026-07-27).
**Blocked by:** ANTS-3649 — `MarkdownScan::codeSpans` and the `fenceMask`
opener overload. A continuation must fill a whole inline span and an
unterminated fence must report its opener line; neither is expressible
against today's primitives.
**Blocker for:** ANTS-3636 (`doc_citations`), which consumes this layer's
output, and ANTS-3654 (anchor-symbol drift), whose anchor rule keys on the
spans this layer locates.
**Composes with:** ANTS-3601 (`doc_integrity` — shares the fence primitives,
inverts the inline-span policy).

**Layman:** The part that reads a document and picks out every "see
`file.cpp`, line 42" pointer in it. It only finds them — looking them up on
disk is a separate step.

---

## 1. Problem

`doc_citations` (ANTS-3636) has to answer "what does this document cite?"
before it can answer "is that citation still true?". The first question is a
**pure function**: document text in, citation tokens out. No filesystem, no
path resolution, no status taxonomy, no response caps.

That makes it separable, and this spec separates it. Three things follow:

- **Its fixtures need no filesystem.** A grammar assertion is a string in and
  a token list out, so every invariant here is testable without a temp dir, a
  seeded index, or a mode-000 file — none of which say anything about whether
  the grammar is right.
- **Its invariants cannot drift against the read path.** They were sharing a
  document with the caps, statuses and wiring, and a fact restated across that
  boundary is how ANTS-3636's cold-eyes loops kept manufacturing their own
  next findings.
- **It maps to a real code boundary.** Qt6::Core-only, in `ants_core_lib`
  beside `MarkdownScan`, unit-testable without `RemoteControl` or
  `MainWindow` — the same layering ANTS-3649 used for the fence primitives.

**Output contract.** The scan emits tokens in document order, each carrying
its `raw` capture, `doc_line`, path text (or the continuation marker), parsed
loci, and the `approximate` / `partial` / `raw_clipped` flags — plus the
`unparsed[]` entries for tokens that recognise but fail validation. It marks
continuations; it does **not** resolve them. Which antecedent a continuation
inherits from is ANTS-3636 § 2.4's sticky rule, because inheritance is over
*resolved* paths and this layer has resolved nothing. Likewise fence
boundaries are reported here and the antecedent *reset* they trigger
(ANTS-3636 INV-8) is applied there.

**Limits.** `maxLocusDigits`, `maxRawChars` and every other cap named below are
fields of ANTS-3636 § 2.7's `Options` struct, which is the single source of
truth for their values. This spec names them and never restates a number — if
you find a literal here where a name belongs, that is the defect.

## 2. Grammar

Matching is two-stage: a permissive **recognise** pass finds token boundaries,
then a **validate** pass decides whether the token is a citation or a
`bad_locus`. This is not decoration — a single strict production cannot report
what it fails to match (see the locus bullet below).

```
--- stage 1: recognise (what the scanner matches) -------------------
token        := path ":" rawlocus trailing?
continuation := codespan( ":" rawlocus trailing? ) // path inherited (sticky rule below)
path         := "/"? seg ( "/" seg )*              // last seg must contain a "."
seg          := [A-Za-z0-9_.@+-]+
rawlocus     := "~"? D [ ("-" | "–") "~"? D ]      // hyphen or EN DASH
trailing     := ( "/" "~"? D )+ | "+"              // extra loci, dropped (partial)
D            := [0-9]+                             // greedy: the WHOLE digit run

A token's LEFT edge is maximal munch leftward from the colon: the scan walks
back over seg characters and "/", stopping at the first character that is
neither. In "word-src/a.cpp:12" the token is therefore the whole
word-src/a.cpp:12 -- which resolves nowhere -- never the src/a.cpp:12 inside
it. Without this rule both raw (ANTS-3636 INV-15) and the document-order column key
(INV-33) are undefined for such a token.

--- stage 2: validate (citation, or unparsed[]/bad_locus) -----------
A recognised token is a citation iff every D it kept satisfies
    len(D) <= Options::maxLocusDigits   and then   value(D) >= 1
and, for a range, start <= end. The length test runs FIRST, so no over-large
digit run is ever converted. Otherwise -> unparsed[], reason "bad_locus".
```

Five constraints that are part of the grammar, not commentary on it:

- **A continuation must fill a whole inline code span.** `` `:45` `` is a
  continuation; the `:45` inside `09:45`, or the `:1` inside `3:1`, is not.
  Without this rule the § 3 raw-line scan would harvest every clock time and
  ratio in the corpus, inherit an unrelated path, and emit *the real text of
  that file's line 45* under `status:"ok"`. The delimiters are what make a
  continuation authored rather than coincidental — delimited is what a
  continuation *is*, which is why ANTS-3636 § 1's scan C can only count them and never
  find a counterexample. A citation *with* a path is guarded by the ladder
  instead — a prose token that happens to parse as a path (`6.2:1`, ANTS-3636 § 2.4)
  resolves nowhere and lands in `unparsed[]`, so no unauthored token reaches
  `ok`. `codespan(…)` is `MarkdownScan::codeSpans`, and "fills" is tested
  against the span's content **after CommonMark's one-space strip**, so
  `` ` :45 ` `` counts — matching what a renderer shows the author. A span
  containing a newline never does.
- **`raw` is the matched token without its delimiters.** `` `:45` `` yields
  `raw:":45"`, and `` `src/a.cpp:2` `` yields `raw:"src/a.cpp:2"`. The
  backticks are grammar, not content.
- **`doc_line` is the line the citation's own first character sits on**, which
  matters only for the rare span that crosses a newline (ANTS-3636 § 2.7): such a span has
  a start line and an end line, and the citation inside it takes whichever line
  its own text begins on, not the span's. Same rule for `unparsed[]` entries.
  Stated because the ANTS-3636 § 2.1 sort order and every fixture assertion key on
  `doc_line`, so an ambiguous case would make two implementations order
  differently.
- **The dot must be in the final segment.** `src.old/README:12` does not parse
  (no dot in `README`); `docs/specs/ANTS-2161.md:5` does. The dot stands in for
  "names a file", and a directory component's dot says nothing about the leaf.
- **A locus is 1–`maxLocusDigits` digits.** **The two-stage split exists for
  this rule specifically.** The obvious single-stage spelling
  `[0-9]{1,maxLocusDigits}(?![0-9])` is safe but silent: against
  `src/a.cpp:99999999999999` it matches *nothing*, so the token is neither a
  citation nor an `unparsed[]` entry and no field reports it — it vanishes
  exactly as the `~:N` gap below does. Stage 1's greedy `D` takes the whole run
  and stage 2 rejects it as `bad_locus`, **testing `len(D)` against
  `maxLocusDigits` before converting anything**, so no over-large value ever
  reaches an `int`: identical safety to the single-stage spelling, with the
  reporting recovered. The same two stages let `:0` and `:10-5` be reported —
  both recognise cleanly and fail only validation.

Further rules:

- **En dash is not optional.** The corpus writes both `:208-228` and
  `:208–228`; a hyphen-only regex loses a large minority of the ranges (ANTS-3636 § 1).
- **Trailing loci are dropped, not guessed, and `trailing` is exhaustive.**
  `:262/265/286/300` and `:5669+` parse as their first locus with
  `partial:true` (a 2% minority, ANTS-3636 § 1). Only further `/`-separated loci and a
  single `+` are absorbed; every other character ends the token, so the `.`
  closing a sentence in `see src/a.cpp:12.` is ordinary punctuation and sets no
  flag.
- **`~` sets `approximate:true` and changes nothing else.** It is an echo so a
  reader can see the author hedged, and it is set when the tilde sits on either
  *kept* locus — `:~752` and `:208-~228` both. A `~` on a **dropped** trailing
  locus (`:262/~265`) is dropped with it. Status is computed identically for
  tilde and non-tilde loci: there is no fuzzy-match tolerance, because there is
  nothing to be tolerant *against* (a <1% minority, ANTS-3636 § 1).
- **Malformed loci are not citations.** A locus of 0, an end below its start, or
  a digit run longer than `maxLocusDigits` → `unparsed[]` with
  `reason:"bad_locus"` (stage 2). None of the three occurs in the corpus today —
  all measured at 0 by re-running ANTS-3636 § 1's `$P` scan filtered to `:0`, a
  start-above-end range, and an over-long run (2026-07-26). The rule exists so
  the read path never receives arguments it would refuse, and so that when one
  does appear it is *visible* rather than dropped.
- **Known unsupported spelling: `~:N`** (tilde *before* the colon, as in
  ``remotecontrol.cpp `~:11985` ``). **10** such tokens across 4 files
  (`grep -rhoE '~:[0-9]+' docs/ --exclude=ANTS-3636.md`, 2026-07-26, counted as
  tokens not lines), and `ROADMAP.md` ANTS-3596 names the class by that
  spelling. They match neither `token` nor `continuation`, so they are invisible
  — absent from `count` *and* from `unparsed[]`. Admitting them would mean a
  second approximate form throughout the grammar for 10 tokens; the gap is
  measured, stated, and tracked as **ANTS-3646**.
- **Two citations on one doc line are two entries**, as are two occurrences of
  the same citation. `count` is occurrences, not distinct targets; the line
  cache (ANTS-3636 § 5) makes the repeat free.

## 3. Scrape rule (inline-span masking is inverted vs. `doc_integrity`)

- **Fenced blocks are skipped**, via `MarkdownScan::fenceMask` (ANTS-3636 § 2.7). **Only
  fenced ones** — `fenceMask` does not model CommonMark's 4-space *indented*
  code blocks, so a `path:line` in one is harvested as a live claim. Accepted:
  the corpus fences its samples, and indent-tracking would need block-context
  state the primitive does not carry. A `path:line` inside a ```` ```cpp ````
  sample is illustrative text, not a claim about the repo. Shared with
  `doc_integrity`, including its ANTS-3638 list-container awareness.
- **An unterminated fence is reported, not absorbed.** `fenceMask` masks an
  unclosed fence true to end-of-input (its documented CommonMark leniency).
  Inherited silently, a single stray ```` ``` ```` would blank every citation
  after it and return `truncated:false` — a clean-looking all-clear over a
  document the verb barely read. So the response carries
  **`unterminated_fence`**, the 1-based line of the unclosed opener, omitted
  when there is none. The mask is not second-guessed (this verb does not get to
  disagree with the project's one fence parser); the reader is told. The risk is
  live: ANTS-3640 was an open-fence defect, and this spec is a doc full of
  fences *about* fences.

  **The fact is not recoverable from the mask, which is why ANTS-3636 § 2.7 adds an
  overload rather than post-processing.** `fenceMask` returns `QVector<bool>`
  and masks the closer line true as well as the opener. A document whose last
  line is a fence *closer* and one whose last line is inside an *unclosed* fence
  therefore end in the same shape — a run of `true` — with nothing in the mask
  to tell the two apart. Any rule
  inferred from the mask alone ("trailing `true` means unterminated")
  false-alarms on every doc that ends in a properly closed code block, which in
  this repo is most specs. The opener line must come from the scanner that
  already knows it.
- **Inline code spans are scanned, not masked — the POLICY inverts, the SCANNER
  is shared.** `doc_integrity` masks spans *out* before harvesting links,
  because a link inside a code span is a code sample; for citations the rule
  inverts, since the span is exactly where the data is. That is a difference in
  what the two verbs *do with* a span, not in how a span is *found*, and only
  the policy is allowed to diverge. Spans are located rather than masked because
  two rules turn on their boundaries — a continuation must fill one (§ 2) and
  an anchor must be one (ANTS-3654 § 2), neither answerable from blanked-out text.
- The scan otherwise runs on the **raw** line, so a citation with a path is
  harvested wherever it appears — bare prose (`ROADMAP.md:19418 was …`), inside
  emphasis (``**`a.cpp:1`**``), or inside link text (``[`a.cpp:1`](x)``).
- **A `doc-examples` region is skipped entirely (ANTS-3659).** An author marks a
  passage whose file references are illustrations, and no token on a masked line
  reaches `citations[]` *or* `unparsed[]`. Same shape as the fence rule above and
  computed from the same `fence` mask — a marker shown inside a fenced sample is
  sample text, not syntax. The rule exists because the documents that define this
  grammar are the ones it drowns: this spec's own family reported 58 illustrations
  against 1 real citation. `ScanResult` grows `unterminatedExamples` and
  `examplesSuppressed` alongside `unterminatedFence`; ANTS-3659 § 2 owns the
  contract and this layer's invariants are unchanged.

## 4. Invariants

**The ids are non-contiguous by design.** They keep the numbers they held in
ANTS-3636, where each is now a tombstone (`specs.md` § 5.5), so every existing
citation of INV-1, 2, 3, 9, 10, 24, 29, 32, 33, 36, 39 or 40 still resolves.
A gap here is not a missing invariant — renumbering would break every
reference in the parent and its cold-eyes log.

- **INV-1** — A `path:line` citation inside a fenced block is not harvested.
  *Test:* three tokens — `` `src/a.cpp:1` `` inside a ```` ```cpp ```` fence,
  `src/a.cpp:2` in prose, and a 4-space-**indented** `src/a.cpp:6` → **two**
  tokens, the fenced one and only the fenced one dropped. All three are written
  directory-bearing so the same fixture text is reusable by ANTS-3636's
  resolution tests; at this layer nothing resolves, and a masked fence yields no
  token at all. The indented row is not incidental: `fenceMask` models no
  indented code blocks (§ 3), so that difference is asserted rather than left
  to be discovered.
- **INV-2** — A citation is harvested from an inline code span (the inverse of
  `doc_integrity`'s link rule), from bold, from link text, and from bare prose.
  *Test:* `` `src/a.cpp:2` ``, ``**`src/a.cpp:3`**``, ``[`src/a.cpp:4`](x)`` and
  a bare `src/a.cpp:5` → four citations.
- **INV-3** — Both range separators parse: `:10-12` and `:10–12` (en dash).
  *Test:* `src/a.cpp:10-12` and `src/a.cpp:10–12` → two citations with identical
  loci. Both carry the path: written bare they would be continuations (§ 2)
  and the assertion would be about ANTS-3636 § 2.4's sticky rule instead.
- **INV-9** — `:262/265/286` and `:5669+` parse as their first locus with
  `partial:true`. *Test:* `src/a.cpp:262/265/286` and `src/a.cpp:5669+` →
  `start_line` 262 and 5669, both `partial`. Paths are written out for INV-3's
  reason.
- **INV-10** — `~` on a **kept** locus sets `approximate:true` and changes
  nothing else; on a dropped trailing locus it does not. *Test:* two fixtures
  identical but for the tilde → byte-identical apart from `approximate` and
  `raw`; plus `src/a.cpp:208-~228` → set; plus `src/a.cpp:262/~265` → `partial`
  set, `approximate` absent.
- **INV-24** — A malformed locus (0, or end below start) is not a citation:
  stage 1 recognises it, stage 2 rejects it → `unparsed[]`/`bad_locus`. *Test:*
  `src/a.cpp:0` and `src/a.cpp:10-5` → two `unparsed`, zero citations. Plus a
  `` `~:11985` `` in the same fixture → **neither** array grows: the tilde
  precedes the colon, which matches no production, so the token is invisible to
  `count` and to `unparsed[]` alike (§ 2's measured gap, ANTS-3646). Asserted
  because "invisible" is otherwise indistinguishable from "not yet
  implemented".
- **INV-29** — Two citations on one doc line, and two occurrences of the same
  citation, are two entries. *Test:* `src/a.cpp:1` twice on one line → two
  tokens. That the repeat costs only one file open is the read path's half and
  stays with ANTS-3636 INV-20's cache counter — this layer opens nothing.
- **INV-32** — A bare `:N` is a continuation only when it fills a whole inline
  code span, tested after CommonMark's one-space strip. *Test:*
  `` `src/a.cpp:1` `` then `09:45` **inside its own code span** (it contains
  `:45` but does not fill the span) and the bare-prose ratio `3:1` → one token,
  no continuation marked; a second fixture writing the continuation
  `` ` :2 ` `` → two tokens, the second **marked as a continuation**. Which
  antecedent it then inherits from is ANTS-3636 § 2.4's, not this layer's.
- **INV-33** — `citations[]` and `unparsed[]` are both in document order:
  ascending `doc_line`, then ascending column. *Test:* two citations on one line
  and one on an earlier line → line-then-column order, stable across two runs.
  Plus one inside a code span that **opens on one line and closes on the next**,
  its own text beginning on the second → `doc_line` is that second line, not the
  span's opening line (§ 2), which is what fixes its place in this order.
- **INV-36** — An unterminated fence sets `unterminated_fence` to the 1-based
  line of the unclosed opener, from `MarkdownScan::fenceMask(lines, &opener)`
  and never inferred from the mask; absent otherwise. *Test:* an unclosed
  ```` ``` ```` at line 4 with a citation at line 9 → `unterminated_fence:4`,
  `count:0`; the same fixture closed → field absent, `count:1`; plus a fence
  opening at line 4 and closing on the doc's *final* line → field absent.
- **INV-39** — `partial:true` is set by a `/`-separated extra locus or a
  trailing `+`, and by nothing else. *Test:* `src/a.cpp:262/265`,
  `src/a.cpp:5669+`, and a **bare-prose** `see src/a.cpp:12.` → the first two
  `partial`, the third key-absent with `end_line:12`. The third must be bare
  prose: inside a code span the token ends at the closing backtick, the `.` is
  never adjacent, and the assertion would hold against an implementation with no
  exhaustiveness rule at all.
- **INV-40** — A locus digit run longer than `maxLocusDigits` is **recognised
  and then rejected**: one `unparsed[]`/`bad_locus` entry, never a citation at a
  truncated line number, never silently dropped. Stage 2 tests the run's
  *length* before converting, so no over-large value is ever computed. *Test:*
  `src/a.cpp:99999999999999` → exactly one `unparsed[]` entry with that reason
  and zero citations; plus a run of exactly `maxLocusDigits` digits → a
  citation, fixing the boundary from both sides.

## 5. Tests

One feature-conformance directory, `tests/features/doc_citations_scan/`, with
`spec.md` naming this document as its contract. Every fixture in it is a
string literal and an expected token list — **no filesystem access at all**,
which is the point of the split and should stay true: a scan fixture that
needs a temp dir has drifted into ANTS-3636's lane.

Wired into an existing bundle's `SOURCES` per `tests/features/README.md`; not
a standalone `add_executable`. Uses `tests/_support/expect.h` and
`ANTS_TEST_SCOPE()` like every other feature test.

**Trap cases.** Each invariant names its own fixtures; this table adds only
what they cannot carry without growing into paragraphs — *what a plausible
implementation gets away with if that fixture is dropped*.

| INV | What passes without the fixture |
|---|---|
| 36 | an implementation deriving `unterminated_fence` from the mask — that mask also ends in a run of `true`, so it passes both the unclosed and the closed case and fails only this one |
| 40 | a strict `[0-9]{1,maxLocusDigits}(?![0-9])` production, which also yields zero citations — it just emits nothing at all, reporting neither |

Verified **RED against feature-absent code** before the implementation lands,
per the project convention.
