# ANTS-1407 — Tasks tracker mirrors CC inline view (Bundle F pull 1)

- **Status:** Draft (pre-cold-eyes).
- **Source:** user-report 2026-05-15 — two screenshots showing the
  tracker drifting from Claude Code's inline task list in opposite
  directions (undercount + overcount). Logged in ROADMAP.md at the
  Bundle F entry.
- **Lanes:** `claudetasklist` (parser).
- **Kind:** fix.

## 1. Problem

The Tasks chip / Task List dialog should mirror what the focused
Claude Code session shows in its inline task display. Two failure
modes confirmed:

### 1.a Overcount (Ants Terminal tab — this session)

| | tracker | CC inline |
|---|---|---|
| total | 40 | 0 |
| completed | 30 | (collapsed) |
| in_progress | 0 | 0 |
| pending | 8 | 0 |
| deleted (hidden) | 2 | — |

Chip reads `☰ 30/40`. CC's inline view shows zero. The 2 `deleted`
tasks inflate `total` without showing in the dialog breakdown
(30 + 0 + 8 = 38; the gap is `deleted`). The 8 "pending" entries are
historical Mode-B TaskCreates whose TaskUpdate-to-terminal events
arrived but didn't fire the ANTS-1246 batch-reset because the
reset's terminal-state set is `completed` only — a single `deleted`
or `in_progress` blocks the reset forever.

### 1.b Undercount (MAME Curator tab)

| | tracker | CC inline |
|---|---|---|
| total | 4 | 6 |
| completed | 0 | 2 |
| in_progress | 0 | 0 |
| pending | 4 | 4 |

Chip reads `☰ 0/4`. CC shows 4 pending + 1 explicit completed +
"+1 completed" rollup = 6. Most likely cause: CC fires an empty
`TodoWrite { todos: [] }` between bursts to clear its sidebar; the
parser sets `sawTodoWrite = true` and locks out all subsequent
Mode-B TaskCreate/TaskUpdate events, dropping the 2 completed
items that landed via TaskCreate after the empty TodoWrite.

### 1.c Shared diagnosis

Three independent failures in `parseTranscript`
(`src/claudetasklist.cpp`):

1. `deleted` tasks live in `m_tasks` after TaskUpdate, inflating
   `totalCount()`.
2. ANTS-1246 batch-reset (§ 2.e of `docs/specs/ANTS-1246.md`) only
   treats `completed` as terminal; `deleted` blocks the reset.
3. The `sawTodoWrite` mode-lock is sticky on *any* TodoWrite,
   including an empty one. An empty TodoWrite is semantically "no
   active todos" and should not lock out Mode B going forward.

## 2. Mechanism

Three textual changes in `src/claudetasklist.cpp::parseTranscript`.
No header / public-API change — `pendingCount()`, `inProgressCount()`,
`completedCount()`, `totalCount()` keep their signatures; the
underlying list shrinks (deleted excluded) so all four counts shift
together.

### 2.a Empty TodoWrite does not lock Mode B (TodoWrite handler)

```cpp
// BEFORE
if (name == QLatin1String("TodoWrite")) {
    out.clear();
    idxByToolUseId.clear();
    sawTodoWrite = true;
    const QJsonArray todos =
        input.value(QStringLiteral("todos")).toArray();
    for (const QJsonValue &tv : todos) {
        out.append(taskFromTodoEntry(tv.toObject()));
    }
    continue;
}

// AFTER
if (name == QLatin1String("TodoWrite")) {
    out.clear();
    idxByToolUseId.clear();
    const QJsonArray todos =
        input.value(QStringLiteral("todos")).toArray();
    // ANTS-1407: an empty TodoWrite is a "no active todos" signal,
    // not a mode commitment. Only lock out Mode B when CC actually
    // listed items via TodoWrite; an empty list lets a subsequent
    // TaskCreate resume Mode B.
    sawTodoWrite = !todos.isEmpty();
    for (const QJsonValue &tv : todos) {
        out.append(taskFromTodoEntry(tv.toObject()));
    }
    continue;
}
```

### 2.b Widen batch-reset terminal set to `{completed, deleted}` (TaskCreate handler)

```cpp
// BEFORE (TaskCreate batch-reset, ANTS-1246)
if (!out.isEmpty()) {
    bool allCompleted = true;
    for (const auto &existing : out) {
        if (existing.status != QLatin1String("completed")) {
            allCompleted = false;
            break;
        }
    }
    if (allCompleted) {
        out.clear();
        idxByToolUseId.clear();
    }
}

// AFTER
if (!out.isEmpty()) {
    // ANTS-1407: widen ANTS-1246's batch-reset terminal predicate
    // from `completed` only to `completed OR deleted`. Both are
    // terminal in TaskUpdate semantics; a `deleted` task should not
    // block a fresh burst from starting.
    bool allTerminal = true;
    for (const auto &existing : out) {
        if (existing.status != QLatin1String("completed")
                && existing.status != QLatin1String("deleted")) {
            allTerminal = false;
            break;
        }
    }
    if (allTerminal) {
        out.clear();
        idxByToolUseId.clear();
    }
}
```

### 2.c Drop `deleted` tasks at end of parse

```cpp
// At the bottom of parseTranscript(), just before `return out;`:
// ANTS-1407: `deleted` tasks live in `out` during the walk so that
// later TaskUpdate-by-id can find them, but the visible tracker
// does not surface them — dialog header sums (done + running +
// outstanding) already exclude `deleted`, and the chip's total
// should match. Drop them as a final pass.
out.erase(std::remove_if(out.begin(), out.end(),
    [](const ClaudeTask &t) {
        return t.status == QLatin1String("deleted");
    }),
    out.end());
```

Add an explicit `#include <algorithm>` at the top of
`claudetasklist.cpp` (see § 5.c).

### 2.c.i Empty-out-after-filter — no special case

If the final-pass filter removes every task (`out` was entirely
`deleted` after the walk), `out.size() == 0`, `totalCount() == 0`.
The chip's hide gate at `claudestatuswidgets.cpp:758` (`total <= 0
→ hide()`) already covers this — no separate "all-deleted" branch
needed.

### 2.d Downstream — no separate edits

`ClaudeTaskListTracker::totalCount() = m_tasks.size()` and the
dialog's `total = tasks.size()` line both already read the
post-filter list, so excluding `deleted` from `out` propagates to
both surfaces. The chip's `done/total` ratio becomes meaningful
(30/38 instead of 30/40 in the § 1.a overcount example — the
§ 2.c filter alone yields this; the § 2.b batch-reset does NOT
fire because 8 pending tasks remain in `out` mid-walk).

## 4. Invariants

| # | Lane | Statement |
|---|------|-----------|
| 1 | empty-TodoWrite | `parseTranscript` does NOT set `sawTodoWrite = true` on a TodoWrite event whose `todos` array is empty. Behavioural: `[TodoWrite todos=[]] → [TaskCreate A]` yields `totalCount() == 1` (Mode B engages because the empty TodoWrite did not lock the parser). |
| 2 | non-empty-TodoWrite | A TodoWrite with at least one entry still locks Mode B for subsequent events. Behavioural: `[TodoWrite todos=[A]] → [TaskCreate B]` yields `totalCount() == 1` (still just A; the TaskCreate is dropped because Mode A wins). |
| 3 | batch-reset-with-deleted | The Mode-B batch-reset fires when every prior task in `out` is `completed` OR `deleted`. Behavioural: `[TaskCreate A → tool_result id=A → TaskUpdate A=deleted] → [TaskCreate B → tool_result id=B]` yields `totalCount() == 1` (B only; A was dropped on the widened batch-reset, then further pruned by INV-4). The `tool_result` step is required for `TaskUpdate` to match A by `taskId` (see `claudetasklist.cpp:312-333` — `tool_result` is the only path that sets `t.id`). |
| 4 | deleted-filter | A task with status `deleted` at end of parse is removed from the returned list. Behavioural: `[TaskCreate A → tool_result id=A → TaskUpdate A=deleted]` yields `totalCount() == 0`. |
| 5 | deleted-during-walk | Mid-walk, a `deleted` task remains visible to a subsequent TaskUpdate event addressing it by `taskId` (so the parser still records subsequent updates to that id). The final-pass filter at the end of parse strips them. Behavioural: `[TaskCreate A → tool_result id=A → TaskUpdate A=deleted → TaskUpdate A=completed]` yields `totalCount() == 1` with A in `completed` state (deleted-then-resurrected, observable). The second TaskUpdate matches by `taskId` because `t.id` was set by the prior `tool_result` and the intermediate deleted-state flip preserves the id field. |
| 6 | mode-A-unchanged-when-non-empty | The existing TodoWrite snapshot-replace path is unchanged for non-empty inputs. Regression-pin against ANTS-1246-INV-8: `[TodoWrite [2 tasks]] → [TodoWrite [1 task]]` yields `totalCount() == 1`. |
| 7 | mode-A-then-mode-B-via-empty | Mode A then empty TodoWrite then Mode B: `[TodoWrite [A, B]] → [TodoWrite []] → [TaskCreate C]` yields `totalCount() == 1` (just C — Mode B resumes after the empty TodoWrite cleared the lock). |
| 8 | preserved-1246-INV-6 | The pre-existing ANTS-1246-INV-6 test passes verbatim against the post-1407 parser (all-completed prior batch still resets). |
| 9 | preserved-1246-INV-7 | The pre-existing ANTS-1246-INV-7 test passes verbatim — partial batch (any `pending` or `in_progress`) preserves prior entries. |

transitive availability.

## 7. Memory budget

Zero new allocations. Three changes:
- `sawTodoWrite = !todos.isEmpty()` — same field, different value.
- Widened `if` predicate — one extra string compare per prior
  task; same allocation footprint.
- `std::remove_if` final pass — operates in place on the existing
  `QList<ClaudeTask>`; QList's erase shrinks the vector but does
  not allocate.

Net per-rescan delta: O(N) extra string compares (N = parsed task
count, capped by transcript ≤ 16 MiB / event size). No new
fields, no caches, no signals.

## 8. Re-open conditions

- **CC introduces a new task tool name** (e.g. `Plan.Step`) with
  different semantics. Re-derive the mode-lock invariants.
- **Persistent in_progress leak** (ANTS-1341) — orthogonal but
  visible in the same surface; track separately.
- **User wants `deleted` visible in the dialog** for diagnostic
  purposes (e.g. "what did Claude drop?"). Add a "show resolved"
  toggle; not on by default.
- **CC's transcript stops emitting `status: "deleted"`** (replaces
  with a different sentinel). The filter becomes a no-op; harmless,
  but watch for a regression in the count if a new sentinel takes
  its place.

## 9. Out of scope

- Per-task timestamps + abandonment detection — ANTS-1341 territory.
- Surfacing the `+N completed` rollup that CC's inline UI shows.
  The tracker reflects the JSONL ground truth; matching CC's
  collapse-rendering is a UI affordance, not a tracker contract.
- Dialog list filtering. The list previously rendered `deleted`
  tasks in the default foreground (the existing grey-out branch at
  `claudetasklistdialog.cpp:136` matches `completed` only). Post-
  filter, `deleted` tasks no longer appear in `m_tasks` at all, so
  the list correctly stops showing them with no further edit.
- Reflecting `deleted` count in any user-visible total. They're
  hidden everywhere.
