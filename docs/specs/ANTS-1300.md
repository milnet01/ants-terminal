# ANTS-1300 — `test_results` MCP — last test run summary + failure excerpts

**Status:** spec draft (2026-05-19).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-1300 (mcp-general-claude-code-workflows-2026-05-13,
pull 34 of the post-1308 bundle plan; sibling of ANTS-1299).
**Pairs with:** ANTS-1299 (`build_status` — sibling tool, same
`.audit_cache/` cache directory, same record/read op shape).
ANTS-1310 (`validate_commit`, future — no spec yet, ROADMAP
entry only) is the planned wrapper that will gate a commit on
both caches reading clean.

## 1. Problem

Whole-suite ctest output is the biggest single token sink in
multi-step Claude workflows on this project:

- `ctest --output-on-failure 2>&1 | tail -20` collapses to ~600
  bytes when **passing**. When 1 test fails, the tail still only
  shows the last 20 lines — Claude is forced to re-run with a wider
  tail (or no tail) to see what failed. That re-shell is the same
  test run, twice.
- Failing builds re-print the same N lines of failure on every
  iteration. Across context-compacts, a later session re-reads the
  same output.
- The parsed shape — pass count, fail count, names of failing
  tests, last ~20 lines per failure — is small and stable. Caching
  it lets a later read return the compact summary instead of
  re-paging the scrollback or re-running the suite.

The cache shape mirrors ANTS-1299's `build_status` for consistency
— callers learn one op surface and apply it twice.

## 2. Goal

`test_results` returns the most-recent recorded ctest run's
`{passed, failed, skipped, total, failing_tests:[{name, excerpt}]}`
envelope without re-running the suite. Claude records the outcome
via `op=record` after each `ctest` invocation; subsequent reads
return the cached summary. A `detail=<name>` arg on `op=read`
returns the full captured excerpt for one failing test instead of
the default last-20-lines slice.

## 3. Surface

### 3.1 Tool wiring

Tool wiring mirrors ANTS-1299 § 3.1 — same Required contract, same
MCP-only surface, same dispatcher-driven op-agnostic etag injection,
same Cheap rate-limit class. Differences from the sibling:

- **Name:** `test_results`.
- **Cache file:** `<project>/.audit_cache/tests.json`.
- **Kind bucket:** `[test]` in `kindForName` (a new bucket branch
  added to the lambda alongside ANTS-1299's `[build]`).
- **Ops:** `read` (default) and `record`, as in ANTS-1299; `op=read`
  additionally accepts a `detail=<name>` selector that switches the
  return shape (see § 3.3.2).
- **Token-cost ledger:** `{QStringLiteral("test_results"), {800, 3000}}` (matches the `QStringLiteral` style of every existing entry).

The etag note from ANTS-1299 § 3.1 applies here too: the dispatcher
injects an `etag` field on every JSON response from a tool in
`isEtagSupportedTool`. `op=record` and `op=read detail=<name>`
responses therefore also carry an etag, but the field is only
semantically useful on the default `op=read` path (the two other
shapes are not stable under repeat calls).

### 3.2 Cache layout

`<project>/.audit_cache/tests.json` — single-file JSON document.
v1 schema:

```json
{
  "schema_version": 1,
  "recorded_at_ms": 1747681940000,
  "exit_code": 1,
  "passed": 417,
  "failed": 2,
  "skipped": 0,
  "total": 419,
  "failing_tests": [
    {
      "name": "BuildStatusCacheRoundtrip.WiringContract",
      "excerpt": "<last 20 lines of the test's captured output>"
    }
  ],
  "started_at_ms": 1747681900000,
  "finished_at_ms": 1747681938421,
  "duration_ms": 38421,
  "output_byte_size": 12283
}
```

Field guarantees:

- `schema_version` is `1` for this release. Unknown values → cache
  treated as absent (returns `not_cached`).
- `recorded_at_ms` is the Ants-side wall-clock ms when the cache
  was written. Always present.
- `exit_code` is the integer the caller passed in. Required for
  `record` (matches ANTS-1299; the caller already knows it from
  their shell).
- `started_at_ms` / `finished_at_ms` / `duration_ms` echo the
  caller's values when supplied, omitted otherwise. If the caller
  supplies both `duration_ms` AND a ctest `Total Test time (real)
  =` line in the output, the caller-supplied value wins (same
  policy as ANTS-1299).
- `output_byte_size` is the byte length of the caller-supplied
  output the parser was fed (mirrors ANTS-1299 § 3.2).
- `passed`, `failed`, `skipped`, `total` are integers extracted
  from the ctest summary block. When the summary is unparseable
  (e.g. the caller passed a non-ctest blob), all four are `0` and
  `failing_tests[]` is empty — the cache is still written, so a
  later read can branch on `failed=0` knowing the record exists.
  The implementer SHOULD NOT silently overwrite a prior valid
  record with a zero-record from an unparseable blob; instead the
  handler refuses with `bad_args` when neither a summary footer
  NOR any per-test line is recognised in the input (see § 3.3.1).
- `failing_tests[].excerpt` is the **last 20 lines** of the
  test's captured-output block by default. Lines are joined with
  `\n`; trailing whitespace stripped per line. Each line is
  additionally truncated at record time to 1 000 chars; the joined
  `excerpt` field is capped at 4 000 chars total (whichever bound
  hits first wins). Pathological single-line output (e.g. a giant
  JSON dump from a Qt-debug emit) therefore cannot blow the cache
  size.
- `failing_tests[].name` is the ctest test name with trailing
  whitespace and dot-fill stripped (ctest pads names with `....`
  to column ~110 before the status word; the parser strips that
  fill before storing the name).
- `duration_ms` is the caller-supplied value when present; ctest
  emits a total-wall-clock line (`Total Test time (real) = N.NN
  sec`) which the parser also tries to extract. If both are
  present, the caller-supplied value wins.
- `failing_tests[]` is capped at 50 entries (v1). When more than
  50 tests fail, `failing_tests_truncated:true` is set;
  `failed` always reflects the total (not the cap).

### 3.3 Op surface

#### § 3.3.1 — `op=record`

```json
{
  "op": "record",
  "caller_cwd": "/abs/path",
  "output": "<full stdout+stderr of the ctest run>",
  "exit_code": 1,
  "started_at_ms": 1747681900000,    // optional
  "finished_at_ms": 1747681938421,   // optional
  "duration_ms": 38421               // optional (derived if both bounds present)
}
```

Server-side flow:

1. Validate `caller_cwd` (Required contract).
2. Validate `exit_code` (integer) and `output` (non-empty string).
   Missing / wrong-typed → `bad_args`. `op` values outside
   `{record, read}` also refuse with `bad_args`.
3. Parse `output` into `{passed, failed, skipped, total,
   failing_tests, duration_ms}` via the ctest summary regex +
   per-test capture-block extraction. When NEITHER the summary
   footer NOR any per-test status line is recognised, refuse with
   `{ok:false, code:"bad_args", error: "output does not look like
   ctest"}` rather than write a zero-record over a prior valid
   cache. The zero-record path (§ 3.2 field guarantee) applies
   only when the summary parses but yields zeros (e.g. an empty
   suite ran).
4. Build the response envelope per § 3.2.
5. Write `<root>/.audit_cache/tests.json` atomically.
6. Return the envelope with `ok:true`.

#### § 3.3.2 — `op=read` (default)

```json
{
  "op": "read",                      // optional; default
  "caller_cwd": "/abs/path",
  "detail": "BuildStatusCacheRoundtrip.WiringContract",  // optional
  "etag_match": "<optional, ANTS-1499 304 pattern>"
}
```

Server-side flow:

1. Validate `caller_cwd` (Required contract).
2. Load `<root>/.audit_cache/tests.json`. If absent / malformed /
   `schema_version != 1` → `{ok:false, code:"not_cached"}`.
3. If `detail` is present:
   - Look up the matching entry in `failing_tests[]` by exact
     name match. Not found → `{ok:false, code:"detail_not_found"}`
     (the cache exists; the caller's named test was not in the
     failing list).
   - On hit, return `{ok:true, detail:{name, excerpt:<full
     captured block, not truncated>}}` — the full block is
     preserved in the cache for this purpose (see § 3.4).
4. If `detail` is absent, return the cached envelope with
   `ok:true` injected. **Before serialising**, the handler MUST
   strip the on-disk `full_excerpt` field from each
   `failing_tests[i]` so the wire shape carries only
   `{name, excerpt}`. The natural "load JSON → return JSON"
   implementation echoes every field on disk — the strip step is
   load-bearing and lives at this step explicitly (see INV-18).

Etag injection is op-agnostic at the dispatcher level (per § 3.1);
the field is only *useful* on the default (non-detail) read path.

### 3.4 Ctest output parser

The parser targets `ctest --output-on-failure` (the project's
canonical test invocation). All anchors below use `^\s*` because
ctest pads the leading `N/M` count with spaces aligned to the
total test count (e.g. `   1/1221 Test #1: …`). Recognised blocks:

**Per-test status line:** matches
`^\s*\d+/\d+\s+Test\s+#\d+:\s+(\S+)\s+\.+\s+(?:\*\*\*)?\s*(\S+)\s+\d+\.\d+\s+sec\s*$`
where capture 1 is the test name (dot-fill trailing the name is
already excluded by the `\.+` separator) and capture 2 is the
status token (`Passed`, `Failed`, `Subprocess`, `Timeout`,
`Skipped`, etc.). The optional `(?:\*\*\*)?` prefix matches
ctest's `***Failed`, `***Timeout`, `***Exception` markers (no
asterisks on the `Passed` token). Used to count
passed/failed/skipped without relying on the summary footer alone.

**Summary footer:** matches
`^\d+% tests passed,\s+(\d+) tests failed out of\s+(\d+)\s*$`.
Used to confirm the per-test count and to source `total` when
per-test parsing missed entries.

**Total time footer:** `^Total Test time \(real\) =\s+(\d+\.\d+)\s*sec\s*$`
— parsed into `duration_ms` (ms = sec × 1000) when the caller did
not supply one.

**Per-failure capture block:** spans from a per-test status line
whose capture-2 token matches `Failed|Subprocess|Timeout|Exception`
(`^\s*` prefixed as above) through to the next per-test status
line (or the summary footer, whichever comes first). The parser
keeps the FULL block in memory while parsing; § 3.2 stores the
last 20 lines per failure as `excerpt` (with the per-line and
per-excerpt caps in § 3.2). The detail-mode return path (§ 3.3)
preserves the full block in the cache as `full_excerpt` so
`detail` can return it without re-parsing — this is the one
place v1 spends extra bytes for ergonomics.

Specifically: when `op=record` writes the cache, each
`failing_tests[i]` carries `excerpt` (last 20 lines, with the
per-line + per-excerpt caps from § 3.2) AND `full_excerpt`
(whole block, capped at 8 000 chars per failure to bound disk
use). `op=read` without `detail` returns only `name + excerpt` —
the handler strips `full_excerpt` from each entry before
serialising the wire envelope (§ 3.3.2 step 4). `op=read` with
`detail` returns `{name, excerpt: <full_excerpt body>}` — the
field on the wire is always named `excerpt`, never
`full_excerpt`, because the detail-mode shape replaces the
truncated value rather than carrying both.

### 3.5 Refusal codes

All codes below are in
[`docs/standards/mcp-error-codes.md`](../standards/mcp-error-codes.md).
ANTS-1299 + ANTS-1300 add `not_cached` and `detail_not_found` to
Category 2 (Resource state) in the same commit that ships the
implementations.

- `caller_cwd_required` — Required-contract gate (dispatcher).
- `bad_args` — `op=record` without `exit_code`/`output`, wrong
  type, empty `output`, `op` not in `{record, read}`, `detail`
  set on `op=record`, or `output` that contains no recognised
  ctest summary or per-test line.
- `not_cached` — `op=read` with no cache file (or it failed
  schema check).
- `detail_not_found` — `op=read` with `detail=<name>` where
  `name` is not in `failing_tests[]` (cache exists but the test
  was not in the failing list).
- `no_project` — `resolveRootCanonical` returned empty.
- `write_failed` — `op=record` and atomic write failed.

## 5. Memory & cost budget

- Per call: one `QJsonDocument` + one `QFile`. Cache file is ≤ ~500 KiB in the worst case: 50 failures × (8 000-char `full_excerpt` cap + ~500 bytes of envelope per entry — `name`, the 4 000-char-capped `excerpt`, JSON structural keys). The `full_excerpt` is the load-bearing constant; halving it would halve the cache.
- Wire envelope on `op=read` (no detail) is much smaller — strip the on-disk `full_excerpt` and the worst-case shrinks to 50 × 4 000 ≈ 200 KiB.
- Parser is single-pass over the input string; bounded by `output_byte_size`. On the project's 1 219-test suite with 0 failures, parsing time is < 10 ms.
- Atomic write fits in one `QSaveFile` commit; no risk of partial files on crash.
- No new in-process state. Cache is read-on-demand.

## 6. Out of scope

- Running ctest server-side. v1 is record-after-test only.
- An `op=clear` op. Re-recording overwrites.
- Per-label / per-test-target caches. The cache is per-project, one slot. A `--label-regex=fast` run overwrites a full-suite record. v2 may key by label-filter.
- Non-ctest parsers (pytest, jest, go test, etc.). v1 is ctest only.
- Streaming per-test progress events. v1 is post-hoc record only.
- A history array (multiple recorded runs). Single-slot. The pattern is "compare to git log + most recent" not "diff two test runs in-process".
- `detail` returning context lines beyond the captured `full_excerpt` block. The 8 000-char per-failure cap is a hard bound; longer failures are tail-truncated at record time, not at read time.
- A `stale:true` field on `op=read` (the sibling ANTS-1299 surfaces this for build_status). Test status doesn't have a clean per-file invalidation signal — a passing suite stays passing across most source edits, and a stale-mtime probe would flag every edit as suspect. Implementer SHOULD NOT add a stale-walk by analogy with ANTS-1299; the asymmetry is deliberate.
