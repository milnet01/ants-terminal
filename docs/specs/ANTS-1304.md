# ANTS-1304 — `workspace_search` returns surrounding context lines

## Problem

The MCP `workspace_search` tool already accepts a `context` parameter
(server-clamped to 10) and forwards it to ripgrep as `--context N`.
ripgrep dutifully emits `type=="context"` events around each match in
its JSON stream — but `cmdWorkspaceSearch`'s parser
(`remotecontrol.cpp:3238`) only captures `type=="match"` events and
silently drops the context events.

Net effect: callers can ask for `context=3` and get no error, but the
response carries only the match lines. The token-saving usecase the
roadmap entry describes — "grep returned `foo.cpp:42`, now I read
`foo.cpp` to see the context" — is unmet.

ANTS-1304 closes the loop: when `context > 0`, each match carries
`context_before[]` and `context_after[]` arrays with the surrounding
lines that ripgrep emitted, attributed to the right match.

## Goal

`workspace_search(pattern=..., context=N)` returns each match with the
N surrounding lines on either side, structured as
`{file, line, text, context_before:[{line, text}], context_after:[{line, text}]}`.

## Design

### Parse loop change

In `cmdWorkspaceSearch` (`remotecontrol.cpp`), the NDJSON parse loop
ignores any event whose `type` is not `match`. Extend it to also
recognise `context` events:

- Track `lastMatchIdx` (index into `matches[]` of the most recent
  match in the current ripgrep file group). Reset on `begin` / `end`.
- Buffer "pending before" context events whose owning match has not
  yet been seen.
- On each `context` event with line `L`:
  - If `lastMatchIdx >= 0` and `L > matches[lastMatchIdx].line` and
    `L - matches[lastMatchIdx].line <= N`: append `{line, text}` to
    that match's `context_after`.
  - Else: stash `{line, text}` in the pending-before buffer.
- On each `match` event with line `M`:
  - Drain the pending-before buffer: any entry with line in
    `[M - N, M - 1]` becomes the new match's `context_before`. Drop
    older entries (they belonged to nothing reachable — `end` cleared
    them already, but defensive).

We rely on ripgrep's documented forward-only emission order: each
context line is emitted once, in line-number order, between the
matches whose windows it touches. If a future rg release ever
double-emits a context line, the after-window path takes
precedence (the line is consumed by the prior match's
`context_after` before the next match's `context_before` drain can
claim it).

### `max_results` truncation

When `matches.size() >= max_results`, the parse loop sets
`truncated = true` and skips further match events. The
`lastMatchIdx` pointer is left pointing at the final accepted match;
the window check (`L - lastMatch.line <= N`) still bounds how many
context events can attach to it. Context lines from the truncated
tail either:

- fall inside the boundary match's window and become its
  `context_after`, or
- fall outside the window, get stashed in pending-before, and are
  discarded on the next `begin`/`end` reset.

No silent over-fill of `context_after` past the documented
window. The spec does NOT specify a separate cap on
`context_after.size()` — the window itself is the cap, bounded by
`min(context, lines-between-this-match-and-next-event)`.

### Response shape

When `context == 0` (default), match objects keep their pre-1304
shape: `{file, line, text, also_at?}`.

When `context > 0`, every match carries two new keys — both arrays
that may be empty:

```json
{
  "file": "src/foo.cpp",
  "line": 42,
  "text": "    bar();",
  "context_before": [
    {"line": 40, "text": "void foo() {"},
    {"line": 41, "text": "    // call bar"}
  ],
  "context_after": [
    {"line": 43, "text": "}"}
  ]
}
```

When dedup collapses occurrences AND context is requested, the
primary carries its own surroundings; collapsed duplicates only
contribute `{file, line}` to `also_at[]`:

```json
{
  "file": "src/foo.cpp",
  "line": 42,
  "text": "    bar();",
  "context_before": [{"line": 41, "text": "    // call bar"}],
  "context_after":  [{"line": 43, "text": "}"}],
  "also_at": [
    {"file": "src/baz.cpp", "line": 17},
    {"file": "src/qux.cpp", "line": 92}
  ]
}
```

The fields are always emitted together when `context > 0`, so the
caller can rely on their presence without a probe. An empty array
means "no context lines were available on that side" (start/end of
file, or the match landed in a single-line file).

### Server clamp

The existing clamp inside `cmdWorkspaceSearch` already pins
`context` to `[0, 10]` at the parameter parse site. ANTS-1304 keeps
that clamp — surfacing the upper bound in the tools/list schema
description so callers know up front, without trial-and-error.

### Dedup interaction

The ANTS-1501 near-duplicate dedup collapses matches by
whitespace-normalised `text`. The primary keeps its
`context_before` / `context_after`; the collapsed duplicates
contribute only their `{file, line}` to `also_at[]` — their context
is discarded. Acceptable: by definition the dedupe-keyed match line
is the same text, and the surrounding lines were not the basis for
the dedup decision.

A caller who needs per-hit context (e.g. a "show me each occurrence
with its actual surroundings, not the first one's") must pass
`dedup:false`. The envelope's `dedup_collapsed > 0` counter is the
diagnostic signal that lossy collapse happened on this call.

### Schema description

The `tools/list` entry for `workspace_search` already mentions the
`context` parameter. Refresh the description so it states:

- `context` adds `context_before[]` + `context_after[]` to each
  match;
- the server clamps the value to `[0, 10]`;
- when omitted or 0, the legacy compact envelope ships.

### Resource budget

The new fields add bounded overhead per response:

- Per match: at most `2 × context` context entries (≤ 20 with the
  server clamp of 10).
- Per response: at most `max_results × 2 × context` entries —
  default ceiling is `50 × 20 = 1000` entries, the explicit cap is
  `500 × 20 = 10 000` entries. Each entry inherits ripgrep's
  `--max-columns 500` byte cap on `text`.
- Worst-case envelope inflation: ~5 MiB at the explicit cap. The
  default-config envelope grows by ≤ 500 KiB. No new caches, no
  cross-call retained state.

| 2 | When `context > 0`, every emitted match object carries `context_before` and `context_after` keys; the arrays may be empty. When `context == 0` (default), neither key appears. |

| 6 | tools/list description for `workspace_search` mentions `context_before`/`context_after` and the 10-line server cap. |

| 8 | Under `max_results` truncation, the window check in INV-4 still bounds `context_after` on the boundary match; pending-before context lines from the truncated tail are discarded at the next `begin`/`end` boundary. No accumulation past the window. |

## Tests

The existing `tests/features/mcp_workspace_search/spec.md` already
locks the wiring contract for `workspace_search`. This spec's INVs
become INV-1304-N entries appended to that file's table — mirroring
the ANTS-1452 / ANTS-1565 pattern of "sibling extension INVs as a
sub-section." The source-grep harness picks them up via the same
compile-time `SRC_REMOTECONTROL_CPP_PATH` /
`SRC_CLAUDE_INTEGRATION_CPP_PATH` slurp.

## Out of scope

- ripgrep's runtime correctness (covered by ANTS-1248 spec + manual
  smoke).
- The "attribute borderline context to the closer match" tie-break
  refinement — rg already deduplicates context events, and the
  forward-only attribution above mirrors rg's emission order.
- A new tool name (`grep_context`) — the existing `workspace_search`
  surface is the cleaner home; the roadmap entry's name was a
  description, not a binding contract.
- Capping `context_after.size()` separately from the per-match
  window. INV-4's window IS the cap; an explicit length cap is
  redundant.
