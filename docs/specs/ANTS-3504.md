# ANTS-3504 — ship-date stamp on shipped feedback findings (stale-binary self-check)

**Status:** Draft (2026-07-12) — pending cold-eyes
**Kind:** enhancement
**Source:** user-request-2026-07-12 (stamp the shipping build into feedback files so other CC sessions self-check before re-reporting)

## 1. Problem

The dominant failure mode in the `*_Ants_MCP_Feedback.md` corpus is the
**stale-binary re-report**: a contributor session running an old MCP-server
binary re-files a bug that already shipped, because it cannot tell
"not fixed yet" from "fixed — you just need to relaunch." The 2026-07-10 triage
batch alone had **8 of ~14** external findings be re-reports of already-shipped
fixes (ROADMAP ANTS-3499 tallies them); the 2026-07-12 finbreak batch added
three more (ANTS-3468 re-confirmations).

The information needed to self-check already exists on both sides but is never
joined:

- Each session's `session_orient` returns `server_build.build_commit` +
  `server_build.build_date` — *when the running binary was built*.
- A fix's ship date is recorded in its `ROADMAP.md` bullet's `Resolved <date>`
  line (parentheses optional — see §2.1) — *when the fix shipped*.

If a shipped finding carried its fix's ship-date, a contributor could compare
`build_date < shipped_date ⟹ relaunch before re-reporting`. ANTS-3499 proposed
solving this binary-side (the server computes how far behind HEAD it is), but
that needs the running binary to know where its own source repo lives — brittle
for the home-copy, location-independent binary. This spec is the simpler
feedback-file-side half: **record the ship-date where the fix is marked shipped**,
so the contributor's normal read path surfaces it.

The anchor is the **date**, not the version string: `ANTS_VERSION` (e.g.
`0.7.99`) spans many commits and cannot distinguish a pre-fix from a post-fix
build, whereas `build_date` is directly comparable to a `Resolved` date. A
short commit is intentionally NOT stamped: mapping an id → its shipping commit
is not reliably mechanical (an id may appear in several commits, or none), while
the `Resolved` date is a single, mechanically-parseable field the maintainer
already writes.

## 2. Surface

Two touch-points, both fed from the same ship-date source.

### 2.1 Ship-date source

`shipDateFor(id)` = the ISO date captured by the **last** line of the id's
`ROADMAP.md` bullet body (`RoadmapDialog::BulletRecord::body`, which carries the
bullet's continuation lines — the parser stores them with leading indent
trimmed) matching the anchored regex

```
^\s*Resolved\s+\(?(\d{4}-\d{2}-\d{2})
```

— a line-leading `Resolved` marker, then the ISO date **with or without**
surrounding parentheses. This both-forms rule is load-bearing: the live corpus
mixes `Resolved (2026-07-09):` **and** un-parenthesized `Resolved 2026-05-29:` /
`Resolved 2026-05-26 (in-session …).`, so a parens-only matcher would silently
emit no ship-date for most shipped bullets and the feature would no-op.

The `^\s*Resolved\s+\(?\d` shape is deliberately narrow: it matches only a
**line-leading** `Resolved` immediately followed by the (optionally
parenthesised) date. This excludes prose (`Resolved the deadlock` — no date
follows) AND the less-common corpus variants `… .** Resolved 2026-05-08 by …`
(mid-line, not line-leading) and `Resolved as of 2026-04-28` (a word between
`Resolved` and the date). Those variants therefore yield **no** ship-date and
fall back to the dateless stub — an accepted graceful miss, not a
correctness bug; the canonical resolution note (§ below) is line-leading.

"Last" because a bullet may carry `Progress (date)` lines and earlier
`Resolved`/`Progress` updates before its final `Resolved` line; the final
resolution is the ship date. This intra-bullet rule is **positional-last** (the
last matching line, by design), which is distinct from the cross-id rule when a
finding maps to several ids — there the stamped date is the **max** across the
per-id dates (§2.2, INV-3). When no body line matches, the id has **no**
ship-date (graceful — never fabricated). `shipDateFor(id)` is the single helper
both surfaces below (§2.2 compaction, §2.3 query) consume.

The `Resolved <date>:` resolution note is the established maintainer convention,
written via `roadmap_log op:flip` / `op:annotate` `note=` (it is a de-facto
habit, not yet a `roadmap-format.md` rule). ANTS-3504 reads it opportunistically
and degrades to the dateless form when absent, so it imposes no new authoring
obligation.

### 2.2 `compact_resolved` stub carries the date

When `compact_resolved` collapses a shipped finding, its provenance stub gains
the ship-date:

```
→ shipped ✅ 2026-07-12 (write-up compacted, ANTS-3443)
```

When no ship-date is resolvable for the finding's id(s), the stub is the
pre-3504 dateless form (`→ shipped ✅ (write-up compacted, ANTS-3443)`) — no
regression. A finding with multiple shipped ids stamps the **latest** (max) of
their ship-dates (conservative: "relaunch if your build predates the newest fix
folded in here").

**Plumbing.** The pure `FeedbackFile::compactResolved(content, opts)` renders the
stub but receives the roadmap only as the `ResolveOptions.roadmapIds` /
`.shippedIds` *sets*. ANTS-3504 adds one `ResolveOptions` field — an id→ship-date
map — that the `cmdFeedbackLog` wrapper fills from the **same**
`RoadmapDialog::parseBullets` pass that already fills those sets (running the
§2.1 regex over each ✅ bullet's `body`). The pure helper only looks the date up
per collapsed finding and picks the max; it never parses roadmap text itself, so
INV-5 (no synthesis) is tested at the wrapper's extraction and the helper's
lookup, not inside a roadmap parser.

### 2.3 `feedback_query.mapped_id_status` carries the date

Each `mapped_id_status` entry gains an optional `shipped_date`:

```json
{"id": "ANTS-3468", "status": "✅", "shipped_date": "2026-07-09"}
```

`shipped_date` is present **only** when `status == "✅"` and a `Resolved` date is
parseable for that id. This is the actionable surface: a contributor's normal
`feedback_query` read gets both the live status and the ship-date, so the
`build_date < shipped_date ⟹ relaunch` check needs no raw-file read.

**Plumbing.** `cmdFeedbackQuery` already resolves each mapped id's live status
against `ROADMAP.md` (the `mapped_id_status` builder, ANTS-3478). ANTS-3504
extends that same resolution to also run `shipDateFor(id)` (§2.1) over the id's
`RoadmapDialog::parseBullets` `body` and attach the result as `shipped_date` on
the ✅ entries — the query surface's own path, distinct from §2.2's
`ResolveOptions` map but sharing the one `shipDateFor` extraction rule.

### 2.4 Contributor convention (documented, not enforced)

A contributor, before re-reporting a finding whose `mapped_id_status` is ✅,
compares its `shipped_date` against their own `session_orient`
`server_build.build_date`. If the build predates the ship-date, the running
binary is stale — relaunch before assuming the fix did not land. Advisory only;
no verb blocks on it.

## 3. Invariants

- **INV-1** — `compact_resolved`'s collapse stub carries the ship-date captured
  by the §2.1 regex (the ✅ bullet's last `Resolved` line, parentheses optional)
  when one is parseable; otherwise the dateless pre-3504 stub is emitted verbatim
  (no regression for a bullet with no `Resolved` line).
- **INV-2** — idempotent: re-running `compact_resolved` on a file whose stubs
  already carry dates is a byte-identical no-op. The `→ shipped` already-stub
  probe still matches the dated stub, so a collapsed finding is never
  re-collapsed or double-stamped.
- **INV-3** — a finding with multiple shipped ids stamps the **maximum**
  (latest, lexicographic == chronological for `YYYY-MM-DD`) ship-date among its
  ids that have one; ids without a ship-date do not lower the max.
- **INV-4** — `feedback_query.mapped_id_status[i].shipped_date` is present iff
  that id's `status == "✅"` and a `Resolved` date is parseable; it is absent
  for non-✅ ids and for ✅ ids whose bullet has no `Resolved` line. No
  fabrication.
- **INV-5** — the stamped/echoed date is copied verbatim from the §2.1 regex's
  ISO-date capture on the bullet's `Resolved` line; the verbs never synthesise a
  date (e.g. the compaction wall-clock) when the source is absent.

## 4. Tests

`tests/features/feedback_ship_date/` (new bundle) + extensions to the existing
`feedback_log_compact_resolved` / `feedback_query` conformance:

1. **Stub carries the date** — a ✅ finding whose ROADMAP bullet body contains
   `Resolved (2026-07-12): …` collapses to `→ shipped ✅ 2026-07-12 (write-up
   compacted, ANTS-3443)`.
2. **Dateless fallback + no synthesis** — a ✅ finding whose bullet has no
   `Resolved` line collapses to the pre-3504 dateless stub, and the stub carries
   **no** date at all — the compaction wall-clock is never substituted (INV-1,
   INV-5).
3. **Idempotent** — re-running `compact_resolved` on the dated output is a
   byte-identical no-op (INV-2).
4. **Multi-id max (incl. a dateless id)** — a finding mapped to two ✅ ids with
   `Resolved` dates `2026-07-05` and `2026-07-12` stamps `2026-07-12`; and a
   finding mapped to one dated (`2026-07-12`) + one dateless ✅ id still stamps
   `2026-07-12` — the dateless id does not lower the max (INV-3).
5. **Progress-then-Resolved** — a bullet with `Progress (2026-07-01)` then
   `Resolved (2026-07-09)` stamps `2026-07-09`, not the Progress date (§2.1).
6. **Un-parenthesized form** — a bullet whose only date line is the no-paren
   `Resolved 2026-07-12: …` (and a second case `Resolved 2026-07-12 (note).`)
   stamps `2026-07-12`, proving the §2.1 both-forms regex (this is the corpus's
   majority form — C1).
7. **Prose is not a date** — a bullet body line `Resolved the deadlock in …`
   (no ISO date) yields no ship-date → dateless stub (§2.1 anchor).
8. **feedback_query shipped_date** — `mapped_id_status` carries `shipped_date`
   for a ✅ id with a `Resolved` date and omits it for a non-✅ id and for a ✅
   id without a `Resolved` line (INV-4).
9. **Wiring** — source-scrape that `cmdFeedbackLog op:compact_resolved` and
   `cmdFeedbackQuery` both populate the ship-date from the parsed bullets, and
   the `feedback_query` schema/description documents `shipped_date`.
