# ANTS-1438 — GFM-adapter bold-ID extraction handles multi-token shapes

**Status:** in flight (Vestige sweep pull 2, 2026-05-16).
**Kind:** fix.
**Lanes:** `roadmapdialog` (`parseBullets` / `extractBoldId`),
`remotecontrol` (`cmdRoadmapQuery` envelope), `ANTS-1428` (GFM adapter
follow-up).
**Source:** vestige-cc-feedback-2026-05-16.
**Pairs with:** ANTS-1428 (introduced the adapter), ANTS-1437
(section_index — both surfaced through the same envelope shape).

## Problem

Vestige CC session 2026-05-16: `roadmap_query` on Vestige's GFM-task-
list roadmap returned `bullets[].id` as a 10-char content-hash nonce
(e.g. `nwd5vars2r`) for most entries. The human-readable bold prefix
— the thing Vestige *uses* as the ID, the thing that maps to commit
prefixes — was inside the headline string, unrecoverable without
parsing prose.

Concrete bullets from `/mnt/Games/Scripts/Linux/3D_Engine/ROADMAP.md`:

```markdown
- [ ] **FW W5 (cont.)** — add a reference-regression spec ...
- [ ] **Audit X1** — Phase 3 of the audit self-learning loop ...
- [ ] **Audit/FW X2** — write a unified-pattern doc ...
- [x] **Terrain System** — wrap `environment/terrain` ...
```

Root cause: `roadmapdialog.cpp::extractBoldId` regex:

```cpp
"^\\*\\*([A-Z][A-Za-z0-9_-]{0,15})\\.\\*\\*"
```

Requires:
1. A single token (no whitespace).
2. Strict char set `[A-Z][A-Za-z0-9_-]{0,15}`.
3. **Trailing period** inside the bold (`**X.**`, not `**X**`).

None of Vestige's bullets match: they contain spaces, parens,
slashes, and have no trailing period inside the bold. So
`extractBoldId` returns false on every Vestige bullet → `boldId` is
empty → the synthetic content-hash fallback fires → user sees a
10-char nonce.

## Goal

In GFM-adapter mode (`format == "github-task-list"`):

- **Recognise** the full `**...**` prefix as the bold-ID, regardless
  of trailing period, whitespace, parens, slashes, or other
  punctuation inside the bold.
- **Expose** the bold-ID through a dedicated `bold_id` field on the
  envelope (additive — keeps `id` filled with the same value for
  back-compat callers that read `id` only).
- **Set the headline** to the prose after the `—` em-dash separator
  (Vestige's universal convention), not to a re-capture of the bold
  text. If no em-dash separator exists, fall back to the existing
  behaviour (bold text as headline).
- **Skip the synthetic content-hash fallback** when a bold-ID was
  found — that path was only ever the "no human ID exists" branch.

Native (`ants-v1`) parsing is untouched. Bullets there don't start
with `**`, so `extractBoldId` returns false regardless of regex
widening; the existing `[ANTS-NNNN]` → headline-bold path is
preserved exactly.

## Design

### Regex change

`extractBoldId` regex becomes:

```cpp
"^\\*\\*(.{1,80}?)\\*\\*"
```

Captures any non-empty bold-prefixed run at start of head, up to 80
characters, non-greedy (matches `**…**` minimally — won't span two
bold runs). 80 is generous headroom over the typical ~30-char prefix
Vestige uses; pathological "the whole headline is bold" cases are
truncated rather than mis-classified.

Trailing-period normalisation: if the captured token ends with `.`,
strip it. `**Sh4.**` (existing ants-style) and `**Sh4**` (Vestige-
style) both yield `boldId = "Sh4"`. Round-trip-stable: the trimmed
form is what consumers correlate with commit prefixes.

### Headline derivation

Existing code (lines 807-846 in `roadmapdialog.cpp`) extracts the
headline from the first `**...**` capture in body, with a fallback
to "next bold" when boldId is set and matches the first bold.

New rule for GFM mode with non-empty boldId: split `head` on the
first ` — ` (em-dash, U+2014) separator. The post-separator text is
the headline; only fall through to the existing bold-or-prose
logic when no em-dash separator exists.

The separator detection accepts both ` — ` (preferred per
roadmap-format.md examples) and ` -- ` / ` - ` (lenient fallbacks
for projects that haven't typographic-em-dashed yet). All three
shapes are bracketed by whitespace to avoid mid-word hits.

### Envelope addition

`cmdRoadmapQuery` envelope (both full-file and section paths) emits
`bold_id` when `rec.boldId` is non-empty:

```jsonc
{
  "id": "FW W5 (cont.)",
  "bold_id": "FW W5 (cont.)",
  "synthetic": false,
  "headline": "add a reference-regression spec per library formula...",
  ...
}
```

When `id` is a synthetic content-hash (no boldId, no `[ANTS-NNNN]`):
the envelope still emits `synthetic:true`, no `bold_id` field. The
two fields are mutually exclusive in practice but the spec doesn't
forbid both — a future format could carry both.

### Cross-renderer parity

`renderCardsHtml` reads `rec.id` for the card-face label. With this
fix, a Vestige card that previously showed a nonce now shows
"FW W5 (cont.)" — strictly better for the human reader. No CSS
change needed; the `rm-card-synthetic` decoration only fires when
`rec.synthetic` is true, which is now correct (skipped when boldId
exists).

## Invariants

- **INV-1 / widened regex matches multi-token bold prefixes.**
  `extractBoldId` returns true for `**FW W5 (cont.)**`,
  `**Audit/FW X2**`, `**Terrain System**`, and `**Sh4**` (no
  trailing period). Captured token is the unescaped bold content
  (with trailing `.` stripped).
- **INV-2 / existing ants-style still matches.** `**Sh4.**`
  continues to yield `boldId == "Sh4"` (trailing period stripped).
  No regression on multi-prefix ants-style projects.
- **INV-3 / native path untouched.** A bullet whose head doesn't
  start with `**` (ants-v1 native: `- ✅ [ANTS-NNNN] **Title.**`)
  produces `boldId == ""`; `extractBoldId` returns false. ants-v1
  headline derivation runs unchanged.
- **INV-4 / em-dash separator splits headline from bold-ID.**
  When `boldId` is non-empty AND `head` contains ` — ` (or ` -- `
  / ` - `), `rec.headline` is the trimmed text after the
  separator. Pre-separator bold and the separator itself are not
  in the headline.
- **INV-5 / no em-dash falls back to existing behaviour.** A
  GFM bullet with bold-ID but no separator (rare in practice but
  legal) falls through to the existing bold-or-prose headline
  path. Loop coverage: `**X**` alone, `**X** body without separator`,
  `**X**\n  continuation`.
- **INV-6 / `bold_id` envelope field present when boldId set.**
  Both full-file and section-mode paths in `cmdRoadmapQuery` emit
  `bold_id` on bullets that have a non-empty `BulletRecord::boldId`.
  When boldId is empty (native path, synthetic content-hash path),
  the field is absent (not emitted as `""`).
- **INV-7 / synthetic suppression.** When boldId is non-empty,
  `rec.synthetic` stays false and the synthetic content-hash
  branch (lines 850-856) does not fire. `rec.id` is set to
  `boldId` (existing line 805 logic, now exercised by Vestige
  cases).
- **INV-8 / round-trip via roadmap_log:flip locator.** The
  `flip` op's bold-ID locator (`bold-ID → caret anchor → headline-
  hash`) walks `rec.boldId` first. A bullet flipped by ANTS-1437's
  bold-ID (e.g. `id:"FW W5 (cont.)"`) round-trips: parseBullets
  yields the same boldId on next read. (The locator path itself
  is unchanged by this fix; the regression risk is only that the
  ID a caller supplies now matches a real parser output instead
  of failing silently.)

## RAM / build cost

`BulletRecord` gains one `QString boldId` (~24 B per record).
Typical roadmap ~600 records → ~14 KiB extra. Net wire-cost change
is positive (a 10-char nonce → 16-char human ID is +6 B/record;
across 600 GFM records ≈ +3.5 KiB on full-active responses).
Code addition: ~30 LoC in `roadmapdialog.cpp`, ~10 LoC in
`remotecontrol.cpp` (two envelope emit sites), ~200 LoC test.

## Migration

None. Existing callers reading `id` only get a human-readable value
instead of a nonce for affected bullets — strictly better. Callers
relying on `id` being a 10-char nonce specifically (none known,
nonce is documented as fallback-only) would need to read
`synthetic:true` to disambiguate, which already worked.
