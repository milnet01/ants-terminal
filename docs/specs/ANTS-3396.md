# ANTS-3396 — opt-in async `audit_run` (job handle + `audit_poll`)

**Status:** implemented 2026-07-01 (cold-eyes loops 1–4 converged clean
before implementation; loop 5 = one implementation-time refinement,
root-scoping, surfaced by the forward-completeness lint). Shipped in
`src/mainwindow.cpp` (async branch + `audit_poll` provider),
`src/claudeintegration.{h,cpp}` (job registry + `kindForName` bucket +
`callerCwdContractFor`), tests `tests/features/mcp_audit_run_async/`.
Full suite green (2402/2402).
**Kind:** enhancement.
**Source:** ROADMAP.md ANTS-3396 (cc-feedback-2026-06-30, Contact_List +
RetroDB); the live remainder of ANTS-2183 (whose doc/recovery slice
shipped 2026-06-30).
**Composes with:** ROADMAP bullet ANTS-2183 (the synchronous-path
`transport: timed out` recovery note stays for sync callers — that work
shipped as a verb-description edit, not a spec file), ANTS-1351
(`audit_run`), ANTS-1397 (in-flight gate), ANTS-1555 (`.audit_cache`),
ANTS-1569 (`last_audit_summary`).

**Layman:** A big or slow audit takes minutes, but the link between
Claude and Ants gives up after ~60 seconds. The audit actually finishes
and saves its results to disk — but Claude only sees "timed out" and
wrongly re-runs the whole expensive scan. This adds an opt-in "start it
and hand me a ticket" mode: Claude asks for the audit, gets a ticket
back instantly, and checks the ticket when it's ready. Nothing changes
for callers that don't ask for the ticket.

## 1. Problem

`audit_run` is synchronous. The handler spawns a worker thread, runs
the whole sweep, and **joins** on it before returning the envelope:

```cpp
// src/mainwindow.cpp:4579-4586
AuditRunner::RunResult r;
{
    QThread *worker = QThread::create(
        [&req, &r]() { r = AuditRunner::runAudit(req); });
    worker->start();
    worker->wait();   // blocks the dispatch thread until the sweep ends
    delete worker;
}
```

The `wait()` is a deliberate join (it does NOT pump events — that is
what avoids the ANTS-2103 foreign-socket use-after-free), but it means
the MCP response is only produced after the entire sweep finishes. On a
full-tree sweep of a mid-size repo, or a cold `semgrep` registry-rule
fetch / `trivy` / `mypy` run, the wall-clock exceeds the **Claude Code
MCP client's ~60 s request timer** (the transport cap is the client's,
not Ants's — `src/claudeintegration.cpp` documents this for
`verify_changes`; ANTS-2183 confirmed it is not raisable from Ants).

When the client cap fires it closes the socket and surfaces
`MCP error -32000: Ants MCP transport: timed out` **outside** any
response. The run, meanwhile, **completes server-side and writes a fresh
SARIF + findings JSON to `.audit_cache`** — fully recoverable via
`last_audit_summary`. But the caller has no envelope (not even the
ANTS-2032 `partial` / `incomplete_tools[]` fields), cannot tell success
from failure, and re-runs the expensive sweep.

ANTS-2183 shipped the doc/recovery half: the `audit_run` description now
points a timed-out caller at `last_audit_summary` / the envelope's
`cache_path`. The remaining fix (kept open under ANTS-2183, re-reported
as this item) is to **make the caller never block on the transport at
all** — return a job handle immediately and let the caller poll.

Rejected alternatives (from the ANTS-2183 analysis, recorded here so the
loop does not re-litigate them):

- **Raise the transport timeout** — not achievable from Ants; the timer
  is the client's.
- **Clamp the aggregate cap** so the sweep returns before ~60 s — the
  sweep writes the FULL SARIF *after* the transport gives up, so
  clamping would truncate findings. Rejected.
- **Result-offload (ANTS-2094) alone** — the failure is wall-clock, not
  envelope size. Does not help.

## 2. Surface

### 2.1 `audit_run` gains an opt-in `async` arg

- `async` (bool, default **false**). Absent / false → **today's exact
  synchronous behaviour, byte-for-byte** (INV-1). No existing caller
  changes.
- `async: true` → the handler acquires the in-flight slot, spawns the
  worker **detached** (no `wait()`), registers a job, and returns
  **immediately**:

```jsonc
{
  "ok": true,
  "async": true,
  "job_id": "audit-7",
  "status": "running",
  "started_at_ms": 1719792000000,
  "poll_with": "audit_poll",
  "note": "Sweep running server-side; poll audit_poll {job_id} or read last_audit_summary when done. Results are written to .audit_cache regardless of poll."
}
```

(The `note` value is a single line — shown wrapped here only for the
page; no newlines are emitted.)

The verb **description** is updated to recommend `async:true` for
`scope:"full"` or slow tool sets (cold `semgrep`/`trivy`/`mypy`) — the
discoverability piece, so an agent knows to opt in before it hits the
cap. The ROADMAP-bullet-ANTS-2183 sync-timeout recovery note stays for
callers who run sync anyway.

**Master gate + config.** `async` is a per-call arg, **not** a new
feature gate — there is no new Settings/`config.json` key. Both the
`async` branch and the `audit_poll` verb sit under the existing
`claude.mcp_enabled` dispatcher guard (ANTS-1901) like every verb: when
the gate is off both refuse with `mcp_disabled` before the provider
lambda runs. `async:true` does not change the in-flight semantics
(§2.5): if a sweep is already in flight for the root, the call returns
the existing `already_running` envelope whether or not `async` was set.

### 2.2 New verb `audit_poll`

`audit_poll { caller_cwd, job_id }` reads the in-memory job registry,
scoped to the caller's own project root (see the root-scoping note under
**Refusals**):

```jsonc
// running
{ "ok": true, "job_id": "audit-7", "status": "running",
  "started_at_ms": …, "elapsed_ms": … }

// done — the worker has flipped the entry and recorded the cache path
{ "ok": true, "job_id": "audit-7", "status": "done",
  "cache_path": "<root>/.audit_cache/audit-<iso>-<sha>.sarif",
  "total_raw": 142, "total_actionable": 9, "partial": false,
  "incomplete_tools": [],
  "read_full_with": "last_audit_summary" }

// done with no cached artefact — the sweep completed but the
// .audit_cache write failed (r.cachePath empty) OR there were no
// changes to scan (r.noChanges). cache_path falls back to the /tmp
// SARIF; no_changes flags the empty-changeset short-circuit.
{ "ok": true, "job_id": "audit-7", "status": "done",
  "cache_path": "<r.sarifPath /tmp fallback, or '' if neither>",
  "total_raw": 0, "total_actionable": 0,
  "no_changes": true,
  "read_full_with": "last_audit_summary" }

// error — runAudit returned ok:false (its own code/message)
{ "ok": true, "job_id": "audit-7", "status": "error",
  "code": "<runAudit code>", "error": "<message>" }

// expired — job_id never existed or was reaped from the bounded
// registry. This is a normal terminal poll STATUS, not a refusal:
// ok:true, no `code`. The durable result is still off-disk.
{ "ok": true, "job_id": "audit-7", "status": "expired",
  "hint": "job not in registry (completed long ago or evicted); read the latest result via last_audit_summary." }
```

**Branch on `status`, not `ok`, for the job outcome.** A successful
`audit_poll` always returns `ok:true` — `ok` reports whether the *poll*
succeeded, not whether the *job* did. The job outcome lives in `status`
(`running`/`done`/`error`/`expired`). A top-level `code` appears only
with `status:"error"`, where it is the failed run's job-scoped code
(NOT a poll refusal); `ok:false` + `code` is reserved for poll-level
refusals (`bad_args`, `mcp_disabled`, `caller_cwd_required`,
`too_many_jobs`). `RunResult.error` is guaranteed non-empty on failure
but `RunResult.code` is not — when `r.code` is empty the `status:"error"`
envelope omits `code` and carries the detail in `error` alone.

**`done`-envelope field mapping** (symbol-anchored — all fields verified
present in `struct RunResult`, `src/auditrunner.h`, 2026-07-01; cite by
symbol, not line, since line numbers drift):

| `done` JSON key      | `RunResult` field              |
|----------------------|--------------------------------|
| `cache_path`         | `cachePath` ⟶ else `sarifPath` |
| `total_raw`          | `totalRaw`                     |
| `total_actionable`   | `totalActionable`              |
| `partial`            | `partial`                      |
| `incomplete_tools`   | `incompleteTools`              |
| `no_changes`         | `noChanges`                    |

`cache_path` comes verbatim from `r.cachePath`; **when that is empty
(cache-write failure) the worker stamps `r.sarifPath` instead** — the
recovery story breaks otherwise. `elapsed_ms` is intentionally omitted
on `done` (the authoritative per-tool timings live in the cached SARIF's
`by_tool`); it appears only on `running` as a liveness hint.

**Refusals.** `audit_poll` is read-only, cheap, and never blocks. A
missing or non-string `job_id` → `ok:false, code:"bad_args"`; an absent
`caller_cwd` → `caller_cwd_required` (dispatcher contract); a
`caller_cwd` that is not an existing directory → `bad_cwd` (the shared
`resolveInflightCallerCwd` guard, same as `audit_run`). It is registered
in `callerCwdContractFor` as `Required` (parity with `audit_run`), under
the `claude.mcp_enabled` master gate (`mcp_disabled` when off). No new
config/Settings key (a read-only poll adds no resource).

**Root-scoping (implementation refinement, loop 5).** The job registry
lives on the single process-wide `ClaudeIntegration`, so its `audit-N`
ids form one namespace across every project a session touches. `caller_cwd`
is therefore not merely a dispatcher formality: `audit_poll` resolves it to
the same canonical root the async registration keyed on (`canon`) and a
job whose stored `root` differs reads as `status:"expired"` —
indistinguishable from a genuine miss. A session can only see its own
project's jobs; a cross-project `audit-N` probe can neither read another
root's `cache_path` nor confirm the job exists. (On this single-project
host the leak is largely theoretical, but root-anchoring every Required
verb is the established MCP isolation posture — ANTS-1404 — and it is the
honest, non-dead-code use of the `caller_cwd` the contract already
demands. The forward-completeness lint, ANTS-1642, surfaced it.)

**`cache_path` is the authoritative artefact, not `last_audit_summary`.**
`last_audit_summary` returns the **lexicographically-greatest**
`audit-<iso-utc>-<sha>.sarif` basename in `.audit_cache`
(`cmdLastAuditSummary`, `src/remotecontrol.cpp:11804-11813`) — which
equals newest-by-time only because the iso-utc timestamp prefix sorts in
time order — and is **not** keyed by `job_id`. If a second sweep
completes between this job's `done` and the caller's
`last_audit_summary` read, that read surfaces the newer run. The
`cache_path` in the live `done` envelope names this job's exact SARIF —
prefer it for an unambiguous read.

### 2.3 Job registry — clone the in-flight pattern

A new bounded, mutex-guarded registry on `ClaudeIntegration`, modelled
exactly on the existing in-flight gate
(`verbInFlightTryAcquire`/`Release`, `src/claudeintegration.cpp:9997`,
members `src/claudeintegration.h:606-617`):

```cpp
struct AuditJob {
    QString status;        // stored: "running" | "done" | "error"
                           // ("expired" is synthesised at poll time for
                           //  a registry miss — never stored here)
    QString root;          // canonical project root (== the in-flight key)
    QString cachePath;     // == r.cachePath on done, else r.sarifPath
    QString code, error;   // set on error
    qint64  startedMs = 0;
    int     totalRaw = 0, totalActionable = 0;
    bool    partial = false, noChanges = false;
    QStringList incompleteTools;
};
QHash<QString /*job_id*/, AuditJob> m_auditJobs;   // guarded by mutex
QMutex m_auditJobsMutex;
```

- `job_id` = `"audit-" + QString::number(<atomic monotonic counter>)`.
  Monotonic, no wall-clock / RNG dependence. The counter is
  **process-lifetime** and resets when Ants restarts: a `job_id` minted
  before a restart resolves to `status:"expired"` afterward (the durable
  result is still on disk). The `audit-N` id namespace is distinct from
  `last_audit_summary`'s `audit-<iso>-<sha>.sarif` cache basenames —
  they share the `audit-` prefix in logs but never collide as keys.
- The registry `root` is the **canonical** root (`canon`, the in-flight
  key — used at `src/mainwindow.cpp:4511`, declared at `:4504`), NOT the
  raw `req.projectRoot` (= `callerCwd`, `:4534`). `cachePath` is copied
  verbatim from `r.cachePath`/`r.sarifPath` by the completion slot —
  never re-derived from a root.
- **Bound:** keep at most `kAuditJobsMax = 16` entries. On insert, apply
  three ordered steps: (1) reap entries older than `kAuditJobReapMs`;
  (2) if still at the cap, evict the oldest terminal entry; (3) if there
  is still no room (all entries running), refuse `too_many_jobs` (below).
  Concretely: reap
  entries older than `kAuditJobReapMs` (= `kVerbInFlightReapMs`,
  270 000 ms — same window as the in-flight gate); if still at the cap,
  evict the oldest *terminal* (done/error) entry, ordered by `startedMs`
  (the only timestamp stored — a completion timestamp is not kept; this
  start-time ordering is a deliberate simplification, and on the
  16-entry single-project cap the start-vs-finish ordering corner is
  effectively unreachable). A running entry is never evicted. An evicted id → `audit_poll` returns
  `status:"expired"` (the result is durable on disk; INV-4). A `done`
  entry is idempotently pollable any number of times until it is reaped
  or evicted.
- **Cap saturation (all running).** The in-flight gate (§2.5) caps
  concurrent sweeps at one *per root*, but up to 16 distinct roots could
  each hold a running entry. If a 17th `audit_run {async:true}` arrives
  with no evictable terminal entry, it refuses with
  `ok:false, code:"too_many_jobs", retry_after_ms: 5000` (reusing the
  `already_running` hint value at `mainwindow.cpp:4521`); the
  synchronous path stays available. (In practice this host runs one
  project; the cap is a backstop, not an expected state.)
- **RAM budget:** ≤ 16 records × a handful of short strings
  (≈ few hundred bytes each) ≈ low single-digit KB, fixed. The multi-MB
  SARIF and findings JSON stay on disk in `.audit_cache` (already reaped
  to `kHistoryMax = 10` runs by `auditcache.cpp`). The registry holds
  liveness + a path + compact counts only — never the payload.

### 2.4 Detached worker + cross-thread completion

The async path replaces `start(); wait(); delete;` with a detached
worker that posts its result back to the **main thread** on completion:

- **The in-flight slot must outlive the handler.** The sync path
  releases it via `qScopeGuard` on scope exit
  (`src/mainwindow.cpp:4528-4531`). The guard arms at line 4528 —
  *before* the `async` arg is read or branched on — so the single safe
  contract is: on the async branch, after reading `async:true`, call
  `inFlightGuard.dismiss()` and let the completion slot own the release.
  (The current binding is `const auto inFlightGuard` at :4528;
  `dismiss()` is non-const, so the implementer must drop the `const`.)
  Leaving the guard armed would free the slot the moment the handler
  returns the job handle — allowing a duplicate concurrent sweep, then a
  double-release at completion. Do NOT instead try to "return before the
  guard is armed": the slot is acquired at :4510, so an early return
  would hold the slot with no guard at all and silently diverge from
  INV-5's dismissal test.
- Spawn the `QThread` running `runAudit(req)` (unchanged engine call);
  do not `wait()`. The worker is **created on the main/dispatch thread**
  (where the verb runs), so its thread affinity is the main thread and
  `deleteLater()` / parent-ownership in the completion slot are
  same-thread-safe (a `QThread` cannot be reparented across threads).
- On the thread's `finished` signal, a **queued** slot on the main
  thread (`QMetaObject::invokeMethod(..., Qt::QueuedConnection)` or a
  queued signal/slot) flips the job entry to `done`/`error`, stamps
  `cachePath` (`r.cachePath` if non-empty, else `r.sarifPath`) + the
  compact counts + `noChanges`, releases the in-flight slot, and
  `deleteLater()`s the worker.
- This re-introduces a cross-thread completion callback. It is safe
  because it is a **queued post to the main thread's own event loop** —
  the post is drained on a normal event-loop turn, never nested inside
  another in-flight `audit_run` dispatch. This is distinct from the
  ANTS-2103 hazard, which was *pumping the main event loop at all* while
  a foreign MCP socket call was mid-dispatch (the rationale in the
  `src/mainwindow.cpp:4566-4578` comment: the sync `wait()` is a join
  that does NOT pump events). The worker touches only its own result
  struct — it never touches `m_auditJobs`. Both the initial `running`
  insert (dispatch thread) and the terminal flip (completion slot) run
  on the main thread, so `m_auditJobsMutex` is defensive: it matches the
  `m_verbInFlightMutex` pattern and covers any future off-thread reader
  (e.g. a stats verb), not a current data race.
- **Shutdown (open implementation decision — no data at risk).** A
  detached worker still inside `runAudit` at `QCoreApplication` teardown
  is a crash class, so the completion slot **must** guard against a
  destroyed owner via a `QPointer<ClaudeIntegration>` (early-return when
  null). Beyond that guard, how a still-`running` worker is handled at
  teardown is left to the implementer and is NOT a full `wait()` join —
  joining would re-block process exit for the sweep's wall-clock, the
  very stall §1 escapes. No result is at risk either way: `runAudit`
  writes its SARIF to `.audit_cache` independently, and a pre-restart
  `job_id` resolves to `expired` on the next run (§2.3), recoverable via
  `last_audit_summary`. (No INV/Test for shutdown — it is a teardown
  policy, not part of the verb contract.)

### 2.5 In-flight gate composition

`async:true` acquires the same `(verb="audit_run", root)` in-flight slot
the sync path uses (`mainwindow.cpp:4508-4531`). A second concurrent
`audit_run` (sync or async) for the same root returns the existing
`already_running` envelope. The slot is released by the completion slot
(§2.4), not on handler return. The job thus *is* the in-flight slot for
its lifetime.

### 2.6 Out of scope

- **Semgrep registry-rule pre-warming / caching** (the third bullet of
  the ANTS-3396 fix line). Orthogonal network-caching optimisation;
  tracked as **ANTS-3398** so this spec stays a clean async-contract
  change (Karpathy: surgical, no orthogonal edits).
- A persistent (cross-restart) job ledger. Jobs are process-lifetime;
  the durable artefact is `.audit_cache` + `last_audit_summary`.
- Cancellation of a running job (`audit_cancel`). Deferred; not asked
  for by the report.

## 3. Invariants

- **INV-1** — with `async` absent or `false`, the `audit_run` envelope
  **shape and fields** are identical to the pre-ANTS-3396 synchronous
  path (no semantic regression); the `async` branch is reached only when
  `async:true`. (Run-to-run timings like `elapsed_ms` naturally vary —
  the invariant is shape, not bytes.) *Test:* source-grep that the sync
  branch is structurally unchanged + a behavioural field-set equality
  check on a trivial scoped run.
- **INV-2** — with `async:true`, the handler returns **without joining**
  the worker, carrying `{ok:true, async:true, job_id, status:"running",
  poll_with:"audit_poll"}`. *Test:* the async branch does not call
  `wait()`; envelope shape asserted.
- **INV-3** — `audit_poll {job_id}` returns `running` before completion
  and, after the worker's queued completion slot fires, `done` with
  `cache_path` + compact counts (`total_raw`, `total_actionable`,
  `partial`, `incomplete_tools`). On a cache-write failure `cache_path`
  is `r.sarifPath` (the /tmp fallback), never empty when a SARIF exists;
  on an empty changeset the entry carries `no_changes:true` +
  `total_raw:0`. A `runAudit` `ok:false` surfaces as `status:"error"`
  carrying its `code`.
- **INV-4** — the registry is bounded at `kAuditJobsMax = 16` and reaps
  entries older than `kAuditJobReapMs`; a running entry is never
  evicted; an unknown/evicted `job_id` → `status:"expired"` (`ok:true`,
  no `code`) with a `last_audit_summary` recovery hint. Recovery via
  `last_audit_summary` returns the **newest** cached SARIF, which is
  this job's result only if no later sweep has completed since — the
  live `done` envelope's `cache_path` is the exact artefact. *Test:*
  insert > 16 terminal jobs, assert size ≤ 16 and a recovery hint on the
  evicted id.
- **INV-5** — the worker→main completion is a **queued** post drained on
  a normal main-loop turn (never nested inside another `audit_run`
  dispatch — distinct from the ANTS-2103 pumping hazard); the registry
  is mutated only under `m_auditJobsMutex`. The async branch
  **dismisses the sync `qScopeGuard`** (`mainwindow.cpp:4528`) so the
  in-flight slot is released exactly once, by the completion slot.
  *Test:* source-grep for the queued-connection idiom + mutex guard +
  guard dismissal on the async branch; ThreadSanitizer-clean under the
  `debug` preset.
- **INV-6** — RAM bound is fixed and stated: ≤ `kAuditJobsMax` records ×
  ~few hundred bytes; the SARIF/findings payload stays on disk in
  `.audit_cache`. The registry never stores a finding payload.
- **INV-7** — the async path acquires and releases the same
  `(audit_run, root)` in-flight slot as the sync path; a concurrent
  `audit_run` for the same root returns `already_running`; the slot is
  released by the completion slot, not on handler return.
- **INV-8** — refusal wiring: both the `async` branch and `audit_poll`
  sit under the `claude.mcp_enabled` master gate (`mcp_disabled` when
  off); `audit_poll` with a missing/non-string `job_id` →
  `bad_args`, an unresolvable `caller_cwd` → `bad_cwd`; `audit_run
  {async:true}` at registry saturation with no evictable terminal entry →
  `too_many_jobs`. *Test:* gate-off → both refuse `mcp_disabled`;
  malformed `job_id` → `bad_args`.
- **INV-10** (loop 5) — `audit_poll` scopes the registry read to the
  caller's canonical root: a `job_id` owned by a different root reads as
  `status:"expired"`, so no cross-project `cache_path` leaks and job
  existence is not confirmable across projects. *Test:*
  `Inv3RegistryRunningThenDone` (cross-root poll of a live job → `expired`,
  no `cache_path`).
- **INV-9** — no new config/Settings key is introduced (`async` is a
  per-call arg; `audit_poll` is a read-only poll). *Test:* source-grep
  asserts no new `claude.*` key is read for these paths.

cycle against a real sweep is exercised by a scoped run with a fast tool
(e.g. a single grep-rule pass) so the poll transitions are observable
without a minutes-long fixture. That behavioural cycle test is
**CI-gated** the same way the refusal-path tests are: it is skipped when
the tool's toolchain is absent on the runner, so it cannot flake on a
minimal CI image — the source-grep + registry-bound coverage is the
unconditional part.
