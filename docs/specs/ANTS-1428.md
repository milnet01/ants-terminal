# ANTS-1428 — Adapter mode for non-Ants ROADMAP formats

**Status:** in flight (Bundle C pull 13, 2026-05-16).
**Kind:** implement.
**Lanes:** `remotecontrol`, `roadmapdialog`, `session_memory`.
**Source:** user-request-2026-05-16 + vestige-cc-feedback-2026-05-16.
**Pairs with:** ANTS-1429 (`unrecognised_format` gate), ANTS-1430
(dialect cache surface), ANTS-1431 (format-compat doc section),
ANTS-1432 (failed-call metric, used to measure adapter
effectiveness).

## Problem

`roadmap_query` against the Vestige engine roadmap
(`/mnt/Games/Scripts/Linux/3D_Engine/ROADMAP.md`, ~2130 lines,
402 KB) returns `{bullets:[], count:0}` against the
pre-ANTS-1429 surface and now returns
`{ok:false, code:"unrecognised_format"}` post-ANTS-1429. Vestige
uses the GFM task-list convention
(`- [x] **Sh4.** ...` / `- [ ] **Ed1.** ...`) with
project-specific multi-prefix short IDs.

The Ants parser anchors on the `📋/🚧/✅/💭 [PROJ-NNNN]` combo
and skips everything else. Vestige is the canary; any project
that grew out of a GitHub README task-list looks the same.

**2026-05-16 Vestige CC feedback inverted the strategy.** First
instinct was migration (rewrite Vestige's roadmap into Ants
format); the Vestige CC's response was "fix the tool, not the
file." Concrete reasons:

1. Vestige's roadmap already has IDs — just in a different shape
   (multi-prefix short form, not `[PROJ-NNNN]`); migrating would
   mean renaming hundreds of existing IDs.
2. ANTS-1429 (the silent-empty fix) is the immediate pain — fix
   that first, then adapter mode is a natural follow-on.
3. Migrating swaps visual rendering on a file the user may still
   review on github.com — the cost is asymmetric (small ongoing
   tooling benefit, real one-time aesthetic loss).

Adapter mode is the primary path; the Roadmap dialog also adapts
(not just the MCP).

## Goal

Read and write both formats. The Ants emoji format remains the
native shape — adapter mode never tries to make Ants tools
**prefer** GFM task lists, only to **handle** them.

## Design

### Tier 1 — Read-side adapter

When `roadmap.format == "github-task-list"` per ANTS-1430's
cached envelope (or when the `<!-- ants-roadmap-format: 1 -->`
marker is absent at parse time on a cache-miss path), engage the
permissive parser branch:

- `- [x]` → `status:"✅"`, `- [ ]` → `status:"📋"`.
- Heading-level completion marker. A `##`/`###` heading whose
  trailing token (post-trim, post-final-punctuation-strip)
  matches the case-insensitive regex `\b(complete|done)\b`
  causes enclosed bullets to inherit `✅` unless overridden
  inline by an emoji prefix. Worked examples that DO match:
  `## Phase 11A (COMPLETE)`, `## Phase 11A (Complete)`,
  `### Initial milestone — done`, `## v0.6 (DONE):`.
  Worked examples that DO NOT match: `## Completion criteria`
  (substring, not whole-word), `## Doneness check` (same).
- **Existing-ID preservation.** If the bullet begins with a
  `**Bold-ID.**` token (e.g. `**Sh4.**`, `**VEST-0042.**`,
  `**Ed1.**`), extract it as the stable ID. Multi-prefix
  projects work — Ants no longer assumes one prefix per repo.
  Token regex (anchored to the start of the headline,
  post-emoji-strip): `^\*\*([A-Z][A-Za-z0-9_-]{0,15})\.\*\*`.
- **Synthetic-ID fallback (content-hash).** When no bold-ID
  token is present:
  - Strip the bullet headline to a **normalised key** (lowercase,
    collapse whitespace, drop trailing punctuation).
  - `FNV-1a` **64-bit** hash of the normalised key.
  - Encode as base36, take first 10 chars.
  - Prefix with the project's `prefix_hint` from the
    `project_layout` envelope (default: uppercase first 4
    chars of the project root's leaf directory; override via
    the `prefix_hint` arg to `roadmap_log` — see § Write-side
    schema additions).
  - Example: `VESTIGE-a8f3kp2qm1`.
  - Stable across line reorders; only changes when the
    headline text itself changes. Line-number-based synthetic
    IDs (the earlier draft of this spec) were strictly worse —
    line shifts on every insert/delete.
  - `BulletRecord.synthetic = true` on these.
  - **Collision math.** Birthday-paradox on 2⁶⁴ slots gives
    p(collision) ≈ N²/(2·2⁶⁴). At N=1000 bullets that's
    ~2.7×10⁻¹⁴; at Vestige's ~600 bullets it's ~9.8×10⁻¹⁵ —
    negligible. (The earlier 32-bit draft hit ~10⁻⁴ at N=1000,
    which would have been a measurable per-document collision
    rate; 64-bit pushes it past the realistic-fleet horizon.)
    Per-document scope: the locator only compares hashes within
    a single ROADMAP.md.
- **Inline status override.** `- [ ] 🚧 **Headline** ...` is
  parsed with `status:"🚧"` (the inline emoji wins over the
  checkbox state). This rule is **unconditional** — an
  inline-emoji prefix on a `- [x]` bullet (e.g.
  `- [x] 📋 **Headline**`) parses as `status:"📋"`. Rationale:
  the inline emoji is the explicit Ants-side signal and always
  wins; the bracketed checkbox is the GitHub-side rendering
  hint. We never warn or refuse on the contradiction — the file
  may be a snapshot of a sync-in-progress state where the two
  sides legitimately disagree.
- **Theme emoji.** Heuristic from heading title — **first
  matching pattern in the listed order wins** (linear scan, no
  scoring; case-insensitive substring match):
  1. "Visual" / "Render" / "Graphics" → 🎨
  2. "Performance" / "Perf" → ⚡
  3. "Security" / "Auth" → 🔒
  4. "Test" / "QA" → 🧪
  5. "Doc" / "Documentation" → 📚
  6. "Plugin" / "Integration" → 🧩
  7. Fallback → 📂

  Worked example: `## Visual performance` → 🎨 (rule 1 matches
  first), not ⚡. Project-specific overrides are out of scope
  for v1 (Open question 1 resolution; if a project needs a
  different mapping, `.roadmap-themes.json` is the future
  escape hatch).
- `kind` / `lanes` / `layman` empty (degraded features, not
  errors) — these are Ants-format-only metadata.
- Envelope echoes `format:"github-task-list"` so callers know
  they're in adapter mode.

### Tier 2 — Write-side via Obsidian-style caret anchors

Key insight from prior-art research: Obsidian uses
`- [ ] task content ^block-id` (caret-prefix at end of line). The
caret-anchor is **invisible-on-GitHub** (renders as plain trailing
text), real-block-link-in-Obsidian, and a stable-ID-handle for
Ants. The pattern is **opt-in and incremental** — Ants never
rewrites a file just because it parsed it; the anchor only appears
on a bullet that Ants actively writes or status-flips.

#### `roadmap_log` shape changes — new `op` field

Today `cmdRoadmapLog` (`src/remotecontrol_roadmap_query.cpp`) is
**append-only with always-bump counter**: every call splices a
new bullet at the section end and rewrites `.roadmap-counter` to
`counter + 1`. Adapter mode introduces a
second mode of operation. The shape change:

```jsonc
// New schema for roadmap_log (additive — defaults preserve
// existing behaviour for callers that don't pass `op`):
{
  // --- new in this spec ---
  "op": "append" | "flip",   // default: "append" (status quo)

  // --- required for op:"flip" ---
  "id":       "Sh4" | "VEST-0042",  // OR "anchor" OR "headline"
  "anchor":   "vest-0042",
  "headline": "...",
  "to_status": "✅" | "🚧" | "📋" | "💭",

  // --- optional override for adapter mode ---
  "prefix_hint": "VEST",

  // --- required for op:"append" (existing ANTS-1424 contract,
  //     unchanged; verified in src/remotecontrol_roadmap_log.cpp) ---
  "caller_cwd": "...",       // required (Required contract)
  "section":    "...",
  "status":     "✅" | "🚧" | "📋" | "💭",
  "headline":   "...",
  "kind":       "fix" | "implement" | "doc" | "test" | "perf" | "chore",
  "source":     "...",
  // optional in op:"append":
  "body":       "...",
  "layman":     "...",
  "lanes":      ["...", "..."],
  "id_hint":    1234        // append-only: must be > counter
}
```

`caller_cwd` is required for both ops (Required contract via
`callerCwdContractFor` — see § Cross-refs to ANTS-1404). `op`
defaults to `"append"` so existing callers see no behaviour
change. The headline / status fields are required by both ops
but mean different things — for `"append"` they're inputs to
the new bullet; for `"flip"` they're a locator + the target
state.

`op:"append"` is the **status quo path** and is byte-identical
to today's behaviour, including the always-bump counter. The
existing ANTS-1424 contract (every field listed above) is
preserved unchanged.

`op:"flip"` is the **new adapter-mode path** and has its own
counter contract — see § Counter file below. `id_hint` is
**not** accepted under `op:"flip"` (the locator selects the
target bullet; a counter hint is meaningless when the verb
isn't allocating a new ID). Passing both is a `bad_op_combo`
refusal — see § Error code taxonomy.

#### Anchor placement

```text
- [ ] **Headline** — body text ^prefix-NNNN
  Continuation line if needed.
```

The anchor is on the **last line of the headline content**
(defined as the contiguous run of non-blank lines after the
bullet token and before any `Lanes:` / `Kind:` / `Source:`
metadata block). Whitespace is preserved byte-for-byte except
the trailing newline. Anchor placement rules:

1. **Existing anchor preserved.** If the line already ends with
   `\^[a-z0-9-]+\s*$`, that anchor is the existing locator —
   Ants does NOT inject a second one; subsequent flips reuse
   the existing anchor unchanged.
2. **Fenced code-block refusal.** If the bullet headline is
   inside an open fenced code block (\`\`\` ... \`\`\`), the
   write refuses with
   `{ok:false, code:"anchor_unsafe_context",
     error:"cannot inject caret anchor inside a fenced code
     block"}`. See § Error code taxonomy below for where this
   joins the project's MCP error-code set.
3. **Inline-code tolerated.** Inline code with a literal `^`
   inside backticks (e.g. \`A^B\`) is fine — the new anchor is
   appended after a space and after the closing backtick, so
   the line reads as two separate caret tokens (the inline-code
   one is plain text on GitHub, the trailing one is the
   anchor).
4. **Single-line bullets** (no continuation) get the anchor on
   the same line as the headline.

#### Counter file

`.roadmap-counter` lives at project root just like Ants.

**Counter semantics under `op:"flip"`:** counter advances only
when an anchor is **actually injected**. Specifically:

- Locate the bullet (bold-ID / anchor / headline order — see
  Status-flip locator below).
- If the located bullet has a bold-ID **or** an existing
  anchor: flip the status token, **do not advance the
  counter**, **do not rewrite `.roadmap-counter`**. The
  existing identifier is the durable locator; the counter is
  not consumed.
- If the located bullet has neither: read the counter,
  compute `newId = counter + 1`, inject `^prefix-newId`,
  rewrite `.roadmap-counter` atomically to `newId`. Counter
  advances exactly once per anchor injection.
- If the locator **fails** (zero matches or > 1 match): refuse
  the write per § Status-flip locator INV-7; counter
  unchanged, ROADMAP unchanged.

**Open question 4 (now resolved):** single shared counter,
prefix-stamped at write time. Per-prefix high-water-mark
counters (`.roadmap-counter.Sh = 8`) would force the adapter
to discover all live prefixes on every write — strictly more
state for no measurable benefit. The prefix comes from
`caller_cwd`'s project root leaf-dir uppercased (override via
`prefix_hint` in `roadmap_log`).

**Concurrency.** Counter writes use `QSaveFile`'s atomic
write-then-rename (already in use in
`cmdRoadmapLogAppend`). Two MCP calls racing on the
same project will end up with one of the two counter values —
the loser's anchor is invalid (its `newId` collides) and the
write should be retried by re-running the verb. The retry
detects the now-existing anchor and falls into the
"no-counter-bump" branch. v1 accepts the race — the rc socket
is UID-scoped (per CLAUDE.md `remotecontrol` § lines 54–57:
"UID-scoped + 0700 perms + `lstat`-checked `S_ISSOCK`"). The
socket is single-listener (one Ants process per UID instance
hosts the rc server), but multiple MCP clients can connect to
the same listener concurrently; v1 accepts the resulting low
contention probability without explicit locking. Defer
explicit `flock`-based serialisation to a follow-up if a real
workload surfaces collisions.

#### Status-flip locator

When `roadmap_log op:"flip"` is told to flip a bullet's status,
locate it in this order:

1. **By bold-ID token.** If the request carries
   `id:"Sh4"` or `id:"VEST-0042"`, match
   `^\*\*Sh4\.\*\*` or `^\*\*VEST-0042\.\*\*` (regex-anchored).
2. **By caret anchor.** If the request carries
   `anchor:"vest-0042"`, match `\^vest-0042\s*$` at any line
   end inside the document.
3. **By headline.** If the request carries `headline:"..."`,
   normalise the headline (same rule as synthetic-ID), then
   match the normalised first-line of each bullet. FNV-1a 64-bit
   hash-equality is the disambiguator; collision probability at
   document scale is negligible (see Tier 1 § Synthetic-ID
   collision math), but the spec still handles the > 1 match
   case — see "match-failure handling" below.

**Both-handle resolution.** When a bullet carries BOTH a bold-ID
AND a caret anchor on the same line (legal but unusual — e.g.
hand-injected anchor on a multi-prefix project), the bold-ID is
the **canonical handle**. INV-5's pre-condition for anchor
injection is "neither bold-ID nor existing anchor"; Ants never
injects an anchor onto a bold-ID'd bullet. When BOTH `id` and
`anchor` are passed in the request, locate by bold-ID first
(rule 1) and ignore the `anchor` arg.

4. **Match-failure handling.** When zero matches OR > 1 match,
   refuse:
   ```jsonc
   {
     "ok": false,
     "code": "bullet_not_found",
     "matched": 0,
     "suggestions": [
       {"headline": "...", "anchor": "..."},
       ...
     ]
   }
   ```
   Never blind-write. The suggestions list returns up to 3
   nearest-neighbour bullets by headline-prefix match.

#### Anchor injection on first touch

If the located bullet has neither a bold-ID nor an existing
anchor, Ants injects an anchor on the **same write** that flips
the status. The next status-flip uses the anchor as the locator
(no re-search). Anchors persist across edits; rebooting Ants
doesn't invalidate them.

#### In-progress / deferred states

`🚧` (in progress) and `💭` (deferred / idea) have no GFM
checkbox equivalent. Adapter writes them as inline emoji prefix:

```text
- [ ] 🚧 **Headline** — body ^vest-0042
- [ ] 💭 **Headline** — body ^vest-0043
```

Both render as **unchecked + in-progress** on GitHub (the
checkbox stays empty, the emoji is just text), and as the
correct emoji status in Ants. `✅` is `- [x]` (no emoji prefix
needed). `📋` is `- [ ]` (also no emoji prefix needed).

### Tier 3 — One-shot `roadmap_migrate` MCP verb (deferred)

Out of scope for v1. The adapter handles read + write in-place;
explicit migration is reserved for the case where a project
deliberately wants to switch to Ants native format. The
2026-05-16 Vestige migration prompt drafted earlier stands as
the reference workflow when this surface lands.

### Round-trip strategy

Research (remark-stringify docs, mdast-util-from-markdown) confirmed
that **complete AST round-trip is impossible** — markdown is not a
bijection between text and AST. Strategy: **line-locator surgery,
not AST rewrite.** The Ants line-oriented parser:

1. Walks the file once recording each top-level bullet's
   start/end line range.
2. To flip a status: identifies the line(s) carrying the
   `- [ ]` / `- [x]` token, rewrites just those characters,
   preserves everything else byte-for-byte (whitespace,
   continuation lines, inline emphasis).
3. To inject an anchor: appends `^prefix-NNNN` to the last line
   of the bullet's headline content, before any
   `Lanes:` / `Kind:` lines.

Byte-for-byte preservation of unchanged regions means the file's
diff stays minimal — easy to review on GitHub, doesn't trip
pre-existing CI line-numbered checks (none in Vestige; relevant
for future consumers).

### Library choice

**Don't add `cmark-gfm` or `remark` as a dependency.** Ants'
existing line-oriented parser handles 95% of cases and is
auditable; adapter mode adds:

- ~150 LoC of shape-detection on the read side
  (`roadmapdialog.cpp::parseBulletsGfm`).
- ~250 LoC of locator-surgery on the write side
  (`remotecontrol_roadmap_query.cpp::cmdRoadmapLog` extension).
- ~80 LoC for the dialog renderer to recognize the GFM bullet
  shape (`roadmapdialog.cpp::renderCardsHtml` GFM branch).

If the line-oriented approach hits a recursive-list edge case
that genuinely needs a real markdown AST, the fallback is
`cmark-gfm` (C library, linkable, GitHub's own fork). For v1 it
doesn't earn its dependency weight.

### Dialect cache hand-off (ANTS-1430)

First call on a project triggers `project_layout` scan; the
detected dialect (`roadmap.format`) persists until TTL expires
or any scanned-path mtime advances. Subsequent calls hit the
cache — no re-parse of the format header on every query.

This means **ANTS-1430 ships first** even though they land the
same week. The adapter's read path consults the
`session_memory[project_layout].roadmap.format` field before
deciding which parser branch to run.

## Invariants

- **INV-1 / Read-side detection.** When the file has no
  `<!-- ants-roadmap-format: 1 -->` marker AND contains ≥ 1
  `^- \[[ x]\]` line in its first 100 non-empty lines, the
  adapter parser engages. When the marker is present, the
  native parser engages regardless of file content. **Note:**
  this is the cache-miss path; INV-9 short-circuits it when
  `project_layout.roadmap.format` is fresh in the
  `session_memory` cache (ANTS-1430).
- **INV-2 / Existing-ID preservation.** A bullet with a
  `**Bold-ID.**` token reports that token as `BulletRecord.id`
  with `synthetic == false`. Multi-prefix projects work without
  any per-project configuration.
- **INV-3 / Synthetic-ID stability.** A bullet with no bold-ID
  token reports a content-hash-derived ID with
  `synthetic == true`. The ID is stable across line moves and
  whitespace edits; it only changes when the headline text
  itself changes.
- **INV-4 / Status mapping.** `- [x]` → `status:"✅"`,
  `- [ ]` → `status:"📋"`, unless an inline emoji prefix
  overrides.
- **INV-5 / Write-side anchor injection.** When
  `cmdRoadmapLog` flips a bullet's status on a GFM-format
  roadmap and the bullet has neither a bold-ID nor a caret
  anchor, the same write injects a `^prefix-NNNN` anchor on
  the last line of the headline content.
- **INV-6 / Line-locator surgery.** Every byte outside the
  located bullet's status token and the (optional) injected
  anchor is byte-identical before and after the write.
- **INV-7 / Status-flip locator order.** Locator tries bold-ID
  → caret anchor → headline hash in that order. On zero or
  > 1 matches the call refuses with `code:"bullet_not_found"`;
  blind-write is never legal.
- **INV-8 / Counter consumes only on write.** A failed locator
  call must NOT advance `.roadmap-counter`. A successful flip
  that doesn't need a new anchor (bold-ID or existing anchor
  present) also doesn't advance the counter.
- **INV-9 / Dialect cache hand-off.** When
  `session_memory[project_layout].roadmap.format ==
  "github-task-list"`, the adapter engages without re-reading
  the file header. When the cache is absent or stale, the
  adapter re-detects.
- **INV-10 / Dialog renderer parity.** When `parseBullets`
  engages adapter mode, `RoadmapDialog::renderCardsHtml`
  emits one card per GFM bullet with:
  - status icon mapped per INV-4 (`- [x]` → ✅, `- [ ]` → 📋,
    inline-emoji override wins);
  - headline preserved with bold formatting;
  - `kind`/`lanes`/`layman` chips suppressed when the underlying
    `BulletRecord` field is empty (degraded gracefully, no
    placeholder text);
  - bullet ID rendered (bold-ID token verbatim if present,
    synthetic ID with `prefix-hash` shape otherwise);
  - `synthetic == true` cards get a small marker (CSS class
    `rm-card-synthetic`) so the user can tell hand-authored
    bullets from auto-anchored ones at a glance.
- **INV-11 / `prefix_hint` default.** When `roadmap_log
  op:"flip"` is called and the bullet needs anchor injection,
  the prefix is taken from the request's `prefix_hint` field
  if present (regex `^[A-Z][A-Z0-9_-]{0,15}$`); otherwise it
  defaults to the uppercase first 4 chars of the project root's
  leaf directory (e.g. `caller_cwd:/home/user/Vestige` →
  prefix `VEST`).
- **INV-12 / Both-handle resolution.** When a bullet carries
  both a `**Bold-ID.**` token AND a caret anchor on the same
  line, the bold-ID is the canonical handle: locator rule 1
  matches and the anchor is non-authoritative. Ants never
  injects a new anchor onto a bold-ID'd bullet (INV-5's
  pre-condition is "neither bold-ID nor existing anchor").
  When the request carries both `id` AND `anchor` args, the
  `anchor` arg is ignored.
- **INV-13 / Fenced-code refusal.** When the located bullet's
  headline line is inside an open triple-backtick fenced code
  block, the write refuses with
  `code:"anchor_unsafe_context"`; no ROADMAP write, no
  counter bump.

## Error code taxonomy

New error codes introduced by this ticket join the existing
`roadmap_log` codes in `src/remotecontrol_roadmap_query.cpp`. The
full per-verb set after this ship:

| Code                     | Verb side      | Meaning |
|--------------------------|----------------|---------|
| `no_roadmap`             | both ops       | ROADMAP.md missing under caller_cwd |
| `counter_read_failed`    | append         | `.roadmap-counter` unreadable or non-numeric |
| `counter_write_failed`   | append + flip  | Atomic counter rewrite failed |
| `roadmap_read_failed`    | both ops       | ROADMAP.md unreadable |
| `roadmap_write_failed`   | both ops       | Atomic ROADMAP rewrite failed |
| `unrecognised_format`    | both ops       | File parses zero bullets and exceeds the 1 KB threshold (ANTS-1429) |
| `bad_section`            | append         | Unknown section slug |
| `id_taken`               | append         | `id_hint` ≤ current counter |
| `bullet_not_found`       | flip (NEW)     | Locator returned zero matches; envelope carries `suggestions[]` (≤ 3 nearest-neighbour bullets by headline-prefix match) |
| `bullet_ambiguous`       | flip (NEW)     | Locator returned > 1 match; envelope carries `matched: N` AND `suggestions[]` (the N actual matches, for caller disambiguation) |
| `anchor_unsafe_context`  | flip (NEW)     | Headline line is inside a fenced code block |
| `bad_op_combo`           | flip (NEW)     | Incompatible argument combination (e.g. `id_hint` under `op:"flip"`, or two locator keys when only one is permitted). Name fits the existing `bad_<noun>` shape (`bad_status`, `bad_kind`, `bad_section`) — the `<noun>` here is "op-combo" since the validity depends on the `op` value. |

`anchor_unsafe_context` is sibling to `unrecognised_format` —
both describe a file-shape state that makes the requested
operation unsafe. The `_unsafe_context` suffix is reserved for
"file shape blocks this operation" codes; future adapter-mode
write paths will reuse it for analogous cases (e.g. anchor on
a bullet that crosses an HTML comment boundary).

## Out of scope v1

- Phase-to-release heading restructuring (Vestige's
  `## Phase 11A` → `## 0.x.y — gameplay` mapping needs human
  judgment).
- `roadmap_migrate` MCP verb (Tier 3 above) — deferred.
- Round-trip of `<details>` / `<summary>` collapsible sections
  Vestige uses for archives — adapter parses the visible
  bullets only; collapsed sections are out of contract.
- AppStream-metainfo-style category emoji prefixes (Vestige's
  `## ✨ Visual quality` heading — supported via theme-emoji
  heuristic but not extracted as a structured field).
- **Nested GFM bullets** (indented `  - [ ]` sub-tasks). The
  adapter parses only top-level bullets, matching the native
  parser's behaviour in `roadmapdialog.cpp::parseBullets` —
  two-space indentation is treated as a continuation of the
  parent bullet, not as a new bullet. Vestige's roadmap uses
  nested bullets in a few sections; those sub-tasks are
  preserved as body text on their parent bullet's record and
  are not surfaced as independent records.
- Per-project theme override (`.roadmap-themes.json`) —
  deferred. The heuristic in § Tier 1 is the v1 surface; if a
  real project needs a different mapping, the override file is
  the natural escape hatch.

## RAM budget

- **Read-side.** Parser allocates one `QString` per bullet
  body (already does this for native format). GFM branch adds
  ~32 B per bullet for the synthetic-ID cache. On Vestige's
  ~600 bullets, that's ~19 KiB additional resident — fully
  within scrollback-budget territory.
- **Write-side.** `cmdRoadmapLog` reads the whole roadmap into
  memory (already does this — 400 KB Vestige fits in a single
  QByteArray). Locator surgery is O(N lines) in pass, O(1) in
  additional memory.
- **Cache surface.** Dialect detection result is stored in
  `project_layout.roadmap.format` (one short string, ~20 B per
  project) — covered by ANTS-1430's RAM budget.

Total feature footprint: **< 25 KiB resident** per active GFM
roadmap, transient (released on next garbage cycle).

## Migration

None for **callers**. Existing `roadmap_query` calls against
Ants-native roadmaps continue to return the same envelope shape.
Existing `roadmap_log` calls without an `op` field default to
`op:"append"`, byte-identical to today's behaviour.

New behaviour for **GFM-task-list roadmaps**:
- `roadmap_query` returns `format:"github-task-list"` in the
  envelope, populates `bullets[]` with adapter-mode parsing,
  drops `kind`/`lanes`/`layman` to empty strings (these are
  Ants-format-only).
- `roadmap_log op:"flip"` injects `^prefix-NNNN` anchors on
  first touch of a bullet that needs one. The anchors render
  as plain trailing text on GitHub; users may strip them on
  the next hand-edit (the adapter falls back to headline match
  on subsequent flips).
