# ANTS-2126 — `roadmap_log` heading-format writer (`#### Pass N.M`)

**Status:** implemented + shipped (2026-06-15); accepted 2026-06-12, cold-eyes loops 1–5 folded. See commit `ANTS-2126` + `tests/features/mcp_roadmap_log_pass_writer/`.
**Kind:** enhancement.
**Source:** ROADMAP.md ANTS-2126 (cross-session-2026-06-12 RetroDB, follow-on to ANTS-2031).
**Pairs with:** ANTS-2031 (shipped the `format_mismatch` refusal this spec replaces with a real writer).
**Composes with:** ANTS-1530 (the pass-headings *reader* whose model the writer mirrors).

## 1. Problem

RetroDB's `roadmap.md` is a **heading-format** roadmap: work items are
`#### Pass N.M <Title>` level-4 headings with a `- **Status**: <word>`
sub-bullet and prose, not GFM `- **headline** (id)` bullets. The reader
handles it — `parsePassHeadingBullets` in `src/roadmapdialog.cpp:763`
classifies the doc as `pass-headings` and synthesises a `PASS-N-M` id
per pass (`roadmapdialog.cpp:867-870`).

The **writer** does not. ANTS-2031 shipped only a *refusal*:
`rcBulletsArePassHeadings` (`src/remotecontrol.cpp:209`) detects the
format and all five `roadmap_log` write paths return
`rcPassHeadingsWriteRefusal` (`remotecontrol.cpp:220`) with
`code:"format_mismatch"`. The bullet (ANTS-2031) explicitly scoped that
as "the minimum-viable warning … a real heading-format writer remains
future work."

Consequence (RetroDB re-confirmed on v3.7.0, 2026-06-12): a session that
needs to (1) flip a pass's status `todo → done`, or (2) append a new
`#### Pass 43.5` section, falls back to hand-`Edit` for **both** — the
exact two operations a roadmap maintainer performs most. The fallback
ergonomics are good (the refusal hint says "Edit directly"), but the
token-frugal write path the GFM/ants-v1 formats enjoy is absent for this
format.

**Layman:** Ants can *read* heading-style to-do lists but can't *write*
to them. This adds the writing — both ticking off an item and adding a
new one.

## 2. Surface

The design **replaces the refusal with a route** at four of the five
gate sites: `op:append`, `op:append_batch`, `op:flip`, `op:flip_batch`
(and `op:annotate`, which shares the flip path). `op:create_section`
keeps refusing (§ 5, out of scope). Detection is unchanged —
`rcBulletsArePassHeadings` still gates; it now dispatches to a writer
instead of returning a refusal. The format-detection heuristic itself
(including the ANTS-2048 rule that a stray `- [ ]` checkbox does **not**
flip a pass-headings doc to GFM) is untouched — only the post-detection
action changes (INV-1).

All new code lives in `src/remotecontrol.cpp` (the write handlers) plus
a small pure helper file `src/passheadingwrite.{h,cpp}` joining
`ants_core_lib` (the splice/flip primitives, unit-testable without the
`m_main` guard — mirrors `changeloglog.{h,cpp}`).

### 2.1 Status-keyword mapping (single source of truth)

The writer and reader must agree on the keyword ⇄ emoji map. The reader
classifies in `roadmapdialog.cpp:872-889`. `passStatusKeyword` is the
inverse — a **total function** over the four roadmap_log status values,
emitting exactly one canonical keyword each:

```cpp
// src/passheadingwrite.h — the canonical write keyword for a status.
// Total over the roadmap_log status/to_status enum; the single keyword
// it emits re-parses through the reader (roadmapdialog.cpp:872-889) to
// the intended emoji.
//   planned      → "todo"        (reader: else-branch → 📋)
//   in-progress  → "in-progress" (reader: 🚧)
//   shipped      → "done"        (reader: ✅)
//   considered   → "deferred"    (reader: 💭)
QString passStatusKeyword(const QString &roadmapStatus);
```

The reader *accepts* more inbound keywords than the writer emits
(`done`/`shipped`/`completed` → ✅; `deferred`/`considered`/`parked` →
💭; `roadmapdialog.cpp:872-889`). `passStatusKeyword` deliberately emits
one canonical keyword per status (e.g. `shipped → "done"`, never
`"shipped"`); the extra synonyms are read-only and never written. This
keeps INV-11 / INV-12 round-trips unambiguous.

The roadmap_log `status` (append) / `to_status` (flip) enum is already
`planned | in-progress | shipped | considered`
(`remotecontrol.cpp` schema). No new enum.

### 2.2 `op:append` — write a new `#### Pass` block

When the target roadmap is pass-headings, `op:append` renders a pass
block instead of a GFM bullet. The pass designator is **caller-supplied**
(pass ids are not counter-allocated — § 2.5), via a new optional arg:

```
pass   string  e.g. "43.5" or "43.5.B"
               validated ^\d+\.\d+(?:\.[A-Za-z][A-Za-z0-9]*)?$
               REQUIRED when the target is a pass-headings roadmap;
               ignored on GFM / ants-v1 roadmaps.
```

Rendered block (inserted at the end of the `section` slug's body, before
the next `##`/`###` heading of equal-or-higher level — or, when the
section heading is immediately followed by the next heading with no body
in between, directly under the section heading; INV-15):

```markdown
#### Pass <pass> <headline>
- **Status**: <keyword>
<body, verbatim, blank-line-separated>
```

- `headline` (existing arg) is the title tail. A `(SEVERITY, SIZE)` meta
  prefix, if wanted, is written as part of `headline` (§ 5, OQ-5).
- `status` (existing arg) → `passStatusKeyword`, written in keyword
  form (OQ-2). **Required** — an absent `status` refuses `bad_args`, no
  silent default. (The GFM/ants-v1 `op:append` guard at
  `remotecontrol.cpp:4209` also requires `status`, but emits the
  *undocumented* `missing_field`; the pass path uses the documented
  `bad_args` — see § 6 / ANTS-2128.) The status-required refusal is
  folded into INV-3.
- `pass` absent or malformed → `bad_args` (INV-3); the documented code
  for a missing/ill-shaped required arg (defined in INV-3).
- `body` (existing arg) is written verbatim under the Status line.
- `kind` / `source` / `lanes` / `layman` are **not** emitted (the
  pass-headings format has no slot for them); passing them is accepted
  and ignored, not refused.
- `.roadmap-counter` is **not** touched (§ 2.5).
- Return envelope: `{ok, id:"PASS-<major>-<minor>[-<sub>]", file, line,
  format:"pass-headings", bytes_written}` — `id` is the same value the
  reader would synthesise for the block just written (round-trip, INV-12).
  `bytes_written` (the written block's UTF-8 byte size) mirrors the GFM
  append envelope's field (`remotecontrol.cpp:4675`); `line` is the
  1-based line of the new `#### Pass` heading.

`op:append_batch` applies N such blocks in one read + one atomic commit,
per-block failures landing in `skipped[]` (parity with the GFM batch).

### 2.3 `op:flip` / `op:flip_batch` — rewrite a pass's Status line

The flip locates a pass by its **reader-synthesised id** (`PASS-N-M` or
`PASS-N-M-SUB`) via the existing `id` locator — a caller does
`roadmap_query` (which returns those ids) then flips by id, no new
locator arg. `headline` (hash-match on the pass title) is also accepted.

Algorithm (pure helper `flipPassStatus`):

1. Walk lines for the `#### Pass <major>.<minor>[.<sub>] …` heading whose
   synthesised id equals the locator (reuse `rxHead` from the reader).
2. From the heading, scan forward (bounded by the next `#`-heading of
   level ≤ 4, or 50 lines — same window as the reader) for the **first**
   `- **Status**:` line (reuse `rxStatusLine`).
3. Rewrite that line's value to `passStatusKeyword(to_status)`,
   **preserving the line's existing style** (INV-5):
   - keyword-only (`- **Status**: todo`) → `- **Status**: done`
   - emoji+keyword (`- **Status**: ✅ Done`) → `- **Status**: 🚧 In-progress`
   - emoji-only (`- **Status**: ✅`) → `- **Status**: 🚧`
   Any emoji the writer emits is **always one of the four canonical
   glyphs** ✅ / 🚧 / 💭 / 📋, because the reader's bare-emoji branch
   (`roadmapdialog.cpp:831-841`) only re-classifies those four — a
   non-canonical glyph would parse back to 📋 (INV-5, INV-11).
4. If the pass has **no** Status line in the window, insert
   `- **Status**: <keyword>` as the first line directly under the heading
   (keyword form; INV-6).
5. Every other byte of the block is unchanged (INV-4). When the located
   block has more than one `- **Status**:` line, only the first is
   rewritten (INV-13).

`op:annotate` shares the locate step, then appends `note` as a new body
line at the end of the pass block — before the next `#`-heading, or at
EOF when the located pass is the file's last block. Status is untouched,
and **no caret anchor is injected**: a pass id is synthesised from its
heading (§ 2.5), so unlike a GFM bullet a pass needs no durable
`^anchor` handle (INV-8). An empty `note` refuses `bad_args` (the
documented missing-required code; INV-3). This
deliberately diverges from the existing GFM `op:annotate` empty-note
guard, which emits the undocumented `missing_field`
(`remotecontrol.cpp:4822`) — the same documented-vs-undocumented split
ANTS-2128 tracks for the field guards; ANTS-2128's scope covers this
annotate guard too.

`op:flip_batch` flips N passes (by id locators) in one commit; an
unresolvable locator → `skipped[]` (parity with GFM flip_batch).

### 2.4 Gate-site routing

Each gate currently reads (e.g. append, `remotecontrol.cpp:4495`):

```cpp
if (rcBulletsArePassHeadings(preflightBullets)) {
    return rcPassHeadingsWriteRefusal(roadmapPath,
                                      QStringLiteral("append"));
}
```

It becomes:

```cpp
if (rcBulletsArePassHeadings(preflightBullets)) {
    return cmdRoadmapLogPassAppend(req, roadmapPath, markdown);
}
```

The four routed handlers (`…PassAppend`, `…PassAppendBatch`,
`…PassFlip` [serves flip + annotate], `…PassFlipBatch`) live next to
their GFM siblings in `remotecontrol.cpp` and call the pure
`passheadingwrite` primitives. `create_section` keeps the
`rcPassHeadingsWriteRefusal` call (§ 5).

### 2.5 ID allocation

Pass ids are **synthesised from the heading**, never allocated from
`.roadmap-counter` (verified: the reader builds `PASS-N-M` purely from
the parsed `major`/`minor`, `roadmapdialog.cpp:867-870`; the counter serves
only GFM/ants-v1 writers). The pass writer therefore:

- requires the caller to supply `pass` on append (no auto-allocation —
  § 5, OQ-3);
- never reads or writes `.roadmap-counter` (INV-10).

## 3. Invariants

- **INV-1** — Detection is unchanged: a `#### Pass N.M`+`- **Status**:`
  roadmap is still classified `pass-headings`
  (`rcBulletsArePassHeadings` true), including the ANTS-2048 stray-`- [ ]`
  case. *Test:* `mcp_roadmap_log_pass_format_mismatch` detection cases
  retained.
- **INV-2** — `op:append` with a valid `pass` on a pass-headings roadmap
  writes `#### Pass <pass> <headline>` + `- **Status**: <keyword>` (+
  body) at the end of `section`, and returns `id:"PASS-<major>-<minor>
  [-<sub>]"` + `format:"pass-headings"`. *Test:* `mcp_roadmap_log_pass_writer`
  INV-2.
- **INV-3** — `op:append` on a pass-headings roadmap refuses `bad_args`
  when `pass` is absent, when `pass` is malformed against
  `^\d+\.\d+(?:\.[A-Za-z][A-Za-z0-9]*)?$`, or when the required `status`
  is absent — naming the offending arg; the file is untouched.
  `bad_args` is the documented code for "a required argument is missing
  or has the wrong shape" (`mcp-error-codes.md:35`), so one code covers
  all three (§ 2.2). *Test:* `mcp_roadmap_log_pass_writer` INV-3
  (three refusal cases).
- **INV-4** — `op:flip` by `PASS-N-M[-SUB]` id rewrites the located
  pass's `- **Status**:` line to the new keyword; every other byte of
  the block and the rest of the file is byte-identical. *Test:* INV-4
  (byte-diff). (The multiple-Status-line disambiguation is INV-13.)
- **INV-5** — flip preserves the Status line's existing style: keyword-only
  stays keyword-only, emoji-only stays emoji-only, emoji+keyword keeps
  both. *Test:* INV-5 (three fixtures).
- **INV-6** — flip of a pass that has no `- **Status**:` line in the
  lookahead window inserts `- **Status**: <keyword>` as the first line
  under the heading (OQ-4). *Test:* INV-6.
- **INV-7** — `op:flip_batch` flips N passes by id in one atomic commit;
  an unresolvable id lands in `skipped[]` while the rest apply. *Test:*
  INV-7.
- **INV-8** — `op:annotate` appends `note` as a body line at the end of
  the located pass block, status unchanged, no anchor injected. *Test:*
  INV-8.
- **INV-9** — `op:create_section` on a pass-headings roadmap still
  refuses `format_mismatch` (out of scope this spec). *Test:*
  `mcp_roadmap_log_pass_format_mismatch` INV-2 (rewritten to
  create_section-only) retained.
- **INV-10** — No pass-headings write path reads or mutates
  `.roadmap-counter`. *Test:* INV-10 (counter byte-identical before/after
  an append).
- **INV-11** — The status written by `passStatusKeyword` re-parses
  through the reader to the intended emoji (planned→📋, in-progress→🚧,
  shipped→✅, considered→💭). *Test:* INV-11 (write then `parseBullets`).
- **INV-12** — Round-trip: after an `op:append`, `parseBullets` on the
  new file returns a record whose `id`, `status`, and `headline` match
  what the append reported/intended. *Test:* INV-12.
- **INV-13** — when a located pass block contains more than one
  `- **Status**:` line, flip targets the **first**; the byte-identity of
  every other line is the INV-4 contract. *Test:* INV-13 (two-Status-line
  fixture: first rewritten, second unchanged).
- **INV-14** — `op:append_batch` / `op:flip_batch` are skip-and-continue:
  a malformed/unresolvable entry lands in `skipped[]` while the valid
  entries commit in one atomic write; an all-invalid batch leaves the
  file untouched. *Test:* INV-14.
- **INV-15** — `op:append` into an empty section (a `##`/`###` heading
  with no body before the next heading) inserts the pass block directly
  under the section heading. *Test:* INV-15.
- **INV-16** — a `pass` arg passed to `op:append` on a **GFM / ants-v1**
  roadmap (not pass-headings) is accepted and ignored, not refused — the
  GFM append path is unchanged. *Test:* INV-16 (GFM append with a stray
  `pass` still writes a normal bullet).

## 4. RAM / build cost

No held state — the writer is read-modify-write on the roadmap file,
same as the GFM writers. New TU `src/passheadingwrite.cpp` in
`ants_core_lib` (~150 LoC) + four thin handlers in `remotecontrol.cpp`.
No new external libraries (Qt6::Core regex + `QSaveFile`, already used).
One new feature-test bundle source. No new runtime allocation beyond the
transient `QStringList lines` the existing writers already build.

## 5. Out of scope

- **`op:create_section` on pass-headings** — a `##`/`###` section heading
  is format-neutral, but RetroDB's need is `#### Pass` append, not
  section creation. Keeps the refusal; tracked as a follow-up if demand
  appears. (OQ-1.)
- **Pass-number auto-allocation** — the caller supplies `pass`; deriving
  "next minor in section" is deferred (passes are not strictly
  sequential and the caller knows the number). (OQ-3.)
- **`(SEVERITY, SIZE)` meta as a dedicated arg** — folded into `headline`
  for now; a structured `pass_meta` arg is deferred. (OQ-5.)
- **Editing arbitrary sub-bullets** (`- **Finding**:`, `- **Decision**:`)
  — only the `- **Status**:` line is writable; other content is appended
  via `op:annotate` as body. A targeted sub-bullet editor is deferred.

## 6. Migration / compatibility

ANTS-2031's feature test
`tests/features/mcp_roadmap_log_pass_format_mismatch/` asserts the
refusal across the ops. Its actual invariant map (verified against
`tests/features/mcp_roadmap_log_pass_format_mismatch/spec.md` +
`test_*.cpp`) is:

(The INV ids in this table are the **format-mismatch test's** invariants,
distinct from this spec's INV-1..15 in § 3.)

| format-mismatch test INV | Op(s) asserted to refuse | Disposition under ANTS-2126 |
|---|---|---|
| its INV-1 | `append` | **removed** (append now writes — § 2.2) |
| its INV-2 | `append_batch` **and** `create_section` | **split**: append_batch half removed (it now writes); create_section half **retained** (still refuses — § 5) |
| its INV-3 | `flip` **and** `annotate` | **removed** (both now write — § 2.3) |
| its INV-4 | `flip_batch` | **removed** (now writes — § 2.3) |
| its INV-5 | ants-v1 control (still appends) | **retained** |
| its INV-6 | ANTS-2048 stray-`- [ ]` detection stays pass-headings | **retained** |

The removed/split INVs **change meaning** (refuse → write), which the
invariant-immutability rule forbids amending in place. Resolution:

- The format-mismatch test is **narrowed** to the invariants that still
  hold: INV-5 (ants-v1 control), INV-6 (ANTS-2048 stray-checkbox
  detection — see note below), and INV-2 **edited in place** to drop its
  `append_batch` sub-assertion while keeping the `create_section` one.
  The test's INV-2 is today a *single fused* `TEST` case asserting
  append_batch **and** create_section refuse together
  (`test_*.cpp` "INV-2 — append_batch + create_section refuse
  identically"); the edit removes the append_batch sub-assertion from
  that one function, it is not a separate-test operation. INV-1/3/4 are
  **deleted**, each with a comment pointing at ANTS-2126.
- The format-mismatch test's own `spec.md` documents only INV-1..5, but
  the `.cpp` carries an undocumented INV-6 (ANTS-2048). This spec's
  migration adds the missing INV-6 line to that `spec.md` while it is
  being edited, so its contract list matches the code.
- The new write behaviour lives in a **new** feature test
  `tests/features/mcp_roadmap_log_pass_writer/` (INV-2..16 here), so no
  existing INV id is repurposed. The two INV namespaces are file-scoped:
  this spec's `INV-N` and the format-mismatch test's `INV-N` are
  unrelated despite numeric overlap.

`docs/standards/mcp-error-codes.md` `format_mismatch` entry is updated:
on pass-headings it now fires for `create_section` only — append /
append_batch / flip / flip_batch / annotate write instead.

**Refusal-code note.** INV-3's `bad_args` is the *documented* code for a
missing/ill-shaped required arg (`mcp-error-codes.md:35`). Note that
roadmap_log's existing GFM `op:append` instead emits an **undocumented**
`missing_field` code for absent required fields
(caller_cwd/section/status/kind/source guards at
`remotecontrol.cpp:4200-4222`; `headline` at `:4213` uses a separate
`headline_empty`) — a pre-existing taxonomy violation. This
spec deliberately does **not** propagate `missing_field` into the new
pass path (that would add a second undocumented emission site); it uses
`bad_args`. Converging the GFM append path onto a documented code (or
adding `missing_field` to the taxonomy) is a separate doc/code-fix
tracked by ANTS-2128.
