# ANTS-1284 — `token_usage` MCP telemetry tool

**Status:** spec draft, pre cold-eyes (2026-05-14). Loop log at end (§ 11).
**Source:** ROADMAP.md ANTS-1284 (line in `📊 Performance — MCP telemetry`
block).
**Blocked by:** none — pure in-process counter; no shell-out, no file I/O
on the hot path.
**Pairs with:** ANTS-1289 (`verify_changes` — shipped 2026-05-14;
counted by this tool), ANTS-1290 (`plan_template` — shipped 2026-05-14;
counted by this tool). Distinct from ANTS-1245 (Tools → Token Usage
dialog with SQLite/charts) which tracks Claude's *full-session*
token spend; this tool measures the MCP server's *displacement
delta* (baseline vs actual response bytes).

## 1. Problem

After ANTS-1289 and ANTS-1290 shipped, the MCP surface displaces
three skill-markdown loads per session worth ~10–30 K tokens. We
**believe** the savings are meaningful, but the assistant has no
way to inspect them at runtime. Today the user and the assistant
both have to reason from spec-time estimates ("we expect ~6–24 K
tokens/session saved by verify_changes") rather than from observed
data ("verify_changes fired 4 times this session and saved 18 K
tokens").

Without runtime data:

- We can't prioritise the next MCP-displacement target by
  measured impact (vs guessed impact). The `superpowers:writing-specs`
  skill is 8 KiB and gets loaded N times per session — but does N
  warrant a `spec_template` tool? Without a counter, we guess.
- We can't catch regressions. If a future change to
  `roadmap_query` makes the response 4× larger by mistake, the
  savings claim silently shrinks; nothing surfaces the drift.
- We can't tell the user "this session saved ~85 K tokens" so
  they see the tooling pay rent.

The fix is a small in-process counter behind a `token_usage` MCP
tool that the assistant can call mid-session. Counter is per-tool,
keyed by name; each entry tracks `n_calls`, `bytes_in`,
`bytes_out`, and `est_tokens_saved` (a `baseline - actual` delta
where the per-tool baseline is a static engine constant — see
§ 2.4). Resets on MCP `initialize` (Claude Code session start) and
on an explicit `reset:true` call.

Per-call instrumentation overhead — the cost of **adding** the
counter, not the savings it surfaces:

| Component | Cost | Notes |
|---|---:|---|
| `QJsonDocument(args).toJson(Compact).size()` | ~50–200 ns | Same compact-JSON the wire emits — args are already small objects (≤ 1 KiB typical) |
| `QString::toUtf8().size()` for response | ~1–5 µs | One transient `QByteArray` alloc per dispatch; size proportional to response length (~5 KiB typical → ~3 µs) |
| `QHash<QString, ToolCounter>::operator[]` + 4 integer adds | ~50–100 ns | One amortised-O(1) lookup per call |
| **Subtotal per MCP call** | **< 6 µs** | Dominated by the `.toUtf8()` alloc; still negligible vs ~ms-scale provider work |

Token math for the `token_usage` tool's own value-add: not
about *direct* token savings (the tool's response is itself
~200–500 B — well below any plausible baseline), but about the
**second-order** savings unlocked by the visibility:

- Catches a regression that would otherwise silently waste ~Nk
  tokens/session for weeks before a manual re-measurement.
- Lets the user judge "is this MCP toolset worth the complexity"
  from data, not narrative — strengthens the case for further
  skill-displacement work.

## 2. Surface

### 2.1 Tool signature

```
mcp__ants__token_usage
  (no required args)
  optional: reset: bool          // default false; true → return current report
                                 // AND clear all counters atomically
  optional: include_zero: bool   // default false; true → include tools with
                                 // est_tokens_saved == 0 in calls[]
```

No required args — the canonical invocation is `mcp__ants__token_usage`
with no arguments, which returns the current per-tool report.

### 2.2 Response shape

```json
{
  "ok": true,
  "since": "2026-05-14T09:23:11Z",
  "since_unix_ms": 1810288991000,
  "calls": [
    {
      "tool": "roadmap_query",
      "n_calls": 8,
      "bytes_in": 124,
      "bytes_out": 48312,
      "est_tokens_saved": 110888
    },
    {
      "tool": "verify_changes",
      "n_calls": 3,
      "bytes_in": 90,
      "bytes_out": 4128,
      "est_tokens_saved": 1170
    },
    {
      "tool": "plan_template",
      "n_calls": 1,
      "bytes_in": 84,
      "bytes_out": 2876,
      "est_tokens_saved": 1281
    },
    {
      "tool": "tab_list",
      "n_calls": 5,
      "bytes_in": 30,
      "bytes_out": 1240,
      "est_tokens_saved": 0
    }
  ],
  "total_saved": 113339,
  "tools_called": 4,
  "reset_performed": false
}
```

- `since` — ISO 8601 UTC timestamp of when counters were last reset
  (session start OR last explicit `reset:true`). `since_unix_ms`
  is the same instant in epoch milliseconds for callers that
  prefer numeric handling.
- `calls[]` — per-tool array sorted by `est_tokens_saved`
  descending (most-saving first). When `include_zero:false`
  (default), tools with `est_tokens_saved == 0` are dropped from
  `calls[]` BUT still contribute to `tools_called`.
- `total_saved` — sum of `est_tokens_saved` across ALL tracked
  tools (whether or not they appear in `calls[]`). Integer tokens.
- `tools_called` — count of distinct tool names that have at least
  one recorded call since `since`.
- `reset_performed` — echoes the request's `reset` arg. When
  `true`, the report reflects the state JUST BEFORE the reset
  (i.e. the caller can read final numbers and clear in one
  round-trip).

When no tools have been called yet (fresh session, no MCP
activity): response has `calls: []`, `tools_called: 0`,
`total_saved: 0`. `since` reflects the session-start timestamp.

### 2.3 Per-call field semantics

| Field | Type | Meaning |
|---|---|---|
| `tool` | string | MCP tool name (e.g. `"roadmap_query"`); matches the registered name without the `mcp__ants__` prefix |
| `n_calls` | int | Number of times this tool's dispatch handler completed since `since` |
| `bytes_in` | int | Sum of compact-JSON `arguments` object size in bytes across all calls (`QJsonDocument::toJson(Compact).size()`) |
| `bytes_out` | int | Sum of the provider lambda's returned `QString` size in **wire bytes** (`QString::toUtf8().size()` — same UTF-8 encoding the response is serialised to over the local socket) |
| `est_tokens_saved` | int | `max(0, (baseline_bytes_per_call × n_calls) - bytes_in - bytes_out) / 4`; floors at 0 |

The `est_tokens_saved` formula is an **order-of-magnitude
estimate**, not a billing-grade metric:

- `baseline_bytes_per_call` is a per-tool static constant in the
  engine (§ 2.4). Unknown tools default to 0 → `est_tokens_saved`
  is then 0 regardless of `bytes_in`/`bytes_out`.
- The `/4` divisor approximates Anthropic's BPE-style tokenisation
  at ~4 chars per token. Real tokenisation varies ±20 % by
  content; this estimate is fine for "which tool is saving the
  most tokens" prioritisation but should not be quoted as a
  billing figure.

### 2.4 Per-tool baseline table

The baseline is the **estimated cost of doing the same work via
Bash + Read instead of this MCP tool**. Baselines are static
constants in the engine. v1 ships three calibrated baselines (all
verified against documented spec sections); the rest default to 0
(counted but no savings claim).

| Tool | Baseline (bytes/call) | Anchor for the number |
|---|---:|---|
| `roadmap_query` | 594 000 | ROADMAP.md raw byte size — `wc -c ROADMAP.md` = 593 632 B (verified 2026-05-14); rounded up to 594 000 for headroom. The in-conversation token cost cited at ROADMAP.md:7300 (~123 K tokens) was measured against an earlier smaller file; the raw-byte anchor is the conservative current value. |
| `verify_changes` | 8 192 | ANTS-1289 § 1 — skill markdown 4 201 B (`wc -c verification-before-completion/SKILL.md` verified 2026-05-14) + 2–3 Bash round-trip frames at ~1 KiB each → ~8 KiB |
| `plan_template` | 8 192 | ANTS-1290 § 1 — skill markdown 6 100 B (`wc -c writing-plans/SKILL.md` verified 2026-05-14) + template-echo overhead ~2 KiB → ~8 KiB |
| (all others) | 0 | Not yet measured; future updates extend the table |

The table lives in `src/tokenusageengine.cpp` as a
`static const QHash<QString, qint64> kBaselineBytes` initialised
at static-init time. Adding a tool to the table is a one-line
code change + commit; the spec does not need to list every
future entry.

**Why static, not config:** the baseline is documentation of an
*estimate*, not user-tunable behaviour. A user who wants different
math should edit the engine source (and ideally upstream the
change). v2 may move this to a `.ants/token_usage.json` override
if a real use case appears.

### 2.5 Engine API

```cpp
namespace TokenUsageEngine {

struct ToolCounter {
    int     nCalls       = 0;
    qint64  bytesIn      = 0;
    qint64  bytesOut     = 0;
};

class Tracker {
public:
    // Constructs an empty tracker with sinceMs = QDateTime::currentMSecsSinceEpoch().
    Tracker();

    // Records one MCP-tool dispatch. Called from claudeintegration's
    // dispatch site (see § 2.6). Thread-safety: caller must hold any
    // necessary lock; in v1 Qt's single-threaded local-socket dispatch
    // serialises calls naturally (INV-7).
    void recordCall(const QString &toolName, qint64 bytesIn, qint64 bytesOut);

    // Atomically clears all counters and resets sinceMs to now.
    void reset();

    // Pure read — no mutation. Builds a snapshot of the current
    // counters with est_tokens_saved computed from § 2.4 baselines.
    // includeZero: when false, omits tools with est_tokens_saved == 0
    // from the result's `calls` list (they still contribute to
    // tools_called and total_saved).
    struct ToolReport {
        QString tool;
        int     nCalls = 0;
        qint64  bytesIn = 0;
        qint64  bytesOut = 0;
        qint64  estTokensSaved = 0;
    };
    struct Snapshot {
        qint64           sinceUnixMs = 0;
        QList<ToolReport> calls;            // sorted estTokensSaved desc
        qint64           totalSaved = 0;
        int              toolsCalled = 0;
    };
    Snapshot buildReport(bool includeZero) const;

    // Per-tool baseline lookup; returns 0 for unknown tools.
    static qint64 baselineFor(const QString &toolName);

private:
    QHash<QString, ToolCounter> m_counters;
    qint64                       m_sinceUnixMs = 0;
};

}  // namespace TokenUsageEngine
```

Layering: `src/tokenusageengine.{h,cpp}` is added to `ants_core_lib`
in `CMakeLists.txt` alongside `verifyengine.cpp` and
`plantemplateengine.cpp` (verified at `CMakeLists.txt:217–236`).
Qt6::Core only — no Qt6::Widgets dependency.

The `Tracker` lives as a `TokenUsageEngine::Tracker m_tokenUsage`
member on `ClaudeIntegration` (one instance per running
ants-terminal process; ClaudeIntegration is already a singleton).
Chrome-lib `ClaudeIntegration` linking core-lib's engine matches
the existing pattern (the chrome lib depends on the core lib at
`CMakeLists.txt:251`).

### 2.7 MCP tool description

```
token_usage: Reports per-tool token-saving telemetry for this MCP
server's current session. Returns {since, calls:[...], total_saved,
tools_called}; calls sorted by est_tokens_saved descending. Pure
read by default; pass reset:true to read-and-clear in one round-
trip. No required args.
```

## 3. Invariants

- **INV-1** — Counter exactness. `recordCall` increments `n_calls`
  by exactly 1 per call AND adds the supplied byte counts; no
  sampling, no batching, no overflow protection needed at v1
  scale (a typical session sees ≤ 1 K MCP calls; `qint64` headroom
  is ~9 EB).

- **INV-2** — Byte units are UTF-8 wire bytes for both
  `bytes_in` (compact-JSON `QJsonDocument::toJson(Compact).size()`)
  AND `bytes_out` (`QString::toUtf8().size()`). The `.toUtf8()`
  conversion allocates a temporary `QByteArray` per dispatch —
  cost is O(response_length), measured ~3 µs on a typical 5 KiB
  response, well under the < 1 µs budget for the rest of the
  instrumentation but kept as a separate line item in § 1's
  cost table for honesty. The alternative (`QString::size()` =
  UTF-16 code-unit count) was rejected because the field name
  `bytes_out` would then be misleading on multi-byte responses.

- **INV-3** — Reset atomicity. `Tracker::reset()` clears the
  counter map AND updates `m_sinceUnixMs` to "now" in the same
  method body, before returning. There is no observable
  intermediate state because v1 is single-threaded (Qt local
  socket events serialise on the main event loop — INV-7).

- **INV-4** — `est_tokens_saved` floor. The formula is `max(0,
  ...)`; a tool whose actual `bytes_in + bytes_out` exceeds its
  baseline (e.g. a verbose error response on a small baseline)
  reports 0 saved, not a negative number. Reason: a negative
  "savings" is confusing and not actionable — the existence of an
  outlier call is better surfaced by inspecting per-tool n_calls
  + bytes_out directly.

- **INV-5** — Baseline lookup is O(1). `baselineFor(toolName)`
  returns 0 for any tool not in the static `kBaselineBytes`
  table. Adding a new baseline requires a code edit + commit (no
  runtime config). Reason: this is documentation of an estimate;
  user-tunable values would invite drift between docs and runtime.

- **INV-6** — Schema: response object sets
  `additionalProperties: false` on the top-level envelope AND on
  each `calls[i]` object. New fields require an explicit schema
  update + invariant bump.

- **INV-7** — Single-threaded mutation. `recordCall` and `reset`
  are called only from the Qt event-loop thread (the MCP local-
  socket dispatch path). No mutex needed in v1. If the MCP path
  ever moves to a thread pool, `Tracker` must add a `QMutex`
  guard — flagged as a v2 hardening item in § 9.

- **INV-8** — RAM bound. `m_counters` size = (number of distinct
  tool names called this session) × ~96 B/entry (`QString` key
  ~48 B [Qt6 inline header 24 B + heap UTF-16 data ~24 B for a
  12-char tool name] + `ToolCounter` struct 24 B + `QHash` slot
  overhead ~24 B). Worst case ≤ ~64 entries × 96 B = **~6 KiB**.
  (64 entries = current 26 registered tools after this work
  [24 outward delegates verified by
  `grep -c registerToolProvider src/mainwindow.cpp` = 24, at
  `mainwindow.cpp:3671–3869`; + `get_session_info` inline at
  `claudeintegration.cpp:2012`; + `token_usage` itself = 26] +
  future headroom; the engine does not retain entries for tools
  never called.) `m_sinceUnixMs` is 8 B. Total tracker RAM
  ≤ **~7 KiB** across an unbounded session.

- **INV-9** — Pure-read `buildReport`. The method does not mutate
  `m_counters` or `m_sinceUnixMs`; safe to call repeatedly. The
  only state mutation in the dispatch path is `recordCall`;
  `reset` is invoked only on `initialize` and on an explicit
  `reset:true` call. Tests can rely on this for setup/assertion
  separation.

- **INV-10** — Self-referential count is allowed. A call to
  `token_usage` increments `token_usage`'s own counter. The tool
  itself has `baseline = 0`, so it contributes 0 to
  `total_saved` regardless of `n_calls`. Documented for
  transparency; tests assert the count behaviour.

## 4. Failure modes

- **`reset` arg is a non-bool JSON value** (e.g. `reset:"yes"`).
  `QJsonValue::toBool()` defaults non-bool to `false`; the report
  is returned without resetting. Documented; not an error.

- **`include_zero` invalid** — same default-to-false handling.

- **Counter overflow.** A single tool's `bytes_in` or `bytes_out`
  exceeds `qint64::max` (9.2 EB). Not achievable in any realistic
  session lifetime. No special handling; the math wraps silently
  (the bug would be elsewhere if this ever happened).

- **Engine called before `Tracker` constructed.** Defensive only —
  `m_tokenUsage` is a member-by-value on `ClaudeIntegration`,
  constructed before any MCP dispatch can occur. If somehow
  invoked on a moved-from tracker, `recordCall` is a no-op on an
  empty hash; `buildReport` returns an empty snapshot with
  `sinceUnixMs = 0`. Not testable in practice.

- **Unknown tool name** (not yet registered) is recorded against
  if it somehow reaches the dispatch site (e.g. a manual JSON-RPC
  invocation). `baselineFor` returns 0; the call appears in the
  counter with `est_tokens_saved == 0`. By design — captures the
  attempt for diagnostics.

## 5. Test plan

`tests/features/token_usage_engine/` with:

- `spec.md` — human contract mirror of INV-1 … INV-10.
- `test_token_usage_engine.cpp` — pure-function engine tests:
  1. **INV-1 exactness.** Construct a `Tracker`; call
     `recordCall("foo", 10, 100)` three times. Assert
     `buildReport(true).calls[0]` has `nCalls==3, bytesIn==30,
     bytesOut==300`.
  2. **INV-2 wire-byte semantics.** Record a response containing
     a single multi-byte UTF-8 character (e.g. an emoji — 4 wire
     bytes / 2 UTF-16 code units). The engine receives the
     wire-byte count from the caller (per § 2.6's `.toUtf8()
     .size()` capture), so the engine-level test just asserts
     that an explicitly-passed `bytesOut=4` records as 4, not 2.
     The wire-byte capture itself is verified at the MCP-layer
     test (REG-N in `mcp_token_usage_tool/`).
  3. **INV-3 reset atomicity.** Record 5 calls across 2 tools,
     `reset()`, assert `buildReport(true)` shows
     `calls:[], totalSaved:0, toolsCalled:0`, AND `sinceUnixMs`
     advanced (post-reset > pre-reset). Record once more; assert
     only that one call is visible.
  4. **INV-4 saved-floor.** Record `recordCall("roadmap_query",
     1000, 700000)` (response 700 KB exceeds the 594 KB
     baseline). Assert `buildReport(true).calls[0].estTokensSaved
     == 0` (clamped, not negative).
  5. **INV-5 baseline lookup.** Assert
     `baselineFor("roadmap_query") == 594000`,
     `baselineFor("verify_changes") == 8192`,
     `baselineFor("plan_template") == 8192`,
     `baselineFor("unknown_tool_xyz") == 0`.
  6. **INV-6 schema round-trip.** Build a synthetic snapshot;
     serialise via the response-builder helper through
     `QJsonDocument::toJson(Compact)`; parse back through
     `QJsonDocument::fromJson`; assert the set of present keys
     on the envelope AND on each `calls[i]` is a subset of the
     spec's declared set. Mirrors the round-trip pattern in
     `tests/features/verify_changes_engine/test_verify_changes_engine.cpp`.
  7. **INV-7 single-threaded** — out of scope for engine test
     (the threading model is enforced by the Qt event-loop site;
     the engine is just a struct with non-thread-safe members).
  8. **INV-8 RAM bound** — implicit in the static counter-map
     size; no separate test (a programmatic check would require
     RSS introspection that's flaky in CI).
  9. **INV-9 pure-read `buildReport`.** Record 3 calls; call
     `buildReport(true)` twice with no intermediate writes;
     assert both snapshots are byte-identical (proves no mutation
     side effect).
  10. **INV-10 self-counted.** Record `recordCall("token_usage",
      50, 300)`; assert `buildReport(true).calls[0].nCalls == 1`
      AND `estTokensSaved == 0` (baseline is 0).
  11. **Sorted descending.** Record 3 tools with different
      synthetic baselines (use the real baselined ones —

  12. **`include_zero` filter.** Record one call to `tab_list`

token_usage test passes.

## 6. Performance / RAM budget

- **Engine RAM per session**: ≤ 5 KiB (INV-8).
- **Per-call instrumentation overhead**: < 1 µs (§ 1 table).
- **`buildReport` cost**: O(distinct tools called) + a
  `std::sort` on the resulting list. Worst case ~64 tools → ~10
  µs. Caller-rare (the assistant invokes `token_usage` at session
  end / per-question, not per-tool-call).
- **MCP response payload**: ≤ ~5 KiB (worst case all 26 tools
  called with non-zero saved counts, full per-tool envelopes);
  ~500 B typical (3–5 tools called).
- **No new caches, no new file watchers, no new background
  threads.** Pure in-process counter on the existing
  `ClaudeIntegration` singleton.

## 7. Workflow integration

Unlike ANTS-1289 / 1290, this tool does NOT displace a skill — it
is a **measurement layer** on top of the existing MCP surface.
There is no `superpowers:token-usage` skill to retire.

Expected usage patterns:

1. **End-of-session "did this pay off?"** — assistant calls
   `mcp__ants__token_usage` once after a substantial work block
   (e.g. shipping a spec + cold-eyes loops). Surface the
   `total_saved` figure to the user as a one-line summary
   ("This session's MCP tools displaced ~85 K tokens of
   skill/Bash overhead.").

2. **Mid-session prioritisation** — assistant calls
   `mcp__ants__token_usage` after running ~10 verify cycles to
   confirm `verify_changes` is actually meeting its predicted
   savings. If `est_tokens_saved` for `verify_changes` is
   anomalously low (e.g. response sizes ballooning), surface as
   a flag for follow-up.

3. **Regression catching in tests** — future feature-conformance
   tests can call the engine directly to assert per-call
   `est_tokens_saved` does not regress below documented floors
   (e.g. "verify_changes response must stay under 5 KiB or the
   savings claim is invalid").

The tool is **always available**; no opt-in flag. The cost of
the counter is negligible (§ 6) so always-on is the simplest
contract.

## 8. Migration

- New tool — no existing API to deprecate.
- No new files in `.ants/` — counters are in-process, no on-disk
  state. (Persistence is explicitly **out of scope**; pairs with
  ANTS-1283 session memory KV if a future use case wants
  cross-session totals.)
- No new menu items, no UI changes — strictly an MCP surface.
- `ClaudeIntegration` adds one new member (`m_tokenUsage`) and
  one new public method (`tokenUsageReport(includeZero)` —
  optional convenience accessor for tests; the MCP-layer goes
  through `RemoteControl::cmdTokenUsage` which queries the
  tracker directly).

## 9. Out of scope

- **Cross-session persistence.** Counters reset on MCP
  `initialize` and on process restart. A user who wants
  "total saved this week" needs ANTS-1245's full-session
  token-usage dialog (which tracks Claude's own token spend,
  not MCP-tool displacement). The two metrics are complementary
  but distinct; merging them is a v2 design question.

- **Per-cwd / per-project breakdown.** Counters are global to the
  ants-terminal process. A user with multiple project tabs
  open sees aggregated numbers across all of them. Adequate v1;
  ANTS-1283 session-memory could later add a project-keyed view.

- **Real Anthropic token counting.** The `/4` chars-per-token
  divisor is a heuristic. A future v2 could call the Anthropic
  tokeniser endpoint, but the call cost + latency would dwarf the
  estimation error.

- **Detecting tool calls that *should* have been MCP but went via
  Bash.** Out of scope — the counter records what happened, not
  what could have happened.

- **Per-call latency tracking.** A separate dimension (when does
  MCP-vs-Bash matter for *speed*); not part of token-displacement
  measurement.

- **A `mutex`-protected `Tracker` for thread-safe access.** Flagged
  as a v2 hardening if the MCP dispatch ever moves off the Qt
  event-loop thread. INV-7 documents the v1 single-threaded
  assumption.

- **Updating the baseline table at runtime.** v1 ships static
  constants; INV-5 documents the rationale. A `.ants/
  token_usage.json` override is a candidate v2 feature if a real
  use case appears.

- **Telemetry exfiltration.** The counter never leaves the local
  process unless the user explicitly invokes `mcp__ants__
  token_usage`. No background reporting, no opt-in beacon, no
  third-party calls.
