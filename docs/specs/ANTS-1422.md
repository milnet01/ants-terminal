# ANTS-1422 — `token_usage` `no_claude_integration` diagnostic

## Problem

2026-05-16 live repro on a fresh Ants Terminal (PID 3152, built
00:39, includes ANTS-1404 + 1400): `mcp_trace`,
`caller_cwd_info`, `roadmap_query` all returned proper data,
but every `token_usage` call returned:

```json
{
  "ok": false,
  "error": "no_claude_integration",
  "message": "token_usage: claude integration unavailable"
}
```

The error envelope comes from
`remotecontrol.cpp::cmdTokenUsage`'s null check on
`m_main->claudeIntegration()`. Static analysis says reaching
that branch is structurally impossible from the MCP-lambda
dispatch path:

1. `m_claudeIntegration` is assigned once at `mainwindow.cpp:3598`
   (`new ClaudeIntegration(this)`) and never re-nulled — no
   `delete`, no `= nullptr`, no `reset`.
2. The MCP server is started at line 3750 on `m_claudeIntegration`
   itself — must be non-null at that point.
3. The `token_usage` lambda is registered AFTER the server
   starts, on the same `m_claudeIntegration` instance.
4. When the lambda fires, it calls
   `m_remoteControl->cmdTokenUsage(args)`. Inside cmdTokenUsage,
   `m_main` is the same `MainWindow` the lambda's `this` captured.
   `m_main->m_claudeIntegration` is the same memory location as
   the singleton serving the call — tautologically non-null.

Yet the null check fires. Hypotheses (in order of suspicion):

1. **Build-cache layout drift.** A header change (virtual function
   added, member reordered) compiled into one TU but not another,
   leaving `m_main->m_claudeIntegration` reading a different
   offset than the singleton's actual field.
2. **Stale RemoteControl::m_main.** RemoteControl was constructed
   with one MainWindow pointer that subsequently went stale (no
   evidence of this in source, but defensive).
3. **Inline getter mis-resolved.** LTO / linker pathology where
   `MainWindow::claudeIntegration()` resolved to an old definition.

The current source can't discriminate between these — the bug
needs runtime introspection.

## Goal v1 (this ticket)

**Diagnostic, not fix.** Surface pointer values in the response
envelope so a re-repro on the rebuilt binary yields actionable
data without an out-of-band stderr capture:

```json
{
  "ok": false,
  "error": "no_claude_integration",
  "code": "no_claude_integration",
  "message": "token_usage: claude integration unavailable",
  "debug": {
    "m_main_ptr": "<hex>",
    "this_rc_ptr": "<hex>",
    "ci_via_getter_null": true
  }
}
```

Pointer values are in hex without `0x` prefix (matching
`QString::number(p, 16)` output). Bypasses the
ANTS-1294 wrap so the diagnostic JSON reads cleanly.

## Goal v2 (follow-up ticket)

Once the root cause is identified from v1's diagnostic, the v2
fix:

- If hypothesis 1 (build-cache drift): full rebuild + a CMake
  guard that invalidates dependent TUs on header churn.
- If hypothesis 2 (stale m_main): tighten RemoteControl's
  lifecycle binding to MainWindow.
- If hypothesis 3 (LTO / linker pathology): force the getter
  out-of-line OR add an explicit anchor TU.

v2 is out of scope here; this ticket just unblocks diagnosis.

## Invariants

- **INV-1.** When the `no_claude_integration` branch fires, the
  envelope carries a `debug` object with `m_main_ptr`,
  `this_rc_ptr`, and `ci_via_getter_null:true`.
- **INV-2.** When the `no_main` branch fires, the envelope
  carries a `debug` object with the same pointer fields
  (`m_main_ptr:"0x0"`) so the two failure modes are
  distinguishable.
- **INV-3.** The legacy `tuErr` helper is retired — both error
  branches use inline envelope construction. Anchor: the
  retirement comment block at the cmdTokenUsage definition.
- **INV-4.** Successful path is unchanged — no diagnostic
  pollution, no `debug` field.
- **INV-5.** The error `code` field matches `error` (both
  `"no_claude_integration"` or both `"no_main"`).

## Test

`tests/features/token_usage_no_ci_diagnostic/`:

1. **INV-1 (source-scrape).** `cmdTokenUsage` no_ci branch
   emits a `debug` object with `m_main_ptr`, `this_rc_ptr`,
   `ci_via_getter_null`.
2. **INV-2 (source-scrape).** no_main branch emits the same
   diagnostic shape.
3. **INV-3 (source-scrape).** Legacy `tuErr` helper is
   gone — the retirement comment block is present.
4. **INV-4 (source-scrape).** Success path unchanged: no
   `debug` field assigned in the `env["ok"] = true` block.
5. **INV-5 (source-scrape).** Both error branches set
   `env["code"]` equal to `env["error"]`.

Label `features;fast`. Source-scrape only — the diagnostic
output is the entire behavioural payload of this ticket.

## Migration

This ticket changes the wire shape of the
`no_claude_integration` and `no_main` error envelopes by adding
a `debug` field. Existing callers that read `ok` / `error` /
`code` / `message` are unaffected. New `debug` field is
diagnostic; v2 of this ticket will retire it.

## RAM budget

Trivial. One QJsonObject per failure call; both failure modes
are dead code in practice.

## Build cost

~30 LoC added (two inline envelopes); ~10 LoC removed (`tuErr`
helper). Net diff small.
