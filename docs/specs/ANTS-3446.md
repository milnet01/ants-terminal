# ANTS-3446 — `feedback_log op:"migrate_v2"`: one-shot mechanical v1→v2 feedback-file migration

**Status:** Implemented (2026-07-05) — `FeedbackFile::migrateV2` +
`cmdFeedbackLog op:migrate_v2` + schema; 17 conformance tests
(`tests/features/feedback_log_migrate_v2/`) green, full suite 2531 pass. §7
standard reconciliation (ten items) landed in the same change. Cold-eyes clean
(9 loops incl. a mid-review design pivot from relocate-tables to leave-in-place)
**Kind:** enhancement
**Source:** in-session-2026-07-05 (v2 feedback-file redesign; the verb that
produces `: 2` files so `compact_resolved` — ANTS-3443 — can act on them)

## 1. Problem

The v2 feedback-file format (docs/standards/mcp-feedback-files.md) records
triage **inline** — each `### ` finding carries a `**Proposed ID:**` line, and
status is resolved live from `ROADMAP.md` (no tracking tables). But **the entire
existing corpus is v1**: findings predate the structural `**Proposed ID:**` line,
and triage lives in appended maintainer *tracking tables*. `compact_resolved`
(ANTS-3443) refuses `not_v2` on every current file, so nothing can be shrunk
until a file is converted. `migrate_v2` is the one-shot converter.

### 1.1 Why mechanical-only, leave-tables-in-place

The standard's original §"Migration from v1" sketch assumed each v1 table is a
clean `finding-recap → ANTS-id` map that migration can parse and stamp onto the
matching finding. **The real corpus falsifies that** (measured 2026-07-05 on
`3D_Engine_Ants_MCP_Feedback.md`, the 267 KB primary target):

- The tables have **no clean id column.** `3D_Engine`'s are
  `| #N <recap> | <status> | <notes> |` — column 0 is a `#N` finding *reference*,
  not an id; the real `ANTS-NNNN` ids are buried in freeform *Notes* prose, and a
  single row often names several (the finding's id **plus** cross-refs like
  "see new Issue #11"). `MAME_Curator`'s are `| # | Item | Status | Evidence |`
  (ids in *Evidence*). Every project's table shape differs.
- Of `3D_Engine`'s **167** `### ` blocks (measured 2026-07-05), only **40** carry
  a `#N` heading token and only ~**37** already have a `**Proposed ID:**` line;
  the other ~127 are prose (`### Positive note`, `### Updated priority`,
  `### What worked well` …) that migration must **not** stamp.
- The shipped ANTS-3371 row parser (`feedbackfile.cpp` `parse()`) assumes column
  1 is the id column, so on these tables it mis-columns and extracts **zero**
  structured finding→id rows.

Reverse-engineering finding→id from that is fuzzy and lossy, and its value is low
(the "which finding became which id" knowledge lives with the maintainer at
triage, not in these messy tables). So `migrate_v2` does only the **unambiguous,
lossless** mechanical work; the real finding→id triage is `op:assign_id`'s job
(spec pending). This is the maintainer's decision, 2026-07-05
(mechanical-only over auto-stamp).

**Tables are left in place, not relocated.** Migration bumps the marker and
stamps blank id-placeholders; it does **not** move, archive, or delete the v1
tracking tables.

Why this matters — the shipped delta reader is **marker-blind**. Today's
`feedback_query` / `session_orient feedback_pending` call `FeedbackFile::parse()`
**unconditionally**, ignoring the version marker (the standard's §"Version
selection" v2 rule and the marker-honoring path are "Still not built" —
mcp-feedback-files.md §"Format version 2" impl-status note; `remotecontrol.cpp`).
So `parse()`'s **v1 rule** governs every file regardless of marker: the
un-triaged delta starts at **the first `#`/`## ` contributor heading strictly
after the last maintainer (watermark) heading** (`### ` headings are *inert* to
the boundary scan — `isBoundaryHeading`/`scanBoundaries`, `feedbackfile.cpp`), and
runs to EOF. Bumping a file to `: 2` therefore does **not** route it to the
unbuilt v2 reader; the v1 rule keeps applying.

An earlier design relocated the tables to a frozen archive appendix for
de-clutter, but that moves the greatest-position maintainer heading (the v1
watermark, `parse().lastMaintainerLine`) to EOF — which would push the delta
start past every finding and **empty the v1 delta** on a migrated file until the
position-independent v2 reader ships (a silent regression window). Leaving the
tables where they are keeps the watermark — and thus the delta start — exactly
where it was, so migration is **delta-preserving** and there is **no ordering
dependency** on the v2 reader (§5 records the de-clutter as a deferred, separate
op). The byte *shrink* the user wants comes later from `compact_resolved`, not
from migration.

## 2. Surface

`feedback_log op:"migrate_v2"` (maintainer). Split mirrors the other
`feedback_log` compaction ops:

- **Pure helper** `FeedbackFile::migrateV2(content)` (ants_core_lib,
  Qt6::Core-only) does the whole transform over a string and returns the new
  content + a structured report. No roadmap, no filesystem, no MainWindow — it
  is fully unit-testable over synthetic content (same posture as
  `compactResolved` / `pruneTracking`).
- **Wrapper** `cmdFeedbackLog` (remotecontrol.cpp) does path resolution, the
  `*_Ants_MCP_Feedback.md` suffix guard, PathValidation, the `caller_cwd`
  contract, `dry_run`, and the atomic `QSaveFile` write — identical plumbing to
  the two v1 ops, **minus** the roadmap read (`migrate_v2` never consults the
  roadmap; mechanical-only).

### 2.1 Request shape

| field | req? | meaning |
|---|---|---|
| `caller_cwd` | yes | resolves the feedback file (path derivation, ANTS-3376) |
| `op` | yes | `"migrate_v2"` |
| `path` | no | feedback-file path; omit to derive `<leaf>_Ants_MCP_Feedback.md`, echoed `path_derived` |
| `dry_run` | no | preview the report without writing (default false) |

No target list, no id args — the transform is whole-file and deterministic.

### 2.2 What migrate_v2 does (two mechanical passes)

Given a `: 1` (or marker-absent/malformed) file, in one helper call:

1. **Marker bump.** Find the first line matching
   `<!--\s*ants-mcp-feedback:\s*([0-9]*)\s*-->` (the version digits **optional** —
   capture group 1 is the version, empty for a malformed `<!-- ants-mcp-feedback:
   -->`; empty/malformed parses as `< 2`, §2.7) and replace **that whole line**
   with the canonical `<!-- ants-mcp-feedback: 2 -->` — a `: 1` marker, a
   malformed one, or a marker not on line 1 (a legacy edge) are all *replaced*,
   never left as junk beside a freshly-inserted one. (Corpus markers occupy the
   line alone; the whole-line replace is safe for them.) If **no** such line
   exists (a legacy file like `DOOM`), insert `<!-- ants-mcp-feedback: 2 -->` as a
   new first line above the H1. The marker is conventionally line 1; taking the
   first occurrence is robust to a mis-placed one (and to a legacy file with no H1,
   where "line 1" is simply the file's first line). This `([0-9]*)` (digit-optional)
   match is **deliberately** more lenient than the sibling `compact_resolved`
   gate's `([0-9]+)` (digit-required, `remotecontrol.cpp`): migrate_v2 must
   *repair* a malformed marker, whereas the gate only *reads* an existing one — so
   the divergence is intentional, not an inconsistency to "fix".
2. **Stamp un-triaged findings.** For each `### ` block **below the v1 watermark**
   that is *finding-shaped* (§2.4) and has **no** `**Proposed ID:**` line, insert
   `- **Proposed ID:** _(maintainer to assign)_` as the finding's **first body
   bullet**: immediately after the heading, or — when the line directly after the
   heading is blank (the canonical `### h\n\n- **What:**` shape from
   `renderFindingBlock`) — immediately after that blank, so the stamp preserves
   the heading → blank → bullets layout. Either way it precedes the finding's
   existing bullets. (The §2.8 example is a no-blank finding, so its stamp sits
   directly under the heading; a blank-first finding keeps its blank above the
   stamp — §6 covers both.) A block that already has the line, a prose block, or a
   finding-shaped block *above* the watermark is left byte-identical (§2.4).

The v1 tracking tables are **not touched** — no relocation, no collapse, no
deletion. `migrate_v2` is **byte-neutral-to-slightly-larger** by design (it only
*adds* stamp lines); the byte *shrink* is `compact_resolved`'s job, run after
migration.

The stamp string `- **Proposed ID:** _(maintainer to assign)_` is byte-identical
to `renderFindingBlock`'s placeholder (`feedbackfile.cpp`) and matches
`enumerateFindingBlocks`'s id-line regex, so a re-run detects it as already-stamped
(§2.7).

### 2.3 The v1 watermark

The watermark = the greatest-position maintainer tracking heading, exactly
`parse(content).lastMaintainerLine` (1-based; -1 when the file has no matched
tracking block). Because tables are left in place, the watermark keeps its
original position, so the shipped v1 delta start — the **first `#`/`## `
contributor heading after the watermark** (`### ` headings are inert to the
boundary scan; §1.1) — is unperturbed by migration. A file with no matched
tracking block
(watermark -1) has every finding-shaped `### ` block treated as "below the
watermark" (all un-triaged) — the correct reading of a never-triaged file (§2.4).

**Precondition — the canonical maintainer-heading anchor.** The watermark
(`parse().lastMaintainerLine`) recognises a tracking block **only** by the exact
anchor `^## 📋 Ants Terminal roadmap tracking( update)? \(` (`feedbackfile.cpp`
`maintainerAnchorRe`) — the heading `renderTrackingBlock` / `op:append_tracking`
emit. A **non-canonical** tracking table (a heading like `## Status of prior
items (…)` or a `### `-level status recap, both of which occur in the real
corpus, e.g. `3D_Engine_Ants_MCP_Feedback.md`) does **not** set the watermark; the
`### ` findings around it are classified (§2.4) against whatever canonical
watermark *does* match (or -1). Migration leaves every table — canonical or not —
exactly where it is, so this only affects which findings are read as "below the
watermark," never data preservation.

### 2.4 Finding-shaped vs prose (the stamp discriminator)

Pass 2 must add the `**Proposed ID:**` line **only** to real findings, never to a
prose note, or the v2 delta floods with "Positive note"/"Updated priority"
blocks (the same never-stamp-prose posture as the standard's finding-shaped
guard, § "The un-triaged delta" step 4). A `### ` block with no existing
Proposed-ID line is **finding-shaped** iff **either**:

- its heading matches `\b(issue|observation)\b` (case-insensitive) — the corpus's
  `### Issue #N` / `### Observation #N` finding convention; **or**
- its body (fences skipped) carries ≥ 1 finding bullet matching
  `^ *[-*] +\*\*(what|repro|impact)[:*]` (case-insensitive) — i.e. a
  `- **What:**` / `- **Repro:**` / `- **Impact:**` bullet. The trailing `[:*]`
  class matches **both** the canonical colon-inside-bold `- **What:**`
  (`renderFindingBlock`, `feedbackfile.cpp`) and a hand-written colon-outside
  `- **What**:`. This **bullet arm** is the same three-field set the standard's
  suspected-untagged guard uses (mcp-feedback-files.md § "The un-triaged delta"
  step 4) and ANTS-3443 § 7 cite — a shared *definition* (the `feedback_query`
  consumer is still unbuilt, so it is not yet shared *code*), no drift on the
  bullet test. The **heading arm** (`\b(issue|observation)\b`) is
  *migrate_v2-specific* (a superset): the standard's suspected-untagged guard is
  bullet-only, so a finding recognised solely by its `Issue #N` heading here would
  not be flagged by `feedback_query` — an intentional widening (migration errs
  toward stamping a real finding), not a shared-definition claim. The same widening
  can also over-stamp a *prose* heading that merely contains "issue"/"observation"
  (e.g. `### Observations summary`) with a blank placeholder — harmless, since it
  only adds a line the maintainer clears during `assign_id`, and only below the
  watermark.

Everything else (`### Positive note`, `### Updated priority`, `### What worked
well`, a bare-prose `### ` block) is prose.

Then, per the v1 "above the last table = already reviewed" semantic, a `### `
block **with no existing Proposed-ID line** is handled by (finding-shaped ×
position). "Below the watermark" means the block's heading line is **strictly
greater than** `lastMaintainerLine` (a `### ` heading can never *equal* the `## `
watermark line, so `>` vs `>=` never bites); a file with watermark -1 treats
every block as below:

- **finding-shaped, below the watermark** → **stamp**
  `_(maintainer to assign)_` (a real, still-un-triaged finding).
- **finding-shaped, above the watermark** → **leave line-less**, report in
  `orphans[]` (§2.6). Under v1 it was already reviewed (it sits above a tracking
  table), so it becomes prose under v2 — but because that inference can be wrong
  (a genuinely un-triaged finding stranded above a *later* table added for other
  findings), it is surfaced, never silently dropped.
- **not finding-shaped, below the watermark** → **leave line-less**, report in
  `unclassified[]` (§2.6). The heuristic cannot tell a freeform finding (no
  `Issue`/`Observation` heading, no template bullet) from a genuine prose note,
  and a mechanical converter must not guess; but because the un-triaged tail sits
  below the watermark, any such block *might* be a finding the maintainer needs to
  id, so it is surfaced for a manual eyeball rather than silently dropped
  (mechanical classification is inherently lossy here — the real judgement is
  `assign_id`'s, §5). This channel is small in practice: the watermark is the
  *last* tracking table (near EOF on the real corpus), so "below the watermark" is
  a short tail, not the whole file. **`unclassified[]` is a one-shot signal.**
  Under today's marker-blind v1 reader (§1.1) the block still appears in the raw
  v1 delta (the post-watermark text), so it is not *immediately* lost; but once
  the marker-honoring v2 reader ships it reads as ordinary v2 prose (no
  `**Proposed ID:**` line) and — being bullet-less — is not caught by that
  reader's bullet-only `suspected_untagged[]` either, so it stops re-surfacing
  automatically. The maintainer should act on it from the migration envelope (or
  by eyeballing the file); it is surfaced once, not tracked.
- **not finding-shaped, above the watermark** → **leave line-less**, **not**
  reported (expected already-reviewed prose — the ~127 `### Positive note` /
  rollup blocks; reporting them would flood the envelope to no purpose).
- **any block that already has a `**Proposed ID:**` line** → untouched (the ~37
  findings that already carry the line — whether an id or a blank placeholder; the
  line is not re-stamped or moved), regardless of position or shape.

Blocks are enumerated with the shared fence-aware `enumerateFindingBlocks`
(ANTS-3443) — `idLine0 >= 0` means "already has the line" (untouched);
`idLine0 < 0` means "candidate for the discriminator above". Reusing that scanner
guarantees migrate_v2, compact_resolved, and the pending v2 `feedback_query` delta
agree on `### ` extents and on the authoritative id line (§7). The finding-bullet
scan (arm 2) is the helper's own fence-aware body loop over the block, reusing
`fenceOpenerChar` — `enumerateFindingBlocks` locates the id line, not the
What/Repro/Impact bullets, so the bullet scan is a small new loop (not a new
scanner function).

### 2.5 The rewrite (order of operations)

Because pass 2 keys on the original watermark position, the helper computes all
decisions first, then applies once:

1. `parse()` for the watermark (`lastMaintainerLine`) and
   `enumerateFindingBlocks()` for the `### ` blocks + their id-line state. No
   maintainer-block extents are needed (nothing is moved), so no `scanBoundaries`
   union is computed — a strict simplification over a relocating design.
2. Classify each `### ` block (stamp / orphan / unclassified / leave) by §2.4 —
   record the 1-based heading line and, for a stamp, the insertion point (the line
   directly under the heading).
3. Apply in one pass: insert the stamp lines **bottom-up** (highest heading line
   first) so an earlier insertion never shifts a later block's recorded line
   (parity with `compactShipped`/`compactResolved`); then bump the marker (pass 1).
   Stamps are disjoint (one per finding, each under its own heading), and the
   tables/prose are untouched, so the apply is unambiguous.

### 2.6 Response envelope

```
{ ok, op:"migrate_v2", path, dry_run,
  already_v2,                    // true ⟹ file marker was already ≥ 2: clean no-op
  stamped_count,                 // findings given a blank Proposed-ID line
  bytes_delta,                   // signed Σ: adds the stamp lines (+ a marker line if inserted)
  stamped:[ {heading, line} … ],       // line = original 1-based heading line
  orphans:[ {heading, line, reason} … ],       // finding-shaped block above the watermark, left line-less
  unclassified:[ {heading, line} … ],  // below-watermark `### ` block left line-less (not finding-shaped)
  path_derived }                 // true when `path` omitted + derived
```

Every `line` is an **input coordinate** — the 1-based heading line in the
*original* file. After a marker insert (marker-absent path, +1 to every line) or
an earlier stamp, the reported `line` will not equal the block's position in the
*written* file; consumers must treat `stamped[]`/`orphans[]`/`unclassified[]`
lines as before-image coordinates, not post-write offsets.

`orphans[].reason` is `"finding_shaped_above_watermark"` (the only orphan class
under mechanical-only). `unclassified[]` carries every below-watermark `### ` block
left line-less because it is not finding-shaped (§2.4) — the eyeball list that
guarantees no below-watermark block is silently dropped; above-watermark prose is
**not** listed (expected already-reviewed content). Between `stamped[]` and
`unclassified[]`, **every** below-watermark `### ` block without an existing id
line is accounted for (INV-5). On an **already-migrated** file (marker ≥ 2):
`ok:true, already_v2:true, stamped_count:0, bytes_delta:0`, file untouched — a
clean no-op, not a refusal (idempotency, §2.7). On a `: 1` file with nothing to
stamp (e.g. an empty skeleton): `ok:true, already_v2:false, stamped_count:0`,
marker still bumped to `: 2`.

Wrapper refusals: `bad_mode` (op not in the valid-op guard), `not_feedback_file`
(suffix guard), `not_found` (absent file), and `read_failed` (present but
unopenable) all precede any work; `write_failed` fires *after* the transform on a
failed non-dry-run `QSaveFile` commit (all inherited from the sibling wrapper,
`remotecontrol.cpp`). There is **no** `not_v2` here (that is `compact_resolved`'s
gate); `migrate_v2`'s whole purpose is to act on a v1 file, and an already-v2 file
is the clean no-op above, not a refusal.

### 2.7 Idempotency

A second `migrate_v2` is a clean no-op: pass 1 finds the marker already `: 2` →
`already_v2:true`, no stamping, file byte-identical. The helper short-circuits
when the version parsed from the **first** `<!-- ants-mcp-feedback: N -->` line
(its own scan — `ParseResult` carries no version field — matching the first
occurrence, conventionally line 1) is **≥ 2**; a missing or malformed version
parses as `< 2`, so migration proceeds and replaces the marker (§2.2 pass 1). The
`≥ 2` test (not merely `== 2`) leaves a future `: 3` file untouched by this v1→v2
tool rather than downgrading it; `: 2` is the only marker this op ever *writes*.
Because a below-watermark finding stamped on the first run now carries a
`**Proposed ID:**` line, the second run's `enumerateFindingBlocks` reports
`idLine0 >= 0` for it (already-tagged → untouched) — so even setting the marker
aside, no finding is re-stamped.

### 2.8 Worked example (before → after)

Watermark = the `## 📋 … tracking` heading. `### Issue #1` is below it and
finding-shaped (heading + bullets) with no id line → stamped. `### Positive note`
is below-watermark prose → left line-less + reported in `unclassified[]`.
`### Issue #0` sits *above* the watermark, finding-shaped, no line → left
line-less + reported in `orphans[]`. **The table stays exactly where it is.**

```markdown
<!-- ants-mcp-feedback: 1 -->
# Feedback TEST

### Issue #0 — earlier finding, never tabled
- **What:** an older gap.

## 📋 Ants Terminal roadmap tracking (2026-06-01, maintainer)

| #N | Status | Notes |
|---|---|---|
| #1 timeout | ✅ | shipped ANTS-1525 |

### Issue #1 — verify_changes timed out
- **What:** hangs on a cold cache.

### Positive note — apply_edits is fast
It felt instant.
```

→

```markdown
<!-- ants-mcp-feedback: 2 -->
# Feedback TEST

### Issue #0 — earlier finding, never tabled
- **What:** an older gap.

## 📋 Ants Terminal roadmap tracking (2026-06-01, maintainer)

| #N | Status | Notes |
|---|---|---|
| #1 timeout | ✅ | shipped ANTS-1525 |

### Issue #1 — verify_changes timed out
- **Proposed ID:** _(maintainer to assign)_
- **What:** hangs on a cold cache.

### Positive note — apply_edits is fast
It felt instant.
```

Only two lines change: the marker (`: 1` → `: 2`) and the inserted
`- **Proposed ID:** _(maintainer to assign)_` under `### Issue #1`. The table and
every other line are byte-identical. Counting the before-file from the marker as
line 1: `### Issue #0` is line 4, the watermark `## 📋 …` line 7, `### Issue #1`
line 13, `### Positive note` line 16. The envelope reports `stamped_count:1`,
`stamped:[{heading:"### Issue #1 …", line:13}]`,
`orphans:[{heading:"### Issue #0 …", line:4,
reason:"finding_shaped_above_watermark"}]`,
`unclassified:[{heading:"### Positive note — apply_edits is fast", line:16}]` —
every below-watermark block accounted for (INV-5). Then `assign_id` fills
`Issue #1`'s slot, and once its id is ✅, `compact_resolved` collapses the
write-up. The v1 delta *start* (the first `#`/`## ` heading after the watermark
at line 7) is unmoved by migration, so the shipped reader returns the exact same
delta before and after. NB in this minimal fixture the below-watermark findings
are **bare `### ` blocks** with no `#`/`## ` session heading between them and the
watermark, so under the `#`/`## `-keyed v1 rule (§1.1) that delta is in fact
**empty** — a real file wraps post-table findings under a `## <date>` session
heading, giving a non-empty delta. Either way, migration leaves it byte-identical
apart from the one stamp line it inserts inside it — the non-trivial (non-empty)
delta-preservation case is exercised by the §6 "v1 delta preserved" test, since
this worked example's delta is ∅→∅.

## 3. Invariants

- **INV-1** — `op:"migrate_v2"` is dispatched inside `cmdFeedbackLog`'s op switch
  (beside `compact_resolved`) and added to the valid-op guard (else `bad_mode`).
  The pure helper is m_main-independent (source-grep); the wrapper alone touches
  the filesystem.
- **INV-2** — **when migration runs** (marker `< 2` or absent/malformed), the
  output marker is exactly `<!-- ants-mcp-feedback: 2 -->` (bumped in place, or
  inserted when absent). A marker ≥ 2 is the no-op (INV-6) and is left untouched.
- **INV-3** — a `**Proposed ID:** _(maintainer to assign)_` line is added iff a
  `### ` block is finding-shaped (§2.4), below the watermark, and has no existing
  Proposed-ID line. It is inserted directly under the heading. A prose block, an
  already-tagged block, and a finding-shaped block above the watermark are never
  stamped; the last is reported in `orphans[]`, and a not-finding-shaped
  below-watermark block in `unclassified[]`; above-watermark prose is neither
  stamped nor reported.
- **INV-4** — **no v1 tracking table is moved, collapsed, or deleted.** Every
  maintainer heading, table row, and separator is byte-identical after migration;
  only the marker and the added stamp lines change. Hence
  `parse(after).lastMaintainerLine` maps to the *same table* as
  `parse(before).lastMaintainerLine`: no stamp line lands above the watermark
  (stamps go only *below* it), stamps are `### `-body `- ` bullets that create no
  new `#`/`## ` boundary (so the delta *start* — first `#`/`## ` heading after the
  watermark — is unmoved), and an inserted marker line (marker-absent path) shifts
  **every** line by +1 uniformly, which the position-*relative* delta is invariant
  to. So `parse(after).delta` equals `parse(before).delta` modulo the stamp lines
  added inside it — the shipped v1 delta is preserved.
- **INV-5** — no below-watermark `### ` block is silently dropped: every one
  without an existing `**Proposed ID:**` line is **either** stamped (finding-shaped
  → enters the v2 delta) **or** listed in `unclassified[]` (not finding-shaped →
  surfaced for a manual eyeball). The two sets partition the below-watermark
  line-less blocks. No contributor `### ` finding body is ever deleted or
  reordered (only a stamp line is *added* under a heading).
- **INV-6** — idempotent: a second run on a `: 2` (or ≥ 2) file is a clean no-op
  (`already_v2:true`, byte-identical), short-circuited on the marker before any
  pass; and a stamped finding is detected already-tagged on re-run regardless
  (§2.7).
- **INV-7** — `dry_run:true` returns the identical envelope (minus the write) and
  leaves the file byte-for-byte unchanged.
- **INV-8** — atomic write via `QSaveFile … .commit()` (source-grep).
- **INV-9** — wrapper refusals: `bad_mode` (invalid op), `not_feedback_file`
  (suffix guard), `not_found` (absent file), `read_failed` (present but
  unreadable) precede any work; `write_failed` fires post-transform on a failed
  commit. An already-migrated file (marker ≥ 2) is the clean no-op (INV-6), not a
  refusal; there is no `not_v2` and no roadmap read.
- **INV-10** — fenced regions are skipped in both the `### `-block enumeration
  (`enumerateFindingBlocks`) and the finding-bullet detection (the helper's own
  fence-aware body scan reusing `fenceOpenerChar` — a new *loop*, not a new
  scanner function), so a `### `/`**Proposed ID:**`/table line pasted inside a
  ``` fence never perturbs migration. The version marker is located by the
  helper's own first-marker-line match (conventionally line 1, above any fence),
  short-circuiting on version ≥ 2 (§2.7).
- **INV-11** — `bytes_delta` is the signed size change: it *adds* the stamp lines
  (and a marker line if one had to be inserted) and re-writes the marker to
  canonical form; no table or prose line is removed. For a canonical-length
  marker `bytes_delta ≥ 0`; the only way it goes slightly negative is
  canonicalising a whitespace-padded original marker (`<!-- ants-mcp-feedback:  1
  -->`) with zero stamps — a non-corpus edge. `migrate_v2` does not shrink content
  — the shrink is `compact_resolved`, run after.

## 4. RAM / build cost

One extra pure function in `ants_core_lib`. Two O(lines) scans — `parse()`
(watermark) and `enumerateFindingBlocks()` (`### ` blocks) — plus the helper's
per-candidate-block finding-bullet loop and one bottom-up apply over a
`QStringList`. No `scanBoundaries` union, no relocation, no blank-line
normalisation (all dropped with the leave-in-place design). No new allocation
class (the file is transient), no new build target, no roadmap read.

## 5. Out of scope

- **Auto-stamping finding→id from the v1 tables** — the fragile reverse-engineer
  the maintainer explicitly declined (§1.1). The real finding→id triage is
  `op:assign_id` (spec pending). `migrate_v2` never reads a table's *id* content.
- **`assign_id`** — the inline triage write (fill a finding's `**Proposed ID:**`
  slot with the id(s) or an `n/a — <reason>` closure). Its own spec.
- **Relocating / archiving / pruning the v1 tables** — migration leaves them in
  place (§1.1). Moving them to a frozen archive (the de-clutter idea) is a
  possible **separate later op**, deliberately deferred here because relocating
  them to EOF empties the shipped v1 delta until the v2 reader lands; a future
  archive op should run only after the v2 `feedback_query` delta rule ships (or
  should not move the watermark). `prune_tracking` (v1) still dedups the in-place
  tables *before* migration if wanted; after migration the file is `: 2` but the
  tables remain readable v1 tracking blocks in place.
- **Normalising v1 closure tokens (`(self-resolved)`) to `n/a — <reason>`** —
  that was part of the dropped auto-stamp path; under mechanical-only the closure
  history stays inside the in-place table verbatim, and a maintainer records a v2
  closure via `assign_id` when they triage the finding.

## 6. Tests

Feature-conformance `tests/features/feedback_log_migrate_v2/`: `spec.md` +
`test_feedback_log_migrate_v2.cpp` (pure `migrateV2` over synthetic v1 content —
no MainWindow) + a live `cmdFeedbackLog` drive + schema/dispatch source-greps.
Cases cover INV-1…INV-11:

- **the §2.8 mixed fixture** — asserts the marker bump, the one stamp (`Issue #1`,
  inserted under the heading), the one `unclassified[]` entry (`Positive note`),
  the one orphan (`Issue #0`, above watermark), that **the table is byte-identical
  and in place** — the whole after-file verbatim — and `bytes_delta > 0` (INV-11).
- **blank-first finding** (§2.2 pass 2): a finding-shaped block below the watermark
  whose heading is followed by a blank line (`### h\n\n- **What:**`) → the stamp is
  inserted **after** that blank (first body bullet), preserving the heading → blank
  → bullets layout; a no-blank finding gets the stamp directly under the heading.
- **finding-shaped discriminator** (INV-3): a heading-numbered finding with no
  bullets is stamped; a `- **What:**`-only finding with a non-numbered heading is
  stamped; a `### Positive note` with prose is left line-less.
- **already-tagged untouched** (INV-3): a finding with an existing
  `**Proposed ID:** ANTS-1525` line is byte-identical (not re-stamped).
- **watermark semantics** (INV-3): a below-watermark finding is stamped; an
  above-watermark finding is an orphan, not stamped.
- **below-watermark freeform** (INV-5/3): a below-watermark `### ` block with a
  non-`Issue`/`Observation` heading and no `- **What/Repro/Impact:**` bullet →
  left line-less, **not** stamped, reported in `unclassified[]`; and an
  above-watermark such block is line-less and **not** in any report.
- **tables untouched** (INV-4): a file with ≥ 1 canonical tracking table → the
  table bytes + position are byte-identical after migration; `lastMaintainerLine`
  is unchanged (stamps land only below it).
- **v1 delta preserved** (INV-4): a fixture with a `## <date>` contributor session
  heading below the watermark (so the `#`/`## `-keyed v1 delta is non-empty) →
  `parse(after).delta` equals `parse(before).delta` apart from the inserted stamp
  line(s); the delta-start line (first `#`/`## ` after the watermark) is
  unchanged. Guards the §2.8 delta claim against the `### `-inert boundary rule.
- **canonical-anchor precondition** (§2.3): a non-canonical tracking table
  (heading `## Status of prior items (…)`) does not set the watermark and is left
  in place; a canonical `## 📋 Ants Terminal roadmap tracking (…` one sets it.
- **no-watermark file** (§2.3): a file with no tracking table stamps every
  finding-shaped block (all below the -1 watermark).
- **marker-absent legacy** (INV-2): a `DOOM`-style file with no marker gets
  `<!-- ants-mcp-feedback: 2 -->` inserted as line 1.
- **malformed marker** (§2.2 pass 1): a `<!-- ants-mcp-feedback: -->` (no digit) is
  replaced by `: 2`, not left beside an inserted one.
- **mis-placed marker** (§2.2 pass 1): a `<!-- ants-mcp-feedback: 1 -->` **not on
  line 1** (e.g. after the H1) is replaced in place (not duplicated by an inserted
  line-1 marker).
- **idempotency** (INV-6): feed the migrated output back → `already_v2:true`,
  byte-identical, `stamped_count:0`.
- **fence safety** (INV-10): a `### `/table/`**Proposed ID:**` line inside a
  ``` fence is not enumerated / stamped.
- **wrapper** (INV-7/9): `dry_run` leaves the file unchanged; `not_found` on an
  absent file; a real write produces a `: 2` file; schema enumerates the op;
  `cmdFeedbackLog` routes it to `FeedbackFile::migrateV2`.

## Cold-eyes loop log

Two-phase review: 6 loops on the original **relocate-tables-to-an-archive**
design, a mid-review **design pivot** to **leave-tables-in-place**, then 3 loops
on the rewritten design. All loops 2 reviewers, cold (loop N+1 briefed
identically to loop 1 — never told what was fixed).

### Phase A — relocate-tables design (loops 1–6)

- **Loop 1** — 0C, 2H, 4M, 4L. H: the finding-shaped bullet regex required
  `**What**` immediately (never matched the canonical `**What:**`); §7's
  standard-reconciliation list was incomplete (3 unflagged auto-stamp sites).
- **Loop 2** — **1C**, 1H, 3M, 2L. C (both lanes): the table-relocation extent
  used `scanBoundaries`'s `#`/`## ` set, which is `### `-blind, so it swept a
  trailing `### ` finding into the archive — the §2.8 example was un-reproducible.
  Fixed by making the extent `### `-aware (union with `enumerateFindingBlocks`).
- **Loop 3** — 0C, 2H, 3M, 5L. Blank-line reproducibility of the relocation;
  §4/§7 still named `scanBoundaries` for extents (contradicting the loop-2 fix).
- **Loop 4** — 0C, 0H, 3M, 6L. "parse exposes the boundaries via its result" was
  false (`ParseResult` has no boundary list); marker malformed/mis-placed edges.
- **Loop 5** — 0C, 0H, 1M, 5L. §7 kept missing scattered stale `migrate_v2`
  provenance markers → replaced item-by-item enumeration with a repo-wide
  provenance-sweep instruction (complete-by-construction).
- **Loop 6** — 0C, 0H, 2M, 3L. **The load-bearing finding:** relocating the
  tables to EOF moves the v1 watermark (`lastMaintainerLine`) to EOF, which
  **empties the shipped v1 un-triaged delta** on a migrated file until the
  position-independent v2 reader ships — a silent regression window. Documented as
  an ordering dependency, then surfaced to the maintainer as a design fork.

### Design pivot (2026-07-05)

The maintainer chose **leave-tables-in-place** over relocate-plus-dependency: it
removes the delta-dark hazard entirely (watermark unmoved → v1 delta preserved),
and drops the extent-computation, blank-line-normalisation, and archive machinery
— which had generated most of the phase-A findings (the loop-2 CRITICAL, the
loop-3 blank-reproducibility, the loop-6 delta hazard). The spec was rewritten to
two mechanical passes (marker bump + stamp), carrying forward every verified
phase-A learning (the `[:*]` bullet regex, the finding-shaped discriminator, the
marker `[0-9]*`/≥2 handling, orphans[]/unclassified[], the §7 provenance sweep,
the refusal set) minus relocation.

### Phase B — leave-in-place rewrite (loops 1–3)

- **Loop 1** — 0C, 1H, 2M, 3L. H (both lanes): the §2.8 envelope line numbers were
  miscounted (Issue #1 12→13, Positive note 19→16 — the numbers a conformance test
  copies). Plus a stale `migrate_v2` attribution in the sibling ANTS-3443 spec.
- **Loop 2** — 0C, 1H, 2M, 3L. H (both lanes): §2.8 narrated the v1 delta as
  "everything after the last maintainer heading" and claimed it returned the
  post-watermark `### ` findings — but the delta is `#`/`## `-keyed (`### ` inert),
  so the minimal fixture's delta is empty. Reworded the delta model accurately and
  stated the load-bearing **marker-blind** premise (shipped readers call `parse()`
  unconditionally, so the `: 2` bump does not route to the unbuilt v2 reader).
- **Loop 3** — **0C, 0H, 0M** (both lanes) — **clean.** Every load-bearing claim
  re-verified live: marker-blind at `remotecontrol.cpp:10748`/`13928`; delta-start
  = first `#`/`## ` after the watermark (`### ` inert, `isBoundaryHeading`);
  `maintainerAnchorRe`, `enumerateFindingBlocks`/`idLine0`, `renderFindingBlock`
  placeholder, `ParseResult`-has-no-version all confirmed; §2.8 line numbers
  byte-exact; §7 ten-item reconciliation complete against the standard; ANTS-3443
  reconciled. Residual: LOW/INFO polish only (a surviving "pure v2" line in the
  standard folded into §7 item 1; blank-first stamp insertion pinned; the
  heading-arm prose false-positive noted; test-coverage nits) — all applied. No
  structural/mechanical/architectural finding survived.

- **Convergence (2026-07-05):** 9 loops across two designs. The pivot to
  leave-in-place was the decisive simplification — it dissolved the phase-A
  CRITICAL and the delta-dark hazard rather than patching them. Phase B converged
  in 3 loops (clean at loop 3 modulo polish). Signed off as implementation-ready;
  the only cross-doc commitments the implementer must honour are the §7 standard
  reconciliation (ten items) and the shared `enumerateFindingBlocks` scanner
  (§2.4/§7).
