## 1. Problem

The in-process MCP server in `src/claudeintegration.cpp:1054-1292`
already exposes 6 tools (`get_scrollback`, `get_cwd`,
`get_session_info`, `get_last_command`, `get_git_status`,
`get_environment`) over a per-Ants Unix socket
(`$TMPDIR/ants-terminal-mcp-<pid>`). Claude Code sessions running
inside Ants tabs can register that socket in
`~/.claude/settings.json`'s `mcpServers` block and use the tools
directly via JSON-RPC `tools/call` — no shell dancing required.

Three of the most useful pieces of state a Claude session typically
wants are **not** in that set:

| Want | Today | Cost (tokens per session that needs this) |
|---|---|---|
| "What's on the project's roadmap?" | `Read ROADMAP.md` (482 KiB file → ~123 K tokens at 4 chars/token) | 123 K |
| "What other tabs are open in this Ants instance?" | `Bash` shells out to `ants-terminal --remote tab-list` and parses the JSON | bash-glue Claude composes (~30-100 tokens) on top of envelope cost both paths share |
| "What did tab N print recently?" | `Bash` → `--remote get-text --tab N --lines 50` | same shape — ~30-100 tokens of bash-glue on top of shared envelope |

The "saving" headline below applies **only to sessions that
actually need the data**. CLAUDE.md autoloads at session start
(13 KiB / ~3.5 K tokens, project convention); ROADMAP.md does
not — Claude pulls it on-demand for planning / triage / status
work. No telemetry today, so the per-session probability isn't
quantified; this tool exists so the *common* path becomes the
cheap path without having to estimate that probability up front.
ANTS-1245 (roadmapped 2026-05-12) will close that telemetry gap
by tracking real per-session token usage.

All three are already implemented as `RemoteControl::cmdRoadmapQuery`
(now `src/remotecontrol_roadmap_query.cpp`), `cmdTabList`, and `cmdGetText`
(`:331`). They return structured JSON, are peer-cred-gated +
mtime-cached (in the roadmap case), and have a test corpus pinning
their semantics.

Surfacing them as MCP tools eliminates the file Read entirely for
`roadmap_query` and the bash-glue token cost for the other two.
For a session that *would have* read ROADMAP.md, the saving is
~110 K tokens (123 K Read cost → ~13 K structured response,
measured per § 7 below). For `tab_list` / `get_text`, per-call
saving is ~30-100 tokens of bash-glue Claude no longer has to
compose, on top of envelope cost that's shared by both transports.

The fix is mechanical: register 3 entries in `tools/list`, add 3
cases to `tools/call`, wire 3 provider lambdas in
`setupClaudeMcpProviders` that delegate to the existing
RemoteControl cmd handlers. No behavior in the IPC transport
changes; no new business logic. Promote the 3 cmd handlers from
`private` to `public` in `remotecontrol.h` so the MCP layer can
call them through the existing `MainWindow::m_remoteControl`.

## 2. Mechanism

### 2.a Delegate vs duplicate

Two paths to share logic between the two transports:

1. **Duplicate** the body of each cmd handler into a lambda in
   `setupClaudeMcpProviders`. Pro: zero header churn. Con: the
   roadmap-query path has a 100 ms mtime cache (`m_roadmapCacheMtimeMs`,
   INV-10 on the IPC verb's spec) — duplicating means each transport
   keeps its own cache, doubling cache-miss latency on the first call
   after an edit.
2. **Promote + delegate.** Make the 3 cmd handlers public on
   `RemoteControl`; provider lambdas call them on the existing
   `MainWindow::m_remoteControl`. Pro: cache is shared, INV-10
   latency budget covers both transports, no body duplication, easy
   regression test (one impl, two transports). Con: small header
   churn (3 lines moved from `private:` to `public:`).

**Chosen: 2 (promote + delegate).** The cache-share alone is worth
the header churn, and it keeps the two transports semantically
identical — a regression-pin in `roadmap-query`'s feature test
covers both transports for free.

### 2.b MCP tool schemas

JSON-RPC `tools/list` payloads for the 3 new tools:

```json
{
  "name": "roadmap_query",
  "description": "Query the active tab's ROADMAP.md as structured bullets. Each bullet returns {id, status, headline, kind, lanes}. Envelope: {ok:true, bullets:[…], path, count} on success or {ok:false, error, code} when the active tab's project has no ROADMAP.md. The full bullet set is returned — narrow client-side by status or substring. Future enhancement (out of scope here, see § 9): optional `status` parameter to gate to active items, cutting payload ~8×."
}
```

```json
{
  "name": "tab_list",
  "description": "List all open terminal tabs in this Ants instance. Each tab object: index, title, cwd, shell_pid, claude_running (bool), color (hex string or empty). Returns {ok:true, tabs:[…]}."
}
```

```json
{
  "name": "get_text",
  "description": "Read trailing scrollback lines from a tab. Optional `tab` (integer, default = active tab) and `lines` (integer, default 100, capped at 10000). Returns {ok, text, lines, bytes} or {ok:false, error} when the tab index is out of range.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "tab":   {"type": "integer"},
      "lines": {"type": "integer", "default": 100}
    }
  }
}
```

The first two take no parameters; `roadmap_query` always queries the
*active* tab (matching the IPC verb's contract — `cmdRoadmapQuery`
calls `m_main->roadmapPathForRemote()` which takes no tab argument).
A Claude session in tab A asking `roadmap_query` therefore gets tab
A's project roadmap; querying tab B's project roadmap is out of scope
for this commit and would require an IPC-verb signature extension
first. `tab_list` is inherently global. `get_text` has the same `tab`
/ `lines` shape as the IPC verb at `remotecontrol.cpp:331-378`.

### 2.c Result envelope

MCP `tools/call` result envelope per the existing pattern (see the
6 current tools at `claudeintegration.cpp:1226-1258`):

```json
{
  "content": [{"type": "text", "text": "<compact-json>"}]
}
```

The JSON returned by the cmd handler is serialised compactly and
wrapped in a single text-content block. Claude sees structured data
inside an MCP tool result.

### 2.d Provider plumbing

Three new `ClaudeIntegration` setters, mirroring the existing 5
provider lambdas (`setScrollbackProvider`, `setCwdProvider`,
`setLastCommandProvider`, `setGitStatusProvider`,
`setEnvironmentProvider`). Five providers but six tools — the sixth,
`get_session_info`, reads `ClaudeIntegration` member state directly
(`m_state`, `m_activeSessionId`, etc.) without a provider lambda.
The new three each need a provider because the source of truth is
`m_remoteControl` on the MainWindow.

```cpp
void setRoadmapQueryProvider(std::function<QString()> provider);
void setTabListProvider(std::function<QString()> provider);
void setGetTextProvider(std::function<QString(int tab, int lines)> provider);
```

Each provider returns the **already-serialised JSON string** (compact
form) so the MCP dispatcher just wraps it in a content block without
re-parsing. `setGetTextProvider` takes `tab` and `lines` ints; a
caller passes `-1` for tab to mean "active tab" and `0` for lines to
mean "default 100" — matching the IPC verb's defaults.

In `MainWindow::setupClaudeMcpProviders`:

```cpp
m_claudeIntegration->setRoadmapQueryProvider([this]() -> QString {
    return QString::fromUtf8(
        m_remoteControl->cmdRoadmapQuery().toJson(QJsonDocument::Compact));
});
m_claudeIntegration->setTabListProvider([this]() -> QString {
    return QString::fromUtf8(
        m_remoteControl->cmdTabList().toJson(QJsonDocument::Compact));
});
m_claudeIntegration->setGetTextProvider(
    // tab < 0 → omit (active tab); lines <= 0 → omit (default 100).
    [this](int tab, int lines) -> QString {
        QJsonObject req;
        if (tab   >= 0) req["tab"]   = tab;
        if (lines >  0) req["lines"] = lines;
        return QString::fromUtf8(
            m_remoteControl->cmdGetText(req).toJson(QJsonDocument::Compact));
    });
```

`m_remoteControl` is created at `mainwindow.cpp:1058` (before
`setupClaudeMcpProviders` at `:3494`). Always non-null; `start()`
failure leaves the object alive and addressable, the socket
listener just doesn't bind. The cmd handlers themselves don't
require the socket to be live — they only read `m_main` state.

### 2.e Dispatcher edit

In `tools/list` add 3 entries. In `tools/call` add 3 `else if`
clauses, each guard-checking the provider before invoking. Tool
description text matches § 2.b. Same `makeTextContent` helper
already in place. No JSON-RPC envelope changes (`reqId`,
`haveResult`/`error`, `disconnectFromServer` flow is unchanged).

The `get_text` case extracts the two optional MCP arguments
explicitly via `isDouble()`, applying the "-1 = active tab" /
"0 = default lines" sentinels that the provider lambda reads
(per INV-9). The pre-existing `get_scrollback` MCP case uses
`.toInt(50)` (default-fallback overload) at
`claudeintegration.cpp:1227-1228` — fine when "argument absent"
and "argument == 0" are interchangeable. `get_text` cannot use
that overload because `tab=0` is a valid index distinct from
"tab omitted", so the dispatcher adopts the IPC verb's
`isDouble()` predicate (`remotecontrol.cpp:347`):

```cpp
QJsonObject args = params.value("arguments").toObject();
const QJsonValue tabVal   = args.value("tab");
const QJsonValue linesVal = args.value("lines");
int tab   = tabVal.isDouble()   ? tabVal.toInt()   : -1;
int lines = linesVal.isDouble() ? linesVal.toInt() :  0;
result["content"] = makeTextContent(m_getTextProvider(tab, lines));
toolHandled = true;
```

Both transports now apply identical semantics for the
omitted-vs-zero distinction.

| 8 | auth | The MCP socket's existing `SO_PEERCRED` UID check at `claudeintegration.cpp:1116-1126` continues to gate every connection. Adding 3 tools does not relax authentication. |
| 9 | tab-zero | `get_text` with `"tab": 0` (a valid tab index, distinct from "tab omitted") routes to tab 0 — the IPC verb's `tabVal.isDouble()` guard at `remotecontrol.cpp:347` distinguishes omitted-from-zero. The IPC verb then sees a JSON object whose `tab` field is present iff the caller supplied one. |

## 5. Acceptance tests

`tests/features/mcp_extra_tools/test_mcp_extra_tools.cpp` — GUI-free,
links `ClaudeIntegration` + `RemoteControl` + `MainWindow` minimum
deps. Drives the MCP socket directly with `QLocalSocket` (no Claude
Code in the loop). Test cases:

1. **T1 — tools/list count.** `initialize` → `tools/list` → expect
   array length == 9. Asserts INV-1.
2. **T2 — roadmap_query no roadmap.** Run against a tab whose cwd
   has no ROADMAP.md. `tools/call` `roadmap_query` → parse inner
   text → `{ok:false, code:"no_roadmap_loaded"}`. Asserts INV-2
   error path.
3. **T3 — roadmap_query happy path.** Stage a tiny `ROADMAP.md` in
   a tmp cwd, point an Ants tab at it, call. Inner JSON has
   `ok:true, bullets[]` with at least one entry. Asserts INV-2
   success path.
4. **T4 — tab_list.** With 2 tabs open, call `tab_list`. Inner JSON
   `ok:true, tabs[]` has length 2 with valid index/title/cwd fields.
   Asserts INV-3.
5. **T5 — get_text default.** Synthetic PTY output → `get_text` no
   args → returns the trailing lines (≤100). Asserts INV-4 happy.
6. **T6 — get_text tab=N.** Same with explicit `arguments:{tab:1}`
   → returns tab 1's text not tab 0's. Asserts INV-9 (zero is
   distinct).
7. **T7 — get_text out-of-range.** `arguments:{tab:99}` → inner
   `{ok:false, error}`. Asserts INV-4 error.
8. **T8 — parity with IPC.** Compare `roadmap_query` MCP response
   inner text against `RemoteControl::cmdRoadmapQuery()` direct call
   — byte-identical. Asserts INV-6.

## 7. Memory + token-saving budget

**Memory:** zero new allocations beyond the 3 `std::function`
slots in `ClaudeIntegration` (~24 B each on x86-64). No buffers,
no caches, no threads.

**Token saving per Claude Code session in an Ants tab** (ROADMAP.md
sized at 8 947 lines / 482 KiB / ~123 K tokens; **397 status-emoji
bullets** today: 309 ✅ + 54 📋 + 31 💭 + 3 🚧, 2026-05-12):

| Workflow | Before | After | Saving |
|---|---|---|---|
| Session-with-roadmap-need: Claude wants project roadmap | `Read ROADMAP.md` (482 KiB → ~123 K tokens) | `roadmap_query` (~52 KiB JSON → ~13 K tokens, 397 bullets × ~133 B/bullet measured from 7 spot-checked rows) | **~110 K tokens** |
| Claude wants to see other tabs | `Bash --remote tab-list` (~30-100 tokens of glue + shared envelope) | `tab_list` direct (envelope only) | ~30-100 tokens (just the glue Claude doesn't write) |
| Claude wants tab N's last 50 lines | `Bash --remote get-text` (~30-100 tokens of glue + shared envelope) | `get_text` direct (envelope only) | ~30-100 tokens |

**Caveat on `roadmap_query` numbers.** Today's `cmdRoadmapQuery`
emits **all** status-emoji bullets including ✅ (309 of the 397
are already-shipped items most Claude queries don't need). A
session that only cares about active work (📋 + 🚧 = 57 bullets ≈
~7.7 KiB JSON ≈ ~1.9 K tokens) pays ~7× more than necessary today.
That's the highest-leverage open enhancement on this surface — see
§ 9 for the `status` filter follow-up that would cut typical-query
output from ~13 K to ~1.9 K tokens.

**`tab_list` / `get_text` numbers.** The headline saving here is
smaller than naively expected. Both `Bash` and MCP `tools/call`
carry comparable JSON-RPC envelope cost in Claude's transcript.
The real differential is the bash-glue Claude composes itself
(`ants-terminal --remote get-text --tab 3 --lines 50 | jq …` →
roughly 30-100 input tokens per call). The MCP tools' *real win*
is removing a category of errors (Claude mis-typing the bash) and
giving the tools a fixed schema Claude can introspect — not the
per-call token count.

The roadmap saving alone pays for the spec + impl in roughly two
sessions; the per-call savings are pure ongoing dividend.

## 8. Re-open conditions

- **MCP `tools/list` count drifts.** If a future change adds a 10th
  tool without updating INV-1, T1 catches it — refresh the
  invariant + test.
- **IPC verb contract changes.** If `cmdRoadmapQuery` / `cmdTabList`
  / `cmdGetText` change their response shape, T2/T3/T4 also change
  — they share the implementation, so the IPC-verb feature test
  flags it first. Update both in lockstep.
- **MCP stdio transport added.** If we later ship a standalone
  `ants-mcp-server` binary that speaks stdio MCP (per
  ANTS-1162 sub-(4)), it should expose the *same* 9-tool surface.
  This spec then becomes the parity baseline.

## 9. Out of scope

- Standalone `ants-mcp-server` binary (stdio transport). Different
  transport, different shape — covered by ANTS-1162 sub-(4).
- **Optional `status` filter on `roadmap_query`.** Highest-leverage
  open follow-up: an optional `arguments.status: "active"` / `"all"`
  / `"shipped"` parameter that gates the returned bullet set. Active-
  only (📋 + 🚧, 57 bullets today) cuts typical-query payload from
  ~13 K to ~1.9 K tokens — additional ~11 K token saving per
  query, on top of this spec's ~110 K. Requires extending
  `cmdRoadmapQuery` to accept the param (~10 LoC) — out of scope
  here because (a) it's an IPC-verb contract change that touches
  ANTS-1117's invariants, (b) we want to ship the wiring first and
  validate the surface before reshaping the verb. Follow-up ANTS
  ID at impl time of that work.
- **Schema enrichment of `cmdRoadmapQuery`.** Today's output omits
  per-bullet `source`, `layman`, and `summary` fields that exist on
  `BulletRecord` and would help Claude prioritise. Adding them
  roughly doubles JSON size (~26 K tokens at current bullet count),
  net-neutral with the `status` filter above but cumulative without
  it. Out of scope; same reasoning as the filter follow-up.
- **New MCP tools without a backing IPC verb** (e.g. a
  `roadmap_search` substring-search tool). Not blocked, just not
  in this commit.
- **Write verbs** (`roadmap-status`, `roadmap-allocate-id`, etc.) —
  this commit ships read-only tools; write-verbs follow in a
  separate ANTS ID once the read surface is validated.
- **Cross-machine MCP.** Unix-domain socket only; no TCP listener.
