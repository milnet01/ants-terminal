# ANTS-1399 — `tool_info(name)` MCP verb

## Problem

`tools/list` is the only path to read MCP tool descriptors —
it returns the whole registry (~30 tools, ~5 KiB compressed)
even when the assistant only needs to refresh memory on one
tool's schema. The friction is per-session: typically Claude
calls `tools/list` once at init, but if the descriptor isn't
in context anymore (compaction, long session), the only way
to refresh one tool's args is to re-fetch the whole list.

## Goal

A new MCP verb `tool_info({name})` that returns a single
descriptor in the same shape `tools/list` emits per-tool:
`{ok:true, name, description, inputSchema}`. Unknown name
returns `{ok:false, code:"unknown_tool", error, available:[]}`.

## Design

### Implementation strategy

Lazy snapshot: `tools/list` populates a private cached
`m_lastToolsList` member at the end of its array build.
`tool_info` reads from the cache. The cache lifetime is the
process lifetime — descriptors are built from compile-time
literals and never change.

Edge case: `tool_info` called before any `tools/list` (i.e.
cache empty). In practice MCP clients call `tools/list`
during init, so this is unlikely. Defensive envelope:
`{ok:false, code:"tools_not_ready", error:"call tools/list first"}`.

This avoids the alternative of extracting the entire 1364-line
`tools/list` inline block into a separate function — that
refactor is properly owned by ANTS-1297 (lazy registration)
and would expand this ticket's diff far beyond the spec's
intent. The lazy-snapshot is the lightest viable v1.

### Schema

```jsonc
{
  "name": "tool_info",
  "description": "Fetch a single MCP tool's descriptor — name,
    description, inputSchema. Cheaper than a full tools/list
    refresh (~50–200 B vs ~5 KiB). Unknown name returns
    code=unknown_tool plus an `available` list of registered
    tool names.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "name": {
        "type": "string",
        "description": "Registered tool name (e.g. \"verify_changes\")."
      }
    },
    "required": ["name"],
    "additionalProperties": false
  }
}
```

`tool_info` is classified `CallerCwdContract::ProcessGlobal` —
it reads a process-wide registry, not per-tab state, so
`caller_cwd` is irrelevant.

### Envelope

**Success (tool found):**
```json
{
  "ok": true,
  "name": "verify_changes",
  "description": "Run the project's build / test / lint gates ...",
  "inputSchema": { "type": "object", "properties": { ... }, ... }
}
```

**Unknown name:**
```json
{
  "ok": false,
  "code": "unknown_tool",
  "error": "tool_info: no MCP tool registered as 'XYZ'",
  "available": ["caller_cwd_info", "file_outline", "..."]
}
```

**Missing/empty `name` arg:**
```json
{
  "ok": false,
  "code": "missing_name",
  "error": "tool_info: 'name' arg is required"
}
```

**Cache empty (defensive):**
```json
{
  "ok": false,
  "code": "tools_not_ready",
  "error": "tool_info: call tools/list first to populate the descriptor cache"
}
```

### Self-registration

`tool_info` is itself registered as a tool in `tools/list`,
so `tool_info({name: "tool_info"})` round-trips. This is
the same self-documenting convention `tools/list` already
follows for every other registered verb.

## Invariants

- **INV-1.** `tool_info` is registered as an MCP tool in the
  `tools/list` block. The schema declares `name` as required
  with `additionalProperties: false`.

- **INV-2.** After any `tools/list` call, the private
  `m_lastToolsList` member holds a deep copy of the emitted
  array.

- **INV-3.** `tool_info({name: X})` with `X` registered
  returns the same `{name, description, inputSchema}` slice
  that `tools/list` would emit for `X`. The slice is
  byte-identical to the corresponding entry.

- **INV-4.** Unknown `name` returns `{ok:false,
  code:"unknown_tool", error, available:[...]}`. The
  `available` array lists every registered tool name in
  registration order (matches `tools/list` ordering).

- **INV-5.** Missing/empty `name` returns
  `{ok:false, code:"missing_name", error}`.

- **INV-6.** Empty snapshot (cache cold) returns
  `{ok:false, code:"tools_not_ready", error}`.

- **INV-7.** `tool_info` is classified `ProcessGlobal` in
  `callerCwdContractFor` — no `caller_cwd` required or
  consulted.

- **INV-8.** Inline-dispatched (not routed through
  `m_toolProviders`) like `get_session_info`. The cached
  snapshot lives on the `ClaudeIntegration` singleton, so
  dispatch is direct.

## Out of scope

- Schema invalidation when descriptors change at runtime.
  Today descriptors are static; ANTS-1297 (lazy registration)
  owns the dynamic case.
- Bulk multi-tool lookup (`tool_info({names: [...]})`). One
  tool per call — keeps the contract simple.
- Wire-side optimisation of the per-tool descriptor (tag
  shortening, etc.) — ANTS-1403 territory.

## RAM budget

One `QJsonArray` snapshot at ~5 KiB compact (~30 tools ×
~150–200 B each). Lifetime: process. Negligible vs the rest
of `ClaudeIntegration`'s state.

## Build cost

~70 LoC added: snapshot member declaration, snapshot-update
at tools/list end, tool_info schema block (~20 lines),
tool_info inline handler (~30 lines), classification table
entry (1 line).
