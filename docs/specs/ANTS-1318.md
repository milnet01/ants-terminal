# ANTS-1318 — Weekly Wednesday release cadence + Patron-tier frozen-RC pipeline

**Status:** spec draft (2026-05-13). Cold-eyes pending — see § 11
loop log. **User-confirmed model:** frozen RC with cherry-pick for
bug fixes; tag-based (no long-lived `rc/<version>` branch).
**Source:** user directives 2026-05-13 (weekly Wed cadence + Patron
7-day frozen-RC lead with bug-fix folding).
**Blocked by:** none — uses existing `/bump`, `/release`,
`release.yml`, `.claude/bump.json` surfaces with small additions.
**Related:** `SUPPORTERS.md` (Patron-tier wording),
`.github/workflows/release.yml`, project CLAUDE.md "Versioning &
release files", global CLAUDE.md § 6 push-cadence rules.

## 1. Problem

Until 2026-05-13, Ants Terminal shipped ad-hoc: every merged feature
or fix landed as its own patch release (4 patch tags landed on
2026-05-13 alone — verified `git tag -l v0.7.*`). Effects:

- Patch numbers churn faster than humans (or distro packagers) can
  consume.
- No coherent batch for release notes.
- The `SUPPORTERS.md` Patron-tier promise ("Early access to release
  candidates" — verified `SUPPORTERS.md:29`) is unrealisable
  without a defined RC window.

**New cadence (user-decided 2026-05-13):**

1. Weekly Wednesday public release.
2. The current `main` tip becomes a frozen RC the Wednesday AFTER
   it ships — Patrons get a 7-day testing window before public.
3. Bug fixes reported by Patrons during that window land on `main`,
   then are cherry-picked into the RC (re-tagged `rcN+1`).
4. On the following Wednesday, the RC (current `rcN`) becomes the
   public release; current `main` tip becomes the new RC.

### 1.1 Timeline visualised

| Wednesday | Public-facing action | Patron-facing action | Dev workflow |
|---|---|---|---|
| W = 2026-05-13 | (none — today's 0.7.91 was last ad-hoc) | (none) | Commits to `main` accumulate. |
| W+1 = 2026-05-20 | (no public release this week — there's no frozen RC yet) | **`v0.7.92-rc1` cut** from current `main`. Patrons start testing. | Commits to `main` continue (these become W+2's RC). |
| W+2 = 2026-05-27 | **`v0.7.92` public** (= `rc1` + any cherry-picked bug fixes). | **`v0.7.93-rc1` cut** from current `main`. | Commits to `main` continue (W+3's RC). |
| W+3 onward | Steady state: every Wed cuts one public + one RC. | | |

The 2026-05-20 → 2026-05-27 cycle is the **bootstrap week** —
public misses one cadence Wednesday so the first RC has its full
7-day window. INV-1 tolerates this.

## 2. Surface

### 2.1 RC version-string convention — `X.Y.Z-rcN`

`0.7.92-rc1`, `0.7.92-rc2`, … (hyphen, lowercase, integer). SemVer §9
pre-release identifier — canonically sorts below `0.7.92` so package
managers + git tag order do the right thing for free.

`CMakeLists.txt` `project(VERSION ...)` carries **plain X.Y.Z only**;
CMake 3.20 doesn't accept pre-release suffixes (verified against
the docs). The `-rcN` lives only at:
- git annotated tag (`v0.7.92-rc1`),
- GitHub Release title + tag,
- AppImage filename (`Ants_Terminal-0.7.92-rc1-x86_64.AppImage`).

`packaging/check-version-drift.sh:33-34` regex
(`[0-9]+\.[0-9]+\.[0-9]+`) extracts from `CMakeLists.txt` and is
unaffected — see INV-3.

### 2.2 RC distribution channel + Patron access — DECIDED option (c)

**Mechanism (user-confirmed 2026-05-13):**

GitHub Release marked `prerelease=true` via `gh release create
--prerelease`. The URL is publicly visible on the Releases page
(dimmed, not promoted on `/releases/latest`). Patrons are notified
each Wednesday via the GitHub Sponsors-tier comms channel (the
opt-in email a 🛠-tier sponsor receives at subscribe-time) with
the rolling pre-release URL.

**Why this beats the alternatives** (per user's earlier
discussion — see [`memory/project-tiered-prerelease-access`]):
- The `SUPPORTERS.md` promise is "early access," not "exclusive
  access." Public-but-unannounced satisfies it.
- Zero new infrastructure; uses GitHub's built-in pre-release flag.
- Patron count today is 0 — gating infra is premature.
- Audit/security-team friendly (distro fuzzers can find RCs).

**Trigger to revisit:** any Patron explicitly requests true
exclusivity → switch to private-mirror or signed-URL channel
(~1-day infra each). Tracked as OQ-1.

### 2.3 Bug-fix mechanism — tag-based cherry-pick (option A)

When a Patron reports a regression against `v0.7.92-rcN` during
the RC window:

1. Fix lands on `main` (normal dev workflow).
2. `/release --rc-respin 0.7.92`:
   - Branches a temporary commit chain off `v0.7.92-rcN`'s commit:
     `git checkout -b _rc-respin v0.7.92-rcN`, `git cherry-pick
     <fix-sha-on-main>` (or `git revert` if undoing).
   - Builds + tests on `_rc-respin`.
   - Tags `v0.7.92-rc(N+1)` (annotated) at the cherry-pick HEAD.
   - Pushes the tag (no branch push — `_rc-respin` is local-only,
     pruned after).
   - `gh release edit v0.7.92-rcN --prerelease` stays prerelease;
     `gh release create v0.7.92-rc(N+1) --prerelease` creates the
     new pre-release.
   - Notifies Patrons (manual email at v1).
3. The original `v0.7.92-rc1` Release stays on the Releases page
   as a historical record; Patrons are pointed at the latest
   `rcN`.

**Why tag-based (no long-lived `rc/` branch):**
- Patron-reported bug rate is expected ~0–3 per RC window. Setting
  up a branch for that is heavy.
- Cherry-pick keeps the audit trail clean (the fix's canonical
  home is `main`).
- No risk of `rc/` branch divergence from `main` over time.

### 2.4 Wednesday cadence script — `/release` flow changes

The Wednesday `/release` invocation cuts two tags in one batch
(after the bootstrap week):

| Step | Today | New behaviour |
|---|---|---|
| 0 — pre-flight | gh auth probe. | Also probe: is today a Wednesday? If no, `--force-ad-hoc` required. Probe: does `v<current>-rcN` exist as a tag? If yes → STEP A is "promote RC" not "fresh public". |
| 3 — bump | One invocation. | If promoting an RC: NO bump (the version is already in CMakeLists.txt from the RC freeze week). Just continue to build/tag. If cutting new RC after promoting: ONE bump for the new RC version. |
| 9 — tag | `v{NEW}` annotated. | Two annotated tags batched in one push: public `v{X.Y.Z}` (the previous RC's SHA, fast-forwarded) AND RC `v{X.Y.Z+1}-rc1` (current main HEAD). Single `git push origin main v{public-tag} v{rc-tag}` per CLAUDE.md § 6 batching rule. |
| 10 — publish | `gh release create` no flag. | Public: as today. RC: pass `--prerelease`. Title prefix `<X.Y.Z> RC1 — Patron preview`. |
| 11 — report | Prints versions + URLs. | Also prints RC freeze-until date (today + 7 days) + recommended Patron notification template. |

### 2.5 AppImage update channel safety — CRITICAL gotcha

`release.yml:172` currently pins zsync `UPDATE_INFORMATION` to the
`latest` tag (verified). If RC AppImages also auto-tag `latest`,
**stable users would auto-update onto an RC** — a regression
escape hatch.

**Mitigation:**
- RC AppImage's `UPDATE_INFORMATION` uses the literal rolling RC
  tag pattern: `gh-releases-zsync|milnet01|ants-terminal|v*-rc|...`
  OR a dedicated `rc-channel` tag the workflow maintains.
- Stable AppImage's `UPDATE_INFORMATION` continues to use `latest`.
- Two distinct update channels side by side.
- The branch is at `release.yml` build step time, gated on whether
  the tag matches `-rc[0-9]+$`.

## 3. Invariants

- **INV-1** — Public releases ship on Wednesdays modulo the
  bootstrap week (W+1 = 2026-05-20 cuts ONLY the first RC, no
  public ship). Soft invariant, not a build-time gate.
- **INV-2** — Every public release on Wed W+2 ships bits
  **identical** to the latest RC tag (`v{X.Y.Z}-rc{N}`) for that
  version, **modulo Patron-reported regression fixes cherry-picked
  into rc(N+1), rc(N+2), …**. Mechanically: `git diff
  v{X.Y.Z}-rc{latest} v{X.Y.Z}` produces zero output.
- **INV-3** — `CMakeLists.txt` `project(VERSION X.Y.Z)` NEVER
  contains a pre-release suffix. The `-rcN` lives only at git tag
  + GitHub Release title + AppImage filename. `check-version-drift.sh`
  regex unaffected.
- **INV-4** — For every RC tag `vX.Y.Z-rcN`, a corresponding
  public tag `vX.Y.Z` lands within **14 calendar days** (one
  cadence cycle of slack). Past 14 days = pipeline broken; the
  next `/release` invocation flags it.
- **INV-5** — Every GH Release from a tag matching
  `^v[0-9]+\.[0-9]+\.[0-9]+-rc[0-9]+$` has `prerelease=true`.
  Every release from `^v[0-9]+\.[0-9]+\.[0-9]+$` has
  `prerelease=false`. Verifiable: `gh api
  repos/milnet01/ants-terminal/releases --jq '.[] | {tag:.tag_name,
  pre:.prerelease}'`.
- **INV-6** — `/release` never cuts an RC AND a public release in
  the same `git push` batch where the RC's underlying X.Y.Z equals
  the public's X.Y.Z. (Wed W+2 cuts public(N) + RC(N+1); never
  public(N) + RC(N).)
- **INV-7** — Trunk is the canonical source. RC bug fixes ALWAYS
  land on `main` first, then are cherry-picked into the RC tag
  chain. No fix lives only in an RC. Verifiable post-hoc: every
  commit in any RC tag's ancestry appears in `main`'s ancestry too.
- **INV-8** — AppImage `UPDATE_INFORMATION` for RC builds points
  at the RC channel (NOT `latest`); stable AppImages keep
  `latest`. Two distinct zsync update streams. Stable users can't
  auto-update onto an RC.
- **INV-9** — `bump.json` schema is NOT extended in v1. The
  `/release` skill computes RC tag strings in-flight by
  post-appending `-rc{N}` to the existing `tag` template.

## 4. Failure modes + recovery

### 4.1 Patron-reported bug mid-RC-window

Path (already in § 2.3): `/release --rc-respin <version>`
cherry-picks fix from `main`, re-tags `rc(N+1)`, re-publishes.
Patrons notified of the new tag.

### 4.2 Patron bug found Wednesday morning of public ship

Path: defer the public release by one week. `v0.7.92-rcN` stays
in flight; affected Patron knows the bug is known + deferred. The
public Wednesday cuts ONLY the next-RC (`v0.7.93-rc1`), not the
delayed public. INV-1's bootstrap-style "no public this Wed"
tolerated by INV-4's 14-day window.

### 4.3 Public-ship build red

Existing `/release` stop-conditions apply. Either fix inline +
re-run, or skip this Wednesday (option 4.2 shape).

### 4.4 Two RCs in flight simultaneously

**Not allowed.** Only one RC at a time. If `v0.7.92-rc1` exists and
the lead wants to cut `v0.7.93-rc1` while `v0.7.92` is not yet
public, `/release` stops and asks: "v0.7.92 not yet public; cut
public first, OR delete v0.7.92-rc1 and replace with v0.7.93-rc1?"
Forces explicit decision.

### 4.5 Cherry-pick conflict

If the bug fix on `main` depends on later commits that don't apply
cleanly to the RC tag, `/release --rc-respin` aborts mid-cherry-pick
and tells the user. Options: hand-resolve, write a fix-specific
commit, or defer the bug to the next RC. v1 does not attempt
automatic conflict resolution.

## 5. CI / disk / RAM budget

### 5.1 CI minutes

Repo is public (verified by the `gh-releases-zsync|milnet01|ants-terminal`
URL in `release.yml:172` + public Sponsors profile) →
unlimited free Linux runner minutes (per global CLAUDE.md § 6 line
33). No quota concern.

Worst-case weekly runs:
- 1 × `release.yml` for public tag (~25 min)
- 1 × `release.yml` for RC tag (~25 min)
- 0–3 × `release.yml` for RC respins (~25 min each)
- = ~50–125 min/week of runner time on top of the existing `ci.yml`
  per-commit lane.

### 5.2 Disk / artefact storage

Public release AppImage: ~200 MB. RC AppImage: ~200 MB. zsync
sidecars: ~1–2 MB each. Annual total (~2 releases/week × 52
weeks × 200 MB) ≈ 21 GB. GitHub Releases storage is free for
public repos — no concern.

RC retention: v1 keeps all RC AppImages indefinitely. OQ-2 covers
optional pruning if storage ever becomes an issue.

### 5.3 Local disk

Each `/release` reuses `build/` (~1 GB Release tree). Wed dual-cut
reuses the same tree for public + new-RC; no multiplier.
`--rc-respin` does a fresh build on the cherry-pick branch tip but
reuses CMake cache → ~5–10 min incremental.
