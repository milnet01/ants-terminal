# ANTS-1463 — `roadmap_log` refusal envelope names `expected_format` on `unrecognised_format`

**Status:** in flight (Bundle E follow-up, 2026-05-17).
**Kind:** enhancement.
**Lanes:** `remotecontrol` (cmdRoadmapLog append path,
cmdRoadmapLogFlip ants-v1-not-recognised path).
**Source:** cross-session-report-2026-05-17 (RetroArch CC
instance, second batch).

## Problem

`roadmap_log` (both `op:"append"` and `op:"flip"`) refuses on
non-bullet roadmaps with `{ok:false, code:"unrecognised_format"}`.
The append path already carries a `hint` field
("this tool expects roadmap-format.md emoji bullets") but the
caller still has to read the source to learn *which* formats
are supported — the hint mentions "emoji bullets" without
listing GFM-task-list. The flip path's refusal envelope (the
"neither GFM nor ants-v1" terminal branch at the end of
`cmdRoadmapLogFlip`) doesn't even have a `hint` field — the
caller gets only `path` + `bytes`.

Same shape as ANTS-1453 (`selection_hint` makes the cost/benefit
choice legible on the descriptor surface) one level down: the
refusal envelope should make the format-shape choice legible to
a caller who's already past the descriptor.

## Fix

Three landing-together changes:

- **Field `expected_format`** added to every
  `unrecognised_format` refusal envelope. Value:
  `["GFM-task-list", "Ants-v1 emoji"]` (array — order = priority,
  GFM first since the read path defaults to it). All four sites
  (listed below) carry the same value, so the caller can branch
  on a single field regardless of which verb refused.

- **Hint wording standardised** across all four sites via a
  shared `kUnrecognisedFormatHint` constant at the top of the
  anonymous namespace:
  ```
  "Roadmap content didn't match GFM-task-list (`- [ ]` /
   `- [x]`) or Ants-v1 emoji-status (`- 📋/🚧/✅/💭 [PROJ-NNNN]`)
   bullet formats. See docs/standards/roadmap-format.md for the
   Ants-v1 spec; reformat the roadmap, write a converter, or
   edit the markdown directly."
  ```
  Emoji codepoints stored as inline UTF-8 byte escapes in the
  source literal (`\xF0\x9F\x93\x8B` etc.) to match the
  existing emoji-handling convention at
  `remotecontrol.cpp:1435-1437` and avoid editor-encoding
  surprises.

- **`cmdRoadmapLogFlip`'s terminal refusal gains the hint
  field** (currently emits only `path` + `bytes` + `code`).
  Shape parity with the other three sites is the invariant.

- **Standards doc touch.** `docs/standards/mcp-error-codes.md`'s
  row for `unrecognised_format` gains a one-line note:
  "envelope additionally carries `expected_format[]` +
  standardised `hint` (ANTS-1463)." Keeps the canonical doc
  in sync without re-litigating the taxonomy.

**Sites (anchor for grep):**
- `cmdRoadmapQuery` section_index mode at `remotecontrol.cpp:~1413-1430`.
- `cmdRoadmapQuery` bullets mode at `remotecontrol.cpp:~1664-1687`.
- `cmdRoadmapLog` append path at `remotecontrol.cpp:~1953-1978`.
- `cmdRoadmapLogFlip` terminal "neither GFM nor ants-v1" branch
  at `remotecontrol.cpp:~2350-2361` (no `hint` field today —
  gains it here).

No schema change — `expected_format` and `hint` are additive
fields; existing callers that ignore them keep working.

## Invariants

- **EF-1.** Every `unrecognised_format` refusal envelope in
  `remotecontrol.cpp` carries `expected_format` as an array of
  exactly two strings: `"GFM-task-list"` and `"Ants-v1 emoji"`,
  in that order.
- **EF-2.** Every `unrecognised_format` refusal envelope sets
  `env["hint"] = kUnrecognisedFormatHint;` (single shared
  constant; no per-site rewording).
- **EF-3.** `cmdRoadmapLogFlip`'s terminal "neither GFM nor
  ants-v1 recognised" refusal emits the same field set as the
  other three sites (`code`, `path`, `bytes`, `hint`,
  `expected_format`).
- **EF-4.** Best-effort consistency on field-emission order
  across the four refusal sites — enforced by the
  `kUnrecognisedFormatHint` constant + reviewer discipline,
  not a runtime invariant. (QJsonObject's wire output is
  alphabetic regardless of insertion order, so byte-equal
  ordering isn't actually wire-visible.)

## Test

Extend `tests/features/mcp_roadmap_unrecognised_format/` with a
fifth `Inv5ExpectedFormatField` source-grep:

- `kUnrecognisedFormatHint` constant appears exactly once in
  `remotecontrol.cpp` (anonymous namespace).
- All four `unrecognised_format` refusal sites set
  `env["expected_format"]` and `env["hint"]` — assert four
  occurrences of each literal in the file.
- The canonical hint string contains all of: `"GFM-task-list"`,
  `"Ants-v1"`, `"- [ ]"`, `"- [x]"`, and the planned-bullet
  emoji byte sequence `\xF0\x9F\x93\x8B` (📋) — wording
  regression guard.

## Out of scope

- Restructuring the refusal taxonomy
  (`docs/standards/mcp-error-codes.md`) beyond the one-line
  envelope-shape note in § Fix above. Renaming the
  `unrecognised_format` code itself would need a separate
  standards update.
- Localising the hint string — English-only matches the rest
  of the MCP surface.
- Emitting `expected_format` on refusals other than
  `unrecognised_format` (e.g. `bad_section`, `bullet_not_found`).
  Those refusals are about caller-input mismatch, not file-shape
  mismatch — the field doesn't apply.
- Adding `expected_format` to `bad_op_combo` errors that name
  ants-v1's anchor-locator restriction. Already self-describing.
