# ANTS-1630 — Caller-cwd-anchor the two focused-gated fold-in verbs

**Status:** accepted, cold-eyes loops 1–4 (loop 4 clean: 0 CRITICAL/HIGH/MEDIUM) (2026-06-18).
**Kind:** enhancement.
**Source:** ROADMAP.md ANTS-1630 (cross-session-report-2026-05-18, MAME Curator `/cold-eyes` sweep, Issue #a).
**Pairs with:** ANTS-1372 (the focused-tab gate being narrowed), ANTS-1401 (`resolveCallerCwdRoot`, the canonical `caller_cwd` decoder this fix reuses).
**Composes with:** ANTS-1581 (ROADMAP — skill→fold_in wiring, more callers hit this path), ANTS-1582 (ROADMAP — `review_*` convergence). _(Both are ROADMAP items, not spec files.)_
**Layman:** When a Claude session runs `/cold-eyes` or `/indie-review` on project A but you're looking at a different tab (project B), the "save findings to the roadmap" step used to refuse with a "wrong folder" error. After this change it saves to project A's roadmap — the project the session is actually working on — regardless of which tab you're looking at.

## 1. Problem

The ANTS-1372 confused-deputy gate (`RcGate::checkCallerCwd`,
`src/remotecontrolgate.cpp`) refuses a mutating MCP write whose `caller_cwd`
does not equal the **focused tab's** project root. That misfires on the
**orchestration** case:

> A single Claude Code conversation runs `/cold-eyes` (or `/indie-review`)
> against *its own* working directory, while the user has a *different* Ants
> tab focused.

MAME Curator 2026-05-18 hit exactly this — `cold_eyes_fold_in` refused with
`{"code":"cwd_mismatch","error":"calling session cwd \".../MAME_Curator\"
does not match focused tab cwd \".../RetroArch\""}`. The session genuinely
owns `MAME_Curator`; the gate trusts the focused tab, not the caller's
project. The fallback is a manual `Edit` of `ROADMAP.md` plus hand-tracking
`.roadmap-counter`, losing the verb's atomic insert + ID-allocation.

### 1.1 The codebase already does the right thing — for two of four sibling verbs

The four ROADMAP-writing MCP verbs split into two patterns today:

| Verb | Handler | Root resolution today |
|---|---|---|
| `roadmap_log` | `cmdRoadmapLogAppend` (`remotecontrol.cpp:4685`) | **caller-anchored**: `QFileInfo(caller_cwd).canonicalFilePath()` → `findRoadmapUnder(cc)` (a *downward* walk to locate `ROADMAP.md`, e.g. `:4738-4739`); refuses `missing_field` / `no_roadmap`. No focused gate. |
| `test_audit_fold_in` | `TestAuditEngine::foldIn` (`testauditengine.cpp:1722`) | **caller-anchored**: `QFileInfo(req.callerCwd).canonicalFilePath()`, requires `isDir`, anchors *at* that dir; refuses `bad_path`. No focused gate. |
| `cold_eyes_fold_in` | `cmdColdEyesFoldIn` (`remotecontrol.cpp:14574`) | **focused-gated**: `RcGate::checkCallerCwd(resolveRootCanonical(m_main), req, …)` then `root = gate.focused`. |
| `indie_review_fold_in` | `cmdIndieReviewFoldIn` (`remotecontrol.cpp:12991`) | **focused-gated**: same `checkCallerCwd(...)` + `root = gate.focused` shape. |

`roadmap_log` and `test_audit_fold_in` already anchor their write to the
caller's own `caller_cwd` and never consult the focused tab — they do **not**
exhibit the orchestration bug. Only `cold_eyes_fold_in` and
`indie_review_fold_in` are focused-gated. The stricter gate on those two is
historical drift, not a design distinction: all four allocate IDs, bump
`.roadmap-counter`, and insert a release block; the two siblings have shipped
the caller-anchored posture without incident.

### 1.2 Why not a stronger identity check

An MCP `tools/call` carries no originating-session identity *in its request
body* — the dispatcher (`claudeintegration.cpp:8488`, `tools/call` branch)
reads only `params.name` and `params.arguments` (which includes `caller_cwd`,
a *claim*). The accept-time `SO_PEERCRED` check (`claudeintegration.cpp:1486-1490`)
reads only `cred.uid` (same-UID); the `struct ucred` carries a `cred.pid`
member but Ants never reads it, and that pid would in any case be the MCP
transport peer, not the originating tab, so it cannot bind a call to a tab.
There is no construct that authenticates "this call came from the tab working
in `caller_cwd`." The same-UID IPC trust boundary (ANTS-1132/1347/1365)
already concedes that a hostile same-UID caller is out of scope — it could
edit `ROADMAP.md` via direct file I/O regardless. So the focused-tab gate was
never a defense against a *hostile* caller; its only teeth were the
`caller == focused` equality (`remotecontrolgate.cpp:38`), which guarded
against *accidental* mis-routing (a write landing on whatever project the
human was looking at). Caller-anchoring removes that accident class outright:
the write lands on the project the caller *named*, never on the focused one.

## 2. Fix

In `cmdColdEyesFoldIn` and `cmdIndieReviewFoldIn`, replace the
`RcGate::checkCallerCwd(resolveRootCanonical(m_main), req, …)` +
`root = gate.focused` preamble with caller-cwd anchoring via the existing
ANTS-1401 decoder (so this introduces no third open-coded `caller_cwd`
canonicalisation — ANTS-1401 INV-1 keeps `resolveCallerCwdRoot` the single
decode site):

1. **Absent `caller_cwd` is already handled upstream — unchanged.** Both verbs
   are `CallerCwdContract::Required` (`claudeintegration.cpp:9358, 9370`), so
   the `tools/call` dispatcher refuses an absent `caller_cwd` with
   `{ok:false, code:"caller_cwd_required"}` (`claudeintegration.cpp:~8559-8585`)
   *before* the handler runs. The handler never sees an empty `caller_cwd`;
   this fix does not touch that path.
2. `rr = ants::resolveCallerCwdRoot(m_main, caller_cwd)` (`remotecontrol.cpp:9242`).
   If `rr.cwd` is empty (`Source::Unresolvable`) **or** `rr.cwd` is not a
   directory (`!QFileInfo(rr.cwd).isDir()`) → refuse `cwd_bad` — the **same
   code the deleted gate emitted** for an unresolvable `caller_cwd`
   (`remotecontrolgate.cpp:28`; `mcp-error-codes.md:100`), so callers see no
   refusal-code change. `Source::ExplicitMatch` and `Source::NoMatch` both
   yield `rr.cwd` = the canonical `caller_cwd`; the fix accepts both (it does
   not require an open tab — a `NoMatch` resolvable dir is a valid target,
   matching how `roadmap_log` accepts any caller dir). `Source::EmptyFallback`
   cannot occur here (step 1 guarantees non-empty `caller_cwd`).
3. `root = rr.cwd`; proceed with the existing narrative-mode / ID-allocation /
   release-block insertion against `root` — `RoadmapFoldIn::allocateIds(root,…)`,
   `findActiveReleaseHeading(root)`, `insertBlock(root,…)` — byte-for-byte
   unchanged from the path that previously ran against `gate.focused`. The
   `.roadmap-counter` canonicalisation (`counterStaysInProject`, ANTS-1372
   §3.2) now bases at the caller's `root` instead of the focused root — same
   invariant, new anchor.

`root` is the **sole** consumer of the resolution *within each handler body*:
verified that neither `cmdColdEyesFoldIn` (`remotecontrol.cpp:14583-14728`)
nor `cmdIndieReviewFoldIn` (`:13000-13107`) reads `gate.focused`/`m_main`
again after the resolution line — no focused-tab dialog refresh, no second
root use *in the handler*. (Whether any signal fan-out *downstream* of
`RoadmapFoldIn::insertBlock` refreshes a focused-tab roadmap dialog is an
implementer check — Open question 4 — but the handler itself introduces no
such cross-tab effect.) The `if (!m_main) … no_window` guard at each handler's
top is retained as a cheap defensive check (`resolveCallerCwdRoot` needs
`m_main` for its tab walk anyway).

No *new* error code is introduced and `docs/standards/mcp-error-codes.md` is
untouched — the fix keeps the gate's own `cwd_bad`. No open-tab requirement,
no handshake token, no `/proc/<pid>/cwd` probe.

`RcGate::checkCallerCwd` and its remaining call sites (`session_memory`
set/delete, `workflow_state` set/clear, `verify_changes`, `plan_template`,
`debt_sweep_apply_fix`, `debt_sweep_defer`) are untouched — those verbs have
real-working-tree side effects where focused-tab match remains the right
guard. Only the two fold-in verbs migrate off it.

## 3. Invariants

- **INV-1 — non-focused fold-in succeeds.** When `caller_cwd` resolves to a
  directory that is **not** the focused tab's, `cmdColdEyesFoldIn` /
  `cmdIndieReviewFoldIn` write to `caller_cwd`'s ROADMAP and return `ok=true`.
  (Pre-fix: refused `cwd_mismatch`.) *Test:* T1.

- **INV-2 — write anchors to caller_cwd, never the focused tab.** Both handlers
  derive `root` from `resolveCallerCwdRoot(m_main, caller_cwd).cwd`; neither
  reads `gate.focused` (nor calls `RcGate::checkCallerCwd`). ID allocation,
  `.roadmap-counter`, and release-block insertion all base at that `root`,
  independent of which tab is focused. *Test:* T1, T2.

- **INV-3 — unresolvable / non-directory caller_cwd refuses, writes nothing.**
  A `caller_cwd` whose canonical form is empty **or** is not a directory →
  `cwd_bad` (the gate's existing code; no contract change). No ID is allocated
  and no file is written. The absent-`caller_cwd` case is the dispatcher's
  `caller_cwd_required` (step 1), not the handler's concern. *Test:* T3.

- **INV-4 — focused-tab caller unchanged.** When `caller_cwd` *is* the focused
  tab (the common single-tab case), `root` equals the canonical path the
  pre-fix `gate.focused` produced. Proof: pre-fix, the gate only returned `ok`
  when `caller == focused` (`remotecontrolgate.cpp:38`), where both were the
  canonicalised focused-tab **shell cwd** (`resolveRootCanonical(m_main)` →
  `QFileInfo(shellCwd).canonicalFilePath()`); post-fix `root` is the
  canonicalised `caller_cwd`, which on this branch is byte-identical. No
  regression for existing single-tab callers. *Test:* T4 (by-construction note;
  no runtime assertion — there is no observable behavioural delta on this
  branch).

- **INV-5 — sibling parity.** Post-fix, all four ROADMAP-writing verbs resolve
  their root from `caller_cwd`; none of the four gates on the focused tab. The
  two migrated verbs anchor *at* `caller_cwd` (like `test_audit_fold_in`),
  reusing `resolveCallerCwdRoot`; `roadmap_log` is further precedent for the
  caller-anchored posture but uses a *downward* `findRoadmapUnder` walk, so it
  is not the byte-level template. *Test:* T2.

- **INV-6 — `RcGate::checkCallerCwd` untouched; call-site count drops 8→6.**
  The gate helper's source is unchanged. The two migrated verbs stop calling
  it, so the literal `RcGate::checkCallerCwd` occurrence count in
  `remotecontrol.cpp` falls from 8 to 6 (S1's `countOccurrences` is a raw
  substring count; no comment carries the literal `RcGate::checkCallerCwd`
  *today*, so the count reflects only the call sites — a future comment
  mentioning the symbol would inflate it). The
  `roadmap_fold_in` S1 assertion (`test_roadmap_fold_in.cpp:474`, currently
  `EXPECT_GE(n, 7)`) is lowered to `EXPECT_GE(n, 6)` in the same change; its
  two count-naming comments (`:467-468` "≥ 7 sites (one per gated verb)" and
  `:474-475` "expected ≥7 gate call sites (one per mutating verb)") are
  updated to the new count and "one per *remaining* gated verb" (the 6 are
  `verify_changes`, `plan_template`, `session_memory` set/delete,
  `workflow_state` set/clear, `debt_sweep_apply_fix`, `debt_sweep_defer`).
  *Test:* T5.

## 4. Tests

Feature-conformance dir `tests/features/fold_in_caller_anchor/` (`spec.md` +
`test_fold_in_caller_anchor.cpp`). Per `tests/features/README.md` the test is
**not** a standalone `add_executable` — its source is added to the `SOURCES`
list of the same bundle that already hosts the existing fold-in narrative
tests (`tests/features/cold_eyes_fold_in_narrative/` /
`indie_review_fold_in_narrative/`). The handlers are GUI-bound (need a live
`MainWindow` + `RemoteControl`), so the contract is pinned by **source-scrape
of per-handler byte windows** — the technique those narrative tests already
use (slurp `SRC_REMOTECONTROL_CPP_PATH`, locate the handler's `cmd…FoldIn(`
body span, assert within it).

- **T1 (INV-1/INV-2)** — within each handler's body span: it derives `root`
  via `resolveCallerCwdRoot(`, and the body does **not** contain
  `gate.focused`.
- **T2 (INV-2/INV-5)** — within each handler's body span: no
  `RcGate::checkCallerCwd(` call remains.
- **T3 (INV-3)** — each handler emits the `cwd_bad` literal, gated on
  `rr.cwd` empty **or** `!isDir()`.
- **T4 (INV-4)** — asserted by construction (see INV-4 proof): no separate
  runtime assertion, pinned as a note in `spec.md`. There is no behavioural
  delta to observe on the focused-tab branch.
- **T5 (INV-6)** — the `roadmap_fold_in` S1 test's threshold reads
  `EXPECT_GE(n, 6)` and still passes against the post-fix tree.

**Pre-fix verification:** T1's "no `gate.focused` in the handler body" and
T2's "no `RcGate::checkCallerCwd`" both fail against the current tree (both
handlers contain those today); T5 fails against the current `EXPECT_GE(n, 7)`
once the two sites are removed. This confirms the tests bite.

## 5. Memory & perf

Zero new allocations, no cache, no member state. `resolveCallerCwdRoot` walks
open tabs once (O(tabCount)) and canonicalises `caller_cwd` — the same work
the pre-fix path did (`resolveRootCanonical(m_main)` focused walk + the gate's
own caller canonicalisation), so no added cost. RAM budget: nil.

## 7. Open questions

1. **(code side, follow-up)** `test_audit_fold_in`'s `foldIn` refuses
   `bad_path` for a non-directory `caller_cwd`, where the migrated verbs use
   `cwd_bad`. Neither is changed by this item; a separate small ROADMAP item
   could align the family on one code.
2. **(docs, follow-up)** The taxonomy carries both `cwd_bad`
   (`mcp-error-codes.md:100`, RcGate lineage) and `bad_cwd` (`:40`,
   path-validation lineage) for "caller_cwd doesn't resolve / isn't a dir."
   This is a pre-existing near-duplication independent of this lane; worth a
   docs cleanup item.
3. **(behaviour, pre-existing)** A `caller_cwd` that is a valid directory with
   **no `ROADMAP.md` at it**: `findActiveReleaseHeading(root)` returns empty →
   `insertBlock` is skipped → `written=false`, but `allocateIds` may still bump
   `.roadmap-counter`. This outcome (`ok=true, written=false`) is unchanged
   from today's focused-tab-with-no-ROADMAP path; the counter-bump-without-write
   is pre-existing and out of this item's scope, flagged here for visibility.
4. **(code side)** Does any signal fan-out downstream of
   `RoadmapFoldIn::insertBlock` refresh the *focused* tab's roadmap dialog? The
   handler bodies don't, but the implementer should confirm no downstream slot
   re-reads the focused tab after a write to a non-focused `caller_cwd`.
