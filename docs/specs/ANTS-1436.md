# ANTS-1436 — `roadmap_query` pagination + auto-truncate for large active payloads

**Status:** shipped 2026-05-16 (commit f9647bc; `src/paginationengine.{h,cpp}`
+ `cmdRoadmapQuery` offset/limit; tests `tests/features/roadmap_query_pagination/`).
**Kind:** perf.
**Lanes:** `remotecontrol` (`cmdRoadmapQuery`), MCP tool descriptor.
**Source:** vestige-cc-feedback-2026-05-16.
**Pairs with:** ANTS-1437 (section_index — primary discovery surface,
removes ~80% of the need for full-active queries), ANTS-1287
(section mode — the targeted-bullet primitive), ANTS-1398 (rollup
filter — same-direction trim, small-payload end).

## Problem

Vestige CC session 2026-05-16: `roadmap_query{status:"active"}` on
Vestige's Phase 10.9 roadmap returned ~100 KB of JSON on a single
line, exceeding the MCP client's 25k-token response cap. The CC
client spilled the response to a tmpfile, forcing Vestige to walk
the file via Python slices instead of consuming the JSON directly.

First-hand reproduction during the ANTS-1437 live test: a
no-arg `roadmap_query{}` on this repo's own ROADMAP.md returned
74,636 chars on one line. Same spillover. Confirmed.

The spillover is a real workflow break:
- The assistant pays the cost twice — once on the spill-file write,
  once on the slicing-back-into-context steps.
- The structured `bullets[]` array is broken into raw text slices
  the consumer has to re-parse.
- Caching layers (ANTS-1357 idempotent-read) can't help — the
  response is too large to cache by design (cap exists for a
  reason).

ANTS-1437 (section_index) addresses **discovery**. ANTS-1287
(section mode) addresses **targeted drill-in**. But the "show me
everything active across the project" use case — common during
planning sweeps, bundle composition, cross-version inventory — still
hits the cap.

## Goal

The full-active payload comes back in size-bounded chunks the
caller can consume directly:

- **Pagination args** (`offset`, `limit`) — caller-controlled paging
  through the bullets array.
- **Auto-truncate fallback** — when no `limit` is supplied AND the
  response would exceed a server-side soft cap (~20 KB JSON
  envelope), emit a truncated response with `truncated:true` and
  `next_offset` so the caller knows there's more without having to
  pre-guess the page size.

Both mechanisms cooperate. The default unfiltered call stays
"works for small roadmaps, degrades gracefully on large ones."

## Design

### Args

```jsonc
{
  // Existing args (status, section, mode, include_section_headers,
  // caller_cwd) unchanged.

  "offset": 0,         // optional, default 0; first bullet index to emit
  "limit": null        // optional; cap on bullets[] length. null → server default
}
```

`offset` clamped to `[0, totalAfterFilter]`. `offset` past end → empty
`bullets[]` with `count:0`, `total:N`, no `next_offset`.

`limit` clamped to `[1, 500]`. Default when unspecified: server picks
based on auto-truncate (see below).

Unknown arg types (e.g. `offset:"foo"`) → bad_args envelope per the
existing hygiene pattern. Negative offset / negative limit → bad_args.

### Auto-truncate path

When caller does NOT supply `limit` and the response would exceed
the soft cap, server picks a smaller `effective_limit` to keep the
response under cap. Algorithm (measure-then-cut, not estimate):

1. After filtering (status + rollup-removal), serialize the
   `bullets` array to Compact JSON: `arr_bytes =
   QJsonDocument(filtered).toJson(Compact).size()`. **Microseconds
   on 100 KB**, far cheaper than the imprecision cost of an estimate.
2. If `arr_bytes <= kSoftCapBytes`, emit all (no truncation).
3. Otherwise, binary-search for the largest `n` such that
   serializing `filtered.mid(0, n)` fits under
   `kSoftCapBytes - kEnvelopeOverheadBytes`
   (the envelope has its own ~512 B of `ok`/`path`/`count`/`filter`/
   `total`/etc.). Emit `filtered.mid(0, n)` with `truncated:true`,
   `next_offset:n`.

Constants:
- `kSoftCapBytes = 20480` (~20 KB; the soft cap before MCP response
  truncation triggers a tmpfile spill)
- `kEnvelopeOverheadBytes = 512` (conservative for the wrapper
  fields; fits all known envelope shapes including the wrap header
  from ANTS-1294)

**Why measure-then-cut over multiplier-estimate.** Cold-eyes review
2026-05-16 H3: actual bullet sizes on this repo's `ROADMAP.md` are
median 106 B / p99 172 B (measured live), not the 150-220 B initial
estimate. A 180 B/bullet multiplier would auto-truncate at ~113
bullets when the real payload could fit ~190. Measure-then-cut
costs ~1 ms on a 75 KB payload and is exact.

`effective_limit` is the auto-picked `n` OR the caller's explicit
`limit`, whichever the caller wants — per INV-9, an explicit `limit`
is honoured (up to the [1, 500] hard clamp); auto-pick only fires
when caller omitted `limit` entirely.

### Envelope additions

```jsonc
{
  "ok": true,
  "bullets": [...],
  "path": "...",
  "count": 113,           // bullets.length (post-truncation)
  "filter": "active",
  // ANTS-1436 — pagination fields. Always emitted when offset/limit
  // were involved (caller passed OR server truncated).
  "offset": 0,            // echo of offset (default 0)
  "limit": 113,           // effective limit (caller's, or auto-picked)
  "total": 491,           // post-filter total before pagination
  "truncated": true,      // bullets.length < total - offset
  "next_offset": 113      // ONLY emitted when truncated; absent otherwise
}
```

`total` always present when pagination applies — caller knows how
many pages to walk. `truncated` is informational; `next_offset` is
the actionable handle.

When pagination doesn't apply (small roadmap, no caller args, full
fit under cap), the envelope omits `offset`/`limit`/`total`/`truncated`/
`next_offset` entirely (back-compat with pre-1436 callers).

### Interaction with existing modes

- **section_index mode (ANTS-1437)** — pagination args ignored
  (section_index envelope is bounded to N sections, typically < 5 KB).
  If caller passes offset/limit with section_index, emit the
  envelope without those fields (silent ignore matches the existing
  status-filter no-op behaviour).
- **section mode (ANTS-1287)** — pagination args ACTIVE. A single
  section can have hundreds of bullets too; caller pages through
  that section's slice. Truncation logic identical.
- **status filter** — runs BEFORE pagination (existing order). `total`
  is the post-status-filter count.
- **include_section_headers** — runs BEFORE pagination (existing
  order). Rollup bullets are removed before counting.

### Dispatch forwarding

`mainwindow.cpp:3860` dispatch lambda forwards new args verbatim
(NOT type-gated) so the handler can emit `bad_args` on non-numeric:

```cpp
// ANTS-1436 — forward unconditionally; handler-side type check.
// Type-gating at dispatch (like get_text's lines) would silently
// drop bad input and the handler couldn't return INV-8's bad_args.
if (args.contains("offset")) req["offset"] = args.value("offset");
if (args.contains("limit"))  req["limit"]  = args.value("limit");
```

Handler-side check in `cmdRoadmapQuery`:

```cpp
const QJsonValue offsetVal = req.value("offset");
if (!offsetVal.isUndefined() && !offsetVal.isDouble()) {
    return /* bad_args envelope per INV-8 */;
}
```

Cold-eyes review 2026-05-16 M6: this is the **only** dispatch
lambda in `mainwindow.cpp` that forwards verbatim — every other
lambda type-gates and silently drops. The deviation is deliberate
(INV-8 needs the handler to see the bad value); add a comment to
that effect at the dispatch site.

## Invariants

- **INV-1 / default unchanged for small roadmaps.** A roadmap whose
  full-active payload fits under the soft cap returns the same
  envelope as pre-1436 (no `offset`/`limit`/`total`/`truncated`/
  `next_offset` fields). Detection: post-filter
  `count * kBulletAverageBytes <= kSoftCapBytes`.
- **INV-2 / explicit pagination args echo back.** When caller passes
  `offset` and/or `limit`, those values appear in the envelope
  (clamped if out of range; echoed pre-clamp via a separate field?
  no — echo post-clamp, the clamped value is what the server actually
  used).
- **INV-3 / auto-truncate fires above soft cap.** When the
  **measured** serialized size of `filtered` exceeds
  `kSoftCapBytes - kEnvelopeOverheadBytes` and caller didn't
  supply `limit`, the server binary-searches for the largest `n`
  such that `filtered.mid(0, n)` fits. Envelope carries
  `truncated:true` and `next_offset:n`. Measure-then-cut (not
  multiplier-estimate) per cold-eyes H3.
- **INV-4 / next_offset advances by limit.**
  `next_offset == offset + bullets.length` whenever `truncated` is
  true. A caller paging with `offset := response.next_offset`
  receives the next chunk; final page has `truncated:false` and
  omits `next_offset`.
- **INV-5 / offset past end returns empty.**
  `offset >= total` returns `{bullets:[], count:0, offset:total,
  total:N, truncated:false}`. No `next_offset` (nothing more to
  fetch).
- **INV-6 / pagination rejected in section_index mode.** When
  `mode:"section_index"`, offset/limit args return
  `{ok:false, code:"bad_mode_combo", error:"section_index mode
  does not accept offset/limit"}` — same shape as the existing
  `mode + section=` refusal. Cold-eyes review 2026-05-16 L3:
  silent-ignore would be a back-compat hazard if section_index
  gains pagination later; reject-loudly preserves the option.
- **INV-7 / status + rollup filters run first.** A bullet that
  status-filters out OR is rollup-filtered out (per ANTS-1398) is
  NOT in `total`. Pagination operates on the post-filter set.
- **INV-8 / bad_args on negative / non-numeric.** `offset:-1`,
  `limit:0`, `offset:"foo"`, `limit:"bar"` all return
  `{ok:false, code:"bad_args"}` with the 64-byte verbatim hygiene
  from `bad_status`. Caller-side gating, not silent clamp.
- **INV-9 / explicit limit ≤ server cap.** If caller passes
  `limit:500` and the server's auto-pick would be 100, the server
  honours the caller's 500 (the auto-pick is a *fallback*
  triggered only when caller omitted `limit` entirely). Above 500
  is clamped by INV-8.
- **INV-10 / mtime invalidation breaks paging contract.** If
  `ROADMAP.md` mtime advances between paged calls, the cache is
  wiped (per `m_roadmapCacheMtimeMs` check at
  `remotecontrol.cpp:1086`) and the next call re-parses against
  the new content. A caller paging with `offset:=prior_next_offset`
  may receive a different bullet set (duplicates or misses).
  Documented limitation — callers needing transactional consistency
  should consume in one call. Cold-eyes review 2026-05-16 L4.
- **INV-11 / one helper call site per emission branch.** The
  pagination logic lives in
  `PaginationEngine::pageBullets(arr, offset, limit, softCap)`
  (`src/paginationengine.{h,cpp}`, joined to `ants_core_lib`).
  Called from exactly two sites in `cmdRoadmapQuery`: the
  section-bullet emission branch and the full-file emission
  branch. Source-scrape regression test asserts call-site count
  (cold-eyes review 2026-05-16 M5).

Pure-function pagination logic factored into a small helper (e.g.
`PaginationEngine::pageBullets(arr, offset, limit)` in
`ants_core_lib`) so unit tests don't need the full `cmdRoadmapQuery`
roundtrip. The helper takes the post-filter JsonArray and returns
the paginated slice + envelope-augment hints. Source-scrape covers
the dispatch + envelope-emission sites; helper covers the math.

## RAM / build cost

In-process: zero new state (pagination is stateless — args in, slice
out). Token-on-the-wire impact: positive (auto-truncate keeps the
response cacheable + parseable; pre-fix a 100 KB response evicted
the idempotent-read cache anyway). Code: ~80 LoC in
`cmdRoadmapQuery`, ~40 LoC dispatch fwd, ~30 LoC helper, ~250 LoC
test = **~400 LoC**.

## Migration

Additive. Callers that ignore the new envelope fields get truncated
responses they previously got spilled-to-file responses for — a
strict improvement (they actually get bullets they can parse).
Callers that read the new fields can page deterministically.

No removed envelope fields, no renamed fields. Schema only adds.

## Pairs / cross-refs

- **ANTS-1437** — section_index mode. Removes ~80% of the need for
  this fix (caller asks for slug list, picks one, drills in). This
  spec covers the remaining 20%: "give me everything active, I'll
  paginate."
- **ANTS-1287** — section mode. Pagination args apply within a
  section too (sections can be large).
- **ANTS-1398** — rollup filter. Runs before pagination so `total`
  is meaningful to the caller.
- **ANTS-1357** — idempotent-read cache. Once paginated, the
  individual page responses ARE cacheable (each fits under cap).
  Pre-1436, the giant unpaginated response was never cached.

## Open questions

- **Should auto-truncate be opt-out via `no_truncate:true`?**
  Resolved: NO for v1. `limit:500` is the documented "I want as
  much as the clamp allows" workaround. A caller that genuinely
  needs the full payload of a >500-bullet roadmap can page
  deterministically via INV-4.
- **`kBulletAverageBytes` adaptive vs constant?** Resolved by
  cold-eyes H3 fold-in: replaced with **measure-then-cut** binary
  search. No constant needed; the actual serialized bytes drive
  the cut point, so dialect (ants-v1 vs GFM) is auto-handled.
- **Cursor-based vs offset-based pagination?** Resolved: offset for
  v1. The mtime-invalidation hazard (INV-10) is documented; the
  typical use is one-shot enumeration where add-during-paging is
  rare. Revisit only if a real bug report surfaces.
