# ANTS-3443 — `feedback_log op:"compact_resolved"`: collapse a shipped v2 finding's write-up to a roadmap-driven stub

**Status:** Implemented (2026-07-05) — cold-eyes clean (6 loops); shipped as
`FeedbackFile::compactResolved` + `enumerateFindingBlocks` (the shared v2
scanner) + `cmdFeedbackLog op:compact_resolved`, tests
`tests/features/feedback_log_compact_resolved/` (15 cases, green)
**Kind:** enhancement
**Source:** user-request-2026-07-04 (compact the `*_Ants_MCP_Feedback.md` files; v2 redesign ANTS-3443 pointer)

## 1. Problem

Under the v2 feedback-file format (docs/standards/mcp-feedback-files.md), a
contributor's finding carries its status **inline** via a `**Proposed ID:**`
line, and the live status is read from `ROADMAP.md` — no tracking tables. But a
finding's full write-up (What / Repro / Impact / Suggested-fix) stays at full
verbosity **forever, even after its `ANTS-NNNN` ships**. That detail now lives
in three places already — the roadmap bullet, the CHANGELOG entry, and git — so
keeping the long write-up in the feedback file is pure bloat (the Vestige
`3D_Engine_…` file is 267 KB). This is the byte-reclaim the user asked for.

`compact_shipped` (ANTS-3421) and `prune_tracking` (ANTS-3442) are the **v1**
compaction ops: both key off the maintainer **tracking table**, which a v2 file
does not have. `compact_resolved` is the v2 equivalent of `compact_shipped` —
same "collapse a shipped write-up, keep a provenance stub, never delete" job,
different gate: it reads the finding's **inline id** and the **live roadmap**
instead of a tracking row. (The near-identical name is deliberate; §2.2 states
the difference so the two ops don't get confused.)

### 1.1 Why per-finding, not per-block

The v1 `compact_shipped` refuses a multi-finding `## ` block (`multi_finding`,
ANTS-3421 §5) — it can only stub a whole `## ` block, so a block mixing shipped
and open findings is un-collapsible. The parent ANTS-3443 roadmap bullet was
written in that v1 framing ("collapse a MULTI-finding `## ` block … to a per-id
stub"). **The v2 redesign dissolves that problem**: because every `### ` finding
carries its own `**Proposed ID:**` line, `compact_resolved` operates at
**`### `-finding granularity** — each finding is gated on its own ids
independently, and a `## ` session block with two shipped findings and one open
finding simply collapses the two and leaves the one. There is no `multi_finding`
refusal under v2. This spec therefore implements the v2 form; §7 notes the
bullet's v1 headline is superseded.

## 2. Surface

`feedback_log op:"compact_resolved"` (maintainer). The split mirrors
`compact_shipped` / `prune_tracking`:

- **Pure helper** `FeedbackFile::compactResolved(content, opts)` (ants_core_lib,
  Qt6::Core-only) does the parse → per-finding gate → rewrite. It takes the
  roadmap truth **pre-resolved** as two id sets (`opts.shippedIds`,
  `opts.roadmapIds`) so it stays MainWindow-free and unit-testable over
  synthetic content — the same testability posture as `pruneTracking`.
- **Wrapper** `cmdFeedbackLog` (remotecontrol.cpp) does path resolution, the
  `*_Ants_MCP_Feedback.md` suffix guard, PathValidation, the `caller_cwd`
  contract, the **version-marker gate** (§2.4), the **roadmap resolution**
  (§2.3), and the atomic `QSaveFile` write — identical plumbing to the two v1
  ops plus the roadmap read.

### 2.1 Request shape

| field | req? | meaning |
|---|---|---|
| `caller_cwd` | yes | resolves the feedback file **and** the project `ROADMAP.md` (same as other ops) |
| `op` | yes | `"compact_resolved"` |
| `path` | no | feedback-file path; omit to derive `<leaf>_Ants_MCP_Feedback.md` (ANTS-3376), echoed as `path_derived` |
| `dry_run` | no | preview the byte report without writing (default false) |

**Auto-discovery — no target list.** Every `### ` finding in the file is a
candidate; there is no per-finding target argument (unlike `compact_shipped`,
which takes an explicit target list). A `scope_ids`-style narrowing is deferred
(§5).

### 2.2 vs. `compact_shipped` (the v1 sibling)

| | `compact_shipped` (v1, ANTS-3421) | `compact_resolved` (v2, this spec) |
|---|---|---|
| unit | whole `## ` block | one `### ` finding |
| shipped-gate source | maintainer tracking row's ✅ status | finding's inline `**Proposed ID:**` + live ROADMAP ✅ |
| targets | explicit list | auto-discovery (all findings) |
| multi-finding block | refused (`multi_finding`) | collapses each shipped finding independently |
| stub keeps | heading only | heading **and** the `**Proposed ID:**` line |
| breadcrumb | `→ shipped ANTS-…, confirmed <sess> <date> (write-up compacted, ANTS-3421)` | `→ shipped ✅ (write-up compacted, ANTS-3443)` |

### 2.3 Roadmap resolution (wrapper prerequisite)

The wrapper loads the project `ROADMAP.md` and calls
`RoadmapDialog::parseBullets(markdown)` — already used from
`remotecontrol.cpp:449` — to build two `QSet<QString>`:

- `roadmapIds` — every **canonical** id present in the roadmap (any status).
  `parseBullets` also emits empty-`id` bullets (narrator/rollup/token-less GFM
  lines); the wrapper filters to non-empty ids matching `RoadmapIndex::isCanonicalId`
  so a blank id never enters the set.
- `shippedIds` — the subset whose bullet status is ✅ (shipped).

Both are passed to the helper via `ResolveOptions`. The helper never reads the
roadmap itself. `roadmap_unavailable` fires only when `ROADMAP.md` is
absent/unreadable (an unknowable "is it ✅?" — collapsing would be unsafe); a
readable-but-empty roadmap (zero bullets) is **not** a refusal — it yields empty
`roadmapIds`/`shippedIds`, so every finding reads `roadmap_unresolved_ids` and
nothing collapses, which is the correct safe outcome.

### 2.4 Version gate (wrapper)

`compact_resolved` is a **v2-only** op. The wrapper reads the file's first-line
marker (§"The un-triaged delta" version-selection contract) and refuses
`not_v2` when it is not `<!-- ants-mcp-feedback: 2 -->` (a `: 1` marker, a
malformed/absent marker). This is deliberate: a v1 file's findings predate the
`**Proposed ID:**` line, so none would be recognised as a finding at all (§2.6)
and the op would be a confusing silent no-op — refusing directs the caller to
`op:migrate_v2` first. An **absent file** refuses `not_found` (parity with the
v1 ops — `compact_shipped`'s `fbNotFound` at `remotecontrol.cpp:10849`).

### 2.5 What a "collapsible" finding is

Only a `### ` block **that carries a `**Proposed ID:**` line** is a *finding* and
therefore a candidate (§2.6). A `### ` block with **no** Proposed-ID line is
non-finding prose (a "Positive note" / "What worked well") per the standard
(§"Maintainer triage" — *"an absent `**Proposed ID:**` line … means the `### `
block is not a finding at all"*); it is **not** enumerated as a finding, **not**
collapsed, and **not** listed in `skipped[]`. A candidate finding is
**collapsed** iff **all** hold; otherwise it is left byte-identical and reported
in `skipped[]` with a `code` (first-failure-wins, in this order):

1. **has a shippable id** — its Proposed-ID value holds ≥ 1 `ANTS-[0-9]+` id
   **and is not an `n/a` closure**. A value that is empty, the
   `_(maintainer to assign)_` placeholder, free text, **or** begins the literal
   `n/a` (case-insensitive, matched `n/a\b` — a closure marker) fails as
   **`no_shippable_id`**. NB
   an `n/a` closure is *triaged* in the standard's delta vocabulary (it has left
   the maintainer work-list) but carries no shippable id, so it is never
   compacted — a distinct notion from "un-triaged." **Closure wins over an
   incidental id:** a value beginning `n/a` is `no_shippable_id` **even if it
   also names an `ANTS-NNNN`** (`n/a — folded into ANTS-1525`), per the standard
   (§"Maintainer triage" — *"a closure regardless of any `ANTS-NNNN` it also
   names … never compacted"*).
2. **not already a stub** — no body line (outside fenced code) begins
   `→ shipped`. Checked *before* the roadmap gates so a re-run is a cheap
   `already_compacted` skip, not a re-resolution — and so a finding **already
   collapsed stays collapsed regardless of later roadmap churn** (idempotency
   under a reopened id). NB the probe is **any** body line (not just the first):
   the v2 stub keeps the `**Proposed ID:**` line *above* the breadcrumb, so the
   breadcrumb is never the first non-blank line (differs from v1's first-line
   sentinel). Fenced regions are skipped so a contributor quoting a `→ shipped`
   line inside a ``` block does not false-trip the sentinel.
3. **all ids resolved** — every id in the Proposed-ID line is in `roadmapIds`.
   An id absent from the roadmap fails as `roadmap_unresolved_ids` (the absent
   ids surfaced in `unresolved_ids`). Checked before the ✅ gate because an
   absent id is a likelier authoring error (wrong project, typo) than an open
   one. **This subsumes archive rotation:** an id long-shipped and then
   archive-rotated *out* of `ROADMAP.md` (roadmap-format.md) is no longer in
   `roadmapIds`, so it reads `roadmap_unresolved_ids` and its write-up stays
   verbose — matching the standard's `unknown` treatment ("never
   silently treated as shipped"). The intended lifecycle is to compact *while*
   the id is still ✅ in `ROADMAP.md`; an archive-aware fallback is deferred
   (§5).
4. **all ids shipped** — every id is in `shippedIds`. Any id present-but-not-✅
   fails as `has_open_id` (the open ids surfaced in `open_ids`).

The ids come from the Proposed-ID line's `ANTS-[0-9]+` tokens; that line is the
authority (a finding may cite other ids in its prose, which are ignored — parity
with the assigned-id set being the Proposed-ID line only, §"The un-triaged
delta" step 3). The line is matched (case-insensitive) by the standard's
canonical id-line regex `^ *(?:[-*] +)?\*{0,2} *proposed id[ *:]+(.*)$`, the
value is capture-group-1 trimmed of whitespace and stray `*`, and a finding uses
its **first** matching line — any later Proposed-ID line is ignored for both the
gate and the retained/relocated line (§2.7). Today's `feedbackfile.cpp parse()`
is v1-only (the watermark rule) and has **no** Proposed-ID matcher; this spec
and the pending v2 delta parser (`feedback_query`) MUST both use this one regex
so the compaction gate and the delta can never disagree on which line is
authoritative (§7 — one shared scanner).

### 2.6 Finding enumeration (`### `-aware scan)

The shipped v1 `scanBoundaries` (`feedbackfile.cpp`) treats only `#`/`## ` as
boundaries and `### ` as inert, so it cannot delimit findings. `compactResolved`
introduces a **fence-aware `### `-block enumerator**: walk the lines skipping
fenced regions (`fenceOpenerChar`, the existing primitive), and for each `### `
heading outside a fence emit a block whose extent runs to the next
`#`/`## `/`### ` boundary (or EOF) — the same extent the v2 delta parser and the
standard's compaction description use. For each block it also extracts the
**first** Proposed-ID line (the §2.5 regex) if present. A block **with** that
line is a *finding* (a compaction candidate); a block **without** it is
non-finding prose — enumerated but classified as a note, so `compactResolved`
skips it silently (never a `skipped[]` entry — it is not a finding). The
fence-aware boundary + first-id-line scanner is factored to be **shared with the
pending `feedback_query` v2 delta parser** (§7 — Rule of Three: one scanner, no
drift on extents or the authoritative id line; whichever consumer lands first
exports it). The *classification* is not fully shared: `feedback_query`
additionally flags a `### ` block with finding-shaped bullets but no Proposed-ID
line as `suspected_untagged` (standard §"The un-triaged delta" step 4), a case
`compact_resolved` deliberately treats as inert prose — so the shared piece is
the scanner, and each consumer layers its own classification.

### 2.7 The rewrite

For each collapsed finding, replace its body — every line after the `### `
heading up to the extent end — with a canonical stub, keeping the heading
**verbatim** and the **first** `**Proposed ID:**` line **verbatim** (relocated
to directly under the heading, regardless of where it sat in the original body;
any later Proposed-ID line is dropped with the rest of the body):

```markdown
### Issue #1 — verify_changes timed out

- **Proposed ID:** ANTS-1525, ANTS-1579
→ shipped ✅ (write-up compacted, ANTS-3443)
```

Stub order is fixed: **heading → blank → the retained `**Proposed ID:**` line →
the breadcrumb → trailing blank**. Retaining the Proposed-ID line is
load-bearing (INV-3): it keeps the block a *finding* (not reclassified as
prose), keeps its ids in the assigned-id set, and keeps a later "Issue #1 STILL
PRESENT" recheck correlatable to the id. The `ANTS-3443` in the breadcrumb is
the **op's provenance tag**, not the finding's shipped id (that is the retained
line above); the breadcrumb carries no `confirmed <session> <date>` because the
v2 gate is roadmap-✅, not contributor-confirmation.

Removals/insertions run **bottom-up** (highest line first) so an earlier
collapse never shifts a later finding's line numbers — parity with
`compactShipped`'s apply loop. `## ` session headings, id-less `### ` notes,
fenced code, the H1 title, and any legacy `## ` tracking block are never
entered.

### 2.8 Response envelope

```
{ ok, op:"compact_resolved", path, dry_run,
  findings_collapsed,                 // count of collapsed findings
  bytes_saved,                        // signed Σ(bytesBefore − bytesAfter)
  collapsed:[ {heading, ids, line} … ],       // line = 1-based heading line; ids = the finding's shipped ids
  skipped:[  {heading, line, code, ids,
              open_ids?, unresolved_ids?} … ],  // line = 1-based heading line (parity w/ collapsed)
  path_derived }                      // true when `path` omitted + derived
```

`line` is **1-based** (parity with `TrackingRow::line` / `CompactOutcome`, both
1-based). In both `collapsed[]` and `skipped[]`, `ids` is the finding's first
Proposed-ID line's `ANTS-[0-9]+` tokens (`[]` for a blank/placeholder value; for
an `n/a` closure the incidental id it names, if any — but the finding is still
`no_shippable_id`). `open_ids` / `unresolved_ids` are the failing subset of that
`ids` list. `code` in `skipped[]` is one of `no_shippable_id`,
`already_compacted`, `roadmap_unresolved_ids` (with `unresolved_ids`),
`has_open_id` (with `open_ids`) — id-less `### ` prose blocks are not findings
and never appear here (§2.5/§2.6). `bytes_saved` is **signed**: a pathological
finding whose entire body is already just its Proposed-ID line grows by the
blank + breadcrumb on collapse, so its per-finding delta is negative — it is
still reported in `collapsed[]` (it now carries the provenance breadcrumb), and
the file-total `bytes_saved` can in principle be negative on such a file, though
in practice the write-ups being collapsed dwarf the breadcrumb.

On a present v2 file with nothing collapsible (every finding `no_shippable_id`,
`has_open_id`, `roadmap_unresolved_ids`, or `already_compacted`): `ok:true,
findings_collapsed:0, bytes_saved:0, collapsed:[]`, `skipped[]` listing each
finding's reason — a clean no-op, not a refusal (parity with the v1 ops' empty
apply, INV-13). Refusals (`not_found`, `not_v2`, `roadmap_unavailable`) are
wrapper-level and precede any per-finding work.

### 2.9 Idempotency

A second `compact_resolved` collapses nothing (`findings_collapsed:0`). Every
stub carries a `→ shipped` body line → gate 2 `already_compacted` short-circuits
*before* the roadmap gates, so a re-run never re-touches a stub even if its id
was reopened; and the retained `**Proposed ID:**` line keeps its ids in the
assigned-id set. Same safety property the user asked about for the v1 ops.

### 2.10 Worked example (before → after)

Roadmap: `ANTS-1525` ✅, `ANTS-1579` ✅, `ANTS-1600` 🚧, `ANTS-9999` absent.

```markdown
## 2026-06-20 — Vestige session

### Issue #1 — verify_changes timed out
- **Proposed ID:** ANTS-1525, ANTS-1579
- **What:** the verb hangs past 5 s on a cold cache.
- **Repro:** first call after relaunch.
- **Impact:** blocks the batch.

### Issue #2 — codebase_index missing counts
- **Proposed ID:** ANTS-1600
- **What:** counts absent on the section rows.

### Issue #3 — typo in error text
- **Proposed ID:** ANTS-9999
- **What:** "occured" → "occurred".

### Issue #4 — duplicate of the timeout
- **Proposed ID:** n/a — folded into ANTS-1525
- **What:** same root cause as #1.

### Positive note — apply_edits is fast
It felt instant on a 2 k-line file. Nice.
```

Collapses **Issue #1** only (both ids ✅). Skips **Issue #2** (`has_open_id`,
`open_ids:[ANTS-1600]`), **Issue #3** (`roadmap_unresolved_ids`,
`unresolved_ids:[ANTS-9999]`), and **Issue #4** (`no_shippable_id` — the value is
an `n/a` closure, so the ✅ `ANTS-1525` it names does **not** make it
collapsible). **Positive note** carries no Proposed-ID line, so it is not a
finding — ignored, never enumerated, absent from `skipped[]`. The `## ` heading
is untouched. Result:

```markdown

- **Proposed ID:** ANTS-1525, ANTS-1579
→ shipped ✅ (write-up compacted, ANTS-3443)

- **What:** counts absent on the section rows.

### Issue #4 — duplicate of the timeout
```

## 3. Invariants

- **INV-1** — `op:"compact_resolved"` is dispatched inside `cmdFeedbackLog`'s
  op switch (beside `compact_shipped` at `remotecontrol.cpp:10847` /
  `prune_tracking` at `:10998`) and added to the valid-op guard
  (`remotecontrol.cpp:10832-10841`, which else emits `bad_mode`). The pure
  helper is m_main-independent (source-grep); the wrapper alone touches the
  roadmap + filesystem.
- **INV-2** — a candidate finding is collapsed **iff** it has a shippable id
  (≥ 1 `ANTS-[0-9]+` in its first Proposed-ID line and that value is **not** an
  `n/a` closure, `n/a\b` case-insensitive), is not already a stub, and **every**
  Proposed-ID id is ✅ in the live roadmap; else it is byte-identical and in
  `skipped[]` with the first-failing code (§2.5 order). An `n/a` closure is
  never collapsed even when it names a ✅ id.
- **INV-3** — the stub keeps the `### ` heading **and** the first
  `**Proposed ID:**` line verbatim (the id line lifted to directly under the
  heading). The finding keeps a shippable id in the assigned-id set and stays
  **out** of the un-triaged delta.
- **INV-4** — per-finding granularity: findings under one `## ` session block
  are gated independently; a mixed block collapses only its all-✅ findings.
  There is no `multi_finding` refusal (the v2 resolution of ANTS-3421 §5).
- **INV-5** — the un-triaged **delta is byte-identical** before and after: only
  collapsible (all-✅) finding bodies are rewritten; un-triaged findings,
  `n/a`-closure findings, id-less `### ` prose blocks, and `## ` headings are
  untouched, and a collapsed finding retains its Proposed-ID line so it never
  enters the delta. Hence
  `parse_v2(after).assignedIds == parse_v2(before).assignedIds`.
- **INV-6** — idempotent: a second run collapses nothing. Every stub trips
  `already_compacted` (a `→ shipped` body line, checked before the roadmap
  gates) and retains its Proposed-ID line, so no gate flips on re-run (§2.9).
- **INV-7** — skip codes are exactly `no_shippable_id`, `already_compacted`,
  `roadmap_unresolved_ids` (surfaces `unresolved_ids`), `has_open_id`
  (surfaces `open_ids`), evaluated first-failure-wins in §2.5 order. An id-less
  `### ` prose block is **not** a finding and is never in `skipped[]`.
- **INV-8** — fenced code, the H1 title, `## ` session/tracking headings, and
  id-less `### ` prose blocks are never modified.
- **INV-9** — `dry_run:true` returns the identical envelope (minus the write)
  and leaves the file byte-for-byte unchanged.
- **INV-10** — atomic write via `QSaveFile` … `.commit()` (source-grep).
- **INV-11** — wrapper refusals precede any collapse: `not_feedback_file`
  (path basename not `*_Ants_MCP_Feedback.md`, the shared suffix guard),
  `not_found` (absent file), `not_v2` (marker ≠ `ants-mcp-feedback: 2`),
  `roadmap_unavailable` (ROADMAP.md unreadable). A present v2 file with nothing
  collapsible is a clean no-op (`findings_collapsed:0`), not a refusal (INV-13).
- **INV-12** — auto-discovery: no target list; every `### ` block **that
  carries a `**Proposed ID:**` line** is a candidate finding. The enumerator is
  fence-aware and `### `-boundary aware (§2.6), distinct from the v1
  `scanBoundaries`; a `### ` block without a Proposed-ID line is non-finding
  prose and is not a candidate.
- **INV-13** — `bytes_saved` is the signed Σ over collapsed findings; a
  present v2 file with zero collapsible findings yields
  `findings_collapsed:0, bytes_saved:0` and per-finding `skipped[]` reasons.

## 4. RAM / build cost

One extra pure function in `ants_core_lib` (parse is already O(lines); the
enumerate-and-gate pass is O(lines) with two `QSet<QString>` membership tests
per finding). The wrapper does one extra `ROADMAP.md` read + `parseBullets`
parse — the same cost `roadmap_query` already pays, and only on this op. No new
allocation class (the file + roadmap are transient), no new build target.

### 4.1 Relation to the v1 compaction ops

`compact_resolved` never touches a v1 tracking table (it only enters `### `
findings; a `## ` tracking block's rows are `| … |` lines, never `### `
findings), and it is gated `not_v2` on a v1 file — so it and the two v1 ops
(`compact_shipped`, `prune_tracking`) are mutually exclusive by file version and
cannot fight over the same bytes. Like every `feedback_log` op the write is
atomic-*replace* (`QSaveFile`) but not *isolated*: a `compact_resolved` racing a
contributor's `append_finding` is last-writer-wins (pre-existing to all
`feedback_log` ops). `dry_run` never writes, so it never races.

## 5. Out of scope

- **`drop_prose`** — also collapsing id-less procedural notes ("Positive note",
  "What worked well"). An id-less note has no `ANTS-NNNN` recovery anchor, so
  collapsing it is a bare deletion of contributor prose (against "never rewrite
  a contributor's description", §"Two roles"). Deferred until a
  provenance-preserving stub for id-less prose is defined; explicitly NOT in
  this op's contract (mirrors the standard).
- **`scope_ids` narrowing** — restricting the auto-discovery to a caller id set
  (parity with `prune_tracking`). Low value while auto-discovery is safe and
  idempotent; a later add if a caller wants surgical collapse.
- **Rewriting or removing a legacy tracking table** — out of this op's scope.
  (Nor is it `migrate_v2`'s: under ANTS-3446's mechanical-only decision,
  `migrate_v2` leaves the v1 tables **in place**; a future de-clutter op could
  archive them, but neither op does today.)
- **Archive-aware collapse** — an id archive-rotated *out* of `ROADMAP.md`
  (roadmap-format.md) reads `roadmap_unresolved_ids` (§2.5 gate 3), so a finding
  never compacted before its id rotated stays verbose. A fallback that also
  scans the archive / CHANGELOG to treat a rotated-shipped id as ✅ is deferred
  — it needs the archive location defined and must still honour the standard's
  "never silently treat an absent id as shipped." The v1 lifecycle is: compact
  while the id is still ✅ in `ROADMAP.md`.

## 6. Tests

Feature-conformance `tests/features/feedback_log_compact_resolved/`:
`spec.md` + `test_feedback_log_compact_resolved.cpp` (pure `compactResolved`
over synthetic v2 content with injected `shippedIds`/`roadmapIds` — no
MainWindow), plus a schema/dispatch source-grep. Cases cover INV-2…INV-13:

- the §2.10 mixed block (one collapse, four distinct skip outcomes) — asserts
  the collapsed stub bytes, the `has_open_id` / `roadmap_unresolved_ids` /
  `no_shippable_id` codes with their `open_ids` / `unresolved_ids` payloads, and
  that the id-less "Positive note" is **absent** from `skipped[]` (not a
  finding).
- **idempotency** (INV-6): feed the collapsed output back → `findings_collapsed:0`,
  byte-identical, the finding reported `already_compacted`; plus a
  reopened-id case (id flipped ✅→🚧 between runs) still reports
  `already_compacted`, never re-touched.
- **delta invariance** (INV-5): a direct assigned-id-set diff before/after shows
  the collapsed finding still carries its shippable id and is out of the delta.
- **Proposed-ID lift** (INV-3): a finding whose `**Proposed ID:**` line sits
  *below* its What/Repro bullets → the stub relocates the **first** such line to
  directly under the heading, verbatim; a second Proposed-ID line is dropped.
- **multi-id partial** (INV-2): `ANTS-1525, ANTS-1579` where only one is ✅ →
  `has_open_id`, not collapsed.
- **n/a closure-wins** (INV-2/7): Proposed-ID `n/a — folded into ANTS-1525` with
  `ANTS-1525` ✅ in the roadmap → `no_shippable_id`, never collapsed (the
  incidental id does not make it collapsible).
- **id-less block** (INV-8/12): a `### ` block with no Proposed-ID line is
  untouched and absent from both `collapsed[]` and `skipped[]`.
- **fence safety** (INV-8): a `### Active` heading pasted inside a ``` fence is
  not enumerated; a `→ shipped` line quoted inside a fence does not trip
  `already_compacted`.
- **archive rotation** (§2.5 gate 3): a finding whose only id is absent from the
  injected `roadmapIds` → `roadmap_unresolved_ids`, not collapsed.
- **wrapper refusals** (INV-11): `not_v2` on a `: 1` file, `not_found` on an
  absent file, `roadmap_unavailable` on an unreadable roadmap (source-grep of
  the wrapper gate order, since the pure helper assumes v2 + injected sets).
- **dry_run** (INV-9): identical envelope, file unchanged.

Until the v2 delta parser (`feedback_query`) ships, the delta-invariance check
uses the assigned-id-set helper directly rather than the full `feedback_query`
path.
