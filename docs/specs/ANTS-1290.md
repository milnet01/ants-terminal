## 1. Problem

The `superpowers:writing-plans` skill is invoked whenever Claude is asked
to scaffold an implementation plan from a spec. Each invocation pulls
**152 lines / ~5.96 KiB** of skill markdown into Claude's context (verified
2026-05-14 via `wc -l` + `wc -c` on
`~/.claude/plugins/cache/claude-plugins-official/superpowers/5.1.0/skills/writing-plans/SKILL.md`).
The markdown is ~95 % boilerplate scaffolding:

| Skill section | Lines | Mechanical? |
|---|---:|:---:|
| Overview / announce hook | 14 | mechanical |
| Scope check (one-subsystem rule) | 4 | judgment |
| File-structure decomposition advice | 8 | judgment |
| Bite-sized granularity rules | 8 | mechanical |
| **Plan document header template** | 15 | **mechanical** |
| **Task structure template** | 38 | **mechanical** |
| No-placeholders anti-pattern list | 14 | mechanical |
| Self-review checklist | 11 | mechanical |
| Execution handoff prompt | 19 | mechanical |

Two sections (judgment) need Claude's thinking; the rest (~125 lines /
~5 KiB) is template text the assistant has to re-emit verbatim. Today
Claude reads the whole skill, then writes the plan inline using the
templates it just read. The skill burns tokens twice: once on the read,
once on the in-conversation echo.

Per-invocation token math (verified 2026-05-14):

| Component | Lines | KiB | K tokens |
|---|---:|---:|---:|
| Skill markdown load | 152 | ~6.0 | ~1.5 |
| In-conversation template echo (header + task structure + handoff prompt) | ~50 | ~2.0 | ~0.5 |
| **Subtotal per plan** | | | **~2.0 K** |

Per-session math (assume ~3 plans drafted in a typical multi-feature
session):

| Component | Per plan | Per session (×3) |
|---|---:|---:|
| Skill markdown (conditional on § 7(a)) | ~1.5 K | ~4.5 K |
| Template-echo overhead (unconditional) | ~0.5 K | ~1.5 K |
| **Floor (unconditional only)** | **~0.5 K** | **~1.5 K** |
| **Ceiling (with skill update)** | **~2.0 K** | **~6.0 K** |

Headline: **~1.5 K tokens saved per session unconditionally, ~6 K with
the optional skill update** (§ 7(a)). Smaller absolute savings than
ANTS-1289 (because plan-drafting is rarer than verify-loops per
session), but the per-call ratio (~2 K skill markdown → ~0.3 K MCP
response → ~85 % reduction) is comparable.

The mechanical loop has no reasoning content — it's "emit this header,
emit this task skeleton, emit this handoff prompt." Claude still
authors the *plan body* (which tasks, which files, which test
assertions); the MCP tool just supplies the surrounding scaffolding
with project-specific conventions pre-baked.

## 2. Surface

### 2.1 Tool signature

```
mcp__ants__plan_template
  required: feature_name: string        // kebab-case; becomes both filename + h1
  optional: goal: string                // one-sentence "what this builds"
  optional: architecture: string        // 2–3 sentences about the approach
  optional: tech_stack: string          // comma-separated stack list
  optional: task_count_hint: integer    // server-clamped [1, 12]; default 4
  optional: includes_tests: bool        // default true
  optional: ants_id: string             // e.g. "ANTS-1290"; if omitted, server allocates the next from .roadmap-counter (see § 2.4)
  optional: save: bool                  // default false — return-only;
                                        // true → also write to disk per § 2.5
```

`feature_name` is the only required arg. Everything else has a sensible
default — the resulting plan still scans cleanly with placeholder text
for the unfilled fields (Claude fills them in post-call when authoring
the body).

### 2.2 Response shape

```json
{
  "ok": true,
  "plan_markdown": "# Live Search Implementation Plan\n\n> **For agentic workers:** ...\n\n**Goal:** [goal text or placeholder]\n\n... (full skeleton, ~3 KiB) ...",
  "plan_path": "docs/plans/ANTS-9999-live-search.md",
  "ants_id": "ANTS-9999",
  "ants_id_source": "provided" | "allocated" | "none",
  "saved": false,
  "task_count": 4,
  "conventions": {
    "commit_format": "ANTS-NNNN: description",
    "test_path_pattern": "tests/features/<feature>/{spec.md,test_<feature>.cpp}",
    "test_bundle_hint": "test_chrome | test_audit | test_claude | test_vt | test_dialogs | test_lua",
    "build_command": "cmake --build build",
    "test_command": "ctest --test-dir build --output-on-failure",
    "save_location": "docs/plans/"
  }
}
```

`plan_markdown` is the full skeleton string — ready for Claude to either
echo back to user or persist to disk via Write. `plan_path` is the
**suggested** save path computed from `ants_id + feature_name`; the
file is NOT written unless `save:true` (per § 2.5). `conventions` is
a compact summary so Claude doesn't need to re-fetch the standards
files for the surrounding workflow.

`ants_id_source` enum:
- `"provided"` — caller supplied an `ants_id` arg, used as-is.
- `"allocated"` — server read+incremented `.roadmap-counter`, returns the
  fresh ID. Side effect: counter file mutated (see INV-3).
- `"none"` — `.roadmap-counter` missing/unreadable AND no caller-provided
  ID. Skeleton uses literal `<ANTS-ID>` placeholder; `plan_path` uses
  `<feature_name>.md` (no ID prefix).

### 2.4 ANTS-ID allocation

If the caller doesn't supply `ants_id`, **call the existing
`RoadmapFoldIn::allocateIds(projectRoot, 1)`** helper at
`src/roadmapfoldin.cpp:51–92`. That function already implements the
correct semantics for this project's counter file:

1. `::flock(fd, LOCK_EX)` against `<project_root>/.roadmap-counter`
   (5 s budget) — protects against cross-process races between two
   MCP server instances *and* between this tool and any other
   ID-allocator (e.g. `RoadmapFoldIn::generateFoldIn`).
2. Read current integer value (`raw.trimmed().toInt`).
3. Write `current + 1` via `QSaveFile::commit()` (Qt's atomic-rename
   under the hood).
4. Release the lock.

Return on success: `ants_id = "ANTS-<N>"`, `ants_id_source = "allocated"`,
where `<N>` is `allocateIds(...).at(0)`.

Cross-process concurrency **IS supported** via the `flock` lift — this
is a free upgrade over the original spec draft. If `allocateIds`
returns an empty list (counter missing / unreadable / lock contention
timeout / write failure), fall through to `ants_id_source = "none"`:
response sets `ants_id = ""`, the skeleton uses literal `<ANTS-ID>`
placeholders. **No error** — caller may still want the skeleton even
on a fresh project without the counter convention.

Reuse rationale (per global rule §3): re-implementing a parallel
counter mutator would duplicate logic that already ships, drift over
time, and miss the flock guarantee. `allocateIds` is already covered
by `tests/features/roadmap_fold_in/test_roadmap_fold_in.cpp` (lines
71, 80, 93, 101 exercise the success path + corruption fallback +
empty-list-on-failure semantics). The plan_template engine becomes a
2-line consumer instead of a 30-line fsync+rename loop.

### 2.5 Optional disk write

When `save:true`:

1. Compute `plan_path = "docs/plans/<ants_id>-<feature_name>.md"`
   (or `"docs/plans/<feature_name>.md"` if `ants_id_source == "none"`).
   **Naming deviates from the writing-plans skill's
   `YYYY-MM-DD-<feature>.md` convention** — reason: a date prefix
   would be a time-of-call dependency that breaks INV-2 (determinism)
   unless surfaced as an explicit `date` arg. The ANTS-ID is already
   monotonic + chronological by construction (`.roadmap-counter`
   advances strictly forward), so it satisfies the skill's
   sort-order intent without breaking byte-identical reproduction.
   Plans for non-Ants projects without an ANTS-ID would still need
   a different scheme, but this tool is Ants-Terminal-specific by
   design.
2. **Refuse to overwrite**: if `<plan_path>` exists, return
   `{ok:false, error:"plan_exists", plan_path, message:"refusing to
   overwrite existing plan; pass save:false to retrieve the skeleton
   only"}`.
3. Path-traversal guard per INV-4: the canonical resolved path MUST
   start with `<project_root>/docs/plans/`. Symlinks pointing outside
   the project are rejected.
4. Atomic-rewrite: write to `<plan_path>.tmp`, fsync, rename.
5. Set `saved: true` in the response.

The default `save:false` is the safe path: Claude gets the skeleton
back as a string, decides what to do (echo to user, edit further, then
Write to disk). The `save:true` path is the convenience case for
end-to-end "scaffold and commit" workflows.

### 2.6 Engine API

```cpp
namespace PlanTemplateEngine {

struct PlanOptions {
    QString featureName;            // required, kebab-case
    QString goal;                   // empty = placeholder
    QString architecture;
    QString techStack;
    int     taskCountHint = 4;      // server-clamped [1, 12]
    bool    includesTests = true;
    QString antsId;                 // empty = allocate from counter
    bool    save = false;
};

enum class AntsIdSource { Provided, Allocated, None };

struct PlanResult {
    bool         ok = false;
    QString      planMarkdown;
    QString      planPath;          // suggested OR actual when saved
    QString      antsId;            // empty when source==None
    AntsIdSource antsIdSource = AntsIdSource::None;
    bool         saved = false;
    int          taskCount = 0;
    QString      errorCode;         // "plan_exists" | "bad_feature_name" | ""
    QString      errorMessage;
};

// String mapper used by the MCP layer (response is keyed by the
// lowercase enum strings, not by integer).
QString antsIdSourceKey(AntsIdSource s);   // "provided" | "allocated" | "none"

// Pure template emission. No file I/O when opts.save == false.
// Validates featureName (^[a-z0-9_-]+$, max 64 chars); rejects with
// errorCode="bad_feature_name" otherwise.
PlanResult buildPlan(const QString &projectRoot, const PlanOptions &opts);

}  // namespace PlanTemplateEngine
```

Layering: `src/plantemplateengine.{h,cpp}` is added to `ants_core_lib`
in `CMakeLists.txt` (verified at lines 217–236 — `verifyengine.cpp`,
`indiereviewengine.cpp`, `debtsweepengine.cpp`, `roadmapfoldin.cpp`
all live in `ants_core_lib`, NOT `ants_chrome_lib`). Qt6::Core only —
no Qt6::Widgets dependency, matches the established
skill-displacement-engine pattern.

## 3. Invariants

- **INV-1** — Feature-name validation. `feature_name` must match
  `^[a-z0-9_-]+$` (lowercase kebab-case, max 64 chars). Reason: it
  appears verbatim in both `plan_path` and the emitted test-file path
  `tests/features/<feature_name>/`, both of which need
  filesystem-safe names. Reject with
  `{ok:false, error:"bad_feature_name", message:"feature_name must be
  ^[a-z0-9_-]+$, max 64 chars"}`. No auto-normalisation (e.g. "Live
  Search" → "live-search") — explicit is better.

- **INV-2** — Skeleton is deterministic from inputs. Given the same
  `PlanOptions`, `buildPlan` produces byte-identical `planMarkdown`
  (no timestamps, no random IDs in the body). The body MAY include
  `ants_id` if allocated, but a re-call with `ants_id` supplied
  produces identical output. Reason: lets tests assert exact skeleton
  shape; lets callers diff successive calls without false changes.

- **INV-3** — `.roadmap-counter` mutation is atomic AND cross-process
  safe. When `ants_id_source == "allocated"`, the counter is updated
  by delegating to the existing `RoadmapFoldIn::allocateIds` helper
  (`src/roadmapfoldin.cpp:51–92`), which combines `::flock(fd,
  LOCK_EX)` (POSIX cross-process advisory lock) with
  `QSaveFile::commit()` (Qt's atomic-rename-with-fsync). A crash
  mid-update leaves either the old value or the new value, never a
  partial / empty file; a concurrent allocator (this tool + a
  separate `roadmap-fold-in` invocation) serialises cleanly. This
  spec deliberately reuses the existing helper rather than duplicating
  the lock-and-write idiom — see § 2.4 reuse rationale.

- **INV-4** — Path-traversal guard on `save:true`. The canonical
  resolved `plan_path` (via `QFileInfo::canonicalFilePath()`) must
  start with `<projectRootCanonical> + "/docs/plans/"` — strictly
  **below** that subdirectory, matching the strict-below form used by
  `IndieReviewEngine::assembleBriefManifest` at
  `indiereviewengine.cpp:208–228`. A symlink at `docs/plans/foo.md`
  pointing to `/tmp/escape.md` is rejected. Reason: prevents a hostile
  config from convincing the MCP to write outside the project.

- **INV-5** — `save:true` never overwrites. Existence check pre-write;
  on hit, return `{ok:false, error:"plan_exists"}`. The skeleton is
  still returned in `plan_markdown` so the caller can compare /
  rename / Write manually. Reason: plans accumulate per-feature; an
  accidental overwrite of an in-progress plan would be destructive.

- **INV-6** — Task-count clamp. `task_count_hint` is server-clamped
  to `[1, 12]`. Below 1 → 1 (a plan needs at least one task); above
  12 → 12 (plans wider than 12 tasks should be split per the
  writing-plans skill's scope-check rule). Out-of-range input does
  NOT error — it's clamped silently and reflected in the response's
  `task_count` field.

- **INV-7** — Schema: response object sets
  `additionalProperties: false` on the top-level envelope AND on the
  nested `conventions` object. New fields require an explicit schema
  update + invariant bump.

- **INV-8** — RAM bound. The skeleton is built in a single
  `QString` buffer; max output size per call ≤ `12 tasks × ~600 B
  per-task block + ~1 KiB header/footer` ≈ **8.5 KiB worst case**.
  No streaming, no temp files. The `.roadmap-counter` read+write
  is ≤ 16 B. Peak engine RAM per call ≤ **16 KiB**.

- **INV-9** — Pure-function on the read path. When `save:false`, the
  engine performs ZERO disk writes — only reads (`.roadmap-counter`
  when `ants_id` is unset). A caller that wants to preview the
  skeleton without side effects passes `save:false` AND `ants_id`
  (so the counter is not incremented either). This is the dry-run
  path; documented for tests.

## 4. Failure modes

- **`feature_name` invalid.** Per INV-1 — `{ok:false,
  error:"bad_feature_name"}`. No partial response.

- **`save:true` and target exists.** Per INV-5 — `{ok:false,
  error:"plan_exists", plan_path, plan_markdown}` (the skeleton is
  still emitted so the caller doesn't lose work).

- **`save:true` and path-traversal violation.** Per INV-4 —
  `{ok:false, error:"bad_path", message:"plan_path escapes
  docs/plans/"}`.

- **`save:true` and `docs/plans/` directory missing.** Server creates
  it (`QDir::mkpath`) before writing. Failure to create →
  `{ok:false, error:"mkdir_failed", message:"<reason>"}`.

- **`.roadmap-counter` malformed.** Treated as "no counter
  available" — `ants_id_source = "none"`, skeleton uses `<ANTS-ID>`
  placeholder. **No error** (the counter file is a convention, not
  a hard requirement for a plan skeleton).

- **`.roadmap-counter` write failure** (e.g. read-only mount).
  `ants_id_source = "none"`, skeleton uses `<ANTS-ID>` placeholder.
  `errorMessage` populated for diagnostics but `ok:true` — same
  reasoning as malformed counter.

- **No project root resolved** (no focused project). `{ok:false,
  error:"no_project", message:"plan_template: no focused project"}`.

## 6. Performance / RAM budget

- **Engine RAM per call**: ≤ 16 KiB (INV-8).
- **MCP response payload**: ≤ ~9 KiB (full skeleton at 12 tasks +
  conventions block + envelope); ~3 KiB typical (4-task default).
- **Caller token cost** (per § 1 table):
  - (a) **conditional** ~1.5 K tokens skill-markdown displacement —
    only when the writing-plans skill is updated to short-circuit on
    Ants projects (§ 7(a)).
  - (b) **unconditional** ~0.5 K-per-call template-echo overhead
    collapsed into one MCP call frame.
  Floor is (b) only (~1.5 K tokens/session at 3 plans); ceiling is
  (a) + (b) (~6 K tokens/session).
- **No new caches, no new file watchers, no new background threads.**
- **`.roadmap-counter` I/O**: at most one read + one
  tmpfile+fsync+rename per call when `ants_id` unset; zero when
  `ants_id` provided. Cost ≤ ~2 ms.

## 7. Workflow integration

The `writing-plans` skill **discipline** stays in place — its rule
("plans assume zero context; bite-sized steps; verify each step")
is preserved regardless of which mechanism produces the scaffolding.
The MCP tool is the *scaffolding generator*; the skill's guidance
about *content* (one action per step, exact commands, complete code
in every step) stays Claude-side because it IS reasoning about the
work being planned.

Two follow-on changes — tracked as separate work items, **NOT gated
on this spec landing.** This spec is sign-off-able with only the
unconditional (b)-class savings in § 6:

(a) **Skill text update** (~1.5 K-token consistent saving per plan
unlocked). The skill markdown at
`~/.claude/plugins/cache/claude-plugins-official/superpowers/5.1.0/skills/writing-plans/SKILL.md`
gets edited so the Plan Document Header section (lines 45–61) and
Task Structure section (lines 63–104) reference
`mcp__ants__plan_template` as the preferred skeleton source on
Ants-equipped projects, deferring the template emission to the
tool. Done in a separate vendor-skill-update commit — file outside
this repo's tree (vendor-cached), so this is a machine-local edit
gated on the user's explicit go-ahead. Spec does NOT require it.

**Caveat:** the cache path is version-scoped (`/5.1.0/`); a future
superpowers plugin upgrade will repopulate the cache and silently
revert the edit. Long-term the right fix is an upstream PR; the
machine-local edit is a short-term token-saver. Re-apply on each
plugin bump until upstream lands.

(b) **Skill activation suppression** (~6 KiB saving × every plan in
every project). A future harness-side change could short-circuit
the skill's auto-load when an MCP `plan_template` tool is
discoverable. Out of scope here — depends on Claude Code's plugin
architecture, not this project's code.

Without (a) and (b), this spec still delivers the unconditional
~0.5 K-token-per-call template-echo saving (§ 6) plus the
structured response format (project conventions surfaced in the
response, not requiring the assistant to re-fetch them from
standards docs).

## 8. Migration

- New tool — no existing API to deprecate.
- The `docs/plans/` directory already exists with three legacy
  entries (`ANTS-1146.md`, `ANTS-1147.md`, `ANTS-1160.md`) — the
  ANTS-1107 rationale flags this directory as **deprecated** in
  favour of `docs/journal/` for shipped plans and `docs/specs/` for
  in-flight design. **Decision for this spec:** new plans still
  land under `docs/plans/` (matches existing convention; the
  deprecation note has not been actioned yet). When ANTS-1107
  migrates the layout, this tool's `save_location` const string
  flips in lockstep — single-line config change, not a behaviour
  change.
- `.roadmap-counter` is a pre-existing convention; this tool reads
  + increments it but does NOT change the file's format
  (single-line integer).
- `task_count_hint` default of 4 matches the median task count
  across existing plans. Empirical reproducer (verified
  2026-05-14):
  ```
  $ grep -cE '^#+ Task ' docs/plans/ANTS-114{6,7}.md docs/plans/ANTS-1160.md
  docs/plans/ANTS-1146.md:4
  docs/plans/ANTS-1147.md:2
  docs/plans/ANTS-1160.md:5
  ```
  Median of {4, 2, 5} = 4. Not arbitrary.

## 9. Out of scope

- **Plan-body authoring.** This tool emits the SCAFFOLDING; the
  per-task code, test assertions, and file lists are Claude's
  authoring work. A future `plan_fill_in` tool that parses the
  skeleton and pre-fills task names from a spec is conceivable but
  not part of v1.
- **Spec generation.** A separate `mcp__ants__spec_template` tool
  could mirror this pattern for `docs/specs/<ID>.md` skeletons;
  proposed as ANTS-1320-family follow-up if this lands well. Out of
  scope here.
- **Multi-spec / multi-feature plans.** The writing-plans skill's
  scope-check rule says plans cover one independent subsystem; this
  tool emits ONE plan per call. Callers wanting multiple plans
  invoke multiple times.
- **Validation of plan completeness post-fill-in.** No
  `validate_plan` follow-up; the self-review checklist in the
  emitted skeleton (§ 2.3) is the lightweight in-skeleton lint.
- **Telemetry of how many tokens this saved** — handled by
  ANTS-1284 (`token_usage` tool).
- **Server-side caching of "last skeleton emitted"** — pairs with
  ANTS-1283 (session memory KV); skeleton is cheap to rebuild, so
  no caching needed v1.
- **Customising the bundle hint per project.** The `conventions
  .test_bundle_hint` string is Ants-Terminal-specific — listed
  for transparency; not adaptive to non-Ants projects (where this
  tool wouldn't make sense anyway since the conventions are
  project-specific).
