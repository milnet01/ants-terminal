# ANTS-1446 — `audit_run` compile_commands.json argument-path validation

Source: deferred from ANTS-1351 § 9 Q4 (audit_run v1 cold-eyes loop 3
2026-05-17 security H-C). ANTS-1448 documents the same-uid trust
model the validator sits inside.

## 1. Goal

`audit_run`'s clazy and clang-tidy invocations consume the project's
`compile_commands.json` via the `-p` flag. Every `-I` / `-isystem` /
`-iquote` / `-include` argument is followed verbatim by the
underlying tool — `-include /home/user/.ssh/id_rsa` directly loads
the named file into every translation unit and the bytes surface
through audit samples.

ANTS-1351 v1 only checks the JSON's *existence* at projectRoot. v2
(this spec) parses the JSON, walks every entry's arguments, and
refuses the audit run with `code:"compile_commands_escape"` if any
include-style path escapes the project root AND isn't under a
hardcoded system-include prefix.

## 2. Threat model

Hostile-clone vector: user clones an untrusted repository, opens it
in a Claude session, runs `audit_run`. A malicious
`compile_commands.json` checked into the clone could:

- `-include /home/user/.ssh/id_rsa` — direct file inclusion;
  contents land in every TU's preprocessing output.
- `-I /home/user/.gnupg` — softer; only matters if source code
  references a header by name that happens to exist there.
- `-isystem /etc/secrets` — same as `-I` for our purposes.

The fence ANTS-1294 ships (the `<ants_mcp_data>` wrap) keeps the
audit envelope from being interpreted as instructions, but it
doesn't prevent the data exfil itself. ANTS-1446 closes that gap
before the bytes reach clazy.

Inside the same-uid trust model (ANTS-1448): an attacker who can
already write `/home/user/.ssh/id_rsa` doesn't need this vector —
they could just `cat` the file. The vector only matters for the
"the user has cloned an untrusted repo and the JSON is the
attack-surface they haven't audited yet" scenario.

## 3. Implementation

### 3.1 Helpers (`src/auditrunner.cpp`)

Four helpers in the anonymous namespace, exposed via thin
`internal::` wrappers (declared in `src/auditrunner.h`) so the test
bundle can drive them:

- `extractIncludeArgsImpl(args)` — walks a clang/gcc arg list,
  emits the path argument for `-I` / `-isystem` / `-iquote` /
  `-include`. Handles both split (`-I /a/inc`) and glued
  (`-I/a/inc`) forms.
- `splitCommandStringImpl(cmd)` — shell-style splitter for the
  `command` field when no `arguments[]` array is present. Honours
  whitespace, double-quotes, single-quotes, and `\<char>` escapes.
- `isIncludePathAllowedImpl(includePath, entryDir, projectRoot,
  reason)` — single-path policy decision. Returns true iff the
  path lives under `projectRoot` OR under a hardcoded system
  prefix. Relative paths resolve against the entry's `directory`
  field; existing paths canonicalise (symlink-resolving).
- `validateCompileCommandsImpl(canonProject, errReason)` —
  end-to-end. Reads `<canonProject>/build/compile_commands.json`
  (fallback: `<canonProject>/compile_commands.json`), parses, and
  walks every entry. Returns true when the file is absent,
  unreadable, or malformed (the downstream tool surfaces its own
  `not_runnable` in those cases).

### 3.2 Allowlisted system prefixes

```
/usr/include       /usr/lib       /usr/lib64
/usr/local/include /usr/local/lib /usr/local/lib64
/usr/share         /opt
/lib               /lib64
```

These are the directories where compilers, distro packages, and
the Qt headers legitimately live. Anything under `/home`, `/root`,
`/tmp`, `/var`, `/etc`, `/proc`, `/sys`, `/run`, `/dev`, …
requires explicit user opt-in (out of v2 scope).

### 3.3 Wiring (`runAudit`)

After tool resolution and before any QProcess spawn, runAudit checks
whether the resolved tool list contains clazy or clang-tidy
(`usesCompileCommands`). When yes, it calls
`validateCompileCommandsImpl` and returns
`{ok:false, code:"compile_commands_escape", error:…}` on failure.
The error string cites the offending include path and the entry's
`file` field for diagnostic context.

### 3.4 Size caps (defence in depth)

- `kCompileCommandsMaxBytes = 32 MiB` — refuses to read JSON bigger
  than this. Beyond that the file is almost certainly malicious.
- `kCompileCommandsMaxEntries = 50000` — refuses to parse arrays
  with more than 50K entries.

Both caps emit `code:"compile_commands_escape"` with the cap
mentioned in the error string.

## 4. Invariants

See `tests/features/audit_run_compile_commands_validation/spec.md`
for the canonical list. Highlights:

- INV-1/2: extractor handles both split and glued forms, ignores
  unrelated flags.
- INV-4/5/6: project root + system prefixes accept; everything
  else rejects.
- INV-7: control chars and backslashes refuse outright.
- INV-9: absent JSON → no error (downstream handles).
- INV-13: `runAudit` calls the validator before spawn.
- INV-14: size caps in place.

## 5. Performance

The validator runs once per audit_run invocation. On a 200 KiB
compile_commands.json (~ours), the walk completes in < 5 ms (most of
which is JSON parsing). Path canonicalisation hits the filesystem
once per unique include path; results aren't cached because
audit_run is per-invocation (no reuse across calls).

## 6. Out of scope

- Auto-detecting include paths in compiler-provided `default-headers`
  paths (`/usr/lib/gcc/.../include`). Those are under `/usr/lib`
  and accepted by the system-prefix allowlist.
- Validating `-D<macro>` definitions (defence-in-depth would be
  excessive — the macro values aren't files clazy follows).
- Validating compiler executable paths in the `command` field.
  Same-uid trust + the existing `resolveToolAbsolute` PATH
  resolution cover this.
- Allowing user-configurable opt-in prefixes
  (`.audit-config.json` allowlist). Future work if real projects
  hit false-positives.

## 7. Trust model

Inside ANTS-1448's same-uid boundary; this is a *defence-in-depth*
check, not the primary trust boundary. The primary boundary is
"don't run `audit_run` against a repo you don't trust"; the
validator just makes the data-exfil path less attractive when an
inattentive user does.
