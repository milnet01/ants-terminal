# ANTS-1402 — merge dispatch observers

## Problem

The MCP `tools/call` dispatch site in
`claudeintegration.cpp:2911–2926` calls
`m_tokenUsage.recordCall(...)` and `recordMcpTrace(...)`
side-by-side on every successful call — both consume the
same `argBytes`, `outBytes`, `wrapBytes`, `durUs` derived
moments earlier in the same block. The two observers are
otherwise independent, but their hook point on the dispatch
site is duplicated:

```cpp
m_tokenUsage.recordCall(toolName, argBytes, outBytes,
                        wrapBytes, durUs);
recordMcpTrace(toolName, argsObj, argBytes, outBytes,
               durUs, cachedHit, QStringLiteral("ok"));
```

Adding a third observer (e.g. a future per-cwd telemetry
tap) would mean a third call here — and easy to drift on
which numbers each observer sees.

## Goal

Collapse the side-by-side observer calls into one
`recordDispatch(...)` entry point that tees the same
arguments to both observers. Adding a third observer later
becomes a single internal change to `recordDispatch`.

## Design

### New member

```cpp
// ANTS-1402 — single dispatch-observation hook. Both
// m_tokenUsage and recordMcpTrace see byte-identical input.
// `result` is "ok" on the success path and the failure code
// (e.g. "tool_not_found") on the failure path. m_tokenUsage
// only counts successful calls (matches pre-1402 behaviour).
void recordDispatch(const QString &toolName,
                    const QJsonObject &argsObj,
                    qint64 argBytes,
                    qint64 outBytes,
                    qint64 wrapBytes,
                    qint64 durUs,
                    bool cachedHit,
                    const QString &result);
```

Body:

```cpp
if (result == QLatin1String("ok")) {
    m_tokenUsage.recordCall(toolName, argBytes, outBytes,
                            wrapBytes, durUs);
}
recordMcpTrace(toolName, argsObj, argBytes, outBytes,
               durUs, cachedHit, result);
```

### Call-site changes

**Success branch** (lines 2911–2926):

```cpp
const qint64 argBytes = ...;
const qint64 outBytes  = ...;
const qint64 wrapBytes = ...;
const qint64 durUs     = mcpTraceTimer.nsecsElapsed() / 1000;
recordDispatch(toolName, argsObj, argBytes, outBytes,
               wrapBytes, durUs, cachedHit,
               QStringLiteral("ok"));
```

**Failure branch** (lines 2932–2939):

```cpp
const qint64 argBytes = ...;
const qint64 durUs    = mcpTraceTimer.nsecsElapsed() / 1000;
recordDispatch(toolName, argsObj, argBytes,
               /*outBytes=*/0,
               /*wrapBytes=*/0,
               durUs,
               /*cachedHit=*/false,
               QStringLiteral("tool_not_found"));
```

## Invariants

- **INV-1.** `recordDispatch` is a private member of
  `ClaudeIntegration` with the signature above.

- **INV-2.** `recordDispatch` tees its arguments to both
  observers. `m_tokenUsage.recordCall` only fires when
  `result == "ok"` — matches the pre-1402 behaviour of the
  failure branch (which previously called only
  `recordMcpTrace`).

- **INV-3.** The success branch at the dispatch site
  emits exactly one `recordDispatch(...)` call instead of
  the previous `recordCall` + `recordMcpTrace` pair.

- **INV-4.** The failure branch emits exactly one
  `recordDispatch(...)` with `result="tool_not_found"`,
  replacing the standalone `recordMcpTrace` call.

- **INV-5.** Byte counts observed by both observers are
  byte-identical (same `argBytes`/`outBytes`/`durUs` are
  passed to recordDispatch and forwarded verbatim).

## Test

`tests/features/mcp_record_dispatch_unification/`:

1. **INV-1 (source-scrape).** `recordDispatch` declared in
   `claudeintegration.h` with the signature shape (private,
   takes argsObj + bytes + durUs + cachedHit + result).

2. **INV-2 (source-scrape).** Function body in
   `claudeintegration.cpp` gates `m_tokenUsage.recordCall`
   on `result == "ok"` and calls `recordMcpTrace`
   unconditionally.

3. **INV-3 (source-scrape).** Dispatch success branch
   emits one `recordDispatch(...)` and zero standalone
   `m_tokenUsage.recordCall(...)` calls within the
   `toolHandled` block.

4. **INV-4 (source-scrape).** Dispatch failure branch
   emits one `recordDispatch(...)` with literal
   `"tool_not_found"` argument.

5. **INV-5 (source-scrape).** Anchor comments
   `ANTS-1402-INV-N` present at the recordDispatch
   definition + the two call sites for grep-stable future
   diffs.

Label `features;fast`. Source-scrape only — token_usage
and mcp_trace already have their own behavioural tests
covering the per-call counters / ring buffer; this ticket
just unifies the hook point.

## Out of scope

- A third observer (per-cwd telemetry, latency histogram).
  This ticket lays the wiring; adding observers is then
  one internal change to `recordDispatch`.
- Restructuring `recordMcpTrace`'s signature. INV-5 above
  preserves its existing args.

## RAM budget

Zero. One non-virtual member function.

## Build cost

~25 LoC added (declaration + ~10-line body); ~15 LoC
removed/replaced at the two call sites; net diff small.
