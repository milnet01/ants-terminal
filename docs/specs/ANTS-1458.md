# ANTS-1458 — Tasks chip + Task List dialog refresh latency

**Status:** shipped — phase 1 (instrumentation) in 0.7.92
(2026-05-20); phase 2 (the latency fix) in 0.7.97 (implemented
2026-06-17; 0.7.97 is the current `project(... VERSION)`, an
unreleased Patron-RC preview cutting at the next release, so the
phase-2 entry sits in CHANGELOG `[Unreleased]` until then).
**Kind:** implement.
**Layman:** when Claude Code logged several tasks at once, the
bottom-bar task count and Task List could lag well past the usual
~2-second refresh; they now keep up.
**Lanes:** `claudestatuswidgets` (refreshTasksButton),
`claudetasklist` (poll + rescan + lastRescanMtimeMs accessor),
`claudebgtasks` (poll + rescan — symmetric fix).
**Source:** user-report-2026-05-17-20-36 (screenshot at
`/home/ants/Pictures/ClaudePaste/paste_20260517_204727_235_*.png`).

## 1. Problem

User-observed 2026-05-17 20:36: multiple `TaskCreate` events
appended to the active Claude Code transcript took longer than the
documented 2-second `refreshTasksButton` cadence to surface in the
bottom-bar chip and the Task List dialog. Chip eventually updated
to the correct `done/total` count (per ANTS-1246), but the lag was
conspicuous. See `ROADMAP.md` ANTS-1458 for the original user
report + full context; the two suspected paths (watch-loss vs
parse-cost) are restated in the roadmap entry and not duplicated
here.

## 2. Surface (phase 1 — instrumentation)

This phase doesn't fix the latency. It ships the diagnostic
plumbing the roadmap entry's step (i) asks for so the next
reproduction by the user yields data instead of guesses:

- **(1)** New `ClaudeTaskListTracker::lastRescanMtimeMs()`
  accessor — read-only view of `m_lastRescanMtimeMs` so the
  status-widget side can compare against the file's current mtime.

- **(2)** `refreshTasksButton` (claudestatuswidgets.cpp) samples
  `(mtime, rescan-mtime, mtime-delta-ms, poll-dur-us, delta)`
  per tick and extends the existing
  `tasks/refresh:` debug log with those five new columns. The
  roadmap entry called the parse-timing column `parse_dur_ms`;
  the implementation lands it as `poll-dur-us` (microseconds) —
  parses are sub-millisecond when cheap so ms granularity
  would round most ticks to 0. The log is already gated on
  `DebugLog::Claude` (set `ANTS_DEBUG=claude` to enable) so
  noise stays opt-in.

- **(3)** Hide-branch label refined: was `HIDE/empty` for both
  `total == 0` and `done >= total`; now `HIDE/empty-or-done` so a
  reader of the log can tell which case fired.

Phase 1 ships no fix; the candidate fixes it lists are now
superseded by §2.5, which a code read (not a reproduction log)
identified as a provable lost-update race.

## 2.5 Surface (phase 2 — the fix)

**Root cause (lost-update race).** `rescan()` recorded its
poll()-shortcircuit signal *after* `parseTranscript()` read the
file to EOF:

1. `parseTranscript()` reads the transcript to its current EOF.
2. `rescan()` then sampled `m_lastRescanMtimeMs =
   fi.lastModified()`.

If Claude appended bytes during that read window — routine in a
`TaskCreate` burst, where it writes every ~100 ms — step 2
captured the *post-append* mtime while step 1's parse missed the
appended bytes. The next `poll()` then saw `mtime ==
m_lastRescanMtimeMs` and short-circuited, stranding the new task
until an *unrelated* later write advanced the mtime again. That is
the conspicuous ">2 s" lag in the user report: the task surfaces
only on the next transcript write, not on the tick following its
own append.

**Fix (two parts, applied symmetrically to `claudetasklist` and
`claudebgtasks`):**

- **(P2-1)** `rescan()` samples the change-signal — both `mtime`
  *and* file `size` — *before* the parse read, and stores that
  pre-read baseline. Any write landing during/after the read
  leaves a strictly newer on-disk signal, so the next `poll()`
  re-parses (at worst one redundant rescan; the parser is a full
  replace, so a redundant pass is harmless).

- **(P2-2)** A new `qint64 m_lastRescanSizeBytes` field is the
  second change-signal. `poll()` re-parses when *either* `mtime`
  or `size` differs from the stored baseline (`mtime ==
  baseline && size == baseline` is the only short-circuit). Size
  catches a same-millisecond / coarse-mtime-granularity append
  that left mtime unchanged — the failure mode phase-1's
  investigation notes flagged as the `mtime_delta_ms == 0`
  candidate.

The two parts are complementary: (P2-1) closes the read-window
race for the mtime signal; (P2-2) closes the residual
same-tick-granularity gap. `setTranscriptPath()` resets both
fields to 0 so a path re-bind always reparses (unchanged
contract, extended to the new field).

Parse cost (the roadmap entry's step (iii), an incremental-parse
fast-path) is NOT addressed here — it remains deferred to phase 3
(see §6); the lost-update race, not parse latency, was the
mechanism behind the reported symptom.

## 3. Invariants

- **INV-1** — `ClaudeTaskListTracker::lastRescanMtimeMs()` returns
  the mtime the tracker stores in `rescan()`. Accessor is `const`
  and side-effect-free. (Phase 2: the value is *sampled* before the
  parse and *stored* at the end of `rescan()`; the accessor and its
  return value are unchanged — only the sample point moved.)
  *Test:* grep `m_lastRescanMtimeMs =` in `src/claudetasklist.cpp` —
  two assignment sites: the `= 0` reset in `setTranscriptPath()` and
  the `= mtimeMs` store inside `rescan()`; accessor body is one line.
- **INV-2** — `refreshTasksButton`'s debug log carries `mtime`,
  `rescan-mtime`, `mtime-delta-ms`, `poll-dur-us`, and `delta`
  columns (added to the existing log columns). Empty-path /
  non-existent-file cases emit `mtime=-1` so the column is
  parseable; `mtime-delta-ms` is also `-1` when the path is
  empty OR the file doesn't exist (`preMtimeMs < 0`) OR no
  prior rescan has captured a mtime yet (`preRescanMs <= 0`,
  i.e. the very first tick after start-up or after
  `setTranscriptPath` reset).
  *Test:* grep `tasks/refresh:` in `src/claudestatuswidgets.cpp` —
  confirm five named columns present; grep
  `path.isEmpty() || !preFi.exists()` for the empty-path /
  non-existent-file guard.
- **INV-3** — Sampling does not call `QFileInfo::lastModified()` on
  an empty path; the `path.isEmpty() || !preFi.exists()` guard
  short-circuits to `-1`. *Test:* grep the guard expression in
  `src/claudestatuswidgets.cpp` `refreshTasksButton` function.

Phase-2 invariants:

- **INV-4** (pre-read sampling) — `rescan()` samples the change
  signal (`fi.lastModified()` and `fi.size()`) *before* calling
  `parseTranscript()`, and stores that pre-read sample into the
  members (`m_lastRescanMtimeMs`, `m_lastRescanSizeBytes`) after the
  parse completes — the members are never re-sampled post-parse.
  This is what closes the read-window race. *Test:* in `src/claudetasklist.cpp`
  and `src/claudebgtasks.cpp`, the `fi.lastModified()` + `fi.size()`
  sampling block appears before the `parseTranscript(` call inside
  `rescan()`, and the `m_lastRescan*` store appears after it.
- **INV-5** (dual-signal short-circuit) — `poll()` re-parses unless
  *both* mtime and size equal the stored baseline; the only
  short-circuit is `mtimeMs == m_lastRescanMtimeMs && sizeBytes ==
  m_lastRescanSizeBytes`. *Test:* grep that conjunction in the
  `poll()` body of both `src/claudetasklist.cpp` and
  `src/claudebgtasks.cpp`.
- **INV-6** (symmetric fix) — both trackers carry the
  `m_lastRescanSizeBytes` field and apply INV-4 + INV-5
  identically; `setTranscriptPath()` resets both `m_lastRescan*`
  fields to 0. *Test:* grep `m_lastRescanSizeBytes` per tracker —
  four hits: the field decl (`.h`), the `= 0` reset in
  `setTranscriptPath()`, the store in `rescan()`, and the `poll()`
  compare (all three non-decl hits in `.cpp`). The pre-read *sample*
  in `rescan()` writes a local `sizeBytes`, not the member, so it is
  not among the member-name hits.

## 4. Tests

Phase 1 shipped no test (the accessor + log columns are glass-box
plumbing). Phase 2 ships a behavioural regression:

- **`claude_task_list` bundle —
  `ClaudeTaskList.Ants1458Phase2PollSizeReparse`.** Writes a
  one-task transcript, binds the tracker, then rewrites it with two
  tasks (a strictly larger file) and pins the file mtime back to the
  tracker's recorded baseline via `QFileDevice::setFileTime` — so
  *size* is the only moved signal. `poll()` must re-parse and surface
  the second task (`totalCount() == 2`). Verified to FAIL against the
  pre-fix mtime-only predicate (the second task is stranded,
  `totalCount()` stays 1) before the fix was restored. The test
  asserts its own precondition (mtime really pinned) so a filesystem
  that refused the pin surfaces rather than passing silently. Its
  internal `expect` assertion labels carry the `ANTS-1458-phase2`
  prefix, so a failing-test log line maps back to this spec.

## 5. RAM / build cost

- **New state per tracker instance:** phase 1 added one `qint64
  m_lastRescanMtimeMs` (8 bytes); phase 2 adds one more `qint64
  m_lastRescanSizeBytes` (8 bytes) to each of `ClaudeTaskListTracker`
  and `ClaudeBgTaskTracker`. Each is a single application-wide
  instance (re-targets to the focused tab via `setTranscriptPath`),
  so the phase-2 addition is 16 bytes total. Zero allocation
  overhead.
- **Build cost:** no new files; phase 2 touches
  `claudetasklist.{h,cpp}` and `claudebgtasks.{h,cpp}` (one field,
  one sample/store restructure, one poll() predicate each) plus one
  new behavioural test in the existing `claude_task_list` bundle. No
  new dependencies. Phase-2 work avoids an incremental parse, so the
  per-rescan cost is unchanged (still one capped transcript walk).

## 6. Out of scope

- Watcher consolidation (`claudetasklist` + `claudebgtasks` share
  a single `QFileSystemWatcher` instance) — ANTS-1285 owns that.
- Incremental-parse fast-path (`ClaudeTaskListTracker::parseTranscript`
  re-walks from the start of the tail window — byte 0 for sessions
  under 16 MiB, or `size − 16 MiB` for larger files — every rescan
  with no byte-offset resume across calls) — **phase 3** if cost
  measurements warrant. Phase 2 deliberately does not pursue this:
  the reported symptom was the lost-update race (§2.5), not parse
  latency, and the parser's stateful full-replace semantics (a
  TodoWrite snapshot clears `out`) make an offset-resume parse a
  meaningfully larger change than the race fix needed.
- A `>`-based predicate (`mtime > baseline || size > baseline`).
  Phase 2 uses `!=` for both signals so an atomic-rewrite that
  *shrinks* or back-dates the transcript (tmpfile+rename, session
  replay) still triggers a re-parse; `>` would miss it.
