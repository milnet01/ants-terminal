# ANTS-1458 — Tasks chip + Task List dialog refresh latency (phase 1: instrumentation)

**Status:** in progress (phase 1, 2026-05-17).
**Kind:** investigate.
**Lanes:** `claudestatuswidgets` (refreshTasksButton),
`claudetasklist` (poll + lastRescanMtimeMs accessor).
**Source:** user-report-2026-05-17-20-36 (screenshot at
`/home/ants/Pictures/ClaudePaste/paste_20260517_204727_235_*.png`).

## Problem

User-observed 2026-05-17 20:36: multiple `TaskCreate` events
appended to the active Claude Code transcript took longer than the
documented 2-second `refreshTasksButton` cadence to surface in the
bottom-bar chip and the Task List dialog. Chip eventually updated
to the correct `done/total` count (per ANTS-1246), but the lag was
conspicuous. See `ROADMAP.md` ANTS-1458 for the original user
report + full context; the two suspected paths (watch-loss vs
parse-cost) are restated in the roadmap entry and not duplicated
here.

## Fix (phase 1 — instrumentation)

This phase doesn't fix the latency. It ships the diagnostic
plumbing the roadmap entry's step (i) asks for so the next
reproduction by the user yields data instead of guesses:

- **(1)** New `ClaudeTaskListTracker::lastRescanMtimeMs()`
  accessor — read-only view of `m_lastRescanMtimeMs` so the
  status-widget side can compare against the file's current mtime.

- **(2)** `refreshTasksButton` (claudestatuswidgets.cpp) samples
  `(file_mtime, last_rescan_mtime, mtime_delta_ms, poll_dur_us,
  total_delta)` per tick and extends the existing
  `tasks/refresh:` debug log with those five columns. The
  roadmap entry called the parse-timing column `parse_dur_ms`;
  the implementation lands it as `poll-dur-us` (microseconds) —
  parses are sub-millisecond when cheap so ms granularity
  would round most ticks to 0. The log is already gated on
  `DebugLog::Claude` (set `ANTS_DEBUG=claude` to enable) so
  noise stays opt-in.

- **(3)** Hide-branch label refined: was `HIDE/empty` for both
  `total == 0` and `done >= total`; now `HIDE/empty-or-done` so a
  reader of the log can tell which case fired.

No fix to the underlying lag; phase 2 lands once the user
reproduces the symptom with `ANTS_DEBUG=claude` and shares the
log. Likely fix candidates (informed by the code read for this
phase):

- If `mtime_delta_ms > 0` but `total_delta == 0` repeatedly during
  the burst window → parse picked up no new events; investigate
  whether `activeSessionPath` returned a different path mid-burst
  or whether the JSONL append happened after the tick fired
  (Claude side asynchronous flush).
- If `mtime_delta_ms == 0` while the user sees Claude adding
  tasks → the file mtime isn't advancing for in-place appends;
  add `QFileInfo::refresh()` to defeat any caching, or switch the
  predicate to `(mtimeMs != m_lastRescanMtimeMs || sizeMs !=
  m_lastRescanSizeMs)`.
- If `poll_dur_us` exceeds ~50 ms consistently → the parse cost is
  the bottleneck; pursue the incremental-parse fast-path suggested
  in the roadmap entry's step (iii).

## Invariants

- **TC-1.** `ClaudeTaskListTracker::lastRescanMtimeMs()` returns
  the value the tracker captures at the end of `rescan()` (the
  `if (fi.exists()) m_lastRescanMtimeMs = …` block at the bottom
  of the function). Accessor is `const` and side-effect-free.
- **TC-2.** `refreshTasksButton`'s debug log carries `mtime`,
  `rescan-mtime`, `mtime-delta-ms`, `poll-dur-us`, and `delta`
  columns. Empty-path / non-existent-file cases emit `mtime=-1`
  so the column is parseable; `mtime-delta-ms` is also `-1`
  when the path doesn't exist OR when no prior rescan has
  captured a mtime yet (`preRescanMs <= 0`, i.e. the very first
  tick after start-up or after `setTranscriptPath` reset).
- **TC-3.** Sampling does not call `QFileInfo::lastModified()` on
  an empty path; the `path.isEmpty() || !preFi.exists()` guard
  short-circuits to `-1`.

## Test

No new test in phase 1. The accessor and the log columns are
both glass-box plumbing for the investigation; a regression test
would just pin the log format. Phase 2 will ship a behavioural
test for the latency itself once the root cause is identified.

## Out of scope

- The actual latency fix (phase 2).
- Behavioural change to `poll()`'s mtime-equality predicate
  (`!= m_lastRescanMtimeMs` may become `mtime > m_lastRescanMtimeMs
  || size > m_lastRescanSizeMs` once we have data).
- Watcher consolidation (`claudetasklist` + `claudebgtasks` share
  a single `QFileSystemWatcher` instance) — ANTS-1285 owns that.
- Incremental-parse fast-path (claudetasklist.cpp:187 parseTranscript
  re-walks from byte 0 every rescan) — phase 3 if cost
  measurements warrant.
