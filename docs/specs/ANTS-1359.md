# ANTS-1359 — `verify_changes` session build-cache

**Status:** spec draft, pre cold-eyes (2026-05-15).
**Source:** ROADMAP.md ANTS-1359 (deferred from the ANTS-1357/1346/1364
bundle on 2026-05-15 for an invalidation-correctness pass).
**Predecessor:** ANTS-1289 (the `verify_changes` MCP tool + `VerifyEngine`
pure functions); ANTS-1357 (the 100 ms idempotent-read cache established
SHA256-hex16 keys + `QHash` + MRU-`QList` pattern).
**Pairs with:** ANTS-1337 (verify-trust gate — explicit interaction with
the cache, see § 2.5 exclusion-list and INV-7).

## 1. Problem

`mcp__ants__verify_changes` shells out to the project's full `build → tests
→ lint` pipeline on every call. On Ants Terminal itself a clean
`cmake --build build && ctest` is ~25 s of wall-clock and dumps ~50 lines
of stdout. A typical refactor turn looks like:

```
Claude: <edit src/foo.cpp>
Claude: verify_changes()      ← 25 s, 50-line log_tail
Claude: <edit src/bar.cpp>
Claude: verify_changes()      ← 25 s, 50-line log_tail
Claude: <edit src/baz.cpp>
Claude: verify_changes()      ← 25 s, 50-line log_tail
```

Each call re-runs cmake from scratch — incremental compilation does help
the build itself, but ctest still re-launches every test process, and
the MCP-layer JSON envelope re-serialises (~8 KB through the
`token_usage` cost table). Worst case is the "Claude verifies its plan
before editing anything," then "Claude verifies after each edit" pattern
— the first call is genuinely a fresh build, the next 2–5 calls inside
the same plan are repeats over **identical inputs**.

**Compute impact, measured 2026-05-15:**

A clean `cmake --build build && ctest --output-on-failure` on Ants Terminal
takes ~25 s wall-clock. Three back-to-back `verify_changes` calls inside a
single turn = ~75 s of redundant compute. The wire-byte envelope per call
is ~2–8 KB depending on `log_tail` length — `tokenusageengine.cpp:20`'s
`8192` is the **counterfactual baseline** (cost of doing the same work
via Bash + Read, fed to the `est_tokens_saved` math), not the actual MCP
response size, so the savings this spec captures live on the **compute
axis** (wall-clock skipped, build CPU avoided) plus the **assistant
context-window axis** (cached responses don't drive parent-context
re-quotes), NOT the wire bytes — see INV-10.

**Why this was deferred:** a stale-cache hit could mask a real build
regression. A cache for a side-effecting verb is fundamentally riskier
than the idempotent-read cache of ANTS-1357. This spec earns the right
to ship through invalidation-correctness invariants (§ 2.5) and a test
matrix that covers each named risk (§ 3).

## 2. Design

### 2.1 Where the cache lives

`RemoteControl` owns the cache. The cache check goes into `cmdVerifyChanges`
(`remotecontrol.cpp:2727`) at this exact sequence position:

1. `RcGate::checkCallerCwd` — cross-project gate (unchanged).
2. `rootInfo.isDir()` check (unchanged).
3. **Parse options** (`gates`, `max_log_lines`, `timeout_sec`,
   `force_refresh`, `cache_only`) — options are part of the cache key.
4. **Reentrancy guard** — set `m_verifyInFlight=true` under RAII
   `QScopeGuard` so every return path resets it. If already set, return
   `{ok:false, error:"verify_in_flight"}` immediately. See INV-11.
5. **Pre-run snapshot** — `collectGitSnapshot(root)` (cheap; ~50 ms).
6. **Trust-aware config load** — `loadGateConfig(root, trustClient)`
   runs first. This MAY show the modal prompt (chrome-layer
   `ModalClient::prompt()`) but the prompt fires at most once per
   `(SHA, session)` pair: `FilePersistedTrustClient::outcomeForConfig`
   (`verifytrust.cpp:58-97`) short-circuits via `m_trustedShas` +
   `m_trustedRepos` + `m_sessionDenied` BEFORE calling `prompt()`.
   So on a fresh first call the user may dismiss a modal; subsequent
   calls within the same session see the decision cached and return
   silently. This is the existing pre-cache behaviour — we run it
   first so the key reflects the actual `verifyUntrusted` outcome.
7. **Compute the cache key** (§ 2.3) using the snapshot from step 5
   AND the trust outcome from step 6 AND the options from step 3.
8. **Check cache** — on a hit AND no `force_refresh`, return the
   stored response with `cache_hit:true`.
9. **`cache_only` branch** — if set and we missed, return the
   `cache_miss:true` envelope without running gates.
10. **Miss path** — `runVerify(opts)` (uses the config from step 6 —
    no second `loadGateConfig` call), then post-run snapshot, then
    the exclusion-list gate (§ 2.5), then maybe-insert.

Rationale for `RemoteControl` (not `ClaudeIntegration`): cache state must
sit next to the verb's single entry-point. Matches `m_roadmapSectionCache`,
`m_coldEyesCache`. No cross-tool sharing.

Rationale for running `loadGateConfig` BEFORE the cache check (step 6
vs the cache check in step 8): the trust outcome is needed for the key.
We could compute it without prompting via a hypothetical
`peekOutcomeForConfig`, but that API doesn't exist and would duplicate
the in-RAM SHA-cache lookup. The existing `outcomeForConfig` is silent
for SHAs the user has already decided — which is the cache-hit case
by definition. The first-contact case (new SHA, modal fires) is also
the cache-miss case by definition (we have no prior entry for an
SHA we've never seen). So the prompt fires zero extra times under
the cache layer compared to today's flow.

**Cache-hit cost.** Step 6's `loadGateConfig` runs on EVERY call —
including cache hits. The cost is one open+read of `.ants/verify.json`
(typically <1 KB), one `QJsonDocument::fromJson` parse, and one
`QHash::contains` lookup for the trust SHA. On a warm pagecache this
is sub-millisecond. The build itself is 10–60 s. The cache wins by
~10000× even paying this overhead on every hit.

**Miss-path `loadGateConfig` is called twice in v1.** `runVerify`
(`verifyengine.cpp:438`) takes `(projectPath, opts)` and re-calls
`loadGateConfig` internally. We keep that signature as-is to avoid a
non-trivial `VerifyEngine` refactor; the second call is silent for
already-decided SHAs (the only case that matters in steady state).
A future cleanup could add a `runVerify(projectPath, cfg, opts)`
overload — out of scope for v1, noted in § 5.

### 2.2 Cache structure

```cpp
// remotecontrol.h
struct VerifyChangesCacheEntry {
    qint64       stampMs = 0;        // QDateTime::currentMSecsSinceEpoch
    QString      key;                 // SHA256-hex16 of canonical inputs
    QJsonObject  response;            // the exact envelope we returned
};
mutable QHash<QString, VerifyChangesCacheEntry>  m_verifyCache;
mutable QList<QString>                            m_verifyCacheLru;
static constexpr int    kVerifyCacheCap   = 8;
static constexpr qint64 kVerifyCacheTtlMs = 300 * 1000;   // 5 min
```

Cap 8 because the access pattern is "1–3 distinct option combinations
per session" (`gates=[]` vs `["build"]` vs `["tests"]` ± `max_log_lines`
tweaks). 8 leaves room for two project roots × four option shapes
without thrashing.

TTL 5 min chosen as: long enough to amortise a 30-s build over a multi-
edit refactor session (single user turn) without re-running; short
enough that out-of-band toolchain changes (e.g., `zypper up` between
turns) self-heal on the next call. The TTL is a **secondary** safety net
— the **primary** correctness comes from the cache-key invariants (§ 2.5).

### 2.3 Cache key

```
keyMaterial = projectRoot       + '\0'
            + gitHeadSha        + '\0'
            + gitStatusSha      + '\0'
            + trustOutcomeSha   + '\0'
            + autoTrustEnv      + '\0'
            + optionsCompactJson
key         = QCryptographicHash::hash(keyMaterial.toUtf8(), Sha256)
                  .toHex().left(16)
```

- `projectRoot` — canonical path from `resolveRootCanonical(main, req)`
  (`remotecontrol.cpp:1349`) which terminates in `QFileInfo::
  canonicalFilePath`, so a symlinked invocation and a direct invocation
  hash identically.
- `gitHeadSha` — output of `git -C <root> rev-parse HEAD` (exit 0 only),
  trimmed to 40 hex chars. HEAD inherently captures the tree-sha via
  commit→tree pointer, so `commit --amend` over an identical tree
  produces a NEW HEAD and busts the cache (conservative false-miss,
  never a false-hit — explicitly accepted, see § 2.6 limitation 4).
- `gitStatusSha` — SHA256-hex16 of `git -C <root> status --porcelain=v1 -z`
  output (NUL-terminated entries, locale-independent, includes untracked
  AND modified-tracked files). Hashing keeps the key bounded — raw
  output can be hundreds of KB on a freshly-cloned repo.
- `trustOutcomeSha` — SHA256-hex16 of
  `cfgSource + ':' + int(verifyUntrusted)` where `cfgSource` is the
  string `loadGateConfig` set (`".ants/verify.json"`, `"auto-detected"`,
  `"auto (untrusted-bespoke)"`, `"none"`, or `"bad_config"`) and
  `verifyUntrusted` is the bool the same call surfaced. Because
  `loadGateConfig` runs at step 6 of § 2.1 BEFORE the cache key is
  computed, this is "the trust outcome that just happened" — not a
  separate trust query. Crucially: when the user grants trust between
  two calls, the next call's `loadGateConfig` returns `Trusted`
  silently (the SHA is now in `m_trustedShas` — no prompt fires), the
  `cfgSource` flips from `"auto (untrusted-bespoke)"` to
  `".ants/verify.json"`, the key changes, and the cache misses —
  that's INV-7. When the client is null (autotrust env path),
  `loadGateConfig` returns the bespoke config unconditionally with
  `verifyUntrusted=false` and `cfgSource=".ants/verify.json"` — also
  deterministic.
- `autoTrustEnv` — `qgetenv("ANTS_VERIFY_TRUST_AUTOTRUST")`. Bypasses
  the trust client (`remotecontrol.cpp:2766`); toggling the env var
  between calls changes which config is used. Including it in the key
  prevents a hit on a key computed under one autotrust state from
  serving a request under the other.
- `optionsCompactJson` — `QJsonDocument(canonOpts, Compact).toJson()`
  where `canonOpts` is the subset of `req` that affects the result:
  `gates` (sorted), `max_log_lines`, `timeout_sec`. **`caller_cwd` is
  excluded** because `resolveRootCanonical` canonicalises it into
  `projectRoot`. **`force_refresh` and `cache_only` are excluded** —
  they're control flags, not result inputs.

### 2.3.1 Why git-snapshot is the right invalidation signal

The cache is correct iff "key match" ⟹ "inputs to the build are
identical." The build's inputs are:

| Input class | Detected by |
|---|---|
| Tracked source files (modified) | `git status` shows ` M path` |
| Tracked source files (deleted) | `git status` shows ` D path` |
| Untracked **non-ignored** new source files | `git status` shows `?? path` (default behaviour respects `.gitignore`) |
| Staged-but-not-committed | `git status` shows `M ` / `A ` / `D ` |
| Commits (rebase, reset, cherry-pick) | `git rev-parse HEAD` changes |
| `.ants/verify.json` edits — when tracked or untracked-non-ignored | one of the above rows |
| Trust state (user grants/revokes) | `trustOutcomeSha` (§ 2.3) |
| `ANTS_VERIFY_TRUST_AUTOTRUST` toggled | `autoTrustEnv` (§ 2.3) |
| `.gitignore`d files (CMake cache, `.ants/verify.json` if ignored, editor swap files) | **Not detected** — see § 2.6 limitation 1 |
| Compiler / toolchain version | **Not detected** — see § 2.6 limitation 3 |
| Environment vars (PATH, CC, …) | **Not detected** — bounded by TTL |

The first eight rows are the **dominant 99 %** of the "did anything that
matters change?" question for an incremental code edit session. The
remaining three are bounded by the 5-min TTL and the explicit
`force_refresh` arg (§ 2.4).

### 2.3.2 Race against mid-run edits

The build itself takes seconds-to-minutes. A second subagent (or a
second tab) can write to disk during that window. If we computed the
key only pre-run, a contaminated result could pollute the cache.

Mitigation: take a `git status` + `git rev-parse HEAD` snapshot
**immediately before** invoking `runVerify` and **immediately after**
it returns (before any other work — in particular, before the cache
insert itself). The pre and post snapshots must match for the entry
to be cached:

```
preSnapshot  = collectGitSnapshot(root)           // (head, statusSha)
preKey       = computeKey(root, preSnapshot, ...)
result       = VerifyEngine::runVerify(...)
postSnapshot = collectGitSnapshot(root)           // sampled immediately
if (preSnapshot != postSnapshot) {
    // Mid-run edit contaminated the result — return the response to
    // the caller (it is correct for THIS call's inputs) but DO NOT
    // insert into the cache. INV-3.
    return response_uncached;
}
insertCache(preKey, response);
```

**Bounded race window — explicit acknowledgement.** A sub-millisecond
write that completes during the `git status` system call is
theoretically not detected by either snapshot (the same race that
makes `git status` itself a non-atomic operation). The next
`verify_changes` call sees the edit in its OWN pre-snapshot and either
hits a stale entry (if the bad-snapshot key happens to equal another
entry's key — astronomically unlikely with SHA256) or misses (the
usual case). The bound on user-visible exposure is "until the next
edit", which is the strongest guarantee a non-atomic file-system
snapshot can provide. INV-3 names this as the contract.

### 2.4 Public arg additions

Two new optional args on `verify_changes`:

| Arg | Type | Default | Effect |
|---|---|---:|---|
| `force_refresh` | bool | `false` | Skip the cache check; run gates; insert on success per § 2.5. Useful when the user knows an out-of-git input changed (e.g., post-`zypper dup`). |
| `cache_only` | bool | `false` | Return the cached response if present; else return `{ok:true, cache_miss:true, ...}` with no `gates` field. Lets a caller cheaply probe "is there a fresh verify?" without paying compute. |

Both are documented in the response shape: the response gains one new
field `cache_hit: bool` (false on a fresh run, true on a hit). `ok` /
`all_passed` / `gates` / `project_root` / `config_source` /
`verify_untrusted` remain byte-identical on a hit per INV-1.

**Naming note.** `verify_changes` deliberately uses `force_refresh`
rather than `reset` (the name `token_usage` adopted at
`remotecontrol.cpp:2918`). The semantics differ: `reset` clears
counter state; `force_refresh` bypasses the lookup AND triggers a
re-run. Different verbs, different control flags — names diverged
deliberately.

**Combination rule.** `force_refresh:true` AND `cache_only:true`
together return `{ok:false, error:"incompatible_args", message:"…"}`.
Rationale: the two intents (force a fresh run vs. probe without
running) are contradictory; surfacing the conflict beats silently
picking one. Codified as part of INV-9.

### 2.5 Exclusion list — what is NEVER cached

Seven classes of result bypass cache insert:

1. **`config_source == "bad_config"`** — malformed `.ants/verify.json`.
   User is one fix away; caching the error means they'd hit it on the
   next call even after the fix lands within the TTL.
2. **`config_source == "none"`** — no gates configured AND auto-detect
   found nothing. There's no run to cache. Caching ok=true,allPassed=true
   here would risk hiding a config that was just added.
3. **`verify_untrusted == true`** — ANTS-1337 fallback path. The trust
   outcome is part of the key (§ 2.3) — so a future trust grant flips
   the outcome and busts the key — but caching an untrusted-fallback
   result is still excluded as belt-and-braces: the next call after
   trust is granted MUST re-run gates fresh, never serve a stale
   "I fell back to auto-detect" envelope.
4. **Pre/post snapshot mismatch** (§ 2.3.2) — the build ran over a
   contaminated input set.
5. **Non-git project root** — `git rev-parse HEAD` exits non-zero
   (no `.git`). Without a `gitHeadSha`/`gitStatusSha` we cannot construct
   a sound key. Bypass cache entirely; `cache_hit:false` always.
6. **Any gate that did not complete naturally.** Specifically:
   - `ran:false, skippedReason == "command not resolvable"` (PATH glitch
     or missing binary mid-install — transient).
   - `ran:true` AND `skippedReason` starts with `"timeout after "`
     (timeout-killed at `verifyengine.cpp:308-315` — also transient,
     could be system-load spike or a hung child).
   Caching either masks recoverable transient failures past the TTL.
7. **`cmdVerifyChanges` did not return via its normal exit path.** Cache
   insert happens only on the synchronous return at the bottom of the
   function — never from a destructor, signal handler, or partial-error
   bailout. This is a structural invariant of the implementation, not a
   runtime check, so the test surface covers it indirectly through
   "no gate killed mid-build cached" (INV-3 + class 6 above).

Test-failures **are** cached. A red build over input set X is the same
red build over the same input set X, so a hit returns the correct
answer; an edit changes the key and busts the cache.

### 2.6 Limitations (documented, not bugs)

1. **`.gitignore`d files are invisible.** `git status --porcelain=v1`
   honours `.gitignore` by default — so editor swap files, build
   artefacts under `build/`, `compile_commands.json`, `.ants/verify.json`
   IF the user adds it to `.gitignore`, and toolchain-local config
   (`CMakeLists.txt.user`, `.cargo/config.toml` under cwd) do not bust
   the cache. We deliberately do NOT pass `--ignored=no/all` — including
   ignored files would re-introduce `build/` mtime churn as a key input
   and defeat the cache entirely. The 5-min TTL + `force_refresh` are
   the escape hatches; an updated `.ants/verify.json` should be tracked
   in git (the common case) so its edits bubble through.
2. **Submodule state changes** — `git status --porcelain` shows a
   submodule as `M` only when the submodule HEAD differs; an
   in-submodule working-tree edit may not bubble up depending on
   `diff.ignoreSubmodules`. The 5-min TTL + the `force_refresh` arg
   are the escape hatches.
3. **Toolchain version drift** — `gcc -v` / `cmake --version` output is
   not in the key. A system update (`zypper dup`, `apt upgrade`,
   `nix-shell` change) between two `verify_changes` calls in the same
   5-min window could falsely hit. **Mitigation:** the documented
   workflow is `force_refresh:true` after any system update; the TTL is
   the safety net. A future enhancement could stat `which gcc` /
   `which cmake` and include those mtimes in the key (cheap, catches
   the named threat) — out of scope for v1, see § 5.
4. **Git operations that change HEAD but not files** — `git commit
   --amend` over the same tree changes `HEAD`, busts the cache, and
   the next call re-runs. Conservative false-miss; no false-hit risk.

### 2.7 Control flow

```
cmdVerifyChanges(req):
  gate = RcGate::checkCallerCwd(...)
  if (!gate.ok) return gateError
  root = gate.focused
  if (!isDir(root)) return cwd_unreachable

  options = parseOptions(req)     // gates, max_log_lines, timeout_sec
  force   = req.value("force_refresh").toBool(false)
  probe   = req.value("cache_only").toBool(false)
  if (force && probe) return incompatible_args      // INV-9

  // INV-11 — reentrancy gate with RAII reset. Belt against Qt
  // event-loop re-entry through QProcess::waitForFinished pumping
  // the event loop during runVerify. QScopeGuard resets the flag
  // on EVERY return path, including mid-function early returns
  // like bad_config below.
  if (m_verifyInFlight) return { ok:false, error:"verify_in_flight" }
  m_verifyInFlight = true
  auto inFlightGuard = qScopeGuard([&]{ m_verifyInFlight = false; });

  preSnapshot = collectGitSnapshot(root)  // (head, status-sha) or empty
  cacheable   = !preSnapshot.empty && !force

  // Trust-aware config load FIRST. May invoke prompt() once for an
  // unknown SHA; silent on subsequent calls for the same SHA in the
  // same session (verifytrust.cpp:58-97 short-circuits via
  // m_trustedShas + m_trustedRepos + m_sessionDenied). The trust
  // outcome is needed to compute the cache key, so this must run
  // BEFORE the cache check.
  cfg, cfgSource, verifyUntrusted =
      loadGateConfig(root, opts.trustClient)
  if (cfgSource == "bad_config") {
      // Early return — inFlightGuard fires, exclusion class 1
      // means we would never cache this anyway.
      return vcErr("bad_config", "...")
  }

  autoTrust   = qgetenv("ANTS_VERIFY_TRUST_AUTOTRUST")
  trustSha    = cacheable ? computeTrustOutcomeSha(cfgSource,
                                                  verifyUntrusted) : ""
  key         = cacheable
              ? computeKey(root, preSnapshot, trustSha, autoTrust, options)
              : ""

  if (cacheable && !force) {
      if (hit = lookup(key); hit && (now - hit.stampMs) <= TTL) {
          response = hit.response
          response["cache_hit"] = true
          moveToFront(key)
          return response   // inFlightGuard resets the flag
      }
  }
  if (probe) {
      return { ok:true, cache_hit:false, cache_miss:true, project_root:root }
  }

  // Miss path. runVerify's existing signature (verifyengine.cpp:438)
  // takes (projectPath, opts) and re-calls loadGateConfig internally.
  // We keep that signature as-is — the second loadGateConfig call is
  // silent for SHAs the user has already decided in this session
  // (m_trustedShas / m_sessionDenied short-circuit the prompt). The
  // wall-clock cost of the duplicate is sub-millisecond
  // (file IO + JSON parse + hash lookup), invisible next to the
  // build itself.
  report = runVerify(root, opts)
  response = envelopeFromReport(report, report.configSource,
                                report.verifyUntrusted)

  postSnapshot = cacheable ? collectGitSnapshot(root) : {}
  response["cache_hit"] = false

  // Exclusion check (§ 2.5 classes 1–6; class 5 already excluded
  // via cacheable=false; class 1 already handled at the early
  // bad_config return; class 7 enforced by inFlightGuard structure).
  shouldInsert =
       cacheable
    && postSnapshot == preSnapshot           // class 4
    && cfgSource != "none"                   // class 2
    && !verifyUntrusted                      // class 3
    && !anyGateNotNaturallyCompleted         // class 6
  if (shouldInsert) {
      insertCache(key, { stampMs:now, key:key, response:response })
      // LRU eviction at cap (8 entries).
  }
  return response   // inFlightGuard resets the flag
```

`collectGitSnapshot` returns `{}` (empty) when the project is not a git
repo OR `git` is not on PATH (rare; bounded by TTL=0 effect — cache
disabled for that root). It runs two `QProcess::start("git", argv)`
calls with a 2-s wall-clock cap each — `git rev-parse HEAD` and
`git status --porcelain=v1 -z`. Both are typically < 50 ms on Ants
Terminal (~600 LOC of changes / ~10 K tracked files).

`anyGateNotNaturallyCompleted` returns true if any gate's
`skippedReason` equals `"command not resolvable"` OR starts with
`"timeout after "` (see `verifyengine.cpp:300, 314-315`).

`qScopeGuard` is the Qt 6.2+ RAII helper (`<QScopeGuard>`); the
lambda fires on every return path including exceptions and
`std::terminate` propagation, so the reentrancy flag cannot leak.

### 2.8 Invariants

- **INV-1 (byte-identity)** A hit returns the SAME `response` object
  the original miss returned, **plus** `cache_hit:true`. No field
  added, no field removed. The cache stores the post-build envelope
  (after `verify_untrusted` etc. are folded in) so callers see
  identical structure.
- **INV-2 (TTL ≤ 300 s)** Entries older than 300 s are treated as a
  miss and overwritten.
- **INV-3 (no mid-run contamination)** If the pre-run git snapshot
  ≠ post-run git snapshot, the result is RETURNED to the caller
  (correct for this call) but NOT inserted into the cache. Verified
  by `MidRunEditNotCached` test. Acknowledges the bounded-race
  window per § 2.3.2 — a write completing during `git status` is
  caught on the NEXT call's pre-snapshot.
- **INV-4 (failure modes never cached)** The seven exclusion classes
  in § 2.5 each bypass insert. Verified by tests
  `BadConfigNotCached`, `NoneConfigNotCached`, `UntrustedNotCached`,
  `NonGitNotCached`, `CommandNotResolvableNotCached`,
  `TimeoutKilledNotCached`. The mid-run case is INV-3.
  Test-failures ARE cached.
- **INV-5 (git-snapshot invalidation)** Editing a tracked file
  between two `verify_changes` calls (same options) busts the cache.
  Editing an untracked file (e.g., a new `.cpp`) also busts. A
  commit also busts. Verified by `TrackedEditBustsCache`,
  `UntrackedFileBustsCache`, `CommitBustsCache`.
- **INV-6 (cap + LRU)** `m_verifyCache.size() ≤ 8`. Insert past cap
  evicts the least-recently-used entry. Hit bumps the entry to MRU.
- **INV-7 (trust-state binding)** The cache entry is keyed on
  `trustOutcomeSha` (§ 2.3) AND `verify_untrusted == true` responses
  are excluded at insert. A trust grant or revoke between two calls
  (which flips `outcomeForConfig`) flips the key and forces a miss.
  Verified by `TrustGrantBustsCache` test. Spelled out as INV so a
  future refactor of `VerifyEngine::loadGateConfig` doesn't drift
  the cache semantics — INV-7 is the contract the trust gate relies
  on for "the user can grant trust mid-session and re-run."
- **INV-8 (force_refresh contract)** `force_refresh:true` skips the
  cache lookup AND re-runs gates AND inserts on success (subject to
  the rest of INV-4). It does NOT mean "skip the cache for this call
  only" — a subsequent normal call within TTL will hit the freshly-
  inserted entry. Documents the intent so future readers don't
  misread it as a no-cache flag.
- **INV-9 (cache_only contract)** `cache_only:true` returns the
  cached response if present (with `cache_hit:true`), else
  `{ok:true, cache_hit:false, cache_miss:true, project_root:<root>}`
  without running gates. Never inserts. `force_refresh:true` AND
  `cache_only:true` together return `{ok:false,
  error:"incompatible_args"}`. Lets a caller cheaply probe for fresh
  verification without spending build time.
- **INV-10 (telemetry transparency)** `token_usage`'s wire-byte
  counter sees a hit as the same wire bytes as a miss (the response
  envelope is identical in size to within ~16 bytes for the
  `cache_hit:true` literal). `recordCall` fires on every dispatch
  (hit and miss). The savings this spec captures live in the
  **assistant's context window** + the **wall-clock skipped on the
  Ants side**, not in `token_usage` numbers — same framing as
  ANTS-1357 INV-8.
- **INV-11 (no reentrancy)** `RemoteControl` carries a
  `bool m_verifyInFlight` flag. A second `cmdVerifyChanges` call
  while a first is still inside `runVerify` (which can happen because
  `QProcess::waitForFinished` at `verifyengine.cpp:308` pumps the Qt
  event loop) returns `{ok:false, error:"verify_in_flight"}`
  immediately, without touching the cache. The flag is reset on
  every return path via `qScopeGuard` — including the early
  `bad_config` return — so the flag cannot leak past a single
  call's wall-clock. Cache reads and writes are constrained to
  before/after the runVerify window where the flag is held. This
  prevents `QHash` / `QList` mutation races through nested dispatch.
  Verified by `ReentrancyRejected` test.

### 2.9 RAM budget

Worst-case entry size:

| Field | Size |
|---|---:|
| `key` | 16 B (SHA256-hex16) |
| `stampMs` | 8 B (qint64) |
| `response` (QJsonObject) | ~2–8 KB typical, ~16 KB ceiling per `log_tail` cap (`verifyengine.cpp:19` `kHardByteCap = 16 * 1024`, applied per gate × 3 gates → 48 KB absolute ceiling, but real-world `log_tail` strings cluster at 1–2 KB each in green-build runs) |
| QHash + QList overhead | ~96 B per entry |
| **Per-entry total** | **~2.1–48.1 KB** (typical 10 KB) |

8 entries × 48.1 KB worst case = **~385 KB absolute ceiling, ~80 KB
typical**.

Order-of-magnitude consistent with the other `RemoteControl` caches
(`m_roadmapSectionCache`, `m_coldEyesCache`, `m_idempotentReadCache`) —
none of which exceed 50–500 KB in the cap × entry-size product. The
absolute ceiling sits well below the 32 GiB host budget and the
`build-workstation` preset's `-j3` CPU cap dominates resource concerns
during a verify run regardless.

## 3. Test surface

`tests/features/verify_changes_build_cache/spec.md +
test_verify_changes_build_cache.cpp` — behavioural tests against real
`QTemporaryDir` projects, plus inline-grep tests for the cap/TTL constants.

Behavioural tests use a synthetic git project with a `.ants/verify.json`
that runs `/bin/true` for `build` and `/bin/true` for `tests` (each
gate ~1 ms). This exercises the full `cmdVerifyChanges` path including
the cache insert/lookup without paying real-build wall-clock.

The test driver constructs a `RemoteControl` against a stub
`MainWindow*` — or, if that proves impractical (the actual `MainWindow`
constructor is heavy), drives a thin `RemoteControl`-shaped facade via
direct cache-API inspectors mirroring ANTS-1357 § 3:

```cpp
// remotecontrol.h — test-only seam (private members exposed)
int  verifyCacheSizeForTest() const;
QStringList verifyCacheLruForTest() const;
qint64 kVerifyCacheTtlMsForTest() const { return kVerifyCacheTtlMs; }
// Direct put/try to exercise put/get/TTL/LRU without standing up
// a real build. Mirrors ANTS-1357's pattern.
QJsonObject tryGetVerifyCacheForTest(const QString &key) const;
void putVerifyCacheForTest(const QString &key, const QJsonObject &resp);
```

The integration coverage (cache transparently interposes on real
`cmdVerifyChanges` traffic) rides on a second-tier test that drives
the verb end-to-end against the synthetic git project.

### 3.1 Test list

1. **HitWithinTtl** — drive verify on a synthetic project; second
   call within 100 ms returns `cache_hit:true` with byte-identical
   `gates` array. INV-1, INV-2.
2. **MissAfterTtl** — same project, advance time mock past TTL (or
   `QTest::qWait(120ms)` against a test-only TTL of 100 ms via a
   compile-flag override). Second call returns `cache_hit:false`.
   INV-2.
3. **TrackedEditBustsCache** — verify once; `echo // tweak >>
   src/foo.cpp`; verify again; second call is a miss (different
   `gitStatusSha`). INV-5.
4. **UntrackedFileBustsCache** — verify once; `echo x > new.cpp`
   (creates a non-`.gitignore`d file → shows as `?? new.cpp`);
   verify again; miss. INV-5.
5. **CommitBustsCache** — verify once; `git commit --allow-empty -m
   x`; verify again; miss (different HEAD). INV-5.
6. **MidRunEditNotCached** — drive a custom gate command that
   appends content to a tracked file mid-run (between pre and post
   snapshot); verify returns ok BUT cache size stays at 0. INV-3.
   Implementation: `.ants/verify.json` with `build: "sh -c 'echo x
   >> src/foo.cpp && /bin/true'"` (content change — `touch` would
   not bust the snapshot because `git status --porcelain=v1` reads
   content, not mtime). Requires `src/foo.cpp` to exist tracked
   under git.
7. **BadConfigNotCached** — corrupt `.ants/verify.json` (invalid
   JSON); verify returns `error: bad_config`; cache size 0. INV-4
   class 1.
8. **NoneConfigNotCached** — empty project root, no `.ants/`, no
   build system; verify returns `ok:true, all_passed:true` with no
   gates ran; cache size 0. INV-4 class 2.
9. **UntrustedNotCached** — `verify_untrusted=true` response is not
   inserted. INV-4 class 3. Test owns a `FakeTrustClient` subclass
   of `VerifyTrust::Client` whose `outcomeForConfig` returns a
   stub-controlled `Decision`; the fake's setter (e.g.,
   `setOutcome(Outcome::UntrustedFellBack)`) flips the return value
   between calls.
10. **TrustGrantBustsCache** — same `FakeTrustClient`. First, set
    outcome to `UntrustedFellBack`; call A returns
    `verify_untrusted:true` (NOT cached per #9). Call the fake's
    setter to switch outcome to `Trusted`; call B re-runs gates
    (different `trustOutcomeSha` because `cfgSource` flipped from
    `"auto (untrusted-bespoke)"` to `".ants/verify.json"`). Call C
    within TTL hits the cache. INV-7. The reverse direction
    (Trusted → revoked) is symmetric and shares this test's framing
    and fake.
11. **NonGitNotCached** — `QTemporaryDir` with no `.git`; verify
    runs; cache size 0; `cache_hit:false`. INV-4 class 5.
12. **CommandNotResolvableNotCached** — `.ants/verify.json` with
    `build: "no-such-binary-xyz"`; verify returns
    `skipped_reason: "command not resolvable"`; cache size 0.
    INV-4 class 6 (first half).
13. **TimeoutKilledNotCached** — `.ants/verify.json` with
    `build: "sleep 15"`; pass `timeout_sec: 10` (the floor at
    `verifyengine.cpp:451-454` — `minTotalTimeoutSec` defaults to 10
    and is NOT reachable via the public MCP `timeout_sec` arg, so
    the test exercises the actual floor). Gate kills with
    `skippedReason` starting `"timeout after "`; cache size 0.
    INV-4 class 6 (second half). Test takes ~10 s wall-clock —
    acceptable as one slow test in the bundle.
14. **TestFailureIsCached** — `.ants/verify.json` with
    `build: "/bin/true"`, `tests: "/bin/false"`; first call returns
    `all_passed:false`; second call within TTL returns
    `cache_hit:true` with the same `all_passed:false`. Failures
    over identical inputs are deterministic; the user must change
    code (which busts the key) to re-run.
15. **ForceRefreshBypassesLookup** — verify; verify again with
    `force_refresh:true`; second call's `cache_hit:false` AND the
    underlying VerifyEngine ran (instrument via a `runCount` shim
    on the gate command — e.g., `build: "sh -c 'echo $$ >>
    /tmp/runcount.log && /bin/true'"`).
16. **CacheOnlyProbe** — first call with `cache_only:true` returns
    `cache_miss:true`, no `gates` field, no compute paid; verify
    (normal); second `cache_only:true` returns `cache_hit:true`
    with full `gates`. INV-9.
17. **ForceAndCacheOnlyIncompatible** — both `force_refresh:true`
    AND `cache_only:true` returns
    `{ok:false, error:"incompatible_args"}`; no gates run; cache
    untouched. INV-9.
18. **AutoTrustEnvBustsCache** — verify with
    `ANTS_VERIFY_TRUST_AUTOTRUST` unset; flip env var to `1`;
    verify again with same project state; second call is a miss
    (different `autoTrustEnv` field in keyMaterial). INV-5
    (extended).
19. **LruEvictionAtCap** — drive 9 distinct option shapes (e.g.,
    `max_log_lines` 10, 20, 30, … 90); cache size lands at 8;
    least-recently-used entry absent from `verifyCacheLruForTest()`.
    INV-6.
20. **HitBumpsMru** — direct-API: put A, B, C; tryGet(A); insert
    D, E, F, G, H, I — A still present (most recently used), B
    evicted. INV-6.
21. **ReentrancyRejected** — drive a `.ants/verify.json` with
    `build: "sh -c 'sleep 0.5 && /bin/true'"`; the test runs under
    `QCoreApplication` and uses `QTimer::singleShot(100, this,
    &fireSecondCall)` to schedule the second `cmdVerifyChanges`
    while the first is in flight, pumping the event loop with
    `QTest::qWait(2000)` so the timer and the in-flight
    `waitForFinished` co-execute. Second call returns
    `{ok:false, error:"verify_in_flight"}` synchronously. INV-11.
22. **CapConstantDeclared** — source-grep on `remotecontrol.h` that
    `kVerifyCacheCap = 8` is declared. Catches accidental cap drift.
    (TTL value is tested numerically through `MissAfterTtl` rather
    than grep — a literal `5 * 60 * 1000` vs `300000` rewrite would
    fail a grep but is semantically identical, so we don't grep it.)

## 5. Out of scope

- **Persistence across restarts.** Cache lives in `RemoteControl`'s
  process memory only. Matches every other cache in the codebase;
  a restart is past the 5-min TTL anyway.
- **Cross-project sharing.** Each `projectRoot` is its own key
  prefix; two projects' caches never collide and never share.
- **Auto-invalidation on file watcher.** We deliberately use git as
  the invalidation signal rather than `QFileSystemWatcher` — the
  watcher would need to descend the full source tree, fight `.gitignore`,
  and re-fire on every editor save (vs git's coarse but authoritative
  "did the project state change?" signal).
- **Per-call TTL override (`cache_max_age_sec` arg).** Considered;
  the 5-min default + `force_refresh:true` cover today's needs. Revisit
  if a real caller surfaces a use case (e.g., a paranoid CI runner that
  wants ≤ 30 s cache age).
- **Toolchain-version baking into the key.** Cheap to add (`stat
  $(which gcc) $(which cmake)`) and catches the named § 2.6 limitation
  3 threat; out of scope for v1 because no concrete incident has been
  observed yet — keeping the key small until a real false-hit lands.
- **`VerifyEngine::runVerify(projectPath, cfg, opts)` overload.** The
  miss path re-calls `loadGateConfig` inside `runVerify` even though
  step 6 already loaded it. The duplicate is silent (sub-millisecond)
  per § 2.1 rationale, so the refactor is pure cleanup, not a
  correctness fix. A v2 spec could introduce the overload alongside
  whatever next change touches the engine.
- **Cache hit annotation in the existing `tokenusageengine` cost
  table.** Out of scope for v1; a future `token_usage` enhancement
  can split hit vs miss bytes.
- **Distributed cache (ccache / sccache integration).** Different
  scope — those caches sit under cmake, not above `verify_changes`.
  This cache is one level higher: it short-circuits the entire MCP
  dispatch.

## 6. Migration

None. New behaviour layers on top of existing dispatch:

- Existing callers that don't pass `force_refresh` / `cache_only`
  see the new `cache_hit:false` field on every fresh-run response.
  Schema additive; no contract broken.
- Existing tests under `tests/features/verify_changes_engine/`
  remain green — they exercise `VerifyEngine` directly, not
  `cmdVerifyChanges`, so the cache layer is invisible to them.
- `tokenusageengine.cpp:20` keeps `verify_changes=8192` — the cache
  reduces compute-side cost, not wire bytes.
