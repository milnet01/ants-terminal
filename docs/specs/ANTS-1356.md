# ANTS-1356 — MCP per-tool rate-limit / quota

**Status:** in flight (Bundle E pull 2, 2026-05-17).
**Kind:** security.
**Lanes:** `claudeintegration` (`processTools` dispatcher; new
`m_rateLimitBuckets` private state), `docs/standards/mcp-error-codes.md`
(new `rate_limited` code row).
**Source:** indie-review-2026-05-14 (self-observed during the review
sweep that produced the ANTS-1352…1410 bundle).
**Pairs with:** ANTS-1357 (idempotent-read cache — rate-limit runs
*before* the cache lookup so cache hits still consume bucket budget),
ANTS-1404 (`caller_cwd_required` contract check — runs *before*
rate-limit so a misconfigured caller gets the precise refusal first),
ANTS-1402 (`recordDispatch` hook — `rate_limited` refusals route
through it so `mcp_trace` surfaces them; `m_tokenUsage` continues to
skip non-`"ok"` results), ANTS-1353 (`mcp-error-codes.md` taxonomy).

## Problem

Today the MCP dispatcher in `ClaudeIntegration::processTools` has no
cap on call rate. A misbehaving Claude session — runaway loop,
oscillation in a polling skill, or a deliberate flood — can fire any
verb in a tight loop and the server will dutifully process every one.
The existing wall-clock idle timer (5 s) catches dead-air, not floods.

Risk surface:

- **Cheap reads** (`get_scrollback`, `get_cwd`, `roadmap_query`,
  `tab_list`, …) cost negligible CPU each, but a 10 K-call/min flood
  burns a useful amount of main-thread time + log volume.
- **Expensive operations** (`audit_run`, `cold_eyes_brief`,
  `workspace_search`, `verify_changes`, `debt_sweep_scan`, …) can
  shell out to multi-second processes. A flood here is the
  observable-as-system-load attack — earlyoom or runaway disk-IO.
- **Caller-cwd-less control plane** (`get_session_info`,
  `token_usage`, `tool_info`, `mcp_trace`, `caller_cwd_info`) is
  cheap state-reads from server-owned data; flooding here is
  harmless but adds noise to `mcp_trace`.

## Goal

Add a per-tool per-session call-rate cap with a 60-second sliding
window. Three tiers:

| Tier | Cap (calls/min) | Tools |
|---|---|---|
| Cheap | 60 | default — all read verbs not listed below, including `last_audit_summary`, `roadmap_query`, `roadmap_log`, `tab_list`, `get_scrollback`, `get_text`, `get_cwd`, `get_environment`, `get_last_command`, `get_git_status`, `git_state`, `file_outline`, `subsystem`, `session_memory`, `project_layout`, `plan_template`, `debt_sweep_defer`, `debt_sweep_triage_prompt`, `indie_review_synthesis_prompt`, `test_audit_synthesis_prompt` |
| Expensive | 10 | `audit_run`, `workspace_search`, `verify_changes`, `cold_eyes_brief`, `cold_eyes_partition`, `cold_eyes_cross_doc_diff`, `cold_eyes_fold_in`, `indie_review_brief`, `indie_review_partition`, `indie_review_corroborate`, `indie_review_fold_in`, `test_audit_brief`, `test_audit_partition`, `test_audit_fold_in`, `debt_sweep_scan`, `debt_sweep_apply_fix` |
| ControlPlane | uncapped | `get_session_info`, `token_usage`, `tool_info`, `mcp_trace`, `caller_cwd_info` |

`last_audit_summary` is in the Cheap tier **and** the ANTS-1357
idempotent-read cache (one of four cached tools). INV-5
demonstrates that cache hits still consume bucket budget. The
other three cached tools (`get_cwd`, `get_environment`, `tab_list`)
are also Cheap; `workspace_search` and other Expensive verbs are
NOT cached.

When a tool is at cap, the dispatcher refuses with:

```jsonc
{
  "ok": false,
  "code": "rate_limited",
  "error": "<tool>: rate-limited (<n> calls in last 60 s, cap <cap>). retry_after_ms=<m>",
  "retry_after_ms": <int>
}
```

`retry_after_ms` is exact for sliding-window — `(oldest_ts +
window_ms) - now_ms`. Callers can busy-wait that long and re-issue
the call.

## Design

### Bucket structure

Per-(toolName, callerCwd) bucket holding a queue of recent call
timestamps within the window:

```cpp
// In claudeintegration.h (private):
struct RateLimitBucket {
    QQueue<qint64> tsMs;   // wall-clock ms epoch, ascending
};
QHash<QPair<QString, QString>, RateLimitBucket> m_rateLimitBuckets;
static constexpr int kRateLimitMapCap = 256;
```

Key is `(toolName, callerCwd)`. Tools called without `caller_cwd`
share the `(toolName, "")` bucket — a single global quota for that
tool across all callers. This is the correct semantic for
caller-cwd-less invocations: they aren't routable to a specific
project, so there's no project-scoped bucket to use.

### Tier classification

```cpp
enum class RateLimitClass { Cheap, Expensive, ControlPlane };
static RateLimitClass rateLimitClassFor(const QString &toolName);

struct RateLimitTier { int capPerWindow; qint64 windowMs; };
static RateLimitTier rateLimitTierFor(RateLimitClass cls);
```

`rateLimitClassFor` checks two explicit allowlists (Expensive,
ControlPlane) and returns `Cheap` as the default. The lists are
compile-time constants; adding a new tool is a one-line edit to
the relevant list (default-Cheap means most additions need no
change).

`rateLimitTierFor` returns:

- `Cheap`        → `{ capPerWindow: 60, windowMs: 60'000 }`
- `Expensive`    → `{ capPerWindow: 10, windowMs: 60'000 }`
- `ControlPlane` → `{ capPerWindow: INT_MAX, windowMs: 60'000 }`

### Rate-limit check

```cpp
// In claudeintegration.h (public-for-tests):
//
// Returns 0 if the call is accepted (and the timestamp is appended
// to the bucket as a side-effect). Returns retry_after_ms (> 0) if
// the call is refused.
//
// `nowMs` is parameterised so tests can drive synthetic time.
// In production, callers pass monotonic time:
// `s_rateLimitClock.elapsed()` against a `static QElapsedTimer
// s_rateLimitClock` initialised once at startup. Monotonic time
// defends against NTP / suspend-resume wall-clock skew that would
// otherwise corrupt the queue ordering invariant
// (`tsMs` must be strictly ascending).
qint64 rateLimitCheck(const QString &toolName,
                      const QString &callerCwd,
                      qint64 nowMs);
```

Implementation:

1. Determine tier via `rateLimitClassFor`. If `ControlPlane`, return
   0 immediately (no bucket touched, no growth).
2. Look up bucket at key `(toolName, callerCwd)`.
3. Prune the front of the queue while `tsMs.front() < nowMs - windowMs`.
4. If empty post-prune, erase the bucket entry from `m_rateLimitBuckets`
   (keeps the map size proportional to active load) and append `nowMs`
   to a fresh bucket; return 0.
5. If `tsMs.size() < capPerWindow`, append `nowMs`; return 0.
6. At cap: compute `retryAfterMs = (tsMs.front() + windowMs) - nowMs`,
   floor at 1, return.

### Map-cap eviction

If the map size hits `kRateLimitMapCap` AND the bucket for the
incoming call doesn't already exist, evict one entry. Eviction
policy: linear scan, pick the bucket whose most-recent timestamp is
oldest. This is O(N) per insertion at the cap, but the cap is small
(256) and only triggered under high cardinality of (tool, cwd)
pairs — a normal workstation runs ≤ 30. Worst-case eviction cost is
~256 µs (256 QHash lookups + back() reads), bounded.

### Dispatch order

In `processTools`, the order of checks at the head of
`if (method == "tools/call")` becomes:

1. **caller_cwd_required** check (ANTS-1404, existing). Refused
   calls bypass everything else.
2. **NEW: rate-limit check (ANTS-1356).** Refused calls bypass
   cache lookup + dispatch. Routed through `recordDispatch` with
   `result = "rate_limited"`.
3. **idempotent-read cache** lookup (ANTS-1357, existing). Cache
   hits return the cached response. Cache hits *consume* a bucket
   slot (the rate-limit check ran before the cache lookup) — this
   is by design (see "Cache-hit accounting" below).
4. **Dispatch to provider** (or inline `get_session_info` /
   `tool_info`).

### Cache-hit accounting

Cache hits run AFTER the rate-limit check, so they consume the
bucket. Rationale:

- The threat model is "runaway loop spamming a tool". The loop
  doesn't know or care whether the underlying tool ran or was
  served from cache — it's the call rate that matters.
- Without this, a polling caller learns that cacheable tools
  (`get_cwd`, `get_environment`, `tab_list`, `last_audit_summary`)
  are effectively free, defeating the rate-limit on exactly the
  most-flooded surface.
- The semantic stays: cache exists to save *server-side compute
  and token round-trips*, rate-limit exists to bound *call rate*.
  Different concerns, both apply.

### Refusal-record handling

A rate-limited refusal is routed through `recordDispatch` with
`result = "rate_limited"`. Per the ANTS-1432 wiring at
`claudeintegration.cpp:1273-1275`, `recordCall` now fires on every
dispatch with `succeeded = (result == "ok")`. So:

- The refusal is counted as a **failed call** in `m_tokenUsage`
  (success=false). Bytes-in (argsObj size) and bytes-out (refusal
  envelope size) flow into the failed-call accumulator. This
  surfaces refusal cost in `token_usage` dashboards — the right
  visibility per ANTS-1432's "waste-on-failure cost" intent.
- The refusal is recorded in `mcp_trace` so debugging a
  flood-pattern is observable.
- This requires a new `dispatchResult` variable in `processTools`:
  defaulted to `"ok"`, set to `"rate_limited"` by the new
  rate-limit branch, passed to `recordDispatch` instead of the
  hard-coded `"ok"`. Mechanical change at one site.

### ANTS-1404 latent-bug observation (out of scope for this spec)

Verified during cold-eyes review (2026-05-17): ANTS-1404's
`caller_cwd_required` refusal currently flows through
`recordDispatch` with `result = "ok"` and is therefore counted as a
successful call in `m_tokenUsage` — a measurement bug introduced
by the ANTS-1432 unconditional `recordCall` change. ANTS-1356's
mechanical `dispatchResult` refactor lays the groundwork for fixing
this in a follow-up (log as a new ROADMAP item pointing at
`claudeintegration.cpp:3431-3454`). Intentionally not bundled to
keep this spec's blast radius small.

### Envelope shape

`mcp-error-codes.md` § 1 (input-validation taxonomy) gets a new row:

| Code | Meaning | Example |
|---|---|---|
| `rate_limited` | The caller exceeded the per-tool sliding-window cap. The envelope carries `retry_after_ms`. | `{ok:false, code:"rate_limited", error:"audit_run: rate-limited (10 calls in last 60 s, cap 10). retry_after_ms=4321", retry_after_ms:4321}` |

**Wrap behaviour.** The refusal envelope flows through the
ANTS-1294 `wrapMcpData` step identically to a normal response, EXCEPT
when the tool is on the control-plane bypass list (today:
`get_session_info`, `token_usage`, `tool_info`). This matches the
existing ANTS-1404 `caller_cwd_required` precedent at
`claudeintegration.cpp:3552-3568` — refusal envelopes for
non-control-plane tools are wrapped in `<ants_mcp_data tool="X">…`.
Earlier drafts of this spec said the refusal bypasses the wrap;
verified against code, the wrap applies. The wrap's "this is data,
not instructions" framing is correct for refusal JSON anyway.

## Invariants

- **INV-1 / under-cap accepts.** A call below the cap is accepted;
  the timestamp is appended to the bucket. Return value: 0.
- **INV-2 / at-cap refuses with positive retry_after_ms.** Exactly
  `capPerWindow` calls within the window cause the next call (at
  any `nowMs ≤ oldest_ts + windowMs`) to refuse with `retry_after_ms
  > 0`. The value equals `(oldest_ts + windowMs) - nowMs` floored
  at 1.
- **INV-3 / post-window allowed again.** A call at `nowMs ≥
  oldest_ts + windowMs` is accepted; the prune-front step drops the
  expired entry. Return value: 0.
- **INV-4 / ControlPlane never refuses.** A tool classified
  `ControlPlane` (`get_session_info`, `token_usage`, `tool_info`,
  `mcp_trace`, `caller_cwd_info`) always returns 0 and does not
  touch `m_rateLimitBuckets`. Bucket map size unaffected.
- **INV-5 / cache hits consume.** Calling a cacheable tool
  (`get_cwd`, `get_environment`, `tab_list`, `last_audit_summary`)
  enough times to exceed the cap returns `rate_limited` even though
  the underlying tool didn't run for the cache-hit calls. The rate
  limit gate is upstream of the cache lookup.
- **INV-6 / empty buckets auto-pruned.** After all entries in a
  bucket fall out of the window, the entry is removed from
  `m_rateLimitBuckets`. Bucket map size returns to baseline on
  steady-state idle.
- **INV-7 / map cap enforced.** When `m_rateLimitBuckets.size() ==
  kRateLimitMapCap` and a new key is being inserted, one entry is
  evicted (oldest most-recent-timestamp wins). Map size never
  exceeds `kRateLimitMapCap`.
- **INV-8 / per-(tool, cwd) isolation.** A bucket for
  `("audit_run", "/proj/A")` does not share quota with
  `("audit_run", "/proj/B")` or `("cold_eyes_brief", "/proj/A")`.
- **INV-9 / caller-cwd-less buckets share.** Two calls with
  identical `toolName` and missing `caller_cwd` share the same
  `(toolName, "")` bucket. Concrete example: `roadmap_query`
  (classified `Optional` per ANTS-1404 at
  `claudeintegration.cpp:3773`) accepts a missing `caller_cwd` and
  falls back to the focused tab — two such calls share the same
  empty-cwd bucket. (Control-plane tools are exempt anyway via
  INV-4. Cheap/Expensive tools called without `caller_cwd` are
  rare in practice and a shared bucket is the right default for
  them.)
- **INV-10 / refusal routed through recordDispatch.** The refusal
  branch calls `recordDispatch(toolName, args, argBytes, outBytes,
  wrapBytes, durUs, /*cachedHit=*/false, "rate_limited")` with
  `outBytes` measuring the (wrapped) refusal envelope and
  `wrapBytes` the wrap delta. Per the ANTS-1432 wiring at
  `claudeintegration.cpp:1273-1275`, `recordCall` fires with
  `success = false` (since `result != "ok"`), routing the bytes
  into `m_tokenUsage`'s failed-call accumulator and surfacing the
  refusal cost in `token_usage` dashboards. `mcp_trace` ring sees
  the record with `result = "rate_limited"`.
- **INV-11 / refusal envelope shape.** The refusal carries `ok:false`,
  `code:"rate_limited"`, `error` string (containing tool name + the
  observed count + cap), and `retry_after_ms` integer.
  Non-control-plane refusals are wrapped in
  `<ants_mcp_data tool="X">…` per ANTS-1294 (matching the
  ANTS-1404 `caller_cwd_required` precedent at
  `claudeintegration.cpp:3552-3568`).
- **INV-12 / order vs caller_cwd_required.** A call missing
  `caller_cwd` on a `Required`-contract tool refuses with
  `caller_cwd_required` (ANTS-1404), not `rate_limited`. The
  caller_cwd_required check runs first; the rate-limit check never
  sees these calls.
- **INV-13 / ControlPlane allowlist literally matches the
  ANTS-1294 control-plane wrap-bypass list, modulo additions for
  diagnostic verbs.** The set is: `get_session_info`, `token_usage`,
  `tool_info`, `mcp_trace`, `caller_cwd_info`. Other tools that
  bypass the wrap for other reasons (none today) do NOT
  automatically inherit rate-limit exemption.
- **INV-14 / test-only cap override.** Two public static methods
  `setRateLimitCapsForTest(int cheap, int expensive)` and
  `resetRateLimitCapsForTest()` override the per-tier caps for
  the duration of a test. Mirrors the existing `*ForTest`
  convention in `claudeintegration.h` (no `#ifdef` gating).
  Production code paths read the override transparently —
  defaults are 60 / 10 when unset.
- **INV-15 / probe accessors for tests.** `rateLimitBucketCountForTest()`
  returns `m_rateLimitBuckets.size()`; `rateLimitBucketDepthForTest(tool,
  cwd)` returns the queue depth for one bucket (0 if absent).
  Used by INV-6 and INV-7 tests; INV-15 itself is verified by a
  dedicated test that probes both accessors on a constructed bucket
  state (empty / one entry / post-prune empty).
- **INV-16 / monotonic clock for production calls.** The production
  call site uses `s_rateLimitClock.elapsed()` (a static
  `QElapsedTimer` initialised at startup); tests inject synthetic
  `nowMs`. The queue's strictly-ascending invariant on `tsMs`
  cannot be violated by wall-clock NTP / suspend-resume jumps.
- **INV-17 / refusal-flood visibility trade-off.** A sustained
  flood at the cap rate (60 Cheap + 10 Expensive = ≤ 70
  refusals/min total) fills the 200-record `m_mcpTraceRing` in
  ~3 minutes, evicting earlier successful records. Acceptable
  trade-off for v1: the rate-limit itself bounds the flood
  volume, normal records refill the ring within ~3 min of the
  flood ending. Documented here for visibility; mitigation
  (collapse consecutive same-(tool,cwd) refusals into one record
  with a `count` field) is logged as a follow-up roadmap item if
  real workloads show the eviction is painful.

## RAM / build cost

Per bucket: at most `capPerWindow` × 8 bytes of timestamps plus the
QQueue head/tail overhead (~32 bytes). Cheap bucket peak ≈ 60 × 8 +
32 = ~512 B; Expensive bucket peak ≈ 10 × 8 + 32 = ~112 B.

Map cap: `kRateLimitMapCap = 256`. Absolute worst case — **assuming
all 256 buckets are Cheap-tier and at peak fill** — is 256 × 512 B
= ~128 KiB. With the current classification, the upper bound on
Expensive buckets is `≤ N_expensive_tools × N_distinct_cwds`; for a
workstation with 5 projects × 16 Expensive tools, the Expensive
contribution caps at ~9 KiB (80 buckets × 112 B). Typical steady
state: ≤ 20 active (tool, cwd) pairs × ~150 B average ≈ 3 KiB.
Well inside the per-feature RAM budget the user requires.

Code addition: ~120 LoC in `claudeintegration.cpp` (rate-limit
helpers, classification function, dispatcher hook), ~30 LoC in
`claudeintegration.h` (struct + state + signatures), ~280 LoC test.

Compile cost: negligible (no new headers, all-`QHash`/`QQueue`).

## Migration

None. The cap shipping (60/min Cheap, 10/min Expensive) is generous
relative to observed sustained traffic — `mcp_trace` records show
typical Claude Code sessions issue 5–15 MCP calls per minute
total, distributed across many tools. The cap targets pathological
loops, not normal traffic.

The first deploy may surface a hit for a poorly-paced skill (e.g.
a `cold_eyes` orchestrator that issues 12 `cold_eyes_brief` calls
in a 30-second window). That's the intended catch: the skill
author is expected to back off using `retry_after_ms` from the
refusal envelope.

A test-only knob (`setRateLimitCapsForTest`) lets the regression
test in `mcp_rate_limit/` drive the cap down to a tractable
number (e.g. 3) without depending on a 60-call setup.

## Out of scope

- **Configurable caps via config / env.** Caps are compile-time
  constants. A future ANTS-NNNN can promote them to
  `~/.config/ants-terminal/config.json` if real workloads show the
  60/10 defaults are wrong. Until we have data, keep the surface
  minimal.
- **Burst tokens.** A token-bucket scheme would let callers burst
  briefly past the cap. The sliding-window approach is simpler and
  matches the "N/min" mental model; bursting is a v2 concern.
- **Cross-(tool, cwd) global cap.** This spec only caps per-bucket.
  A global "all-tools, all-cwds" cap is a different attack surface
  (the QLocalSocket accept loop itself); guarding it is its own
  spec.
- **Backoff coordination with the bridge.** `mcp-bridge.py` doesn't
  retry on `rate_limited`; the caller (Claude) is expected to
  honour `retry_after_ms`. Adding retry to the bridge would mask
  the refusal from the caller — defeats the visibility goal.
