# ANTS-1339 — `AuditEngine::applyFilter` streaming line-split

## Problem

`src/auditengine.cpp` previously called
`raw.split('\n', Qt::KeepEmptyParts)` at the head of
`AuditEngine::applyFilter`, materialising the full QStringList up front.
The upstream `MAX_TOOL_OUTPUT_BYTES = 64 * 1024 * 1024` cap (1119's
incremental-output drain) means a pathological tool emitting 64 MB of
single-character lines allocates ~64 M `QString` headers (~1.5–2 GB
peak working set) before `f.maxLines` (default 100) truncates.

The `maxLines` cap is applied AFTER the split has already paid the
materialisation cost, so the early-bail at line 231 saves nothing on
the input side. The 64 MB cap is the only backstop and the
amplification factor between input bytes and resident memory is
roughly 30×.

Source: indie-review-2026-05-14 lane-4 M3.

## Fix

Replace the up-front split with a single-pass `indexOf('\n')` + slice
walk that:

1. Tracks `pos` and `nextNl = raw.indexOf('\n', pos)`.
2. Yields each line as a `QStringView` slice without allocating per-
   line QStrings up front (only kept lines materialise QString copies
   when appended to `out`).
3. Bails the loop as soon as `f.maxLines > 0 && keptCount >= f.maxLines`
   — the previous filter chain runs unchanged on each candidate slice.

Tail handling: if `raw` does not end with `\n`, the final slice from
the last `\n + 1` through `raw.size()` is processed exactly like any
other line.

The drop/keep predicate composition and SARIF-side outputs are
byte-identical to v1 — the only observable change is peak memory
consumption on tool outputs that produce far more lines than the
`maxLines` cap permits.

## Invariants

- **INV-1** `auditengine.cpp` does not contain the literal token
  `raw.split('\n'` inside the `applyFilter` body. (Source-grep guard
  against regression.)
- **INV-2** `applyFilter` against a 4 KiB raw output of 100 short
  lines with `maxLines=10` returns 10 lines (same as v1) and the
  filter respects `dropIfContains` / `keepOnlyIfContains`.
- **INV-3** `applyFilter` against a synthetic 1 MiB output of
  `'a'\n` × ~512 K with `maxLines=5` returns 5 lines AND completes
  in under 250 ms of wall-clock (smoke gate against full-split
  reintroduction — peak working set is the harder property to test,
  so the loop-bail latency is the proxy).
- **INV-4** Tail handling: an input that does NOT end with `\n`
  yields the final line as a kept candidate when filters pass.
- **INV-5** Empty input → `{ "", 0 }` (no allocation, no candidates).

## Out of scope

- `parseFindings` uses `body.split('\n', Qt::SkipEmptyParts)` at
  line 257 against the already-filtered body. The filtered body is
  bounded by `maxLines × kMaxLineWidth` (well below 64 MB), so
  streaming `parseFindings` would only add complexity without a
  measurable benefit. Leave as-is.

## Tests

`tests/features/audit_engine_stream_line_split/`:

- INV-1 sentinel-grep against `auditengine.cpp`.
- INV-2/4/5 behavioural via direct `AuditEngine::applyFilter` calls.
- INV-3 throughput gate (5-line bail on 1 MiB input, < 250 ms).
