# ANTS-1235 — RoadmapDialog v2: accessible status / theme glyph labels

- **Status:** 📋 Spec draft 2026-05-11. Pending user sign-off. On
  sign-off, advance the ROADMAP bullet from 💭 → 📋 (or 🚧 if
  implementation starts immediately).
- **Source:** roadmap-v2 research synthesis 2026-05-11 (NN/g, Pope.tech
  / W3C H86) + standing user accessibility context (partially sighted,
  routinely runs Orca on the Linux desktop).
- **Lanes:** roadmapdialog (renderer), roadmapdialog (filter row).
- **Kind:** implement (additive — pure addition of plain-text labels).

## 1. Problem

Screen readers (Orca / NVDA / VoiceOver) announce Unicode emoji
codepoints by their CLDR name unless the application controls the
announced text. Today the Roadmap dialog renders the four status
glyphs (`✅` / `🚧` / `📋` / `💭`) and the theme glyphs (`🎨` / `⚡`
/ `🔌` / `🖥` / `🔒` / `🧰` / `📚` / `📦` / `🐛` / `🔍` / `🧹` —
see `docs/standards/roadmap-format.md` §3.4 for the canonical
list) without adjacent text labels in three places:

1. **Per-card state cell** (`<span class="rm-state">✅</span>`,
   `src/roadmapdialog.cpp:1136`). Orca speaks "white heavy check
   mark" before each card body, on every card.
2. **Section-header count chips**
   (`<span class="rm-section-counts">✅ 47 🚧 2 📋 3 💭 8</span>`,
   `src/roadmapdialog.cpp:1097-1100`). Orca speaks "white heavy
   check mark 47 construction sign 2 clipboard 3 thought balloon 8"
   — useless as a scan cue.
3. **Filter-row QCheckBoxes** (`tr("✅ Done")` etc.,
   `src/roadmapdialog.cpp:1402-1416`). Orca reads "white heavy
   check mark Done" — the trailing word is fine but the emoji name
   precedes it.

The cards are the most painful site (one announcement per card,
times hundreds of cards). For a partially-sighted user reading a
several-hundred-bullet roadmap with Orca, the glyph names dominate
the audio. The user's verbatim Layman expectation in the ROADMAP
entry: *"make sure screen readers say 'Shipped' instead of 'white
heavy check mark' when they hit a ✅."*

## 2. Mechanism — what was investigated, what was chosen

### 2.a Rejected — HTML `aria-label` / `alt` / `title`

The ROADMAP entry suggested *"wrap each status emoji in `<span
aria-label='Shipped'>…</span>`"*. **This mechanism does not work
in Qt 6 QTextBrowser** and was rejected after verification:

- `QTextDocument`'s HTML parser supports a fixed subset of HTML +
  CSS (see Qt docs *Supported HTML Subset*) and silently strips
  attributes it doesn't recognise — `aria-*`, `alt`, `role`, and
  `title` are all dropped from the document model on parse.
- `QAccessibleTextInterface` (declared at
  `/usr/include/qt6/QtGui/qaccessible.h:122`, with the relevant
  pure-virtual `text(int startOffset, int endOffset) const` at
  `:138`) exposes content via character-offset access into the
  document's plain text. There is no path for an HTML metadata
  attribute to reach an AT-SPI / IAccessible2 client.
- `QTextCharFormat` / `QTextFormat`
  (`/usr/include/qt6/QtGui/qtextformat.h`) have no `setAlt` /
  `setAccessibleName` / `setAriaLabel` property either. There is
  no Qt-level escape hatch for per-fragment a11y metadata in
  QTextDocument.

So any mechanism that depends on the screen reader picking up
metadata distinct from the visible text is dead on arrival.

### 2.b Rejected — visually-hidden labels (`font-size:0`)

A `<span style="font-size:0">Shipped</span>` next to the emoji
would land in `toPlainText()` and therefore in the AT-SPI text
stream. Rejected for two reasons:

- `QAccessibleTextInterface::characterRect(int offset)` returns an
  empty rect for 0-sized text. Screen-reader behaviour on
  empty-rect text fragments is not specified by AT-SPI / IA2 — it
  varies by reader version and is brittle to depend on.
- Even when it works, the screen reader announces *both* the
  hidden label and the emoji codepoint name (Qt doesn't have an
  `aria-hidden` equivalent for the glyph). So the user hears
  "Shipped white heavy check mark" — strictly worse than the
  visible-label approach below, which still announces both but at
  least keeps the visible UI honest with what's spoken.

### 2.c Chosen — visible compact labels in the rendered text

Render a short, semantically-meaningful text label after each
status emoji in the document body. Style it compactly via a CSS
class so it reads as a label, not a sentence. The visible UI gains
~6-12 characters per card; the audio stream picks up the label
deterministically because it's plain text inside QTextDocument.

Trade-off accepted: the dialog gets visibly wordier for sighted
users. Mitigation: the label CSS uses 10-11px, `bgSecondary`-tone
muted colour, padding-left for separation — same visual weight as
the existing `.rm-id` / `.rm-date` chips. Industry precedent —
Linear, GitHub Projects, and Carbon Design's status-tag pattern
all show emoji + text label together.

Theme glyphs (the full eleven-glyph set listed in §1) are **out
of scope** for labelling because they appear inside section
heading text — the heading already labels them (`## 🎨 Roadmap
dialog v2 follow-ups` → Orca reads "art palette Roadmap dialog v2
follow-ups", the heading text itself disambiguates). Adding
"Visual" before "Roadmap dialog v2 follow-ups" is redundant.

### 2.d Chosen — `setAccessibleName` on the filter checkboxes

QCheckBox is a QWidget, so `setAccessibleName("Show shipped
items")` is the idiomatic Qt 6 a11y path
(`src/claudestatuswidgets.cpp:50`, `src/commandpalette.cpp:47`
both follow this pattern). The visible checkbox label is renamed
from `✅ Done` to `✅ Shipped` at the same time (see §3.d for
rationale) so the visible vocabulary aligns with what the screen
reader announces.

## 3. Fix

### 3.a Status-label map

A four-entry table living next to the existing `kEmoji*`
constants (`src/roadmapdialog.cpp:40-43`) so codepoints and
labels stay co-located. Labels go through `QT_TR_NOOP` so
`lupdate` extracts them when a translation pass arrives:

```cpp
struct StatusLabel { const char *emoji; const char *label; };
constexpr StatusLabel kStatusLabels[] = {
    {kEmojiDone,       QT_TR_NOOP("shipped")},
    {kEmojiInProgress, QT_TR_NOOP("in progress")},
    {kEmojiPlanned,    QT_TR_NOOP("planned")},
    {kEmojiConsidered, QT_TR_NOOP("considered")},
};
static_assert(std::size(kStatusLabels) == 4,
              "Add a label here when introducing a new status emoji.");

QString RoadmapDialog::statusAccessibleLabel(const QString &emoji) {
    for (const auto &row : kStatusLabels) {
        if (emoji == QLatin1String(row.emoji))
            return tr(row.label);
    }
    return {};
}
```

The helper is a static method on `RoadmapDialog` — matching the
existing `renderHtml` / `renderCardsHtml` purity pattern
(`src/roadmapdialog.h:134, 183`). `tr()` inside a `Q_OBJECT`
class's static method resolves to that class's translation
context, same as `tr("✅ Done")` and friends on the same dialog.

Labels are lowercase at the source — QTextDocument's CSS subset
does not include `text-transform`, so the casing is locked in
the source string. The lowercase reads as a chip ("shipped") not
a sentence ("Shipped"), and the screen reader speaks it verbatim.

### 3.b Per-card emission

`emitCard` in `renderCardsHtml`, after the existing `<span
class="rm-state">` (`src/roadmapdialog.cpp:1136`):

```cpp
html += QStringLiteral("<span class=\"rm-state\">%1</span>")
            .arg(rec.status);
const QString stateLabel = statusAccessibleLabel(rec.status);
if (!stateLabel.isEmpty()) {
    html += QStringLiteral("<span class=\"rm-state-label\">%1</span>")
                .arg(htmlEscape(stateLabel));
}
```

### 3.c Section-header counts

The chip builder at `src/roadmapdialog.cpp:1097-1100` adds a single
trailing word per active status, separated by a thin middle dot:

```cpp
if (c.done > 0)        chips += QStringLiteral("✅ %1 shipped · ").arg(c.done);
if (c.inProgress > 0)  chips += QStringLiteral("🚧 %1 in progress · ").arg(c.inProgress);
if (c.planned > 0)     chips += QStringLiteral("📋 %1 planned · ").arg(c.planned);
if (c.considered > 0)  chips += QStringLiteral("💭 %1 considered · ").arg(c.considered);
```

The existing trim of the chip string (`chips.trimmed()` at
`src/roadmapdialog.cpp:1104`) only strips ASCII whitespace and
will leave the trailing ` · ` in place. Replace with explicit
chopping:

```cpp
// chop the trailing " · " (3 codepoints) introduced by the separator
if (chips.endsWith(QStringLiteral(" · "))) chips.chop(3);
```

`QString::chop(int n)` removes `n` characters from the end
in-place; this is the idiomatic Qt 6 pattern for the case. Drop
the `.trimmed()` call — the explicit chop is now sufficient.

**Wrap concern:** the labelled form is roughly half again as wide
as the current `✅ 47 🚧 2 📋 3 💭 8`. (Exact pixel widths depend
on font + DPI and are not measured here; estimated visually
against the existing dialog at 800 px and an 11 px chip font.)
At realistic widths the chip line still fits between the chevron
and the section title on common monitor configurations, but to
guard against narrower dialog widths or three-digit counts the
renderer adds `white-space:nowrap` on `.rm-section-counts` (§3.e).
That keeps the chip line on one row and lets the section title
wrap underneath if necessary.

### 3.d Filter QCheckBoxes

In the dialog ctor (`src/roadmapdialog.cpp:1402-1416` — the
four-status `m_filter*` checkboxes plus `m_filterCurrent`):

```cpp
m_filterDone->setAccessibleName(tr("Show shipped items"));
m_filterPlanned->setAccessibleName(tr("Show planned items"));
m_filterInProgress->setAccessibleName(tr("Show in-progress items"));
m_filterConsidered->setAccessibleName(tr("Show considered items"));
m_filterCurrent->setAccessibleName(
    tr("Show only items currently being worked on"));
```

**Visible-label rename.** The visible `tr("✅ Done")` checkbox
label is renamed to `tr("✅ Shipped")` so the visible vocabulary
matches the card/section-count "shipped" labels and the
accessibleName "Show shipped items". The standards doc
(`docs/standards/roadmap-format.md` §3.3) lists *both* "Done"
and "shipped" as accepted names for ✅, so either is conformant
— the rename is a vocabulary-alignment choice across the dialog,
not a correction. One-line `QStringLiteral` swap; in-scope here
because leaving the visible word disagreeing with the
accessibleName would guarantee a future re-open.

**Internal-API name kept.** The `Filter::ShowDone` enum value
(`src/roadmapdialog.h:71`) keeps its historic name — only the
user-visible string changes. Renaming the enum would ripple
through every Filter operator and persisted config key, all for
zero user-visible effect.

### 3.e CSS

Append to the `<style>` block in `renderCardsHtml`
(`src/roadmapdialog.cpp:1010-1056`):

```css
.rm-state-label {
    font-size: 10px;
    color: %6;          /* textSecondary — same muted role used by .rm-id / .rm-date */
    padding-right: 6px;
}
.rm-section-counts {
    white-space: nowrap;   /* prevent chip line from wrapping mid-chip */
}
```

The first rule styles the per-card label. The second is a pre-
emptive guard against the wider chip lines from §3.c overflowing
their row — the existing `.rm-section-counts` rule (line 1028) is
augmented, not replaced, so the existing font/colour/padding stay.

Lowercase casing is locked in the source literal (§3.a), not in
CSS — `text-transform` is not in QTextDocument's CSS subset.

## 4. Invariants

| #  | Lane | Statement |
|----|------|-----------|
| 1  | render | Each `<span class="rm-state">` emitted by `renderCardsHtml` MUST be followed immediately by a `<span class="rm-state-label">` containing the verbatim lowercase text "shipped" / "in progress" / "planned" / "considered" matching the preceding emoji. |
| 2  | render | The label text comes from `statusAccessibleLabel(emoji)`; the four-entry `kStatusLabels` table (§3.a) lives in the same TU as the four `kEmoji*` constants, and a `static_assert(std::size(kStatusLabels) == 4)` fires if a fifth entry is added without bumping the assert (forcing the implementer to surface the new label in source review). The runtime backstop is INV-1's test — adding a fifth status emoji without an entry in `kStatusLabels` makes `statusAccessibleLabel` return empty, INV-1 sees a missing `<span class="rm-state-label">`, test fails. |
| 3  | render | Section count chips MUST emit a text word after the count: `✅ 47 shipped`, `🚧 2 in progress`, `📋 3 planned`, `💭 8 considered`. |
| 4  | render | Theme glyphs in section headings (`🎨` etc.) MUST NOT be wrapped with a label — the heading text already labels them; double-labelling is noise. |
| 5  | a11y  | The five filter QCheckBoxes MUST have `setAccessibleName()` called with the form "Show {state} items" — Orca speaks the accessibleName when set and skips the visible label. The visible `tr("✅ Done")` is renamed to `tr("✅ Shipped")` for vocabulary consistency with the rest of the roadmap-format standards (§3.d). |
| 6  | render | `.rm-state-label` CSS rule MUST use the theme's muted-text colour (the same `%6` placeholder as `.rm-id` / `.rm-date`) so the label inherits theme palette on every theme change. |
| 7  | a11y  | Plain-text extraction from the rendered HTML (`QTextDocument::toPlainText()`) MUST contain the four label words in document order. (This is the behavioural backstop — if a future refactor accidentally drops the spans, this fires.) |

## 5. Test plan

`tests/features/roadmap_dialog_cards/test_roadmap_dialog_cards.cpp`
gains an ANTS-1235 block, modelled on the existing INV-17 block.
Each invariant gets a direct assertion:

1. **Card emission** — render a synthetic ROADMAP with one
   `✅`, one `🚧`, one `📋`, one `💭` bullet. Assert each card's
   HTML contains the matching `<span class="rm-state-label">{Label}</span>`
   immediately after the matching `<span class="rm-state">`.
2. **Section counts** — render with mixed status counts in one
   section. Assert the section-counts span text contains
   "shipped", "in progress", "planned", "considered" with the
   correct numerics.
3. **Theme glyphs NOT labelled** — assert the rendered HTML does
   NOT contain `<span class="rm-state-label">` adjacent to a theme
   emoji in a section heading.
4. **Plain-text projection** — load the rendered HTML into a
   `QTextDocument`, call `toPlainText()`, assert all four label
   words appear in document order with the same counts as the
   cards.
5. **Filter checkbox accessibleNames** — checked via a separate
   short test (or extended into the existing
   `tests/features/roadmap_dialog_cards` runner) that constructs
   the QCheckBoxes and asserts `accessibleName()` returns the
   expected string. **Caveat:** the existing
   `roadmap_dialog_cards` test is renderer-only (no QDialog
   instantiation). If the QCheckBox test would require pulling in
   QApplication + the full RoadmapDialog ctor, it lives in a new
   `tests/features/roadmap_dialog_a11y_filter_names/` directory
   instead (decision deferred to implementation).
6. **Source grep** — assert the CSS rule `.rm-state-label` is
   present in `renderCardsHtml`. Locks the CSS in place.

Pre-fix verification per testing standard: revert the
`<span class="rm-state-label">` emission, confirm tests 1, 2, 4, 6
fail; restore.

Build cost: zero new targets, single test file gains ~70 lines.

## 6. Memory budget

Per-card HTML cost: ~48 characters of additional markup —
`<span class="rm-state-label">in progress</span>` is 47 chars
(29 for the opening tag, 11 for the longest label, 7 for the
closing tag). At ~500 cards, that's ~24 KB additional HTML in
the QTextBrowser document. Negligible against the existing
~280 KB document size for a fully rendered ROADMAP.md.

CSS cost: ~80 characters in the `<style>` block, one-shot.

Code cost — roughly tallied:

- §3.a `kStatusLabels` table + `static_assert` + `statusAccessibleLabel` helper: ~12 LoC.
- §3.b per-card emission: 4 LoC.
- §3.c chip rewrite + `chop(3)` separator strip: 6 LoC net (replaces 4 existing lines).
- §3.d five `setAccessibleName` setters: 5 LoC.
- §3.d visible `tr("✅ Done")` → `tr("✅ Shipped")` rename: 0 LoC net.
- §3.e CSS rules (one new, one augmentation): 2 LoC.

Total ~29 LoC of additive code in `src/roadmapdialog.cpp`. No new
files, no new translation units, no new build deps.

Runtime cost: a four-way `if` chain per card during rendering;
indistinguishable from noise next to the existing renderer
arithmetic.

## 8. Re-open conditions

- **Orca / NVDA changes default emoji pronunciation** to something
  like "Shipped check mark" out of the box. Re-open to re-evaluate
  whether the visible labels are still needed; possibly drop them
  if the AT layer handles it.
- **Qt 6.X adds per-fragment accessible-name support in
  QTextCharFormat.** Re-open to evaluate replacing visible labels
  with metadata, which would let the visible UI stay terser.
- **User reports the visible labels are too noisy.** Re-open to
  consider a settings toggle ("Show status labels" — defaults on
  for a11y-enabled environments, defaults off otherwise, detected
  via `QAccessible::isActive()`).
- **A future ROADMAP item adds a fifth status emoji** without an
  updated `statusAccessibleLabel` entry. Caught by the
  static_assert in INV-2; the failure surface is compile-time,
  but if it's hand-edited around, the runtime test fails too.

## 9. Out of scope

- Theme-glyph labelling (decorative; heading text labels them).
- Custom emoji-pronunciation rules for Orca. That's per-user
  config and outside the application's reach.
- Producing actual translation files (`.ts` / `.qm`) for the four
  status labels and the five filter `setAccessibleName` strings.
  The strings are wrapped in `tr()` / `QT_TR_NOOP` per §3.a so
  `lupdate` extracts them when a future translation pass arrives;
  no translation files exist in the repo today.
- Audio cue / chime per status. Out of scope for a roadmap viewer.
- The `aria-label`-on-spans mechanism described in the ROADMAP
  entry (§2.a — rejected after verification).
