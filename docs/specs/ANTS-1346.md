# ANTS-1346 — `roadmap_query` section cache LRU eviction

**Status:** spec, ship-ready after cold-eyes pass.
**Source:** indie-review-2026-05-14 (lane-5 ME-1).

## 1. Problem

`m_roadmapSectionCache` at `remotecontrol.h:380` is a
`QHash<QString, QJsonArray>` keyed on section slug. It is only
wiped when the ROADMAP's mtime advances (`remotecontrol.cpp:801`).

On a stable ROADMAP across a long-lived session, the cache grows
**monotonically up to the heading count** as the assistant queries
each section once. Measured 2026-05-15:

```
$ grep -cE "^##+ " ROADMAP.md   # 177 heading lines (H2 + H3 + H4)
$ grep -cE "^- "   ROADMAP.md   # 627 top-level bullets
```

The bound is implicitly the heading count, but **(a)** the count
isn't fixed at write-time — the ROADMAP grows continuously, and
already crosses 175; **(b)** `sliceSection` returns whatever lies
between two headings — on a malformed / un-anchored ROADMAP the
slice could be hundreds of KB per slug.

## 2. Design

Per-slug LRU eviction at 64 entries.

```cpp
mutable QHash<QString, QJsonArray> m_roadmapSectionCache;
mutable QList<QString>             m_roadmapSectionLru;   // MRU front
static constexpr int               kRoadmapSectionCacheCap = 64;
```

Read path (`remotecontrol.cpp:861`):

```cpp
if (m_roadmapSectionCache.contains(sec->slug)) {
    sectionBullets = m_roadmapSectionCache.value(sec->slug);
    // bump MRU
    m_roadmapSectionLru.removeOne(sec->slug);
    m_roadmapSectionLru.prepend(sec->slug);
}
```

Insert path (`remotecontrol.cpp:890`):

```cpp
m_roadmapSectionCache.insert(sec->slug, sectionBullets);
m_roadmapSectionLru.removeOne(sec->slug);   // no-op on first insert
m_roadmapSectionLru.prepend(sec->slug);
while (m_roadmapSectionLru.size() > kRoadmapSectionCacheCap) {
    const QString evicted = m_roadmapSectionLru.takeLast();
    m_roadmapSectionCache.remove(evicted);
}
```

mtime-stale wipe (`remotecontrol.cpp:801`) clears both:

```cpp
m_roadmapSectionCache.clear();
m_roadmapSectionLru.clear();
```

## 3. Invariants

- **INV-1** `m_roadmapSectionCache.size() ≤ 64` after any insert.
- **INV-2** `m_roadmapSectionLru.size() == m_roadmapSectionCache.size()`
  at every observable point.
- **INV-3** `m_roadmapSectionLru.first()` is the most-recently-accessed
  slug (either inserted or hit).
- **INV-4** On mtime-stale wipe, BOTH the section cache and its LRU
  list are cleared in the same statement block as the existing
  `m_roadmapIndex.clear()` at `remotecontrol.cpp:800` — three clears,
  one transition.
- **INV-5** Cap value (64) is `static constexpr`, not a magic number
  in the body.
- **INV-6** The hit-path bump (`removeOne` + `prepend`) is a mutation
  on what was previously a `value()`-only read path. The members
  involved (`m_roadmapSectionCache`, `m_roadmapSectionLru`) are
  already declared `mutable` in the header to match the existing
  cache fields' const-method usage pattern.

## 4. RAM budget

Per-entry cost dominated by the cached `QJsonArray` of parsed bullets.
Measured 2026-05-15 against the live ROADMAP (627 bullets across
177 headings):

- Mean per-section bullet count: 627 / 177 ≈ **3.5 bullets/section**.
- Largest sections (release blocks like `## 0.7.x — shipped`) hold up
  to ~30 bullets in practice; at ~150 B/bullet compact-JSON ≈ **4.5 KB**.
- Median section: ~5 bullets ≈ **750 B**.

64-entry cap → worst-case **~288 KB** if every cached section is at
the upper-30-bullet bound; realistic working-set RAM is well under
**50 KB**. Below the 100 KiB cap on `session_memory` × 4 stores, and
two orders of magnitude below the scrollback default.

Heading-count vs cap: with 177 headings against a 64-slug cap, a
session that queries every distinct section over its lifetime
**will** hit LRU eviction. That's intentional: the cap protects
against a pathological growth case (long-lived session sweeping
the whole ROADMAP); in normal use the assistant's working set is a
handful of currently-active sections that fit far below the cap,
and the mtime wipe (fires on any ROADMAP edit) drops the whole
cache so eviction churn only matters between ROADMAP edits with
sustained whole-ROADMAP query traffic — uncommon but bounded.

## 5. Test surface

`tests/features/roadmap_section_cache_lru/` with a **synthetic
fixture** ROADMAP file (not the project's live ROADMAP — deterministic
heading set is required for the eviction-ordering assertions):

```
# Test ROADMAP fixture
## SectionA
- 📋 [TST-0001] **First.** Kind: test. Source: fixture.
## SectionB
- 📋 [TST-0002] **Second.** Kind: test. Source: fixture.
## … (65 sections total, slugs section-a..section-z + section-aa..)
```

Tests:
1. **CapNotExceeded** — call `cmdRoadmapQuery` with 65 distinct
   section slugs against the synthetic ROADMAP. Inspect cache size:
   ≤ 64.
2. **OldestEvicted** — call section A, B, ..., A again (bumps A);
   then call section past-cap. Expect B (not A) evicted.
3. **MtimeWipeClearsLru** — touch the fixture ROADMAP mtime forward
   (re-write with a different timestamp); next call wipes all three
   structures. Verify `m_roadmapSectionLru.isEmpty()` after.

Inspector accessors (test-only header section, `mutable` already):
- `int sectionCacheSizeForTest() const`
- `QStringList sectionLruForTest() const`

## 6. Build cost

- ~10 LOC `remotecontrol.h` (1 member, 1 constant, 2 inspectors).
- ~15 LOC `remotecontrol.cpp` (hit-path bump + insert-path eviction +
  wipe path).
- Test target ~80 LOC C++.

## 7. Out of scope

- No byte-cap on individual entries. A malformed ROADMAP slice still
  loads in full; the slug count cap bounds the explosion. A per-slug
  byte cap is a follow-up if a real malformed ROADMAP ever surfaces.
- The full-ROADMAP `m_roadmapCacheBullets` is single-valued, not
  multi-keyed, so it doesn't need LRU.
