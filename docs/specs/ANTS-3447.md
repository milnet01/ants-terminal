# ANTS-3447 — `feedback_log op:"assign_id"`: v2 inline triage write

**Status:** Reviewed (2026-07-05) — cold-eyes clean (2 loops; loop 2 = 0C/0H,
polish-converged); ready for implementation
**Kind:** enhancement
**Source:** in-session-2026-07-05 (v2 feedback-file redesign; the triage-write
verb that replaces `op:append_tracking` for v2 files — fills the
`**Proposed ID:**` slot `migrate_v2` (ANTS-3446) stamps)

## 1. Problem

Under the v2 feedback-file format (docs/standards/mcp-feedback-files.md), triage
is recorded **inline**: the maintainer writes a finding's assigned `ANTS-NNNN`
(or an `n/a — <reason>` closure) into that finding's own `**Proposed ID:**` line,
and status is derived live from `ROADMAP.md`. There is no tracking table.

`migrate_v2` stamps a **blank** `- **Proposed ID:** _(maintainer to assign)_`
placeholder on each un-triaged finding; `compact_resolved` collapses a finding
once its id ships. The missing middle step is the **write that fills the
placeholder** — today the only working triage-write op is `append_tracking`,
which appends a v1 *table* (the very thing v2 removes). `assign_id` is the v2
replacement: it edits **one finding's `**Proposed ID:**` line in place**.

## 2. Surface

`feedback_log op:"assign_id"` (maintainer). Same split as the sibling
`feedback_log` ops:

- **Pure helper** `FeedbackFile::assignId(content, target)` (ants_core_lib,
  Qt6::Core-only) locates the finding, writes/inserts its id line over a string,
  and returns the new content + a structured outcome. No roadmap, no filesystem,
  no MainWindow — fully unit-testable over synthetic content (same posture as
  `compactResolved` / `migrateV2`).
- **Wrapper** `cmdFeedbackLog` (remotecontrol.cpp) does path resolution, the
  `*_Ants_MCP_Feedback.md` suffix guard, PathValidation, the `caller_cwd`
  contract, `dry_run`, and the atomic `QSaveFile` write — identical plumbing to
  `compact_resolved`/`migrate_v2`, **minus** the roadmap read (`assign_id` never
  consults the roadmap; it only records the id the maintainer supplies).

### 2.1 Request shape

| field | req? | meaning |
|---|---|---|
| `caller_cwd` | yes | resolves the feedback file (path derivation, ANTS-3376) |
| `op` | yes | `"assign_id"` |
| `heading` | yes | the target `### ` finding's **full heading line verbatim, including the `### ` prefix** — matched (trimmed) against `FindingBlock::heading`, which is the whole heading line (§2.2 step 1) |
| `heading_line` | no | 1-based line of the `### ` heading — disambiguates a repeated heading |
| `ids` | no* | array of `ANTS-NNNN` to assign (rendered comma-joined) |
| `closure` | no* | a closure reason string → writes `n/a — <closure>` (empty string → bare `n/a`) |
| `path` | no | feedback-file path; omit to derive `<leaf>_Ants_MCP_Feedback.md`, echoed `path_derived` |
| `dry_run` | no | preview the outcome without writing (default false) |

**\*The assign-vs-close predicate is an exclusive-or over two explicit booleans,
so the JSON is unambiguous:**

- `hasIds` ≝ the `ids` key is present **and** its array is non-empty.
- `hasClosure` ≝ the `closure` key is present **with a string value** (any
  string, including `""`). A non-string `closure` (e.g. JSON `null`) counts as
  absent.
- The request is valid iff `hasIds XOR hasClosure`. An **empty** `ids:[]`
  counts as *absent* (`hasIds` false) — so `ids:[]` alongside `closure` is a
  valid **closure**, not a "both supplied" refusal. `!hasIds && !hasClosure`
  (neither) and `hasIds && hasClosure` (a real id array *and* a closure key)
  are each `bad_args`.

A finding is either assigned or closed, not both — the v1 idiom
`n/a — folded into ANTS-1525` is a *closure* that happens to name an id, written
via `closure` (not `ids`), so it takes the `hasClosure` branch.

### 2.2 What assign_id does

1. **Locate the finding.** Enumerate every `### ` block with the shared
   fence-aware `enumerateFindingBlocks` (ANTS-3443) and resolve `heading`
   (+ optional `heading_line`) to exactly one block, **inheriting
   `compact_shipped`'s heading-resolution gate pattern** (ANTS-3421 § 2.3):
   `heading_line` pins a repeated heading; a bare `heading` matching **> 1**
   block is `target_ambiguous` (with a `candidates[]` list of the colliding
   1-based `### ` heading lines); **0** matches is `target_not_found`. The match
   is over `### ` sub-headings (via the enumerator), **not** the `#`/`## `
   boundaries `compact_shipped` resolves — so the *gate shape* is inherited, the
   *heading universe* is v2's `### ` findings.
2. **Compose the id-line value.**
   - `ids` non-empty → `<id1>, <id2>, …` (comma-space join, request order,
     de-duplicated keeping first occurrence), each validated `^ANTS-[0-9]+$` by
     the wrapper (`bad_args` otherwise).
   - `closure` present → `n/a — <closure>` when the reason is non-empty, else the
     bare `n/a`. The written value begins `n/a`, so the standard's closure rule
     (matched `n/a\b` against the already-trimmed value) reads it as a closure —
     excluded from the assigned-id union and never compacted (§"Maintainer
     triage"). **The wrapper folds any newline / control char in `closure` to a
     single space before composing the value** (the sibling write-verbs' scrub
     idiom), so a `closure:"foo\nbar"` cannot inject a second line and break the
     one-line-per-write invariant (INV-3). `ids` need no such guard — the
     `^ANTS-[0-9]+$` validation already rejects any control char.
3. **Write the line.** The canonical form is
   `- **Proposed ID:** <value>` (byte-identical prefix to `renderFindingBlock`'s
   placeholder, so the enumerator + `compact_resolved` recognise it):
   - the block **has** a `**Proposed ID:**` line (`idLine0 >= 0`, incl. the
     `_(maintainer to assign)_` placeholder or an existing id) → **replace that
     whole line** with the canonical form (normalising bullet marker / spacing).
     Only the **first** id line is touched (the enumerator's first-line-wins);
     any stray second `**Proposed ID:**` line in the body is left as-is (a
     malformed finding the maintainer can hand-fix — not this op's concern).
   - the block has **no** id line (`idLine0 < 0`) → **insert** the canonical line
     as the finding's first body bullet: directly under the heading, or after a
     single blank line that follows it (the same insertion rule as `migrate_v2`
     § 2.2 pass 2, preserving heading → blank → bullets). Unlike `migrate_v2`,
     `assign_id` applies **no** finding-shaped gate — the maintainer explicitly
     named this `### ` block, and that intent overrides the heuristic. This is
     reachable when the maintainer assigns on a still-un-migrated file, or on a
     finding `migrate_v2` left line-less and surfaced in its `orphans[]` /
     `unclassified[]` report (ANTS-3446 § 2.6) — assign_id is how the maintainer
     resolves those.

Nothing else changes — no other finding, no tracking table, no marker. The write
is a single line replaced or inserted.

### 2.3 No version gate, no marker bump

`assign_id` does **not** gate on the file version and does **not** touch the
`<!-- ants-mcp-feedback: N -->` marker. An inline `**Proposed ID:**` line is
valid in a file of either format, and requiring `migrate_v2` first would be an
unnecessary round-trip. The interaction to understand: under today's
**marker-blind** delta reader (`feedback_query` / `session_orient
feedback_pending` call `parse()` unconditionally — the v1 rule; ANTS-3446 § 1.1),
an assigned id **removes the finding from the un-triaged delta only under the
future v2 (marker-honoring) reader**; on a still-`: 1` file the v1 rule keys off
the tracking-table watermark, not the inline id, so the finding's delta
membership is unchanged until the file is migrated. `assign_id` records the
maintainer's decision immediately regardless; the delta bookkeeping catches up
when the file is `: 2` **and** the v2 reader ships. (`migrate_v2` is the marker
bump; the v2 delta rule is a separate pending change — §5.)

### 2.4 Response envelope

```
{ ok, op:"assign_id", path, dry_run,
  heading,               // the resolved `### ` heading, verbatim
  line,                  // 1-based `### ` heading line in the ORIGINAL file
  value,                 // the composed id-line value written (e.g. "ANTS-1525" or "n/a — folded")
  inserted,              // true ⟹ the finding had no id line (inserted); false ⟹ replaced
  changed,               // false ⟹ the line already held `value` (byte-identical no-op)
  bytes_delta,           // signed size change
  path_derived }         // true when `path` omitted + derived
```

`line` is an **input coordinate** (the heading line in the *original* file).
`inserted` and `changed` describe **this call**, not the file's end-state: on the
insert path `inserted:true ⟹ changed:true` (a new line always adds bytes); a
re-run of the same assign on that finding then takes the replace path with
`inserted:false, changed:false` (the byte-identical no-op, §2.5). On a refusal the
envelope is the standard `{ok:false, code, error}` (+ `candidates[]` for
`target_ambiguous`).

Wrapper/helper refusals:

- `target_not_found` — no `### ` block matches `heading` (or `heading_line` is
  not a `### ` heading / disagrees with `heading`).
- `target_ambiguous` — a bare `heading` matches > 1 `### ` block;
  `candidates[]` lists the colliding 1-based heading lines (pass `heading_line`).
- `bad_args` — the `hasIds XOR hasClosure` predicate fails (neither, or a
  non-empty `ids` **and** a `closure` key — §2.1); an empty `heading`; an `ids`
  entry not matching `^ANTS-[0-9]+$`. (A wholly-absent required scalar may instead
  be `missing_field` per the `feedback_log` convention — INV-9.)
- `not_feedback_file` (suffix guard), `not_found` (absent file), `read_failed`
  (present but unopenable) precede any work; `write_failed` fires after the
  transform on a failed non-dry-run commit. All inherited from the sibling
  wrappers (remotecontrol.cpp). No `not_v2` (§2.3), no roadmap read.

### 2.5 Idempotency

Assigning a value a finding already holds **in canonical form** is a **clean
no-op**: the composed canonical line equals `lines[idLine0]` → `changed:false`,
`bytes_delta:0`, file byte-identical. A finding whose existing line holds the
same id in a *non-canonical* seed (`* **Proposed ID**: ANTS-1525`) is instead
normalised on the first assign (`changed:true`, small `bytes_delta`); a **second**
assign with the same value is then the byte-identical no-op — so `assign_id`
always converges in ≤ 1 write per value. Re-assigning a **different** id is an
intentional correction (`changed:true`), not blocked.

### 2.6 Worked example

Fill the placeholder `migrate_v2` stamped on `### Issue #1`:

```markdown
### Issue #1 — verify_changes timed out
- **Proposed ID:** _(maintainer to assign)_
- **What:** hangs on a cold cache.
```

`assign_id {heading:"### Issue #1 — verify_changes timed out", ids:["ANTS-1525"]}`
→

```markdown
### Issue #1 — verify_changes timed out
- **Proposed ID:** ANTS-1525
- **What:** hangs on a cold cache.
```

Envelope: `{heading:"### Issue #1 …", line:<n>, value:"ANTS-1525",
inserted:false, changed:true, bytes_delta:-15}` (the 24-char placeholder
`_(maintainer to assign)_` → the 9-char `ANTS-1525`). A closure instead —
`assign_id {heading:"### Issue #4 …", closure:"folded into ANTS-1525"}` — writes
`- **Proposed ID:** n/a — folded into ANTS-1525`, which reads as a closure.

## 3. Invariants

- **INV-1** — `op:"assign_id"` is dispatched inside `cmdFeedbackLog`'s op switch
  (beside `migrate_v2`), added to the valid-op guard (else `bad_mode`), **and
  enumerated in the `feedback_log` input schema's `op` enum**
  (`claudeintegration.cpp`) — an un-enumerated op is schema-rejected / not
  advertised. The pure helper is m_main-independent (source-grep); the wrapper
  alone touches the filesystem and never reads the roadmap.
- **INV-2** — exactly one `### ` finding is affected: the one `heading`
  (+ optional `heading_line`) resolves to. Its `**Proposed ID:**` line is
  replaced (when present) or inserted (when absent, as the first body bullet).
  No other line — heading, other findings, tables, marker — changes. The
  envelope's `line` is that finding's 1-based `### ` heading line in the
  *original* file (an input coordinate, unaffected by a same-run insert).
- **INV-3** — the written line is exactly `- **Proposed ID:** <value>`, where
  `<value>` is the comma-joined `ids` **or** `n/a`/`n/a — <closure>`. The prefix
  is byte-identical to `renderFindingBlock`'s, so `enumerateFindingBlocks`
  reports the block's `idLine0 >= 0` with the new `idValue` after the write.
- **INV-4** — resolution mirrors `compact_shipped` (ANTS-3421 § 2.3) over the
  `### ` enumerator: 0 matches → `target_not_found`; > 1 (bare heading) →
  `target_ambiguous` + `candidates[]`; `heading_line` disambiguates and must name
  a `### ` heading equal to `heading`.
- **INV-5** — request validation: `hasIds XOR hasClosure` (else `bad_args`),
  where `hasIds` = `ids` present and non-empty and `hasClosure` = `closure` key
  present (§2.1); every `ids` entry matches `^ANTS-[0-9]+$`; a closure value
  begins `n/a` so the standard's closure rule excludes it from the assigned-id
  union; any newline / control char in `closure` is folded to a space so the
  written line stays single-line (INV-3).
- **INV-6** — idempotent: re-running with the same `ids`/`closure` is a
  byte-identical no-op (`changed:false`, `bytes_delta:0`), because the first run
  wrote the canonical form (§2.5).
- **INV-7** — `dry_run:true` returns the identical envelope (minus the write) and
  leaves the file byte-for-byte unchanged.
- **INV-8** — atomic write via `QSaveFile … .commit()` (source-grep) — performed
  **only** on a non-dry-run call that actually changes a byte (`changed:true`).
  A `changed:false` no-op (§2.5) skips the commit, so it never bumps the file
  mtime (which would needlessly invalidate the `feedback_query` ETag).
- **INV-9** — refusal precedence: the wrapper checks `not_feedback_file` (suffix
  guard) then `not_found` (absent file) then `read_failed` **first**; the
  request-shape `bad_args` (empty `heading`, the `hasIds XOR hasClosure`
  violation, a malformed `ids` entry) and `target_not_found` / `target_ambiguous`
  are checked **after** the file opens but **before** the transform; `write_failed`
  fires post-transform on a failed commit. A *wholly-absent* required scalar may
  be reported as `missing_field` (the `feedback_log` field-guard convention,
  mcp-error-codes.md) — a present-but-empty `heading` is `bad_args`. No `not_v2`,
  no `roadmap_unavailable` (no roadmap read). `path_derived:true` is echoed iff
  `path` was omitted and the conventional name derived (§2.1, ANTS-3376).
- **INV-10** — fenced regions are inert: a `### `/`**Proposed ID:**` line inside
  a ``` fence is neither a resolution target nor the line written, because both
  the enumeration and the id-line location run through the fence-aware
  `enumerateFindingBlocks`.
- **INV-11** — `assign_id` does **not** bump or read the version marker (§2.3);
  the file's format version is unchanged by the op.

## 4. RAM / build cost

One extra pure function in `ants_core_lib`. One O(lines) scan
(`enumerateFindingBlocks`) plus one line replace/insert and a `join`. No roadmap
read, no new build target, no new allocation class (the file is transient).

## 5. Out of scope

- **Batch assignment** (`assignments[]` in one call) — the first cut assigns
  **one** finding per call (the standard's "fill one finding's slot"). A batch
  variant (parity with `compact_shipped`'s `targets[]`) is a deferred sibling;
  add it only if triage round-trips prove costly.
- **Reading / resolving ROADMAP.md** — `assign_id` records the id the maintainer
  supplies; it never checks the id exists or its status (that is
  `feedback_query`'s live resolution and `compact_resolved`'s ✅ gate).
- **The v2 (marker-honoring) delta rule** in `feedback_query` /
  `session_orient feedback_pending` — the read-side change that makes an
  assigned id remove a finding from the un-triaged delta (§2.3). Its own change.
- **Deprecating / removing `op:append_tracking`** — it stays the v1 triage-write
  op for un-migrated files; `assign_id` is the v2 path. The standard's §"Tooling"
  row already marks `append_tracking` "deprecated once `assign_id` ships"; the
  actual deprecation (a refusal / warning) is a follow-up, not this spec.

## 6. Tests

Feature-conformance `tests/features/feedback_log_assign_id/`: `spec.md` +
`test_feedback_log_assign_id.cpp` (pure `assignId` over synthetic content +
a live `cmdFeedbackLog` drive + schema/dispatch source-greps). Cases cover
INV-1…INV-11:

- **fill placeholder** (§2.6 / INV-2/3): a `_(maintainer to assign)_` line is
  replaced by `- **Proposed ID:** ANTS-1525`; `inserted:false`, `changed:true`,
  `bytes_delta:-15`, `line` = the finding's 1-based heading line, the rest of the
  finding + siblings byte-identical.
- **multi-id** (INV-3): `ids:["ANTS-1525","ANTS-1526"]` →
  `- **Proposed ID:** ANTS-1525, ANTS-1526`.
- **closure** (INV-3/5): `closure:"folded into ANTS-1525"` →
  `- **Proposed ID:** n/a — folded into ANTS-1525`; the enumerator's `idValue`
  begins `n/a`; an empty `closure:""` → bare `- **Proposed ID:** n/a`.
- **insert when absent** (INV-2): a legacy `### ` finding with no id line gets
  the canonical line inserted as the first body bullet (`inserted:true`);
  blank-first heading → inserted after the blank.
- **replace existing id** (INV-2): a finding already carrying
  `- **Proposed ID:** ANTS-1000` is rewritten to the new id (`changed:true`).
- **idempotency** (INV-6): re-assigning the same `ids` → `changed:false`,
  `bytes_delta:0`, byte-identical.
- **ambiguous heading** (INV-4): two `### ` blocks with the same heading and no
  `heading_line` → `target_ambiguous` + `candidates[]` (both 1-based lines);
  passing `heading_line` resolves to the intended one.
- **not found** (INV-4): a heading that matches no `### ` block →
  `target_not_found`; a `heading_line` that is not a `### ` heading →
  `target_not_found`.
- **bad_args** (INV-5): neither `ids` nor `closure`; a **non-empty** `ids` array
  **and** a `closure` key (both); an `ids` entry not matching `^ANTS-[0-9]+$`; an
  empty `heading`.
- **empty-ids-plus-closure is a valid closure** (INV-5 / §2.1): `ids:[]` +
  `closure:"folded"` is **not** `bad_args` — it writes the closure (empty `ids`
  counts as absent, so `hasClosure` alone holds).
- **closure newline folded** (INV-3/5): `closure:"foo\nbar"` writes a single
  `- **Proposed ID:** n/a — foo bar` line (the newline folded to a space) — the
  finding gains no spurious second line.
- **line coordinate** (INV-2): the envelope `line` equals the target `### `
  heading's 1-based line in the original file, unchanged by an insert on an
  earlier finding.
- **fence safety** (INV-10): a `### `/`**Proposed ID:**` line inside a ``` fence
  is not a target and is never written.
- **no marker change** (INV-11): the `<!-- ants-mcp-feedback: N -->` marker is
  byte-identical after an assign on a `: 1` file and on a `: 2` file.
- **wrapper** (INV-7/8/9): `dry_run` leaves the file unchanged; a `changed:false`
  no-op skips the write (mtime unchanged); `not_found` on an absent file;
  `path_derived:true` when `path` is omitted (derived name); a real write
  persists the line; the schema `op` enum lists `assign_id`; `cmdFeedbackLog`
  routes it to `FeedbackFile::assignId`. (The `not_feedback_file` / `read_failed`
  / `write_failed` refusals are exercised by the sibling-wrapper tests — same
  `resolveFeedbackPath` / `QSaveFile` plumbing.)
