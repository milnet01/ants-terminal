# ANTS-1893 — Switch-event surfacing: toast + chip-pulse + Undo

**Status:** accepted (2026-05-28). Cold-eyes loops 1+2+3+4+5+6+7
folded; user gated stop at loop 7 with remaining clarifications
deferred to implementation time.
**Kind:** implement.
**Source:** ROADMAP.md ANTS-1893 (in-session-2026-05-26 — surfaced from
ANTS-1891 brainstorm; sharpened by ANTS-1894 once near-miss telemetry
made the firing-side opacity the next gap to close).

**Layman:** When Ants auto-switches the Claude model, a small message
slides into the status bar telling you what happened ("Ants switched:
Opus → Haiku — mechanical") and gives you a one-click "Undo" button
for ~10 seconds. The current model chip in the status bar also pulses
once so peripheral vision catches the event. Right now the switch is
silent — the only evidence is a ledger record and the next assistant
turn happening on the new tier.

**Pairs with:** ANTS-1894 (near-miss telemetry — once visibility
lands on both the firing AND blocked sides, the user has the
full picture of what the switcher is doing this session);
ANTS-1890 override cool-down (Undo seeds the in-memory cool-down
cache so the switcher's 10-min lock-out trips immediately, NOT
the ledger's `userOverrideWithin5` outcome field — see § 6 for
the precise contract). **Composes with:** ANTS-1735 §2.3 firing
path (the `sendToPty` injection at `claudestatuswidgets.cpp:1429`)
and ANTS-1888 per-tab model chip (the pulse animates
`m_modelStateBtn`). **Blocker for:** ANTS-1895 dry-run UX (the
dry-run mode reuses the toast/chip-pulse surface to say "Ants
would have switched … (preview only)").

## 1. Problem

The auto-switcher's actuator path (`claudestatuswidgets.cpp:1429`)
fires `/model <tier>\n` into the focused PTY with no UI signal. The
ANTS-1888 chip (`m_modelStateBtn`) updates passively on the next
transcript-mtime tick — typically 2–10 s later, by which time the
user has already typed past the switch. Three observable failures:

1. **Invisible firings.** A user looking at the screen at switch time
   sees no event; the chip's relabel from "Opus" to "Haiku" happens
   silently on the next tick. The user-reported phrasing — *"I
   haven't seen it change once since the implementation"* — captured
   2026-05-26 reflects both no-records-this-project AND the deeper
   gap that even when a switch DID fire (the global ledger has two
   records), the user never noticed.

2. **No reversal affordance.** When the switcher gets it wrong
   (e.g. fires Opus → Haiku just as the user starts a refactor that
   needs Opus), the user has to: (a) notice the chip changed, (b)
   open the Claude `/model` prompt manually, (c) type the correct
   tier. Three clicks + recall, vs. one click for the corrected
   action. The friction discourages users from leaving the switcher
   ON, which is exactly the trust loop ANTS-1891 §1 was designed to
   close.

3. **No reason surfaced.** The score_reason ledger field
   (`mechanical` / `commit_intent` / `plan_keyword` / `long_prompts`)
   never reaches the user. A switch that *looks* wrong might be
   defensible once the user sees "Ants switched to Haiku because
   your last 5 prompts mentioned `commit`" — but the rationale is
   buried in the ledger.

Three surfaces — toast (announce), chip-pulse (peripheral catch),
Undo button (one-click reversal) — close these three gaps with the
minimum new UI. Each surface is independently muteable so a power
user who finds the toast noisy can keep just the chip-pulse, and
vice versa.

## 2. Surface

Four concerns. Pure controller-side wiring — no new MCP tools, no
new config files; one new persisted bool, two new code constants,
one new status-bar widget.

### 2.3 Chip-pulse — `m_modelStateBtn` accent border for 600 ms

The ANTS-1888 chip (`m_modelStateBtn` —
`claudestatuswidgets.h:268`) is a `QPushButton` with
`setFlat(true)`. To pulse it on a switch:

1. Set a dynamic Qt property `pulse=true` on `m_modelStateBtn`.
2. Force a `style()->unpolish(btn); style()->polish(btn);` repolish
   so the QSS rule below picks up the property.
3. Start a `m_modelStatePulseTimer` (owned `QTimer*`, single-shot,
   `kModelChipPulseMs = 600`); on timeout, clear `pulse=false` +
   repolish.
4. If a second pulse arrives within the 600 ms window: restart the
   timer (extending the pulse) but DO NOT re-emit. The timer is
   single-shot per pulse, owned by the controller.

**Stylesheet delivery — programmatic, NOT `themes/*.qss`.** The
project has no `themes/` directory; the application stylesheet is
built programmatically by
`themedstylesheet::buildAppStylesheet(const Theme &)`
(`src/themedstylesheet.cpp:13`), which returns a single
parameterised `QString` consumed by MainWindow's theme-apply path
(MainWindow calls into it on every theme change). The pulse rule
is appended to that returned string. The `%5` placeholder in
`buildAppStylesheet` is `theme.accent.name()`
(`src/themedstylesheet.cpp:215`) — bind the pulse border to that
slot so the accent follows the active theme. Verbatim rule
fragment to append inside `buildAppStylesheet`, immediately AFTER
the `QPushButton:disabled` rule at `src/themedstylesheet.cpp:149`
and BEFORE the `QLineEdit` block at L150:

```cpp
"QPushButton#claudeModelStateBtn[pulse=\"true\"],"
"QPushButton#claudeModelStateBtn[pulse=\"true\"]:hover:enabled,"
"QPushButton#claudeModelStateBtn[pulse=\"true\"]:pressed:enabled {"
"  background-color: %1;"
"  color: %3;"
"  border: 1px solid %5;"
"  padding: 6px 14px;"
"  border-radius: 4px; }"
```

The `[pulse="true"]` selector reads the dynamic property; Qt's
QSS engine matches dynamic properties iff `unpolish + polish`
is called after the property change (Qt docs:
https://doc.qt.io/qt-6/stylesheet-syntax.html#qt-style-sheets-and-properties).
`%5` resolves to the theme's `accent` colour at apply time —
no hard-coded colour, no per-theme override needed.

**No text-shift on pulse — same border width before/after.**
The generic `QPushButton` rule at
`src/themedstylesheet.cpp:135-136` already carries
`border: 1px solid %4;` — so the un-pulsed chip ALREADY has a
1 px border (in colour `%4`, the muted "border" role). The
pulse rule changes only the border COLOUR (`%4` → `%5`, the
accent role) and pins the base padding (`6px 14px`, identical
to the generic rule). Border WIDTH is unchanged, so the
chip's interior box is bit-for-bit identical between pulsed
and un-pulsed states; no text twitch on engage/disengage.

**Triple-selector ordering — hover/pressed overlay.** The
pulse rule sets `background-color`/`color`/`border` for ALL
three states (base, hover, pressed) so the generic
`:hover:enabled` rule at L146 (which sets background/color/border
to the accent fill) does NOT win over the pulse during the
600 ms window. **By design, the normal hover styling (accent
fill) is SUPPRESSED on the chip while pulse is active** —
the pulse border is the dominant visual signal for the 600 ms
window, and competing with the hover fill would dilute it.
A user hovering during the window sees: base background (%1) +
text colour (%3) + pulse border (%5). Once pulse expires
(property cleared), the generic `:hover:enabled` rule resumes
governing hover appearance. QSS selector specificity:
attribute selectors contribute the same weight as
pseudo-classes, so `[pulse="true"]:hover:enabled` (one attr +
two pseudo) ties the generic `:hover:enabled` (one pseudo) —
and our rule wins by source-order (later in the cascade per
Qt's QSS implementation).

**`setFlat(true)` + `:default` interactions.**
`setFlat(true)` on the chip (`claudestatuswidgets.cpp:183`)
does NOT alter QSS application — Qt 6 still cascades
stylesheet rules to flat buttons; the flat flag only affects
native-style rendering when no QSS applies.
The generic `QPushButton:default { border: 1px solid %5; }`
rule (`src/themedstylesheet.cpp:148`) only applies to a
dialog's default button (Enter-key target). `m_modelStateBtn`
is constructed with `setFocusPolicy(Qt::NoFocus)`
(`claudestatuswidgets.cpp:184`) and is a status-bar widget
(not a dialog child), so the `:default` rule is unreachable
on this chip — no interaction with the pulse rule.

**Hover/pressed overlay.** Without the `:hover:enabled` and
`:pressed:enabled` siblings, a user mousing over the chip
during the 600 ms window would hit the generic rule at
`src/themedstylesheet.cpp:146-147` which OVERWRITES `border` +
`border-color` with the accent fill — visually indistinguishable
from the non-pulse hover state. The three-rule block (base,
hover, pressed) above keeps the pulse border visible across all
three interaction states.

Mute toggle: `cfg.claudeAutoModelChipPulseEnabled()` (see § 2.5).
When false, the pulse helper short-circuits before setting the
property — no QSS work, no timer arm.

```cpp
// claudestatuswidgets.h — private members
QTimer  *m_modelStatePulseTimer = nullptr;       // single-shot, owned
static constexpr int kModelChipPulseMs = 600;
```

The timer is constructed lazily on first pulse (matches the
existing `m_errorHideTimer` pattern at L247): construct, set
single-shot, connect to a lambda that clears the property +
repolishes.

### 2.4 Undo — one-click revert button

A new `QPushButton *m_undoSwitchBtn` is added to the status bar
in the controller's ctor body, AFTER the `m_modelStateBtn`
addPermanentWidget call so the visual order reads
`[recommender chip] [model+thinking chip] [Undo: back to Opus] [error]`.

```cpp
// claudestatuswidgets.cpp — controller ctor, immediately after
// m_modelStateBtn = new QPushButton(…) block (L179-L186 today).
m_undoSwitchBtn = new QPushButton(QString(), m_statusBar);
m_undoSwitchBtn->setObjectName(QStringLiteral("claudeUndoSwitchBtn"));
m_undoSwitchBtn->setAccessibleName(tr("Undo last auto-model switch"));
m_undoSwitchBtn->setSizePolicy(QSizePolicy::Fixed, QSizePolicy::Preferred);
m_undoSwitchBtn->hide();
m_statusBar->addPermanentWidget(m_undoSwitchBtn);

connect(m_undoSwitchBtn, &QPushButton::clicked, this,
        &ClaudeStatusBarController::onUndoSwitchClicked);
```

`onUndoSwitchClicked` is a new private slot:

```cpp
void ClaudeStatusBarController::onUndoSwitchClicked() {
    if (m_undoSwitchPendingFromTier.isEmpty() ||
        m_undoSwitchPendingProject.isEmpty() ||
        m_undoSwitchPendingShellPid <= 0) return;

    auto *focused = m_focusedTerminalProvider
        ? m_focusedTerminalProvider() : nullptr;
    if (!focused) return;
    // Refuse the undo if the user switched tabs since the switch
    // fired. Match on BOTH project root AND shell PID — two tabs
    // rooted at the same project (e.g. two splits of the same repo)
    // share `shellCwd()` but have distinct `shellPid()`. Without
    // the PID guard, an Undo click in tab B would inject
    // `/model <fromTier>` into tab B's PTY even though the switch
    // fired on tab A.
    if (focused->shellCwd() != m_undoSwitchPendingProject) {
        emit statusMessageRequested(
            tr("Undo unavailable — switch was on a different project"),
            3000);
        return;
    }
    if (focused->shellPid() != m_undoSwitchPendingShellPid) {
        // Dead-PID fallback: if the original shell has exited
        // (e.g. user typed `exit` inside the 10 s window), the
        // recorded PID is gone but the focused tab is still at the
        // SAME project. Treat dead-pid as "same project, new
        // session" — refuse with a distinct toast so the user knows
        // why the click was lossy. `::kill(pid, 0)` with errno
        // ESRCH is the canonical liveness probe (no signal sent on
        // signum=0).
        if (::kill(m_undoSwitchPendingShellPid, 0) == -1 &&
                errno == ESRCH) {
            emit statusMessageRequested(
                tr("Undo unavailable — the original session has ended"),
                3000);
        } else {
            emit statusMessageRequested(
                tr("Undo unavailable — switch was on a different session"),
                3000);
        }
        return;
    }

    // Capture before clearing — the "Switched back to <X>" toast
    // below reads the prior tier; clearing the pending fields
    // first would leak a default-Sonnet read into the toast.
    const QString priorTierName = m_undoSwitchPendingFromTier;
    const QString priorProject  = m_undoSwitchPendingProject;
    // Also cache the original Tier enum captured at switch time
    // (see m_undoSwitchPendingFromTierEnum below) so the toast's
    // tierTitle() lookup goes via the cached enum, NOT via
    // tierFromModelId() — the latter is documented for full
    // Claude model IDs (`claude-3-5-haiku-…`), and reading a
    // bare tier alias `"haiku"` through it works only by
    // accident of substring matching.
    const ModelRecommender::Tier priorTier =
        m_undoSwitchPendingFromTierEnum;

    focused->sendToPty(
        (QStringLiteral("/model ") + priorTierName +
         QStringLiteral("\n")).toUtf8());

    // INV-7 — record the override-by-undo so the gate's cool-down
    // sees it on the next tick. Bypass the userOverrideWithin5
    // fill-in path (which scans the transcript) — the undo IS the
    // user override, no transcript inference needed.
    m_lastOverrideMsByProject[priorProject] =
        QDateTime::currentMSecsSinceEpoch();

    m_undoSwitchBtn->hide();
    m_undoSwitchPendingFromTier.clear();
    m_undoSwitchPendingProject.clear();
    if (m_undoSwitchHideTimer) m_undoSwitchHideTimer->stop();

    emit statusMessageRequested(
        tr("Switched back to %1").arg(tierTitle(priorTier)),
        3000);

    focused->setFocus();   // ANTS-1849 — keep typing focus in the terminal
}
```

`emitSwitchSurfacing` populates the pending fields and starts a
`m_undoSwitchHideTimer` (single-shot, 10 s) that hides the button:

```cpp
// claudestatuswidgets.h — private members
QPushButton *m_undoSwitchBtn = nullptr;
QTimer      *m_undoSwitchHideTimer = nullptr;          // single-shot, owned
QString      m_undoSwitchPendingFromTier;              // empty when no pending undo
QString      m_undoSwitchPendingProject;               // == shellCwd() at switch time
pid_t        m_undoSwitchPendingShellPid = 0;          // == shellPid() at switch time (per-tab guard);
                                                       // pid_t reaches claudestatuswidgets.h via
                                                       // claudeintegration.h's transitive includes.
                                                       // The cpp adds `#include <csignal>` and
                                                       // `#include <cerrno>` for the ::kill / ESRCH
                                                       // dead-pid probe in onUndoSwitchClicked.
ModelRecommender::Tier m_undoSwitchPendingFromTierEnum =
    ModelRecommender::Tier::Sonnet;                    // cached enum (avoid string round-trip)
static constexpr int kUndoVisibleMs = 10'000;

// (in emitSwitchSurfacing, after toast + pulse work)
if (cfg.claudeAutoModelUndoEnabled()) {
    m_undoSwitchBtn->setText(tr("Undo: back to %1").arg(tierTitle(fromTier)));
    m_undoSwitchPendingFromTier     = ModelRecommender::tierName(fromTier);
    m_undoSwitchPendingFromTierEnum = fromTier;
    m_undoSwitchPendingProject      = projectRoot;
    m_undoSwitchPendingShellPid     = focused->shellPid();
    m_undoSwitchBtn->show();
    if (!m_undoSwitchHideTimer) {
        m_undoSwitchHideTimer = new QTimer(this);
        m_undoSwitchHideTimer->setSingleShot(true);
        connect(m_undoSwitchHideTimer, &QTimer::timeout, this, [this]() {
            if (m_undoSwitchBtn) m_undoSwitchBtn->hide();
            m_undoSwitchPendingFromTier.clear();
            m_undoSwitchPendingProject.clear();
            m_undoSwitchPendingShellPid = 0;
            m_undoSwitchPendingFromTierEnum =
                ModelRecommender::Tier::Sonnet;   // back to default
        });
    }
    m_undoSwitchHideTimer->start(kUndoVisibleMs);
}
```

A second switch firing inside the 10 s window: the new pending
overwrites the previous (the old "Undo: back to Opus" becomes
"Undo: back to Sonnet"). Per the user-visible semantics — at any
moment the Undo button refers to the *most recent* switch.

The 10 s window deliberately matches the order-of-magnitude
typical user reaction time for a peripheral-vision catch (toast +
chip-pulse → glance up → read → decide → click). Shorter (5 s)
would be too tight for users mid-keystroke; longer (30 s) makes
the button stale — the user might want to undo *the previous*
switch, not the current one, if they didn't notice the first.

### 2.5 New config keys + `shortenReason` helper

Three new bool config keys persisted via `Config`:

- `claude.auto_model_toast_enabled` — bool, default **true**.
- `claude.auto_model_chip_pulse_enabled` — bool, default **true**.
- `claude.auto_model_undo_enabled` — bool, default **true**.

All three default ON because §1 motivates the surfacing as the
primary trust-building affordance. A user who finds any one
overbearing flips it off in Settings (§ 2.7).

Add three pairs of `Config::claude*` accessors mirroring the
existing bool-pair `claudeAutoModelNudgeShown()` /
`setClaudeAutoModelNudgeShown()` at `config.h:95-96` (the only
current bool get/set pair in the auto-model family — note
`setClaudeAutoModelSwitch(bool)` at L89 is a setter without a
matching plain-bool getter; the read side goes through the
umbrella `claudeAutoModel()` JSON object at L86). One-line
bodies; each just reads/writes the key via
`m_data.value(...).toBool(true)` (defaulting `true`) and
`storeIfChanged(...)` for the setter.

`shortenReason` is a new file-static helper in
`claudestatuswidgets.cpp`'s anonymous namespace. Maps the
score_reason string from `ModelRecommender::score` to a short
human label suitable for the toast (the reason today is a
space-joined keyword list — e.g. `"many_writes tool_diversity"`
or the override `"commit_intent"`). Mapping table:

| `rec.reason` token       | Short label              |
|--------------------------|--------------------------|
| contains `commit_intent` | `tr("commit intent")`    |
| contains `mechanical`    | `tr("mechanical")`       |
| contains `plan_keyword`  | `tr("design / plan")`    |
| contains `many_writes`   | `tr("many writes")`      |
| contains `long_prompts`  | `tr("long prompts")`     |
| contains `tool_diversity`| `tr("varied tools")`     |
| otherwise (`default`)    | `tr("recommender")`      |

Precedence: `commit_intent` first (it's an OVERRIDE, not an
ensemble), then `mechanical` (a single negative signal), then
`plan_keyword`/`many_writes`/`long_prompts`/`tool_diversity` in
that order (first match wins). The helper finds the FIRST matching
token in precedence order — never concatenates two short-labels,
never returns the full reason string.

**Reachability note.** `commit_intent` and `mechanical` /
`many_writes` are mutually exclusive in practice:
- `commit_intent` is the OVERRIDE branch (returns from
  `score()` before scoring), so a `reason` string carrying it
  is always the single token `"commit_intent"`. The remaining
  precedence entries cannot appear in the SAME reason string.
- `mechanical` requires `fileWriteCount == 0 && toolDiversity <= 2`
  (per `modelrecommender.cpp:243-244` — the predicate is
  conjunctive); `many_writes` requires `weightedWrites >= 8.0`
  (L239), which implies `fileWriteCount >= 1`. The two are
  mutually exclusive via the `fileWriteCount` clause —
  `many_writes` firing forces `fileWriteCount >= 1`, which
  blocks `mechanical`'s required `fileWriteCount == 0`.
- The reachable reason-string shapes are thus: (a) a single
  `commit_intent` or `default` token; or (b) a space-joined
  list drawn from `{many_writes, plan_keyword, long_prompts,
  tool_diversity}` ± `mechanical`, with `mechanical` NEVER
  co-occurring with `many_writes`.

Precedence order is correct as-is; this note documents the
reachable shapes so a future signal-table edit doesn't
inadvertently break the contains-match assumption.

**rec.reason field shapes — important.** The recommender emits
`rec.reason` in three distinct shapes (`src/modelrecommender.cpp`):

- **Commit-intent override** (L173): `reason = "commit_intent"`
  — the whole string is the single token.
- **Default branch** (L86): `reason = "default"` — the whole
  string is the single token; `topSignals` is empty.
- **Normal scoring path** (rule additions L239-244; final
  assignment at L250 / L253 / L256 per the tier branch): `reason`
  is a space-joined fragment list (e.g.
  `"many_writes tool_diversity plan_keyword"`).

`shortenReason` is a contains-match in every case; for the
override / default shapes it sees a single-token string and
matches that token directly. For the multi-token shape it picks
the first match in precedence order. The contains-match works
uniformly because the tokens never overlap as substrings (no
token is a substring of another).

The `tr()` wrap puts the short label under i18n — matches the
toast body's `tr()` wrap in § 2.2.

### 2.6 `themedstylesheet::buildAppStylesheet` — add the pulse rule

The pulse rule lands in `src/themedstylesheet.cpp` —
`buildAppStylesheet` returns the single parameterised stylesheet
that MainWindow applies on every theme change. Insertion point:
immediately after the `QPushButton:disabled` rule at L149, before
the `QLineEdit` block at L150 — keeps the QPushButton rules
contiguous. The `%5` slot resolves to `theme.accent.name()` at
arg-substitution time (`src/themedstylesheet.cpp:215`), so the
border colour follows the active theme without any per-theme
override.

Why this site, not `m_modelStateBtn->setStyleSheet` or a separate
helper? A widget-local setStyleSheet would override the generic
`QPushButton` cascade (padding, border, hover) for the chip's
non-pulsed state too — undesirable. A new helper would fragment
the chip's styling across two functions. Appending the rule
inside `buildAppStylesheet` keeps the chip's full QSS contract in
one place, follows the existing pattern for every other status
widget, and inherits the `%5` accent substitution for free.

Standards-doc impact: add one sentence to
`docs/standards/status-bar.md` (the standard CLAUDE.md L201 cites
for status-bar widget conventions) noting that a controller-owned
chip with a dynamic `pulse` property needs a matching
`QPushButton#<id>[pulse="true"]` rule in `themedstylesheet.cpp`'s
`buildAppStylesheet`. (NOT `docs/standards/dialogs.md` — that
standard owns `QDialog` chrome / resize / persist / recenter, a
different surface.)

## 4. RAM / build cost

- **RAM (per process):** two `QString` + two `QTimer*` + one
  `QPushButton*` + one `pid_t` + one `Tier` enum byte on the
  controller. Per-instance footprint < 200 bytes including the
  QTimer object. **No** new
  per-project hash (the existing `m_lastOverrideMsByProject` from
  ANTS-1890 already keys override timestamps per project).
- **Disk:** no new on-disk artifacts. Three new bool config keys
  add ~120 bytes to `~/.config/ants-terminal/config.json` worst
  case (all three persisted).
- **CPU per tick:** zero on idle ticks (`emitSwitchSurfacing` is
  called only inside the `if (dec.act)` branch — i.e. once per
  switch, not once per tick). Per-switch cost: one
  `style()->unpolish + polish` repaint of one button (sub-ms),
  one `QTimer::start` (sub-µs), one `setText` on the Undo button
  (sub-µs). Below profiler noise.
- **CPU during pulse window:** zero — the QSS rule renders the
  border once per repaint; pulse timeout is a single deferred
  property clear + repolish.
- **Build cost:** one new TU consumer (`claudestatuswidgets.cpp`
  gains ~120 lines: `emitSwitchSurfacing` + `onUndoSwitchClicked`
  + `tierTitle` + `shortenReason` + ctor wiring); 3 new accessors
  on `config.{h,cpp}` (~24 lines); ~10 lines in
  `src/themedstylesheet.cpp` for the three-rule pulse block
  (base + hover + pressed states, all bound to `%5`
  `theme.accent.name()`). No new theme files (the project
  has no `themes/*.qss` layout). Test bundle: add new sources
  to `test_claude` (the bundle that already links
  `ants_claude_lib`; no `add_executable`) — 15 test files
  totaling ~700 lines.

## 6. Migration / compatibility

- **No on-disk migration.** Three new config keys default TRUE; a
  pre-1893 `config.json` lacking them reads as if all three were
  present and TRUE. No version bump on the config schema.
- **Status-bar layout.** The Undo button slots between
  `m_modelStateBtn` and `m_errorLabel` — only shown post-switch
  for 10 s. When hidden (the steady state), the bar reads
  identically to pre-1893.
- **`statusMessageRequested` signal.** Reused as-is — no signature
  change. Existing slot
  (`MainWindow::showStatusMessage` via the `statusMessageRequested
  ↔ showStatusMessage` connect in `mainwindow.cpp`) handles the
  toast.
- **Stylesheet builder.** `src/themedstylesheet.cpp:13`
  (`buildAppStylesheet`) gains a 4-line rule. The project has no
  `themes/*.qss` file layout — themes are programmatic `Theme`
  structs. The rule's `%5` placeholder substitutes to
  `theme.accent.name()` on every theme apply, so every theme
  acquires the pulse style automatically; no third-party theme
  delivery surface to worry about.
- **No interaction with the ledger schema** — ANTS-1893 adds no
  new ledger fields; the `trigger:"auto"` record format is
  unchanged. An Undo writes to `m_lastOverrideMsByProject` in
  memory (the cool-down cache) ONLY, NOT to the ledger record
  itself. The ledger's `userOverrideWithin5` outcome field
  continues to settle via the existing
  `fillPendingLedgerOutcomes` transcript-scan path on its 30 s
  tick. The two mechanisms are complementary: the in-memory
  cache feeds the gate's next-tick cool-down decision (fast,
  per-process); the ledger field feeds the regret-math
  aggregator over time (durable, per-record). The ROADMAP-bullet
  body currently leaks this split by saying Undo "records a
  userOverrideWithin5=true"; the spec's contract is the
  in-memory cache only, and the ROADMAP correction in § 8 below
  drops that line. ROADMAP-bullet-correction landing-rule:
  must commit IN THE SAME ROADMAP edit as the spec-acceptance
  commit, NOT as a separate later edit — otherwise the
  spec-vs-roadmap divergence persists across reads.
- **Undo-OFF path — manual `/model` override detection
  unchanged.** When `claude.auto_model_undo_enabled = false`
  the Undo button never appears (INV-10). If the user manually
  types `/model <prev>` after a switch they didn't undo via
  this surface, the existing
  `fillPendingLedgerOutcomes` transcript-scan path at
  `claudestatuswidgets.cpp:1687` still detects the manual
  override via `userOverrideWithin5=true` on the next 30 s
  fill-in tick — the cool-down then trips when
  `m_lastOverrideMsByProject` is seeded from the settled
  ledger record. So the two detection paths are NOT redundant:
  Undo seeds the cool-down within milliseconds (in-memory,
  immediate); manual `/model` seeds the cool-down within ~30 s
  (transcript-scan, durable). When Undo is muted, only the
  slower path applies; the safety net survives.

## 9. Open questions

- **OQ-1: Toast position — left or right of m_statusMessage?** The
  existing `m_statusMessage` is the stretch=1 elastic widget; the
  status-bar layout has fixed widgets either side. The toast body
  goes into `m_statusMessage` (via `showStatusMessage`), so it
  appears in the centre-elastic slot. No alternative considered.
  **Resolved by design** — no OQ.
- **OQ-2: Should the Undo button include the "to-tier" context?**
  Current spec: `"Undo: back to Opus"` (names the prior tier). An
  alternative is `"Undo last switch"` (no context). Pro-context:
  user sees *what* the undo will do. Anti-context: longer text
  pushes the button width up. **Decision:** keep the prior-tier
  context (informative trumps compact for a 10 s ephemeral
