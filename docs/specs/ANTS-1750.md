# ANTS-1750 — Run each Lua plugin VM on its own worker thread

**Status:** accepted — cold-eyes loops 1–4, loop 4 clean (2026-05-22).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-1750 (indie-review #5, 2026-05-21 — Tier 2 hardening; deferred as architectural).
**Pairs with:** ANTS-1736 (wires the dormant veto/hot-path events — inherits the synchronous-veto contract in § 2.6).
**Out-of-scope follow-up:** ANTS-1795 (full process isolation).

## 1. Problem

Lua plugin handlers run **synchronously on the GUI thread**, and the
plugin watchdog can only interrupt the VM at a bytecode/line boundary —
so a single long-running pure-C library call (`string.gsub` with a
pathological pattern, `string.rep`, `string.find`) freezes the whole
terminal until it returns.

Grounded in current source:

1. `PluginManager::fireEvent` (`src/pluginmanager.cpp:362`) loops every
   loaded engine and calls `LuaEngine::fireEvent`
   (`src/luaengine.cpp:376`), which runs `lua_pcall`
   (`src/luaengine.cpp:390`) **inline on the calling (GUI) thread**.
2. The watchdog is an instruction-count + line hook plus a wall-clock
   deadline checked *inside* that hook
   (`LuaEngine::instructionHook`, `src/luaengine.cpp:142`;
   `lua_sethook(... LUA_MASKCOUNT | LUA_MASKLINE, 100000)` at
   `src/luaengine.cpp:136`). The hook only fires between VM
   instructions, so it cannot preempt a single C call already in flight.
   The code says so explicitly at `src/luaengine.cpp:129-131`:
   *"A SINGLE C call (one giant gsub) still can't be preempted on the
   main thread — the budget is enforced at the next bytecode boundary."*
3. The per-VM memory cap (`LuaEngine::MAX_LUA_MEMORY = 10 MiB`,
   `src/luaengine.h:59`, enforced in `LuaEngine::luaAlloc`,
   `src/luaengine.cpp:34`) bounds *memory* but not *time*: a pathological
   pattern match can run for many seconds while allocating almost
   nothing.

Consequence: a buggy or malicious plugin can hang the UI indefinitely.
The memory cap, the instruction hook, and the wall-clock budget
(ANTS-1172 / ANTS-1332) already neutralise pure-Lua loops and the
C-call-in-a-Lua-loop pattern; the **single uninterruptible C call** is
the one residual freeze vector, and it can only be closed by moving
plugin execution off the GUI thread.

**Layman:** a plugin can currently lock up the whole terminal by asking
a built-in function to chew on one enormous job; this moves every
plugin onto its own background worker so the terminal stays responsive
no matter what a plugin does.

## 2. Surface

### 2.1 Threading model

Each plugin already has its own `LuaEngine` (one VM per plugin —
`PluginManager::m_engines`, `src/pluginmanager.h:106`). This spec gives
each `LuaEngine` its own `QThread` and moves the engine onto it:

- `PluginManager` (GUI thread) stays the controller. For each plugin it
  owns a `QThread`, moves the engine onto it with
  `engine->moveToThread(thread)`, then `thread->start()`.
- **The engine must be parentless.** `loadPlugin` currently constructs
  `new LuaEngine(this)` (`src/pluginmanager.cpp:333`), parenting it to
  `PluginManager`. Qt refuses `moveToThread` on a parented `QObject`
  (it warns and the move silently does not happen). Construct the engine
  with `new LuaEngine(nullptr)` and manage its lifetime explicitly:
  delete it via `deleteLater` *posted to the worker thread* on clean
  unload, or move it to the `m_zombies` list on the detach path
  (§ 2.5.1). `unloadAll` is updated to follow the same teardown. Because
  the engine has worker affinity, a `deleteLater` posted to the worker
  runs `~LuaEngine` — and therefore `shutdown()` / `lua_close` — **on the
  worker**, never the GUI thread (see § 2.5.1 + INV-12).
- The `lua_State` is created (`LuaEngine::initialize`,
  `src/luaengine.cpp:94`) and **only ever touched** on the engine's
  worker thread. Lua states have single-thread affinity; every
  `lua_*` call must execute on the owning worker.
- `initialize`, `loadScript`, and a new `dispatchEvent` slot become the
  worker-side entry points; `PluginManager` invokes them across the
  thread boundary with `QMetaObject::invokeMethod(..., Qt::QueuedConnection)`
  (non-blocking) — see § 2.3.

`PluginManager::wireEngine` (`src/pluginmanager.cpp:73`) connects the
engine's outbound signals (`sendToTerminal`, `showNotification`,
`setStatusText`, `logMessage`, `clipboardWriteRequested`,
`paletteEntryRegistered`). These are already Qt signals; once the engine
lives on a worker thread Qt auto-delivers them to the GUI-thread
receiver via a queued connection — no change to the signal/slot
declarations, only to the affinity that makes them cross-thread.

### 2.2 Event dispatch (GUI → worker, non-blocking)

`PluginManager::fireEvent` becomes a non-blocking post. The current
inline loop:

```cpp
// before — runs the handler synchronously on the GUI thread
for (auto *engine : snapshot)
    if (!engine->fireEvent(event, data)) allow = false;
```

becomes a queued hand-off to each healthy worker:

```cpp
// after — posts to the worker; returns immediately. No veto for
// async events (every event fired today is fire-and-forget; see § 2.6).
for (auto *engine : healthyEngines())
    QMetaObject::invokeMethod(engine, "dispatchEvent",
                              Qt::QueuedConnection,
                              Q_ARG(int, int(event)),
                              Q_ARG(QString, data));
```

`LuaEngine::dispatchEvent(int,QString)` is a new slot that runs the
existing `fireEvent` body (the `lua_pcall` loop) **on the worker
thread**. The public `bool fireEvent(...)` return value is retained only
for the synchronous-veto path that ANTS-1736 will build (§ 2.6); async
callers ignore it.

Events to a single plugin are processed FIFO (one worker, one event
queue), preserving today's per-plugin handler ordering. Across plugins,
workers run in parallel — already-isolated VMs, no shared Lua state.

#### 2.2.1 Targeted dispatch — palette + keybinding

Two events reach a *single* plugin, not the broadcast loop, and both
currently call `engine->fireEvent(...)` **directly on the GUI thread**:

- `PluginManager::firePaletteAction` (`src/pluginmanager.cpp:88`) →
  `engine->fireEvent(PluginEvent::PaletteAction, ...)`.
- The `Keybinding` shortcut lambda in `MainWindow`
  (`src/mainwindow.cpp:537-539`) reaches into
  `m_pluginManager->engineFor(pluginName)` and calls
  `engine->fireEvent(PluginEvent::Keybinding, actionId)` directly (the
  call is at `src/mainwindow.cpp:538`, lambda spanning 535-540) —
  bypassing `PluginManager::fireEvent` entirely.

Both are converted to go through one new controller method
`PluginManager::dispatchTo(const QString &pluginName, PluginEvent,
const QString &data)` that does the same queued `invokeMethod` post to
the named healthy engine (the targeted twin of the broadcast loop in
§ 2.2, sharing the `healthyEngines()` health filter). `firePaletteAction`
calls it internally; the MainWindow keybinding shortcut calls
`dispatchTo(...)` instead of touching the engine pointer. The existing
GUI-side callers of `firePaletteAction` —
`src/mainwindow.cpp:6686` (QAction `triggered`) and `:6699` (standalone
`QShortcut`) — and the broadcast `PaletteAction` at
`src/mainwindow.cpp:2138` are unchanged: they call `firePaletteAction` /
`PluginManager::fireEvent`, both now queued internally. `engineFor()`
stays for non-Lua lookups but **must not** be used to call a
`lua_*`-touching method from the GUI thread — `dispatchTo` is the only
supported synchronous-from-GUI entry into a worker.

New `PluginManager` members this introduces (declared for the
implementer): `void dispatchTo(const QString&, PluginEvent, const
QString&)` (queued targeted post); `QList<LuaEngine*> healthyEngines()
const` (the broadcast/targeted filter excluding demoted plugins);
`void healthTick()` (the 2 s slot, § 2.5); plus the `m_zombies` list and
per-plugin in-flight bookkeeping.

#### 2.2.2 Load-event ordering

`loadPlugin` currently runs `initialize()` and `loadScript()`
**synchronously and branches on their `bool` return**
(`src/pluginmanager.cpp:338`, `:349` — `shutdown()`+`deleteLater()`+
`return` on failure). Once those become queued worker posts they return
`void` immediately, so the GUI can no longer gate `Load` on their
result. The load sequence becomes three queued posts to the *same*
worker, processed FIFO: `initialize` → `loadScript(init.lua)` →
`dispatchEvent(Load)`, and **failure-gating moves worker-side via the
`m_state` latch that already exists**:

- `initialize` failure leaves `m_state == nullptr`, so the existing
  null-guards in `loadScript` (`src/luaengine.cpp:322`) and `fireEvent`
  (`:377`) make the queued `loadScript` and `Load` no-op. No change
  needed.
- A `loadScript` **script error** currently returns `false` *without*
  nulling `m_state` (`src/luaengine.cpp:347-352`), so a queued `Load`
  would fire into a half-loaded VM. Fix: on its failure path the
  worker-side `loadScript` calls `shutdown()` **itself, on the worker**
  (nulling `m_state`) — which both gates the queued `Load` and keeps
  `lua_close` off the GUI thread (replacing today's GUI-side
  `engine->shutdown()` at `src/pluginmanager.cpp:351`; see § 2.5.1 +
  INV-12).

The GUI thread never waits for any of the three posts.

### 2.3 Synchronous reads into Lua

Three API callbacks return data *into* Lua and need care once the VM is
off-thread:

- **`ants.get_output` / `ants.get_cwd`** (`src/luaengine.cpp:450`,
  `:465`) read `m_recentOutput` / `m_cwd`. Today
  `PluginManager::setRecentOutput` / `setCwd`
  (`src/pluginmanager.cpp:373`, `:379`) write these from the GUI thread.
  Fix: make `LuaEngine::setRecentOutput` / `setCwd` **queued slots**, so
  the members are mutated on the worker thread only — no GUI-write /
  worker-read race. Handlers see a best-effort recent snapshot
  (documented in PLUGINS.md).
- **`ants.settings.get`** (`src/luaengine.cpp:529`) needs a real
  synchronous round-trip: it emits `settingsGetRequested(name, key,
  QString &out)` (`src/luaengine.h:88`) and reads `out` back before
  returning to Lua. The chain is a **two-hop relay**: engine emits →
  `PluginManager` re-emits the same signal (`src/pluginmanager.cpp:80`)
  → a `MainWindow` lambda (`src/mainwindow.cpp:566`) fills `QString &out`
  from Config. Today all three are same-thread, so `out` is filled
  synchronously. Once the engine is on a worker, the **first hop only**
  (`LuaEngine::settingsGetRequested` → `PluginManager`, set in
  `wireEngine`) becomes a **`Qt::BlockingQueuedConnection`**; the
  `PluginManager` → `MainWindow` hop stays a direct same-thread call that
  runs on the GUI thread *inside* the worker's block, and the worker's
  stack keeps `out` alive across the block. The *worker* blocks until the
  GUI services the request; the GUI never blocks on a worker (see § 2.4),
  so no deadlock and no UI freeze. Config is touched only on the
  GUI/Config thread, preserving its affinity. The worker-side block is
  **intentionally unbounded** (no timeout, unlike the future veto path in
  § 2.6): a worker stalling on a busy GUI is acceptable — it is the
  plugin that waits, never the UI — and `settings.get` is a rare,
  plugin-initiated synchronous read. The § 2.6 timeout exists only
  because that path blocks the *GUI* on a worker, which this one never
  does. The two are not the same risk.
- **`ants.settings.set`** (`src/luaengine.cpp:547`) emits
  `settingsSetRequested` with no value returned into Lua, so it needs no
  blocking round-trip — it stays a plain (now cross-thread) **queued**
  signal. Listed only so a future reader (and ANTS-1736) does not assume
  `set` blocks like `get`.

### 2.4 No GUI→worker blocking call (deadlock + freeze avoidance)

The design's load-bearing rule: **the GUI thread never blocks waiting on
a worker.** All GUI→worker invocations (`dispatchEvent`, `setRecentOutput`,
`setCwd`, `initialize`, `loadScript`, abort) are `Qt::QueuedConnection`.
Only worker→GUI calls may block (`settings.get`). This makes the two
directions asymmetric and acyclic, so there is no
`BlockingQueued`-into-`BlockingQueued` cycle — no deadlock — and a
runaway worker can never stall the UI thread.

### 2.5 Watchdog, abort flag, and runaway handling

- The existing instruction/line hook + 1.5 s wall-clock budget
  (`startPcallBudget`, `src/luaengine.cpp:181`; `m_pcallBudgetMs = 1500`,
  `src/luaengine.h:145`) stays, now running on the worker. It continues
  to catch pure-Lua and C-in-Lua-loop runaways without GUI involvement.
- Add `std::atomic<bool> m_abortRequested` to `LuaEngine`, set by the
  GUI controller and read inside `instructionHook`. When set, the hook
  raises `luaL_error` at its **next fire** — bounded by the existing
  100k-instruction / per-line cadence (`src/luaengine.cpp:136-137`), i.e.
  sub-millisecond for pure-Lua / C-in-loop runaways. The GUI does **not**
  call `lua_sethook` to shrink that window: `lua_sethook` mutates the
  worker's `lua_State` and calling it cross-thread would race the running
  VM. (The wall-clock path's count=1 re-arm at `src/luaengine.cpp:175-176`
  runs *inside* the hook, on the worker — safe; an equivalent for abort
  is unnecessary because the first hook fire that observes the flag
  already `luaL_error`-longjmps out, so there is no "subsequent" fire to
  accelerate.) For the single-uninterruptible-C-call case the hook is
  dormant and abort cannot fire — that is exactly why the detach path
  (§ 2.5.1) exists. Besides this atomic and
  the queued-slot members of § 2.3 (`m_recentOutput` / `m_cwd`, mutated
  on the worker only), no engine state is shared across threads — in
  particular the `lua_State`, `m_handlers`, and the
  `m_timedOut`/`m_killed`/`m_pcallDeadlineMs` watchdog fields are touched
  only on the worker. This lets the controller cancel a cooperating
  runaway (e.g. on plugin unload) without racing the VM.
- **Single uninterruptible C call** (the ANTS-1750 bug): neither the
  hook nor the abort flag can fire while pure C is executing. The GUI
  controller detects it instead: `dispatchEvent` brackets each handler
  with two worker→GUI signals — `eventStarted(quint64 seq)` emitted at
  the *top* of the slot (before `lua_pcall`) and `eventCompleted(quint64
  seq)` after. `PluginManager` records the **execution** start time from
  `eventStarted` (not the post time) and, on a periodic health tick,
  flags any plugin whose *currently-executing* event has been running
  past `budget + grace` as **unhealthy**: it sets `m_abortRequested`,
  stops routing new events to it (`healthyEngines()` excludes it), and
  logs the demotion. Measuring from `eventStarted` (not from when the
  GUI posted the event) is deliberate: a healthy-but-backed-up worker
  draining a long FIFO queue keeps emitting `eventStarted`/`eventCompleted`
  per event, so each event's *execution* time stays short and the plugin
  is not falsely demoted; a worker stuck in a C call emits `eventStarted`
  and then never `eventCompleted`, so its execution time ages past the
  deadline. The plugin is neutered for the rest of the session; the UI
  was never blocked.
- **The health tick is `PluginManager`-owned.** The existing 2 s status
  timer (`m_statusTimer`, constructed at `src/mainwindow.cpp:737`)
  belongs to `MainWindow` and drives status-bar/tab-title refresh —
  `PluginManager` cannot reach it. Give `PluginManager` its own
  lightweight `QTimer` (2 s) wired to a `healthTick()` slot, so the
  health logic is self-contained in the controller with no `MainWindow`
  coupling. The execution-start timestamp is recorded from the worker→GUI
  `eventStarted(seq)` signal and cleared on `eventCompleted(seq)`, so the
  health tick measures handler *execution* time, not queue wait (see the
  single-C-call bullet above).

### 2.5.1 Teardown / detach

Today `unloadAll` (`src/pluginmanager.cpp:64-67`) runs
`engine->fireEvent(Unload)` + `engine->shutdown()` + `deleteLater()`
**synchronously on the GUI thread** — and `shutdown()` calls `lua_close`
(`src/luaengine.cpp:367-368`), a `lua_*` call, so the current teardown
would violate INV-1 if left as-is. The destructor `~LuaEngine`
(`src/luaengine.cpp:90-92`) also calls `shutdown()`. The new teardown
keeps every `lua_close` on the worker. On unload or app exit, for each
plugin:

1. Post `Unload` via `dispatchEvent` (queued) so the handler runs on the
   worker before teardown (FIFO).
2. `thread->quit(); thread->wait(kTeardownMs)`.
3. On clean exit, destroy the engine with `deleteLater` **posted to the
   worker** (or a worker-side shutdown slot run before `quit`) so
   `~LuaEngine` → `shutdown()` → `lua_close` executes on the worker, not
   the GUI thread (§ 2.1, INV-12). The GUI-side `engine->shutdown()`
   calls at `pluginmanager.cpp:65` (unloadAll) and `:351` (load-failure)
   are removed in favour of this worker-side path.
4. If `wait` times out (worker stuck in a C call), **detach**: do not
   `delete` the engine/thread and do not call `shutdown()`; move the pair
   to a bounded `m_zombies` list and let the process tear down. The
   zombie holds ≤ 10 MiB (the existing per-VM cap) + its worker stack
   until its C call returns (or until process exit). It never receives
   further work and is never destroyed (its `lua_State` is owned by the
   stuck C frame).

This guarantees teardown completes within `kTeardownMs` regardless of a
stuck plugin (today a stuck plugin would block destruction) and keeps
all `lua_close` off the GUI thread.

### 2.6 Veto / hot-path event contract (consumed by ANTS-1736)

Every `PluginEvent` fired in the current build is fire-and-forget — no
caller consumes the `bool` return to cancel:

- Fired today (the complete set of engine-invoking sites):
  - Broadcast via `PluginManager::fireEvent` (converted in § 2.2):
    `WindowConfigReloaded` (`src/mainwindow.cpp:1902`), `CommandFinished`
    (`:2107`), `UserVarChanged` (`:2116`), `PaneFocused` (`:2706`),
    `ThemeChanged` (`:3123`), and `Load`/`Unload` (fired from
    `src/pluginmanager.cpp` — `:358` / `:66`).
  - Targeted (converted in § 2.2.1): `Keybinding`
    (`src/mainwindow.cpp:538`) and `PaletteAction`
    (`PluginManager::firePaletteAction`, `src/pluginmanager.cpp:90`).
- Defined but **not yet wired** (ANTS-1736): `Output`, `Line`, `Prompt`,
  `KeyPress`, `TitleChanged`, `TabCreated`, `TabClosed`
  (`src/luaengine.h:14`).

So async delivery (§ 2.2) is a *complete* fix for the freeze surface
that exists today. The veto-capable event is `KeyPress` (swallow a key
by returning `false`), and it is part of ANTS-1736, not this spec.

**Contract ANTS-1736 must satisfy** when it wires a synchronous-veto
event: the GUI→worker call for that event uses a
`Qt::BlockingQueuedConnection` **with a bounded timeout** (~5–10 ms via
a `QSemaphore::tryAcquire(timeoutMs)` / wait-condition handshake — Qt's
`BlockingQueuedConnection` has no native timeout). On timeout the action
proceeds **un-vetoed** (the key is sent) and the plugin is demoted to
observe-only. This bounds even a malicious `KeyPress` handler to a
single sub-frame input hiccup, then neuters it — it never reintroduces
the indefinite freeze. ANTS-1750 ships no veto event; this paragraph is
the documented contract, not code in this spec.

## 3. Invariants

- **INV-1** — Each loaded plugin's `lua_State` is created and accessed
  only on its dedicated worker `QThread`; no `lua_*` C-API call executes
  on the GUI thread after the engine is moved. *Test:* primary — a
  runtime assert of `QThread::currentThread() == thread()` inside
  `dispatchEvent`/`initialize`/`loadScript` (the test trips it if any
  Lua entry runs on the GUI thread); source-grep that all `lua_*` calls
  live in worker-affine `LuaEngine` methods is an advisory backstop.
- **INV-2** — `PluginManager::fireEvent` returns to the GUI event loop
  without waiting for any handler: a handler that busy-loops does not
  block the GUI thread. *Test:* `tests/features/lua_threading/` posts an
  event to a plugin whose handler busy-loops and asserts a queued
  GUI-thread callback still runs within a short deadline.
- **INV-3** — A plugin executing a single uninterruptible C call past
  `budget + grace` does not freeze the GUI; it is marked unhealthy and
  receives no further events. *Test:* feature test loads a plugin whose
  handler runs a pathological `string.gsub`/`string.rep`; asserts the
  host stays responsive and a subsequently-posted event is **not**
  delivered to that plugin.
- **INV-4** — At teardown a worker stuck in a C call is detached, not
  joined; `PluginManager` destruction / unload completes within
  `kTeardownMs`. *Test:* feature test wedges a worker then tears down
  the manager; asserts teardown returns under the deadline and the
  engine is tracked as a zombie (not deleted, not joined).
- **INV-5** — `m_abortRequested` set by the GUI controller is honoured
  by `instructionHook`: a pure-Lua / C-in-loop runaway raises
  `luaL_error` at the next VM boundary. *Test:* unit test invokes the
  hook with the flag set and asserts it errors on the next fire.
- **INV-6** — `m_recentOutput` / `m_cwd` are written only on the worker
  thread (via queued `setRecentOutput` / `setCwd` slots); the GUI thread
  never writes them. *Test:* source-grep that the setters are slots
  invoked via `QueuedConnection` and that no GUI-thread code path
  assigns the members; design assertion documented.
- **INV-7** — `ants.settings.get` returns the live Config value via a
  worker→GUI `BlockingQueuedConnection`; no GUI→worker invocation in the
  design is blocking. *Test:* feature test plugin calls
  `ants.settings.get` and receives the seeded value; source-grep asserts
  the `settingsGetRequested` edge is `BlockingQueuedConnection` and that
  every GUI→worker edge (`dispatchEvent`/`setRecentOutput`/`setCwd`/
  `initialize`/`loadScript`/abort) is `QueuedConnection`.
- **INV-8** — Events posted to a single plugin are processed FIFO in
  post order. *Test:* feature test posts a numbered sequence to one
  plugin; the handler records arrival order; asserts it matches.
- **INV-9** — Per-plugin memory stays bounded: `MAX_LUA_MEMORY` (10 MiB)
  is unchanged and each worker thread's stack is explicitly capped
  (≤ ~512 KiB); the zombie list is bounded by the number of plugins that
  ran away this session. *Test:* assert `MAX_LUA_MEMORY` unchanged;
  assert the worker stack size is set at thread creation; assert zombie
  bookkeeping is per-runaway, not per-event.
- **INV-10** — Targeted dispatch is also non-blocking on the GUI thread:
  `firePaletteAction` and the `MainWindow` keybinding shortcut both route
  through `PluginManager::dispatchTo` (queued), so no `lua_*` call runs
  on the GUI thread for `PaletteAction` or `Keybinding`. The `Load` event
  is delivered via the same queued path, after `initialize`+`loadScript`,
  FIFO on the worker. *Test:* feature test fires a keybinding/palette
  action and the `Load` event into a busy-looping plugin and asserts the
  GUI thread is not blocked; source-grep asserts no
  `engineFor(...)->fireEvent(` / inline `engine->fireEvent(` call remains
  on a GUI-thread path.
- **INV-11** — A loaded engine has no `QObject` parent (so `moveToThread`
  succeeds) and its lifetime is managed explicitly: cleanly-unloaded
  engines are destroyed via `deleteLater` posted to the worker; detached
  (zombie) engines are never deleted. *Test:* feature test asserts
  `engine->parent() == nullptr` after load and that
  `engine->thread() != qApp->thread()`; teardown test asserts a clean
  unload deletes the engine and a wedged unload moves it to `m_zombies`.
- **INV-12** — No `lua_close` (via `shutdown()` or `~LuaEngine`) executes
  on the GUI thread: clean unload destroys the engine via `deleteLater`
  posted to the worker (destructor runs worker-side), the load-failure
  path calls `shutdown()` on the worker, and zombies are never destroyed.
  No GUI-thread code path calls `engine->shutdown()`. *Test:* teardown
  feature test asserts `shutdown()`/`lua_close` runs on the worker thread
  (thread-affinity check in a shutdown hook); source-grep asserts no
  GUI-path `engine->shutdown()` call survives (the `pluginmanager.cpp:65`
  + `:351` calls are gone).

## 4. RAM / build cost

- **Per loaded plugin:** existing 10 MiB Lua-heap cap (unchanged) + one
  worker `QThread` with an explicitly small stack + `QThread`/event-queue
  bookkeeping. For a handful of plugins this is low single-digit MiB.
  The stack cap is a *chosen* small value (~512 KiB) with comfortable
  headroom, not a derived figure: the sandbox can't deep-recurse (Lua
  bounds C-call depth at `LUAI_MAXCCALLS` = 200, and the `ants.*` shims
  are shallow), so a small stack is safe; the exact number is tuned at
  implementation time if any test trips a stack guard.
- **Zombies:** bounded by the number of plugins that hit the
  uninterruptible-C-call path in a session (rare, author error). Each
  holds its ≤ 10 MiB VM + stack until its C call returns or the process
  exits. No unbounded growth: a plugin becomes a zombie at most once
  (demoted, never re-dispatched).
- **No new external libraries.** `QThread` is Qt6::Core, already linked.
- **Build:** no new library target — `luaengine.cpp` stays in
  `ants_lua_lib` (`add_library` at `CMakeLists.txt:423`, the source
  listed at `:424`). One feature-test source added to an existing test
  bundle (no new `add_executable`).

## 5. Out of scope

- **Full process isolation** (SIGKILL-able per-plugin helper process to
  reclaim a runaway's CPU + RAM) — deferred to **ANTS-1795**. Approach A
  here keeps the UI responsive and neuters the plugin but cannot reclaim
  a deliberately-infinite C call's leaked thread/core; that requires a
  separate process boundary and its own spec cycle.
- **Wiring the dormant `Output`/`Line`/`Prompt`/`KeyPress`/
  `TitleChanged`/`TabCreated`/`TabClosed` events** — owned by
  **ANTS-1736**, which must satisfy the synchronous-veto contract in
  § 2.6.
