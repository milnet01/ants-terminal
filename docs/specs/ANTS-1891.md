# ANTS-1891 — Auto-switcher trust signal v2: inconclusive bucket, harm signal, sample-size floor, session-end positive

**Status:** spec draft, cold-eyes loops 1–10 folded (2026-05-26).
**Kind:** implement.
**Source:** ROADMAP.md ANTS-1891 (in-session-2026-05-26 — ANTS-1890
follow-up; the §8 OQ-3 default-ON flip gate cannot trust a structurally
misleading headline, and the live ledger on 2026-05-26 produced exactly
the misleading shape on its first 2 real-world records).

**Composes with:** ANTS-1735 §2.5 (the effectiveness-ledger contract this
spec sharpens) and §8 OQ-3 (the default-ON flip gate this spec keeps
honest). **Pairs with:** ANTS-1893 (switch-event surfacing — once visible,
the user can sense-check the trust signal); ANTS-1894 (near-miss
telemetry — explains *why* switches don't fire when the ratio is small).
**Extends:** ANTS-1889 (the `model_switch_stats` envelope this spec
modifies). **Does not supersede:** ANTS-1735's INV-1..INV-14 stay
unchanged; this spec adds new outcome fields and aggregation rules
without renumbering existing invariants.

## 1. Problem

The `model_switch_stats` MCP envelope (`src/modelswitchledger.cpp`
`statsEnvelope` at L298–386) reports a structurally misleading headline
on small samples — exactly the regime in which the §8 OQ-3 default-ON
flip decision will be made. Four convergent gaps, verified against the
live ledger on 2026-05-26 (2 records, both
`fromTier="opus"`, `toTier∈{"haiku","sonnet"}`, both
`turns_on_to_tier=0`, one with `under_route_signal_within_5_turns=true`,
neither with `userOverrideWithin5` or `correctionSignalWithin5`).

Compounding the four data-aggregation gaps below is a fifth structural
issue: the **current settlement criteria** for `computeOutcome`
(`src/modelswitchledger.cpp` L203–296 — settlement at L286–287) require
*either* a subsequent auto-switch *or* `kOutcomeWindowTurns` (5)
assistant turns *or* a divergent assistant turn. Most 0-turn downgrades
in practice DO settle (either via a subsequent auto-switch later in the
same session, as the 2026-05-26 ledger's first record did, or via a
divergent assistant turn when the user resumes on a different tier,
as the second record likely did) — but **the very last 0-turn
downgrade in any project's history** has nothing after it to trip
those three clauses. A project where the user finished cleanly on the
cheaper tier and walked away therefore carries one trailing record
stuck at `pending=true` indefinitely, and the would-be "cleanly ended"
signal in problem (d) below has nothing to attach to until the next
session's first auto-switch lands. The spec adds a fourth settlement
clause (§ 2.1) so the trailing-record case can actually be observed.

1. **0-turn records count toward the regret denominator.** In
   `statsEnvelope` L332–338 a record is counted in `measuredDowngrades`
   as soon as it settles (`!r.outcome.pending`), regardless of whether
   `turnsOnToTier > 0`. The denominator therefore includes records that
   carry no information about whether the cheaper tier could handle the
   work — they're inconclusive evidence, not measured success. The 2026-
   05-26 ledger reports `regret_count=0 / measured=2 = 0.0%` over two
   0-turn records (one with `under_route_signal=true` but not folded
   into regret today — problem (b) — and one with no signals at all)
   — false confidence.
2. **Under-route harm is reported but not folded into the regret
   numerator.** L334 reads `regret_count =
   userOverrideWithin5 || correctionSignalWithin5`. The third harm
   signal — `underRouteSignalWithin5` (INV-12: the recommender
   immediately re-recommended a higher tier) — is reported separately
   as `under_route_count` and never folded into the headline regret
   number. On 2026-05-26 the live ledger has 1 under-route record and
   the headline still reads "0 regretted" — the harm is invisible to
   the OQ-3 gate.
3. **Headline overpromises on tiny samples.** Below ~10 measured
   downgrades, "avoided 0 Opus turns, 0 regretted (regret 0.0%)"
   (L361–364) is statistically meaningless. A user reading the
   headline cannot distinguish "the switcher is doing well" from
   "the switcher has barely run, every record happens to be 0-turn,
   and the math says 0/0".
4. **The dominant ledger shape is `turnsOnToTier=0`.** Most auto-
   switches happen at end-of-task — the user finishes the heavy work,
   `refreshAutoModelSwitch` catches the cool-down and switches to the
   cheaper tier, and the user moves on (closes the tab, starts a
   different project) without further turns. `computeOutcome`
   (`src/modelswitchledger.cpp` L203–296) measures success only by
   "user kept working on the new tier without complaint," which never
   observes this common case. A 0-turn record with no negative signals
   today reads as "no evidence" rather than what it almost always is —
   "the user finished cleanly on the cheaper tier."

The four gaps compose: tiny samples + 0-turn dominance + harm signal
omission + flattering headline = the §8 OQ-3 flip can trip on noise
that *looks* like clean success.

Three concerns, all under `src/modelswitchledger.{h,cpp}` and the

### 2.1 Outcome — new positive field

Add one field to the `Outcome` struct
(`src/modelswitchledger.h` L28–34):

```cpp
struct Outcome {
    int  turnsOnToTier            = 0;
    bool userOverrideWithin5      = false;
    bool correctionSignalWithin5  = false;
    bool underRouteSignalWithin5  = false;
    bool sessionCleanlyEndedOnNewTier = false;   // NEW — ANTS-1891
                                                  // placed before `pending`
                                                  // so toJson/fromJson
                                                  // reading order groups
                                                  // all signal bools
                                                  // contiguously
    bool pending                  = true;
};
```

JSON field name: `session_cleanly_ended_on_new_tier`
(snake_case matches the existing outcome-key style in
`toJson`/`fromJson` — the `_within_N_turns` suffix that the other
three signal keys carry deliberately does **not** apply here: this
signal is a quiet-window measurement, not a turn-count window).
`fromJson` defaults missing field to `false` (back-compat for ledger
records written before this spec lands — see § 6). The ROADMAP entry's
wording (`session_completed_cleanly_on_new_tier`) was an informal
working name during item write-up; this spec's name (`session_cleanly_ended_on_new_tier`)
is canonical and the ROADMAP entry is updated in the same commit
(§ 8 Cross-doc).

**Detection** (extends `computeOutcome` at
`src/modelswitchledger.cpp` L203–296). The detection has two paired
mechanics — a new *settlement clause* (so a pending end-of-task record
can actually become non-pending) and the *positive-signal predicate*.

**Derivation of `lastAssistantTurnTsMs`** — added to the
`computeOutcome` body before the settlement check at L286. **Do not
reuse the `onTier` scan at L228–238**: that loop early-breaks at the
first divergent assistant turn, so it tracks the last *on-tier*
assistant turn, not the last assistant turn overall. The quiet-
window predicate needs the absolute last assistant turn, so add a
separate pass over the (already-filtered) `turns` list:

```cpp
// ANTS-1891 — separate scan; do NOT fold into the `onTier` loop
// above (that one early-breaks at first divergent assistant).
qint64 lastAssistantTurnTsMs = 0;
for (const TranscriptTurn &t : turns) {
    if (t.isAssistant && t.tsMs > lastAssistantTurnTsMs)
        lastAssistantTurnTsMs = t.tsMs;
}
```

The empty-turns case leaves `lastAssistantTurnTsMs == 0`; the
settlement predicate's `max(switchTsMs, lastAssistantTurnTsMs)`
fallback then collapses to `switchTsMs` (which the `switchTsMs > 0`
guard protects from malformed records — see below).

**New settlement clause** — added alongside the three existing
settlement paths at L286–287 (`dwellEndedByNextAuto`,
`fullWindowObserved`, `dwellEndedByDivergence`):

> A pending downgrade settles via **`dwellEndedByQuietWindow`** when
> `switchTsMs > 0` **and** `nowMs - max(switchTsMs,
> lastAssistantTurnTsMs) ≥ kCleanEndQuietMs`, where
> `lastAssistantTurnTsMs` is the `tsMs` of the most recent assistant
> turn in `postSwitchTurns` (or `switchTsMs` itself when
> `postSwitchTurns` contains no post-switch assistant entries). The
> `switchTsMs > 0` guard rejects malformed records whose `ts` field
> failed `parseIso8601Ms` (which returns `0` on parse failure —
> `src/modelswitchledger.cpp` L420–423); a 0-ts record would
> otherwise satisfy `nowMs - 0 ≥ kCleanEndQuietMs` for any real
> `nowMs` and spuriously earn settlement + clean-end credit.

**Design intent: empty-`postSwitchTurns` is the credited case.** When
the controller fills outcomes on first launch after a long gap (e.g.
app reopens 30 min after the user closed it), a pending 0-turn
downgrade from before the close will settle via this clause and earn
the clean-end credit. This is the *intended* behaviour — it is the
exact "user finished cleanly on the cheaper tier and walked away"
case from § 1 problem (d). The ½-weight credit (§ 2.2) discounts the
uncertainty that the user might have interrupted rather than
finished; over many records the trade-off averages out, and the
trailing-record case otherwise contributes zero signal at all.

This is **additive** — the three pre-existing settlement clauses still
apply to upgrades, multi-turn downgrades, and any record whose dwell
ends naturally. The new clause exists specifically so the end-of-task
0-turn-downgrade case (problem (d)) gets a deterministic settlement.
Without it, the new positive-signal predicate below would never have
a settled record to act on.

**Positive-signal predicate** — on a settled downgrade,
`sessionCleanlyEndedOnNewTier` becomes `true` iff **all** of:

- `userOverrideWithin5 == false`.
- `correctionSignalWithin5 == false`.
- `underRouteSignalWithin5 == false`.
- **EITHER** `turnsOnToTier > 0` (the user kept working on the new
  tier — already-measured success, kept as the inclusive case for
  symmetry) **OR** the new `dwellEndedByQuietWindow` clause is what
  settled the record (i.e. `nowMs - max(switchTsMs,
  lastAssistantTurnTsMs) ≥ kCleanEndQuietMs`).

Only downgrades earn the positive signal — the "avoided Opus turns"
framing requires `fromTier != toTier` and the lower tier to be cheaper.
Upgrades never set it (mirrors ANTS-1735 INV-12's downgrade-only
guard).

**`nowMs` plumbing.** `nowMs` is the only `now` that crosses the pure-
function boundary; it is injected by the controller. To keep v1 call
sites (and the existing `model_switch_ledger` test files on the
`test_core` bundle) compiling without lockstep edits, `nowMs`
defaults to `0`. With
`nowMs == 0`, the new quiet-window clause is unreachable: any real
`lastAssistantTurnTsMs > 0` (or, when `postSwitchTurns` is empty,
any real `switchTsMs > 0`) makes the comparison `nowMs - max(…) ≥
kCleanEndQuietMs` a large-negative-vs-positive check that is always
false; pre-existing settlement behaviour is bit-for-bit preserved. Production callers (the controller's outcome-fill tick)
MUST pass a real `nowMs`; the test seam (§ 2.5) makes the parameter
explicit.

```cpp
// modelswitchledger.h — computeOutcome signature
// (`kCleanEndQuietMs` declared once in § 2.4, used here)
OutcomeFillResult computeOutcome(
    const QString &fromTier, const QString &toTier,
    qint64 switchTsMs,
    const QList<TranscriptTurn> &postSwitchTurns,
    const QList<AutoSwitch>     &subsequentAutoSwitches,
    const QStringList           &subsequentRecommendedTiers,
    const Outcome               &inputBefore = {},   // default preserved
    qint64                       nowMs       = 0);   // NEW (defaulted)
```

The new parameter slots at the end with a default so the existing v1
test-bundle call sites compile unchanged (per § 6 Migration). The
existing `inputBefore = {}` default is preserved verbatim — no v1
caller's argument list shifts position.

The `changed` flag in `OutcomeFillResult` (L289–294) gains a sixth
comparison for `sessionCleanlyEndedOnNewTier` — without this, a record
whose only update on a tick is the new positive signal would not be
flushed by the controller (cf. INV-12 below).

Existing expression at `src/modelswitchledger.cpp` L290–294:

```cpp

           || (res.outcome.turnsOnToTier != inputBefore.turnsOnToTier)

           || (res.outcome.correctionSignalWithin5 != inputBefore.correctionSignalWithin5)
           || (res.outcome.underRouteSignalWithin5 != inputBefore.underRouteSignalWithin5);
```

Post-change — append one clause:

### 2.2 statsEnvelope — denominator, regret numerator, weighted credit

Amend (do **not** replace) the per-record loop in `statsEnvelope`
(`src/modelswitchledger.cpp` L298–386 — current loop body at L308–339)
so the regret denominator excludes inconclusive records, the regret
numerator includes under-route, and weighted-avoided credits clean
session-ends. All existing counters (`downgrades`, `upgrades`,
`opusAvoided`, `opusRoutedIn`, `toHaiku`, `toSonnet`, `toOpus`,
`pendingCount`) keep their existing increments verbatim — the new
logic is **additive**, not a rewrite.

Two new `int` locals — declare alongside the existing counter list at
the top of `statsEnvelope` (currently L299–303):

```cpp
int inconclusiveCount = 0;   // NEW — settled downgrades with no
                             //       signal AND no positive evidence
int cleanEndCount     = 0;   // NEW — settled downgrades whose
                             //       sessionCleanlyEndedOnNewTier=true
```

The new fragment slots into the existing
`if (isDowngrade && !r.outcome.pending)` block (currently L332–338),
replacing its body:

```cpp
// (existing per-record loop, existing counters preserved …)
// Replace the body of:
//   if (isDowngrade && !r.outcome.pending) { … }
// with:
if (isDowngrade && !r.outcome.pending) {
    const bool hasNegativeSignal =
        r.outcome.userOverrideWithin5
     || r.outcome.correctionSignalWithin5
     || r.outcome.underRouteSignalWithin5;
    const bool hasPositiveEvidence =
        r.outcome.turnsOnToTier > 0
     || r.outcome.sessionCleanlyEndedOnNewTier;

    if (r.outcome.underRouteSignalWithin5)
        ++underRouteCount;
    if (r.outcome.sessionCleanlyEndedOnNewTier)
        ++cleanEndCount;

    if (hasNegativeSignal || hasPositiveEvidence) {
        ++measuredDowngrades;
        if (hasNegativeSignal)
            ++regretCount;          // INV-1: under-route folded in
    } else {
        ++inconclusiveCount;        // INV-2: 0-turn + 0-signals
    }
}
// (`opusAvoided`, `opusRoutedIn`, `downgrades`, `upgrades`,
//  `pendingCount`, `byTier` increments unchanged — see L308–328 of
//  the current source.)
```

**Bucketing truth table** — for an implementer mis-bucketing risk,
the four possible settled-downgrade shapes and the buckets they
land in. (Settled = `!outcome.pending`. "Negative signal" =
`userOverrideWithin5 || correctionSignalWithin5 ||
underRouteSignalWithin5`. The columns count the same record into
multiple counters when both apply — they are not mutually
exclusive.)

| Record shape | `measuredDowngrades` | `inconclusiveCount` | `regretCount` | `underRouteCount` | `cleanEndCount` | `opusAvoided` |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| Negative signal only (turns=0, clean-end=false) | 1 | 0 | 1 | per-signal | 0 | 0 |
| Positive turns (turns>0, no signal, clean-end=false) | 1 | 0 | 0 | 0 | 0 | turns |
| Clean-end only (turns=0, clean-end=true, no signal) | 1 | 0 | 0 | 0 | 1 | 0 |
| Negative signal, clean-end forced false (INV-4 prohibits both) | 1 | 0 | 1 | per-signal | 0 | 0 |
| Neither (turns=0, no signal, clean-end=false) — inconclusive | 0 | 1 | 0 | 0 | 0 | 0 |

INV-4 enforces that `sessionCleanlyEndedOnNewTier` is `false` whenever
any negative signal is true, so the row "negative + clean-end" cannot
have `clean-end=true` simultaneously — listed as the negative-signal
shape for symmetry. The clean-end-only row IS measured (because the
positive evidence is real) and its ½-Opus-turn credit lands in
`weighted_avoided` via `cleanEndCount`; it never inflates the
`regret_count` numerator because no negative signal fired.

**Note on the `underRouteCount` column.** The "per-signal" entry
means **1 if `underRouteSignalWithin5==true`, else 0** — the counter
is gated on that single bool, not on the count of negative signals.
A record with `userOverride=true` AND `underRoute=true` contributes
`+1` to both `regretCount` (via the OR fold-in) and `underRouteCount`
(via the standalone increment); a record with `underRoute=false` and
some other negative signal contributes `+1` to `regretCount` only.
The "Neither — inconclusive" row cannot have `underRoute=true`
because under-route is itself a negative signal — so its row entry
is `0` by definition.

```cpp
// Weighted credit — clean session-ends count as ½ of an Opus turn avoided.
const double weightedAvoided =
    static_cast<double>(opusAvoided) + 0.5 * cleanEndCount;
```

Three new envelope fields (additive — existing fields keep their
contract; `regret_count` and `regret_rate` *semantics* tighten —
see § 6 Migration):

```cpp
env["inconclusive_count"]   = inconclusiveCount;
env["clean_end_count"]      = cleanEndCount;
env["weighted_avoided"]     = weightedAvoided;       // double
env["headline_floor"]       = kHeadlineFloorMeasured; // 10 (constant)
```

### 2.3 Headline formatter — floor + scope + weighted credit

Replace the L353–365 block. The format is one of (in branch order):

```
auto-switch OFF
auto-switch ON (floor=<floor>) in this project: no switches yet
auto-switch ON (floor=<floor>) globally: no switches yet
auto-switch ON (floor=<floor>) in this project: insufficient data (<N>/<F> measured)
auto-switch ON (floor=<floor>) globally: insufficient data (<N>/<F> measured)
auto-switch ON (floor=<floor>) in this project: avoided <X> Opus turns (+<Y> clean end), <R> regretted (regret <P>%)
auto-switch ON (floor=<floor>) globally: avoided <X> Opus turns (+<Y> clean end), <R> regretted (regret <P>%)
```

Where:

- `<floor>` = `cfg.floorTier` (`haiku` | `sonnet`) — exposes the
  current floor in the headline so "no switches yet" / "insufficient
  data" reads honestly (improvement E).
- `<N>` = `measuredDowngrades` (new tightened definition — § 2.2).
- `<F>` = `kHeadlineFloorMeasured` (10 by default; see § 2.4).
- `<X>` = `opusAvoided` (existing).
- `<Y>` = `cleanEndCount` (new).
- `<R>` = `regretCount` (new tightened definition — § 2.2).
- `<P>` = `regretRate`, 1 decimal place (existing format).

When `recs.isEmpty()`, the headline is the "no switches yet" form.
When `recs` non-empty but `measuredDowngrades < kHeadlineFloorMeasured`,
the "insufficient data" form. At/above the floor, the full form. The
floor branch uses `measuredDowngrades` (the *measured* count), so a
ledger full of inconclusive records reads "insufficient data (0/10
measured)" rather than the flattering ratio.

### 2.4 Constants

```cpp
// src/modelswitchledger.h
constexpr int    kHeadlineFloorMeasured = 10;   // headline ratio floor
constexpr qint64 kCleanEndQuietMs       = 10 * 60 * 1000;  // § 2.1
```

`kHeadlineFloorMeasured` is intentionally **smaller** than the §8 OQ-3
default-ON flip threshold (50 switches across 10 sessions). The
headline floor controls *when the user sees a ratio*; the OQ-3 flip
threshold (out of scope here — lives in the future flip-gate code)
controls *when the default flips*. Two different thresholds because
the user benefits from seeing the ratio earlier than the flip can
safely happen.

### 2.5 Controller call site

`src/claudestatuswidgets.cpp` `fillPendingLedgerOutcomes` — the
**path overload** gains a `nowMs` parameter so the new quiet-window
settlement (§ 2.1) has a `now` to compare against. The **public no-
arg overload's external signature is unchanged**; internally it
computes `nowMs` from `QDateTime::currentMSecsSinceEpoch()` and
forwards it to the path overload. The declaration in
`src/claudestatuswidgets.h` for the path overload (currently at
L116) updates to take the new arg; the public declaration at L109
stays put. Without this header touch, INV-13's test (calling the
path overload with explicit `nowMs`) cannot compile.

Post-change signatures:

```cpp
// src/claudestatuswidgets.h — public (production caller; status timer)
void fillPendingLedgerOutcomes();          // unchanged signature
                                           // body computes nowMs and
                                           // forwards to the path overload

// src/claudestatuswidgets.h — test seam (behavioural tests bypass throttle)
void fillPendingLedgerOutcomes(const QString &ledgerPath,
                               qint64 nowMs = 0);   // NEW second arg
```

Post-change body of the public no-arg overload (replaces L1524–1533):

```cpp
void ClaudeStatusBarController::fillPendingLedgerOutcomes()
{
    const qint64 nowMs = QDateTime::currentMSecsSinceEpoch();
    if (m_lastPendingFillMs > 0 &&
        nowMs - m_lastPendingFillMs < kPendingFillIntervalMs) {
        return;
    }
    m_lastPendingFillMs = nowMs;
    // ANTS-1891: forward `nowMs` so the path overload (and the pure
    // `computeOutcome` it calls per pending record) can evaluate the
    // new quiet-window settlement clause.
    fillPendingLedgerOutcomes(ModelSwitchLedger::defaultLedgerPath(),
                              nowMs);
}
```

The only delta vs the pre-change body is the second argument to the
forwarding call at L1532 (`, nowMs` appended). The throttle gate
keeps the existing semantics — `nowMs` is computed once for both
purposes.

**Throttle ownership note (re-stating the existing ANTS-1890
contract, plus the ANTS-1891 clock seam).** Per the existing
ANTS-1890 docstring on the path overload (`claudestatuswidgets.cpp`
L1535–1537 — "Test seam. Behavioural overload reachable from
behavioural tests; bypasses the 30 s throttle"), the path overload
already bypasses the throttle today. ANTS-1891 does NOT change
this: the new `nowMs` parameter is **purely a clock seam for
`computeOutcome`**, not a throttle-state input. The path overload
continues to neither read nor write `m_lastPendingFillMs`; the
no-arg overload's throttle gate at L1527–1530 is unchanged
(post-change body still reads and writes `m_lastPendingFillMs`
once per call). A test that drives the path overload directly
does NOT update `m_lastPendingFillMs`; a subsequent call to the
no-arg overload from production code can therefore see arbitrary
throttle state relative to the test's wall-clock. Tests that mix
both overloads must reset the controller (or its
`m_lastPendingFillMs` cache, via a test seam if one is added)
between calls. INV-13's test does NOT mix overloads, so this is
informational, not a contract.

**Pre-change** (currently in source at L1524–1533): the public no-arg
overload calls `QDateTime::currentMSecsSinceEpoch()` at L1526 only for
the throttle gate, then calls `fillPendingLedgerOutcomes(defaultLedgerPath())`
at L1532 — single-arg, no `nowMs` forwarded.

**Post-change**: the public overload reuses that same `nowMs` for both
the throttle gate AND the forwarding call to the path overload
(replacing the single-arg L1532 call with
`fillPendingLedgerOutcomes(defaultLedgerPath(), nowMs)`). The path
overload at L1538–1614 forwards `nowMs` into each `computeOutcome`
call at L1592–1595.

The test-seam default (`nowMs = 0`) preserves v1 test behaviour: any
existing test that calls `fillPendingLedgerOutcomes(path)` without an
explicit `nowMs` still compiles, and the unreachable-quiet-window
guarantee from § 2.1 means v1 outcome behaviour is bit-for-bit
preserved. New v2 tests pass `nowMs` explicitly to exercise the
quiet-window branch.

No other call-site changes — the `model_switch_stats` MCP dispatch
(`src/remotecontrol.cpp` `cmdModelSwitchStats`) calls `statsForScope`
which calls `statsEnvelope`; both pick up the new fields and headline
automatically.

## 3. Invariants

- **INV-1** — `regret_count` is the count of settled downgrades on which
  any of `overrideUndidDowngrade`, `correctionSignalWithin5`, or
  `underRouteSignalWithin5` is true. (Adds under-route to the existing
  numerator — addresses problem (b).) **ANTS-1957:** the override term was
  narrowed from the broad `userOverrideWithin5` (any manual `/model`) to the
  direction-aware `overrideUndidDowngrade` (a manual switch to a tier *above*
  the downgrade's `to_tier` — i.e. the user moved back up). A lateral /
  further-down / same-tier manual switch is not evidence the downgrade was
  wrong and no longer inflates regret; `userOverrideWithin5` still drives the
  ANTS-1890 cool-down and clean-end conservatism. *Test:*
  `tests/features/model_switch_stats_v2/test_model_switch_stats_v2.cpp`
  (`ModelSwitchStatsV2_ANTS1957.NonCorrectiveOverrideIsNotRegret`).
- **INV-2** — A settled downgrade contributes to `measuredDowngrades`
  iff it has at least one negative signal (per INV-1) **or** positive
  evidence (`turnsOnToTier > 0` **or**
  `sessionCleanlyEndedOnNewTier`). Settled downgrades with neither
  contribute to `inconclusive_count` instead. (Excludes 0-turn-zero-
  signal records from the regret denominator — addresses (a).) *Test:*
  `tests/features/model_switch_stats_v2/test_inconclusive_bucket.cpp`.
- **INV-3** — `regret_rate = 100.0 * regret_count /
  measured_downgrades` when `measured_downgrades > 0`, else `0.0`.
  (The denominator is the *new* tightened count.) Envelope consumers
  MUST check `measured_downgrades > 0` (or the headline string —
  INV-6) before treating `regret_rate` as meaningful: a non-empty
  ledger of entirely inconclusive records emits `regret_rate=0.0`
  identical to "no records at all," and the headline / new
  `inconclusive_count` field are the disambiguators. *Test:*

  `tests/features/model_switch_stats_v2/test_quiet_window_edge.cpp`.
- **INV-12** — `OutcomeFillResult.changed` is `true` whenever
  `outcome.sessionCleanlyEndedOnNewTier` differs from
  `inputBefore.sessionCleanlyEndedOnNewTier`. **Defensive**: on the
  current production path, settlement via the new quiet-window
  clause flips `pending` true→false in the same call that flips the
  clean-end signal, so the existing `pending` comparison already
  fires `changed=true`. The sixth comparison costs nothing and
  protects against two forward scenarios: (i) future callers (tests,
  or a future controller change) that invoke `computeOutcome` on an
  already-settled record where the clean-end signal could flip in
  isolation; (ii) a future tweak that lifts
  `fillPendingLedgerOutcomes`'s settled-record skip (`L1556`
  `if (!r.outcome.pending) continue;`) to retroactively scan settled
  records for the new signal. Without the sixth comparison, either
  scenario would silently drop the clean-end credit. *Test:*
  `tests/features/model_switch_stats_v2/test_changed_flag_clean_end.cpp`.
- **INV-13** — `computeOutcome` settles a pending downgrade
  (sets `outcome.pending = false`) via the new
  `dwellEndedByQuietWindow` clause when
  `switchTsMs > 0` **and** `nowMs - max(switchTsMs,
  lastAssistantTurnTsMs) ≥ kCleanEndQuietMs`, even when none of the
  three pre-existing settlement clauses (next-auto, full-window,
  divergent-turn) apply. `lastAssistantTurnTsMs` is the `tsMs` of
  the most recent **assistant** turn in `postSwitchTurns`; user
  turns are not consulted for the quiet-window check, so a
  post-switch user turn with no assistant reply yet leaves
  `lastAssistantTurnTsMs == 0` and the `max(switchTsMs, 0)`
  fallback reduces the predicate to `nowMs - switchTsMs ≥
  kCleanEndQuietMs` (the same form as the empty-`postSwitchTurns`
  case). The `switchTsMs > 0` guard prevents a malformed record
  (whose `ts` failed `parseIso8601Ms`, returning `0` —
  `src/modelswitchledger.cpp` L420–423) from spuriously settling
  via this clause and earning a clean-end credit; the three pre-
  existing clauses are immune because they key off subsequent-
  record existence rather than `switchTsMs`. The pre-existing
  clauses are unchanged — this clause is additive. Upgrades are
  unaffected by this clause (the three pre-existing paths continue
  to govern upgrade settlement). *Test:*
  `tests/features/model_switch_stats_v2/test_quiet_window_settles.cpp`
  (the test bundle includes a malformed-ts case: `switchTsMs=0`,
  `nowMs - 0 ≥ kCleanEndQuietMs` must NOT settle and must NOT set
  the clean-end signal).

## 6. Migration / compatibility

- **Existing ledger records on disk** (written before this spec ships)
  lack the `session_cleanly_ended_on_new_tier` JSON field. `fromJson`
  reads missing fields as `false` (per INV-10), so legacy records
  load cleanly and aggregate as if their cleanly-ended signal had
  not been observed. The next `fillPendingLedgerOutcomes` pass on a
  still-pending legacy record will compute and persist the new field
  for it **only when settlement happens via the new
  `dwellEndedByQuietWindow` clause** — a legacy pending record that
  settles on a later tick via one of the three pre-existing clauses
  (`dwellEndedByNextAuto`, `fullWindowObserved`, `dwellEndedByDivergence`)
  will NOT earn `sessionCleanlyEndedOnNewTier=true` even when
  objectively true. Acceptable: divergence settlement means the user
  kept working, so any "positive evidence" is captured by
  `turnsOnToTier > 0` (the natural counter for the user-worked case)
  rather than the clean-end signal. Settled legacy records keep
  `false` permanently (we don't retroactively rescan settled records
  — keeps the fill path bounded).
- **`regret_count` semantics tighten**. Pre-1891 callers reading the
  envelope's `regret_count` got "user override or correction"; post-
  1891 they get "user override or correction or under-route". This is
  a behaviour change for any external reader that compared
  `regret_count` to `under_route_count` separately. The only known
  caller is the `model_switch_stats` MCP dispatch
  (`src/remotecontrol.cpp` — `cmdModelSwitchStats` at L7553) which
  forwards both fields verbatim; the headline switcher behaviour
  does not depend on the pre-1891 value. Acceptable break — flagged
  in CHANGELOG + CLAUDE.md behavioural-notes entry.
- **`regret_rate` semantics tighten** — denominator changes from
  "settled downgrades" to "settled downgrades with positive evidence
  or negative signal." A pre-1891 ledger that was producing a
  flattering 0.0% over inconclusive records will now produce a
  `regret_rate` over fewer records (possibly `0.0` still if all
  measured ones happened to be clean — but the new `inconclusive_count`
  makes the small N visible to the caller).
- **Envelope-schema additions are additive.** `inconclusive_count`,
  `clean_end_count`, `weighted_avoided`, `headline_floor` are new
  keys; existing readers ignoring unknown keys are unaffected.
- **`computeOutcome` signature gains a defaulted `nowMs` parameter**.
  The new parameter is added **at the end** of the parameter list with
  `= 0` default, so the existing v1 test-bundle call sites
  (`tests/features/model_switch_ledger/`) and the controller path
  (`fillPendingLedgerOutcomes` in `claudestatuswidgets.cpp`) compile
  unchanged on the bump. The production caller is updated to pass a
  real `nowMs` (§ 2.5) so the new quiet-window settlement actually
  fires; tests that don't care get the bit-for-bit pre-1891 behaviour
  via the default (the quiet-window comparison `nowMs -
  lastAssistantTurnTsMs ≥ kCleanEndQuietMs` is unreachable when
  `nowMs == 0` and any real `lastAssistantTurnTsMs > 0`). No out-of-
  tree consumers of `ants_core_lib` exist today (the project ships as
  a statically-linked executable); a future out-of-tree consumer
  would compile against the new default-arg signature unchanged and
  would need to opt into the quiet-window behaviour by passing a
  real `nowMs`.
- **ETag composes** — `model_switch_stats` already emits an
  envelope-wide ETag per ANTS-1499; the new fields are part of the
  envelope JSON so the ETag naturally bumps on any change.

## 9. Open questions

- **OQ-1: Floor value (10).** Is 10 measured downgrades the right
  headline floor? The §8 OQ-3 flip uses 50 — too high to be the
  user's first glimpse of the ratio. 10 is small enough to reach in
  a few days of normal use but large enough that a single 100% or
  0% record does not dominate. Re-tune if live data over the next
  release cycle says otherwise; the constant is centralised
  (`kHeadlineFloorMeasured`) for easy adjustment.
- **OQ-2: Quiet window (10 min) — and constant sharing.** Is 10 min
  the right quiet-window for "session cleanly ended"? Shorter (e.g.
  5 min) classifies more records as clean-end but risks a "user just
  stepped away briefly" false positive. Longer (e.g. 30 min) is
  conservative but slows the clean-end count's growth. 10 min is the
  *same numeric value* as ANTS-1890's `kOverrideCooldownMs`
  (`modelautoswitch.h` — `10 * 60 * 1000`). The spec keeps a separate
  `kCleanEndQuietMs` constant because the two thresholds answer
  different questions (override-cooldown is "stop trying to switch
  back too soon"; quiet-window is "consider the session ended");
  they could legitimately diverge later (e.g. tighter override
  cool-down, looser quiet-window). If a future tuning pass concludes
  they must always move together, fold both into a single shared
  constant — the spec does not preclude this. Re-tune either if
  real-world records call for it.
- **Design note (not an OQ): retroactive credit for pre-1891 settled
  records.** § 6 Migration intentionally does **not** rescan settled
  legacy records to compute their clean-end signal (the fill path is
  bounded; a retroactive sweep would re-touch every record on every
  tick). One consequence is that pre-1891 settled records contribute
  neither to `clean_end_count` nor (under the new tighter
  denominator) to `measured_downgrades` — they fall into
  `inconclusive_count` instead. The §8 OQ-3 default-ON flip gate's
  countdown therefore effectively resets for post-1891 data: the
  gate's "≥ 50 measured downgrades across ≥ 10 sessions" criterion
  can only be met by switches that happen after this spec ships.
  This is the intended behaviour — the flip decision should be made
  on the honest signal, not on a back-patched one. The future
  flip-gate spec (§ 5 Out of scope) inherits this trade-off
  unchanged; no code change required here.
