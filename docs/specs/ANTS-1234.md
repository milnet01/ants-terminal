# ANTS-1234 — RoadmapDialog v2: `/`-focus + Esc-clear + auto-expand on match

- **Status:** ✅ Shipped 2026-05-11 in [Unreleased]. Spec
  cold-eyes-clean after 7 loops + ~25 verified findings fixed
  (audit trail in `ROADMAP.md` § "📝 Cold-eyes 2026-05-11").
  ROADMAP bullet flipped 💭 → ✅; CHANGELOG entry added.
- **Source:** roadmap-v2 research synthesis 2026-05-11 (Linear,
  GitHub Issues, Notion, VS Code, Slack — all use `/` as the
  search-focus keybinding, Esc to dismiss); user keyboard-first /
  partially-sighted workflow.
- **Lanes:** roadmapdialog (key event handler + renderCardsHtml
  auto-expand wiring).
- **Kind:** implement (extends the existing search; no new module).

## 1. Problem

The Roadmap dialog already ships a working substring filter:
`m_searchBox` (`src/roadmapdialog.cpp:1481`) is debounced 120 ms,
supports `id:NNNN` jump shortcut + plain substring match across
`id + headline + layman + body` (`renderCardsHtml` line 1019-1023),
and survives across re-renders. What it doesn't ship is the
keyboard-first ergonomics that a heavy roadmap-scanning user
expects from every other tool they touch:

1. **No `/` focus.** To type a search, the user must Tab into the
   box or mouse-click it. Linear / GitHub / Notion / VS Code /
   Slack all bind `/` to focus-search (the de-facto convention
   since IRC). A keyboard-first user — especially one driving the
   dialog via screen reader — currently can't reach the box without
   counting Tab stops.

2. **No Esc-clear.** Esc closes the dialog (good default), but
   gives the user no way to undo a search without retyping. In
   practice users learn to Ctrl+A → Backspace, which is two key
   sequences and surfaces focus problems for keyboard-only users.

3. **No auto-expand on match.** The card renderer already filters
   so that only matching bullets survive (any card whose
   `id + headline + layman + body` contains the predicate stays).
   But matched cards render *collapsed* — the user sees the summary
   row + ID + date, and has to click the `▾` toggle to see the
   body where the match might live. For a body-only match (e.g.
   searching "scrollback" hits ANTS-1188's body, not its
   summary), the user sees a card with no visible reason it
   matched. Linear / GitHub auto-expand on match; we should too.

User-impact: keyboard-first ergonomics. The dialog is currently
keyboard-*usable* but not keyboard-*fluent*. ANTS-1235 fixed the
screen-reader vocabulary; ANTS-1236 merged the cheatsheet via
commit `daceb70` (currently in [Unreleased]); this entry adds the
missing keybind. The cheatsheet table gains one row when this
lands — § 4 INV-9 covers the lockstep.

## 2. Mechanism — what was investigated, what was chosen

### 2.a Rejected — `Ctrl+F` instead of `/`

`Ctrl+F` is the platform-native "find" shortcut on most desktops
(Find in Files, Find in Browser, etc.). Rejected because:

- The Roadmap dialog runs inside the terminal, where Ctrl+F is
  often grabbed by TUIs (vim, less, tmux). On a Roadmap dialog
  invoked from a tmux pane, Ctrl+F is ambiguous.
- The roadmap-v2 research synthesis (2026-05-11) found every
  modern keyboard-first tool — Linear, GitHub, Notion, VS Code's
  command palette, Slack's quick-switcher — uses `/`. Matching
  user muscle memory beats matching desktop-find convention.
- `Ctrl+F` is already mapped to `QTextBrowser::find()` in some Qt
  builds; binding it ourselves risks conflict.

### 2.b Rejected — Esc-clear without focus check

Naively binding Esc to "clear the search box" anywhere in the
dialog breaks the existing Esc-closes-dialog behaviour, which is
the standard Qt `QDialog::reject` default and what the cheatsheet
already documents (ANTS-1236 row 2).

### 2.c Rejected — auto-expand all cards when search is non-empty

Auto-expanding every visible card when search is active makes the
list shape unreadable on dense queries — typing "ANTS" would
explode every card. Auto-expand must be tied to *which cards
actually need expansion to surface the match*, i.e. cards whose
*body* (continuation lines) contains the match. Summary-only
matches stay collapsed because the summary is already visible.

### 2.d Chosen — `/`-focus + targeted Esc-clear + body-match auto-expand

Key decisions:

1. **`/` focuses `m_searchBox`.** Extend the existing
   `RoadmapDialog::keyPressEvent` override (added in ANTS-1236 for
   the `?` cheatsheet trigger) to also catch
   `event->text() == "/"`. Match on `text()` not
   `Qt::Key_Slash` for the same layout-robust reason ANTS-1236 uses
   for `?` (AltGr on Polish, dead-key sequences, etc.). The
   handler calls `m_searchBox->setFocus(Qt::ShortcutFocusReason)`
   and `selectAll()` so any pre-existing search predicate is
   primed for replacement on the user's next keystroke.

   **Gate:** if `m_searchBox` already has focus, fall through to
   `QDialog::keyPressEvent` — the user is typing `/` into the
   search predicate itself. Legitimate use cases: searching for a
   URL fragment (`http://`), a path token (`docs/specs`), or any
   bullet that contains a literal slash in its body or Layman line.

2. **Esc on focused search clears + blurs.** Install an event
   filter on `m_searchBox` (lighter than subclassing). When the
   filter sees `QKeyEvent::Type::KeyPress` with
   `key() == Qt::Key_Escape`, it calls:

   ```cpp
   m_searchBox->clear();              // also triggers rebuild via textChanged
   m_searchBox->clearFocus();         // Qt picks the next focus per tab order
   return true;                       // consume the event — load-bearing
   ```

   The `return true` is load-bearing: without it, the unhandled
   Esc bubbles to `QDialog::reject` and closes the dialog (which
   is exactly what we want to *prevent* on a focused-search Esc).
   For every non-Escape key, the filter returns
   `QDialog::eventFilter(obj, event)` so PgUp, F5, typing
   characters, etc. all reach the QLineEdit normally.

   When the search box does *not* have focus, the existing
   `QDialog::reject` path runs — Esc closes the dialog. This means
   one Esc undoes a search (predicate gone, focus back on the
   viewer); a second Esc closes the dialog. Matches Linear /
   GitHub behaviour exactly.

   **Detail:** the `clear()` call fires `textChanged("")` which
   starts `m_searchDebounce`. The 120 ms debounce is acceptable
   — the user sees the search field empty immediately; the card
   list re-renders 120 ms later. Faster would mean writing a
   bypass path that rebuilds synchronously on Esc-clear, which
   adds complexity for no ergonomic win on a sub-second action.

3. **Auto-expand cards whose body matches the predicate.** Inside
   `renderCardsHtml::emitCard`, before computing the `expanded`
   flag, compute a body-only-match override.

   Key fact about `BulletRecord` (verified against `roadmapdialog.cpp:
   516-564`): `rec.body` is the joined post-emoji text including the
   headline, the `Layman:` line, the `Kind:` line, and every
   continuation paragraph. `rec.headline` (first **bold** chunk),
   `rec.layman`, and `rec.id` are *substrings* of `body` in the
   normal case. **Edge case:** when the bold chunk exceeds 120 chars,
   `roadmapdialog.cpp:540` truncates `rec.headline` and appends
   `"…"`, so `rec.headline` is no longer a literal substring of
   `body`. Practical consequence: a search predicate that lives only
   in the truncated tail of an over-long headline will (a) match
   `rec.body` (because `body` carries the un-truncated text), (b)
   NOT match the truncated `rec.headline`, so `predicateOnlyInBody`
   evaluates true and the card auto-expands. This is accepted as a
   feature: surfacing the full hit by expanding when a headline
   match would otherwise be hidden by truncation. INV-6 below is
   worded as "matches the *visible* summary text", reflecting this.

   So a "match is only in continuation prose" test is: matches
   `body` but does NOT match `id`, `headline`, or `layman`:

   ```cpp
   const bool predicateOnlyInBody =
       !plainSearch.isEmpty() &&
       rec.body.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.id.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.headline.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.layman.contains(plainSearch, Qt::CaseInsensitive);
   const bool expanded = opts.expandedItems.contains(rec.id)
                         || predicateOnlyInBody;
   ```

   Why the three `!contains` checks: if the match is already
   visible in the card's summary row (ID chip, headline text,
   Layman line — all rendered on the collapsed card), there's no
   reason to expand — the user already sees why the card matched.
   Only when the match is *exclusively* in continuation prose do
   we expand.

   Importantly: this expansion does NOT mutate `m_expandedItems`.
   It's a render-time-only flag. When the user clears the search,
   the card returns to its prior expand state (whatever they had
   manually set). This preserves the user's intent and avoids the
   "my expand state randomly changed" surprise GitHub has been
   criticised for.

4. **`id:NNNN` jumps don't auto-expand.** The `id:NNNN` shorthand
   filters to a single card; auto-expanding that one card is fine
   in principle, but the rendered list is already a single-item
   result, so the user almost-always wants the body. We special-
   case `idMarker` to also trigger expansion. Concretely:
   `if (!idMarker.isEmpty() && rec.body.contains(idMarker))` adds
   to the `expanded` OR.

   Subtle but useful: typing `id:1188` lands the user on
   ANTS-1188 with its body open, no extra click.

## 3. Fix

### 3.a Header changes — `src/roadmapdialog.h`

The existing override `keyPressEvent` (ANTS-1236) already exists.
Extend it to handle `/` in addition to `?`. No new methods.

Add a private helper:

```cpp
// ANTS-1234 — focus the search box on `/` (layout-robust),
// select-all so the next keystroke replaces any pre-existing
// predicate. No-op if m_searchBox is null.
void focusSearchBox();
```

No new members. The event filter on `m_searchBox` (for Esc-clear)
uses the existing dialog as the filter object — the dialog
already inherits `QObject::eventFilter` via `QDialog`. Override
in the .cpp.

### 3.b Source changes — `src/roadmapdialog.cpp`

**Four discrete edits:**

1. **Extend `keyPressEvent`** (at `roadmapdialog.cpp:1928` — the
   existing ANTS-1236 handler). Add a `/` branch before the `?`
   branch:

   ```cpp
   if (event
       && event->text() == QLatin1String("/")
       && !(m_searchBox && m_searchBox->hasFocus())) {
       focusSearchBox();
       event->accept();
       return;
   }
   ```

2. **Implement `focusSearchBox()`** as a private member:

   ```cpp
   void RoadmapDialog::focusSearchBox() {
       if (!m_searchBox) return;
       m_searchBox->setFocus(Qt::ShortcutFocusReason);
       m_searchBox->selectAll();
   }
   ```

3. **Install the Esc-clear event filter** in the ctor, just after
   the `m_searchBox->setClearButtonEnabled(true)` call (line 1485):

   ```cpp
   m_searchBox->installEventFilter(this);
   ```

   And override `eventFilter` on the dialog:

   ```cpp
   bool RoadmapDialog::eventFilter(QObject *obj, QEvent *event) {
       if (obj == m_searchBox && event->type() == QEvent::KeyPress) {
           auto *ke = static_cast<QKeyEvent *>(event);
           if (ke->key() == Qt::Key_Escape) {
               m_searchBox->clear();
               m_searchBox->clearFocus();
               return true;  // consume — don't let QDialog::reject fire
           }
       }
       return QDialog::eventFilter(obj, event);
   }
   ```

4. **Auto-expand on body-only match in `emitCard`** (lambda starts
   at `roadmapdialog.cpp:1173`; the line to replace is at L1174).
   Replace:

   ```cpp
   const bool expanded = opts.expandedItems.contains(rec.id);
   ```

   With:

   ```cpp
   const bool predicateOnlyInBody =
       !plainSearch.isEmpty() &&
       rec.body.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.id.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.headline.contains(plainSearch, Qt::CaseInsensitive) &&
       !rec.layman.contains(plainSearch, Qt::CaseInsensitive);
   const bool idJumpToThisCard =
       !idMarker.isEmpty() && rec.body.contains(idMarker);
   const bool expanded = opts.expandedItems.contains(rec.id)
                         || predicateOnlyInBody
                         || idJumpToThisCard;
   ```

   `plainSearch` and `idMarker` are already in scope in this
   lambda (they're computed once at the top of `renderCardsHtml`).

## 6. Memory budget

Zero new persistent state. Reuses:

- The existing `m_searchBox` QLineEdit (one per dialog).
- The existing `m_expandedItems` QSet (no new entries — see INV-5/8).
- The dialog itself as the `eventFilter` host (no new QObject; the
  dialog is already a QObject and inherits `QObject::eventFilter`).

**Runtime cost added per render.** Each `emitCard` invocation now
runs an additional **four** case-insensitive
`QString::contains(plainSearch, Qt::CaseInsensitive)` calls — on
`rec.body`, `rec.id`, `rec.headline`, `rec.layman` — in addition
to the `hay.contains` call already done by `passesFilter`. On a
200-card render this adds 800 `contains` calls against short
strings (id ≤ 12 chars, headline ≤ 120 chars, layman typically ≤
200 chars, body up to ~2 KiB). The `idJumpToThisCard` branch adds
one more `body.contains(idMarker)` when an `id:NNNN` predicate is
active (mutually exclusive with `plainSearch`, so doesn't
compound). Worst-case ≈ 0.3 ms on a 2026 desktop CPU per render;
well below the existing 120 ms search debounce.

No heap allocation per card — `QString::contains` on existing
fields does not copy. The three `bool` flags
(`predicateOnlyInBody`, `idJumpToThisCard`, `expanded`) are
stack-local in the lambda.

## 8. Re-open conditions

1. **Non-Latin keymap regression** — if a Polish / Korean / Arabic
   keyboard reports `/` not focusing the search box, the
   `event->text() == "/"` check is failing on that layout. Capture
   the `QKeyEvent::text()` value on the affected keypress and
   either add a `Qt::Key_Slash` fallback or specialise.
2. **Auto-expand collateral** — if a user reports cards "randomly
   expanding" on what they consider a summary match, the
   summary/body boundary in `BulletRecord` may have shifted (e.g.
   a future parser change folds the layman line into `body`). The
   spec's INV-6 should fail in that case.
3. **Esc-clear surprise** — if a user reports Esc closes the
   dialog instead of clearing search, the event filter may not be
   installed (`installEventFilter(this)` missing from the ctor).
4. **120 ms feels sluggish on Esc-clear** — if user reports the
   field clears visually but the card list takes too long to
   re-render, add a synchronous-rebuild bypass when Esc-clearing
   from a non-empty predicate. Keep the debounce for typing.

## 9. Out of scope

The ROADMAP.md bullet for ANTS-1234 (line 8565) was written from
the 2026-05-11 research synthesis and listed three richer
behaviours that this spec deliberately defers:

- **Highlighting the matched substring inside the body.** Useful,
  but involves an HTML span injection that risks crossing card
  markup boundaries. Future entry.
- **Cross-section auto-expand** ("auto-expand sections containing
  matches"). The ROADMAP bullet's wording suggests expanding
  whole sections; this spec auto-expands *cards*, not sections.
  Section-level auto-expand could pile on the open list shape;
  defer until requested.
- **Persist last query per tab via a fifth `Config::roadmap*`
  key.** The 120 ms debounce + clearButton already keeps queries
  visible across re-renders; cross-session persistence is a
  separate concern. Future entry.

Additionally out of scope:

- Regex / glob search syntax. The substring filter covers the
  use case; regex is power-user territory.
- Cross-section search jumping (auto-scrolling to the first
  match's section).
- A search-result count label ("3 of 47 cards match"). Useful UX
  signal but separable.

If any of the three deferred ROADMAP-bullet items become priority,
a follow-on ROADMAP entry (suggested IDs ANTS-1244 / 1245 / 1246)
should be filed; the bullet at L8565 in the meantime can be
trimmed in a future doc-drift pass to match the narrower scope
this spec implements.
