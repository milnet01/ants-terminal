# ANTS-1896 — Recommender confidence + top_signals refactor

**Status:** accepted (2026-05-28). Cold-eyes loops 1+2+3+4+5+6+7
folded; user gated stop at loop 7 with remaining clarifications
deferred to implementation time.
**Kind:** refactor.
**Source:** ROADMAP.md ANTS-1896 (in-session-2026-05-26 — ANTS-1891
brainstorm; recommender opacity surfaced once the trust signal made
the per-record `score_reason` field visible without explaining the
*margin* between competing tiers).

**Layman:** Today the recommender just says "use Haiku" with no idea
how *sure* it is. This change makes it say "use Haiku — I'm 78% sure,
mostly because your last 5 turns are all small file edits." Two
benefits: (a) Ants can skip switches when it's only barely confident
(killing the marginal regret cases), and (b) the user can hover the
status-bar chip and see *why* the recommender picked what it picked
— making the system feel less like a black box.

**Pairs with:** ANTS-1894 (near-miss telemetry — the new
`confidence_too_low` blocker token slots into the existing taxonomy).
**Composes with:** ANTS-1893 surfacing (the toast body's
`shortenReason` consumer benefits from a structured signal list to
pick the top contributor). **Blocks on:** ANTS-1895 ledger-data
(the confidence threshold's default is chosen from a week of
dry-run distribution — landing 1896 before 1895 has accumulated
data means the threshold ships at a conservative default and is
re-tuned later).

**Co-drafted bundle.** ANTS-1893 and ANTS-1895 are both at
"draft (2026-05-28)" with cold-eyes in progress — same loop
state as this spec. Merge order is fluid; the §2.6 grey-out
fallback below has explicit code for "ANTS-1895 not landed yet
→ gate on `switch_enabled:bool`" so this spec can ship
independently if the others slip.

## 1. Problem

`ModelRecommender::score` (`src/modelrecommender.cpp:83`) returns a
discrete `Result { Tier, reason, currentModel }`. Two costs follow
from the bare tier enum:

1. **No margin → no skip.** The gate (`ModelAutoSwitch::decide`)
   treats every recommendation equally. A turn that scored
   `+3 → Opus` looks identical to a turn that scored `+8 → Opus`
   — but the former is on the cusp of `Sonnet` and an extra cue
   would flip it. The user's regret data (per `model_switch_stats`)
   includes regrets that, on inspection, were always going to be
   wrong because the recommender was only barely past the threshold.
   No way to filter those out today.

2. **No structured reason → opaque chip tooltip.** Today's
   `rec.reason` is a space-joined keyword list — e.g. `"many_writes
   tool_diversity plan_keyword"`. Useful for grep, useless for a
   chip tooltip — the user reading the chip sees no ranking, no
   weight, no contribution percentage. The status-bar chip's
   tooltip (`m_modelStateBtn->setToolTip(...)` at
   `claudestatuswidgets.cpp:1305-1310`) currently shows just the
   tier name; we want it to surface "78% confident — drivers:
   many_writes (40%), tool_diversity (30%), plan_keyword (30%)"
   so the recommender's *reasoning* is one hover away.

## 2. Surface

Five concerns. **Pure-source refactor**: no on-disk format changes,
no MCP-tool additions, no new persisted state. The `score()` return
type changes; every call-site updates in the same change.

### 2.1 `ModelRecommender::Result` — gain confidence + top_signals

Today (`src/modelrecommender.h:10-14`):

```cpp
struct Result {
    Tier    tier         = Tier::Sonnet;
    QString reason;
    QString currentModel;
};
```

Add two fields:

```cpp
struct Result {
    Tier    tier         = Tier::Sonnet;
    QString reason;            // unchanged — space-joined keyword list
    QString currentModel;
    // ANTS-1896 — new fields. confidence is in [0..100]; 100 = a
    // clear-margin pick, 0 = a coin-flip between this tier and the
    // runner-up. top_signals is a ranked breakdown of the
    // contributing scoring rules, descending by abs(contribution).
    int                       confidence = 0;
    QList<SignalContribution> topSignals;
};

struct SignalContribution {
    QString name;          // canonical signal name (see § 2.3 taxonomy)
    int     weight    = 0; // raw points the signal contributes (+/-)
    double  fraction  = 0; // contribution share in [0..1] of total magnitude
};
```

`reason` is preserved as the space-joined keyword list because the
firing-side ledger record (`ModelSwitchLedger::Record::scoreReason`
— `src/modelswitchledger.h:45`) writes that string verbatim, and
ANTS-1735's `score_reason` field has on-disk consumers in
`statsEnvelope` (per-record). Keeping `reason` source-compatible
avoids a ledger-schema break; the new fields are additive.

`SignalContribution` lives in `modelrecommender.h` alongside the
other Recommender types. It's a small POD; `sizeof` is
implementation-defined but ~32 bytes per entry on x86-64
(`QString` 8 bytes pointer-only + `int` 4 + `double` 8, with
padding); typical `topSignals` size is 3-5 entries. The §4 RAM
budget below uses the conservative `~32 bytes × 5 = ~160 bytes`
worst-case figure (replacing an earlier draft's `× 24`).

### 2.2 `score()` body — compute confidence + top_signals

The existing scoring at `modelrecommender.cpp:237-258` accumulates
an `int sc` from five rules and one negative rule:

| Rule (today) | Contribution |
|---|---|
| `weightedWrites >= 8.0` | +2 |
| `toolDiversity >= 6` | +1 |
| `planKeyword` | +2 |
| `avgLen >= 500` | +1 |
| `fileWriteCount == 0 && toolDiversity <= 2` (mechanical) | -2 |

Plus the `commit_intent` HARD OVERRIDE (`modelrecommender.cpp:170-176`)
returning `Tier::Haiku` immediately — bypassing the score.

**Refactor:**

1. Build `topSignals` inline with `sc`. Each rule that fires (i.e.
   contributes a non-zero weight) emits one
   `SignalContribution{name, weight, fraction=0}`. The `fraction`
   field is filled in a single pass after the loop:
   ```cpp
   int totalAbs = 0;
   for (const auto &s : topSignals) totalAbs += std::abs(s.weight);
   for (auto &s : topSignals) {
       s.fraction = (totalAbs > 0)
           ? double(std::abs(s.weight)) / totalAbs : 0.0;
   }
   ```
   `totalAbs` is the L1 norm of the contributions. The fraction is
   the share of TOTAL MAGNITUDE — a +2 and a -2 each contribute
   50%, even though they cancel in the bare `sc`. This reflects
   "how much of the recommender's attention" each signal is taking.

2. Sort `topSignals` by `abs(weight)` descending, then by name
   ascending (stable). Cap at the top 5 (`kMaxSignals = 5` —
   constant in `modelrecommender.cpp` namespace block).

3. Compute `confidence`:
   ```cpp
   // The score `sc` selects the tier (>=3 Opus, <=-1 Haiku, else
   // Sonnet). Confidence is the margin from the nearest threshold,
   // normalised to 0-100. Distance 0 → 0 confidence; distance >= 3
   // saturates at 100 via the clamp.
   const int distance = distanceFromNearestThreshold(sc);
   const int confidence = std::clamp(distance * 34, 0, 100);
   ```

   `distanceFromNearestThreshold` is a new file-static helper:

   ```cpp
   int distanceFromNearestThreshold(int sc) {
       // Tier rules: sc >= 3 Opus; sc <= -1 Haiku; else Sonnet.
       // Sonnet window: -1 < sc < 3, i.e. sc in [0, 2].
       if (sc >= 3) return sc - 3;          // distance ABOVE Opus threshold
       if (sc <= -1) return -1 - sc;        // distance BELOW Haiku threshold
       // Sonnet: distance to nearest boundary
       return std::min(sc - (-1), 3 - sc);   // min(sc+1, 3-sc) for sc in [0,2]
   }
   ```

   Worked examples:
   - `sc = 6` → distance 3 → confidence 100 (max-margin Opus).
   - `sc = 5` → distance 2 → confidence 68.
   - `sc = 3` → distance 0 → confidence 0 (on the boundary).
   - `sc = 1` → distance 2 (to -1 or 3 — both are 2) → confidence 68.
   - `sc = 0` → distance 1 → confidence 34.
   - `sc = -1` → distance 0 → confidence 0.
   - `sc = -3` → distance 2 → confidence 68 (note: `sc <= -3`
     is unreachable under v1 weights — the only negative rule
     `mechanical` contributes -2, so min sc is -2 / distance 1 /
     confidence 34).

   **Multiplier choice — `× 34`, not `× 33`.** Under v1 weights
   the maximum positive `sc` is `+6` (all four positive rules
   firing — `weightedWrites:+2 + toolDiversity:+1 +
   planKeyword:+2 + avgLen:+1`; the negative rule `mechanical`
   cannot fire alongside `weightedWrites` because they have
   mutually-exclusive predicates on `fileWriteCount`). Distance
   max-above-Opus = `6 - 3 = 3`. With multiplier `× 33`,
   `distance=3 → 99` and `distance=4` is unreachable, so
   confidence 100 would be dead code. Pick `× 34` so the natural
   v1 max (`sc=6, distance=3`) saturates at 100 via the clamp
   (`3 × 34 = 102 → clamp → 100`). The clamp is preserved for
   defence-in-depth: any future scoring rule that grows the
   positive headroom still clips cleanly at 100.

4. The `commit_intent` hard override case bypasses the scoring:
   `confidence = 100` (the override is by definition unambiguous —
   the user typed a VCS verb), `topSignals = [{name: "commit_intent",
   weight: +5, fraction: 1.0}]`. The override branch returns
   from `score()` BEFORE the scoring loop runs
   (`modelrecommender.cpp:170-176` early-returns from the
   override case), so `topSignals` contains exactly one entry —
   no risk of the regular-path signals being appended on top.
   The synthetic weight `+5` is a sentinel reflecting "single
   hard signal, no contention" — distinct from any normal
   scoring rule's natural weight (the max natural weight is
   `weightedWrites/planKeyword` at +2).

5. The `turns.isEmpty()` short-circuit at L178 returns `def` with
   `confidence = 0` and `topSignals.empty()` — explicit
   "no signal" rather than a guess. **Important:** L178 is only
   reached when the `commit_intent` override branch (L170-176)
   did NOT fire — the override runs BEFORE the empty-turns
   short-circuit (per source-order verified at
   `modelrecommender.cpp:166-178`). A fresh session with a
   single user turn typing "commit and push" hits the override
   path with `confidence=100` even though `turns.isEmpty()`
   would otherwise have been true; the L178 short-circuit is
   reachable only when both the override AND the normal
   scoring path produced no Result (no `latestUserText` AND
   empty `turns`).

### 2.3 Signal taxonomy — stable names

Five **scoring rules** + one **override sentinel** = six entries
total. The names are stable handles (mirroring the ANTS-1894
INV-9 blocker-taxonomy pattern) and never renamed once written
to disk via the ledger's `score_reason` field. The name in
`SignalContribution::name` is the same string token used in
`reason` for these six entries.

| Name             | Kind     | Trigger | Weight |
|------------------|----------|---------|--------|
| `commit_intent`  | override | `hasCommitIntent(latestUserText) == true` | +5 (sentinel) |
| `many_writes`    | rule     | `weightedWrites >= 8.0` | +2 |
| `plan_keyword`   | rule     | `hasPlanKeyword(text)` for any text in window | +2 |
| `tool_diversity` | rule     | `toolDiversity >= 6` | +1 |
| `long_prompts`   | rule     | `avgLen >= 500.0` | +1 |
| `mechanical`     | rule     | `fileWriteCount == 0 && toolDiversity <= 2` | -2 |

The taxonomy is exposed as a `static const QStringList
kSignalNames` in `modelrecommender.cpp`'s anonymous namespace —
exactly six entries, ordering preserved for deterministic
tie-break. Tests assert the taxonomy size and exact names
(sentinel against accidental rename).

**`reason` superset note.** `rec.reason` carries a third non-
taxonomy token — `"default"` — emitted by `score()` at
`modelrecommender.cpp:86` when the file is absent or has no
assistant turns. `"default"` is NOT a signal (it has no rule, no
weight) — it's a sentinel meaning "no transcript data, returning
default tier." Excluded from `kSignalNames` by design. INV-1
captures this: a `"default"` result returns
`confidence=0, topSignals=[]` (no entry referring to the
sentinel). So `reason` is a strict superset of `kSignalNames ∪
{"default"}`, not a strict subset of `kSignalNames`.

### 2.4 Gate — confidence threshold skip

`ModelAutoSwitch::Gate` (`src/modelautoswitch.h:24-46`) gains
one field:

```cpp
// ANTS-1896 INV-4 — confidence floor in [0..100]. The gate adds
// the canonical `confidence_too_low` blocker token when the live
// recommendation's confidence is below this floor. Default 0 (no
// skip — pre-1896 behaviour). The controller passes the value
// from `claude.auto_model_confidence_floor` (config default 0 in
// v1 — sharpened by post-1895 dry-run data in a follow-up).
int recommendationConfidence  = 100;     // post-1896 fill from rec.confidence
int confidenceFloor           = 0;       // post-1896 fill from config
```

`decide()` (`src/modelautoswitch.cpp:29-63`) gains one new guard,
inserted in the evaluation order AFTER `target_equals_current` and
BEFORE `ticks_target_stable_insufficient`. Note `decide()` is
evaluate-all (post-1894 INV-2 — no short-circuit; every guard
runs and accumulates its token). The placement is chosen so the
`confidence_too_low` token, when present, sits next to
`target_equals_current` in the `blockedBy` array — both express
"recommendation is uninteresting" in adjacent positions:

```cpp
if (target == g.current)
    d.blockedBy << QStringLiteral("target_equals_current");
// ANTS-1896 — confidence floor. Skip switches the recommender
// itself isn't sure about. Default floor = 0 keeps pre-1896
// behaviour (every recommendation passes).
if (g.recommendationConfidence < g.confidenceFloor)
    d.blockedBy << QStringLiteral("confidence_too_low");
if (g.ticksTargetStable < kStableTicks)
    d.blockedBy << QStringLiteral("ticks_target_stable_insufficient");
```

The new token `confidence_too_low` joins the v1 blocker taxonomy
(ANTS-1894 INV-9). Per the immutability rule, the existing 7
tokens stay; the new 8th token is appended. The actual
supersedence is performed by the §8 coordinated edits to
ANTS-1894 INV-9 (taxonomy list + test alternation) — those
edits ARE the supersedence; this paragraph just signposts
intent.

### 2.5 Config + chip tooltip

New config key:

- `claude.auto_model_confidence_floor` (int, default `0`,
  clamp `[0, 100]`).

Default 0 keeps pre-1896 behaviour. A follow-up calibration ID
(picked from ANTS-1895 dry-run data) will tune this to e.g. 30 or
50; until then, v1 ships with the floor disabled by default. A
power user wanting to opt into stricter skipping sets the value
manually (Settings → AI Assistant → "Skip switches below X%
confidence" — see § 2.6).

**Accessor placement.** The new key is exposed BOTH via the
existing `Config::claudeAutoModel()` JSON envelope (as
`confidence_floor:int`) AND a typed accessor
`Config::claudeAutoModelConfidenceFloor() / setClaudeAutoModelConfidenceFloor(int)`.
The envelope key keeps the related `auto_model_*` settings
together for the controller's per-tick read (one
`claudeAutoModel()` call, all fields available); the typed
setter mirrors `setClaudeAutoModelSwitch`'s pattern at
`config.cpp:444`.

**`claudeAutoModel()` extension.** The body of
`Config::claudeAutoModel()` at `src/config.cpp:429-441`
currently builds 3 keys (`switch_enabled`, `min_dwell_sec`,
`floor`). Add a 4th `confidence_floor` insert with the same
clamp-on-read pattern as `min_dwell_sec`:

```cpp
int confFloor =
    m_data.value("claude.auto_model_confidence_floor").toInt(0);
confFloor = std::clamp(confFloor, 0, 100);
out.insert("confidence_floor", confFloor);
```

Insertion point: after the `min_dwell_sec` insert and before
the `floor` insert, so the keyset reads `switch_enabled →
min_dwell_sec → confidence_floor → floor`. The envelope
remains the source of truth at read time; the typed setter
writes the underlying config key AND `save()`s.

The chip tooltip change at `claudestatuswidgets.cpp:1305-1310`
expands to:

```cpp
QString topSignalsText;
if (!rec.topSignals.isEmpty()) {
    QStringList lines;
    for (const ModelRecommender::SignalContribution &s :
            rec.topSignals) {
        lines << tr("  • %1 (%2%)").arg(s.name)
                                   .arg(int(s.fraction * 100));
    }
    topSignalsText = QStringLiteral("\n") + lines.join(QStringLiteral("\n"));
}
m_modelStateBtn->setToolTip(
    tr("Focused tab is using %1 (from the transcript's most recent "
       "assistant turn).\nThinking level: %2.\n"
       "Recommender confidence: %3%.%4")
        .arg(tierTitle)
        .arg(thinkLabel.isEmpty() ? tr("unknown") : thinkLabel)
        .arg(rec.confidence)
        .arg(topSignalsText));
```

A four-line tooltip on a hover — no extra status-bar real estate,
visible only on intent. When `topSignals` is empty (no transcript
turns), the line reads just "Recommender confidence: 0%." with no
breakdown below.

`m_modelStateBtn` is the ANTS-1888 chip; its render path
`refreshModelStateChip` (`claudestatuswidgets.h:99`) needs the
`rec` value. Today `refreshAutoModelSwitch` calls
`ModelRecommender::score` (`modelrecommender.cpp:83`) once per
tick (no mtime short-circuit on that path); `refreshModelStateChip`
also calls `score()` at L1276 BUT short-circuits at L1267 when
both `transcriptPath` and `mtimeMs` match the prior call.
Within a single tab the second call typically short-circuits;
on the first tick after a transcript change BOTH score, producing
genuine double-scoring on that boundary tick only. To avoid that, declare a controller member to
cache the most recent `Result` (NORMATIVE addition to
`claudestatuswidgets.h` — not optional):

```cpp
// claudestatuswidgets.h — new private member
ModelRecommender::Result m_lastModelRec;
```

Wiring (master-switch-agnostic — works against pre-1895
`switch_enabled:bool` and post-1895 `mode != "off"` per
ANTS-1895 INV-7's `switch_enabled == (mode == "on")`
derivation):
- `refreshAutoModelSwitch` (when the master is ON / mode ==
  "on") stores `m_lastModelRec = rec` immediately after its
  `score()` call at the pre-existing
  `claudestatuswidgets.cpp:1363` site.
- `refreshModelStateChip` reads `m_lastModelRec` for the
  tooltip composition. When `refreshAutoModelSwitch` returned
  early at L1350 (master OFF) `m_lastModelRec` is stale — in
  that case `refreshModelStateChip` falls back to calling
  `score()` itself (its pre-existing call at L1277 is the
  seed) and stores the result via `m_lastModelRec = rec` on
  the same path. The existing mtime short-circuit at
  `m_modelStateMtimeMs` (`claudestatuswidgets.h:270`) is
  preserved and gates BOTH the score call AND the store, so a
  no-change transcript pays neither cost.

Both refresh functions run on the same 2 s tick — no race
(single-threaded UI). **Tick order is load-bearing:**
`refreshAutoModelSwitch` MUST execute BEFORE
`refreshModelStateChip` in the status-timer slot, so that on
ticks where the switcher is ON, the chip's tooltip reads the
just-stored `m_lastModelRec` rather than a stale prior value.

**NORMATIVE wiring change required.** Verified against current
source: `src/mainwindow.cpp:783-798` connects
`refreshModelStateChip` (L789-791) BEFORE
`refreshAutoModelSwitch` (L796-798) — the OPPOSITE order of what
INV-13 requires. Qt fires `QTimer::timeout`-connected slots in
connection order, so today the chip runs first and reads stale
state. Part of this spec's implementation MUST reverse the
two `connect()` calls so `refreshAutoModelSwitch` is connected
before `refreshModelStateChip`. The reversal is bit-trivial
(two `connect()` blocks swap position) and is enumerated in
§8 cross-doc impact below as a code-side normative change.
INV-13 locks the resulting order as a contract; the test
asserts it directly.

## 3. Invariants

- **INV-1** — `ModelRecommender::score` populates `result.confidence`
  in `[0..100]` AND `result.topSignals` (a ranked list of at most
  `kMaxSignals=5` entries, descending by `abs(weight)`, tie-broken
  by `name` ascending) on every call. An empty-transcript call
  returns `{confidence: 0, topSignals: []}`. **`confidence=0`
  is NOT a "never-scored" sentinel** — it's a legitimate result
  for boundary scores (`sc=3` for Opus, `sc=-1` for Haiku, the
  edge of the Sonnet window). The unambiguous "never-scored"
  discriminator is `result.topSignals.isEmpty()` alone — the
  empty branches at `modelrecommender.cpp:94` and `:178` are
  the only paths that produce an empty list. Boundary scores
  (sc=3, sc=-1) ARE assigned by the normal scoring path
  (L237-258), so they have non-empty `topSignals` even when
  confidence=0. Do NOT use `currentModel.isEmpty()` as a
  proxy — a fresh-session `commit_intent` override fires
  (L170-176) BEFORE any assistant turn exists, returning
  `topSignals=[commit_intent]` (non-empty) AND `currentModel=""`
  (empty, because `def.currentModel` was never populated by the
  missing assistant turn). A caller checking
  `currentModel.isEmpty()` would misclassify that override as
  "never scored".
  *Test:*
  `tests/features/model_recommender_confidence/test_score_returns_confidence.cpp`.
- **INV-2** — The `commit_intent` hard-override branch returns
  `confidence: 100` AND `topSignals: [{name:"commit_intent",
  weight:+5, fraction:1.0}]`. The sentinel weight `+5` is the
  v1-stable handle for the override; never renumber. *Test:*
  `tests/features/model_recommender_confidence/test_commit_intent_full_confidence.cpp`.
- **INV-3** — `confidence = distance_from_nearest_threshold(sc) *
  34`, clamped to `[0..100]`. Boundary scores (`sc=3`, `sc=-1`)
  produce confidence 0; distance 3 (the v1 max-above-Opus,
  achieved at `sc=6`) saturates at 100 via the clamp
  (3×34=102 clamped → 100). Table: `sc=6 → 100`; `sc=5 → 68`;
  `sc=3 → 0`; `sc=2 → 34`; `sc=1 → 68`; `sc=0 → 34`; `sc=-1 → 0`;
  `sc=-2 → 34` (the v1 negative-side reach — `mechanical` is
  the only negative rule, weight -2).
  **v1 confidence-side asymmetry — known and deliberate.**
  Under v1 weights the Opus side can reach distance 3 (max
  confidence 100); the Haiku side caps at distance 1 (max
  confidence 34). A maximally-confident Haiku pick is
  therefore impossible until a future ID rebalances the
  negative-rule weights or adds a second negative rule. Spec
  ships v1 as-is; a follow-up tracks the asymmetry as
  ANTS-1896-followup (TBD). The asymmetry is acceptable
  because (a) the Haiku-side confidence floor is rarely the
  triggering gate in practice — the gate already filters
  haiku picks via the floor_tier config (ANTS-1735); (b) the
  tooltip shows raw numbers without claiming symmetry. *Test:*
  `tests/features/model_recommender_confidence/test_confidence_calibration.cpp`.
- **INV-4** — `ModelAutoSwitch::decide` appends the
  `confidence_too_low` blocker token to `blockedBy` iff
  `g.recommendationConfidence < g.confidenceFloor`. The token
  fires only on confidence comparison — never as a side effect of
  any other guard. The token joins the v1 taxonomy alongside the
  ANTS-1894 INV-9 7 tokens; the v1 list is now 8 tokens. *Test:*
  `tests/features/model_recommender_confidence/test_confidence_too_low_blocker.cpp`.
- **INV-5** — Pre-1896 `Gate` default (`confidenceFloor=0`,
  `recommendationConfidence=100`) reproduces pre-1896 behaviour:
  `100 < 0` is false → no `confidence_too_low` token →
  bit-for-bit identical decision shape. The two defaults MUST be
  member-initialisers on the `Gate` struct (per the snippet in
  § 2.4) so a caller that constructs a `Gate{}` without setting
  the new fields inherits the no-op values automatically.
  *Test:*
  `tests/features/model_recommender_confidence/test_default_gate_backcompat.cpp`.
- **INV-6** — The `kSignalNames` taxonomy in `modelrecommender.cpp`
  contains exactly 6 entries (the v1 set in § 2.3 — 5 scoring
  rules plus the `commit_intent` override sentinel); test asserts
  size + canonical names. `"default"` (the no-transcript fallback
  reason) is intentionally NOT in `kSignalNames` — it's a
  sentinel, not a signal (see § 2.3 superset note). *Test:*
  `tests/features/model_recommender_confidence/test_signal_taxonomy.cpp`.
- **INV-7** — `Config::claudeAutoModelConfidenceFloor()` reads the
  key, clamps to `[0..100]`, defaults to `0`. The setter clamps
  the input. *Test:*
  `tests/features/model_recommender_confidence/test_config_confidence_floor.cpp`.
- **INV-8** — Sort order of `topSignals`: primary key
  `abs(weight)` DESC, secondary key `name` ASC (stable). A
  signal list of e.g. `[("plan_keyword", +2), ("many_writes", +2),
  ("tool_diversity", +1)]` sorts to `[("many_writes", +2),
  ("plan_keyword", +2), ("tool_diversity", +1)]` (name
  alphabetical tie-break). *Test:*
  `tests/features/model_recommender_confidence/test_top_signals_sort.cpp`.
- **INV-9** — On the SCORING path, `topSignals[i].fraction` is
  `abs(weight) / totalAbs` (the L1 norm); sum of `fraction`
  equals 1.0 ± floating epsilon when topSignals is non-empty.
  On the OVERRIDE path (commit_intent fires per § 2.2 step 4),
  the single entry's fraction is set directly to `1.0` —
  bypasses the totalAbs computation, since there's no
  contention. Empty topSignals (no transcript data) leaves
  `fraction` at the field default (0). **Negative-only edge
  case:** if only `mechanical` (-2) fires (e.g. `sc=-2`,
  tier=Haiku), `totalAbs=2`, the single entry has
  `fraction=1.0` — meaning "mechanical is taking 100% of the
  recommender's attention." The tier-selection confidence is
  still gated by `distance × 34 = 34` per INV-3, so the chip
  tooltip shows `confidence=34%` AND `mechanical (100%)`.
  These two numbers are independently meaningful: confidence
  is "how sure the tier pick is"; fraction is "share of
  attention each signal took." § 2.5 tooltip copy makes the
  distinction explicit. *Test:*
  `tests/features/model_recommender_confidence/test_top_signals_fraction.cpp`
  covers THREE paths — scoring-path table with `[+2, -2, +1]`
  asserting fractions sum to 1.0; override-path call asserting
  the single `commit_intent` entry has `fraction == 1.0`;
  negative-only `mechanical` firing asserting the entry has
  `fraction == 1.0` AND the parent `Result.confidence == 34`.
- **INV-10** — `score()` preserves backward-compatible behaviour:
  the chosen `tier` is unchanged from pre-1896 for every input
  the existing tests cover. The refactor is observation-additive,
  not logic-modifying. *Test:*
  `tests/features/model_recommender_confidence/test_tier_unchanged_pre_1896.cpp`
  — the existing tier assertions in
  `tests/features/model_recommender/test_model_recommender.cpp`
  (verified to currently lock specific `Result::tier` values
  against synthetic transcripts) MUST continue to pass against
  the refactored `score()`. INV-10's test is a thin guard that
  re-runs the existing fixtures' tier assertions; the
  existing test file IS the golden surface.
- **INV-11** — Controller's `m_lastModelRec` is updated on every
  `refreshAutoModelSwitch` tick that calls `score()` (i.e. when
  the master is ON). When the controller's master toggle is
  OFF (pre-1895: `!switch_enabled`; post-1895: `mode == "off"`),
  `refreshModelStateChip` calls `score()` on-demand and caches
  the result. The mtime short-circuit at
  `claudestatuswidgets.cpp:1267` early-returns when BOTH path
  AND mtime match the prior call. **First-paint guarantee:**
  on a fresh process, `m_modelStatePath` starts EMPTY (member
  default), so the first paint of any tab fails the path
  equality test, falls through to the `score()` call at
  `claudestatuswidgets.cpp:1276`, and populates
  `m_lastModelRec`. Same-tab steady-state ticks then
  short-circuit but the cached rec correctly reflects the
  unchanged transcript. Tab switches force a fresh score
  because `transcriptPath` changes. The chip tooltip thus
  shows a meaningful (never empty / never stale)
  most-recent-scoring outcome for the focused tab in every
  observable case. `m_lastModelRec` is default-constructed at
  controller construction; `ModelRecommender::Result`'s field
  initialisers (`tier=Sonnet, reason="", currentModel="",
  confidence=0, topSignals=[]`) guarantee well-defined state
  without any explicit member-initialiser. The chip's
  tooltip-composition path uses the INV-1 discriminator
  (`m_lastModelRec.topSignals.isEmpty()`) — NOT
  `currentModel.isEmpty()` — to decide whether to render the
  confidence line; on a never-scored Result `topSignals` is
  empty and the confidence line is hidden, while a fresh-
  session `commit_intent` override still renders the
  confidence line (`topSignals=[commit_intent]`) even though
  `currentModel` happens to be empty. *Test:*
  `tests/features/model_recommender_confidence/test_chip_tooltip_freshness.cpp`
  covers (a) first paint of a fresh tab; (b) two-tab
  alternation to confirm path-change forces a fresh score;
  (c) same-tab no-change ticks return the cached rec without
  re-scoring; (d) member-init: a freshly-constructed
  controller has `m_lastModelRec.confidence == 0` and
  `topSignals.isEmpty()` before any refresh runs.
- **INV-12** — Chip tooltip format includes the line
  `"Recommender confidence: %1%."` with `%1` substituted with
  the integer confidence. When `topSignals` is non-empty, the
  tooltip continues with `\n  • <name> (<%>%)\n  • …` per
  contribution. Per-contribution percentages are rendered via

  rare rounding cases (3-way split of e.g. 100/3 each); this
  is acceptable for a tooltip surface and the test allows

  `tests/features/model_recommender_confidence/test_chip_tooltip_format.cpp`.
- **INV-13** — Within a single 2 s status-timer tick,
  `refreshAutoModelSwitch` executes BEFORE

  tooltip reads the just-stored `m_lastModelRec` rather than

## 4. RAM / build cost

- **RAM (per Result):** ~230 bytes worst case — base struct
  ~70 bytes (Qt string overhead + the three new
  ints/lists) + up to 5 `SignalContribution` × ~32 bytes =
  ~160 bytes. Per-call lifetime (stack-local in `score()`'s
  return; controller stores ONE in `m_lastModelRec`). Process
  steady-state cost: ~230 bytes (a single cached Result on
  the controller). Below profiler noise; figure is a
  conservative upper bound — `QString`'s shared-buffer
  optimisation means the per-entry footprint is typically
  much smaller in practice.
- **RAM (per Gate):** +8 bytes for `confidenceFloor` +
  `recommendationConfidence`. Per-tick lifetime. Below noise.
- **CPU per `score()`:** The fraction-normalisation loop is O(n)
  in topSignals — n ≤ 5. The sort is O(n log n), same n. Adds
  ~6 boolean checks + one division per call. Below profiler
  noise (`score()` already does a 512 KB tail-read + JSON parse —
  the new work is sub-µs against that).
- **CPU per `decide()`:** one additional `<` comparison per tick
  for the confidence floor check. Below noise.
- **Disk:** ZERO new on-disk artifacts. The
  `claude.auto_model_confidence_floor` config key is a single
  int.
- **Build cost:** ~80 lines on `modelrecommender.{h,cpp}` (new
  struct + helper + fraction-normalisation pass), ~20 lines on
  `modelautoswitch.{h,cpp}` (new Gate field + decide() guard),
  ~30 lines on `config.{h,cpp}` (accessor + setter), ~30 lines
  on `claudestatuswidgets.cpp` (tooltip composition + m_lastModelRec
  caching), ~20 lines on `settingsdialog.cpp` (slider control).
  Test bundle: ~12 new `.cpp` files in
  `tests/features/model_recommender_confidence/`, ~550 lines, split
  across `test_core` (pure Recommender + Gate tests) and
  `test_claude` (chip-tooltip tests). No new `add_executable`.

## 5. Out of scope

(IDs marked *ROADMAP-only* below are 📋 bullets in `ROADMAP.md` at
this spec's writing — no `docs/specs/<id>.md` file exists yet.)

- **Confidence-floor calibration from dry-run data.** Tracked
  separately as a follow-up to ANTS-1895; this spec ships the
  threshold default at 0 (no-skip). When ANTS-1895 has
  accumulated a week of dry-run records, a calibrator analyses
  the regret-rate vs confidence-floor curve and sets the
  default. Calibration is a one-line `Config` default change
  + spec update, not a refactor.
- **Continuous confidence (real-valued).** Current spec quantises
  to integer percent. A real-valued internal could feed a more
  precise floor but the user-facing tooltip is integer-only;
  the precision delta is invisible. Defer until UI demands it.
- **Confidence-driven dwell adjustment.** A high-confidence
  Opus recommendation could short-cut the 90 s min-dwell. Out
  of scope; the min-dwell is a stability guarantee, not a
  confidence input.
- **Per-signal weight tuning surface.** Letting the user
  re-weight `plan_keyword` from +2 to +3 (e.g. for a user whose
  workflow over-triggers Opus). Too much config surface for v1;
  the recommender is an opinionated default. Tracked in spirit
  by ROADMAP-only entries.
- **Toast body uses top_signals.** ANTS-1893's `shortenReason`
  could in principle consume `top_signals[0].name` for a
  better-targeted short label. Defer — the existing precedence
  map (§ 2.5 in ANTS-1893) already covers the common cases.

## 6. Migration / compatibility

- **`ModelRecommender::Result`'s new fields are additive.** Every
  existing call site reads `tier` / `reason` / `currentModel` —
  those are unchanged. The new fields default to
  `{confidence:0, topSignals:[]}` for any constructor that
  doesn't set them, so legacy paths are bit-for-bit identical.
- **`Gate`'s new fields default to no-op.** `confidenceFloor=0`
  and `recommendationConfidence=100` means the new guard is
  never triggered — preserves pre-1896 behaviour for any caller
  that doesn't set the fields. The `test_decide_act_iff_unblocked`
  invariant (ANTS-1894 INV-1) continues to hold.
- **`decide()`'s blocker list gains an 8th token.** No on-disk
  schema change — the v1 taxonomy already permits append-only
  growth per ANTS-1894 INV-9. The near-miss aggregator
  `statsSlim` / `statsFull` (ANTS-1894 § 2.3) handle unknown
  tokens by including them in `by_blocked_by` automatically.
- **`ledger.score_reason` field unchanged.** The space-joined
  keyword list still writes through `Result::reason`; on-disk
  records continue to parse on older code paths. The new
  `confidence` / `topSignals` fields are NOT persisted to the
  ledger (RAM-only, per-tick state).
- **`m_lastModelRec` is a new controller member.** No external
  consumer, no signal, no serialisation. Process-lifetime cache.

## 9. Open questions

- **OQ-1: Should the slider's persisted default be 0 (no-skip)
  or 30 (a conservative skip)?** Current spec: 0. **Argument for
  0:** ships the refactor without changing the firing rate; users
  opt into stricter skipping by hand. **Argument for 30:** the
  recommender's lowest-confidence picks empirically correlate
  with regret; skipping them by default improves trust. **Decision:
  0 in v1.** Reverting a too-aggressive default that drops live
  firings would damage trust more than the marginal gain.
  ANTS-1895's dry-run data picks the production default in a
  follow-up. **Resolved by design** — no OQ.

- **OQ-2: What confidence does the `commit_intent` override
  carry?** Current spec: 100 (sentinel — see INV-2). **Argument
  for 100:** the override is by definition unambiguous (the user
  typed a VCS verb). **Argument for < 100:** if the override
  ever fires on a false positive, the recommender should label
  it low-confidence so the floor can filter it. **Decision:
  100.** False-positive risk against the 5-alternation regex
  (`commit/push/stage/bump/rebase` —
  `src/modelrecommender.cpp:46-52`):
  - `committee` against `commit(?:s|ted|ting)?`: after `commit`,
    the next char is `t` which is a word char, so
    `(?:\W|$)` fails → no match (verified by tracing the
    regex anchors `(?:^|\W)/?` + stem + `(?:\W|$)`).
  - `pushcart`, `pushpin`: same reason — `(?:\W|$)` requires a
    non-word boundary after the matched alternation; the
    next char is alphanumeric → no match.
  - `staged area` (a noun phrase, not a verb): MATCHES — false
    positive. Acceptable: the user is talking about staging a
    code change, semantically aligned with the override's
    intent.
  - `bumpy road`: against `bump(?:s|ed|ing)?` → `bumpy` has `y`
    after `bump`, which is a word char → `(?:\W|$)` fails → no
    match.
  - `rebase64`: against `rebase(?:s|d|ing)?` → `rebase64` has
    `6` after `rebase`, word char → no match.
  - **One genuine FP class — `stage` as a noun** (e.g. "stage
    left", "stage manager"): unbounded but exceedingly rare in
    a Claude-Code session context. Sentinel 100 is fine; the
    user-facing confidence is in the tooltip only — if the FP
    bothers them they can flip the master toggle.
  **Resolved by design** — no OQ.

- **OQ-3: Does the confidence-too-low blocker fire BEFORE or
  AFTER ticks_target_stable_insufficient?** Current spec: AFTER
  target_equals_current, BEFORE ticks_target_stable_insufficient
  (§ 2.4). **Reason:** confidence is a cheap int comparison; the
  ticks-stable check is a per-tick counter — placing confidence
  earlier means a low-confidence pick never starts accumulating
  ticks_stable, which is the right behaviour (the recommender
  hasn't stabilised on a pick). **Resolved by design** — no OQ.

- **OQ-4: Should `confidence_too_low` near-miss records carry
  the `recommendationConfidence` value in their JSON?** Current
  spec: NO. **Reason:** the ANTS-1894 near-miss record schema
  carries `currentTier`/`recommendedTier`/`blockedBy` but does
  NOT carry the per-signal confidence value. Adding a field
  would extend the schema; v1 keeps the blocker token + the
  existing fields. A follow-up ID can extend the record once
  the trust signal is actively used. **Resolved by design** —
  no OQ.
