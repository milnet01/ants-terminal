# ANTS-1341 — Mode B `in_progress` task abandonment (Bundle F pull 2)

- **Status:** Draft (pre-cold-eyes).
- **Source:** indie-review-2026-05-14 lane-3 H3 finding, logged in
  ROADMAP.md.
- **Lanes:** `claudetasklist` (parser).
- **Kind:** fix.

## 1. Problem

The Mode-B batch-reset shipped in ANTS-1246 (see
`docs/specs/ANTS-1246.md` § 2.e, and as widened in
`docs/specs/ANTS-1407.md` § 2.b to include `deleted`) only triggers
on the NEXT `TaskCreate` event AND only when every prior task in
`out` has reached a terminal status (`completed` or `deleted`
post-ANTS-1407).

A single `in_progress` task without a follow-up `TaskUpdate` blocks
the reset forever. This happens when:

- The CC subagent crashed mid-task.
- A partial network failure dropped the closing TaskUpdate.
- A transcript-replay artefact skipped the final status flip.

Result: across multi-day sessions, `in_progress` tasks pile up in
the tracker indefinitely. The chip's `done/total` ratio
plateaus (`5/13`, `5/15`, `5/17` ...) as fresh bursts cumulatively
append because reset never fires.

## 2. Mechanism

Add a per-task event timestamp; drop `in_progress` tasks that have
not received a status event within `T = 24 h` of the latest event
in the transcript.

### 2.a Add `lastEventAtMs` to `ClaudeTask`

```cpp
// src/claudetasklist.h
struct ClaudeTask {
    QString id;
    QString subject;
    QString description;
    QString activeForm;
    QString status;
    qint64  lastEventAtMs = 0;  // ANTS-1341: epoch ms of the
                                // latest event affecting this task
                                // (TaskCreate timestamp; bumped on
                                // each TaskUpdate). Zero if absent
                                // from the transcript.
};
```

One new field, 8 bytes per task. The existing `m_tasks` cap
(transcript-bounded ≤16 MiB) keeps the worst case well under
1 MiB of struct overhead.

### 2.b Stamp `lastEventAtMs` on each event

In `parseTranscript`:

- **TodoWrite path**: after `out.append(taskFromTodoEntry(...))`,
  set the new entry's `lastEventAtMs` to the event's timestamp.
  TodoWrite is itself an event affecting every entry.
- **TaskCreate path**: set the appended task's `lastEventAtMs`.
- **TaskUpdate path**: when a matching `taskId` is found and the
  status (or any field) is updated, bump the task's
  `lastEventAtMs` to the new event's timestamp.

```cpp
qint64 parseIsoMs(const QString &ts) {
    if (ts.isEmpty()) return 0;
    const QDateTime dt = QDateTime::fromString(ts, Qt::ISODateWithMs);
    return dt.isValid() ? dt.toMSecsSinceEpoch() : 0;
}
```

Pattern matches `src/claudebgtasks.cpp:245-246` (same JSONL,
same format).

`Qt::ISODateWithMs` is strict on the millisecond fraction —
input must be `YYYY-MM-DDTHH:MM:SS.fffZ` (or `.fff±hh:mm`).
`2026-05-16T12:00:00Z` (no fractional seconds) parses but **only
because Qt 6 is lenient by default**; tests should always pass
the explicit `.000Z` form to match real CC transcripts (see
sampling at `~/.claude/projects/**/*.jsonl` — every `timestamp`
field carries `.fffZ`).

**No-timestamp events**: if the JSONL event lacks a `timestamp`
field (or it is empty / unparseable), `parseIsoMs` returns 0.
Tasks then carry `lastEventAtMs = 0`, which INV-7 preserves
unconditionally — the abandonment filter never sees them. This
is fail-soft by design: a malformed timestamp should not drop
user-visible work. New `T-1341-*` test fixtures MUST emit
explicit `timestamp` fields on every JSONL line they construct
(extend the existing `assistantToolUse(...)` helper at
`tests/features/claude_task_list/test_claude_task_list.cpp:67`
to take an optional `ts` parameter).

`#include <algorithm>` for `std::remove_if` is added by
ANTS-1407 § 5.c — do not re-add.

### 2.c Drop stale `in_progress` at end of parse

Track the latest event timestamp seen during the walk
(`latestEventMs`). `latestEventMs` advances on EVERY parsed JSONL
line that carries a valid ISO-8601 `timestamp` field —
**including** sidechain-skipped events and
`isCompactSummary`-skipped events (both filters short-circuit
BEFORE the type/tool dispatch but the timestamp update happens
FIRST, before any filter). This makes `latestEventMs` track real
session progress rather than "events the parser bothered to
process", which would let a long `/compact` pause artificially
suppress the threshold and never abandon stuck tasks.

After the main walk, after the ANTS-1407 deleted-filter pass
(§ 2.c of ANTS-1407), apply the abandonment filter:

```cpp
constexpr qint64 kStaleInProgressMs = 24LL * 3600LL * 1000LL;  // 24 h
if (latestEventMs > 0) {
    const qint64 threshold = latestEventMs - kStaleInProgressMs;
    out.erase(std::remove_if(out.begin(), out.end(),
        [threshold](const ClaudeTask &t) {
            return t.status == QLatin1String("in_progress")
                   && t.lastEventAtMs > 0
                   && t.lastEventAtMs < threshold;
        }),
        out.end());
}
```

Reference time = latest event in the transcript (deterministic,
testable). NOT wall-clock `QDateTime::currentMSecsSinceEpoch()`,
which would make tests flaky against synthetic fixtures.

A task with `lastEventAtMs == 0` (timestamp missing or
malformed) is preserved — fail-soft: an unparseable timestamp
should not drop user-visible work.

### 2.c.i Adjacency to ANTS-1407 filter

Pull 1 (ANTS-1407 § 2.c) installs the `deleted` filter as the
final pass before `return out;`. Pull 2 inserts its abandonment
filter immediately after the deleted filter, both before the
return:

```cpp
// ANTS-1407 § 2.c — deleted filter
out.erase(std::remove_if(out.begin(), out.end(),
    [](const ClaudeTask &t) {
        return t.status == QLatin1String("deleted");
    }),
    out.end());

// ANTS-1341 § 2.c — in_progress abandonment filter
if (latestEventMs > 0) {
    /* ...as above... */
}

return out;
```

Order matters only between these two filters and the return;
they do not interact (a task is one status at a time, never both
`deleted` and `in_progress`). The deleted filter runs first, so
the abandonment filter never sees `(status == "deleted" &&
lastEventAtMs == 0)` — moot intersection.

### 2.d Constant placement

`kStaleInProgressMs` lives in an anonymous namespace at the top
of `claudetasklist.cpp`, alongside `extractIdFromResultBody` and
`taskFromTodoEntry`. Not header-exported — internal threshold.

## 7. Memory budget

- `+8 bytes` per `ClaudeTask` (one `qint64`).
- At the 16 MiB transcript cap with worst-case ~1 KiB / event,
  `m_tasks.size() ≤ ~16 000` → `+128 KiB` worst-case heap.
  Typical sessions carry ≤100 tasks → `+800 bytes`. Negligible.
- One additional `QDateTime` parse per assistant event with a
  tool_use carrying TaskCreate / TaskUpdate / TodoWrite — `O(N)`
  in tool_use count, not in transcript bytes. `QDateTime::fromString`
  is allocation-free for the ISO-8601 fast path; cost ≈
  one date parse per event.
- One `std::remove_if` final pass over `out` — same shape as
  ANTS-1407's deleted filter.

No new caches, no new signals, no heap-resident state outside the
existing `m_tasks` array.

## 8. Re-open conditions

- **24 h is too aggressive** for users running multi-day Plan
  sessions where Claude legitimately leaves a task `in_progress`
  overnight. Re-evaluate the constant; configurable via
  `config.json` if needed.
- **CC starts emitting an explicit "abandoned" status** in
  TaskUpdate. The filter becomes a hot-path redundancy; switch
  to honouring the explicit status.
- **Wall-clock vs latest-event reference time** — if synthetic
  fixtures stop being the primary test surface (e.g. live
  integration tests via QTest), reconsider whether the reference
  time should track real "now" with a settable clock-source.
- **Task with `lastEventAtMs == 0` clogs the UI** — a stream of
  malformed timestamps escapes the abandonment filter. Add a
  warn-log if more than M `in_progress` tasks have zero
  timestamps in a single rescan.

## 9. Out of scope

- Surfacing abandoned tasks anywhere (dialog "show abandoned"
  toggle). Out for v1; the dropped tasks are recoverable from
  the JSONL transcript if a user needs forensic visibility.
- Wall-clock abandonment (every poll, drop tasks idle > 24 h
  relative to "now"). The parser is deterministic per transcript
  state; "now" creep would change the chip count between polls
  with no event having happened.
- Time-based reset of `pending` or `completed` tasks. They have
  legitimate long-lived states (backlog, history) — only
  `in_progress` is the "stuck" symptom.
- Per-tab override of `kStaleInProgressMs`. Single global
  constant for v1.
