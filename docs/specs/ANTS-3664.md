# ANTS-3664 — one finding shape for the doc-lint verbs

**Status:** spec draft, cold-eyes loop 4 folded and ANTS-3677's tail closed
(2026-07-28). § 2.4 was added the same day, when the ANTS-3663/3669 split was
unwound, making this document the family's wire-convention owner — for the
finding element and the conventions, **not** for each verb's envelope (§ 2.4's
closing paragraph draws that line).
**Kind:** refactor.
**Source:** ROADMAP.md ANTS-3664 (in-session-2026-07-27, grounding pass for
ANTS-3660..3663).
**Blocker for:** ANTS-3660 (`doc_dedup`), ANTS-3661 (`doc_symbols`),
ANTS-3662 (`spec_lint`) — each emits this natively rather than inventing a
shape — and ANTS-3663 (`doc_lint`), which composes them.
**Composes with:** ANTS-3601 (`doc_integrity`) and ANTS-3636 (`doc_citations`),
the two producers that already ship and are adapted rather than rewritten.

**Layman:** Before we build three more document checkers, agree one way for a
checker to say "here is a problem, in this file, on this line". Otherwise the
tool that runs them all has to translate five different dialects, forever.

---

## 1. Problem

ANTS-3663 (`doc_lint`) composes five checkers into one findings list. Measured
2026-07-27, there is nothing to compose them *into*:

1. **No shared finding type, serialiser, or aggregator exists.** A search for
   `findingToJson` across `src/` returns zero. Six unrelated `struct Finding`
   declarations do exist — `DocIntegrity::Finding` (`src/docintegrity.h`,
   four fields), `DebtSweep::Finding` (`src/debtsweepengine.h`, seven),
   `AuditEngine::Finding` (`src/auditengine.h`, around twenty, *plus* a
   separate `AuditSummaryFinding` at `src/auditengine.h` that exists
   precisely because the first could not carry what the MCP summary needed),
   `FeedbackFile::Finding` (`src/feedbackfile.h`, beside three more shapes
   in the same header), and a sixth GUI-side.
2. **The closest sibling emits no findings at all.** `DocCitations::check`
   (`src/doccitations.h::check()`) hand-builds a different vocabulary:
   `citations[]` entries carry `doc_line`, `raw` and `status` — not `line`,
   `message` and `kind`. There is no field in common with `DocIntegrity::Finding`
   except the file path.
3. **The only existing "aggregator" normalises by discarding structure.**
   `BriefManifest::docIntegrity` (`src/coldeyesengine.h`) flattens
   `doc_integrity` to a `QStringList` of `"<file>:<line>: [<kind>] <message>"`.
   That works for a brief a human reads and is useless to a verb that must
   filter, count, or fix.

So `doc_lint` written today normalises five vocabularies permanently, and each
of ANTS-3660/3661/3662 adds a sixth, seventh and eighth unless handed a shape
first. The project rule is to extract the shared base *before* the instances,
and the precedent is in this exact lane: `MarkdownScan` (ANTS-3603/3649/3659)
is the one genuinely shared foundation these engines have, and its header
records that it was hoisted the moment a second call-site appeared.

**What this is not.** Not a refactor of `AuditEngine` or `DebtSweep`. Those
serve a different consumer with a different surface (severity, confidence,
blame, AI triage), the Rule of Three has not fired on them, and dragging them in
would turn a small enabling change into a cross-lane migration. § 5 states that
boundary as a decision rather than an omission.

## 2. Surface

### 2.1 The struct

New `src/docfinding.{h,cpp}` in `ants_core_lib`, Qt6::Core-only, beside
`markdownscan.h`:

```cpp
namespace DocFinding {

// One problem found in one document by one checker. Deliberately small: every
// field below has a named consumer in ANTS-3663, and nothing is here "in case".
struct Finding {
    QString verb;        // producer: "doc_integrity", "doc_citations", …
    QString kind;        // rule slug, unique within `verb`: "dead_anchor", …
    QString file;        // project-relative, always set
    int     line = 0;    // 1-based; 0 means "the document", not "line 0"
    QString message;     // one line, no trailing period, no file:line prefix
    bool    autoFixable = false;   // doc_lint's fix path may repair this

    // ANTS-3663 INV-7's tiebreak of last resort: the producer's own 0-based
    // emission index within one run. Set by the producer, never serialised.
    // It is here because the six fields above are all properties of the
    // *problem*, so two findings can agree on every one of them — two
    // `broken_link`s on one line naming the same missing target — and a
    // comparator over those six alone is therefore not a total order. Without
    // this field the composer would have to carry the index out-of-band.
    int     emissionIndex = 0;
};

QJsonObject toJson(const Finding &f);
QJsonArray  toJson(const QList<Finding> &fs);

// counts[verb][kind] -> n, over the WHOLE list it is handed. A consumer that
// caps or filters must call this BEFORE doing so, or its counts describe the
// page rather than the run — the discipline ANTS-3636 INV-42 states for its own
// whole-doc tallies.
QJsonObject countsByVerbAndKind(const QList<Finding> &fs);

}  // namespace DocFinding
```

Seven fields. Six describe the *problem* and are argued below on their own
terms; the seventh, `emissionIndex`, describes only the producer's emission
order and is argued in the struct comment above.

- **`verb`** — `doc_lint` reports which checker fired, and a caller silences one
  checker without silencing a rule name that two checkers might share.
- **`kind`** — the filter `doc_integrity` already exposes as `kinds[]`
  (`src/remotecontrol.cpp::docIntegrityBuildResponse()` narrows findings *and* counts together). Slug,
  not prose, so it is greppable and stable across message rewording.
- **`file`, `line`** — the two things every consumer needs to navigate. `line`
  is 1-based to match `DocIntegrity::Finding` and every citation in the corpus;
  `0` is the whole-document case (a missing required section has no line), which
  is why it is not `-1`: a sentinel that sorts before line 1 keeps
  document-level findings at the top of a file's group for free.
- **`message`** — human-readable, one line. It carries no `file:line` prefix,
  because `BriefManifest`'s flattening adds one and a prefixed message *would*
  double it (`"a.md:3: a.md:3: …"`). No shipping producer does this — all four
  `DocIntegrity` messages are bare — so this is a rule that keeps a defect out,
  not one that fixes an existing defect.
- **`autoFixable`** — `doc_lint`'s fix path (ANTS-3663 § 2.3) is deliberately
  narrow, and this flag is what carries membership of it to the fixer rather
  than having the fixer pattern-match on `kind` strings. That indirection is the
  whole point: a fixer keyed on `kind` breaks the moment a native producer marks
  something else repairable.

  **Its justification is weaker than it first looks, and the weakness is worth
  stating.** The three native producers (ANTS-3660/3661/3662) set it themselves,
  which is the intended shape. But § 2.2 freezes the two shipping producers as
  *adapter-only*, and `DocIntegrity::Finding` has no such field — so its adapter
  must decide from a per-adapter kind list, which is exactly the "knowledge in a
  worse place" this field exists to avoid. That is accepted rather than hidden:
  the alternative is editing a shipped, tested struct for one consumer's
  benefit, and one small list inside one adapter is the cheaper of the two. Every
  *new* producer sets the flag directly, so the list does not grow.

**`emissionIndex` is never serialised — by any verb in this family, in any
array.** It is an in-process ordering aid for ANTS-3663 INV-7's comparator and
means nothing to a consumer: it counts a producer's emissions within one run, so
the same document reviewed with a different `checks[]` set yields different
indices for identical findings. Putting it on the wire would make every response
carry a number that is unstable across calls and meaningless across them.

This settles it for the one place it was reaching the wire: **`doc_lint`'s
`fixed[]` element is `{verb, kind, file, line}`** (ANTS-3663 §§ 2.1, 2.3).
`fixed[]` is a *report of what was repaired*, not a join key back onto
`findings[]` — and it could not be one even with the index, because `toJson`
never emits it, so `findings[]` has no column to join against. A caller that
must correlate the two matches on `{verb, kind, file, line}` and, in the rare
case where that is ambiguous (two findings agreeing on all four), in order:
both arrays are totally ordered by ANTS-3663 INV-7.

**No `severity`.** No verb here produces one today, so every producer would have
to invent one, and an invented severity is worse than none: it reads as
judgement and is guesswork. `kind` is the honest discriminator, and a consumer
that wants ranking can map kinds to a policy it owns. Addable later without
breaking the JSON (an absent key is not a changed key).

### 2.2 What each producer does

| Producer | Change |
|---|---|
| ANTS-3660 `doc_dedup` | emits `Finding` natively |
| ANTS-3661 `doc_symbols` | emits `Finding` natively |
| ANTS-3662 `spec_lint` | emits `Finding` natively |
| `doc_integrity` (ships) | **adapter only** — `DocIntegrity::Finding` → `DocFinding::Finding` in the verb layer. Its own struct, engine and response are untouched; `doc_integrity`'s existing envelope is a shipped contract with tests. |
| `doc_citations` (ships) | **adapter only** — a non-`ok` citation becomes one `Finding` with `kind` from its `status`. Its envelope is untouched for the same reason. |

The adapters live with ANTS-3663, not here: this spec ships the type and its
serialiser, and nothing else changes until a consumer exists. That is what makes
it safely landable ahead of the four.

### 2.3 The engine calling convention

Four rules every checker engine in this family follows. They are stated here,
once, because each of ANTS-3660/3661/3662/3663 previously stated some part of
this and no two agreed — one spec gave no engine signature at all, one gave a
signature that could not perform the resolution its own § 4 costed, and one
required its engine to read a file it also declared it never opens.

**1. The engine never opens the *document*.** The caller reads each file and
hands over its text. That is what makes ANTS-3663's one-open-per-document
guarantee achievable at all: five checkers, one read.

This is not "the engine never touches the filesystem", and the difference is
where the previous contradiction came from. `doc_symbols` walks the *source
tree* to resolve a symbol; that walk is the engine's own and is costed in its
§ 4. The rule constrains who opens the document under review, nothing else.

**2. The per-document signature is:**

```cpp
Result check(const QString &text, const QString &relPath, const Options &opts = {});
```

`doc_dedup` is the deliberate exception, because it compares passages *between*
documents rather than within one: it accumulates per call and scores once at the
end. Its own § 2.6 gives that shape. An exception stated here is a design
choice; an exception discovered at implementation time is this section's absence.

**3. Anything `ants_core_lib` cannot see is injected through `Options`.** The
engines are Qt6::Core-only, so they cannot read the MCP registration tables, the
project's format standard, or resolve the project root for themselves. Each such
input is an `Options` member the verb layer fills before the first call:

| Engine | Injected | Filled by the verb layer from |
|---|---|---|
| `doc_symbols` | `excludedNames` | the MCP verb names and schema argument names |
| `doc_symbols` | `rootCanonical` | the resolved project root, for `SymbolQuery::findDefinition` |
| `spec_lint` | `requiredSections` | the `<!-- required-sections -->` block in the format standard, read once per run |
| `doc_dedup` | the generated-artifact path globs | § 2.4 of its own spec |

The composer forwards each of these — ANTS-3663 § 2.5 carries them on
`DocLint::Options` as pass-throughs and fills them in `cmdDocLint`. A composer
that drops them does not fail: it produces the false-positive flood each
injected input exists to prevent, which is why this is a stated contract rather
than an implementation detail.

**4. `Options` and `Result` are declared in each engine's own header** and shown
in that engine's spec. This section fixes the *convention*; the fields are each
spec's own business.

### 2.4 The family wire conventions

Five rules for how any verb in this family puts a value on the wire. They are
stated here, once, and the five sibling specs **cite them and restate none** —
which is the narrow sense in which this document is the wire-contract owner.

| | Rule |
|---|---|
| **W1** | **Names are snake_case on the wire, camelCase in C++** — `autoFixable` ↔ `auto_fixable`, matching `ScanResult::unterminatedFence` ↔ `unterminated_fence`. INV-3 asserts the key literal so renaming a member cannot silently rename the field. |
| **W2** | **A boolean flag is omitted when false.** ANTS-3636 INV-28's convention. A consumer reads an absent flag as false. |
| **W3** | **A meaningful zero is always emitted.** `line:0` is document scope, not a missing line, so omitting it would make a document-level finding indistinguishable from a malformed one. W2 governs flags; W3 governs values that happen to be falsy. |
| **W4** | **A field that means nothing to a consumer is never serialised at all** — `emissionIndex` is the only one today (§ 2.1). Not "omitted when zero": absent from every array in every verb, always. |
| **W5** | **Tallies are computed over the whole run, before any cap or filter.** A `counts` that describes the returned page rather than the run is the defect ANTS-3636 INV-42 states for its own whole-document tallies. A cap is a page over one array; it never changes another array, another tally, or anything on disk. |

**W2 and W3 are the pair that gets confused**, and the confusion is one-way: a
reader who knows only W2 omits `line:0` and breaks the document-scope case.
Stating them as separate rules beside each other is deliberate.

**Two words in this family carry more than one meaning, and both are load-bearing
in at least two of them.** Renaming the wire keys to dodge the collision would
cost more than the collision does, so the rule is that the *bare* word belongs to
one sense and every other sense is qualified:

- **`candidate`** — bare, in any prose about a `Finding`, means **a finding the
  producer will not assert as a defect** (ANTS-3662: `autoFixable:false`, wording
  that says *candidate*, a human decides). The other two senses are always
  qualified: a **candidate pair**, two passages selected for scoring
  (ANTS-3660 § 2.2), and a **symbol candidate**, a span matching the identifier
  production before resolution (ANTS-3661 § 2.1). Both of those are
  engine-internal and never reach the wire; the first does, which is why it keeps
  the bare word.
- **`check`** — bare means **one of the five checkers**, the sense frozen into
  `checks[]`, `checks_run[]`, `check_stats` and `check_errors`. The engine entry
  point is always written `Type::check()`, with the type. A single test *inside*
  a checker is a **rule**, never a "check" — its slug is the finding's `kind`.

**Which key is which is each verb's own business.** This section fixes how a
value is shaped, not which values exist — a verb's envelope belongs to that
verb's spec, and this document owns no field name outside `Finding` itself. The
distinction matters because this type is Qt6::Core-only and has no idea what an
envelope is: it is an engine type, not a verb contract (§ 7).

## 3. Invariants

- **INV-1** — `toJson` always emits the five value keys, `line` included when it
  is `0`, plus `auto_fixable` only when true. *Test:* a default-constructed
  `Finding` and a fully-populated one → five keys with `line:0` on the first,
  six on the second, and **no `emission_index` on either**. That last clause is
  the one that fails against the obvious serialiser: `emissionIndex` orders
  findings *within* a run and means nothing to a consumer, so emitting it would
  make the wire carry a number that is noise everywhere it lands. `line` is
  deliberately *not* omit-when-false: `0` is a
  meaningful value (document scope), unlike the flags ANTS-3636 INV-28 governs,
  and omitting it would make a document-level finding indistinguishable from a
  malformed one. A consumer reads an absent `auto_fixable` as false; ANTS-3663
  § 2.2 states that on the reading side.
- **INV-2** — `countsByVerbAndKind` counts every finding it is handed, nesting
  `verb` then `kind`. *Test:* three findings across two verbs and three kinds →
  the exact nested shape, with each leaf the true count; plus an empty list →
  `{}`. The counts must be asserted by *value*, not merely by shape: a
  serialiser that emitted every leaf as `1` would pass a shape-only assertion.
- **INV-3** — JSON key names are snake_case (`auto_fixable`), while the C++
  members are camelCase, matching the `ScanResult::unterminatedFence` ↔
  `unterminated_fence` convention this lane already uses. *Test:* assert the
  key literal, so a rename of the member cannot silently rename the wire field.
- **INV-4** — `src/docfinding.h` includes exactly four Qt headers, all QtCore.
  *Test:* an **allow-list** scrape — extract every `#include <Q…>` line from
  `src/docfinding.h` and assert the set is exactly `{QString, QList,
  QJsonObject, QJsonArray}`. Set equality, not membership: an include outside
  the set is the GUI leak this invariant is for, and a *missing* one means the
  struct changed shape without anyone revisiting the claim. A **deny**-list of GUI class names cannot falsify: it
  enumerates `QColor`, `QWidget`, `QPixmap`, `QFont` and passes a header that
  included `QBrush`, and the point of the invariant is the names nobody thought
  to list. The allow-list is finite and closed, the deny-list is neither.

  The compiler is the stronger half and is stated as the primary proof: the test
  bundle links `ants_core_lib`, which links `Qt6::Core` alone, so a GUI include
  fails to build rather than fails an assertion. The scrape exists because a
  build failure names the wrong culprit — it points at the test, not the header.
  It does **not** cover a GUI include acquired *transitively* through another
  Core-only header: a scrape of this header's own lines cannot see one, and the
  compiler is the only proof available for that case.
- **INV-5** — Every checker engine in this family takes its document as text,
  never as a path it opens itself (§ 2.3 rule 1). *Test:* a source-scrape across
  `src/docdedup.cpp`, `src/docsymbols.cpp` and `src/speclint.cpp` for
  `QFile`, `QSaveFile` and `QTextStream` → hits only inside `docsymbols.cpp`
  (whose § 4-costed source-tree walk is the § 2.3 exception), zero in the other
  two. The scrape is the falsifiable half: an engine that quietly re-opens the
  document under review still returns correct findings and passes every
  behavioural test, while breaking ANTS-3663's one-open-per-document guarantee
  invisibly. Naming the exception in the assertion is what stops the row being
  either vacuous or a permanent false alarm.

## 4. RAM / build cost

A `Finding` is four `QString`s, two `int`s and a `bool` — implicitly-shared
strings, so a list of a few thousand is a few hundred KB and is built, serialised
and dropped inside one call. No cache, no cross-call state. The producers'
existing per-run caps (`DocIntegrity::Options::maxDocsPerRun` and friends) bound
the count; this spec adds no cap of its own because it holds nothing across
calls.

**The family build-cost default**, stated here once and cited by the five
sibling specs rather than repeated in each of their § 4s: **one new translation
unit joining `ants_core_lib`, no new external dependency, and one new
feature-test source into an existing bundle's `SOURCES`** — never
`add_executable`, per `tests/features/README.md`. A sibling's § 4 names only its
*deviation* from this (ANTS-3663's fix path adds no TU of its own; ANTS-3660
adds run-scoped state). Six copies of an identical stanza was the highest-scoring
duplicate ANTS-3666 measured across this corpus, and reconciling six copies
leaves six copies to diverge again.

## 5. Out of scope

- **`AuditEngine` and `DebtSweep`.** Different lane, different consumer, ~20
  fields of surface this type deliberately lacks. Converting them is a migration
  with its own risk and no consumer asking for it. Stated so the boundary is a
  decision, not an oversight.
- **Rewriting `doc_integrity`'s or `doc_citations`' response envelopes.** Both
  ship with tests and callers. They gain adapters under ANTS-3663; their own
  contracts are untouched.
- **A severity field** — § 2.1's reasoning. Revisit when a consumer needs to
  rank rather than group.
- **A fix-application API.** ANTS-3663 § 2.3 owns what "auto-fixable" means in
  practice and how a fix is applied; this type only carries the flag.
- **`FeedbackFile::Finding` and the GUI-side sixth shape.** § 1 counts them as
  evidence that the corpus has no shared shape, which they are; neither has a
  consumer in the composed set, so converting them buys nothing here. Named so
  § 1's six existing shapes are each dispositioned: three are replaced by native
  producers, two gain adapters (§ 2.2), and these two are left alone.

rather than dressing up. The invariant that carries real weight is INV-1's
omission rule, which fails against a serialiser that emits every key
unconditionally.

## 7. Cross-doc impact

- **ANTS-3660, ANTS-3661, ANTS-3662** each name this type as their finding shape
  rather than declaring one, and each lists this spec as a blocker.
- **ANTS-3663** gains the two adapters (§ 2.2) and drops any normalisation layer
  it would otherwise have carried.
- **ANTS-3663 § 2.3** (the fix path, ROADMAP item ANTS-3669) is the only
  consumer of `autoFixable`; § 2.1's note on that field's weaker justification
  is written for its benefit.
- **ANTS-3660, ANTS-3661, ANTS-3662, ANTS-3663** each cite § 2.4's wire
  conventions and § 4's build-cost default rather than restating either.
- **`docs/subsystems.md`** — `src/docfinding.{h,cpp}` joins the `ants_core_lib`
  entry beside `markdownscan`.
- **`docs/standards/mcp-tools.md`** — no change. This is an engine type, not a
  verb contract; nothing in the authoring checklist moves.
